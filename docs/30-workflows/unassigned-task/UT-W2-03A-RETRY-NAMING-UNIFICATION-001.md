## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

W2-seq-03a の実装で `handleRetry()` 関数が実装された。この関数は「`formData` を保持し、それ以外の状態をリセットして Step 0 に戻る」という明確な方針を持っている。

しかし、この方針を説明するテスト名・仕様書見出し・コメントで「復帰」「やり直し」「リトライ」という3つの異なる表現が混在している。

### 1.2 問題点・課題

1. **表現ゆれによる読解コスト増大**: テストコードを読む際に、同じ概念（handleRetry）が3種類の日本語で表現されているため、同じ機能を指しているかどうか判断に時間がかかる。

2. **仕様書とテストの不整合リスク**: 仕様書で「リトライ」と書かれているのに、テストで「やり直し」と書かれると、将来の保守者が別の機能と勘違いする可能性がある。

3. **新規テスト追加時の命名迷い**: どの表現を使うべきか迷い、さらなる表現ゆれが生まれるサイクルが続く。

### 1.3 放置した場合の影響

- コードレビュー時に「この `handleRetry` テストと『やり直し』テストは同じものか？」という確認コストが発生する。
- テスト名の不統一が積み重なり、テストスイートの可読性が低下する。

---

## 2. 何を達成するか（What）

### 2.1 目的

`handleRetry` に関するテスト名・仕様書見出し・コメントを統一し、同じ概念が常に同じ言葉で表現されている状態にする。

### 2.2 最終ゴール

- `handleRetry` の動作説明に使う日本語を「リトライ（retry）」に統一する。
  - 「Step 0 に戻る」「やり直し」「復帰」→ 「リトライ（Step 0 復帰）」に統一
- テストの `describe` / `it` ブロック名が `handleRetry` と一致するキーワードを使用している。

### 2.3 スコープ

#### 含むもの

- テストファイル（`SkillCreateWizard.test.tsx`, `SkillCreateWizard.W2-seq-03a.test.tsx`）内の `handleRetry` 関連の `describe` / `it` 名称変更
- 仕様書（`W2-seq-03a-skill-create-wizard/` 配下のファイル）の見出し統一
- コメント内の表現統一

#### 含まないもの

- `handleRetry` の動作ロジック変更
- `handleRetry` の引数・戻り値変更
- 英語表記の変更（`handleRetry` はそのまま）

### 3.3 必要な知識

- Vitest / Jest の `describe` / `it` の命名規則
- プロジェクトのテスト命名パターン（camelCase vs 日本語）

### 3.4 推奨アプローチ

1. **表現の調査**: `grep -r "やり直し\|復帰\|リトライ" apps/desktop/src/renderer/components/skill/` でゆれ箇所を特定する
2. **統一方針の決定**: 「リトライ（Step 0 復帰）」または英語 `retry` に統一する
3. **一括置換**: テストファイル・仕様書の該当箇所を変更する
4. **テスト実行確認**: 名称変更後もテストが正常に動作することを確認する

### 3.5 苦戦箇所（事前想定）

| 苦戦ポイント                         | 詳細                                               | 推奨対策                                           |
