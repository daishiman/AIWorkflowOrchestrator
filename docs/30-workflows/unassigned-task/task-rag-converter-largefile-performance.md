## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

RAG変換システム（ファイル→チャンク変換処理）のパフォーマンス要件が`quality-requirements.md`に定義されている。10KB未満〜1MBまでのファイルサイズについては実測値が取得済みで目標を達成しているが、**1MB〜10MB** および **10MB超** のファイルサイズについては「未検証」と記載されており、性能目標の達成状況が不明である。

| ファイルサイズ | 目標処理時間 | 実測値     | 状態   |
| -------------- | ------------ | ---------- | ------ |
| 10KB未満       | 50ms未満     | 3-12ms     | 達成   |
| 10KB - 100KB   | 200ms未満    | 50-100ms   | 達成   |
| 100KB - 1MB    | 1秒未満      | 400ms      | 達成   |
| 1MB - 10MB     | 5秒未満      | **未検証** | 要検証 |
| 10MB超         | 30秒未満     | **未検証** | 要検証 |

### 1.2 問題点・課題

1. 大容量ファイル（1MB以上）のRAG変換処理時間が不明
2. 同時実行制御（最大5件並列）時の大容量ファイル処理のメモリ消費量が不明
3. 10MB超ファイルでタイムアウト（60秒）を超過する可能性がある
4. 最大コンテンツ長（100,000文字）に達した場合の挙動が未検証

### 1.3 放置した場合の影響

- ユーザーが大容量ファイルをRAG処理した際に予期せぬタイムアウトやメモリ不足が発生する可能性がある
- パフォーマンス劣化基準（目標値の2倍超過で調査開始）の判定ができない
- 品質保証の観点で、仕様に記載されたパフォーマンス要件が未達のまま放置されることになる

## 2. 何を達成するか（What）

### 2.1 目的

1MB〜10MBおよび10MB超のファイルに対してRAG変換処理のパフォーマンスを実測し、目標値との差異を明らかにする。目標未達の場合は最適化方針を提案する。

### 2.2 最終ゴール

- `quality-requirements.md` の「未検証」セルに実測値が記入されている
- 全ファイルサイズ帯で目標値を達成している、または未達の場合は最適化タスクが作成されている
- 大容量ファイル専用のパフォーマンステストスイートが追加されている
- メモリ消費量のベースラインが記録されている

### 2.3 スコープ

#### 含むもの

- 1MB〜10MBファイルのRAG変換パフォーマンス計測
- 10MB超ファイルのRAG変換パフォーマンス計測
- 同時実行（5件並列）時のパフォーマンス計測
- メモリ使用量プロファイリング
- パフォーマンステストスイートの作成
- `quality-requirements.md` への実測値記入

#### 含まないもの

- パフォーマンス最適化の実装（計測結果が未達の場合は別タスクとして起票）
- 新規ファイルフォーマットのサポート追加
- RAG変換ロジック自体の機能変更
- フロントエンドUI側の変更

### 2.4 成果物

| 成果物                          | 説明                                         |
| ------------------------------- | -------------------------------------------- |
| パフォーマンス計測レポート      | ファイルサイズ別処理時間・メモリ消費量の記録 |
| パフォーマンステストスイート    | Vitest ベンチマークテスト                    |
| テストデータ生成スクリプト      | 各サイズ帯のテストファイル生成               |
| quality-requirements.md（更新） | 実測値と状態の更新                           |

## 3. どのように実行するか（How）

### 3.1 前提条件

- RAG変換システム（コンバーター）が正常に動作していること
- テスト環境でNode.js/Electron環境が利用可能であること
- 十分なディスク容量（テストデータ用に最低100MB）があること

### 3.2 依存タスク

| タスクID | タスク名                 | ステータス |
| -------- | ------------------------ | ---------- |
| なし     | 直接的な依存タスクはなし | -          |

### 3.3 必要な知識

- Node.js パフォーマンスプロファイリング（`performance.now()`, `process.memoryUsage()`）
- Vitest ベンチマークテスト（`vitest bench`）
- RAG変換パイプラインのアーキテクチャ理解
- ストリーミング処理とバッファ管理の基礎知識

### 3.4 推奨アプローチ

1. テストデータ生成スクリプトを作成（Markdown, TypeScript, JSON等の各フォーマットで1MB, 5MB, 10MB, 15MB, 20MBを用意）
2. 単一ファイル処理のベンチマークを実行
3. 同時実行（5件並列）のベンチマークを実行
4. メモリ使用量をプロファイリング
5. 結果を集計し、目標値との比較レポートを作成
6. `quality-requirements.md` に実測値を記入

## 4. 実行手順

### Phase構成

本タスクは中規模であり、準備 → 計測 → 分析・報告 の3段階で実施する。

### Phase 1-3: 要件定義・設計・設計レビュー

#### 目的

テスト計画を策定し、計測環境を準備する。

#### 手順

1. RAG変換パイプラインの処理フローを確認
2. テスト対象ファイルフォーマットを決定（Markdown, TypeScript, JSON, HTML, PDF）
3. テストデータ生成スクリプトを設計
4. パフォーマンス計測のメトリクス定義（処理時間、メモリ使用量、CPU使用率）
5. テスト計画をレビュー

#### 成果物

- テスト計画書
- テストデータ生成スクリプト設計

#### 完了条件

- テスト対象フォーマットとサイズ帯が決定している
- メトリクス定義が明確

### Phase 4-6: テスト作成・実装・テスト拡充

#### 目的

テストデータ生成、ベンチマークテスト実装、計測実行。

#### 手順

1. テストデータ生成スクリプトを実装
2. 各サイズ帯のテストデータを生成:
   - 1MB（Markdown, TypeScript, JSON）
   - 5MB（Markdown, TypeScript）
   - 10MB（Markdown）
   - 15MB（Markdown）
   - 20MB（Markdown）
3. 単一ファイル処理ベンチマークテストを実装
4. 5件並列処理ベンチマークテストを実装
5. メモリプロファイリングテストを実装
6. 全ベンチマークを実行し結果を記録

#### 成果物

- テストデータ生成スクリプト
- ベンチマークテストスイート
- 計測結果ログ

#### 完了条件

- 全サイズ帯で計測結果が取得できている
- メモリ使用量が記録されている
- 5件並列時の結果が取得できている

### Phase 7-9: 分析・品質保証・ドキュメント

#### 目的

計測結果を分析し、レポートを作成する。

#### 手順

1. 計測結果を集計し、目標値と比較
2. 目標未達の場合はボトルネックを特定
3. パフォーマンスレポートを作成
4. `quality-requirements.md` に実測値を記入
5. 目標未達の場合は最適化タスクを別途起票

#### 成果物

- パフォーマンス計測レポート
- quality-requirements.md（更新）
- 最適化タスク仕様書（必要な場合）

#### 完了条件

- 全サイズ帯の実測値が記録されている
- quality-requirements.md が更新されている

## 6. 検証方法

### テストケース

| TC-ID  | テスト内容                     | 期待結果                     |
| ------ | ------------------------------ | ---------------------------- |
| TC-001 | 1MB Markdown変換               | 処理時間 < 5秒               |
| TC-002 | 5MB Markdown変換               | 処理時間 < 5秒               |
| TC-003 | 10MB Markdown変換              | 処理時間 < 5秒               |
| TC-004 | 15MB Markdown変換              | 処理時間 < 30秒              |
| TC-005 | 20MB Markdown変換              | 処理時間 < 30秒              |
| TC-006 | 5件並列（各1MB）               | 全件完了、メモリ < 1GB       |
| TC-007 | 5件並列（各5MB）               | 全件完了、メモリ < 1GB       |
| TC-008 | 100,000文字超コンテンツ        | 適切にトランケートされる     |
| TC-009 | タイムアウト（60秒）超過ケース | タイムアウトエラーが返される |

### 検証手順

1. `pnpm --filter @repo/shared vitest bench` でベンチマーク実行
2. 計測結果を `quality-requirements.md` の目標値と比較
3. メモリ使用量が1GBを超えないことを確認
4. 処理時間が目標値の2倍を超えるケースがないことを確認

## 7. リスクと対策

| リスク                               | 影響度 | 発生確率 | 対策                                                 |
| ------------------------------------ | ------ | -------- | ---------------------------------------------------- |
| 10MB超ファイルで60秒タイムアウト超過 | 高     | 中       | ストリーミング処理化、タイムアウト値の見直し         |
| メモリ使用量が1GBを超過              | 高     | 中       | チャンク単位処理、メモリプール導入                   |
| テストデータ生成に時間がかかる       | 低     | 低       | テストデータをgitignoreしキャッシュ利用              |
| CI環境でパフォーマンス結果がブレる   | 中     | 高       | 相対的な比較（目標値の倍率）で判定、統計的手法を使用 |
