## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-AUTH-CALLBACK-001（OAuth PKCE移行）のPhase 1で、トークンリフレッシュ戦略の変更はスコープ外として除外された。PKCE移行によりAuthorization Code Flow + リフレッシュトークンの基盤が整ったが、現在のリフレッシュ戦略はSupabase SDKのデフォルト動作に依存しており、エッジケース（オフライン状態、トークン期限切れ直前のAPI呼び出し等）に最適化されていない。

### 1.2 問題点・課題

**現在のリフレッシュ動作**:

| 項目                     | 現状                           | 理想状態                             |
| ------------------------ | ------------------------------ | ------------------------------------ |
| リフレッシュトリガー     | Supabase SDKの自動リフレッシュ | プロアクティブリフレッシュ           |
| オフライン時の動作       | エラー発生                     | キューイング＋復帰時自動リフレッシュ |
| リフレッシュ失敗時       | セッション切断                 | リトライ＋ユーザー通知               |
| トークン期限切れ直前     | API呼び出し失敗の可能性        | 事前リフレッシュで防止               |
| リフレッシュトークン保存 | safeStorage暗号化              | safeStorage暗号化（維持）            |

### 1.3 放置した場合の影響

| 影響領域     | 影響度 | 説明                                             |
| ------------ | ------ | ------------------------------------------------ |
| ユーザー体験 | Medium | 突然のセッション切断でデータ喪失のリスク         |
| 信頼性       | Medium | ネットワーク不安定時にトークンリフレッシュが失敗 |
| データ整合性 | Low    | トークン期限切れ時のAPI呼び出し失敗で操作が中断  |

## 2. 何を達成するか（What）

### 2.1 目的

堅牢なトークンリフレッシュ戦略を実装し、セッション維持の信頼性を向上させる。

### 2.2 最終ゴール

- プロアクティブリフレッシュ（期限切れ5分前に自動リフレッシュ）
- オフライン復帰時の自動リフレッシュ
- リフレッシュ失敗時のリトライ（指数バックオフ）
- リフレッシュ不可時のユーザー通知（再ログイン要求）
- リフレッシュトークンローテーション対応

### 2.3 スコープ

#### 含むもの

- `TokenRefreshManager` モジュール（リフレッシュ戦略制御）
- プロアクティブリフレッシュスケジューラ
- オフライン検出＋復帰時リフレッシュ
- リトライロジック（指数バックオフ、最大3回）
- リフレッシュトークンローテーション対応
- ユニットテスト・統合テスト

#### 含まないもの

- セッション管理の全面改修
- マルチデバイス間のセッション同期
- トークン暗号化方式の変更（safeStorage維持）

## 3. どのように実行するか（How）

### 3.1 前提条件

- [ ] TASK-AUTH-CALLBACK-001（PKCE移行）が完了していること
- [ ] リフレッシュトークンが`safeStorage`で暗号化保存されていること
- [ ] Supabase Auth SDKの`refreshSession()` APIが利用可能であること

### 3.2 依存タスク

**先に完了している必要があるタスク**:

- TASK-AUTH-CALLBACK-001: PKCE移行（完了済み）

**同時実施可能なタスク**:

- task-auth-oauth-provider-expansion（OAuthプロバイダー追加）

### 3.3 必要な知識・スキル

- OAuth 2.0 リフレッシュトークン仕様（RFC 6749 Section 6）
- Supabase Auth SDK `refreshSession()` API
- Electron Main Process タイマー管理
- ネットワーク状態監視（`navigator.onLine` / Electron `net` モジュール）
- 指数バックオフアルゴリズム

### 3.4 推奨アプローチ

1. **プロアクティブリフレッシュ**: `setInterval` でトークン期限の5分前にリフレッシュ実行
2. **ネットワーク監視**: Electron `net.isOnline()` + `online`/`offline` イベントで検出
3. **リトライ戦略**: 指数バックオフ（1秒→2秒→4秒）、最大3回、リトライ可能エラーのみ
4. **トークンローテーション**: リフレッシュ応答で新しいリフレッシュトークンが返された場合、即座に`safeStorage`を更新

### 3.5 実装上の注意点（TASK-AUTH-CALLBACK-001の知見）

| 課題                                    | 原因                                    | 解決策                           | 本タスクへの適用                                                                                                        |
| --------------------------------------- | --------------------------------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Zustandリスナー二重登録                 | React StrictModeの2回実行               | モジュールスコープフラグでガード | TokenRefreshManagerのインターバルタイマーも二重起動を防止すること。`setInterval`を`clearInterval`で確実にクリーンアップ |
| IPC経由でエラー情報がRendererに届かない | ペイロードにerrorフィールドが未定義     | 構造化エラーフィールドを追加     | リフレッシュ失敗時もIPC経由で`{ error, errorCode }`をRendererに通知                                                     |
| PKCEバリデーション定数のデッドコード化  | テスト用定数と実装用定数の乖離          | 共有定数ファイルで一元管理       | リフレッシュ間隔、リトライ回数、バックオフ係数などの定数を`auth/constants.ts`で一元管理                                 |
| ルールファイルと仕様書の同期ギャップ    | 仕様書更新後にrulesファイル更新を忘れた | 3箇所同時更新                    | リフレッシュ戦略の設計判断を`architecture-auth-security.md`に追記、rulesも同時更新                                      |

**参照先**:

- `skill-creator/references/patterns.md` - 関連パターン参照

## 6. 検証方法

### ユニットテスト

1. プロアクティブリフレッシュのタイマー起動
2. トークン期限切れ5分前でリフレッシュ実行
3. リフレッシュ成功時のトークン更新
4. リフレッシュ失敗時のリトライ（1回目）
5. リフレッシュ失敗時のリトライ（3回で打ち切り）
6. 指数バックオフの間隔確認
7. オフライン検出
8. オフライン→オンライン復帰時のリフレッシュ
9. トークンローテーション（新リフレッシュトークン保存）
10. リフレッシュ不可時のIPC通知
11. 複数タイマーの二重起動防止
12. クリーンアップ（アプリ終了時のタイマー破棄）

### 手動テスト

| No  | カテゴリ | テスト項目                   | 操作手順                             | 期待結果                         |
| --- | -------- | ---------------------------- | ------------------------------------ | -------------------------------- |
| 1   | 正常系   | プロアクティブリフレッシュ   | ログイン後、トークン期限切れまで待機 | 期限切れ前に自動リフレッシュ     |
| 2   | 正常系   | オフライン復帰               | ネットワーク切断→再接続              | 自動リフレッシュでセッション維持 |
| 3   | 異常系   | リフレッシュ失敗             | サーバー停止中にリフレッシュ試行     | リトライ後、再ログイン通知表示   |
| 4   | 異常系   | 期限切れリフレッシュトークン | リフレッシュトークンの期限切れを待つ | 再ログイン要求UIが表示される     |

## 7. リスクと対策

| リスク                                 | 影響度 | 発生確率 | 対策                                           |
| -------------------------------------- | ------ | -------- | ---------------------------------------------- |
| リフレッシュタイマーのメモリリーク     | Medium | Medium   | `clearInterval` + アプリ終了時のクリーンアップ |
| ネットワーク状態誤判定（VPN等）        | Low    | Medium   | 実際のAPI呼び出しで到達性を確認                |
| リフレッシュとAPIコールの競合状態      | High   | Medium   | リフレッシュ中はAPIコールをキューイング        |
| Supabase側のリフレッシュトークン無効化 | Medium | Low      | エラーコード判定で再ログインフローに誘導       |

## 9. 備考

### TASK-AUTH-CALLBACK-001の設計資産活用

- **safeStorage暗号化パターン**: リフレッシュトークンの暗号化保存は既に実装済み。ローテーション時は同パターンで上書き
- **AuthFlowOrchestrator**: リフレッシュフローもOrchestrator経由で統一管理可能
- **IPC経由エラー伝達**: `{ error, errorCode }` パターンでリフレッシュ失敗もRendererに通知

### 苦戦ポイントの事前対策

1. **タイマー二重起動防止**: `TokenRefreshManager` はシングルトンパターンまたはモジュールスコープフラグでインターバルの二重起動を防止
2. **テストでのタイマー制御**: `vi.useFakeTimers()` を使用し、5分間のプロアクティブリフレッシュを数ミリ秒でテスト。`beforeEach`でリセットを忘れないこと（P9: モジュールスコープ変数リーク参照）
3. **エラーカテゴリ判定**: ネットワークエラー（3000番台）はリトライ可能、認証エラー（2000番台: リフレッシュトークン無効）はリトライ不可で即座に再ログインフローに遷移
