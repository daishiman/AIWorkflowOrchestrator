## 目的

`aiworkflow-requirements` の `task-workflow-backlog.md` において、同一タスクのエントリが
複数行に分散する重複問題を防ぐための明文化されたガイドラインを整備し、
追跡・レビュー・完了確認のコストを削減する。

---

## 背景

Phase-12 の skill-feedback-report レビューで、`task-workflow-backlog.md` 内の
UT-RT-06 エントリが行 626 と行 629 に分散していることが指摘された。

重複エントリが発生する主な原因は以下のとおりである:

| 原因                         | 説明                                                                             |
| ---------------------------- | -------------------------------------------------------------------------------- |
| 並行 worktree からの独立追加 | 異なるブランチ・worktree から同じタスクの進捗エントリが独立して追加される        |
| マージ時の重複チェック欠如   | マージ時に既存エントリとの重複確認が行われない                                   |
| 更新ルールの未明文化         | backlog 更新ルールが存在しないため、既存エントリの存在に気づかずに追記してしまう |

この状態では、タスクの「現在の状態」がどの行を正とするのか判断できず、
追跡・レビュー・完了確認のコストが増大する。

---

## スコープ

### 含むもの

- `task-workflow-backlog.md` の重複エントリ統合ルールの文書化
- 重複検出のための grep / スクリプト手順
- backlog 更新時の確認手順（pre-merge チェックリスト等）

### 含まないもの

- backlog ファイル形式そのものの再設計
- CI/CD パイプラインへの自動重複チェックの組み込み（別タスク検討）

## 4. 実行手順

1. `task-workflow-backlog.md` の現状を確認し、重複エントリの件数と該当タスクIDを列挙する

   ```bash
   # タスクIDの出現回数を集計して重複を発見する
   grep -oP '(?<=\|)\s*(UT-[^\s|]+|TASK-[^\s|]+|task-[^\s|]+)' \
     references/task-workflow-backlog.md \
     | tr -d ' ' | sort | uniq -c | sort -rn | head -30
   ```

2. 重複エントリをリストアップし、統合ルールに基づいて「正とするエントリ」を決定する

   統合優先順位:
   1. より新しいタイムスタンプを持つエントリ
   2. より詳細な状態情報（completed / in-progress / blocked 等）を持つエントリ
   3. 判断できない場合は、下方（後に追加された）エントリを正とする

3. 重複エントリを統合し、古いエントリを削除する（削除前に `git diff` で確認）

4. ガイドラインドキュメントを作成し、`references/task-workflow-backlog-guide.md` または
   `docs/30-workflows/backlog-management-guide.md` に配置する

5. `.claude/rules/05-task-execution.md` の backlog 更新手順に
   「既存エントリの存在確認」ステップを追加する

6. `pnpm lint` と `pnpm typecheck` を実行して変更に問題がないことを確認する
   （対象がドキュメントのみの場合はスキップ可）

## 6. 検証方法

```bash
# task-workflow-backlog.md の重複エントリがゼロであることを確認
grep -oP '(?<=\|)\s*(UT-[^\s|]+|TASK-[^\s|]+|task-[^\s|]+)' \
  references/task-workflow-backlog.md | tr -d ' ' | sort | uniq -d
# 出力がゼロ行であれば重複なし
```

ガイドラインドキュメントのレビュー:

- 統合ルール（新旧の優先順位）が明示されていること
- backlog 更新手順に重複確認ステップが存在すること

## 7. リスクと対策

| リスク                                        | 影響度 | 対策                                                                              |
| --------------------------------------------- | ------ | --------------------------------------------------------------------------------- |
| 統合時に誤って必要なエントリを削除してしまう  | 中     | 統合前に `git stash` または別ブランチで作業し、差分を確認してからコミット         |
| ガイドラインが実際の運用に合わず形骸化する    | 低     | ガイドライン適用後の最初の backlog 更新で手順に沿って実施し、フィードバックを反映 |
| worktree 運用を前提としたフローに対応できない | 中     | worktree 固有の注意事項（同一ファイルの並行更新リスク）をガイドラインに明記する   |
