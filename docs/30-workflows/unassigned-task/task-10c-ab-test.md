## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-9CのPromptOptimizerには`generateVariants()`メソッドがあり、同じプロンプトに対して複数のバリアント（言い換え）を生成できる。しかし、それらのバリアントを実際にテストして効果を比較する機能は未実装である。

### 1.2 問題点・課題

- 生成されたバリアントのうち、どれが最も効果的かを客観的に判断できない
- プロンプト改善の効果を定量的に測定できない
- 「なんとなく良さそう」という主観的判断に頼っている
- 統計的に有意な差を検出する手段がない

### 1.3 放置した場合の影響

- プロンプト最適化の効果が不明確なまま
- 改善サイクルが科学的でなくなる
- 最適なプロンプトを見逃す可能性がある

---

## 2. 何を達成するか（What）

### 2.1 目的

複数のプロンプトバリアントを実際のタスクで実行し、結果を比較して最適なプロンプトを選定できるようにする。

### 2.2 最終ゴール

- 複数バリアントを同一タスクで実行できる
- 実行結果（成功率、品質スコア、実行時間）を収集できる
- 統計的有意差を計算して表示できる
- 最適なバリアントを自動推奨できる

### 2.3 スコープ

#### 含むもの

- ABTestRunner サービス（テスト実行エンジン）
- テスト結果の収集・保存（DB永続化）
- 結果比較UI
- 統計的有意差の計算

#### 含まないもの

- リアルタイムA/Bテスト（本番環境でのトラフィック分割）
- 外部サービスとの連携
- 自動プロンプト置換機能

### 3.5 実装課題と解決策（TASK-9Cからの学び）

TASK-9Cで発生した実装課題と解決パターンを、本タスク実装時に参照する。

| 課題                    | 解決策                                          | 本タスクへの適用                                    |
| ----------------------- | ----------------------------------------------- | --------------------------------------------------- |
| SDK接続エラー時の処理   | `tryAgentSdkWithFallback<T>(fn, fallback)`      | テスト実行中のSDKエラーを記録し、エラー率を指標化   |
| queryFn DI パターン     | SDK呼び出しをパラメータ化し、テストでモック注入 | ABTestRunnerでSDK呼び出しをDI可能に設計             |
| ESModule モッキング制約 | SDK本体をモックせず `queryFn` を注入してテスト  | Vitest + DI でSDK非依存のユニットテストを実現       |
| スキル名バリデーション  | 禁止文字リスト `<>:"\|?*` でサニタイズ          | テスト名/バリアント名にも同様のバリデーションを適用 |

#### 参照パターンの詳細

**queryFn DI パターンのA/Bテストへの応用**: ABTestRunnerのコンストラクタで `queryFn` を受け取り、テスト時はモック関数を注入する。これにより、実際のClaude API呼び出しなしで統計計算ロジックをテストできる。

**エラー率の指標化**: TASK-9CのGraceful Fallbackパターンを拡張し、各バリアントのエラー発生率も統計指標として収集する。エラーが多いプロンプトは品質が低いと判断できる。

**テスト名バリデーション**: A/Bテスト結果をファイル/DBに保存する際、テスト名にファイルパスで使用できない文字が含まれないよう、TASK-9Cと同じバリデーションパターンを適用する。

1. テストプロンプトを用意
2. バリアントを生成
3. A/Bテストを開始
4. 結果を確認
5. 統計的有意差を確認
