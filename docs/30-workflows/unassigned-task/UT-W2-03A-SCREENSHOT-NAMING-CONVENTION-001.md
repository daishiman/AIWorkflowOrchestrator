## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

W2-seq-03a の Phase 11 手動テストでは、`skillPath` 表示確認や外部連携チェックリスト確認のスクリーンショットが取得された。これらは重要な品質証跡となる。

現状、スクリーンショットの命名は各タスクで独自に決められており（例: `ss-01-skillpath.png`, `TC-11-01-skillpath.png` など）、統一された命名規則が存在しない。

### 1.2 問題点・課題

1. **再検証時の証跡追跡困難**: 命名規則が不明確なため、どの手動テストケースに対応するスクリーンショットかを把握するのに時間がかかる。

2. **複数タスク間での証跡比較が困難**: タスクごとに異なる命名を使うと、同じ機能を異なるタスクで検証した際の証跡を横断的に比較できない。

3. **自動化への障壁**: 将来的に VRT（Visual Regression Test）を導入する際、証跡ファイルの命名が統一されていないと自動化スクリプトの作成が難しくなる。

### 1.3 放置した場合の影響

- Phase 11 手動テストのたびに命名規則を決める時間が発生する。
- 証跡ファイルが増えるにつれて管理コストが増大する。
- VRT 導入時に命名の統一作業が必要になる。

## 2. 何を達成するか（What）

### 2.1 目的

Phase 11 手動テストのスクリーンショット命名規則を明文化し、全タスクで統一された命名を使用できるようにする。

### 2.2 最終ゴール

- `TC-{phase}-{sequential_number}-{feature}-{state}.png` 形式の命名規則を文書化する。
- 命名規則を `docs/30-workflows/unassigned-task/README.md` または専用のガイドラインファイルに記載する。
- W2-seq-03a の Phase 11 スクリーンショットが命名規則に準拠した名前に変更されている。

### 2.3 スコープ

#### 含むもの

- スクリーンショット命名規則の定義・文書化
- W2-seq-03a Phase 11 スクリーンショットの命名規則準拠確認（必要に応じてリネーム）
- 将来タスクへの適用ガイドラインの記載

#### 含まないもの

- VRT の導入（別タスク）
- 既存タスク（W2-seq-03a 以外）のスクリーンショット一括リネーム（スコープ外）
- 自動スクリーンショット取得スクリプトの実装（別タスク）

### 2.4 成果物

| 種別     | ファイルパス                                           | 変更内容                                 |
| -------- | ------------------------------------------------------ | ---------------------------------------- |
| 新規作成 | `docs/30-workflows/phase11-screenshot-naming-guide.md` | 命名規則ガイドライン                     |

## 3. どのように実行するか（How）

### 3.1 前提条件

- W2-seq-03a Phase 11 が完了していること（スクリーンショット取得済み）

### 3.2 依存タスク

| タスクID   | 状態 | 内容                                |
| ---------- | ---- | ----------------------------------- |
| W2-seq-03a | 完了 | Phase 11 スクリーンショットの取得元 |

### 3.3 必要な知識

- プロジェクトの手動テスト実施プロセス（Phase 11 の概要）
- ファイル命名のベストプラクティス（kebab-case, 体系的な連番）

### 3.4 推奨アプローチ

**命名規則案:**

```
TC-{phase_number}-{test_case_number}-{feature_key}-{state_key}.png
```

| 部位             | 形式                | 例                                       |
| ---------------- | ------------------- | ---------------------------------------- |
| phase_number     | 2桁ゼロ埋め         | `11`                                     |
| test_case_number | 2桁ゼロ埋め         | `01`, `02`                               |
| feature_key      | kebab-case の機能名 | `skill-path`, `external-integration`     |
| state_key        | kebab-case の状態名 | `initial`, `filled`, `error`, `complete` |

**例:**

```
TC-11-01-skill-path-display.png
TC-11-02-external-integration-checklist.png
TC-11-03-complete-step-with-retry.png
```

### 3.5 苦戦箇所（事前想定）

| 苦戦ポイント                   | 詳細                                                   | 推奨対策                                                               |
| ------------------------------ | ------------------------------------------------------ | ---------------------------------------------------------------------- |
| feature_key の粒度が曖昧       | 機能名が細かすぎると長くなり、大まかすぎると識別困難   | 主要 UI 要素を基準に `skill-path`, `external-integration` レベルで統一 |
| 既存スクリーンショットとの整合 | リネームすると過去の PR やドキュメントへの参照が切れる | リネームは W2-seq-03a のもののみに限定し、他は将来対応                 |
