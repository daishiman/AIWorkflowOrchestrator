## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

`W1-par-02a-skill-info-step-2`（SkillInfoStep 実装）の Phase 12 未タスク検出において、
以下の改善候補が記録された。

現在の `SkillInfoStep.tsx` では、目的フィールド（purpose）のバリデーション最小文字数が
ハードコードされている：

```typescript
// 現在の実装（ハードコード）
purpose.trim().length >= 10;
```

この `10` という値は仕様書のどこにも外部定義されておらず、将来の要件変更（例：最小文字数を
5文字に変更したい、または20文字にしたい）があった際にコード内の全参照箇所を手動で探す
必要がある。

### 1.2 問題点・課題

1. **マジックナンバーの存在**: `10` という定数がコード内にハードコードされており、
   命名された定数として管理されていない。コードを読む際に「なぜ10なのか」が
   コメントなしには分からない。

2. **テストとの乖離リスク**: テストコードが同じ `10` という値に依存している場合、
   変更時にテストと実装の同期が漏れるリスクがある。

3. **将来の要件変更コスト**: スキル作成仕様の変更（例：最小文字数の調整）が
   コードの直接修正を必要とし、意図せぬ場所の変更見落としが発生しやすい。

### 1.3 放置した場合の影響

- バリデーション値の変更時にコード内の全参照を手動で探す必要がある
- テストとの同期漏れによる回帰リスク
- `10` という値の意味がコードを読む開発者に伝わらない（ドキュメント負債）

---

## 2. 何を達成するか（What）

### 2.1 目的

`SkillInfoStep.tsx` のバリデーション最小文字数を命名された定数として外部化し、
コードの可読性・保守性・テスト容易性を向上させる。

### 2.2 最終ゴール

- `SKILL_INFO_VALIDATION` または同等の定数オブジェクトとして最小文字数を定義する
- バリデーションロジックが定数を参照する形に修正される
- テストコードも同定数を参照するため、変更時の同期が保証される

### 2.3 スコープ

#### 含むもの

- `SkillInfoStep.tsx` 内のバリデーション定数の命名・外部化
- バリデーション定数を参照するテストコードの修正
- 定数ファイルまたは `SkillInfoStep.tsx` 先頭への定数定義（規模に応じて判断）

#### 含まないもの

- バリデーション最小文字数の値自体の変更（`10` のまま維持）
- バリデーションロジックの仕様変更
- UI 表示（エラーメッセージ）の変更
- 他フィールド（スキル名）のバリデーション変更

| 種別 | ファイル                                                                                               |
| ---- | ------------------------------------------------------------------------------------------------------ |
| 修正 | `apps/desktop/src/renderer/components/skill/wizard/SkillInfoStep.tsx`（定数参照に変更）                |

## 3. どのように実行するか（How）

### 3.1 前提条件

- `W1-par-02a-skill-info-step-2` が Phase 12 完了済みであること
- `apps/desktop/src/renderer/components/skill/wizard/SkillInfoStep.tsx` が存在すること

### 3.2 依存タスク

| タスクID                               | 状態 | 内容                                               |
| -------------------------------------- | ---- | -------------------------------------------------- |
| UT-SKILL-WIZARD-W1-SKILL-INFO-STEP-001 | 完了 | SkillInfoStep.tsx 実装（定数外部化の対象ファイル） |

### 3.3 推奨アプローチ

1. **定数定義の場所を決定する**: `SkillInfoStep.tsx` の先頭に `const MIN_PURPOSE_LENGTH = 10;`
   として定義するか、または `wizard/constants.ts` のような共有定数ファイルに追加するかを判断する。
   規模が小さいため、`SkillInfoStep.tsx` 内での定義を推奨（YAGNI 原則）。

2. **バリデーション箇所を定数参照に変更する**: `purpose.trim().length >= 10` を
   `purpose.trim().length >= MIN_PURPOSE_LENGTH` に変更する。

3. **テストを定数参照に修正する**: テストコード内で `10` という値を直接使用している箇所を
   定数（`import { MIN_PURPOSE_LENGTH }` または同等）に変更する。

4. **エラーメッセージも定数参照を検討する**: エラーメッセージに `10文字以上` などと
   ハードコードされている場合、同定数でテンプレートリテラルを使用する。

## 9. 備考

### 苦戦箇所【記入必須】

#### 苦戦箇所 1: W1-par-02a 実装時に検出されたマジックナンバー問題

| 項目     | 内容                                                                                          |
| -------- | --------------------------------------------------------------------------------------------- |
| 症状     | `purpose.trim().length >= 10` の `10` がコード内にハードコードされており、意味が不明瞭        |
| 原因     | W1-par-02a の実装スコープを「動作するコンポーネント」に絞ったため、定数外部化が後回しになった |
| 対応     | Phase 12 未タスク検出で記録し、本タスクとして独立させた                                       |
| 再発防止 | Phase 1（要件定義）の段階でバリデーション値を定数化する方針を明記し、実装時に即座に適用する   |

### 補足事項

- 本タスクは機能追加ではなく品質改善（リファクタリング）である
- バリデーション値（`10`）を変更するのは本タスクのスコープ外
- `UT-SKILL-WIZARD-CATEGORY-UI-ICON-001` と同じファイルが対象のため、並列実施時はコンフリクトに注意
