## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-9Cで実装したスキル改善機能は、改善実行時にバックアップを作成するのみで、改善履歴（いつ、何を、どう改善したか）は永続化されていない。

### 1.2 問題点・課題

- 過去の改善内容を振り返ることができない
- 改善の効果を時系列で追跡できない
- 同じ改善を重複して適用してしまう可能性がある
- スキル品質の変遷を可視化できない

### 1.3 放置した場合の影響

- スキル改善のPDCAサイクルが回らない
- 「どの改善が効果的だったか」の知見が蓄積されない
- 長期的なスキル品質管理が困難

---

## 2. 何を達成するか（What）

### 2.1 目的

スキル改善の履歴をデータベースに永続化し、履歴の表示・検索・比較を可能にする。

### 2.2 最終ゴール

- 改善実行時に履歴がDBに自動保存される
- 履歴一覧を時系列で閲覧できる
- 改善前後の差分を比較できる
- スキル別・期間別でフィルタリングできる

### 2.3 スコープ

#### 含むもの

- ImprovementHistory エンティティ定義
- improvement_history テーブル追加（Drizzle Migration）
- ImprovementHistoryService 実装
- 履歴表示UI

#### 含まないもの

- 改善の自動ロールバック機能（別タスク候補）
- 改善効果の統計分析（TASK-10C連携）
- 外部エクスポート機能

### 3.5 実装課題と解決策（TASK-9Cからの学び）

TASK-9Cで発生した実装課題と解決パターンを、本タスク実装時に参照する。

| 課題                     | 解決策                                         | 本タスクへの適用                                 |
| ------------------------ | ---------------------------------------------- | ------------------------------------------------ |
| バックアップファイル管理 | 改善前に自動バックアップ、エラー時は自動復元   | 履歴レコードにバックアップパスを紐付けて保存     |
| 差分データの永続化       | 改善前後の全文を保存し、差分は表示時に動的計算 | beforeContent/afterContentカラムをテーブルに追加 |
| 大量履歴のパフォーマンス | インデックス設計、ページネーション             | skillName, createdAtにインデックス追加           |
| ESModule モッキング制約  | `queryFn` DI パターンでSDKをモックせず回避     | サービステストでRepository層をモック             |

#### 参照パターンの詳細

**バックアップファイル管理パターン**: TASK-9CのSkillImproverは `{skillPath}.backup.{timestamp}` 形式でバックアップを作成する。履歴サービスはこのパスを記録し、ロールバック機能実装時に活用可能。

**差分表示の設計**: 差分アルゴリズム（diff-match-patch等）は表示時に計算し、DBには全文を保存する。これによりストレージ効率と柔軟性のバランスを取る。
