## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-FIX-13-1（deprecatedプロパティ正式移行）において、`Skill.lastUpdated` を `Skill.lastModified` に移行する際、コードベース内に `lastUpdated` という名前を持つプロパティが複数の型に存在することが判明した。しかし、これらは異なるドメインの異なる型であり、日時の表現形式も統一されていなかった。

### 1.2 問題点・課題

現在、プロジェクト内の日時表現が以下の3パターンで混在している：

| 型                  | プロパティ     | 表現形式 | 理由                                   |
| ------------------- | -------------- | -------- | -------------------------------------- |
| `Skill`             | `lastModified` | `Date`   | TypeScript ネイティブ操作に最適        |
| `SkillImportConfig` | `lastUpdated`  | `string` | electron-store JSON シリアライズ互換   |
| `StorageMetadata`   | `lastUpdated`  | `number` | Unix タイムスタンプ（DB/IPC 効率優先） |
| `StorageStats`      | `lastUpdated`  | `number` | Unix タイムスタンプ（DB/IPC 効率優先） |
| `ExecutionInfo`     | `startedAt`    | `number` | Unix タイムスタンプ                    |
| `SkillRunResult`    | `startedAt`    | `Date`   | TypeScript ネイティブ操作に最適        |

この混在は意図的な設計判断に基づくものだが、その理由がドキュメント化されていない。

### 1.3 放置した場合の影響

- 新規開発者が日時プロパティの型を選択する際に一貫性のない判断をする
- TASK-FIX-13-1 のように `lastUpdated` の grep 結果から誤ったスコープ判定をするリスク
- 型変換の必要性やそのパターンが暗黙知として残り、実装時の混乱要因になる
- コードレビューで日時表現の妥当性を判断する基準がない

## 2. 何を達成するか（What）

### 2.1 目的

プロジェクト内の日時表現について、どの形式をどの状況で使うべきかのガイドラインを策定し、既存の型選択理由をドキュメント化する。

### 2.2 最終ゴール

1. 日時表現の選択基準ガイドラインがドキュメント化されている
2. 既存型の日時プロパティが選択基準に照らして妥当であることが確認されている
3. 新規型定義時に参照できるリファレンスが存在する

### 2.3 スコープ

#### 含むもの

- 日時表現ガイドラインの策定（`Date` / `string` / `number` の使い分け基準）

- `interfaces-agent-sdk-skill.md` または `development-guidelines.md` への追記

#### 含まないもの

- 既存型定義の変更（表現形式の統一リファクタリング）
- 新しい型の追加
- 実行時のバリデーション実装

### 2.4 成果物

### 3.3 必要な知識

| ---------------------- | --------------------------------------------------------------- |
| Skill型定義            | `packages/shared/src/types/skill.ts`                            |

| JSON シリアライズ制約  | electron-store ドキュメント                                     |
| 日時表現のトレードオフ | TypeScript/JavaScript Date vs Unix timestamp vs ISO 8601 string |

### 3.4 推奨アプローチ

#### Step 1: 日時プロパティの網羅的調査

```bash
# 全型定義ファイルから日時関連プロパティを検索
rg -n "Date\b|timestamp|At:|Updated|Modified|Created" packages/shared/src/types/ --type ts
```

#### Step 2: 選択基準の策定

以下の基準をガイドラインとして文書化する：

| 表現形式       | 使用場面                              | 理由                               |
| -------------- | ------------------------------------- | ---------------------------------- |
| `Date`         | UI表示・TypeScriptロジックで直接操作  | フォーマット・比較・算術が容易     |
| `number`       | IPC通信・DB永続化・パフォーマンス重視 | シリアライズ不要、比較が高速       |
| `string` (ISO) | JSON永続化・外部API互換               | JSON.stringify/parseで情報劣化なし |

#### Step 3: 仕様書への追記

`interfaces-agent-sdk-skill.md` に「日時表現ガイドライン」セクションを追加する。

### 3.5 TASK-FIX-13-1からの実装課題と教訓

本タスクはTASK-FIX-13-1の実装過程で発見された改善候補である。以下の課題と教訓が背景にある。

#### 課題1: 削除対象プロパティの境界判定

| 項目           | 内容                                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **課題**       | `lastUpdated` が `Skill` / `SkillImportConfig` / `StorageMetadata` / `StorageStats` の4型に存在し、どれが削除対象かの判定が困難だった |
| **苦戦した点** | 同名プロパティが異なる型に存在する場合、grepの結果を型スコープで分類する作業に時間がかかった                                          |
| **解決策**     | TypeScript の型定義を起点に、各 `lastUpdated` の所属型を特定し、`Skill.lastUpdated` のみを対象と判定                                  |
| **教訓**       | 日時プロパティの命名・型表現のガイドラインが整備されていれば、スコープ判定が迅速に行えた                                              |

#### 課題2: ドキュメント偏重による実装検証省略

| 項目           | 内容                                                                                                            |
| -------------- | --------------------------------------------------------------------------------------------------------------- |
| **課題**       | Phase 1-12の仕様書作成に注力した結果、実際のコード実装の検証が不十分だった                                      |
| **苦戦した点** | 並列エージェントでドキュメント生成を効率化したが、コード検証工程が省略された                                    |
| **解決策**     | 再検証で3つの専門エージェント（Anchor.name参照検索、lastUpdated型分類、型import使用状況）を投入し、網羅的に確認 |
| **教訓**       | ドキュメント作成の前に必ずコード検証を完了させる。並列実行後は統合チェックを必須とする                          |

#### 課題3: プロパティ名衝突によるgrep誤検出

| 項目           | 内容                                                                                                                                   |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **課題**       | `name` プロパティは JavaScript/TypeScript で極めて一般的な名前であり、`Anchor.name` の参照を grep で特定する際に大量の誤検出が発生した |
| **苦戦した点** | `grep -rn "\.name"` では数百件の無関係な結果が混入し、手作業での分類が必要だった                                                       |
| **解決策**     | `Anchor` 型のインポート・使用箇所を先に特定し、そのファイル内でのみ `.name` を検索するスコープ限定戦略を採用                           |
| **教訓**       | 一般的なプロパティ名の移行では、型スコープでの検索が必須。コードベース全体の grep は誤検出が多すぎて非効率                             |

**参照**: [lessons-learned.md](../../../.claude/skills/aiworkflow-requirements/references/lessons-learned.md)

## 9. 備考

### 発見元の原文

```
TASK-FIX-13-1 Phase 12にて検出:
コードベース内の日時プロパティが Date / string / number の3形式で混在している。
各形式の選択は意図的だが、その理由がドキュメント化されておらず、
新規型定義時や型移行タスク実行時の判断基準が不明確。
```

### 補足事項

- 本タスクはコード変更を伴わない純粋なドキュメント改善タスクである
- `SkillImportConfig.lastUpdated` が `string` 型である理由は electron-store の JSON シリアライズ制約に起因する（Date オブジェクトは JSON.stringify で文字列化されるが、JSON.parse で復元されない）
- 将来的に日時表現の統一リファクタリングが検討される場合、本ガイドラインが移行計画の基礎資料となる
