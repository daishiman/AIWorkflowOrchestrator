## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-CI-FUTURE-002 にて `test-web` ジョブを 2 シャードに分割する実装を行った。この実装の中で、GitHub Free Tier の並列上限（20 同時実行ジョブ）を考慮したシャード数の計算・`test-desktop` とのシャード数バランス調整など、知識がなければ手戻りが発生しやすい設計判断が複数存在した。

現時点では `test-web` は 2 シャード構成で安定稼働しているが、`apps/web` のテスト数が今後増加した場合に「シャード数をさらに増やしたい」という需要が生じる。その際に必要な手順・計算式・判断基準が現状どこにも文書化されていない。

### 1.2 問題点・課題

- `test-web` のシャード数を増やす手順が未文書化であり、担当者が変わった場合や時間が経過した場合に一から調査が必要になる
- GitHub Free Tier 並列上限（20）の計算方法と、ジョブ間のシャード数バランス調整基準が明示されていない
- どのジョブ（`test-desktop` / `test-web` 等）を優先してシャードを割り当てるかの選定基準が曖昧なままである
- TASK-CI-FUTURE-002 実装時の知見（苦戦箇所・回避策）が個人の記憶に依存しており、チーム全体に共有されていない

### 1.3 放置した場合の影響

- テスト数増加時にシャード数を増やそうとした担当者が、並列上限計算や設定変更方法を一から調査する工数が発生する
- 誤った計算で GitHub Free Tier 上限 20 を超えるシャード設定が CI に混入し、キューイング遅延が発生するリスクがある
- `test-desktop` と `test-web` のシャード数バランスを崩す変更が、根拠なく行われるリスクがある
- 知見が失われることで、TASK-CI-FUTURE-002 で発生した手戻りが繰り返される

## 2. 何を達成するか（What）

### 2.1 目的

`test-web` のシャード数を将来的に増やす際に参照できる手順書・計算ガイド・選定基準を整備し、担当者が変わっても迷わず安全にスケールアップできる状態を作る。

### 2.2 最終ゴール

以下の 3 点を網羅した手順書ドキュメントを作成し、`docs/30-workflows/` 配下に配置する:

1. **増やす手順**: `.github/workflows/ci.yml` のシャード設定変更手順（コマンド例・YAML 例を含む）
2. **GitHub Free Tier 上限計算**: 全ジョブの並列数合計を算出する計算式と具体例
3. **削減候補ジョブの選定基準**: シャード数を増やすために他ジョブを削減する際の判断フレームワーク

### 2.3 スコープ

- スケールアップ後の動作確認手順（ローカル・CI 両方）

#### 含まないもの

- `test-desktop` のシャード数変更
- E2E テスト（Playwright）のシャード化ガイド

- `apps/web` のアプリケーションコード変更

## 3. どのように実行するか（How）

### 3.1 前提条件

- TASK-CI-FUTURE-002 が完了し、`test-web` の 2 シャード構成が CI 上で安定稼働していること
- `.github/workflows/ci.yml` の現在のジョブ構成（`test-desktop` / `test-web` / `typecheck` / `test-shared` / `e2e`）の並列数を把握していること
- TASK-CI-FUTURE-002 の実装経緯（設計判断・手戻り内容）を把握している担当者がドキュメント執筆に参加できること

### 3.2 依存タスク

- TASK-CI-FUTURE-002（test-web シャード化）の完了が前提

### 3.3 必要な知識

- GitHub Actions の matrix strategy（`matrix.shard` / `--shard` オプション）
- GitHub Free Tier の並列上限（最大 20 同時実行ジョブ）の計算方法
- Vitest の `--shard` オプション（例: `--shard=1/4`）
- 現在の CI ジョブ構成（`test-desktop×N + test-web×M + typecheck×1 + test-shared×1 + e2e×1`）
- TASK-CI-FUTURE-002 実装時の知見（設計判断・苦戦箇所）

### 3.4 推奨アプローチ

#### Step 1: 現在の CI 構成を調査する

```bash
# ci.yml の現在のジョブ構成とシャード数を確認する
grep -A 10 "strategy:" .github/workflows/ci.yml

# 各ジョブの並列数を集計する
grep -E "(shard|matrix)" .github/workflows/ci.yml
```

調査結果から現在の並列数合計を算出し、ドキュメントのベースライン情報として記録する。

#### Step 2: 並列上限計算式を設計する

GitHub Free Tier 上限（20）を基準に、汎用的な計算式を定義する:

```
test-web 最大シャード数 = 20 - (test-desktop_shards + typecheck + test-shared + e2e)
```

具体例も記載する（現在の構成での計算結果を含む）:

```
現在: test-desktop(15) + test-web(2) + typecheck(1) + test-shared(1) + e2e(1) = 20
test-web を 4 に増やす場合: test-desktop を 13 に削減 → 13+4+1+1+1=20
```

#### Step 3: 削減候補ジョブの選定基準を整理する

シャード数を増やすために他ジョブのシャードを削減する場合の判断基準を定義する:

- **実行時間基準**: 最長シャード実行時間が最も短いジョブから削減する
- **テスト密度基準**: 1 シャード当たりのテスト件数が最も少ないジョブを削減候補とする
- **CI 影響度基準**: 削減によって CI 全体の実行時間への影響が最小のジョブを選ぶ

#### Step 4: スケールアップ手順を具体化する

実際に `ci.yml` を変更する際の手順を YAML 例・コマンド例付きで記述する:

```yaml
issue_number: 2185
# test-web シャード数を 2 → 4 に増やす例
test-web:
  strategy:
    matrix:
      shard: [1, 2, 3, 4]
  steps:
    - run: pnpm --filter @repo/web test -- --shard=${{ matrix.shard }}/4
```

```bash
# ローカル動作確認コマンド（シャード数 4 の場合）
pnpm --filter @repo/web test -- --shard=1/4
pnpm --filter @repo/web test -- --shard=2/4
pnpm --filter @repo/web test -- --shard=3/4
pnpm --filter @repo/web test -- --shard=4/4
```

#### Step 5: ドキュメントをレビュー・公開する

作成したドキュメントを `docs/30-workflows/ci-guides/` に配置し、既存の CI 関連ドキュメントからの参照リンクを追加する。

### Phase 2: 計算式・選定基準の設計

#### 目的

GitHub Free Tier 上限計算式と削減候補ジョブの選定基準を確定し、ドキュメントの核となる判断フレームワークを定義する。

#### 手順

1. Phase 1 で収集した情報を基に、汎用的な並列上限計算式を策定する

   ```
   test-web 追加可能シャード数 = 20 - (現在の全ジョブ並列数合計)
   test-web シャード数変更後の検証式: test-desktop + test-web(新) + typecheck + test-shared + e2e ≦ 20
   ```

2. シャード削減候補ジョブの選定基準を 3 つの観点で整理する:
   - 実行時間観点（最長シャード時間が短いジョブを優先削減）
   - テスト密度観点（1 シャード当たりのテスト件数）
   - CI インパクト観点（削減後の実行時間への影響度）

3. 具体的な計算例を複数パターン（+1 シャード・+2 シャード・+4 シャード）で作成する

4. 計算式と選定基準が実際の CI 構成と矛盾しないことを検証する

#### 成果物

- 並列上限計算式（汎用式 + 具体例複数パターン）
- 削減候補ジョブ選定基準（チェックリスト形式）

#### 完了条件

- 計算式が GitHub Free Tier 上限 20 を正しく反映している
- 選定基準が 3 つの観点を網羅している
- 具体例が現在の CI 構成に基づいて正確に算出されている

## 7. リスクと対策

| リスク                                                                                | 影響度 | 発生確率 | 対策                                                                                                                  |
| ------------------------------------------------------------------------------------- | ------ | -------- | --------------------------------------------------------------------------------------------------------------------- |
| ドキュメント作成時点の CI 構成が変更されてドキュメントの計算例が陳腐化する            | 中     | 中       | 計算例には「執筆時点」の注記を入れ、汎用計算式を主体とする。CI 構成変更時にドキュメントも更新する運用ルールを明記する |
| TASK-CI-FUTURE-002 の実装知見を把握している担当者が不在でドキュメントの精度が低下する | 中     | 低       | 本タスクと TASK-CI-FUTURE-002 の仕様書（苦戦箇所テーブル）を合わせて参照し、記録された知見を最大限活用する            |
| 削減候補ジョブの選定基準が曖昧なまま文書化され、誤った判断を誘発する                  | 中     | 低       | 選定基準には具体的な数値例と「この基準で選んだ場合の具体例」を必ず付記し、抽象的な記述を避ける                        |
| ドキュメントが長大になり読まれなくなる                                                | 低     | 中       | 各セクションは「3 行サマリー＋詳細」の構成にし、スキャンしやすい形式（表・コードブロック中心）を維持する              |
| GitHub Free Tier の上限値（20）が変更されてドキュメントの計算式が無効化される         | 低     | 低       | 計算式中の「20」は定数ではなくコメント付きの参照値として記述し、GitHub 公式ドキュメントへのリンクを添付する           |

### 補足事項

- 本タスクは TASK-CI-FUTURE-002 Phase 12 の未タスク検出で発見され、正式なタスクとして切り出したものである
- 実装（シャード数変更）自体は本タスクのスコープ外である。本タスクはドキュメント整備のみを対象とする
