## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-FIX-IPC-SKILL-NAME-001（2026-04-06）の修正作業中に、`registerRuntimeSkillCreatorHandlers()` 関数内で `ipcMain.handle()` が同一チャネルに対して 2 回実行されていることが発覚した。これにより後続 14 個のハンドラが実際には登録されない状態が継続していた。

この重複登録バグは **コードレビューのみに依存していた**ため、長期間にわたって検出されなかった。今後同種の回帰が発生した場合も、CI が存在しなければ再び見逃される可能性がある。

### 1.2 問題点・課題

- `ipcMain.handle()` は同一チャネルに 2 回目の登録をしても例外を投げず、後続ハンドラが静かに無視される（サイレントフェイル）
- 重複ブロック（約 35 行）がコードレビューでもテストでも完全にカバーされていなかった
- 登録チャネル数・チャネル名を検証するスナップショットテストが存在せず、欠損を自動検出できない
- `registerAiHandlers` 等の他の登録関数も同様のリスクを抱えている可能性がある

### 1.3 放置した場合の影響

- 将来の開発でリファクタリングや機能追加時に同種の重複登録が再発し、複数の IPC チャネルが無効化される
- IPC チャネルが未登録の場合、Renderer 側の呼び出しは応答なしでタイムアウトし、ユーザーには「フリーズ」として見える
- バグの発覚がコードレビュー・手動テストに依存するため、修正コストが高くなる

## 2. 何を達成するか（What）

### 2.1 目的

全 IPC ハンドラ登録関数が呼び出された後に登録されているチャネル名の一覧をスナップショットとして保存し、**重複登録・欠損を CI で自動検出できる**仕組みを構築する。

### 2.2 最終ゴール

- `ipcMain` に登録されたチャネル数・名称をスナップショットで固定し、差分が生じた場合に CI テストが FAIL する
- 重複登録が発生した場合（同一チャネルが複数回 `handle()` される場合）にもテストが FAIL する
- 既存 CI パイプラインへの統合が確認できる

### 2.3 スコープ

#### 含むもの

- `registerRuntimeSkillCreatorHandlers()` のスナップショットテスト作成
- `registerAiHandlers()` 等の主要な IPC ハンドラ登録関数のスナップショットテスト
- チャネル名一覧・登録数の検証ロジック
- 重複登録検出ロジックの追加
- `pnpm vitest run` による CI 統合確認

#### 含まないもの

- 各 IPC ハンドラの処理ロジック自体のテスト（他タスクで対応済みまたは別タスク）
- Renderer 側（preload）のチャネル一覧との突合（別タスク: UT-IPC-EXECUTION-CHANNELS-PARITY-001）
- 実際の IPC 通信の E2E テスト（Playwright 系）

### 2.4 成果物

| 成果物                         | 説明                                                           |
| ------------------------------ | -------------------------------------------------------------- |
| スナップショットテストファイル | `ipc-handler-registration.snapshot.test.ts` 相当の新規ファイル |

- `ipcMain` のモック方法を把握していること（`vi.mock("electron")` または `vi.spyOn`）

### 3.2 依存タスク

| タスク                               | 関係 | 備考                                |
| ------------------------------------ | ---- | ----------------------------------- |
| TASK-FIX-IPC-SKILL-NAME-001          | 前提 | 重複バグ修正済み・正常系確立が先決  |
| UT-IPC-EXECUTION-CHANNELS-PARITY-001 | 関連 | Renderer 側との突合は別タスクで実施 |

### 3.3 必要な知識

- `ipcMain.handle()` の Electron API 挙動（同一チャネル 2 回登録時のふるまい）
- Vitest でのスナップショットテスト（`expect(x).toMatchSnapshot()`）
- `vi.mock("electron")` を使ったモック作成パターン
- `registerRuntimeSkillCreatorHandlers()` が存在するファイル: `apps/desktop/src/main/ipc/creatorHandlers.ts`

### 3.4 推奨アプローチ

1. `ipcMain` をモックし、`handle()` の呼び出し引数（チャネル名）をすべて記録する spy を作成する
2. 各登録関数を呼び出し、記録されたチャネル名配列をソートしてスナップショットとして保存する
3. 同一チャネルが複数回登録されていないか（配列に重複がないか）も並行アサーションで検証する
4. スナップショットが一度確定したら、チャネルを追加・削除・リネームした時点で CI が FAIL するように担保する

### 3.5 苦戦箇所（発見元タスクからの教訓）

| 項目     | 内容                                                                                                                                                                |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 症状     | `registerRuntimeSkillCreatorHandlers()` 内で `ipcMain.handle()` が 2 回実行され、後続 14 チャネルが未登録になっていた（重複ブロック約 35 行が静かに無視されていた） |
| 原因     | 重複ブロックが完全性テストでカバーされておらず、コードレビューのみに依存していたため長期間検出されなかった                                                          |
| 対応     | 重複ブロックを削除して全 16 チャネルを正常登録、CI スナップショットテストを追加して再発防止を図る                                                                   |
| 再発防止 | IPC ハンドラは `handle()` 単一登録を enforce する CI チェックを必須とする。スナップショットによるチャネル数・名称の固定が最も低コストかつ効果的                     |

#### Task 12-1: 実装ガイド

##### Part 1: 中学生でも理解できる説明（日常の例えで）

**「受付係の名簿管理」の例え**

学校の文化祭で、各クラブが「相談窓口」を開設するとします。受付係は「どのクラブが窓口を担当しているか」を名簿に記録します。

もし同じクラブが名簿に 2 回書かれていたら、どうなるでしょうか？後から書いた行が優先されるのではなく、**最初の行しか使われない**まま 2 行目以降がずっと無視されます。しかも「名簿がおかしい」というエラーは何も出ません。来場者が「吹奏楽部の窓口はどこですか？」と聞いても、正しく案内されないことになります。

このアプリでも同じことが起きていました。プログラムの「窓口係（IPC ハンドラ）」が名前を登録するとき、同じ名前を 2 回書いてしまっていたため、14 個の窓口が誰にも案内されない状態になっていました。

今回追加するテストは「名簿チェック係」です。名簿を見て「重複はないか？」「全部の窓口が書かれているか？」を毎回自動で確認します。これで将来また同じミスが起きたとき、すぐに気づけます。

##### Part 2: 技術者向け説明

**問題の本質**

`ipcMain.handle(channel, handler)` は同一チャネルに対して 2 回目の登録をしても例外を投げない。後発の `handle()` 呼び出しは ElectronJS 内部で無視される（または警告のみ）。これにより、重複ブロック以降のハンドラが静かに未登録になる。

**スナップショットテストの実装パターン**

```typescript
import { vi, describe, it, expect, beforeEach } from "vitest";

// electron をモック
vi.mock("electron", () => {
  const registeredChannels: string[] = [];
```

## 7. リスクと対策

| リスク                                                | 影響度 | 発生確率 | 対策                                                            |

## 9. 備考

### 苦戦箇所【記入必須】

> 実行中に迷った点・判断に時間がかかった点・再利用したい回避策を記録する。

| 項目     | 内容                                                                                                                                                                                                            |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 症状     | `registerRuntimeSkillCreatorHandlers()` で `ipcMain.handle()` が 2 回実行され後続 14 ハンドラが未登録になっていた。重複ブロック（約 35 行）が完全性テストでも未カバーだった                                     |
| 原因     | 同一チャネルの重複 `handle()` 登録が ElectronJS 内部でサイレント無視されるため、ランタイムエラーが発生せず、コードレビューのみに依存していた結果として長期間未検出になった                                      |
| 対応     | 重複ブロック削除で全 16 チャネルを正常登録し、CI スナップショットテストを追加することで再発防止を図る（本タスク）                                                                                               |
| 再発防止 | IPC ハンドラは `handle()` 単一登録を enforce する CI チェックが必須。スナップショットによるチャネル数・名称の固定が最も低コストかつ効果的な防止策。登録関数変更時は必ず `--update-snapshots` を明示的に実行する |

### 補足事項

- 本タスクは小規模であるため、Phase 1〜3 設計が自明な場合は Phase 2・3 の outputs 省略を許容する（小規模タスク tier）
- スナップショット更新は意図的変更時のみ許可し、`--update-snapshots` を使う際はチャネル変更の意図をコミットメッセージに明記すること
