## 概要

`buildPlanSystemPrompt()` と `parsePlanResponse()` はモジュールスコープで export されているが、直接の単体テストが存在しない。Facade の統合テスト経由でのみ検証されている。

将来のリファクタリング（プロンプトテンプレート変更、パースロジック改修）時に、リグレッション検出が間接的になるリスクがある。

## 対応方針

1. `buildPlanSystemPrompt` の単体テスト追加:
   - agent仕様書の内容がセパレータ付きで連結されることの検証
   - PLAN_RESPONSE_SCHEMA_INSTRUCTION が末尾に含まれることの検証
   - 空配列の場合の動作検証
2. `parsePlanResponse` の単体テスト追加:
   - 有効な JSON → LLMPlanResponse への変換
   - Markdownコードブロック付き JSON のstrip + パース
   - 余分なフィールドを含む JSON の許容（strict mode でない）
   - 型不一致のフィールドでのバリデーションエラー
   - ネスト構造（agents内のフィールド型不一致）のエラー
3. テストファイルは既存の `.plan.test.ts` に `describe("Helper functions")` として追加

## 苦戦箇所の記録

- **テスト設計の判断**: Facade 統合テスト vs ヘルパー単体テストの境界線。統合テストで全カバーされている場合、単体テストは「冗長」にも見えるが、リファクタリング安全性のために必要
- **stripMarkdownCodeBlock の正規表現**: ` ```json ` 以外のバリエーション（` ```typescript ` や ` ``` ` のみ）も考慮すべきか。現在は `(?:json)?` で json のみ対応
- **推奨**: `describe("parsePlanResponse")` と `describe("buildPlanSystemPrompt")` を `.plan.test.ts` の末尾に追加。テスト数は 5-8 件程度
