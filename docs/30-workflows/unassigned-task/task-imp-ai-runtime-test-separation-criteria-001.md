## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

Phase 4（契約テスト）と Phase 6（回帰テスト）の仕様を分離したが、migration まわりのケースで重複が残存した。

### 1.2 問題点・課題

- MR-01〜MR-03 と TC-C112〜TC-C113 が同系統検証を実施。
- テスト責務の定義が文書化されていないため、実装時に再重複しやすい。

### 1.3 放置した場合の影響

- テスト保守コスト増大。
- 失敗時の原因切り分けが遅延。
- coverage は満たしても品質密度が下がる。

## 2. 何を達成するか（What）

### 2.1 目的

契約テスト/回帰テスト/統合テストの責務境界を明文化し、重複を抑制する。

### 2.2 最終ゴール

- テスト種別ごとの判定基準が仕様書に固定される。
- 重複ケースの扱い（統合/削除）が決定される。

### 2.3 スコープ

#### 含むもの

- テスト責務定義表の作成。
- Phase 4/6 仕様書への境界注記。
- 重複ケースの整理方針。

#### 含まないもの

- 実装コード改修。
- 新機能テスト追加。

### 2.4 成果物

- 棲み分け基準ドキュメント。
- Phase 4/6 仕様の更新。
- 重複ケース判定表。

## 3. どのように実行するか（How）

### 3.1 前提条件

- Task01 の Phase 4/6/10 文書が最新。
- 既存のテストケースIDが整理されている。

### 3.2 依存タスク

- TASK-IMP-AI-RUNTIME-AUTHMODE-UNIFICATION-001（spec_created）。

### 3.3 必要な知識

- 契約テスト設計、回帰テスト設計、coverage 指標の運用。

### 3.4 推奨アプローチ

- 先に「重複定義ルール」を決めてからケースを分類する。
- 仕様書先行で境界を固定し、実装タスクで再利用する。

## 4. 実行手順

### Phase構成

- Phase A: 現状ケース分析
- Phase B: 基準策定
- Phase C: 文書反映

### Phase A: 現状ケース分析

#### 目的

重複箇所を定量化する。

#### 手順

1. MR 系と TC-C 系を一覧化する。
2. 入力/期待値/責務を比較する。
3. 重複候補を抽出する。

#### 成果物

重複候補一覧。

#### 完了条件

対象ケースが漏れなく分類されている。

### Phase B: 基準策定

#### 目的

テスト種別ごとの責務を固定する。

#### 手順

1. 契約テスト: 単一関数入出力に限定。
2. 回帰テスト: 伝播経路/状態遷移に限定。
3. 統合テスト: ユーザー操作の最終結果に限定。

#### 成果物

責務定義表（種別/対象/粒度/例）。

#### 完了条件

重複判定ルールが一意に説明できる。

### Phase C: 文書反映

#### 目的

基準を Task02-10 へ再利用可能にする。

#### 手順

1. Phase 4/6 仕様書の冒頭へ境界注記を追加。
2. 重複ケースの統合/削除方針を記録。
3. `task-workflow.md` と `lessons-learned.md` へ同期。

#### 成果物

更新済み仕様書と同期記録。

#### 完了条件

MINOR-05 の再発防止条件が明文化されている。

## 5. 完了条件チェックリスト

- [ ] 契約/回帰/統合テストの責務定義が明文化されている
- [ ] 重複ケースの処理方針が確定している

### 品質要件

- [ ] 重複判定基準が客観的である
- [ ] coverage 基準と両立している

### ドキュメント要件

- [ ] Phase 4/6 仕様へ境界注記が反映されている
- [ ] 関連台帳への同期記録がある

## 6. 検証方法

### テストケース

- 重複候補の再評価で同一結論になること。
- 境界定義を適用した新規ケースで分類迷いが発生しないこと。

### 検証手順

1. 更新後の Phase 4/6 文書をレビュー。
2. 既存ケースを再分類し、重複率を比較。
3. Task02-10 の担当者レビューで運用可能性を確認。

## 7. リスクと対策

| リスク                               | 影響度 | 発生確率 | 対策                            |
| ------------------------------------ | ------ | -------- | ------------------------------- |
| 基準が抽象的すぎて運用されない       | 中     | 中       | 具体例（MR/TC-C）を必ず添付する |
| 境界変更で既存テスト削減が過剰になる | 中     | 低       | 削除前に代替検証経路を明記する  |
| 文書更新のみで実装側へ伝播しない     | 中     | 中       | Task02-10 参照表へ同時反映する  |
