## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-CI-OPT-001 にて node_modules キャッシュを導入し、CI 実行時間を大幅に短縮した（15分超 → 約5〜7分）。
しかし、キャッシュは一度設定すれば永続的に機能するわけではなく、依存関係の変化やキャッシュ無効化により、徐々にヒット率が低下する可能性がある。

現在、キャッシュのヒット／ミスの状況は CI 実行ログを手動で確認しなければわからない。定常的なモニタリング手段がないため、キャッシュ劣化が発生しても即座に気付ける体制になっていない。

### 1.2 問題点・課題

- キャッシュヒット率を自動でモニタリングする仕組みがない
- キャッシュが古くなったり無効化されても、CI のログを個別に確認しない限り気づかない
- `actions/cache@v4` の `cache-hit` output の仕様（完全一致のみ `true` になり、`restore-keys` フォールバック時は `false` になる）を理解していないと、ヒット率の判定を誤る恐れがある

### 1.3 放置した場合の影響

- キャッシュが機能しなくなっても気付かず、CI 実行時間が元の15分超に戻るリスクがある
- キャッシュ劣化の発見が遅れ、開発者体験（CI 待ち時間）の悪化が継続する
- CI コストが不必要に増大する可能性がある

## 2. 何を達成するか（What）

### 2.1 目的

node_modules キャッシュのヒット率を継続的にモニタリングし、キャッシュ劣化を早期検知できる仕組みを整備する。

### 2.2 最終ゴール

CI 実行後に自動でキャッシュヒット率をレポートし、ヒット率が低下した場合に警告が発生する仕組みを整備する。具体的には以下の状態を実現する。

1. 各 CI 実行でキャッシュのヒット／ミスを判定し、結果を GitHub Actions Summary に出力する
2. ヒット率が閾値（70%）を下回った場合、ワークフローに警告メッセージを出力する
3. キャッシュ状態（完全ヒット・フォールバックヒット・ミス）を区別して記録する

### 2.3 スコープ

#### 含むもの

- GitHub Actions ワークフロー（`.github/workflows/ci.yml`）へのキャッシュヒット率確認ステップの追加
- キャッシュヒット率を GitHub Actions Summary（`$GITHUB_STEP_SUMMARY`）に出力する処理
- ヒット率が閾値（70%）を下回った場合の警告出力（`::warning::` アノテーション）
- `cache-hit` と `cache-matched-key` の両方を利用したヒット状態の正確な判定ロジック

#### 含まないもの

- 外部モニタリングサービス（Datadog、Grafana 等）の導入
- Slack / メールアラートの設定
- キャッシュヒット率の長期トレンド蓄積・可視化ダッシュボードの構築

### 2.4 成果物

- `.github/workflows/ci.yml`（キャッシュヒット率モニタリングステップ追加）
- GitHub Actions Summary 出力のサンプル（動作確認ログ）

## 3. どのように実行するか（How）

### 3.1 前提条件

- TASK-CI-OPT-001 が完了しており、`.github/workflows/ci.yml` に `actions/cache@v4` を使った node_modules キャッシュが設定済みであること
- GitHub Actions の `$GITHUB_STEP_SUMMARY` および `::warning::` アノテーション構文が利用可能な環境であること
- ワークフローの `pnpm-install-retry` アクションまたはキャッシュステップが `id` を持ち、後続ステップから `outputs` を参照できること

### 3.2 依存タスク

- TASK-CI-OPT-001（node_modules キャッシュ導入）: 完了済み（本タスクの前提）

### 3.3 必要な知識

- `actions/cache@v4` の `outputs` 仕様
  - `cache-hit`: キャッシュキーが完全一致した場合のみ `true`。`restore-keys` によるフォールバック時は `false`
  - `cache-matched-key`: 実際にヒットしたキー（フォールバックキーを含む）。ミス時は空文字列
- GitHub Actions の `$GITHUB_STEP_SUMMARY` への書き込み方法（Markdown 形式で追記可能）
- GitHub Actions の `::warning::` アノテーション構文
- bash の条件分岐と文字列比較

### 3.4 推奨アプローチ

キャッシュ判定は `cache-hit` と `cache-matched-key` の2つの output を組み合わせて行う。

| cache-hit | cache-matched-key | 状態                    |
| --------- | ----------------- | ----------------------- |
| `true`    | 任意              | 完全ヒット（Exact Hit） |
| `false`   | 空でない文字列    | フォールバックヒット    |
| `false`   | 空文字列          | キャッシュミス          |

ヒット率の計算は「直近N件の実行における完全ヒット数 / 総実行数」では なく、**現在の実行における状態（ヒット or ミス）を Summary に記録する**アプローチとする。長期トレンドは本タスクのスコープ外。

各 CI ジョブにキャッシュ状態確認ステップを追加し、Summary に表形式で出力する。

## 4. 実行手順

### Phase 1: 現状把握

#### 目的

現在の `.github/workflows/ci.yml` におけるキャッシュステップの構成を確認し、`outputs` 参照に必要な `id` が設定されているかを確認する。

#### 手順

1. `.github/workflows/ci.yml` を開き、`actions/cache@v4` または `pnpm-install-retry` アクションの設定を確認する
2. 各キャッシュステップに `id` が設定されているか確認する（例: `id: cache-node-modules`）
3. `id` が設定されていないステップには追加する
4. `steps.<id>.outputs.cache-hit` および `steps.<id>.outputs.cache-matched-key` が参照可能な構成かを確認する

#### 成果物

- 現状の `.github/workflows/ci.yml` のキャッシュステップ一覧メモ

#### 完了条件

- 全キャッシュステップに `id` が設定されている
- `outputs` 参照の方法が明確になっている

---

### Phase 2: キャッシュヒット判定ステップの実装

#### 目的

各 CI ジョブにキャッシュヒット状態を判定・出力するステップを追加する。

#### 手順

1. キャッシュステップの直後に、以下のロジックを持つステップを追加する

```yaml
issue_number: 2169
- name: キャッシュヒット率レポート
  if: always()
  shell: bash
  run: |
    CACHE_HIT="${{ steps.cache-node-modules.outputs.cache-hit }}"
    MATCHED_KEY="${{ steps.cache-node-modules.outputs.cache-matched-key }}"

    if [ "$CACHE_HIT" = "true" ]; then
      STATUS="完全ヒット (Exact Hit)"
      ICON="✅"
    elif [ -n "$MATCHED_KEY" ]; then
      STATUS="フォールバックヒット (Partial Hit)"
      ICON="⚠️"
    else
      STATUS="キャッシュミス (Miss)"
      ICON="❌"
    fi

    echo "## node_modules キャッシュ状態" >> $GITHUB_STEP_SUMMARY
    echo "" >> $GITHUB_STEP_SUMMARY
    echo "| 項目 | 値 |" >> $GITHUB_STEP_SUMMARY
    echo "| ---- | -- |" >> $GITHUB_STEP_SUMMARY
    echo "| 状態 | ${ICON} ${STATUS} |" >> $GITHUB_STEP_SUMMARY
    echo "| cache-hit | ${CACHE_HIT} |" >> $GITHUB_STEP_SUMMARY
    echo "| マッチしたキー | ${MATCHED_KEY:-（なし）} |" >> $GITHUB_STEP_SUMMARY

    if [ "$CACHE_HIT" != "true" ] && [ -z "$MATCHED_KEY" ]; then
      echo "::warning::node_modules キャッシュがミスしました。依存関係の変更またはキャッシュ削除が発生した可能性があります。"
    fi
```

2. `if: always()` を付けることで、前のステップが失敗してもレポートが出力されることを確認する
3. 必要に応じて複数のジョブ（lint、typecheck、test 等）それぞれに同様のステップを追加する

#### 成果物

- `.github/workflows/ci.yml`（キャッシュヒット判定ステップ追加済み）

#### 完了条件

- キャッシュヒット判定ステップが全対象ジョブに追加されている
- `if: always()` が設定されており、前ステップ失敗時も動作する

---

### Phase 3: 閾値アラートの実装

#### 目的

キャッシュミスが発生した場合に警告アノテーションを出力する処理を実装する。

#### 手順

1. Phase 2 で実装したスクリプトに、ミス発生時の `::warning::` アノテーション出力が含まれていることを確認する（Phase 2 のサンプルコードに実装済み）
2. フォールバックヒット（`restore-keys` でのヒット）の場合も、完全な再インストールは発生していないため、警告ではなく情報レベル（`::notice::`）で通知するか検討する
3. 閾値として「キャッシュミス（完全ミス）の場合に警告」とする設計とする

**注意**: 単一 CI 実行内での「ヒット率70%未満」という閾値は、複数ジョブが存在する場合に意味を持つ。単一ジョブの場合はヒット／ミスの二値判定となる。複数ジョブがある場合は、ジョブ横断でのヒット率集計ステップを別途検討する。

#### 成果物

- 警告アノテーション出力ロジックの確認済み実装

#### 完了条件

- キャッシュミス時に `::warning::` アノテーションが出力される
- フォールバックヒット時に適切なレベルで通知が出力される

---

### Phase 4: 動作確認

#### 目的

実際に CI を実行し、キャッシュヒット率レポートが GitHub Actions Summary に正しく出力されることを確認する。

#### 手順

1. 変更をプッシュし、CI を実行する
2. GitHub Actions の実行結果ページで「Summary」タブを確認し、キャッシュ状態テーブルが表示されることを確認する
3. キャッシュヒット（完全ヒット）時と、意図的にキャッシュを無効化した場合（ミス時）の両方のパターンで出力を確認する
   - キャッシュを無効化するには、`pnpm-lock.yaml` に軽微な変更を加えてキャッシュキーを変える、または GitHub Actions の Cache を手動で削除する

#### 成果物

- GitHub Actions Summary の出力スクリーンショットまたはログ
- ヒット時／ミス時それぞれの出力サンプル

#### 完了条件

- 完全ヒット時に `✅ 完全ヒット (Exact Hit)` が Summary に表示される
- キャッシュミス時に `❌ キャッシュミス (Miss)` が Summary に表示され、`::warning::` アノテーションが出力される
- フォールバックヒット時に `⚠️ フォールバックヒット (Partial Hit)` が Summary に表示される

## 7. リスクと対策

| リスク                                                               | 影響度 | 発生確率 | 対策                                                                                                             |
| -------------------------------------------------------------------- | ------ | -------- | ---------------------------------------------------------------------------------------------------------------- |
| `cache-hit` のみで判定し、フォールバックヒットを誤判定する           | 中     | 高       | `cache-hit` と `cache-matched-key` の両方を確認する設計を徹底する                                                |
| `id` が設定されていないキャッシュステップで `outputs` 参照に失敗する | 高     | 中       | Phase 1 で全ステップの `id` 確認を必須手順とする                                                                 |
| キャッシュ状態確認ステップ自体がエラーになり CI がブロックされる     | 高     | 低       | `if: always()` と `continue-on-error: true` を組み合わせ、レポートステップの失敗が CI 全体に影響しないようにする |
| フォールバックヒットを「ミス」と誤解し不要なアラートが多発する       | 中     | 中       | 3状態の定義をドキュメント化し、チーム内で認識を統一する                                                          |
