## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-CI-OPT-001 により、GitHub Actions の CI 実行時間を 15分24秒 から 7分40秒以内（キャッシュヒット時）に削減した。
この最適化は pnpm キャッシュ戦略の改善、vitest の並列化設定調整、ジョブ依存関係の見直し等を通じて達成されたものである。

しかし、ソフトウェア開発が継続する限り、以下の要因によって CI 実行時間は自然に増加していく傾向がある：

- テストケースの追加（機能拡張・バグ修正に伴う）
- 依存ライブラリのバージョンアップ（ビルド時間変化）
- monorepo パッケージの増加
- 新たな lint ルール・型チェック対象の拡大

このような「技術的劣化」を早期に検知するには、CI 実行時間のトレンドデータを継続的に記録・監視する仕組みが必要である。

### 1.2 問題点・課題

現状、CI 実行時間の推移を自動で追跡する仕組みが存在しない。
実行時間の確認は `gh run view` を手動実行するか、GitHub Actions の UI を確認する形でしか行えない。

このため以下の課題がある：

- 劣化が緩やかな場合（例：週に10秒ずつ増加する場合）は気づきにくい
- キャッシュヒット時とキャッシュミス時で実行時間が大きく異なるが、その区別なく比較すると誤った判断をする可能性がある
- 再最適化が必要なタイミングを定量的な根拠で判断できない

### 1.3 放置した場合の影響

- CI 実行時間が徐々に増加しても検知が遅れ、再最適化のタイミングを逃す可能性がある
- TASK-CI-OPT-001 で得た最適化効果が静かに消失し、開発フィードバックループが遅くなる
- 「なぜ CI が遅くなったのか」の原因特定のための過去データが存在しないため、調査コストが増大する

## 2. 何を達成するか（What）

### 2.1 目的

CI 実行時間のトレンドを自動計測し、TASK-CI-OPT-001 で達成した最適化効果の維持状況を継続的に監視する。
閾値（10分）を超えた場合にアラートを出力することで、再最適化の判断を定量的・タイムリーに行えるようにする。

### 2.2 最終ゴール

定期実行スクリプト（ローカル実行または GitHub Actions スケジュール）が CI 実行時間のトレンドデータを収集し、
キャッシュ状態（ヒット/ミス）を区別してCSVまたはJSONに記録する。
閾値超過時にはアラートメッセージを標準エラー出力に表示し、即座に認識できる状態を実現する。

具体的な成功状態：

1. `scripts/measure-ci-timing.sh` が gh CLI を使用して直近 N 件の CI 実行時間を取得・記録できる
2. 記録データにキャッシュヒット/ミスの区分が含まれる
3. 実行時間が閾値（デフォルト 10分）を超えた場合にアラートメッセージが出力される
4. 記録ファイルは `docs/30-workflows/task-ci-optimization-001/outputs/ci-timing-trend.csv` に蓄積される

### 2.3 スコープ

#### 含むもの

- CI 実行時間を gh CLI で取得してCSVまたはJSONに記録するシェルスクリプトの作成
- キャッシュ状態（ヒット/ミス）の識別と記録カラムへの追加
- 実行時間が閾値（10分）を超えた場合のアラート出力（標準エラー出力）
- `scripts/` ディレクトリへのスクリプト配置
- README または利用手順コメントのスクリプト内記述

#### 含まないもの

- 外部ダッシュボードとの連携（Grafana、Datadog、Slack 等）
- GitHub Actions のスケジュールジョブへの組み込み（スクリプト作成のみ、ワークフロー追加は別タスク）
- Grafana/Datadog 等の外部モニタリングサービスの導入
- 可視化UI・グラフ表示

### 2.4 成果物

- `scripts/measure-ci-timing.sh`（CI 実行時間計測・記録スクリプト）
- `docs/30-workflows/task-ci-optimization-001/outputs/ci-timing-trend.csv`（初回実行後に生成されるトレンドデータ）

## 3. どのように実行するか（How）

### 3.1 前提条件

- `gh` CLI がインストール済みで `gh auth login` が完了していること
- リポジトリへのアクセス権限（`gh run list` が実行できること）
- `bash` バージョン 3.2 以上（macOS デフォルトで満たす）
- `jq` コマンドが利用可能であること（JSON パース用）

### 3.2 依存タスク

- TASK-CI-OPT-001（完了済み）: 最適化後のベースライン値（キャッシュヒット時 7分40秒以内、ミス時 11分前後）を定義

### 3.3 必要な知識

- `gh run list` および `gh run view` のオプション構文
- GitHub Actions の実行ログからキャッシュヒット/ミスを判定する方法
- CSV/JSON の追記処理（bash でのファイル操作）
- 終了コードによるアラート制御

**キャッシュ状態の判定方法（TASK-CI-OPT-001 の知見）**:

GitHub Actions のログに出力される以下の文字列でキャッシュ状態を判別できる：

- キャッシュヒット: `Cache restored from key:` または `Cache hit for`
- キャッシュミス: `Cache not found for` または `Cache restored using restoreKeys`

`gh run view --log <run-id>` で取得したログに対して `grep` で判定する。

### 3.4 推奨アプローチ

以下の構成でスクリプトを実装する：

```bash
#!/bin/bash
# scripts/measure-ci-timing.sh
# CI 実行時間トレンド計測スクリプト
#
# 使用方法:
#   ./scripts/measure-ci-timing.sh [件数] [閾値(秒)]
#   例: ./scripts/measure-ci-timing.sh 10 600
#
# 引数:
#   件数    - 取得する最新CI実行件数（デフォルト: 5）
#   閾値    - アラートを出力する実行時間の秒数（デフォルト: 600 = 10分）

# Step 1: gh run list で直近 N 件の run ID と実行時間を取得
# Step 2: 各 run について gh run view --log でキャッシュ状態を判定
# Step 3: 結果を CSV に追記（run_id, date, duration_sec, cache_status, conclusion）
# Step 4: 閾値超過チェックとアラート出力
```

CSV フォーマット:

```
run_id,date,duration_sec,cache_status,conclusion
12345678,2026-04-15T10:00:00Z,460,hit,success
12345679,2026-04-15T12:00:00Z,680,miss,success
```

## 4. 実行手順

### Phase 1: 事前調査・設計確認

#### 目的

gh CLI で取得できる情報の構造を確認し、スクリプト実装の設計を固める。

#### 手順

1. `gh run list --workflow=ci.yml --limit=5 --json databaseId,startedAt,updatedAt,conclusion` を実行し、出力フォーマットを確認する
2. `gh run view --log <run_id>` を1件実行し、キャッシュ判定に使える文字列を特定する
3. 実行時間の計算方法を確認する（`startedAt` と `updatedAt` の差分、または `gh run view` の `durationMs` フィールドの有無）
4. 出力先ディレクトリ `docs/30-workflows/task-ci-optimization-001/outputs/` の存在を確認する

#### 成果物

- gh CLI 出力サンプル（調査メモ）
- キャッシュ判定に使う文字列パターンの確定

#### 完了条件

- `gh run list` で必要なフィールドが取得できることを確認済み
- キャッシュ判定パターンが特定済み

---

### Phase 2: スクリプト実装

#### 目的

`scripts/measure-ci-timing.sh` を実装する。

#### 手順

1. `scripts/` ディレクトリが存在することを確認する（なければ作成）
2. スクリプトの骨格を作成する（ヘッダコメント・引数処理・メイン関数）
3. gh run list による run ID 一覧取得処理を実装する
4. 各 run のログ取得とキャッシュ状態判定処理を実装する
5. CSV への追記処理を実装する（ヘッダ行は初回のみ出力）
6. 閾値超過チェックとアラート出力（`>&2` で標準エラーに出力）を実装する
7. 実行権限を付与する: `chmod +x scripts/measure-ci-timing.sh`

#### 成果物

- `scripts/measure-ci-timing.sh`

#### 完了条件

- スクリプトが構文エラーなく実行できる（`bash -n scripts/measure-ci-timing.sh`）
- `--help` または引数なし実行で使用方法が表示される

### Phase 3: 動作検証

#### 目的

実際の CI 実行履歴に対してスクリプトを実行し、CSV が正しく生成されることを確認する。

4. キャッシュヒット/ミスの判定結果が実際のログと一致していることを目視確認する（1件以上）
5. 閾値超過の run が存在する場合、アラートメッセージが標準エラー出力に表示されることを確認する
6. 既存 CSV が存在する場合に追記（重複なし）で動作することを確認する

#### 成果物

- `docs/30-workflows/task-ci-optimization-001/outputs/ci-timing-trend.csv`（検証結果サンプル）

#### 完了条件

- CSV が正常に生成される
- キャッシュ状態の判定が少なくとも1件のキャッシュヒット run で正しい
- 閾値超過チェックが動作する（テスト用に閾値を低く設定して確認）

# 閾値アラートのテスト（閾値を1秒に設定して強制アラート）

## 7. リスクと対策

| リスク                                                               | 影響度 | 発生確率         | 対策                                                                                                |
| -------------------------------------------------------------------- | ------ | ---------------- | --------------------------------------------------------------------------------------------------- |
| gh run view --log が大量の出力でタイムアウトする                     | 中     | 中               | `--log` の代わりに特定ジョブのログのみ取得する (`--job` オプション)。キャッシュ判定対象ジョブを絞る |
| キャッシュ判定パターンが GitHub Actions のバージョンアップで変化する | 中     | 低               | 判定パターンをスクリプト冒頭の変数として定義し、変更しやすくしておく                                |
| CSV ファイルが肥大化する                                             | 低     | 高（長期運用時） | 90日以上前のエントリを自動削除するオプションをスクリプトに追加する（または手動運用）                |
| CI の実行時間に `gh run list` の `durationMs` フィールドが存在しない | 高     | 低               | Phase 1 の調査でフィールド存在を確認する。存在しない場合は `startedAt`/`updatedAt` の差分で計算する |
| run ログへのアクセスに GitHub API レート制限がかかる                 | 中     | 低               | 取得件数を少数（デフォルト5件）に抑える。必要に応じて `--limit` 引数で調整可能にする                |

## 9. 備考

### 苦戦箇所【記入必須】

以下は TASK-CI-OPT-001 Phase 11 から引き継ぐ知見であり、本タスク実装時に必ず考慮すること。

| 症状                                                      | 原因                                                                                                                                                   | 対応                                                                                             | 再発防止                                                                                               |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| CI 実行時間のベースライン計測で数値にばらつきが大きかった | キャッシュヒット（初回以降）とキャッシュミス（初回 or キャッシュ無効化後）で実行時間が大きく異なるため、混在した状態で平均を取ると意味のない数値になる | Phase 11 でキャッシュヒット時（7分40秒以内）とキャッシュミス時（11分前後）を別々に計測・記録した | トレンド計測スクリプトでもキャッシュ状態（hit/miss）を記録カラムに含め、集計・比較時は必ず区別して行う |

### 補足事項

- 本タスクはスクリプト単体の作成に留める。GitHub Actions スケジュールジョブへの組み込みは、運用実績を積んだ後に別タスクとして検討する
- TASK-CI-OPT-001 で達成した目標値（キャッシュヒット時 7分40秒以内）を閾値の参考にしたが、アラート閾値は 10分（余裕を持たせた値）をデフォルトとする
- スクリプトのデフォルト閾値は引数で上書き可能にし、プロジェクトの成長に合わせて調整できるようにする
