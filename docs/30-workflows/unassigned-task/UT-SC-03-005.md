# UT-SC-03-005: plan() エラーハンドリングの Result<T,E> パターン移行

## メタ情報

| ---------- | ----------------------------------------------------------- |

| 検出元     | TASK-SC-03-PLAN-LLM-PROMPT エレガント検証（30種思考法分析） |
| 優先度     | 中                                                          |
| 影響範囲   | RuntimeSkillCreatorFacade.ts, creatorHandlers.ts            |

## 概要

`RuntimeSkillCreatorFacade.plan()` のエラーハンドリングが `throw new Error()` パターンを使用している。`02-code-quality.md` のルール「サービス層のエラーは Result<T, E> パターンで明示的に返す」との乖離がある。

現在は `creatorHandlers.ts` の try-catch で例外を捕捉し `IpcResult<T>` に変換しているため機能的な問題はないが、以下の課題がある:

- JSON パースエラーと API タイムアウトが同じ catch ブロックで処理され、エラー種別の識別ができない
- サービス層のエラー契約が暗黙的（throw）であり、呼び出し元がどのエラーを期待すべきか不明確

## 対応方針

1. `Result<T, E>` 型を `@repo/shared` に定義（既存の場合はインポート）
2. `plan()` の戻り値を `Promise<Result<RuntimeSkillCreatorPlanResponse, PlanError>>` に変更
3. `PlanError` ユニオン型を定義: `ValidationError | LLMParseError | LLMTimeoutError | ResourceLoadError`
4. `creatorHandlers.ts` の try-catch を Result パターンの match に置換
5. 既存テストのアサーションを `rejects.toThrow()` から Result のエラーチェックに変更

## 苦戦箇所の記録

- **判断の困難さ**: `throw` パターンでもテストは全 PASS し、IPC 層で適切にラップされるため「動作上は問題ない」状態。設計基準（`02-code-quality.md`）との整合性を優先するか、動作優先で据え置くかの判断が難しい
- **影響範囲**: Result パターンに移行すると、既存テスト 20+ 件のアサーションを全て書き換える必要がある。P21/P35 パターン（DI追加時のテストモック大規模修正）と同様のリスク
- **推奨**: Phase 2 設計時にエラーカテゴリ表（`02-code-quality.md`）のコード番号体系を参照し、LLM 関連エラーの体系化を先行する
