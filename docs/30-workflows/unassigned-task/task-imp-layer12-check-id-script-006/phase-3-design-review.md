## 目的

Phase 2 の設計内容を検証し、Phase 4 以降の実装に進めるかを判定する。特にテーブル行スコープの正規表現パターンが例示値を正しく除外できるかを重点的に確認する。

## 実行タスク

### タスク1: grep パターンの妥当性検証

**目的**: 設計した正規表現パターンが誤検知なく動作することを確認する

**手順**:

1. 設計書の正規表現パターン（`/^\|\s+(L[1-4]-\d{3})\s+\|/gm`）を以下の入力で検証する:

   **テストケース1（テーブル行 — マッチすること）**:

   ```
   | L1-001 | SKILL.md の存在確認 | `error` | ファイルが存在する |
   | L2-007 | output-schema.json が有効な JSON か確認 | `error` |
   ```

   期待: `L1-001`, `L2-007` がマッチする

   **テストケース2（例示値 — マッチしないこと）**:

   ```
   1. 該当 Layer の現在の最大連番 + 1 を新しい check ID とする（例: Layer 2 に追加なら L2-008）
   ```

   期待: `L2-008` がマッチしない

   **テストケース3（将来の check ID — マッチすること）**:

   ```
   | L2-008 | 新しいチェック項目 | `warning` | 条件を満たす |
   ```

   期待: テーブル行に `L2-008` が登場した場合はマッチする

2. 上記を Node.js の REPL や簡易スクリプトで実際に確認する
3. 問題があれば Phase 2 に差し戻す

### タスク2: スクリプトアーキテクチャのレビュー

**目的**: 関数構成・ファイル配置が適切かを確認する

**レビュー観点**:

| 観点         | 基準                                                                     |
| ------------ | ------------------------------------------------------------------------ |
| 責務分離     | extractCheckIdsFromImpl / extractCheckIdsFromSpec が明確に分かれているか |
| 拡張性       | check ID 数の増加（30 件超）にハードコードなしで対応できるか             |
| 配置の妥当性 | 既存スクリプトの配置先と整合しているか                                   |
| テスト容易性 | 各関数が単体テスト可能な設計になっているか                               |

### タスク3: 入出力仕様のレビュー

**目的**: CLI インターフェースと出力フォーマットが使いやすいかを確認する

**レビュー観点**:

- デフォルトパスが現在のリポジトリ構造と一致しているか
- PASS/FAIL 時の出力が CI ログで視認しやすいか
- 終了コードの定義が CI 組み込みに適切か

### タスク4: 判定と記録

**判定基準**:

| 判定  | 条件                   | 対応                  |
| ----- | ---------------------- | --------------------- |
| PASS  | 全観点で問題なし       | Phase 4 へ進行        |
| MINOR | 軽微な修正で解決可能   | 修正後 Phase 4 へ進行 |
| MAJOR | 設計の根本的な問題あり | Phase 2 へ差し戻し    |
