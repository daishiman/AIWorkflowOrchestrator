## 目的

スクリプトの可読性・保守性を改善し、将来の check ID 追加時にメンテナンスコストが増えないことを確認する。インターフェースは変更しない。

## 実行タスク

### タスク1: コードレビューと改善点の特定

**目的**: Phase 5 実装のコードを見直し、改善箇所を特定する

**確認観点**:

| 観点               | 確認内容                                                          |
| ------------------ | ----------------------------------------------------------------- |
| 正規表現の可読性   | テーブル行スコープの正規表現に説明コメントがあるか                |
| 定数の分離         | ファイルパスのデフォルト値が定数として分離されているか            |
| エラーハンドリング | ファイル未存在・JSON パース失敗等の異常系が適切に処理されているか |
| ハードコード排除   | check ID の件数や値がハードコードされていないか                   |
| 出力フォーマット   | PASS/FAIL 出力が設計書の仕様と一致しているか                      |

### タスク2: リファクタリングの実施と記録

**手順**:

1. 改善点を特定し、以下の形式で記録する:

| 対象               | Before                 | After                    | 理由                               |
| ------------------ | ---------------------- | ------------------------ | ---------------------------------- |
| テーブル行正規表現 | コメントなし           | 説明コメント追加         | 例示値除外ロジックの意図を明示する |
| デフォルトパス定数 | 関数内にインライン記述 | モジュール先頭で定数定義 | 変更時の影響範囲を限定する         |
| （その他の改善点） |                        |                          |                                    |

2. リファクタリング後に全テストが PASS であることを確認する:

```bash
pnpm vitest run scripts/__tests__/verify-check-id-parity.test.js
```

### タスク3: テーブル行スコープ正規表現への説明コメント追加（必須）

**目的**: grep 誤検知問題の知識を後続の実装者に伝える

**追加コメント例**:

```javascript
/**
 * 仕様書のテーブル行から check ID を抽出する。
 *
 * NOTE: ファイル全体スコープの grep（/L[1-4]-\d{3}/g）は
 * 拡張ガイドライン内の例示値（例: 「L2-008 から連番」）にもマッチし、
 * 誤検知が発生する。このため、行頭が | で始まるテーブル行に限定している。
 *
 * 誤検知の詳細: lessons-learned.md を参照
 */
const TABLE_ROW_PATTERN = /^\|\s+(L[1-4]-\d{3})\s+\|/gm;
```
