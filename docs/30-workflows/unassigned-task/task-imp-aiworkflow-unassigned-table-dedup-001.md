## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-9F の Phase 12 再監査で `task-workflow.md` の残課題テーブルを確認した際、同一タスクIDが重複し、未完了行と完了行が同時に残る状態が確認された。

### 1.2 問題点・課題

- 同一タスクIDの重複行が発生しても、現在の確認はリンク存在チェック中心で検知漏れが起きる
- 完了/未完了の状態矛盾が残ると、優先度判断と実行順序の判定がぶれる
- Phase 12 の更新が複数仕様書に跨るため、台帳統合時のヒューマンエラーが再発しやすい

### 1.3 放置した場合の影響

- 未タスクの実施漏れ、または完了済みタスクの再着手が発生する
- `current/baseline` の監査結果解釈がさらに難しくなる
- 後続タスクの計画精度が低下し、Phase 12 の再作業コストが増大する

---

## 2. 何を達成するか（What）

### 2.1 目的

残課題テーブルの「重複ID」「状態矛盾（未完了と完了の共存）」を機械的に検知し、Phase 12 で確実に是正できる運用を確立する。

### 2.2 最終ゴール

1. `task-workflow.md` を対象に重複IDを検出し、行単位でレポートできる
2. 同一IDの状態矛盾を FAIL として判定できる
3. Phase 12 の検証手順に「台帳重複検知」が組み込まれている

### 2.3 スコープ

#### 含むもの

- 残課題テーブル重複検知ルールの定義
- 監査スクリプトの拡張、または補助スクリプトの追加
- `task-workflow.md` の重複/状態矛盾是正手順の標準化

#### 含まないもの

- すべての歴史的ドキュメントの一括整形
- 新機能の実装（IPC/Preload/API契約変更）

### 2.4 成果物

- 重複・状態矛盾検知を実装した監査スクリプト
- 検出結果レポート（対象ID、行番号、矛盾種別）
- `task-workflow.md` の更新ルール追記（または関連仕様書への反映）

## 3. どのように実行するか（How）

### 3.1 前提条件

- `task-specification-creator` の監査スクリプトを実行できること
- `aiworkflow-requirements/references/task-workflow.md` が正本として更新されていること
- Phase 12 検証コマンド群（`verify-all-specs` など）が利用可能であること

### 3.2 依存タスク

- ~~UT-IMP-PHASE12-SPEC-SYNC-SUBAGENT-GUARD-001~~（完了済み）
- UT-IMP-UNASSIGNED-FORMAT-NORMALIZATION-001（並走時は影響範囲を事前調整）

### 3.3 必要な知識

- Markdownテーブルの構造解析
- `current/baseline` 監査の運用ルール
- Phase 12 Task 4（未タスク検出）と Task 2（仕様更新）の連携要件

### 3.4 推奨アプローチ

1. 残課題テーブルを機械抽出し、タスクID単位で集計する
2. 「通常行」と「取り消し線行（完了扱い）」の混在を矛盾として判定する
3. 検出と同時に是正手順（どの行を残し、どの行を統合するか）を出力する
4. Phase 12 完了チェックに重複検知を必須化する

### 3.5 実装課題と解決策（親タスクからの教訓）

| 課題                                               | 発見経緯                                                                  | 解決策                                                               | 教訓                                                    |
| -------------------------------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------- |
| 同一タスクIDが未完了行と完了行で重複               | TASK-9F 再監査で `UT-IMP-AIWORKFLOW-SPEC-REFERENCE-SYNC-001` の重複を確認 | 台帳更新時にID単位の一意性チェックを追加し、重複時は更新を中断       | 「リンクが生きている」だけでは台帳品質を担保できない    |
| 既存監査が構文/リンク中心で状態矛盾を検知できない  | `verify-unassigned-links` は実在確認のみで、同一ID重複はスルー            | 重複ID・状態矛盾専用の監査ロジックを追加する                         | Phase 12 監査は「存在確認」と「意味整合確認」を分離する |
| 仕様書別SubAgent更新後の統合時に台帳ドリフトが混入 | 複数仕様書更新の統合段で、最終台帳への反映順序が曖昧だった                | SubAgentごとの最終統合チェック項目に「残課題テーブル重複なし」を追加 | 並列更新は最後の統合ゲートを明示しないと再発する        |

## 4. 実行手順

### Phase構成

- Phase A: 監査要件定義
- Phase B: 重複検知実装
- Phase C: 既存台帳への適用と是正
- Phase D: Phase 12 運用への組み込み

### Phase A: 監査要件定義

#### 目的

重複IDと状態矛盾の判定ルールを確定する。

#### 手順

1. `task-workflow.md` 残課題テーブルの行抽出ルールを定義する
2. タスクID正規化ルール（取り消し線除去、空白除去）を定義する
3. 矛盾判定条件（重複・完了/未完了混在）を仕様化する

#### 成果物

- 判定ルール定義書

#### 完了条件

- 重複IDと状態矛盾を機械判定できる入力仕様が確定している

### Phase B: 重複検知実装

#### 目的

監査スクリプトで重複・矛盾を検出可能にする。

#### 手順

1. `task-specification-creator` 側に検知ロジックを実装する
2. JSON出力に `duplicateTaskIds` / `statusConflicts` を追加する
3. 単体ケース（正常/重複/矛盾）で期待値を確認する

#### 成果物

- 更新済み監査スクリプト
- テストまたは検証ログ

#### 完了条件

- サンプル入力で重複・矛盾を正しく検知できる

### Phase C: 既存台帳への適用と是正

#### 目的

現行台帳の重複を解消し、一意状態に戻す。

#### 手順

1. 監査スクリプトを `task-workflow.md` に適用する
2. 重複IDの片方を統合/削除して状態を一意化する
3. `verify-unassigned-links.js` で参照整合を再確認する

#### 成果物

- 重複解消済み `task-workflow.md`
- 検証結果ログ

#### 完了条件

- 重複IDゼロ、状態矛盾ゼロが確認できる

### Phase D: Phase 12 運用への組み込み

#### 目的

再発防止として検証手順を標準化する。

#### 手順

1. Phase 12 チェックリストに重複検知を追記する
2. 関連仕様書（task-workflow / lessons）に運用手順を同期する
3. 変更履歴に本改善の目的と検証結果を記録する

#### 成果物

- 更新済み運用チェックリスト
- 更新履歴

#### 完了条件

- Phase 12 の標準手順として再利用可能になっている

## 6. 検証方法

### テストケース

- Case 1: 重複なし・状態矛盾なしの台帳で PASS
- Case 2: 同一ID重複（未完了同士）で FAIL
- Case 3: 同一IDが未完了/完了で混在し FAIL

### 検証手順

```bash
node .claude/skills/task-specification-creator/scripts/verify-unassigned-links.js
node .claude/skills/task-specification-creator/scripts/audit-unassigned-tasks.js --json --diff-from HEAD
node .claude/skills/task-specification-creator/scripts/verify-all-specs.js --workflow docs/30-workflows/completed-tasks/skill-share --json
```

## 7. リスクと対策

| リスク                                   | 影響度 | 発生確率 | 対策                                                        |
| ---------------------------------------- | ------ | -------- | ----------------------------------------------------------- |
| 既存テーブル記法の揺れで誤検知が増える   | 中     | 中       | 判定前にID正規化（取り消し線・空白除去）を行う              |
| 歴史的重複が大量に検出され是正が停滞する | 中     | 中       | `--diff-from HEAD` で段階導入し、全体是正は別Waveで実施する |
| 監査追加でPhase 12実行時間が増える       | 低     | 中       | 既存監査と同一実行パスに組み込み、単体実行も可能にする      |
