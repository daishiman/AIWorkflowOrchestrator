## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

CONV-07-05でRRF Fusion + Reranking機能を実装した。Rerankingは外部API（Cohere/Voyage）やLLMを呼び出すため、同一クエリ・同一候補に対して繰り返しAPIコールが発生するとコスト・レイテンシが増大する。

### 1.2 問題点・課題

- 同一クエリに対する繰り返しAPIコール
- 外部API呼び出しコストの増大
- レスポンスタイムの遅延

### 1.3 放置した場合の影響

- **影響度**: 中
- API利用コストの増加（Cohere/Voyage API）
- ユーザー体験の低下（レスポンス遅延）
- ただし機能は正常に動作

---

## 2. 何を達成するか（What）

### 2.1 目的

同一クエリ・同一候補セットに対するReranking結果をキャッシュし、パフォーマンスを向上させる。

### 2.2 最終ゴール

- キャッシュヒット時、外部APIを呼び出さずに結果を返却
- キャッシュTTLを設定可能
- キャッシュ統計（ヒット率等）を取得可能

### 2.3 スコープ

#### 含むもの

- キャッシュキー生成ロジック（query + candidates hash）
- インメモリキャッシュ実装
- キャッシュTTL設定
- キャッシュ統計API

#### 含まないもの

- 分散キャッシュ（Redis等）- 将来対応
- Fusion結果のキャッシュ - 別タスク

### 2.4 成果物

| 成果物                   | 説明                      |
| ------------------------ | ------------------------- |
| RerankingCacheクラス     | キャッシュ機構の実装      |
| キャッシュキー生成関数   | query + candidates → hash |
| キャッシュ設定オプション | TTL、最大サイズ等         |
| キャッシュ統計API        | ヒット率、エントリ数等    |

### 3.4 推奨アプローチ

```typescript
interface RerankingCacheOptions {
  maxSize: number; // 最大エントリ数（デフォルト: 1000）
  ttlMs: number; // TTL（デフォルト: 5分）

  private cache: LRUCache<string, FusedSearchResult[]>;

}
```

## 5. 完了条件チェックリスト

### 機能要件

- [ ] キャッシュキーが一意に生成される

## 6. 検証方法

### テストケース

1. 同一クエリ・候補でキャッシュヒットすること
2. TTL経過後にキャッシュミスすること
3. 最大サイズ超過時にLRU削除されること
4. キャッシュ統計が正確であること

### 検証手順

1. 同一クエリで2回Rerankingを実行
2. 2回目でキャッシュヒットし、APIコールがないことを確認
3. TTL経過後に再度実行し、キャッシュミスを確認
4. パフォーマンス測定でレスポンス改善を確認
