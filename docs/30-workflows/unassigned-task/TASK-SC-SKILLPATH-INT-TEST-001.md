## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

`TASK-SC-CREATOR-UPDATE-IMPL-001` の実装で `skillPath` を指定した update モードのフローが追加されたが、統合テスト（実際のファイルパスを通じた end-to-end 検証）が存在しない。現在はフォールバック連鎖による保護が機能しているが、長期的には回帰リスクがある。

### 1.2 問題点・課題

- `skillPath` を指定した場合の update フロー（ファイル読み込み → purpose 抽出 → StructurePlanJson 生成）の統合テストが存在しない
- ユニットテストのみでは `skillPath` の実際のファイルシステム操作を検証できない
- フォールバック連鎖の保護に依存しており、将来の変更で保護が外れた場合にリグレッションが発生するリスクがある

### 1.3 放置した場合の影響

- `skillPath` 指定フローのリグレッションが発生しても、テストが検出できない
- フォールバック連鎖の動作変更時に既存機能が壊れていても気づかない

---

## 2. 何を達成するか（What）

### 2.1 目的

`skillPath` を指定した update モードの統合テストを追加し、ファイルシステムを介した end-to-end の動作を検証できるようにする。

### 2.2 最終ゴール

- `skillPath` 指定時の update フローが統合テストでカバーされている
- フォールバック連鎖（`skillPath` なし時の graceful degradation）も統合テストで検証される

### 2.3 スコープ

#### 含むもの

- `skillPath` を指定した update フローの統合テスト追加
- フォールバック連鎖（`skillPath` 未指定時の通常フロー）の統合テスト確認

#### 含まないもの

- `runUpdateWorkflow()` の実装変更
- 差分更新契約の定義（TASK-SC-UPDATE-MODE-DIFF-SEMANTICS-001 が対応）
- E2E テスト（Playwright）の追加

### 2.4 成果物

- 追加されたテストケース（`SkillCreatorService.test.ts` 内の skillPath 統合テスト）

---

## 3. どのように実行するか（How）

### 3.1 前提条件

- `TASK-SC-CREATOR-UPDATE-IMPL-001` が完了済み
- 既存テスト（update-TC-01〜06）が全パスしている
- Vitest の `fs` モックまたはテスト用フィクスチャの利用方法を理解している

### 3.2 依存タスク

- `TASK-SC-CREATOR-UPDATE-IMPL-001`（完了済み）
- `TASK-SC-UPDATE-MODE-DIFF-SEMANTICS-001`（先行して完了推奨）

### 3.3 必要な知識

- Vitest を使ったファイルシステムモックまたはテンポラリディレクトリを使った統合テストの書き方
- `SkillCreatorService` の `runUpdateWorkflow()` と `skillPath` パラメータの仕様

### 3.4 推奨アプローチ

- `tmp` ディレクトリにテスト用 SKILL.md を作成し、`skillPath` として渡して update を実行する
- 実行後に生成される `StructurePlanJson` の内容を検証する
- テスト後に `tmp` ディレクトリを削除してクリーンアップする

## 4. 実行手順

### Phase構成

| Phase | フェーズ名 | 概要                               |
| ----- | ---------- | ---------------------------------- |
| 1     | 設計       | テストケース設計とフィクスチャ準備 |
| 2     | 実装       | テストコード実装                   |
| 3     | 検証       | テスト実行と確認                   |

### Phase 1: 設計

#### 目的

テストケースとフィクスチャを設計する。

#### 手順

1. `skillPath` 指定時のフロー仕様を `SkillCreatorService.ts` で確認する
2. テスト用 SKILL.md フィクスチャの内容を設計する（最小限の frontmatter と body）
3. テストケースを列挙する（正常系・異常系・フォールバック）

#### 成果物

テストケース設計書（メモ）

#### 完了条件

テストケースが列挙されていること

---

### Phase 2: 実装

#### 目的

統合テストを実装する。

#### 手順

1. テスト用 SKILL.md フィクスチャを `__tests__/fixtures/` に作成する
2. `skillPath` を指定した update フローの統合テストを追加する
3. フォールバック連鎖の統合テストを追加する

#### 成果物

追加されたテストケース

#### 完了条件

テストコードが実装されていること

---

### Phase 3: 検証

#### 目的

テストが正しく動作することを確認する。

#### 手順

1. `pnpm --filter @repo/desktop test` を実行する
2. 新規テストがパスすることを確認する
3. 既存テストへの回帰がないことを確認する

#### 成果物

テスト実行結果

#### 完了条件

全テストパス
