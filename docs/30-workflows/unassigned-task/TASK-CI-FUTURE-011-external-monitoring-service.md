## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-CI-FUTURE-003 にて GitHub Actions Summary に CI キャッシュ状態が出力されるようになった。
TASK-CI-FUTURE-009 ではリポジトリ内でのトレンド蓄積・可視化を、
TASK-CI-FUTURE-010 では Slack 通知を計画している。

これらの内部ソリューションは低コストで実装できる反面、次の限界がある：

- データ保存期間が GitHub Actions artifacts の制限（90日）に縛られる
- 複数リポジトリにまたがるダッシュボードが難しい
- アラートの高度なルール（例: 異常値検出、複合条件）が GitHub Actions の `if:` 構文では難しい
- PagerDuty 等のインシデント管理ツールとの統合ができない

Datadog / Grafana Cloud 等の外部モニタリングサービスを導入することで、
これらの制約を解消できる可能性がある。

### 1.2 問題点・課題

- 内部ソリューションはシンプルな閾値アラートに限定される
- CI メトリクスを他の APM / インフラメトリクスと横断的に可視化できない
- 長期（90日超）のトレンドデータが内部ソリューションでは管理困難

### 1.3 放置した場合の影響

- CI キャッシュ健全性の観測可能性が低いまま推移する
- ただし TASK-CI-FUTURE-003/006/007 の内部ソリューションで当面の需要は満たせるため、
  短期的な影響は限定的

## 2. 何を達成するか（What）

### 2.1 目的

Datadog / Grafana Cloud / Prometheus 等の外部モニタリングサービスに
CI キャッシュ状態メトリクスを送信し、統合ダッシュボードおよび高度なアラートを実現する。

### 2.2 最終ゴール

1. CI 実行ごとにキャッシュ状態メトリクスが外部サービスに送信される
2. 外部ダッシュボードでキャッシュヒット率の長期トレンドが確認できる
3. 複合条件アラート（例: 3日間連続でミス率40%超）が設定できる
4. 他のシステムメトリクスとの横断分析が可能になる

### 2.3 スコープ

#### 含むもの

- 外部モニタリングサービス（Datadog を想定）の選定・評価
- GitHub Actions から Datadog API へメトリクスを送信するステップの実装
- 基本ダッシュボードの設定（キャッシュヒット率・状態別件数）
- アラートポリシーの設定

#### 含まないもの

- APM（アプリケーションパフォーマンスモニタリング）の本格導入
- インフラ全体の監視ダッシュボード構築
- Datadog 以外のサービスの並行評価（まず1サービスに絞る）

### 2.4 成果物

- GitHub Actions ワークフロー内のメトリクス送信ステップ
- Datadog ダッシュボード定義（JSON / Terraform）
- アラートポリシー設定
- セットアップ手順ドキュメント

## 3. どのように実行するか（How）

### 3.1 前提条件

- TASK-CI-FUTURE-003 が完了しており、`cache-kind` / `cache-status` output が利用可能
- 外部モニタリングサービスのアカウントが準備されている（Datadog 等）
- GitHub Secrets に API キーが設定可能な権限を持つ管理者が存在する
- 月額コストの予算承認が得られていること（**重要**: Datadog は有料サービス）

### 3.2 依存タスク

- TASK-CI-FUTURE-003（完了済み）: `cache-kind` output の実装
- TASK-CI-FUTURE-009（未実施）: 内部トレンド蓄積（並行検討）
- TASK-CI-FUTURE-010（未実施）: Slack アラート（並行検討）

### 3.3 必要な知識

- Datadog Metrics API（`POST /api/v1/series`）の仕様
- Datadog ダッシュボード JSON 定義の構造
- GitHub Actions Secrets の管理
- Terraform を使った Datadog リソース管理（オプション）

### 3.4 推奨アプローチ

#### メトリクス送信方式

```yaml
# .github/actions/pnpm-install-retry/action.yml 内に追加
- name: Datadogメトリクス送信
  if: env.DD_API_KEY != ''
  shell: bash
  env:
    DD_API_KEY: ${{ inputs.datadog-api-key }}
    CACHE_KIND: ${{ steps.cache-status-check.outputs.cache-kind }}
    REPO: ${{ github.repository }}
    JOB: ${{ github.job }}
  run: |
    # cache_kind を数値メトリクスに変換
    # exact=1, fallback=0.5, miss=0
    case "$CACHE_KIND" in
      exact)   METRIC_VALUE=1 ;;
      fallback) METRIC_VALUE=0.5 ;;
      miss)    METRIC_VALUE=0 ;;
      *)       METRIC_VALUE=0 ;;
    esac

    TIMESTAMP=$(date +%s)
    curl -X POST "https://api.datadoghq.com/api/v1/series" \
      -H "DD-API-KEY: ${DD_API_KEY}" \
      -H "Content-Type: application/json" \
      -d "{
        \"series\": [{
          \"metric\": \"ci.cache.hit_rate\",
          \"points\": [[${TIMESTAMP}, ${METRIC_VALUE}]],
          \"tags\": [\"repo:${REPO}\", \"job:${JOB}\", \"cache_kind:${CACHE_KIND}\"]
        }]
      }"
```

#### コスト考慮

Datadog は Custom Metrics の数に応じた従量課金。
`ci.cache.hit_rate` は1メトリクスだが、タグの組み合わせ（repo×job×cache_kind）で
Custom Metrics のカウントが増加する点に注意。

## 4. 実行手順

### Phase 1: サービス選定と費用対効果評価

#### 目的

外部モニタリングサービスの選定と導入コストの評価を行う。

#### 手順

1. 選定候補を評価する

| サービス                             | 無料枠                     | CI メトリクス向き | 月額目安           |
| ------------------------------------ | -------------------------- | ----------------- | ------------------ |
| Datadog                              | Custom Metrics 500まで無料 | ◎                 | $15〜/月（超過時） |
| Grafana Cloud                        | 10,000 series まで無料     | ○                 | 無料枠で対応可能   |
| Prometheus + Grafana（セルフホスト） | 無料                       | △（運用コスト大） | インフラコストのみ |

2. プロジェクト規模・予算に応じてサービスを選定する
3. 選定理由と予算を文書化する
4. アカウント作成と API キーの発行を行う

#### 完了条件

- サービスが選定され、アカウントが作成されている
- API キーが GitHub Secrets に登録されている

---

### Phase 2: メトリクス送信ステップの実装

#### 目的

GitHub Actions から選定サービスにメトリクスを送信する実装を行う。

#### 手順

1. `action.yml` に `datadog-api-key`（または選定サービスの）input を追加する
2. メトリクス送信ステップを実装する（上記サンプル参照）
3. `ci.yml` から secrets 経由で API キーを渡す修正を行う
4. テスト送信でメトリクスが外部サービスに届くことを確認する

#### 完了条件

- CI 実行後にメトリクスが外部サービスのダッシュボードに表示される

---

### Phase 3: ダッシュボードとアラートの設定

#### 目的

外部サービス上でキャッシュヒット率のダッシュボードとアラートを設定する。

#### 手順

1. キャッシュヒット率の時系列グラフを作成する
2. ジョブ別・リポジトリ別のフィルタリングを設定する
3. アラートポリシーを設定する（例: 直近1時間のミス率が40%超）
4. ダッシュボード定義を JSON / Terraform でエクスポートし、バージョン管理に追加する

#### 完了条件

- ダッシュボードが表示される
- アラートポリシーが設定されている
- ダッシュボード定義がリポジトリに保存されている

## 5. 完了条件チェックリスト

### 機能要件

- [ ] CI 実行ごとにキャッシュ状態メトリクスが外部サービスに送信される
- [ ] 外部ダッシュボードでキャッシュヒット率の長期トレンドが確認できる
- [ ] アラートポリシーが設定されており、閾値超過時に通知が届く

### 品質要件

- [ ] メトリクス送信ステップが失敗しても CI 全体はブロックされない（`continue-on-error: true`）
- [ ] API キーがログに露出しない（`--silent` オプション使用）
- [ ] ダッシュボード定義がコードとして管理されている（Infrastructure as Code）

### ドキュメント要件

- [ ] 外部サービスのセットアップ手順（アカウント作成〜API キー登録）が記述されている
- [ ] ダッシュボードとアラートの設定内容が文書化されている

## 7. リスクと対策

| リスク                                                         | 影響度 | 発生確率 | 対策                                                                        |
| -------------------------------------------------------------- | ------ | -------- | --------------------------------------------------------------------------- |
| Datadog の Custom Metrics 超過で予想外のコストが発生する       | 高     | 中       | タグの cardinality を最小限に抑える設計にする（job タグをグループ化する等） |
| 外部サービスのAPI仕様変更で送信が失敗する                      | 中     | 低       | `continue-on-error: true` で CI への影響をゼロにする                        |
| API キーが git 履歴に混入する                                  | 高     | 低       | Secrets のみで管理し、hardcode を禁止するルールを CLAUDE.md に追記する      |
| サービス選定後に「やはり別サービスが良かった」となる移行コスト | 中     | 中       | Phase 1 でサービス選定を丁寧に行い、移行コストも見積もっておく              |

## 9. 備考

### 苦戦箇所【記入必須】

TASK-CI-FUTURE-003 の実装と本タスクの設計から導出した知見：

| 症状                                                            | 原因                                                                                                                                                                  | 対応                                                                     | 再発防止                                                                                                               |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Datadog Custom Metrics の課金体系が複雑でコスト見積もりが難しい | タグの組み合わせ数（cardinality）が Custom Metrics のカウントに直結する。`job` タグが17シャードある場合、`cache_kind` 3値 × 17シャード = 51 Custom Metrics 消費になる | タグの cardinality を事前に計算し、無料枠内に収まるか確認する            | Phase 1 でカスタムメトリクス数の見積もりを必須手順とする                                                               |
| TASK-CI-FUTURE-003 で意図的にスコープ外とした理由               | 外部サービス導入は費用対効果の評価・チーム合意・予算承認が必要なため、個人の実装タスクとして完結できない。また内部ソリューション（006/007）で当面の需要が満たせる     | 内部ソリューションの運用実績を積んでから本タスクの必要性を改めて評価する | 外部有料サービス導入はチーム全体の意思決定が必要なため、技術検証フェーズと予算承認フェーズを明確に分けてタスク設計する |

### 補足事項

- 優先度「低」の理由: TASK-CI-FUTURE-009/007 の内部ソリューションで当面の需要は満たせるため
- 本タスクは「大規模」の見積もりだが、実装自体は数ステップの追加で済む。
  大規模になる理由はサービス選定・契約・予算承認・ダッシュボード設計等の非実装作業が大部分を占めるため
- Grafana Cloud の無料枠（10,000 series）であれば、本タスクの規模では無償で導入できる可能性がある。
  Phase 1 でコスト試算を行うことを強く推奨する
