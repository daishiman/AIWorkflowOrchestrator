## 1. なぜこのタスクが必要か（Why）

### 背景

TASK-FIX-CONVERSATION-IPC-HANDLER-REGISTRATION の再監査で、`conversationHandlers.ts` 内の7ハンドラのうち **conversation:search だけ** P42 準拠の3段バリデーション（型チェック → 空文字列 → `trim()` 空文字列）が欠落していたことが発覚した。他の6ハンドラ（create/get/list/add-message/update-title/delete）は正しく実装されていた。

これは「同一ファイル内のハンドラグループで、1つだけバリデーションパターンが異なる」という **グループ内不整合** パターンである。既存の UT-9A-B-001（IPC 入力バリデーション標準化）はハンドラ間のバリデーション品質のばらつきをファイル横断で対象としているが、**同一ファイル内のグループ内一貫性**を検証する仕組みは未整備。

### 問題点・課題

| 問題点                                                    | 影響                                                |
| --------------------------------------------------------- | --------------------------------------------------- |
| 同一ハンドラファイル内でバリデーションの有無が不揃い      | 引数を持つハンドラで P42 バリデーション漏れが生じる |
| コードレビューで1つだけ異なるパターンを目視で検出しにくい | 7ハンドラ中1つの漏れを再監査で初めて発見            |
| 自動検出の仕組みがない                                    | grep ベースの手動確認に依存                         |

### 放置した場合の影響

| 影響領域     | 影響                                                                 |
| ------------ | -------------------------------------------------------------------- |
| セキュリティ | 空白文字列がバリデーションをすり抜け、不正入力が DB に到達するリスク |
| 品質保証     | P42 準拠と宣言しながら実際は一部漏れがある状態が継続                 |
| 保守性       | 将来のハンドラ追加時に同じ漏れが再発                                 |

## 2. 何を達成するか（What）

### 目的

同一ハンドラファイル内の全ハンドラで P42 準拠バリデーションが一貫して適用されていることを自動検証するスクリプトまたはテストを作成する。

### 最終ゴール

- `apps/desktop/src/main/ipc/*.ts` 内の全ハンドラファイルに対して、引数を持つハンドラの `trim()` バリデーション適用率が 100% であることを検証
- CI で自動実行され、新規ハンドラ追加時にバリデーション漏れを即座に検出

### スコープ

**含むもの**:

- grep ベースの P42 一貫性検証スクリプト
- テストベースの精密検証
- CI 統合（既存 lint ジョブへの追加）

**含まないもの**:

- P42 バリデーション自体の新規実装（個別ハンドラの修正は別タスク）
- `ipc/` ディレクトリ以外のハンドラファイルの検証

### 成果物

| 種別 | 成果物                                 | 配置先                                                        |
| ---- | -------------------------------------- | ------------------------------------------------------------- |
| 実装 | grep ベースの P42 一貫性検証スクリプト | `scripts/verify-p42-consistency.sh`                           |
| 実装 | テストベースの検証                     | `apps/desktop/src/main/ipc/__tests__/p42-consistency.test.ts` |

### 受入基準

| AC-ID | 基準                                           | 検証方法                           |
| ----- | ---------------------------------------------- | ---------------------------------- |
| AC-01 | 全ハンドラファイルの trim() 適用率が検証される | スクリプト実行結果                 |

## 3. どのように実行するか（How）

### 前提条件

なし（独立して実行可能）

### 推奨アプローチ

#### 改善案の比較

| 案  | 方法                               | メリット                | デメリット                                            |
| --- | ---------------------------------- | ----------------------- | ----------------------------------------------------- |
| A   | grep ベースのシェルスクリプト      | 実装が簡単、CI 統合容易 | AST 解析ではないため false positive/negative の可能性 |
| B   | AST ベースの TypeScript スクリプト | 正確な解析が可能        | 実装コストが高い                                      |
| C   | Vitest テストケースで検証          | テストスイートに統合    | テスト実行時間への影響                                |

#### 推奨: 案 A + C の併用

grep スクリプトで高速検出 + テストケースで精密検証の二層構成。

### 実装課題と解決策（親タスクからの教訓）

| 課題                                            | 発見経緯                                                                                                                                                        | 解決策                                                                          | 教訓                                                               |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| conversation:search だけ P42 バリデーション漏れ | `conversationHandlers.ts` の7ハンドラのうち、search だけ userId と query の3段バリデーションが欠落。他の6ハンドラは正しく実装済みのため「P42 準拠」と思い込んだ | userId と query の両方に3段バリデーションを追加。テスト EC-VAL-07〜10 を4件追加 | 同一ファイル内でもハンドラごとにバリデーション適用状況を検証すべき |
| 引数構造の違いによるコピー漏れ                  | search ハンドラは引数構造が他と異なり（userId + query の2パラメータ）、コピーベースの実装時にバリデーション部分が漏れた可能性                                   | ハンドラ数と trim 呼び出し数を比較する自動検出スクリプトを作成                  | コピーベース実装では引数構造が異なるハンドラで漏れが生じやすい     |

## 4. 実行手順

### 概要ステップ

1. `apps/desktop/src/main/ipc/*.ts` 内の全ハンドラファイルを列挙
2. 各ファイルでハンドラ数と `trim()` 呼び出し数を比較する検出スクリプトを作成
3. バリデーション漏れがある場合に警告を出力する仕組みを実装
4. Vitest テストケースで精密検証を追加
5. CI ジョブに統合

### Phase 構成

| Phase | 名称                           | 内容                                                 |
| ----- | ------------------------------ | ---------------------------------------------------- |
| 1-3   | 要件定義・設計・レビュー       | 検出ロジック設計、CI 統合方式の決定                  |
| 4     | テスト作成                     | 検出・非検出のテストケース                           |
| 5     | 実装                           | 検出スクリプト + テストケース + CI 統合              |
| 6-7   | テスト拡充・カバレッジ         | エッジケース（引数なしハンドラ、複数引数ハンドラ等） |
| 8-10  | リファクタリング〜最終レビュー | 品質検証                                             |
| 11-13 | 手動テスト〜完了               | 文書更新・PR                                         |

## 6. 検証方法

### 実行コマンド

```bash
# grep ベースの高速検出
bash scripts/verify-p42-consistency.sh

# テストベースの精密検証
pnpm --filter @repo/desktop test -- p42-consistency
```

### テストケース

| #   | テストケース                                   | 入力条件                                     | 期待結果                              |
| --- | ---------------------------------------------- | -------------------------------------------- | ------------------------------------- |
| 1   | 全ハンドラに trim() が適用されていることを検出 | 現在の `conversationHandlers.ts`（修正後）   | 全ハンドラで trim() 適用率 100%       |
| 2   | バリデーション漏れを検出できること             | 意図的に1つのハンドラから trim() を削除      | 漏れハンドラ名を警告として出力        |
| 3   | 引数なしハンドラを除外すること                 | `conversation:list` のような引数なしハンドラ | 検証対象から除外、false positive なし |

### 同種課題の5分解決カード

1. `grep -n "ipcMain.handle\|safeRegister" <handler-file>` でハンドラ数を確認
2. `grep -n "trim()" <handler-file>` で trim 適用箇所を確認
3. ハンドラ数と trim 呼び出し数を比較し、漏れがあれば特定
4. 漏れハンドラに3段バリデーション（型チェック → 空文字列 → trim 空文字列）を追加
5. 対応するテストケース（空文字列 + 空白のみ）を追加

## 7. リスクと対策

| リスク                            | 影響度 | 発生確率 | 対策                                           |
| --------------------------------- | ------ | -------- | ---------------------------------------------- |
| 引数なしハンドラの false positive | 中     | 高       | ハンドラの引数パターンを解析して引数なしを除外 |
| grep ベースの false negative      | 中     | 中       | Vitest テストで精密検証を補完                  |
| 新規ハンドラパターンへの未対応    | 低     | 低       | 定期的にスクリプトの検出パターンを更新         |
