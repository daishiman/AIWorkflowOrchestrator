## 2. 代替案ブレインストーミング

### 代替案A: ChatView内インラインProvider/Model選択ドロップダウン

**概要**: Settings画面に遷移させる代わりに、ChatViewのヘッダー領域にコンパクトなProvider/Modelドロップダウンを配置する。

**メリット**:

- コンテキスト切替なし（画面遷移が不要）
- 会話中にモデルを切り替えられる（ChatGPT、Claude Desktopのパターン）
- Task 2のバナーが不要になり、UIがすっきりする

**デメリット**:

- LLMSelectorPanelの再利用またはcompact版の新規作成が必要
- ChatViewのヘッダー領域が複雑化する

**評価**: 現行の4タスク設計より**UX価値が高い**が、実装コストも増加する。将来タスクとして検討する価値がある。

### 代替案B: 初回起動オンボーディングウィザード

**概要**: アプリ初回起動時（またはAPIキー未設定時）に、3ステップのウィザードで Provider選択 → APIキー入力 → Model選択 を完了させる。

**メリット**:

- 初回セットアップの成功率が劇的に向上する
- Task 2のバナーがほぼ不要になる（オンボーディング完了済みユーザーには表示不要）

**デメリット**:

- 実装コストが大きい（新規画面3枚 + フロー管理）
- 既存ユーザーへの影響を考慮する必要がある

**評価**: 長期的には最も効果的だが、現時点では過剰投資。Task 2のバナーは短期的な代替策として適切。

### 代替案C: ChatView内インラインエラー + 自動リトライ

**概要**: Task 1のエラーバナーに加え、リトライ可能なエラー（NETWORK_ERROR等）は自動リトライ（最大2回、指数バックオフ）を行い、全て失敗した場合のみバナーを表示する。

**メリット**:

- 一時的なネットワーク障害でユーザーが手動操作する必要がなくなる
- エラーバナーの表示頻度が下がり、UXが向上する

**デメリット**:

- リトライ中の待ち時間が発生する（ユーザーに「反応が遅い」と感じさせるリスク）
- リトライロジックの複雑性が増す

**評価**: Task 1の設計に「自動リトライ（NETWORK_ERROR/TIMEOUT限定、最大2回）」を追加することで、少ない実装コストで価値を高められる。

### 代替案D: 統合ステータスバー

**概要**: ChatView/WorkspaceView共通のフッター付近に、現在のProvider/Model名 + 接続状態を常時表示するステータスバーを配置する。

**メリット**:

- 現在の状態が常に可視化される（Apple HIG「Clarity」原則に合致）
- エラー時はステータスバーの色が変わるだけで済む（バナーの乱立を防止）

**デメリット**:

- 画面領域を常時消費する

**評価**: Task 2（バナー）の代替ではなく補完として有効。将来タスク候補。

## 3. 類推分析

| 機能         | ChatGPT                                               | Claude Desktop                      | Cursor                           | 本アプリ（修正後）             |

| エラー表示   | メッセージバブル内にインラインエラー + リトライボタン | メッセージバブル内にエラー + 再送信 | エディタ内インラインエラー       | バナー（入力フォーム上部）     |

### 本アプリに適用可能なパターン

1. **ChatGPT/Cursorのインラインモデル選択**: ChatViewヘッダーにcompactなドロップダウンを配置するパターン。Settings遷移より圧倒的にUXが良い。ただし、既存のLLMSelectorPanelをcompactモードで再利用できる可能性がある（`compact` propsは既に存在する）。

2. **ChatGPT/Claudeのメッセージ内エラー表示**: Task 1の「入力フォーム上部のバナー」よりも、「失敗したメッセージバブル内にエラーを表示」するパターンの方が、どのメッセージが失敗したか文脈が明確。ただし、現在のchatSliceの設計（メッセージ単位のエラー状態を持たない）では実装コストが高い。

3. **CursorのAPIキー取得リンク**: Settings画面にProvider別のAPIキー取得URL（例: OpenAI Dashboard、Anthropic Console）を表示するパターン。実装コストが極めて低い（リンク1行追加）にも関わらず、初回セットアップの離脱率を大幅に下げる。

## 4. if分析

### 「もしユーザーが技術者でなかったら？」

- Task 1のエラーメッセージ `"AI機能が利用できません。アプリを再起動してください。"` は適切。ただし `"API_KEY_MISSING"` → `"APIキーが設定されていません。設定画面からAPIキーを入力してください。"` は、**APIキーとは何か**を知らない非技術者には不十分。
- **改善案**: `"AIサービスへの接続キーが設定されていません。設定画面で取得方法を確認してください。"` のように、「APIキー」という技術用語を避けるか、補足テキストを追加する。

### 「もしAPIキーを持っていなかったら？」

- Task 2のバナーは「設定画面へ」への遷移を提供するが、Settings画面に辿り着いた後の**APIキー取得フロー**が設計されていない。
- **改善案**: Settings画面のAPIキー入力欄の近くに「APIキーの取得方法」リンク（各Provider公式ページへ）を配置する。これは4タスクのスコープ外だが、未タスクとして検出すべき。

### 「もし複数のProviderを使い分けたかったら？」

- Task 3の永続化は `selectedProviderId` / `selectedModelId` の1組のみ。複数Provider間の**素早い切替**はSettings画面への往復が必要。
- ChatGPT/Cursorのようにチャット入力横にドロップダウンがあれば、会話途中でのモデル切替が可能になる。
- 現時点では単一Provider/Model運用が主要ユースケースと思われるため、4タスクのスコープとしては適切。

### 「もしネットワークが不安定な環境だったら？」

- Task 4のリトライ機能（手動）は提供されるが、**接続状態のプロアクティブな表示**がない。
- オフライン検知 → チャット入力を無効化 + 「オフラインです」表示があると、送信失敗前にユーザーに伝えられる。未タスク候補。

## 5. トレードオフ評価

### コスト対効果マトリクス

| タスク                    | 実装コスト                                      | UX改善度                       | ROI評価  |
| ------------------------- | ----------------------------------------------- | ------------------------------ | -------- |
| Task 1 (エラー表示)       | 低（chatSlice + バナーUI）                      | 高（サイレント失敗の完全解消） | **最高** |
| Task 2 (導線追加)         | 低（新コンポーネント1つ + GuidanceBlock改修）   | 中（初回設定の迷い解消）       | 高       |
| Task 3 (永続化)           | 中（persist拡張 + migrate + バリデーション）    | 高（毎回の再設定ストレス解消） | 高       |
| Task 4 (ストリームエラー) | 中-高（型定義 + マッピング + 新コンポーネント） | 中（Workspace限定の改善）      | 中       |

### 4タスクの相乗効果（プラスサム分析）

Task 1 + Task 2 の組み合わせは**最大の相乗効果**を生む:

- Task 1がエラーの「可視化」を担い、Task 2が「次のアクション」を担う
- 結果として「エラーが見える → 原因がモデル未選択だと分かる → 設定画面への導線がある → 設定完了 → チャット可能」という**完全なリカバリフロー**が成立する

Task 3はTask 2の**頻度を下げる**効果がある:

- 永続化が機能すれば、再起動後にTask 2のバナーが表示される頻度が激減する

Task 4はTask 1の**Workspace版**として一貫性を提供:

- ChatViewとWorkspaceViewでエラー体験が統一される

### 設計上のトレードオフ

**バナー位置**: Task 1のエラーバナーは「入力フォーム直上」、Task 2のガイダンスバナーは「ヘッダー下部」と異なる位置。同時に表示される場合（モデル未選択 + エラー）、バナーが2つ積み重なるリスクがある。

- **対策案**: Task 2のバナーが表示されている場合、Task 1のエラーメッセージをTask 2のバナーに統合する（エラー優先表示）。または、ChatView上部にバナースタックの最大表示数を1に制限し、優先度が高いものを表示する。

## 6. エレガンス評価

### 総合スコア: 7 / 10

| 評価軸         | スコア | 理由                                                                                                                                                                   |
| -------------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| シンプルさ     | 8/10   | 各タスクの責務が明確に分離されており、変更箇所が最小限に抑えられている                                                                                                 |
| 明確さ         | 7/10   | エラーコードから日本語メッセージへのマッピングが明示的。ただしユーザー向けメッセージに技術用語（APIキー等）が残る                                                      |
| 一貫性         | 6/10   | ChatView（Task 1）とWorkspace（Task 4）でエラー表示の仕組みが異なる（chatSlice vs useState）。将来的な統一が必要                                                       |
| Apple HIG準拠  | 7/10   | カラーパレット・角丸・フェードアニメーションは準拠。ただしTask 1のバナー自動消去5秒はHIGの「ユーザーが dismiss するまで表示」原則と矛盾する可能性がある                |
| 拡張性         | 8/10   | Task 4のStreamingErrorState型はエラーコード追加が容易。Task 3のmigrateパターンはバージョン追加に対応可能                                                               |
| コードの美しさ | 7/10   | P31/P48対策が設計段階で考慮されている点は優秀。ただしTask 1のERROR_MESSAGESがコンポーネント内定数であり、Task 4のmapLLMErrorToStreamingErrorとメッセージ定義が重複する |

### 減点理由の詳細

1. **エラーメッセージの重複** (-1): Task 1の `ERROR_MESSAGES` とTask 4の `mapLLMErrorToStreamingError` で同じエラーコード（API_KEY_MISSING, NETWORK_ERROR等）に対して異なるメッセージ定義が存在する。共通のエラーメッセージ辞書を `packages/shared` に配置すべき。

2. **バナー自動消去の設計判断** (-1): Task 1のエラーバナーが5秒で自動消去される設計は、Apple HIGの「重要な情報はユーザーのアクションで dismiss」原則と矛盾する。特にAPI_KEY_MISSINGのような設定変更が必要なエラーが5秒で消えると、ユーザーがメッセージを読み切れない可能性がある。
   - **改善案**: `retryable` なエラー（NETWORK_ERROR等）は自動消去、`retryable` でないエラー（API_KEY_MISSING等）はユーザーの明示的dismissまで表示。

3. **ChatView/Workspaceのエラー状態管理の非対称** (-1): ChatViewはZustand Store（chatSlice）でエラーを管理し、WorkspaceはuseState（useWorkspaceChatController内）で管理する。アーキテクチャの一貫性が低い。

## 7. 改善提案

### 改善提案一覧（優先度順）

#### 改善1: エラーバナーの自動消去ポリシー分岐 [Task 1 修正]

**現状**: 全エラーが5秒で自動消去される。
**提案**: エラーの `action` フィールドに基づき消去ポリシーを分岐する。

```
retryable === true (NETWORK_ERROR, TIMEOUT): 5秒自動消去 + リトライボタン
retryable === false (API_KEY_MISSING等): ユーザー dismiss まで表示 + アクションボタン
```

**効果**: Apple HIG準拠度が向上し、重要なエラーの見逃しを防止する。
**コスト**: Task 1の設計に条件分岐1つ追加。低コスト。

#### 改善2: エラーメッセージ辞書の共通化 [Task 1 + Task 4 横断]

**現状**: Task 1の `ERROR_MESSAGES` とTask 4の `mapLLMErrorToStreamingError` で同一エラーコードに異なるメッセージが定義される。
**提案**: `apps/desktop/src/renderer/constants/errorMessages.ts` に共通辞書を作成し、両タスクから参照する。

```typescript
// errorMessages.ts
export const LLM_ERROR_MESSAGES: Record<
  string,
  { message: string; retryable: boolean }
> = {
  API_KEY_MISSING: {
    message:
      "APIキーが設定されていません。設定画面からAPIキーを入力してください。",
    retryable: false,
  },
  NETWORK_ERROR: {
    message: "ネットワークエラーが発生しました。接続を確認してください。",
    retryable: true,
  },
  // ...
};
```

**効果**: メッセージの一貫性が保証され、将来のエラーコード追加が1箇所で完結する。
**コスト**: 新規ファイル1つ + 参照変更。低コスト。

#### 改善3: GuidanceBlockへのonAction接続 [Task 2 修正]

**現状**: `WorkspaceChatPanel.tsx` L38-43で `GuidanceBlock` に `actionLabel="Settings を開く"` を渡しているが、`onAction` propsが渡されていない。ボタンが表示されない（GuidanceBlock内部で `actionLabel && onAction` の両方が必要）。
**提案**: `onAction` を渡す。

```typescript
<GuidanceBlock
  variant="blocked"
  message="AIモデルが選択されていません。Settings で使用するモデルを設定してください。"
  actionLabel="Settings を開く"
  onAction={() => setCurrentView("settings")}  // 追加
/>
```

**効果**: 既存の「Settings を開く」ボタンが実際に機能するようになる。現状では**ボタンが表示されていない既存バグ**。
**コスト**: 1行追加。極めて低コスト。
**重要度**: **P0** — これはTask 2の設計以前に、現在のコードに存在するバグである。

#### 改善4: ChatViewヘッダーに現在のモデル名を表示 [将来タスク候補]

**現状**: ChatViewヘッダーに「AIチャット」としか表示されていない。
**提案**: サブタイトル部分（現在RAGステータスが表示されている箇所）に、選択中のProvider/Model名を追加する。

```
AIチャット
Anthropic / Claude 3.5 Sonnet  |  RAG有効
```

**効果**: ユーザーが現在どのモデルで会話しているか常に把握できる（Apple HIG「Clarity」）。
**コスト**: 中（セレクタ追加 + UI変更）。4タスクのスコープ外だが、未タスクとして検出すべき。

#### 改善5: Settings画面にAPIキー取得リンクを追加 [将来タスク候補]

**現状**: Task 2のバナーがSettings画面に遷移させるが、APIキーの取得方法への導線がない。
**提案**: Settings画面のAPIキー入力欄に「キーの取得方法」リンクを配置する。

| Provider  | リンク先                             |
| --------- | ------------------------------------ |
| OpenAI    | https://platform.openai.com/api-keys |
| Anthropic | https://console.anthropic.com/       |

**効果**: 非技術者の初回セットアップ完了率が向上する。
**コスト**: 極めて低（リンク追加のみ）。4タスクのスコープ外。

#### 改善6: ChatViewへのインラインモデルセレクタ導入 [将来タスク候補]

**現状**: モデル切替にはSettings画面への遷移が必要。
**提案**: ChatViewヘッダー右側に `LLMSelectorPanel` の `compact` モードを配置する（既に `compact` propsが存在する）。

**効果**: ChatGPT/Cursorと同等のモデル切替UXを実現する。Task 2のバナーが不要になる。
**コスト**: 中-高。`LLMSelectorPanel` のcompactモード調整 + ChatView統合。

## 付録: 検出した既存コードの問題

### 問題1: GuidanceBlock onAction 未接続（P0）

**ファイル**: `apps/desktop/src/renderer/views/WorkspaceView/WorkspaceChatPanel.tsx` L38-43

### 問題2: ChatViewのエラー状態が未使用

```typescript
const [error] = useState<string | null>(null);
```

`setError` が使われておらず、`error` は常に `null`。L163-165のエラー表示パスは到達不能コード（dead code）。Task 1の設計では `chatSlice` にエラー状態を追加するため、このローカルstateは削除してよい。

### 問題3: callLLMAPIのエラー握りつぶし

**ファイル**: `apps/desktop/src/renderer/store/slices/chatSlice.ts` L96-99

```typescript
return { success: false }; // L95: response.success が false
return { success: false }; // L98: catch ブロック
```

いずれもエラー情報を返していない。Task 1の設計（`error` フィールド追加）で正しく対処されている。

### 問題4: LLMSelectorPanelのTailwindカラーがApple HIG非準拠

**ファイル**: `apps/desktop/src/renderer/components/llm/LLMSelectorPanel.tsx`

`bg-white dark:bg-gray-800`, `border-gray-200 dark:border-gray-700` 等のTailwind標準カラーが使用されており、01-architecture.mdのルール「Tailwind Slate（青みがかった灰色）を light/dark テーマに使用しない — Apple の中性灰を使う」に違反している。CSS変数（`var(--bg-primary)` 等）を使用すべき。

## まとめ

4タスクの設計は全体として**堅実かつ実用的**であり、最も深刻な問題（サイレント失敗）を最小の変更で解消する方針は正しい。特にTask 1（エラー可視化）とTask 2（導線追加）の組み合わせによるリカバリフローの成立は、4タスクの相乗効果として高く評価できる。

一方で、以下の3点は設計段階で対処すべき:

1. **GuidanceBlockのonAction未接続**（既存バグ、P0）
2. **エラーバナーの自動消去ポリシー分岐**（Task 1設計の改善）
3. **エラーメッセージ辞書の共通化**（Task 1 + Task 4の一貫性）

長期的には、ChatViewへのインラインモデルセレクタ導入（改善6）が最もUX価値の高い改善であり、これが実現すればTask 2のバナーは不要になる。
