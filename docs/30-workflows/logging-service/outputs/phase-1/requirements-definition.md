## 1. 概要

### 1.1 目的

ファイル変換処理のログを構造化して記録するサービスを実装する。変換処理の追跡、デバッグ、監査を可能にし、システムの可観測性を向上させる。

### 1.2 スコープ

**スコープ内**:

- ConversionLoggerクラスの実装
- INFO/WARN/ERRORレベルのログ記録機能
- バッファリングによる効率的なログ保存
- 自動フラッシュ機能（時間ベース・サイズベース）
- バッチログ記録機能
- LogRepositoryを通じたDB永続化
- Zodスキーマによる型定義と検証

**スコープ外**:

- LogRepositoryの実装（既存または別タスク）
- ログの検索・分析機能（CONV-05-02で対応）
- ログのローテーション・アーカイブ機能
- 外部ログサービスへの転送（CloudWatch, Datadog等）
- リアルタイムログストリーミング

### 1.3 用語定義

| 用語             | 定義                                                           |
| ---------------- | -------------------------------------------------------------- |
| ConversionLog    | ファイル変換処理の単一ログエントリ                             |
| ConversionLogger | ログ記録を担当するサービスクラス                               |
| LogRepository    | ログのDB永続化を担当するリポジトリインターフェース             |
| バッファリング   | ログをメモリに一時保存し、まとめてDBに書き込む仕組み           |
| フラッシュ       | バッファ内のログをDBに書き込む操作                             |
| 自動フラッシュ   | 一定時間経過またはバッファサイズ到達時の自動書き込み           |
| LogLevel         | ログの重要度（info, warn, error）                              |
| LogAction        | ログの対象アクション（convert, restore, delete, chunk, embed） |

### 3.2 機能要件詳細

#### FR-001: INFOログ記録

**概要**: 情報レベルのログを記録する

**アクター**: 変換処理サービス

**前提条件**:

- ConversionLoggerインスタンスが生成済み
- LogRepositoryが注入済み

**トリガー**: info()メソッド呼び出し

**基本フロー**:

1. ConversionLogInputを受け取る
2. UUIDを生成し、タイムスタンプを付与
3. level="info"でConversionLogを生成
4. バッファに追加
5. Result<ConversionLog, Error>を返却

**事後条件**:

- ログがバッファに追加されている
- バッファサイズ上限到達時は自動フラッシュ

**受け入れ基準**: AC-001参照

---

#### FR-002: WARNログ記録

**概要**: 警告レベルのログを記録する

**アクター**: 変換処理サービス

**トリガー**: warn()メソッド呼び出し

**基本フロー**: FR-001と同様（level="warn"）

**受け入れ基準**: AC-002参照

---

#### FR-003: ERRORログ記録

**概要**: エラーレベルのログを記録する（スタックトレース含む）

**アクター**: 変換処理サービス

**前提条件**:

- ConversionLoggerインスタンスが生成済み

**トリガー**: error()メソッド呼び出し

**基本フロー**:

1. ConversionLogInputとオプションのErrorオブジェクトを受け取る
2. Errorオブジェクトからmessageとstackを抽出
3. detailsにエラー情報を追加
4. level="error"でConversionLogを生成
5. バッファに追加

**事後条件**:

- ログにerrorStackが含まれている（Errorオブジェクト提供時）

**受け入れ基準**: AC-003参照

---

#### FR-004: バッファリング

**概要**: ログをメモリバッファに蓄積し、効率的にDB書き込みを行う

**設計仕様**:

- デフォルトバッファサイズ: 100件
- バッファはConversionLog[]として保持
- バッファ操作はスレッドセーフ（シングルスレッド前提）

**受け入れ基準**: AC-004参照

---

#### FR-005: サイズベース自動フラッシュ

**概要**: バッファサイズが上限に達した時点で自動的にフラッシュ

**トリガー**: バッファサイズ >= bufferSize

**基本フロー**:

1. ログ追加時にバッファサイズを確認
2. 上限到達時にflush()を実行
3. LogRepository.bulkInsert()でDB保存
4. バッファをクリア

**受け入れ基準**: AC-005参照

---

#### FR-006: 時間ベース自動フラッシュ

**概要**: 一定時間経過で自動的にフラッシュ

**設計仕様**:

- デフォルトインターバル: 5000ms
- setIntervalによる定期実行
- disposeで停止

**受け入れ基準**: AC-006参照

---

#### FR-007: バッチログ記録

**概要**: 複数のログを一括で記録する

**アクター**: 変換処理サービス

**トリガー**: batch()メソッド呼び出し

**基本フロー**:

1. Array<{ level: LogLevel; input: ConversionLogInput }>を受け取る
2. 各要素に対してlog()を実行
3. 全ログをResult<ConversionLog[], Error>で返却

**受け入れ基準**: AC-007参照

---

#### FR-008: 手動フラッシュ

**概要**: 明示的にバッファをフラッシュする

**トリガー**: flush()メソッド呼び出し

**基本フロー**:

1. バッファが空の場合はok(undefined)を返却
2. バッファの内容をコピー
3. バッファをクリア
4. LogRepository.bulkInsert()を実行
5. 結果をResult<void, Error>で返却

**受け入れ基準**: AC-008参照

---

#### FR-009: リソース解放（dispose）

**概要**: ロガーのリソースを解放する

**トリガー**: dispose()メソッド呼び出し

**基本フロー**:

1. 自動フラッシュタイマーを停止
2. 残存バッファをフラッシュ

**受け入れ基準**: AC-009参照

### 4.1 非機能要件一覧

| ID      | カテゴリ       | 要件名           | 優先度 |

### 4.2 パフォーマンス要件

#### NFR-001: ログ記録応答時間

**指標**: 単一ログ記録の応答時間
**目標値**: 1ms以内（バッファ追加のみの場合）
**測定方法**: ユニットテストでの計測
**重要度**: High
**根拠**: 変換処理のパフォーマンスに影響を与えないため

### 4.3 信頼性要件

#### NFR-002: データ損失防止

**指標**: ログ損失率
**目標値**: 0%（正常終了時）
**測定方法**: 統合テストでの検証
**重要度**: High
**根拠**: 監査・デバッグに必要なログが欠損しないため

### 4.4 保守性要件

#### NFR-003: 型安全性

**指標**: TypeScript strict mode準拠
**目標値**: 100%
**測定方法**: tsc --noEmit
**重要度**: High
**根拠**: 実行時エラーの防止、IDE補完の活用

### 4.5 テスト容易性要件

#### NFR-004: モック可能な設計

**指標**: 依存注入によるテスト容易性
**目標値**: LogRepositoryをモック可能
**測定方法**: ユニットテストでの検証
**重要度**: High
**根拠**: 単体テストの独立性確保

## 5. 制約条件

### 5.1 技術的制約

- TypeScript 5.x を使用
- Zodによるスキーマ定義・バリデーション
- Result型によるエラーハンドリング（Railway Oriented Programming）
- Drizzle ORM経由でのDB操作

### 5.2 ビジネス制約

- 既存のBaseRepositoryパターンに準拠
- 既存の型定義パターン（Branded Types等）に準拠

### 5.3 運用制約

- Node.js環境での動作
- シングルスレッド前提（Worker Threads未使用）

### 7.1 外部システム依存

| システム          | 依存内容         | リスク                     |

```
FR-006 → FR-009（タイマーがdisposeで停止される）

```
