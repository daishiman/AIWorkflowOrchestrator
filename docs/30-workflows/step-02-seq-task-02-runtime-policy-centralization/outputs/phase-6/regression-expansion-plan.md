## 1. 既知 Pitfall への回帰テスト観点

### 1.1 P31: Zustand Store Hooks 無限ループ

| 観点                          | 検証内容                                                                                  | 検証方法                                                           |
| ----------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| policy 更新時の再レンダー回数 | PolicySlice の policy 値更新時に Renderer コンポーネントの再レンダーが1回のみ発生すること | `renderHook` + `renderCount` カウンタで再レンダー回数を計測        |
| useShallow 適用確認           | policy セレクタが `useShallow` でラップされていること                                     | セレクタ定義コードの静的レビュー + テストで shallow 比較動作を確認 |
| 個別セレクタ使用              | 合成 Store Hook（`usePolicyStore()` 等）を `useEffect` 依存配列に含めていないこと         | `grep -rn "useEffect.*usePolicyStore"` でゼロヒットを確認          |

### 1.2 P48: useShallow 未適用による派生セレクタ無限ループ

| 観点                            | 検証内容                                                                                | 検証方法                                                             |
| ------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 派生配列セレクタの shallow 比較 | `.filter()` / `.map()` で配列を返す policy セレクタに `useShallow` が適用されていること | セレクタ定義コードのレビュー + `renderHook` テストで無限ループ非発生 |
| 新規セレクタ追加時の基準        | セレクタが新規参照を返す場合は `useShallow` 必須であることをテストケース名に明記        | テストケース名に「useShallow適用確認」を含める                       |

### 1.3 P50: 既実装防御の発見による Phase 転換

| 観点             | 検証内容                                                                              | 検証方法                                                     |
| ---------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 実装前の現状確認 | Phase 4 開始前に対象ファイルの `git log` と現在コードを確認し、既実装の判定を行うこと | Phase 4 チェックリストに「既存実装確認」ステップを追加       |
| 重複実装防止     | 既存の `RuntimeResolver` に同等ロジックが存在しないことを確認してからテスト作成       | `grep -rn "resolve.*authMode" apps/desktop/src/main/` で確認 |

### 1.4 P64: Surface 未知値への fallback 動作

| 観点                          | 検証内容                                                                                   | 検証方法                                                            |
| ----------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| unknown surface の拒否        | `SurfaceType` 型外の文字列が渡された場合にコンパイルエラーまたは実行時エラーが発生すること | TypeScript の exhaustive check（`never` 型）+ 実行時 `default` 分岐 |
| fallback 時のエラーメッセージ | 不正 surface 値がエラーメッセージに含まれること（デバッグ容易性）                          | テストで `expect(error.message).toContain(unknownSurface)` を検証   |

### 1.5 P65: 連続呼び出しの冪等性

| 観点                    | 検証内容                                                                                      | 検証方法                                            |
| ----------------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| 同一 surface の重複実行 | 同一 `(authMode, apiKey, surface)` で `resolve()` を2回連続呼び出した場合、同一結果を返すこと | 2回呼び出しの結果を `deepStrictEqual` で比較        |
| 副作用の非蓄積          | 連続呼び出しで内部状態が蓄積されないこと（ステートレス設計の検証）                            | 3回連続呼び出し後に結果が初回と同一であることを確認 |

## 2. Surface 横断連続実行シナリオ

### 2.1 シナリオ A: Chat → Agent → Skill の3 surface 連続実行

| ステップ | Surface | authMode | apiKey   | 期待される判定 | 検証ポイント                                     |
| -------- | ------- | -------- | -------- | -------------- | ------------------------------------------------ |
| 1        | chat    | api_key  | 有効キー | allowed        | Chat surface の policy が独立判定されること      |
| 2        | agent   | api_key  | 有効キー | allowed        | Agent surface の policy が Chat と独立であること |
| 3        | skill   | api_key  | 有効キー | allowed        | Skill surface の policy が前2つと独立であること  |

**検証**: 各ステップの `RuntimeDecision` が独立したオブジェクトであり、前ステップの結果を参照していないこと。

### 2.2 シナリオ B: 中途 blocked 時の後続 surface 非影響

| ステップ | Surface | authMode | apiKey   | 期待される判定 | 検証ポイント                               |
| -------- | ------- | -------- | -------- | -------------- | ------------------------------------------ |
| 1        | chat    | api_key  | 有効キー | allowed        | 正常判定                                   |
| 2        | agent   | api_key  | 空文字列 | blocked        | apiKey 不正で blocked                      |
| 3        | skill   | api_key  | 有効キー | allowed        | Agent の blocked が Skill に伝播しないこと |

**検証**: ステップ2で blocked を返した後も、ステップ3は独立して allowed を返すこと。resolve() がステートレスであることの証明。

### 2.3 シナリオ C: HandoffGuidance の contextSummary 検証

| ステップ | Surface       | 期待される contextSummary 内容                       |
| -------- | ------------- | ---------------------------------------------------- |
| 1        | chat          | `contextSummary` に `"chat"` が含まれること          |
| 2        | agent         | `contextSummary` に `"agent"` が含まれること         |
| 3        | skill         | `contextSummary` に `"skill"` が含まれること         |
| 4        | skill-creator | `contextSummary` に `"skill-creator"` が含まれること |

**検証**: `buildForSurface(surface)` が生成する `HandoffGuidance.contextSummary` に正しい surface 名が埋め込まれていること。
