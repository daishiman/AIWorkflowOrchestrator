## 実装から得られた知見

### 知見1: 型設計の改善 — `category: SkillCategory[]`

単一値型から配列型への変更により、将来的なカテゴリ追加が容易になった。
単一の `SkillCategory` ではなく `SkillCategory[]` を持つことで、
マルチカテゴリ対応や将来の拡張に際してインターフェース変更が不要になる。
型レベルで「複数選択を想定した設計」が明示されるため、
実装者の意図がコードを読む全員に伝わりやすくなる。

### 知見2: トグルロジックの設計 — `??` 演算子による null→配列変換

`handleCategoryClick` において `??` 演算子を活用した `null`→配列変換は、
状態が未初期化（null）の場合でも安全に配列として扱える自然な設計である。
`previousState ?? []` のパターンにより、明示的な null チェック分岐を排除でき、
コードの見通しが向上する。

### 知見3: ProgressBar計算の境界値保証 — `Math.max(1, answeredCount)`

`currentQuestion` の計算に `Math.max(1, answeredCount)` を用いることで、
回答数がゼロのときに分母が0になるゼロ除算を防ぎつつ、
「最低でも1問目を表示する」という UX 仕様を数式で直接表現できる。
シンプルかつ理解しやすい実装として今後のコードレビューでも参照可能。

### 知見4: CSS変数統一によるメンテナンス性向上

Tailwind 固定値から CSS 変数へ統一したことで、テーマ変更時に全ボタンが
自動的に追従するようになった。デザイントークンを一箇所で管理できるため、
将来のブランドカラー変更やダークモード対応のコストが大幅に低減される。

### 知見5: subpath export に閉じた型変更方針

型変更の影響範囲をサブパスエクスポート内に限定したことで、
ルートバレル（`index.ts`）への影響を最小化できた。
変更の局所化は差分レビューの容易さにも直結し、PR のレビュアー負担を軽減する。

## 今後のスキル改善提案

1. **型設計レビューチェックリスト化**: `SkillCategory[]` への変更のように、
   将来拡張を見越した配列型採用基準をコーディング規約として明文化する。

2. **境界値テストの標準テンプレート追加**: `Math.max(0, n)` / `Math.max(1, n)`
   パターンが出現する箇所に対して、ゼロ入力テストケースをスキルのテスト雛形に組み込む。

3. **CSS変数マッピング表の整備**: テーマトークンと Tailwind クラスの対応表を
   `packages/ui/` 配下にドキュメント化し、デザイナーとエンジニアが参照できるようにする。

4. **subpath export ルールのLintチェック追加**: ルートバレルへの不要な再エクスポートを
   ESLint カスタムルールで検出し、意図しない公開 API 拡張を防ぐ。
