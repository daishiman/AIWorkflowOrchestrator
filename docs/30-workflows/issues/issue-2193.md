## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-CI-FUTURE-003 にて、GitHub Actions の `pnpm-install-retry` カスタムアクション内に
キャッシュヒット率の判定ステップを追加し、各 CI 実行の Summary に 3 状態（完全ヒット・
フォールバックヒット・キャッシュミス）を出力できるようになった。

しかし、現在の仕組みは「単一 CI 実行の状態を把握する」に留まる。
長期トレンド（週次・月次でヒット率がどう推移しているか）を可視化する手段がなく、
キャッシュ戦略の健全性を継続的に評価できない。

### 1.2 問題点・課題

- CI 実行ごとのキャッシュ状態は Summary で確認できるが、過去データが蓄積されない
- キャッシュ劣化が「じわじわ進行」する場合（例: フォールバックヒット比率が週ごとに増加）
  を検知する手段がない
- TASK-CI-FUTURE-004 で CI 実行時間のトレンドCSVは作成予定だが、キャッシュヒット率に
  特化した可視化ダッシュボードは別途必要

### 1.3 放置した場合の影響

- キャッシュ戦略の長期的な健全性が見えなくなり、最適化効果が静かに消失するリスクがある
- 「いつからヒット率が下がったか」を遡れないため、原因調査のコストが増大する

---

## 2. 何を達成するか（What）

### 2.1 目的

キャッシュヒット率（完全ヒット・フォールバックヒット・ミスの比率）を時系列で記録・
可視化し、CI キャッシュ戦略の健全性を継続的に評価できる仕組みを構築する。

### 2.2 最終ゴール

GitHub Actions のワークフロー実行ごとにキャッシュ状態データを蓄積し、
長期トレンドを確認できる状態を実現する。

具体的な成功状態：

1. CI 実行ごとのキャッシュ状態（exact/fallback/miss）が時系列データとして蓄積される
2. 蓄積データから週次・月次のヒット率集計が可能になる
3. 可視化の手段（GitHub Pages / グラフ画像 / Markdown サマリーのいずれか）が整備される
4. ヒット率が閾値（例: 直近30件のうちミスが40%超）を超えた場合にアラートが出力される

### 2.3 スコープ

#### 含むもの

- キャッシュ状態データの蓄積スキーム設計（CSV / JSON / GitHub Actions artifacts）
- 蓄積データから集計・可視化するスクリプトまたはワークフローの実装
- 長期トレンドアラートの実装（閾値ベース）

#### 含まないもの

- 外部モニタリングサービス（Datadog、Grafana）の導入（→ TASK-CI-FUTURE-011 参照）
- Slack / メールアラートとの連携（→ TASK-CI-FUTURE-010 参照）
- リアルタイムダッシュボード（GitHub Pages か Markdown レポートに留める）

### 2.4 成果物

- キャッシュ状態蓄積スクリプトまたはワークフロー
- 集計・可視化スクリプト
- `docs/` または `outputs/` 配下のトレンドレポート（Markdown / CSV）

## 3. どのように実行するか（How）

### 3.1 前提条件

- TASK-CI-FUTURE-003 が完了しており、`.github/actions/pnpm-install-retry/action.yml` に
  `cache-kind` / `cache-status` の `GITHUB_OUTPUT` 書き出しが実装済みであること
- `gh` CLI がインストール済みで `gh auth login` が完了していること
- GitHub Actions artifacts 機能または外部ストレージへの書き込み権限があること

### 3.2 依存タスク

- TASK-CI-FUTURE-003（完了済み）: キャッシュ判定ステップの実装
- TASK-CI-FUTURE-004（未実施）: CI 実行時間トレンドCSV（同様のデータ蓄積パターン）

### 3.3 必要な知識

- GitHub Actions の `actions/upload-artifact` / `actions/download-artifact` の仕様
- GitHub API を使った artifacts の一覧取得（`gh api repos/{owner}/{repo}/actions/artifacts`）
- bash による CSV / JSON への時系列データ追記処理
- オプション: GitHub Pages への Markdown / HTML レポート自動デプロイ

### 3.4 推奨アプローチ（設計選択肢）

| 方式                             | 概要                               | 利点       | 欠点                     |
| -------------------------------- | ---------------------------------- | ---------- | ------------------------ |
| A: Git リポジトリ内 CSV 蓄積     | CI 実行後に CSV をコミット         | シンプル   | git history が汚染される |
| B: GitHub Actions artifacts      | 実行ごとに artifact をアップロード | 非侵襲     | 90日で期限切れ           |
| C: 専用ブランチ（data ブランチ） | `data` ブランチに CSV をプッシュ   | 履歴が独立 | ブランチ管理が増える     |

推奨: **方式 B（artifacts）を短期蓄積として使い、週次で集計スクリプトを手動実行して `docs/` に Markdown レポートを生成する**ハイブリッドアプローチ。

## 4. 実行手順

### Phase 1: データ蓄積スキームの設計・実装

#### 目的

CI 実行ごとにキャッシュ状態データを蓄積する方式を決定し、実装する。

#### 手順

1. 上記の設計選択肢 A/B/C を評価し、プロジェクト方針に合う方式を選択する
2. TASK-CI-FUTURE-003 の `cache-kind` output を活用したデータ収集ステップをワークフローに追加する
3. 収集データのスキーマを定義する

```
timestamp,run_id,cache_kind,cache_status,job_name
2026-04-15T10:00:00Z,12345678,exact,✅ 完全ヒット (Exact Hit),lint
2026-04-15T10:00:00Z,12345678,miss,❌ キャッシュミス (Miss),test-desktop-shard-1
```

#### 完了条件

- データ収集スキームが確定し、実装されている
- CI 実行後にデータが蓄積されることを確認済み

---

### Phase 2: 集計・可視化スクリプトの実装

#### 目的

蓄積データから週次・月次のヒット率を集計し、Markdown レポートを生成する。

#### 手順

1. `scripts/analyze-cache-trend.sh` または Python スクリプトを作成する
2. 入力: 蓄積 CSV / artifacts
3. 出力: `docs/reports/cache-trend-YYYY-MM.md`（月次レポート）

レポート形式例:

```markdown
## キャッシュヒット率 月次レポート（2026年4月）

| 期間       | 完全ヒット | フォールバック | ミス | 合計実行数 |
| ---------- | ---------- | -------------- | ---- | ---------- |
| 2026-04-01 | 85%        | 10%            | 5%   | 40         |
| 2026-04-08 | 82%        | 12%            | 6%   | 38         |
```

#### 完了条件

- 集計スクリプトが構文エラーなく実行できる
- 月次レポートが生成される

---

### Phase 3: アラート閾値の実装と動作確認

#### 目的

長期トレンドでミス率が高止まりしている場合のアラートを実装する。

#### 手順

1. 直近 N 件（デフォルト: 30件）のデータからミス率を計算するロジックを追加する
2. ミス率が閾値（デフォルト: 40%）を超えた場合に `::warning::` アノテーションまたは
   標準エラー出力にアラートメッセージを出力する
3. 動作確認: テストデータで閾値超過を意図的に発生させ、アラートが出力されることを確認する

#### 完了条件

- 長期トレンドアラートが正常に動作する
- 誤検知・見逃しがないことを確認済み

## 7. リスクと対策

| リスク                                                                         | 影響度 | 発生確率 | 対策                                                                     |
| ------------------------------------------------------------------------------ | ------ | -------- | ------------------------------------------------------------------------ |
| GitHub Actions artifacts が90日で期限切れになりデータが消える                  | 高     | 高       | 定期的に CSV を git リポジトリにバックアップするジョブを追加する         |
| TASK-CI-FUTURE-003 の `cache-kind` output が変更された場合にデータ収集が壊れる | 中     | 低       | 収集ステップで output の存在確認を行い、存在しない場合はスキップする     |
| CI の並列ジョブが同時に同一 CSV へ書き込み、データが破損する                   | 高     | 中       | artifacts 方式を採用し、各ジョブが独立した artifact を生成する設計にする |

## 9. 備考

### 苦戦箇所【記入必須】

TASK-CI-FUTURE-003 の実装から引き継ぐ知見：

| 症状                                                                          | 原因                                                                                                                                                 | 対応                                                                               | 再発防止                                                                                        |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| キャッシュ状態を「ヒット/ミス」の二値で集計すると実態と乖離する               | `actions/cache@v4` のフォールバックヒットは `cache-hit=false` だが node_modules は復元される。二値集計ではフォールバックヒットを「ミス」と誤算定する | 3状態（exact/fallback/miss）を `GITHUB_OUTPUT` に書き出し、集計時も3状態で区別する | `cache-kind` カラムは常に exact/fallback/miss の3値のみを使用し、未定義値を許容しない設計にする |
| TASK-CI-FUTURE-003 の実装フェーズで、本タスクがスコープ外と判定され見送られた | 単一実行の状態可視化で十分と判断されたため。長期トレンドはコスト対効果のバランスでフェーズ2以降に分離された                                          | TASK-CI-FUTURE-003 を完了させてから、必要性を改めて評価して実施する                | 大きなタスクの Phase 12 で「スコープ外」を明示的に洗い出し、別タスクとして登録する              |

### 補足事項

- 本タスクは TASK-CI-FUTURE-003 の Phase 12 でスコープ外として意図的に除外された
- `TASK-CI-FUTURE-004`（CI 実行時間トレンドCSV）と設計パターンが似ているため、
  同時実施することでコードの共通化が図れる可能性がある
- 優先度が「低」の理由: TASK-CI-FUTURE-003 の単一実行可視化で当面の需要は満たせるため
