## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-FIX-4-2-SKILL-STORE-PERSISTENCE の実装過程で、electron-store の `store.get()` に対する型アサーション（`as Type`）がコンパイル時チェックのみで実行時検証をバイパスする問題が発見された。

TypeScriptの型システムは実行時には存在しないため、ストアファイルが破損・手動編集・別バージョンのアプリで変更された場合、型アサーションでは不正なデータ型を検出できない。TASK-FIX-4-2では `validateStoredSkillIds()` 関数を作成し、実行時に型検証を行う設計に修正した。

### 1.2 問題点・課題

現在のコードベースで以下の箇所が型アサーションまたはジェネリクスのみに依存している：

1. **themeHandlers.ts:78** - `store.get("theme.mode", "system") as ThemeMode`
2. **skillImportStore.ts** - `Store<SkillStoreSchema>` のジェネリクスによる型推論（実行時検証なし）
3. **SessionStorage.ts** - `store.get("sessions")` 等の複数箇所
4. **workspaceHandlers.ts** - `store.get(WORKSPACE_STORE_KEY)` の2箇所
5. **slideSettingsStore.ts** - 複数の `_store.get()` 呼び出し
6. **agent-client.ts** - `store.get("anthropic_api_key")`

これらの箇所では、ストアデータが期待する型と異なる場合にランタイムエラーが発生する。

### 1.3 放置した場合の影響

| 影響                       | 詳細                                                                         |
| -------------------------- | ---------------------------------------------------------------------------- |
| アプリケーションクラッシュ | 不正なデータ型でメソッド呼び出しエラー（例: `undefined.map()` は TypeError） |
| データ損失                 | クラッシュ復旧時にストアデータ全削除が必要になる可能性                       |
| デバッグ困難               | 型アサーション箇所はスタックトレースから原因特定が困難                       |
| ユーザー体験低下           | 設定ファイル破損で突然のクラッシュはユーザー離脱につながる                   |

## 3. どのように実行するか（How）

### 3.1 前提条件

### 3.2 依存タスク

| TASK-FIX-4-2-SKILL-STORE-PERSISTENCE | 完了 | 型バリデーションパターンの確立 |

### 3.3 必要な知識

- TypeScript 型システムと実行時検証の違い
- electron-store API（特に `get()` のデフォルト値引数）
- ユーザー定義型ガード（Type Guard）パターン

### 3.4 推奨アプローチ

TASK-FIX-4-2 で確立したパターンを適用する：

```typescript
// Before（型アサーション - 実行時検証なし）
const mode = store.get("theme.mode", "system") as ThemeMode;

// After（実行時検証あり）
interface SkillStore {
  get(key: string, defaultValue: unknown): unknown;
}

function validateThemeMode(value: unknown): ThemeMode {
  if (value === "light" || value === "dark" || value === "system") {
    return value;
  }
  console.warn(
    "[ThemeStore] Invalid theme mode, falling back to system:",
    value,
  );
  return "system";
}

const rawValue = store.get("theme.mode", "system");
const mode = validateThemeMode(rawValue);
```

### 3.5 実装課題と解決策（TASK-FIX-4-2からの知見）

| 課題                     | 苦戦した箇所                                                                  | 解決策                                                                                       |
| ------------------------ | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 型アサーションの問題認識 | 型アサーション（`as Type`）は実行時検証をバイパスするという事実の発見が遅れた | インターフェース定義で `get()` の戻り値を `unknown` に変更し、型バリデーション関数経由で使用 |
| テストでの検証           | 不正データ型のテストケース設計                                                | `mockStore.get` のモックで意図的に不正な型を返し、フォールバック動作を検証                   |
| 配列内要素の検証         | `string[]` 期待時に `[1, "valid", null]` のような混在データへの対応           | `Array.filter()` + 型ガードで有効な要素のみを抽出                                            |

## 9. 備考

### レビュー指摘の原文（該当する場合）

```
TASK-FIX-4-2-SKILL-STORE-PERSISTENCE Phase 10 最終レビューにおいて、
型アサーション（as Type）が実行時検証をバイパスする問題を発見。
他のelectron-store使用箇所にも同様のリスクが存在するため、
横展開タスクとして未タスク仕様書を作成する。
```

### 補足事項

**TASK-FIX-4-2で苦戦した箇所の詳細**

1. **型アサーションの罠**
   - TypeScriptの `as Type` は「私はこれがこの型であることを知っている」とコンパイラに伝えるだけ
   - 実行時には型情報が存在しないため、不正なデータが渡されても検出されない
   - 解決: インターフェースの戻り値型を `unknown` に変更し、バリデーション関数で明示的に検証

2. **ジェネリクスの限界**
   - `Store<Schema>` のジェネリクスはコンパイル時の型推論のみ
   - ストアファイルが手動編集されたり、別バージョンで保存された場合は検出不可
   - 解決: `get()` 呼び出し後に必ず実行時検証を行う

3. **テスト設計**
   - 不正データ型のテストは、モックの戻り値を意図的に間違った型に設定
   - `console.warn` のモックでログ出力も検証
   - 配列の場合は `Array.filter()` + 型ガードで有効要素のみを抽出

**バリデーションパターンの標準化**

このタスク完了後、以下のパターンを `patterns.md` に追加することを推奨：

```typescript
// electron-store 型バリデーションパターン
//
// 1. インターフェースで get() の戻り値を unknown に
// 2. バリデーション関数で実行時検証
// 3. 不正データは警告ログ + デフォルト値フォールバック
```
