## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

`AI_INDEX` の排他制御をどの層が持つかが未定義で、実装前に責務の置き場を決める必要がある。後続の実装タスクが迷わないよう、IPC / Service / DB のどこが管理するかを固定する。

### 1.2 問題点・課題

- 排他制御の責務が曖昧だと、二重ロックや抜けが起きやすい
- 実装層が決まらないと、後続の `HybridRAGFactory` 配線にも影響する
- 失敗時の戻し方が決まらない

### 1.3 放置した場合の影響

- 同じ問題を複数層で重複実装する
- 仕様書と実装で責務がズレる
- `AI_INDEX` の実装タスクが着手できない

---

## 2. 何を達成するか（What）

### 2.1 目的

排他制御の責務境界を決め、後続実装タスクの前提を固定する。

### 2.2 最終ゴール

- 管理層が 1 つに決まる
- 失敗時の扱いが決まる
- 後続タスクが実装に進める

### 2.3 スコープ

#### 含むもの

- 設計判断
- contract matrix の補足整理
- 後続タスクへの前提化

#### 含まないもの

- 実装コード
- DB スキーマ変更

### 2.4 成果物

- 排他制御の設計メモ
- 後続タスク向けの前提整理

---

## 3. どのように実行するか（How）

### 3.1 前提条件

- 実装層候補を比較できること
- 既存の `AI_INDEX` 呼び出しを把握できること

### 3.2 依存タスク

- UT-RAG-08-002
- UT-RAG-08-012

### 3.3 必要な知識

- IPC / Service / DB の責務分担
- 排他制御と fail-fast の設計

### 3.4 推奨アプローチ

責務を 1 層に集約し、他層は検知と通知に徹する。曖昧な三重管理は避ける。

---

## 4. 実行手順

### Phase 1: 候補比較

#### 目的

管理層の候補を整理する。

#### 手順

1. IPC / Service / DB の役割を列挙する
2. それぞれのメリットと欠点を比較する
3. 推奨層を決める

#### 完了条件

- どの層が持つか決まっている

### Phase 2: 設計決定

#### 目的

実装前提を固定する。

#### 手順

1. 排他制御の置き場を明記する
2. 失敗時の扱いを定義する
3. 後続タスクに引き継ぐ

#### 完了条件

- 設計判断が文書化されている

### Phase 3: 確認

#### 目的

後続タスクが実装可能か確認する。

#### 手順

1. 設計メモをレビューする
2. 依存タスクとの整合を見る
3. 仕様の抜けを埋める

#### 完了条件

- 後続実装に進める
