## task-specification-creator スキルへのフィードバック

### 良かった点

#### 1. P50チェックの設計が的確だった

Phase 1 で「既実装かどうかを最初に確認する」P50チェックを必須ステップとして設けたことで、
TASK-SW-STREAM-002 の実装がすでに存在することを Phase 3 ゲートで正確に検出できた。
「作業の重複を防ぐ」という観点で非常に有効な設計だった。

**学習点**: IPC 配線タスクのように「実装済みである可能性が高いタスク」では、
P50チェックを Phase 1 の必須ステップとして明示するパターンは今後も継続すべき。

#### 2. フェーズゲートによる品質保証

Phase 3 ゲート判定で「PASS（実装済み）」という判断を下し、
不要な実装作業をスキップした。これにより過剰実装（すでに動いているコードを壊す）を防げた。

#### 3. 4層整合チェックの有効性

`skillCreatorHandlers.ts`（Main）→ IPC → `useStreamingProgress`（Renderer）→ `GenerateStep`（UI）
という4層を明示的に追跡する設計が、断絶箇所の特定に役立った。

### 改善提案

#### 提案1: 「実装済み検出」時の専用フロー

**現状の課題**: タスク仕様書は「未実装前提」で書かれており、実装済み検出後のフローが明示されていない。
P50チェックで「実装済み」と判明した場合に何をすべきかのガイドラインが不明確。

**提案**: タスク仕様書テンプレートに以下の分岐を追加する。

```
P50チェック結果:
  - 未実装 → 通常フロー（Phase 4以降）
  - 実装済み → 検証フロー（テスト確認・ドキュメント整備のみ）
  - 部分実装 → 差分実装フロー（不足部分のみ実装）
```

#### 提案2: IPC 配線タスク専用テンプレートの作成

IPC 配線タスク（Main → Renderer への通知接続）は繰り返し発生するパターンである。
以下の観点を含む専用テンプレートがあると効率的:

- 4層確認チェックリスト（Main / IPC チャンネル / Preload / Renderer）
- `isDestroyed()` チェックの必須確認
- エラー時の状態管理確認
- スロットリング要否の確認

#### 提案3: 変更影響範囲の自動チェックリスト

`sendSkillCreatorProgress` のような「定義だけ存在し、呼び出し元がない関数」を
自動で検出するチェックステップをフロー内に組み込む提案。

```bash
# 呼び出し元のない関数を検出する例
grep -rn "sendSkillCreatorProgress" src/ | grep -v "function sendSkillCreatorProgress"
```

## IPC 配線タスクの共通学習点

| 学習点                                          | 詳細                                                       |
| ----------------------------------------------- | ---------------------------------------------------------- |
| 「定義済み・未接続」パターンが頻出する          | 関数が定義されていても呼び出し元がない状態は見逃しやすい   |
| P50チェックは「存在確認」と「動作確認」を分ける | ファイルにコードがあっても接続されていない場合がある       |
| 4層フロー全体を追跡することが重要               | 1層だけ確認しても全体が機能するとは限らない                |
| エラー時の状態管理は後回しにされやすい          | 正常系が動いた後にエラー系を別タスクとして明示しておくべき |
