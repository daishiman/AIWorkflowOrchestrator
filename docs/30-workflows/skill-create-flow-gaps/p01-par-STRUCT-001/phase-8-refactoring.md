## 目的

Phase 5 で実装した `runCreateWorkflow` の修正コードを、最小複雑性・可読性・将来の LLM 統合への
準備という観点で再調整する。テストが全て Green であることを維持しながらコードを整理する。

## 実行タスク

### Task 1: コード品質チェック

実装コードを以下の観点で確認する。

| 観点               | チェック内容                                         |
| ------------------ | ---------------------------------------------------- |
| 命名の明確性       | 変数名・コメントが意図を正確に表しているか           |
| 不要コードの除去   | 削除された `loadAgent` 関連の変数が残っていないか    |
| コメントの適切性   | 「LLM統合は別タスク」コメントが適切な位置にあるか    |
| `try/catch` の意図 | 将来の処理追加に備える旨がコメントで明記されているか |

### Task 2: 命名と構造の整理

`runCreateWorkflow` の実装後コードを確認し、以下を整理する。

- `purpose` の値が `options.description` であることを示す適切なコメントがあるか
- `agents` の値がハードコードのエージェント名リストであることを示すコメントがあるか
- 空の `features` 配列に「LLM統合は別タスク」コメントがあるか

### Task 3: リファクタリング後のテスト全件確認

```bash
# 全テスト Green 確認
pnpm --filter @repo/desktop test -- --testPathPattern="SkillCreatorService"
```

リファクタリング後も全テストが Green であることを確認する。

### Task 4: 技術的負債の記録

| 負債ID | 内容                                               | 対応タスク              |
| ------ | -------------------------------------------------- | ----------------------- |
| TD-001 | `purpose: options.description` は LLM 統合で変わる | LLM統合タスク（別）     |
| TD-002 | `features: []` は LLM 統合で埋まる                 | LLM統合タスク（別）     |
| TD-003 | `try/catch` が実質 no-op（将来の処理追加待ち）     | TASK-SW-STRUCT-002 以降 |
