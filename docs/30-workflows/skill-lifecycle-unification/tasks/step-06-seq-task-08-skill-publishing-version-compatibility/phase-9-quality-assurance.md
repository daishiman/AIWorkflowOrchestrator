## 目的

設計タスクの品質基準（型整合性、仕様書品質、テスト仕様網羅性、セキュリティ）を一括判定し、Phase 10 への進行可否を決定する。

## 背景

TASK-SKILL-LIFECYCLE-08 は設計タスクであり、成果物は実行可能コードではなく型定義・インターフェース仕様・フロー設計文書である。そのため、通常の「コードテスト実行」ではなく「設計の品質基準への適合確認」を品質検証の内容とする。Phase 8 で整理された型定義と設計文書を入力として、4 つの観点から品質を検証する。

## 実行タスク

### タスク1: 型整合性検証

**目的**: 全 TypeScript 型定義が packages/shared と apps/desktop の型体系と整合するかを検証する。

**実行手順**:

1. Phase 8 の `dedup-plan.md` を参照し、一元化先（`packages/shared/src/skill/types.ts`）の型定義を確認する
2. 以下の型が TypeScript strict モードでコンパイル可能な設計かを擬似検証する（コンパイラを実行せず、型の整合性を論理的に確認する）:
   - `SkillVisibility = "local" | "team" | "public"` — union type として成立しているか
   - `SkillPublishingMetadata` — 全フィールドが `required` または `optional` で明示されているか
   - `CompatibilityCheckResult` — semver 判定結果の全パターンが網羅されているか
   - `PublishReadiness` — Task06/07 の入力型への参照が型安全か
3. 各サービスインターフェース（`SkillRegistryService`, `CompatibilityChecker`, `PublishReadinessChecker`）がモック可能な設計（インターフェース分離、DI パターン適合）かを確認する
4. `packages/shared` と `apps/desktop/src/preload/types.ts` の間で型定義が重複していないかを確認する（P23/P32 対策）

**期待される成果物**: `outputs/phase-9/type-integrity-report.md`（型別検証結果・PASS/FAIL・問題箇所リスト）

---

### タスク2: 仕様書品質検証

**目的**: Phase 1〜8 の全仕様書が品質基準（曖昧表現ゼロ・必須セクション準拠・検証可能な完了条件）を満たしているかを確認する。

**実行手順**:

1. 曖昧表現スキャン: 全 Phase 仕様書（phase-1〜phase-8.md）に対して以下の禁止表現が含まれていないかを確認する:
   - 02-code-quality.md で禁止された修飾語（条件・基準が不明確な表現、発動条件が未定義の表現、列挙が不完全な表現、定量基準のない程度表現）
   - 閾値が数値でなく「高い」「低い」で表現されている箇所
2. 必須セクション準拠確認: 各 Phase 仕様書が以下の順序でセクションを持つかを確認する:
   - タイトル（h1）→ メタ情報 → 目的 → 背景 → 実行タスク → 参照資料 → 統合テスト連携 → 成果物 → 完了条件 → タスク100%実行確認 → 次Phase
3. 完了条件の検証可能性確認: 各 Phase の完了条件が「ファイルが存在する」「件数が 0 件」「判定が明示されている」等、客観的に確認可能な形式になっているかを確認する
4. 発見した違反を重大度（CRITICAL/MAJOR/MINOR）別に記録する

**期待される成果物**: `outputs/phase-9/spec-quality-report.md`（仕様書別スキャン結果・違反リスト・修正案）

---

### タスク3: テスト仕様網羅性検証

**目的**: Phase 4〜6 で設計されたテスト仕様が、Phase 7 のカバレッジマトリクスで未検証 0 件であることを確認する。

**実行手順**:

1. `outputs/phase-7/` 配下のカバレッジマトリクスを参照する
2. Phase 4 で定義したテストケース一覧と Phase 7 のカバレッジマトリクスを突き合わせ、未検証テストケースが 0 件であることを確認する
3. 未検証が 0 件でない場合、未検証ケースを列挙し、Phase 6 への差し戻し対象として記録する
4. カバレッジ対象外として意図的に除外したケースがある場合、除外理由が記録されていることを確認する

**期待される成果物**: `outputs/phase-9/test-coverage-report.md`（カバレッジマトリクス照合結果・未検証件数・除外理由確認）

---

### タスク4: セキュリティ確認

**目的**: 公開フロー設計に無認証アクセスパスおよびメタデータインジェクション脆弱性がないことを確認する。

**実行手順**:

1. 無認証公開パスの確認:
   - `outputs/phase-2/skill-center-flow-design.md` のフロー図で、認証チェックを迂回して公開状態に遷移できるパスがないかを確認する
   - local→team→public の各遷移に認証・認可チェックが明示されていることを確認する
2. メタデータインジェクション対策の確認:
   - `SkillPublishingMetadata` の文字列フィールド（description, readme, changelog 等）に対してサニタイズ処理が設計されていることを確認する
   - 外部入力（ユーザー入力の name, tags, author）がそのまま Skill Center に格納されないよう、バリデーション層が設計に含まれていることを確認する
3. IPC チャンネルのセキュリティ確認:
   - 公開操作用の IPC チャンネルが Main Process 側でホワイトリスト管理されていることを確認する
   - Renderer から公開操作を直接呼べない設計（Preload 経由のみ）になっていることを確認する
4. `security-skill-execution.md` の要件との整合が全て PASS であることを確認する

**期待される成果物**: `outputs/phase-9/security-check-report.md`（セキュリティ確認項目別 PASS/FAIL・問題箇所・修正案）

---

### タスク5: 品質ゲート総合判定

**目的**: タスク1〜4 の検証結果を集約し、Phase 10 への進行可否を判定する。

**実行手順**:

1. タスク1〜4 の各レポートから PASS/FAIL 件数を集計する
2. 以下の品質ゲートチェックリストを全て確認する:

   **機能検証**:
   - [ ] 全型定義が TypeScript strict モードでコンパイル可能な設計である
   - [ ] 全サービスインターフェースがモック可能な設計である

   **コード品質（設計タスク版）**:
   - [ ] 全仕様書に曖昧表現が 0 件である
   - [ ] 型定義の命名規則が全て準拠している
   - [ ] 仕様書フォーマットが必須セクション構造に準拠している

   **テスト網羅性**:
   - [ ] Phase 7 カバレッジマトリクスで未検証 0 件である

   **セキュリティ**:
   - [ ] 公開フローに無認証アクセスパスがない
   - [ ] メタデータ入力にインジェクション対策が設計されている

3. 以下の基準で総合判定を下す:
   - PASS: 全チェックリスト PASS
   - CONDITIONAL PASS: MINOR 指摘のみ（致命的でない修正が必要）
   - FAIL: MAJOR/CRITICAL 問題あり（Phase 6 または Phase 8 への差し戻し）
4. CONDITIONAL PASS の場合、修正指示を記録して Phase 10 に引き継ぐ

**期待される成果物**: `outputs/phase-9/quality-gate-result.md`（品質ゲートチェックリスト全結果・総合判定・Phase 10 引き継ぎ事項）
