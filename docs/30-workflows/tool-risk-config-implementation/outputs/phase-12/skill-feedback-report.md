## 改善点1: task-specification-creator スキル — Phase 7 カバレッジ確認の粒度

### 問題

Phase 7 のカバレッジ確認で、security.ts の既存関数（isDangerousCommand 等）のカバレッジが不足していると判明した。原因は security.test.ts が TOOL_RISK_CONFIG のみをテスト対象としていたためである。

既存コードのカバレッジ不足が「本タスクの問題」として誤検知され、カバレッジ基準の判断に迷いが生じた。

### 提案

Phase 7 仕様書テンプレートに、以下の区別を明確にする指示を追加する。

- **新規コードのカバレッジ**: 本タスクで追加・変更したコードのみを対象とする（必達基準）
- **対象ファイル全体のカバレッジ**: 既存コードを含むファイル全体のカバレッジ（参考値として記録するが、本タスクの合否判定には用いない）

### 期待効果

小規模タスク（定数追加・型定義追加等）でも既存コードのカバレッジ不足が誤検知されるのを防止し、Phase 7 の判断を明確化できる。

### 影響範囲

- `task-specification-creator` スキルの Phase 7 テンプレート
- 小規模タスク全般

## 改善点2: docs-only / 定数追加タスクのフロー最適化

### 問題

本タスクは定数追加のみ（約70行）だが、13 Phase の全工程を通過した。Phase 11（手動テスト）は NON_VISUAL のため、実質 Phase 9 品質検証の再実行に近い内容となった。13 Phase を厳格に適用することで、本タスクの規模に対してオーバーヘッドが発生した。

### 提案

docs-only / 定数追加タスクのための「軽量フロー」をテンプレートとして用意する。

**提案する軽量フロー構成（4 Phase）:**

| Phase     | 内容                                   |
| --------- | -------------------------------------- |
| Phase 1   | 要件定義                               |
| Phase 4-5 | テスト作成・実装                       |
| Phase 9   | 品質検証（Lint・型チェック・全テスト） |
| Phase 12  | ドキュメント・完了処理                 |

**適用条件（全て満たす場合に限定）:**

1. UIコンポーネントの変更がない
2. ビジネスロジックの変更がない
3. IPC インターフェースの変更がない
4. 追加コード量が100行未満

### リスク

フロー短縮により、設計レビュー（Phase 3）や最終レビュー（Phase 10）が省略されるため、品質低下の可能性がある。本タスクではセキュリティ不変条件テストが存在したため問題なかったが、軽量フローの一般化には慎重な検討が必要である。適用判断はタスク開始時に明示的に行うべきである。

### 影響範囲

- `task-specification-creator` スキルのフローテンプレート
- 定数追加・型定義追加タスク全般
