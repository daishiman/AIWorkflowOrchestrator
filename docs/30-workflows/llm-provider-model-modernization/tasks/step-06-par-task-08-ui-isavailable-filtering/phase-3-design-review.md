### Task 3-2: 設計品質チェック

#### 2-A: 単一責務原則（SRP）

InlineModelSelector の責務は「チャット画面でのモデル選択 UI」であり、利用可能なプロバイダーのみを表示するのは適切なフィルタリング。ビジネスロジック（isAvailable の判定）は Main Process 側の `handleGetProviders` に存在し、UI 側はフラグを参照するのみ。問題なし。

#### 2-B: 型安全性

`LLMProvider` 型に `isAvailable: boolean` が定義されているため、`.filter((p) => p.isAvailable)` は型安全。`?.` オプショナルチェーンは不要（`isAvailable` は必須フィールド）。問題なし。

#### 2-C: テスタビリティ

InlineModelSelector は `providers` props を受け取るため、テスト時に `isAvailable: true/false` のプロバイダーを直接渡してフィルタリング動作を検証できる。Store モックなしでテスト可能。問題なし。

#### 2-D: P62 準拠の確認

APIキー未設定プロバイダーが InlineModelSelector のドロップダウンに表示されないため、ユーザーが未設定プロバイダーを選択すること自体が不可能になる。DEFAULT_CONFIG への暗黙 fallback リスクを根本的に排除している。問題なし。

### Task 3-3: リスク評価

| リスク                                                         | 可能性   | 影響 | 対策                                                                                 |
| -------------------------------------------------------------- | -------- | ---- | ------------------------------------------------------------------------------------ |
| 全プロバイダーが `isAvailable: false` でゼロ表示               | 低       | 低   | 「モデルを選択」テキスト表示で対応済み。設定画面への誘導は別タスク                   |
| 現在選択中のプロバイダーが `isAvailable: false` に変わった場合 | 低       | 中   | `selectedProvider` が `undefined` になり、表示は「モデルを選択」に切り替わる         |
| props 経由で渡されたプロバイダーにもフィルタが適用される       | 意図通り | -    | テスト用の props でも同じフィルタが適用される。テスト時は `isAvailable: true` を設定 |

### Task 3-5: レビュー判定

**判定: PASS**

以下の根拠で Phase 4 への進行を承認する：

1. 受入基準 AC-01〜AC-05 が設計で全て満たされている

4. 既存のゼロプロバイダーハンドリングロジックが流用可能
