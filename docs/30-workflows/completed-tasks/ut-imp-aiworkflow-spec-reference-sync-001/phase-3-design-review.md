## 目的

Phase 1（要件定義）と Phase 2（設計）の成果物を多角的にレビューし、要件カバレッジ・設計整合性・検証可能性・過去教訓との整合性を確認する。レビュー結果に基づき PASS / MINOR / MAJOR の判定を下す。

## 実行タスク

- Task 1: 要件カバレッジをレビューし、FR/NFR と Design 成果物の対応を検証する
- Task 2: 既存仕様書との設計整合性をレビューする
- Task 3: 完了条件と AC の検証可能性をレビューする
- Task 4: 過去教訓（P1/P2/P3/P4/P25/P26/P27/P28/P29/P43）の反映状況をレビューする

### Task 1: 要件カバレッジレビュー

- Phase 1 で定義した3つの問題点（baseline/current 判定混同、未タスク参照リンク漏れ、fallback 経路片側修正残り）の全てに対応する FR が Phase 2 の設計で充足されているか検証する
- FR-1 ~ FR-4 の全要件 ID（FR-1.1 ~ FR-4.3）が設計成果物 Design 1 ~ Design 5 のいずれかにマッピングされているか確認する
- NFR-1 ~ NFR-3 の全要件 ID（NFR-1.1 ~ NFR-3.3）が設計成果物に反映されているか確認する

### Task 2: 設計整合性レビュー

- Phase 2 の同期ルール（Design 1）が既存の `spec-update-workflow.md` の Step 1-A ~ Step 1-D と矛盾しないか検証する
- Phase 2 のチェックリスト構造（Design 2）が既存の `05-task-execution.md` Phase 12 必須チェックリストと二重定義にならないか検証する
- Phase 2 の検証コマンド手順（Design 5）が `phase-11-12-guide.md` の既存記載と整合しているか検証する

### Task 3: 検証可能性レビュー

- Phase 1 の全完了条件（12項目）が機械的に検証可能であるか1項目ずつ確認する
- Phase 2 の全完了条件（15項目）が機械的に検証可能であるか1項目ずつ確認する
- AC-1 ~ AC-5 の受入基準が実際に実行可能な手順で構成されているか確認する

### Task 4: 過去教訓との整合性レビュー

- P1, P2, P3, P4, P25, P26, P27, P28, P29, P43 の教訓が Phase 2 の設計に反映されているか確認する
- 未反映の教訓がある場合、MINOR または MAJOR 判定の根拠とする

## 判定基準

| 判定              | 条件                                             | 対応                                          |

### ステップ 5: 総合判定

レビュー結果を以下の基準で判定する:

**PASS の条件（全て満たすこと）:**

- 要件カバレッジマトリクスで「未対応」が 0 件
- 設計整合性で矛盾が 0 件
- 検証可能性で「検証不能」が 0 件
- 過去教訓で「未反映」が 0 件

**MINOR の条件（以下のいずれかに該当）:**

- 要件カバレッジマトリクスで「部分対応」が 1 件以上あるが、機能的な欠落ではない
- チェックリストの表現に統一性が欠ける箇所がある
- 過去教訓の反映が間接的で、明示的な記述がない箇所がある

**MAJOR の条件（以下のいずれかに該当）:**

- 要件カバレッジマトリクスで「未対応」が 1 件以上
- 設計成果物が既存の `spec-update-workflow.md` と矛盾する
- AC の Gherkin シナリオが実行不能
- P1-P4 のいずれかの教訓が設計に全く反映されていない

## 統合テスト連携【必須】

本レビューでは、検証スクリプトの設計が Phase 12 運用に適合しているかを以下の観点でレビューする:

| レビュー観点                       | 確認内容                                                                                  | 判定基準                                                           |
| ---------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 検証コマンドの実行順序             | Design 5 の3ステップ（verify → generate → SKILL validator）の順序が依存関係に沿っているか | 前ステップの出力が後ステップの入力に影響する場合、順序が正しいこと |
| 異常時修正フロー                   | Design 5 の異常時フローが実際に実行可能な手順で構成されているか                           | 修正対象ファイルと再実行コマンドが明記されていること               |
| チェックリストと検証コマンドの連携 | Design 2 のチェック項目と Design 5 の検証コマンドが対応しているか                         | チェック項目と検証コマンドの対応関係が明確であること               |

レビューで確定した検証観点を `phase-4-test-creation.md` の検証テスト計画に入力する。
手動で追跡する観点を `outputs/phase-11/manual-test-result.md` に引き継ぐ。
検証コマンドの期待出力がレビューで承認された値であることを確認する。
