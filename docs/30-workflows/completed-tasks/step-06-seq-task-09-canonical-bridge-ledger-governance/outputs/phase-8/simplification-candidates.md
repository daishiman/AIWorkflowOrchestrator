# Phase 8 成果物: 簡素化候補の比較

> タスクID: TASK-IMP-CANONICAL-BRIDGE-LEDGER-GOVERNANCE-001
> 作成日: 2026-03-23
> Phase: 8 - リファクタリング

## 1. 概要

本ファイルは、3 Lane 設計の各コンポーネントについて「より単純な代替案」を列挙し、
採用／不採用の判断根拠を記録する。採用しない案もドキュメントとして保持することで、
将来の実装者が同じ議論を繰り返さないようにする。

---

## 2. L-1 Governance State Machine の簡素化候補

### 2.1 「状態遷移を廃止してフラグ管理にする」案

| 項目       | 内容                                                                                 |
| ---------- | ------------------------------------------------------------------------------------ |
| 概要       | spec_created / implementation_ready / completed の3状態をやめ、boolean flag に変える |
| メリット   | 実装が単純（`is_spec_created: true` 等）                                             |
| デメリット | 同時に複数フラグが true になる無効状態を防げない                                     |
| デメリット | 状態遷移の「進入条件」「退出条件」が flag には表現できない                           |
| 判定       | 不採用                                                                               |
| 理由       | FR-3.1〜3.4 が成果物ベースの遷移条件を必須としており、フラグでは検証不可能           |

### 2.2 「type: design の専用 state machine を作る」案

| 項目       | 内容                                                                                           |
| ---------- | ---------------------------------------------------------------------------------------------- |
| 概要       | 設計タスク専用に別の state machine を定義し、type: implementation とは完全に分離する           |
| メリット   | 各 type の state machine がシンプルになる                                                      |
| デメリット | 2つの state machine を保守する必要があり、共通ロジックが重複する                               |
| デメリット | 新 type が増えるたびに state machine を追加しなければならない                                  |
| 判定       | 不採用                                                                                         |
| 理由       | Phase 2 設計判断の通り、1つの state machine に type 別条件テーブルを持たせる方が保守コスト低い |

### 2.3 「rollback を省略し、forward-only にする」案

| 項目       | 内容                                                                           |
| ---------- | ------------------------------------------------------------------------------ |
| 概要       | 逆遷移（rollback）を定義せず、常に Phase 1 から再開する                        |
| メリット   | state machine がシンプルになる                                                 |
| デメリット | MAJOR 判定で Phase 2 問題が発見された場合に Phase 1 から全部やり直すのは非効率 |
| 判定       | 不採用                                                                         |
| 理由       | gate-decision.md の戻り先マトリクスが rollback 3段階を必要としている           |

## 3. L-2 Canonical Source & Bridge の簡素化候補

### 3.1 「.agents/ ディレクトリを廃止する」案

| 項目       | 内容                                                                              |
| ---------- | --------------------------------------------------------------------------------- |
| 概要       | mirror である .agents/skills/ を削除し、.claude/skills/ のみで運用する            |
| メリット   | mirror sync ステップ（Step E）が不要になり、Phase 12 チェックリストが短くなる     |
| デメリット | .agents/ を参照する既存ツール・スクリプトを全て特定・修正する必要がある           |
| デメリット | 廃止作業自体に大きなスコープが必要であり、本タスクの範囲外                        |
| 判定       | 不採用                                                                            |
| 理由       | design-summary.md L-2 の Simpler Alternative に記録済み。既存参照の破壊回避を優先 |

### 3.2 「legacy-ordinal-family-register.md を削除する」案

| 項目       | 内容                                                                                                  |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| 概要       | 旧パスの逆引き台帳を削除し、canonical パスのみで運用する                                              |
| メリット   | 管理ファイルが1つ減る                                                                                 |
| デメリット | 過去の仕様書が旧パスを参照している箇所が壊れる                                                        |
| デメリット | 旧パスを知っている実装者が canonical パスを探す手段がなくなる                                         |
| 判定       | 不採用                                                                                                |
| 理由       | design-summary.md L-2 の Simpler Alternative に記録済み。「参照のみ・新規追加禁止」で運用コスト最小化 |

### 3.3 「canonical source table を SKILL.md に統合する」案

| 項目       | 内容                                                                                         |
| ---------- | -------------------------------------------------------------------------------------------- |
| 概要       | 独立した canonical-source-table の代わりに SKILL.md の1セクションとして管理する              |
| メリット   | ファイル数が減る                                                                             |
| デメリット | SKILL.md は既に長大であり、phase-8 refactor-boundaries.md 3.2 の参照関係が崩れる             |
| デメリット | validation-matrix.md の grep 検証コマンドがファイル名前提で書かれている                      |
| 判定       | 不採用                                                                                       |
| 理由       | 独立ファイルの方が grep 検索・cross-reference が明確。統合のメリットがデメリットを上回らない |

### 3.4 「5カテゴリを3カテゴリに統合する」案（採用検討対象）

| 項目       | 内容                                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------------------- |
| 概要       | Workflow Ledger / Lessons Learned / System Spec / Indexes / Skill Meta の5カテゴリを3つに削減する               |
| 変更案     | Indexes → System Spec に統合、Skill Meta → Workflow Ledger に統合                                               |
| メリット   | 同期手順 Step A→E が Step A→C（3ステップ）になり、checklist が短くなる                                          |
| デメリット | Index（generate-index.js で自動生成）と System Spec（手動更新）は更新主体が異なり混在させると手順が不明確になる |
| デメリット | LOGS.md / SKILL.md は Workflow Ledger とは更新タイミングが微妙にずれる（全更新の最終ステップ）                  |
| 判定       | 不採用                                                                                                          |
| 理由       | 更新主体の違い（自動/手動）はカテゴリ分割の最重要基準。3カテゴリ化は参照負荷を増やす                            |

## 4. L-3 Same-Wave Sync Protocol の簡素化候補

### 4.1 「全更新を1エージェントで実施する」案

| 項目       | 内容                                                                                                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------ |
| 概要       | Phase 12 の全ファイル更新を分割せず1エージェントに委譲する                                                         |
| メリット   | エージェント間の調整コストがゼロ                                                                                   |
| デメリット | P43（rate limit 中断）リスクが高い（7ファイル以上を1エージェントが担当）                                           |
| 判定       | 不採用                                                                                                             |
| 理由       | P43 の実績：49ツール使用・402秒実行後に rate limit で中断する事例あり。3ファイル/エージェント上限は evidence-based |

### 4.2 「documentation-changelog を廃止する」案

| 項目       | 内容                                                                                 |
| ---------- | ------------------------------------------------------------------------------------ |
| 概要       | Phase 12 の changelog 記録を廃止し、git log で代替する                               |
| メリット   | 更新ファイル数が減る                                                                 |
| デメリット | P4/P51（changelog 早期「完了」記載）の再発防止ができなくなる                         |
| デメリット | git log は「どのファイルを更新したか」は分かるが「各 Step の完了確認」は追跡できない |
| 判定       | 不採用                                                                               |
| 理由       | changelog の主目的は「Step 完了の事後記録」であり git log では代替不可               |

### 4.3 「current → baseline 移管を廃止する」案

| 項目       | 内容                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| 概要       | lessons-learned-current.md を archive へ移管せず、そのまま肥大化させる |
| メリット   | wave 完了の判定ロジックが不要になる                                    |
| デメリット | lessons-learned-current.md が無制限に増大し、検索コストが上昇する      |
| デメリット | 「確定済み教訓」と「進行中の教訓」が混在し、参照時の信頼性が下がる     |
| 判定       | 不採用                                                                 |
| 理由       | current/baseline の切り分けは長期的な知識管理の品質を保つために必要    |

### 4.4 「Step D（index 再生成）を省略可能にする」案

| 項目       | 内容                                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------- |
| 概要       | System Spec の変更がない場合は generate-index.js の実行をスキップ可能にする                             |
| メリット   | Phase 12 の実行時間が短縮できる                                                                         |
| デメリット | P2/P27 の失敗事例：「変更なし」と判断したが実際は再生成が必要だったケースがある                         |
| デメリット | スキップ判定は実行者の主観に依存するため、判断基準が曖昧になりやすい                                    |
| 判定       | 不採用                                                                                                  |
| 理由       | validation-matrix.md の回帰防止ルールに「変更有無に関わらず実行」と明記。例外なし運用の方がコストが低い |

## 5. 採用した簡素化（実際に整理した内容）

Phase 8 で採用する簡素化は、refactor-boundaries.md の「整理可能な構造」セクションで定義したもののみ。

| 採用した簡素化                         | 対象ファイル           | 効果                             |
| -------------------------------------- | ---------------------- | -------------------------------- |
| 表記ゆれ4種の統一                      | 複数 outputs/ ファイル | grep 検索の精度向上              |
| contract-matrix.md の章順序変更        | contract-matrix.md     | Phase 12 実行者の参照コスト削減  |
| 禁止アクション代替手段の補完           | contract-matrix.md     | no-op 検出時の対応が即座に分かる |
| 検証コマンドへの PASS 条件コメント追加 | validation-matrix.md   | 実行者の判断負荷削減             |

上記以外の簡素化は全て「不採用」として本ファイルに記録した。
