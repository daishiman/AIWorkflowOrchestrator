## 目的

スナップショットテスト対象となる `registerRuntimeSkillCreatorHandlers()` を確定し、機能要件・エッジケースを定義する。

**タスク分類**: code task / NON_VISUAL（UI 変更なし）

## 背景

`ipcMain.handle()` は同一チャネルに 2 回目の登録をしても例外を投げず、後続ハンドラが静かに無視される（サイレントフェイル）。このバグはコードレビューのみに依存していたため長期間未検出だった。CI による自動検出の仕組みを設計するために、まず `registerRuntimeSkillCreatorHandlers()` が登録するチャネル数とエッジケースを確定する。

## 要件レビュー一次結論

| 観点               | 一次結論                                                                                |
| ------------------ | --------------------------------------------------------------------------------------- |
| 真の論点           | runtime-only の IPC 登録を 18 件で固定し、重複と欠損を CI で止めること                  |
| 依存関係・責務境界 | Main process の登録責務だけを扱い、AI handler や Renderer surface は scope 外に置くこと |
| 価値とコスト       | 要件定義書を 1 本に集約すると、後続 Phase の参照コストを下げられること                  |
| 改善優先順位       | まず scope を固定し、次に受け入れ基準、最後に edge case を詰めること                    |
| 4条件              | 価値性・実現性・整合性・運用性の4条件を満たすこと                                       |

### 補足

- 因果関係: 重複登録 -> 欠損 -> 検知不能 -> 再発、という流れを CI で断つ
- KJ クラスタ: `scope 固定` / `検証方法` / `blocked gate` に整理する
- 戦略仮説: runtime-only 18 件に絞ると、要件定義・設計・実装・PR 準備の全フェーズが一貫する

## 実行タスク

### タスク1: IPC ハンドラ登録関数の一覧化

**目的**: スナップショットテスト対象となる全ハンドラ登録関数を特定する

**実行手順**:

1. `apps/desktop/src/main/ipc/creatorHandlers.ts` を確認する
2. `registerRuntimeSkillCreatorHandlers()` が登録するチャネル名を抽出する
3. 期待登録数を記録する（18 = public runtime 16 + auxiliary 2）
4. `creatorHandlers.ts` で修正後の正常登録チャネル数（18 チャネル）を確認する
5. 要件定義書に受け入れ基準と FR/NFR を記録する

**期待される成果物**:

- `outputs/phase-1/requirements.md` （要件定義書。対象関数一覧・受け入れ基準・FR/NFR・エッジケースを含む）

---

### タスク2: エッジケース定義

**目的**: スナップショットテストが検出すべきエッジケースを網羅的に定義する

**実行手順**:

1. 以下のエッジケースを一覧化する
   - 同一チャネルの重複登録
   - チャネル名のリネーム
   - チャネルの追加・削除
2. 各ケースの期待動作を明記する
3. エッジケース一覧を文書化する
4. 受け入れ基準の FR/NFR 分類に反映する

**エッジケース一覧（事前定義）**:

| ケース                         | 期待動作                                |
| ------------------------------ | --------------------------------------- |
| 重複 `handle()` 登録           | テスト FAIL（重複チャネルが検出される） |
| チャネル数が変わった場合       | スナップショット不一致で FAIL           |
| チャネル名がリネームされた場合 | スナップショット不一致で FAIL           |
| チャネルが削除された場合       | スナップショット不一致で FAIL           |

**期待される成果物**:

- `outputs/phase-1/requirements.md` （要件定義書に内包）

## 受け入れ基準と FR/NFR

### FR

- `registerRuntimeSkillCreatorHandlers()` の登録チャネル一覧を固定できること
- 重複登録が発生した場合にスナップショット差分または件数差分で FAIL すること
- 18 件（public runtime 16 + auxiliary 2）の登録総数を検証できること

### NFR

- スナップショット比較が決定論的であること
- 追加・削除・リネームが CI で再現性よく検出できること
- runtime-only のスコープが維持されること
