## 目的

Phase 1〜2の成果物（要件定義・設計）をレビューし、実装フェーズに進む前に問題点を検出・修正する。要件と設計の妥当性を検証し、品質ゲートとして機能する。

## 背景

設計レビューゲートは、TDDサイクルの開始前に要件・設計の品質を保証する重要なチェックポイント。ここで問題を検出することで、実装フェーズでの手戻りを最小化する。

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: 要件定義レビュー

**目的**: Phase 1で定義した要件の妥当性と完全性を検証する

**実行手順**:

1. 機能要件のレビュー

| レビュー観点               | 確認内容                                       |
| -------------------------- | ---------------------------------------------- |
| 完全性                     | 必要な機能が全て定義されているか               |
| 一貫性                     | 要件間に矛盾がないか                           |
| 実現可能性                 | 既存システムで実現可能か                       |
| ICommunitySummarizer整合性 | searchSummaries() の仕様と整合しているか       |
| テスト可能性               | 受け入れ基準がテスト可能な形で定義されているか |

2. 非機能要件のレビュー

| レビュー観点       | 確認内容                              |
| ------------------ | ------------------------------------- |
| パフォーマンス目標 | 検索レイテンシ目標が妥当か            |
| 型安全性           | Branded Types、Result型の使用が適切か |
| テスタビリティ     | DIが適切に設計されているか            |

3. 受け入れ基準のレビュー

| レビュー観点 | 確認内容                           |
| ------------ | ---------------------------------- |
| 測定可能性   | 各基準が明確に測定可能か           |
| 網羅性       | 主要なシナリオがカバーされているか |
| 優先度       | 必須/推奨の分類が適切か            |

**期待される成果物**:

- 要件レビュー結果（PASS/MINOR/MAJOR判定）
- 指摘事項リスト

---

### タスク2: 設計レビュー

**目的**: Phase 2で作成した設計の妥当性と実装容易性を検証する

**実行手順**:

1. アーキテクチャ設計のレビュー

| レビュー観点       | 確認内容                       |
| ------------------ | ------------------------------ |
| 責務分離           | 各コンポーネントの責務が明確か |
| 依存関係           | 循環依存がないか、DIが適切か   |
| 拡張性             | 将来の機能追加に対応できるか   |
| 既存システム整合性 | 既存コンポーネントとの整合性   |

2. 処理フロー設計のレビュー

| レビュー観点       | 確認内容                             |
| ------------------ | ------------------------------------ |
| 完全性             | 全ての処理ステップが定義されているか |
| エラーハンドリング | 全エラーケースが考慮されているか     |
| フォールバック     | 適切なフォールバック戦略があるか     |
| パフォーマンス     | ボトルネックとなる処理がないか       |

3. インターフェース設計のレビュー

| レビュー観点             | 確認内容                          |
| ------------------------ | --------------------------------- |
| 型安全性                 | 型定義が厳密か                    |
| API設計                  | 使いやすいAPIになっているか       |
| ICommunitySummarizer統合 | searchSummaries()との統合が適切か |
| プロンプト設計           | コンテキスト構築が適切か          |

**期待される成果物**:

- 設計レビュー結果（PASS/MINOR/MAJOR判定）
- 指摘事項リスト

---

### タスク3: システム仕様整合性チェック

**目的**: aiworkflow-requirements の仕様との整合性を検証する

**実行手順**:

1. インターフェース仕様チェック

```bash
# 仕様検索コマンド
node .claude/skills/aiworkflow-requirements/scripts/search-spec.mjs "ICommunitySummarizer"
node .claude/skills/aiworkflow-requirements/scripts/search-spec.mjs "searchSummaries"
```

| チェック項目                         | 確認内容                                    |
| ------------------------------------ | ------------------------------------------- |
| ICommunitySummarizer.searchSummaries | メソッドシグネチャが仕様通りか              |
| CommunitySummary型                   | 型定義が仕様通りか                          |
| CommunitySummarySearchOptions型      | オプション型が仕様通りか                    |
| Result型パターン                     | success/data/error パターンに準拠しているか |

2. 型定義整合性チェック

| 仕様定義                   | 設計での使用                                        |
| -------------------------- | --------------------------------------------------- |
| CommunityId (Branded Type) | GraphRAGQueryResponse で使用されているか            |
| QueryType                  | local/global/relationship/hybrid が使用されているか |
| SearchWeights              | 重み設定が仕様通りか                                |

**期待される成果物**:

- システム仕様整合性チェック結果

---

### タスク4: 統合テスト観点レビュー

**目的**: 統合テストの観点から設計をレビューする

**実行手順**:

1. 統合ポイントの確認

| 統合ポイント                                | 確認内容                   |
| ------------------------------------------- | -------------------------- |
| GraphRAGQueryService → ICommunitySummarizer | 依存注入が設計されているか |
| GraphRAGQueryService → IQueryClassifier     | 依存注入が設計されているか |
| GraphRAGQueryService → IEmbeddingProvider   | 依存注入が設計されているか |
| ResponseBuilder → ILLMProvider              | 依存注入が設計されているか |

2. モック可能性の確認

| コンポーネント       | モック可能性                   |
| -------------------- | ------------------------------ |
| ICommunitySummarizer | インターフェースでモック可能か |
| IEmbeddingProvider   | インターフェースでモック可能か |
| ILLMProvider         | インターフェースでモック可能か |

3. 統合テストシナリオの確認

| シナリオ                                   | 設計でカバーされているか |
| ------------------------------------------ | ------------------------ |
| 正常系: コミュニティ要約あり回答生成       | ✓/✗                      |
| 正常系: コミュニティ要約なしフォールバック | ✓/✗                      |
| 異常系: 要約検索エラー時のフォールバック   | ✓/✗                      |
| 異常系: LLM生成エラー時の処理              | ✓/✗                      |

**期待される成果物**:

- 統合テスト観点レビュー結果

---

### タスク5: レビュー判定と対応

**目的**: レビュー結果を判定し、必要に応じて修正を実施する

**実行手順**:

1. 総合判定を行う

| 判定     | 条件                     | 次のアクション            |
| -------- | ------------------------ | ------------------------- |
| PASS     | 全レビュー観点で問題なし | Phase 4へ進行             |
| MINOR    | 軽微な指摘あり           | 指摘対応後、Phase 4へ     |
| MAJOR    | 重大な問題あり           | 影響範囲に応じて戻る      |
| CRITICAL | 致命的な問題あり         | Phase 1へ戻りユーザー確認 |

2. 戻り先を決定する（MAJOR/CRITICAL の場合）

| 問題の種類 | 戻り先              |
| ---------- | ------------------- |
| 要件の問題 | Phase 1（要件定義） |
| 設計の問題 | Phase 2（設計）     |

3. レビュー結果をドキュメント化する

**期待される成果物**:

- `outputs/phase-3/review-result.md`
- 判定結果と対応方針
