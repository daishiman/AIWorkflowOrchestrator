# スキルフィードバックレポート - TASK-IMP-IPC-LAYER-INTEGRITY-FIX-001

## 対象スキル

- task-specification-creator

## 改善提案

### 1. Phase 4-5 並列実行の公式サポート

- 設計が仕様書で確定済みの場合、Phase 4（テスト）とPhase 5（実装）を並列実行するパターンを仕様書テンプレートに組み込むと効率が向上する
- 本タスクでは37テストが一発でGreenになった実績あり

### 2. IPC契約整合性チェックリストの Phase 2 組み込み

- 本タスクで修正した「dead channel」「引数命名ドリフト（P45）」「バリデーション不完全（P42）」は、Phase 2（設計）の時点でチェックリスト化することで早期検出が可能
- 現在の ipc-contract-checklist.md は Phase 12 に紐付けられているが、Phase 2 設計書のテンプレートにも「IPC チャンネル登録確認」「Preload/Main 引数形式の一致確認」を必須項目として追加すると効果的

### 3. スタブ実装の明示的マーキング方針

- `updateSkill()` のようなスタブ実装は `// TODO:` コメントだけでなく、実行時に `NOT_IMPLEMENTED` エラーを返す実装にすることで、テスト段階での発見を早められる
- Phase 1（要件定義）のスコープ定義に「スタブで残す実装の一覧と理由」を必須記載項目として追加することを推奨

## ワークフロー改善点

### 1. P50チェック（既実装調査）の効率化

- 仕様書の grep 手順が有効だった。全タスクで P50 チェックを標準化すると無駄な実装を防げる
- Phase 1 開始時に `grep -rn "skill:update\|skillHandlers" apps/desktop/src/main/ipc/` のような調査コマンドを仕様書テンプレートに含める

### 2. dead channel 検出の自動化

- 本タスクの発見契機（IPC チャンネル定義のみでハンドラ未登録）は静的解析で自動検出できる
- `packages/shared/src/ipc/channels.ts` のチャンネル定数を起点に、`ipcMain.handle()` の登録状況をチェックするスクリプトを CI に組み込むと、同様の問題の再発を防止できる
- 関連: `docs/30-workflows/unassigned-task/` に drift detection スクリプト案が存在する

## P42/P45対応における学び

- P42の3段バリデーション（型チェック → 空文字列 → トリム空文字列）は既存ハンドラパターンに完全準拠しており、実装コストが低い
- P45の命名統一（skillId vs skillName）は設計段階で決定しておくと実装時の迷いがなくなる
- Preload 層での早期拒否パターン（invoke 前のバリデーション）は、Main Process の不要な処理を防ぐ効果的な戦略
- P44/P45 の「インターフェース契約ドリフト」は、IPC ハンドラと Preload 側の引数形式を同一コミットで更新する運用ルールで防止できる
