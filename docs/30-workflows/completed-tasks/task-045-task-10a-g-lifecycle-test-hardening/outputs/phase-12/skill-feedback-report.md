## 次回再利用できる知見

### 知見 1: テスト専用タスクの 3層構造パターン

G1（IPC契約）/ G2（Store連携）/ G3（UI結線）の3層分離は、テスト専用タスクの標準パターンとして再利用可能である。

**再利用条件**: IPC ハンドラ + Store アクション + UI コンポーネントの3層にまたがるテスト強化タスク

**パターンの利点**:

- 障害切り分けが明確（どの層が壊れたか即座に特定可能）
- 並列開発が可能（G1/G2 を並列、G3 を直列）
- カバレッジのスコープ限定が容易（ファイル全体ではなく対象行範囲で評価）

### 知見 2: Phase 6 テスト拡充のタイミング

Phase 4-5 で G2 は 12件で開始し、Phase 6 で 9件追加して 21件にした。Phase 6 でのバリデーション分岐（VAL: 6件）と API ガード（GUARD: 3件）の追加は、Phase 7 のカバレッジ計測結果を受けてから行うのが効率的だった。

**再利用ポイント**: カバレッジが不足する分岐パターンを Phase 7 で特定してから Phase 6 でテストを追加する流れは、テスト拡充タスクの標準手順として定着させる。

### 知見 3: P41 exemption の事前記録

G1 の Function Coverage が 0%（v8 のインライン関数カウント問題）となるケースは、Phase 7 で exemption として事前記録しておくことで Phase 10 レビューでの無駄な議論を回避できた。

**再利用ポイント**: v8 カバレッジプロバイダを使用する環境では、`getAllowedWindows: () => [mainWindow]` のようなオプションオブジェクト内のインラインアロー関数が独立カウントされる。テスト設計時に P41 該当箇所を洗い出し、exemption を Phase 7 レポートに明記する。

### 知見 4: 回帰テスト範囲の明示

Phase 11 で回帰テスト対象を明示的に定義した（skillHandlers 関連185件 + agentSlice 50件）。テスト専用タスクでは「何を回帰テストするか」をPhase 1 の段階で定義しておくと、Phase 11 での確認が効率的になる。

### 知見 5: stderr 出力の事前分類

G1 テストで出力される stderr ログ（MockElectronStore 初期化、意図的エラー）を Phase 10 で「情報提供のみ」として事前分類したことで、Phase 11 の手動テストで不要な調査を回避できた。テスト設計段階で「意図的な stderr 出力」をドキュメント化しておくことを推奨する。
