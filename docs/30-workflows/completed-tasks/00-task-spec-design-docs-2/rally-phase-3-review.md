## 1. 4条件の再評価（全 PASS 確認）

Phase 1 では4条件がすべて FAIL であった。Phase 2 の解決策設計を適用した後の再評価を以下に示す。

### 1.1 矛盾なし条件 — PASS（解決策適用後）

**解決策**: RALLY-005 により invoke を正規ソース・push を補完ソースと明示。push 受信時の競合チェック（seqNo / updatedAt 比較）により、古い push による上書きを防ぐ。RALLY-008 により `processWorkflowOutcome` の呼び出し契約を await に統一し、エラー処理タイミングの矛盾を解消する。

**PASS 条件充足の根拠**:

- workflowSnapshot の更新経路が「invoke 優先、push は補完かつ古い場合は無視」と一本化される
- processWorkflowOutcome の呼び出し側が一律 await になり、戻り値処理が矛盾しなくなる

### 1.2 漏れなし条件 — PASS（解決策適用後）

**解決策**: RALLY-010 でラリー完了状態の専用 UI を追加。RALLY-012 でエラー後の再試行・リセット導線を追加。RALLY-013 で Undo 可能範囲の視覚的インジケーターを追加。

**PASS 条件充足の根拠**:

- ユーザーへの主要なフィードバック経路（完了・エラー・Undo 範囲）がすべて UI で表現される
- 待機中と完了後が区別できる状態遷移表現が追加される

### 1.3 整合性あり条件 — PASS（解決策適用後）

**解決策**: RALLY-004 で型定義に正規フィールドを明示し非推奨フィールドに deprecation マーク。RALLY-002 で restoredPendingRequest の優先ルールをコメントで明示。RALLY-001 で dead code を除去しコードの意図と実装を一致させる。

**PASS 条件充足の根拠**:

- 型定義レベルで正規フィールドが明確になり、実装側の使い分けが一意に決まる
- restoredPendingRequest の優先ルールがコードを読んで理解できる状態になる
- dead code が除去されることで「今動いているコード」と「動いていないコード」の混在が解消される

### 1.4 依存関係整合条件 — PASS（解決策適用後）

**解決策**: RALLY-003 で Undo がサーバー状態を rollback する。RALLY-006 で useEffect 依存配列の循環を ref による参照に変換して排除。RALLY-007 で addAssistantMessage の stale closure を useRef パターンで排除。

**PASS 条件充足の根拠**:

- Undo 操作がサーバー状態と UI 状態を同期して巻き戻し、依存先の整合が取れる
- React の依存配列モデルと実装が一致する（exhaustive-deps 警告なし）
- currentStepIndex への依存が ref を通じて常に最新値を参照する

## 3. リスクと軽減策

### リスク 1: RALLY-005 の seqNo / updatedAt 設計がサーバー側に存在しない

**リスクレベル**: 高

**内容**: push 競合チェックに seqNo または updatedAt タイムスタンプが必要だが、サーバー側 workflowSnapshot にそのフィールドが存在しない場合、比較ロジックが実装できない。

**軽減策**:

1. 実装前に `WorkflowSnapshot` 型定義を確認し、タイムスタンプ相当フィールドの有無を検証する
2. 存在しない場合は `updatedAt` フィールドをサーバー側（RuntimeSkillCreatorFacade）で付与して返す設計に変更する
3. 最低限のフォールバックとして「isSubmitting 中は push を全無視（pendingPushRef にキューイング）」だけでも実装する

### リスク 2: RALLY-003 rollback API がワークフローエンジン側の仕様と競合する

**リスクレベル**: 中

**内容**: `rollbackStep` API がワークフローエンジンの内部仕様に依存するため、実装コストが見積もりより大きくなる可能性がある。

**軽減策**:

1. rollback の最小実装として「stepIndex 以降のステップを削除し awaitingUserInput を前の質問に戻す」だけでよいか、ワークフローエンジンの仕様を確認する
2. 完全な rollback が困難な場合は「再入力可能状態へのリセット」に範囲を縮小し、RALLY-013 の Undo インジケーターも「N 回前まで再入力できます」と表現を変える

### リスク 3: RALLY-006 の useEffect 依存配列修正で意図したエフェクトが動かなくなる

**リスクレベル**: 中

**内容**: `workflowSnapshot?.planId` を依存配列から外すことで、planId 変更時のエフェクト実行が抑制され、意図した初期化処理が動かなくなる可能性がある。

**軽減策**:

1. L675-708 のエフェクト本体が「planId 変更時に必ず実行すべき処理」を含むかどうかを実装前に精査する
2. planId 変更時の初期化処理が必要な場合は、planId 専用の useEffect を別途追加し、循環を起こす処理のみ ref 化する

### リスク 4: RALLY-001 の dead code 削除で削除対象が実は他箇所から参照されている

**リスクレベル**: 低

**内容**: `_handleSubmitWorkflowInput` が将来の実装に向けたスタブとして意図的に残されている、または間接参照されている場合、削除によってビルドエラーが発生する。

**軽減策**:

1. 削除前に `grep -r "_handleSubmitWorkflowInput"` で参照箇所を全件確認する
2. 参照が見つかった場合は削除せずコメントでの非推奨マークに留め、Issue を作成して別途整理する

### リスク 5: Wave 直列制約が並列実行環境で守られない

**リスクレベル**: 低（運用上のリスク）

**内容**: 複数のエージェントまたは開発者が並列でタスクを実行した場合、直列制約を破った順序で変更が加えられマージコンフリクトが発生する可能性がある。

**軽減策**:

1. Phase 2 の Wave 設計に従い、Wave 0 完了後に Wave 1、Wave 1 完了後に Wave 2・3 を開始するルールをチームで共有する
2. 同一ファイルを触るタスクは必ず 1 名（または 1 エージェント）が直列で担当するよう割り当てる
