## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-FIX-ELECTRON-APP-MENU-ZOOM-001（83行の新規ファイル + 2行の既存ファイル変更）に13フェーズの完全ワークフローを適用した。テスト20件・カバレッジ100%の高品質は確保できたが、Phase 6（テスト拡充）は Phase 5 完了時点でカバレッジ100%達成済みのため実質不要、Phase 8（リファクタリング）も83行のファイルにリファクタリング余地がなく実質スキップとなった。ワークフロー管理のオーバーヘッドが実装時間を上回る状態が発生した。

### 1.2 問題点・課題

- 200行以下の小規模修正に13フェーズを適用すると、Phase 6（テスト拡充）やPhase 8（リファクタリング）が形式的にスキップされるケースが多い
- 13フェーズのワークフロー仕様書（phase-1 から phase-13）を全て生成・管理するコストが、修正の規模に見合わない
- フルワークフローを省略するか適用するかの判断基準が属人化しており、実行者によって品質にばらつきが出る

### 1.3 放置した場合の影響

- 小規模修正のたびに不要なフェーズの生成・確認コストが発生し続ける
- ワークフロー省略の判断が属人化し、品質基準が曖昧になる
- ワークフロー管理コストへの不満から、ワークフロー全体の形骸化リスクが高まる

## 2. 何を達成するか（What）

### 2.1 目的

小規模修正（200行以下の変更）向けの軽量ワークフローバリアント（7フェーズ構成）を定義し、task-specification-creatorスキルに組み込む。

### 2.2 最終ゴール

- 修正規模に応じてフルワークフロー（13フェーズ）と軽量ワークフロー（7フェーズ）を選択できる明確な判断基準が確立されている
- 軽量ワークフローのフェーズテンプレートが `.claude/skills/task-specification-creator/` に配置されている
- task-specification-creator の SKILL.md に軽量ワークフローの使用条件と選択ロジックが記載されている

### 2.3 スコープ

#### 含むもの

- 軽量ワークフロー（7フェーズ）のフェーズ定義と各フェーズの完了条件
- フル/軽量ワークフローの判断基準の策定
- 軽量フェーズテンプレートの作成（`phase-templates-light.md` 等）
- task-specification-creator スキルへの統合（SKILL.md 更新、判断ロジック追加）

#### 含まないもの

- 既存の13フェーズワークフローの変更や廃止
- 過去タスクへの遡及適用
- 自動判定スクリプトの実装（判断基準の文書化のみ）

## 3. どのように実行するか（How）

### 3.1 前提条件

- 既存の13フェーズワークフロー（`.claude/skills/task-specification-creator/references/phase-templates.md`）の構造を理解していること
- `05-task-execution.md` の Phase 1-13 の各フェーズの責務を把握していること
- TASK-FIX-ELECTRON-APP-MENU-ZOOM-001 のスキルフィードバックレポートの内容を確認済みであること

### 3.2 依存タスク

なし

### 3.3 必要な知識

- task-specification-creator スキルの構造（SKILL.md, references/, assets/, schemas/）
- Phase 1-13 の各フェーズの責務と相互依存関係
- 過去の小規模修正タスクでの実質スキップフェーズの傾向

### 3.4 推奨アプローチ

1. 過去の小規模修正タスク（TASK-FIX-ELECTRON-APP-MENU-ZOOM-001 等）を分析し、実質スキップされたフェーズを特定する
2. フェーズ統合の安全性を評価する（統合しても品質が低下しないことを確認）
3. 軽量ワークフロー（7フェーズ）を定義する
4. フル/軽量の判断基準を策定する
5. task-specification-creator のテンプレートに軽量バリアントを追加する

### 3.5 実装課題と解決策（親タスクからの教訓）

| 課題                                      | 発見経緯                                         | 解決策                                                             | 教訓                                                          |
| ----------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------- |
| Phase 6（テスト拡充）が実質不要だった     | menu.tsのカバレッジがPhase 5完了時点で100%達成   | 小規模修正ではPhase 4でテストを十分に書けるため、Phase 6は省略可能 | 軽量ワークフローではPhase 4の完了条件にカバレッジ基準を含める |
| Phase 8（リファクタリング）の効果が限定的 | 83行のファイルにリファクタリングの余地がなかった | Phase 5で直接高品質なコードを書くことでPhase 8を省略               | 200行以下の新規ファイルではリファクタリングフェーズは不要     |
| Phase 12の仕様同期が最も時間を要した      | 実装83行に対して仕様更新が広範囲                 | Phase 12は規模に関わらず省略不可。更新対象の事前特定を効率化       | resource-mapのタスク種別→ファイル逆引きを活用                 |

## 4. 実行手順

### Phase構成

本タスク自体は軽量な仕様定義タスクであるため、以下の3ステップで実行する。

### Step 1: 過去タスク分析と軽量ワークフロー設計

#### 目的

過去の小規模修正タスクのフェーズ実行状況を分析し、軽量ワークフローの7フェーズ構成を確定する。

#### 手順

1. `docs/30-workflows/completed-tasks/` から200行以下の修正タスクを3件以上特定する
2. 各タスクで実質スキップされたフェーズを一覧化する
3. 以下の提案7フェーズ構成を検証・確定する

**提案する軽量ワークフロー（7フェーズ）:**

| Phase | 名称         | フルワークフロー対応 | 説明                                                           |
| ----- | ------------ | -------------------- | -------------------------------------------------------------- |
| L1    | 要件・設計   | Phase 1-3 統合       | 要件抽出と設計を1フェーズで実施。レビューは簡易チェックリスト  |
| L2    | テスト作成   | Phase 4              | テストファースト（変更なし）                                   |
| L3    | 実装         | Phase 5              | プロダクションコード実装（変更なし）                           |
| L4    | 品質検証     | Phase 7+9 統合       | カバレッジ確認 + Lint/型チェック/全テスト実行を1フェーズで実施 |
| L5    | 最終レビュー | Phase 10             | 多角的品質検証（簡易版）                                       |
| L6    | 手動テスト   | Phase 11             | UIテスト・E2Eシナリオ（該当する場合のみ）                      |
| L7    | ドキュメント | Phase 12             | 実装ガイド・仕様更新・未タスク検出（変更なし）                 |

4. フル/軽量の判断基準を確定する

**判断基準:**

| 条件                 | 軽量      | フル    |
| -------------------- | --------- | ------- |
| 変更行数             | 200行以下 | 200行超 |
| 新規IPC/型定義       | なし      | あり    |
| 影響コンポーネント数 | 1-2       | 3以上   |
| セキュリティ関連     | 非該当    | 該当    |

3条件以上が「軽量」列に該当する場合 → 軽量ワークフローを適用

#### 成果物

- 過去タスク分析結果（確認メモ）
- 7フェーズ構成の確定版
- 判断基準の確定版

#### 完了条件

- [ ] 過去3件以上の小規模タスクの分析が完了している
- [ ] 7フェーズの各フェーズに目的・完了条件が定義されている
- [ ] 判断基準が4条件以上で定義されている

### Step 2: テンプレート作成とスキル統合

#### 目的

軽量ワークフローのフェーズテンプレートを作成し、task-specification-creatorスキルに統合する。

#### 手順

1. `phase-templates-light.md` を作成する
   - 各フェーズ（L1-L7）に目的・実行タスク・成果物・完了条件を定義
   - フルワークフローから統合されたフェーズには、元フェーズの完了条件を全て含める
   - L1（要件・設計）には Phase 1-3 のチェックリストを統合
   - L4（品質検証）には Phase 7 のカバレッジ基準 + Phase 9 の品質ゲート4項目を含める
2. `workflow-selection-guide.md` を作成する
   - 判断基準テーブル
   - 判断フローチャート（テキスト形式）
   - 境界ケースの判断例（3件以上）
3. `task-specification-creator/SKILL.md` を更新する
   - 変更履歴に追加
   - ワークフロー選択の記述を追加

#### 成果物

- `phase-templates-light.md`
- `workflow-selection-guide.md`
- SKILL.md の更新差分

#### 完了条件

- [ ] `phase-templates-light.md` が L1-L7 の全フェーズを含んでいる
- [ ] 各フェーズに目的・実行タスク・成果物・完了条件が記載されている
- [ ] `workflow-selection-guide.md` に判断基準と境界ケース例が記載されている
- [ ] SKILL.md の変更履歴が更新されている

### Step 3: 検証と品質確認

#### 目的

作成したテンプレートと判断基準の妥当性を検証する。

#### 手順

1. TASK-FIX-ELECTRON-APP-MENU-ZOOM-001 を軽量ワークフローに当てはめ、全フェーズが機能することを机上検証する
2. 判断基準テーブルで過去10タスクを分類し、フル/軽量の判定が妥当かを確認する
3. 統合フェーズ（L1, L4）で元フェーズのチェック項目が全て含まれていることを確認する

#### 成果物

- 検証結果レポート（`workflow-selection-guide.md` 内に記載）

#### 完了条件

- [ ] TASK-FIX-ELECTRON-APP-MENU-ZOOM-001 での机上検証が完了している
- [ ] 過去10タスクでの判断基準検証が完了している
- [ ] 統合フェーズのチェック項目漏れがないことが確認されている

## 7. リスクと対策

| リスク                            | 影響度 | 発生確率 | 対策                                                       |

| 判断基準の閾値（200行）が不適切   | 中     | 中       | 過去10タスクで検証し閾値を調整。運用後も定期的に見直す     |

## 9. 備考

### レビュー指摘の原文（該当する場合）

```
本タスクは小規模な修正（83行の新規ファイル + 2行の既存ファイル変更）であり、
13 Phase のワークフローは過剰だった可能性がある。ただし、テスト20件・
カバレッジ100%の品質は確保できており、ワークフローの網羅性が品質に貢献した。
```

（出典: `docs/30-workflows/electron-app-menu-zoom/outputs/phase-12/skill-feedback-report.md` 総合評価）

### 補足事項

- 軽量ワークフローは「品質を下げる」ためではなく「不要なフェーズの管理オーバーヘッドを削減する」ために導入する
- Phase 12（ドキュメント）に相当する L7 は、P1-P4, P26, P51 等の教訓から省略不可とする
- 判断に迷った場合は常にフルワークフロー（13フェーズ）を選択する（安全側に倒す）
- 将来的に運用実績が蓄積されたら、閾値（200行）や条件数（3条件以上）を見直す
