## 1. 登録フロー（新規公開）

新規スキルをSkill Centerカタログに公開するまでの6ステップを定義する。

### 前提条件

- `visibility`が`"team"`または`"local"`のスキルのみ「公開する」操作が可能
- `visibility`が既に`"public"`のスキルに対してこのフローは適用しない

### Step 1: 公開操作の開始

- **操作者**: スキル作成者
- **トリガー**: UI上の「公開する」ボタンのクリック
- **操作可能な前提状態**: `visibility`が`"team"`または`"local"`
- **操作不可の前提状態**: `visibility`が`"public"`（ボタンを非活性または非表示にする）

### Step 2: PublishEligibility チェック（自動）

- システムが`PublishEligibility`チェックを自動実行する
- チェック項目:
  - `isBlocked`フラグの評価
  - ブロック理由（`blockedReasons`配列）の収集
- **結果が`isBlocked=true`の場合**:
  - Step 3以降には進まない
  - UIにブロック理由（`blockedReasons`の全件）を表示してフローを終了する
  - 表示例: 「公開できません: テスト未完了、必須フィールドが未入力」
- **結果が`isBlocked=false`の場合**: Step 3へ進む

### Step 3: metadataフォームの表示（条件付き）

- 以下の必須フィールドが**すべて**入力済みの場合はこのStepをスキップしてStep 4へ進む
  - `license`: 空文字列でないこと（`.trim() !== ""`）
  - `tags`: 1件以上の要素が存在すること
  - `description`: 空文字列でないこと（`.trim() !== ""`）
- 上記いずれかが未入力の場合、metadataフォームを表示して入力を求める
- フォーム送信後に再度Step 2のPublishEligibilityチェックを実行してから Step 4へ進む

### Step 4: 警告の確認（条件付き）

- `PublishEligibility`チェックの`warnings`配列が1件以上ある場合のみ表示する
- `warnings`が0件の場合はこのStepをスキップしてStep 5へ進む
- 表示内容:
  - 警告内容一覧（`warnings`配列の全件）
  - 「理解した上で公開する」チェックボックス
- チェックボックスにチェックを入れない限りStep 5への進行ボタンを非活性にする

### Step 5: 確認ダイアログの表示

- ダイアログ本文: 「公開するとすべてのユーザーが検索・インポートできます。取り消すには取り下げ操作が必要です」
- 選択肢: 「公開する」（登録実行）、「キャンセル」（フロー中断）
- 「キャンセル」選択時はStep 1の状態に戻る（スキルの状態は変更しない）
- 「公開する」選択時はStep 6へ進む

### Step 6: カタログへの反映

- `visibility`を`"public"`に変更する
- 変更をSkill Centerカタログに反映する（検索インデックスの更新を含む）
- 作成者のUIに「公開が完了しました」の通知を表示する

## 2. 更新フロー（新バージョン公開）

既に`"public"`状態のスキルに新バージョンを公開するまでの5ステップを定義する。

### Step 1: 変更保存とバージョン番号の更新

- **操作者**: スキル作成者
- **バージョン番号のルール（semver準拠）**:
  - `major.minor.patch`形式（例: `1.2.3`）
  - 新バージョンは現在の公開バージョンより数値的に大きくなければならない
  - breaking changeを含む変更には`major`バージョンの増加が必要（Step 2で強制される）
- 変更内容の保存とバージョン番号の更新を同時に行う

### Step 2: 互換性チェック（自動）

- breaking changeの有無を自動検出する
- **breaking change検出の基準**:
  - 必須パラメータの追加
  - 既存パラメータの型変更
  - 既存パラメータの削除
  - 出力形式の後方互換性を壊す変更
- **breaking change検出時**:
  - 現在のバージョン番号の`major`が増加していない場合、フローをブロックする
  - UIに「breaking changeが検出されました。メジャーバージョンを増加させてください」を表示する
  - 作成者がバージョン番号を`major`増加に修正後、Step 2を再実行する
- **breaking changeなしの場合**: Step 3へ進む

### Step 3: PublishEligibility チェック（自動）

- 登録フローStep 2と同じチェックを実行する
- `isBlocked=true`の場合: ブロック理由をUIに表示してフローを終了する
- `isBlocked=false`の場合: Step 4へ進む

### Step 4: 旧バージョン削除対象の確認

- 旧バージョンの保持ポリシーに基づき削除対象バージョンを算出してUIに表示する
- **保持ポリシー**:
  - `major`バージョンは過去2世代まで保持する
  - 保持対象: 現在公開する`major`と、その1つ前の`major`のみ
  - 例: 新バージョンが`3.x.x`の場合、`3.x.x`と`2.x.x`を保持し、`1.x.x`以前を削除対象とする
- UIに削除対象バージョンの一覧を表示し、作成者の確認を求める
- 削除対象が0件の場合はこのStepをスキップしてStep 5へ進む

### Step 5: 新バージョンの公開と旧バージョンの deprecated 化

- 確認後に新バージョンをカタログに公開する
- 削除対象の旧バージョンを`deprecated`状態に変更する（即時削除ではない）
- `deprecated`状態のバージョンはSkill Center検索結果に「非推奨」ラベルを表示する
- 作成者のUIに「バージョン X.Y.Z を公開しました」の通知を表示する

## 3. 取り下げフロー

### 3.1 通常取り下げ（deprecation）

- **操作者**: スキル作成者
- **操作**: 「取り下げる」ボタンのクリック
- **処理内容**:
  - `visibility`を`"public"`から`"team"`に変更する
  - Skill Center検索結果に「取り下げ済み」ラベルを表示する
  - 既にこのスキルをインポート済みのユーザーのローカルコピーには変更を加えない
- **事前確認ダイアログ**: 「取り下げると新規インポートができなくなります。既インポート済みユーザーのローカルコピーには影響しません。取り下げますか？」
- **完了後の状態**: `visibility = "team"`、既インポート済みコピーは引き続き利用可能

### 3.2 完全削除（removal）

- **実行可能条件**: 通常取り下げ（3.1）から30日以上経過していること
- **操作者**: スキル作成者
- **操作**: 「カタログから完全削除する」ボタンのクリック
- **事前確認ダイアログ**: 「インポート済みユーザー数：N人」を表示した上で「カタログから完全に削除します。この操作は取り消せません。続行しますか？」を表示する
  - N は削除操作実行時点でのインポート済みユーザー数
- **処理内容**:
  - Skill Centerカタログからスキルエントリを完全削除する
  - 既インポート済みユーザーのローカルコピーには変更を加えない
- **30日未経過の場合**: 削除ボタンを非活性にし、残り日数（例: 「あと23日後から削除可能」）を表示する

### 3.3 緊急取り下げ（emergency withdrawal）

- **発動条件**: セキュリティ脆弱性の発見（`security-operations.md`のP1またはP2インシデント）
- **操作者**: システム管理者（作成者ではない）
- **30日猶予の適用**: なし（即時非公開化）
- **処理内容**:
  - 管理者が`visibility`を強制的に`"local"`に変更する
  - Skill Centerカタログから即時非表示にする
  - インポート済みユーザー全員にアプリ内通知を送信する
    - 通知文: 「スキルXにセキュリティ上の問題が発見されたため、公開が停止されました」
  - 作成者に修正要請通知と再公開手順を送信する
- **再公開の条件**: 脆弱性修正後、管理者レビューを経て通常の登録フロー（Section 1）から再公開する

## 4. カテゴリ/タグ体系

### 4.1 カテゴリ定義

カテゴリは固定値からの選択のみ（自由入力不可）。スキルに設定できるカテゴリは1件のみ。

| カテゴリ値   | 表示名       | 用途説明                       |
| ------------ | ------------ | ------------------------------ |
| `automation` | 自動化       | タスク自動化・ワークフロー実行 |
| `analysis`   | 分析         | データ分析・情報解析           |
| `writing`    | ライティング | 文章生成・編集・翻訳           |
| `coding`     | コーディング | コード生成・レビュー・デバッグ |
| `research`   | リサーチ     | 情報収集・調査・要約           |
| `other`      | その他       | 上記いずれにも属さない         |

- 未選択の場合は`"other"`をデフォルト値として設定する
- カテゴリ変更はスキルが`"public"`の状態でも可能（即時反映）

### 4.2 タグ制約

タグは自由入力（固定値なし）。

| 制約項目           | ルール                                                          |
| ------------------ | --------------------------------------------------------------- |
| 最大件数           | 1スキルあたり10件まで                                           |
| 文字数（1件）      | 1文字以上50文字以下（`.trim()`後の文字数で評価）                |
| 重複               | 同一スキル内での同一タグの重複は不可                            |
| 大文字/小文字      | 区別しない（保存時は小文字に正規化する）                        |
| 使用可能文字       | Unicode文字・数字・ハイフン（`-`）・アンダースコア（`_`）を許可 |
| オートコンプリート | 既存の公開スキル（`visibility="public"`）のタグ一覧から提案する |

- タグが0件の場合はPublishEligibilityの`isBlocked=true`になる（Section 1 Step 2参照）
- タグが10件を超えた場合、11件目以降の入力欄を表示しない（UIレベルで制限）

## 6. エラー条件・ブロック条件

### 6.1 PublishEligibility ブロック条件（isBlocked=true）

以下の条件を1件以上満たす場合、`isBlocked=true`となり公開をブロックする。

| 条件ID | ブロック条件                               | 表示メッセージ例                 |
| ------ | ------------------------------------------ | -------------------------------- |
| B-01   | `metadata.license`が空文字列（trim後）     | ライセンスを入力してください     |
| B-02   | `metadata.tags`が0件                       | タグを1件以上設定してください    |
| B-03   | `metadata.description`が空文字列（trim後） | 説明文を入力してください         |
| B-04   | スキルのテストが未完了（テスト失敗状態）   | テストをすべて通過させてください |
| B-05   | スキルの構文エラーが存在する               | 構文エラーを解消してください     |

### 6.2 PublishEligibility 警告条件（warnings追加）

以下の条件を満たす場合、`warnings`に追加する（ブロックはしない）。

| 条件ID | 警告条件                            | 警告メッセージ例                                 |
| ------ | ----------------------------------- | ------------------------------------------------ |
| W-01   | `metadata.description`が50文字未満  | 説明文が短い可能性があります（推奨: 50文字以上） |
| W-02   | `metadata.tags`が3件未満            | タグが少ない可能性があります（推奨: 3件以上）    |
| W-03   | カテゴリが`"other"`に設定されている | より適切なカテゴリへの変更を検討してください     |

### 6.3 バージョン更新時のブロック条件

| 条件ID | ブロック条件                                             | 表示メッセージ例                                                        |
| ------ | -------------------------------------------------------- | ----------------------------------------------------------------------- |
| B-10   | breaking changeあり、かつmajorバージョンが増加していない | breaking changeが検出されました。メジャーバージョンを増加させてください |
| B-11   | 新バージョン番号が現在の公開バージョン以下               | バージョン番号は現在の公開バージョンより大きくしてください              |
| B-12   | semver形式に不適合（major.minor.patch形式でない）        | バージョン番号はX.Y.Z形式で入力してください                             |

### 6.4 完全削除時のブロック条件

| 条件ID | ブロック条件                            | 処理                                       |
| ------ | --------------------------------------- | ------------------------------------------ |
| B-20   | 取り下げからまだ30日未経過              | 削除ボタンを非活性化し、残り日数を表示する |
| B-21   | 通常取り下げ（visibility="team"）未実施 | 完全削除ボタン自体を非表示にする           |

## 7. テスト可能な条件式サマリー

Phase 4以降のテスト作成で参照する判定ロジックの条件式を明示する。

### 7.1 登録フロー条件式

```
// Step 2: PublishEligibility チェック
isBlocked = (
  metadata.license.trim() === "" ||
  metadata.tags.length === 0 ||
  metadata.description.trim() === "" ||
  hasTestFailures ||
  hasSyntaxErrors
)

// Step 3: metadataフォームスキップ条件
skipMetadataForm = (
  metadata.license.trim() !== "" &&
  metadata.tags.length >= 1 &&
  metadata.description.trim() !== ""
)

// Step 4: 警告確認スキップ条件
skipWarningConfirm = (warnings.length === 0)
```

### 7.2 バージョン更新条件式

```
// Step 2: breaking change によるブロック
blockDueToBreakingChange = (
  hasBreakingChange &&
  parsedVersion(newVersion).major <= parsedVersion(currentPublishedVersion).major
)

// Step 4: 削除対象バージョン算出
retainedMajors = [newVersion.major, newVersion.major - 1]
deprecationTargets = publishedVersions.filter(v =>
  parsedVersion(v).major < newVersion.major - 1
)
```

### 7.3 タグ検証条件式

```
// 1件のタグの有効性
isValidTag = (
  typeof tag === "string" &&
  tag.trim().length >= 1 &&
  tag.trim().length <= 50
)

// スキル全体のタグ配列の有効性
isValidTagList = (
  tags.length >= 1 &&
  tags.length <= 10 &&
  tags.every(t => isValidTag(t)) &&
  new Set(tags.map(t => t.toLowerCase())).size === tags.length // 重複なし
)
```

### 7.4 完全削除可能条件式

```
// 完全削除の実行可能判定
canPermanentlyRemove = (
  skill.visibility === "team" &&
  daysSinceDeprecation(skill.deprecatedAt) >= 30
)
```

## 8. 検証可能性

各受入基準（AC-4）に対する検証方法を定義する。

| 受入基準ID | 検証内容                                                           | 検証方法                                                                   |
| ---------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| AC-4-1     | PublishEligibilityチェックでブロック条件B-01〜B-05が正しく機能する | ユニットテスト: 各ブロック条件を個別にテスト                               |
| AC-4-2     | metadataフォームが未入力時のみ表示される                           | ユニットテスト: skipMetadataForm条件式の境界値テスト                       |
| AC-4-3     | warnings=0件の場合に警告確認ステップがスキップされる               | ユニットテスト: warnings配列長0と1での分岐テスト                           |
| AC-4-4     | breaking change検出時にmajorバージョン増加を強制する               | ユニットテスト: blockDueToBreakingChange条件式テスト                       |
| AC-4-5     | major過去2世代保持ポリシーが正しく動作する                         | ユニットテスト: deprecationTargets算出ロジックテスト                       |
| AC-4-6     | 通常取り下げ後30日未満は完全削除をブロックする                     | ユニットテスト: canPermanentlyRemove条件式の境界値テスト（29日/30日/31日） |
| AC-4-7     | 緊急取り下げがP1/P2インシデントで即時実行される                    | 統合テスト: 管理者権限での強制visibility変更                               |
| AC-4-8     | タグが最大10件制限・重複禁止・文字数制限を守る                     | ユニットテスト: isValidTagList条件式の境界値テスト                         |
| AC-4-9     | カテゴリが6種類の固定値のみ選択可能                                | ユニットテスト: カテゴリ値バリデーション                                   |
| AC-4-10    | 完全削除前にインポート済みユーザー数が表示される                   | 統合テスト: 削除確認ダイアログのN人表示確認                                |
