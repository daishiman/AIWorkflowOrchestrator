## レビュー観点

### 1. スコープ最小化

| チェック項目                                                           | 判定 | 備考                                                                   |
| ---------------------------------------------------------------------- | ---- | ---------------------------------------------------------------------- |
| 変更対象が `useMainlineExecutionAccess.ts` の1ファイルに絞られているか | -    | Phase 2 設計を確認すること                                             |
| 新規実装がゼロであるか（既存 API 呼び出しのみ）                        | -    | `resolveHealthPolicy` / `buildMainlineExecutionAccessState` は実装済み |
| 他の Hook / Component への波及変更が含まれていないか                   | -    | スコープ外への変更がないこと                                           |
| テスト以外のファイルが追加されていないか                               | -    | 新規ファイル作成は不要なはず                                           |

### 2. 型安全性

| チェック項目                                                             | 判定 | 備考                                                         |
| ------------------------------------------------------------------------ | ---- | ------------------------------------------------------------ |
| `HealthPolicyInput` の全フィールドに型安全な値が渡されているか           | -    | `state-mapping.md` の変換ルールを確認                        |
| `connectionStatus` の型キャストが安全か（不正な値を許容しないか）        | -    | Phase 1 調査結果に基づく型ガードの必要性を確認               |
| `resolveHealthPolicy` の戻り値型（`HealthPolicy`）が正しく使われているか | -    | `buildMainlineExecutionAccessState` の引数型と一致しているか |
| `pnpm typecheck` が PASS することが設計上保証されているか                | -    | 型キャストを使用している場合は特に注意                       |

### 3. 後方互換性

| チェック項目                                                           | 判定 | 備考                                              |
| ---------------------------------------------------------------------- | ---- | ------------------------------------------------- |
| 削除される `apiKeyDegraded` が他の箇所で参照されていないか             | -    | Phase 2 の「削除対象確認コマンド」で0件になること |
| `buildMainlineExecutionAccessState()` の他の引数が変更されないか       | -    | healthPolicy 追加のみで既存引数は維持             |
| 既存テストが破壊されない設計になっているか                             | -    | Phase 4 でテストを修正する場合は影響範囲を明示    |
| `resolveHealthPolicy` の動作が既存の `apiKeyDegraded` ロジックと等価か | -    | セマンティクスの変化がないことを確認              |

### 4. インポート規則

| チェック項目                                                                | 判定 | 備考                                         |
| --------------------------------------------------------------------------- | ---- | -------------------------------------------- |
| `resolveHealthPolicy` が `@repo/shared/types` からインポートされているか    | -    | AC-4 の要件を満たすこと                      |
| サブパス直接指定（`@repo/shared/types/health-policy` 等）が禁止されているか | -    | 設計書のインポート例を確認                   |
| プロジェクトの既存インポートスタイルと統一されているか                      | -    | Phase 1 の命名規則確認結果と整合していること |

### 5. 設計完全性

| チェック項目                                  | 判定 | 備考                                            |
| --------------------------------------------- | ---- | ----------------------------------------------- |
| FR-01〜FR-03 に対応する設計が存在するか       | -    | Phase 2 の4ステップが FR を全てカバーしているか |
| AC-1〜AC-6 が検証可能な形式で定義されているか | -    | Phase 1 の検証方法テーブルを確認                |
| NFR-01〜NFR-03 の設計対応があるか             | -    | 型安全・後方互換・インポート規則の各設計観点    |
| リスクと対策が定義されているか                | -    | Phase 2 のリスクテーブルを確認                  |

## 判定基準

| 判定         | 条件                                      | 次のアクション                 |
| ------------ | ----------------------------------------- | ------------------------------ |
| **PASS**     | 全チェック項目が問題なし                  | Phase 4 へ進む                 |
| **MINOR**    | 軽微な指摘あり（実装中に解決可能）        | 指摘事項を記録しPhase 4 へ進む |
| **MAJOR**    | 重大な問題あり（設計の修正が必要）        | Phase 2 に差し戻す             |
| **CRITICAL** | 要件の見直しが必要（AC・FR の変更を伴う） | Phase 1 に差し戻す             |
