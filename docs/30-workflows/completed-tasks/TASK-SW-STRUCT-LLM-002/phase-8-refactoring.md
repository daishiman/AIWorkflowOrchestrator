## 目的

Phase 5 で実装した features 自動生成コードを品質の観点で見直し、
可読性・保守性・責務分離を改善する。動作を変えないリファクタリングのみを行う。

- features生成ロジックのコード品質確認
- プライベートメソッド抽出の要否判断（50行以上なら抽出を検討）

- ログ出力の整理（冗長・不足の確認）
- 型定義の改善（any型の排除・明示的な型付け）
- リファクタリング後のテスト全件 PASS 確認

## 実行手順

### 1. コード品質チェック

以下の観点で features 生成コードを確認する:

| 観点           | チェック内容                                                                 |
| -------------- | ---------------------------------------------------------------------------- |
| 関数サイズ     | features生成ロジックが50行以上ならプライベートメソッドへの抽出を検討する     |
| プロンプト定数 | プロンプト文字列が複数箇所で使用されているなら定数化を検討する               |
| ログ出力       | 冗長なログや不足しているログがないか確認する                                 |
| 型安全性       | any型が使用されていないか確認し、明示的な型定義を追加する                    |
| 命名の一貫性   | 同ファイル内の他のメソッドと一貫した命名スタイルが守られているか確認する     |
| エラー処理     | フォールバック（空配列）のエラーハンドリングが明確に記述されているか確認する |

### 2. リファクタリング方針

**変更が必要な場合のみ**実施する。

主なリファクタリング候補:

```typescript

async runCreateWorkflow(...) {

  try {
    // LLM呼び出しロジック（50行以上の場合はメソッド抽出を検討）
    features = await this.generateFeaturesWithLlm(skillDescription);
  } catch (error) {
    this.logger.warn('features生成失敗、空配列でフォールバック', { error });
    features = [];
  }
  // ...
}

// パターン2: プライベートメソッド抽出（ロジックが肥大化した場合）
private async generateFeaturesWithLlm(description: string): Promise<string[]> {
  // features生成ロジックを分離
}
```

**判断基準**:

- features生成ロジックが50行以上 → プライベートメソッド化
- プロンプト文字列が複数箇所で参照 → 定数化（例: `FEATURES_GENERATION_PROMPT`）
- 上記に該当しない場合 → 変更不要と判断して記録
