## 目的

Phase 2で作成した設計の妥当性を多角的な観点からレビューし、実装フェーズへ進む可否を判定する。

## 背景

Clean Architectureへのリファクタリングは大規模な変更となるため、設計段階で問題を検出することが重要。設計レビューを通じて、アーキテクチャ原則への準拠、ドメインモデルの妥当性、実装可能性を確認する。

---

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: Clean Architecture準拠レビュー

**目的**: 設計がClean Architecture原則に準拠しているか検証する

**実行手順**:

1. 依存関係ルールの検証:
   - [ ] Domain層が他のレイヤーに依存していないか
   - [ ] Application層がDomain層のみに依存しているか
   - [ ] Infrastructure層が正しい方向に依存しているか
   - [ ] Presentation層がApplication層のみに依存しているか

2. レイヤー分離の検証:
   - [ ] 各レイヤーの責務が明確に分離されているか
   - [ ] レイヤー間の通信がインターフェースを介しているか
   - [ ] 具象実装がインターフェースに隠蔽されているか

3. SOLID原則の検証:
   - [ ] **S**ingle Responsibility: 各クラスが単一責務か
   - [ ] **O**pen/Closed: 拡張に開き、変更に閉じているか
   - [ ] **L**iskov Substitution: 派生クラスが基底クラスと置換可能か
   - [ ] **I**nterface Segregation: インターフェースが適切に分離されているか
   - [ ] **D**ependency Inversion: 抽象に依存しているか

**期待される成果物**:

- レビューチェックリスト（本タスク内で完了）

---

### タスク2: ドメインモデルレビュー

**目的**: ドメインモデルがDDD原則に準拠しているか検証する

**実行手順**:

1. エンティティの検証:
   - [ ] エンティティが識別子を持っているか
   - [ ] エンティティがビジネスロジックを含んでいるか（Rich Domain Model）
   - [ ] 不変条件がエンティティ内で保護されているか

2. 値オブジェクトの検証:
   - [ ] 値オブジェクトが不変であるか
   - [ ] 等価性が値で判断されるか
   - [ ] バリデーションがファクトリメソッドで行われるか

3. ユビキタス言語の検証:
   - [ ] 命名がビジネスドメインを反映しているか
   - [ ] 既存のインターフェース仕様（interfaces-chat-history.md）と整合しているか

4. 集約境界の検証:
   - [ ] ChatSessionが集約ルートとして適切か
   - [ ] ChatMessageがChatSessionの一部として扱われるべきか

**期待される成果物**:

- レビューチェックリスト（本タスク内で完了）

---

### タスク3: 実装可能性レビュー

**目的**: 設計が実装可能であり、移行リスクが管理可能か検証する

**実行手順**:

1. 段階的移行の検証:
   - [ ] Strangler Fig Patternが適切に計画されているか
   - [ ] 各フェーズで既存機能を壊さないか
   - [ ] フィーチャーフラグによる切り替えが可能か

2. テスト容易性の検証:
   - [ ] 各コンポーネントが単体テスト可能か
   - [ ] モック/スタブの注入が容易か
   - [ ] 依存関係がテスト用に差し替え可能か

3. リスク評価:
   - [ ] 既存データとの互換性が保たれるか
   - [ ] パフォーマンスへの影響は許容範囲か
   - [ ] ロールバック計画が現実的か

4. 工数見積もり妥当性:
   - [ ] 各タスクの粒度が適切か
   - [ ] 依存関係が正しく定義されているか
   - [ ] リスクバッファが考慮されているか

**期待される成果物**:

- レビューチェックリスト（本タスク内で完了）

---

### タスク4: 既存仕様との整合性レビュー

**目的**: 新設計が既存システム仕様と整合しているか検証する

**実行手順**:

1. インターフェース仕様との整合性:
   - [ ] 既存のRepository/Serviceインターフェースが維持されるか
   - [ ] 既存のDTO型との互換性があるか
   - [ ] 既存のビジネスルール（BR-SESSION-_, BR-MESSAGE-_）が実装されるか

2. データベーススキーマとの整合性:
   - [ ] 既存スキーマを変更せずに移行可能か
   - [ ] マッパーが正しくドメイン-永続化変換を行えるか

3. UI層との整合性:
   - [ ] 既存コンポーネントが新Contextに移行可能か
   - [ ] 既存のカスタムフックが新パターンに対応可能か

**期待される成果物**:

- レビューチェックリスト（本タスク内で完了）

---

### タスク5: レビュー結果判定・レポート作成

**目的**: レビュー結果を総合判定し、次フェーズへの進行可否を決定する

**実行手順**:

1. レビュー結果を集計する:
   - 各観点での問題点を一覧化
   - 問題の重大度を分類（Critical/Major/Minor）

2. 判定を行う:

   | 判定     | 条件                     | 次のアクション          |
   | -------- | ------------------------ | ----------------------- |
   | PASS     | 全レビュー観点で問題なし | Phase 4へ進行           |
   | MINOR    | 軽微な指摘あり           | 指摘対応後、Phase 4へ   |
   | MAJOR    | 重大な問題あり           | Phase 2へ戻り設計修正   |
   | CRITICAL | 致命的な問題あり         | Phase 1へ戻り要件再検討 |

3. レビューレポートを作成する:
   - レビュー観点ごとの結果
   - 検出された問題点と対応方針
   - 最終判定と次のアクション

**期待される成果物**:

- `outputs/phase-3/design-review-report.md` - 設計レビューレポート
