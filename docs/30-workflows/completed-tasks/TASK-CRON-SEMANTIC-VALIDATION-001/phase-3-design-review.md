## 目的

Phase 2 の設計内容を多角的に検証し、Phase 4（テスト作成）に進むための品質ゲートを通過する。PASS / MINOR / MAJOR の判定を行い、MAJOR の場合は Phase 2 に戻る。

---

## 実行タスク

1. **設計内容のレビュー**: Phase 2 の全成果物を読み込み、矛盾・漏れ・整合性を確認する
2. **ブラウザ対応確認**: 純 TypeScript の手動実装がブラウザ（Electron Renderer）で動作するか確認する
3. **バンドルサイズ影響確認**: 外部依存を追加しないため、影響が実質ゼロであることを確認する
4. **パフォーマンス確認**: バリデーション処理時間が 100ms 未満であることを設計上保証できるか確認する
5. **既存テストへの影響確認**: 意味論チェック追加が既存の構文・値域チェックテストを壊さないか確認する
6. **ゲート判定**: PASS / MINOR / MAJOR を判定し、次のアクションを決定する

## 実行手順

### 1. 設計レビューチェックリスト

#### 矛盾チェック

| チェック項目                                                                                   | 確認結果 | 備考 |
| ---------------------------------------------------------------------------------------------- | -------- | ---- |
| バリデーションフロー（3段階）と受け入れ基準（AC-1〜AC-5）が整合しているか                      | -        |      |
| `validateCronSemantics` の関数シグネチャが `validateCronExpression` の拡張方針と整合しているか | -        |      |
| エラーメッセージ（日本語）が AC-5 の「日本語で表示される」要件を満たしているか                 | -        |      |
| UI影響設計が ScheduleDialog / ConversationRoundStep の既存実装と整合しているか                 | -        |      |

#### 漏れチェック

| チェック項目                                                    | 確認結果 | 備考 |
| --------------------------------------------------------------- | -------- | ---- |
| AC-1〜AC-5 の全てがバリデーションフロー設計にカバーされているか | -        |      |
| 実装方式設計に ブラウザ対応確認が含まれているか                 | -        |      |
| 手動実装で 2月29日を有効、2月30日/31日を無効としているか        | -        |      |

#### 整合性チェック

| チェック項目                                                           | 確認結果                   | 備考 |
| ---------------------------------------------------------------------- | -------------------------- | ---- | --- |
| 公開契約が `string                                                     | null` のままで維持されるか | -    |     |
| UI影響設計が既存の `ScheduleConfigValidationResult` 型と整合しているか | -                          |      |

### 2. ブラウザ対応確認

**手動実装の確認項目**

- [ ] 純粋な TypeScript 演算のみを使用していることを確認
- [ ] 外部依存を追加していないことを確認
- [ ] `2月29日` を有効、`2月30日` / `2月31日` を無効としていることを確認

### 3. バンドルサイズ影響確認

| 項目     | 追加サイズ（gzip） | 判定基準         | 判定 |
| -------- | ------------------ | ---------------- | ---- |
| 外部依存 | なし               | 追加なしならPASS | -    |

### 4. パフォーマンス確認

- 意味論チェックは純粋な演算（日付計算）である
- 設計上、バリデーション処理時間は 100ms 未満であることが保証されるか確認する
- 大量の呼び出し（フォーム入力のたびに実行）でも問題ないか確認する

### 5. 既存テストへの影響確認

```bash
# 既存テストファイルの確認
ls apps/desktop/src/__tests__/utils/

# scheduleConfigValidatorのテストが存在する場合は内容を確認
cat apps/desktop/src/__tests__/utils/scheduleConfigValidator.test.ts 2>/dev/null \
  || echo "テストファイルなし（既存拡張）"
```

- [ ] 既存テストが存在する場合、意味論チェック追加後も全て通過できる設計か確認する
- [ ] `0 9 * * *` / `0 9 1 2 *` / `0 9 29 2 *` がエラーを返さない設計か確認する

### 6. ゲート判定基準

| 判定      | 定義                                                         | アクション                          |
| --------- | ------------------------------------------------------------ | ----------------------------------- |
| **PASS**  | 全チェック項目が問題なし                                     | Phase 4 へ進む                      |
| **MINOR** | 軽微な不明点・改善点あり（設計の本質に影響しない）           | 指摘事項を記録しつつ Phase 4 へ進む |
| **MAJOR** | 設計の根幹に関わる問題あり（ブラウザ非対応、型定義の矛盾等） | Phase 2 に戻り再設計する            |

**MAJOR 判定の例:**

- `validateCronSemantics` の関数設計が `validateCronExpression` の既存シグネチャと互換性がない
- エラーメッセージ設計が AC-5 の要件（日本語表示）を満たしていない
