## 1. 未カバー箇所一覧

### UC-001: parseRetryAfterMs - HTTP日付形式パース

| 項目       | 内容                                                        |
| ---------- | ----------------------------------------------------------- |
| 関数       | `parseRetryAfterMs()`（内部関数）                           |
| 箇所       | HTTP日付形式（`Wed, 21 Oct 2015 07:28:00 GMT`）のパース分岐 |
| カバレッジ | Branch未到達                                                |
| 影響度     | 低                                                          |

**分析**:

- Retry-Afterヘッダーは秒数形式（例: `"30"`）とHTTP日付形式（例: `"Wed, 21 Oct 2015 07:28:00 GMT"`）の2種類をサポートする仕様（RFC 7231）
- 現在の実装は秒数形式のみをサポートしており、HTTP日付形式のパース処理は実装されていない
- Claude API（Anthropic API）のRate Limit応答では秒数形式のRetry-Afterのみが使用される
- HTTP日付形式が返されるケースは実運用上ほぼ存在しない

**対応方針**: **テスト追加不要**

- 未実装の機能パスであるため、テスト追加ではなく将来の機能拡張として記録
- 現時点では秒数形式のサポートで十分
- HTTP日付形式が必要になった場合はPhase 8以降で機能追加として対応

---

### UC-002: isRetryableError - エキゾチックなエラーオブジェクト

| 項目       | 内容                                                     |
| ---------- | -------------------------------------------------------- |
| 関数       | `isRetryableError()`                                     |
| 箇所       | 非Errorオブジェクト（Symbol、BigInt、Proxy等）の判定分岐 |
| カバレッジ | 一部Branch未到達                                         |
| 影響度     | 極低                                                     |

**分析**:

- Phase 6でnullおよび文字列のテストケースを追加済み
- Symbol、BigInt、Proxy等のエキゾチックなオブジェクトが渡された場合の分岐が未テスト
- これらの型がisRetryableErrorに渡されることは実運用上あり得ない（Anthropic SDKからはErrorオブジェクトのみが投げられる）
- 全ての非Errorオブジェクトに対して `{ retryable: false }` を返す設計は正しい動作

**対応方針**: **テスト追加不要**

- 実運用上到達しない分岐であり、`{ retryable: false }` を返す安全なデフォルト動作が実装済み
- null/undefined/文字列のテスト（Phase 6）で代表的な非Errorケースはカバー済み
- エキゾチックな型のテストを追加してもコード品質への貢献は限定的

### UC-003: executeWithRetry - 内部例外ハンドリング

| 項目       | 内容                                                            |
| ---------- | --------------------------------------------------------------- |
| 関数       | `executeWithRetry()`                                            |
| 箇所       | リトライループ内での予期しない例外（TypeError等）のキャッチ処理 |
| カバレッジ | 一部Line未到達                                                  |
| 影響度     | 低                                                              |

**分析**:

- executeWithRetry内のtry-catchブロックにおいて、isRetryableErrorの判定でretryable=falseとなる予期しないエラー型のフォールスルーパスが存在
- Phase 4のテスト（non-retryable error、AbortError）で主要パスはカバー済み
- 残りはTypeError等のプログラミングエラーが発生した場合のパスであり、これは正常動作ではなくバグ発生時のフェイルセーフ

**対応方針**: **テスト追加不要**

- フェイルセーフパスの動作は「リトライしない」であり、安全な動作が保証されている
- プログラミングエラーのテストは意図的なバグ注入となり、テストの保守性を低下させる
- 非リトライ対象エラーのテスト（HTTP 400/401/403、AbortError、unknown error）で代表パスはカバー済み
