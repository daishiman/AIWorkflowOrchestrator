# 実装ガイド Part 1: リトライ機構の概念説明

## はじめに

この文書は、SkillExecutor に追加されたリトライ（再試行）の仕組みについて、専門知識がなくても理解できるように説明します。

---

## リトライって何？

### 日常の例え話

電話をかけて「話し中」だったら、少し待ってからもう一度かけ直すよね。それが「リトライ」です。

自動販売機にお金を入れてボタンを押したのに反応しなかったら、もう一度押すよね。それもリトライです。

コンピュータの世界でも同じことが起きます。インターネットを通じて何かのサービスにリクエストを送ったとき、たまたま回線が混んでいたり、サーバーが一時的に忙しかったりして、うまく届かないことがあります。そのとき、もう一度やり直すのが「リトライ」です。

---

## なぜ自動リトライが必要？

### 手動リトライの面倒さ

インターネットが一瞬切れただけで、やっていた作業が全部やり直しになったら困るよね。

たとえば、AIにお願いごとを送ったときに、たまたまネットワークが不安定で失敗したとします。手動でもう一度やり直すのは面倒だし、何が失敗したかもわかりにくいです。

自動リトライがあれば、一時的なトラブルのときに、プログラムが自動的にもう一度やり直してくれます。ユーザーは失敗があったことすら気づかず、うまくいった結果だけを受け取れます。

---

## 待ち時間が長くなる仕組み（Exponential Backoff）

### なぜ少しずつ長く待つのか

レストランが混んでいたとします。最初は5分待って、次は10分待って、さらに20分待つ。すぐに何度もドアを叩いたらお店の人が困るからです。

コンピュータの世界でも同じです。サーバーが忙しいときに、すぐに何度もリクエストを送りつけると、余計にサーバーが大変になります。だから、「最初は1秒待つ、次は2秒待つ、その次は4秒待つ」というように、待ち時間を段階的に長くしていきます。

この仕組みを「指数バックオフ」と呼びます。「指数」というのは、待ち時間が「倍々に増えていく」という意味です。

### 具体的な待ち時間

| 何回目のリトライ | 基本の待ち時間 |
| ---------------- | -------------- |
| 1回目            | 1秒            |
| 2回目            | 2秒            |
| 3回目            | 4秒            |

ただし、どんなに待ち時間が増えても30秒を超えないように上限が決まっています。

---

## ちょっとランダムにする仕組み（Jitter）

### なぜランダムにするのか

学校の授業が終わったとき、みんなが同時にドアに向かったら混み合うよね。少しずつバラバラのタイミングで出ていけば混まないよね。

コンピュータの世界でも、たくさんのユーザーが同時にエラーを受け取ったとき、全員が同じタイミングでリトライすると、また同じようにサーバーが混み合ってしまいます。

だから、待ち時間に少しだけランダムなばらつき（これを「ジッター」と呼びます）を入れます。これにより、みんなが少しずつ違うタイミングでリトライするので、サーバーへの負荷が分散されます。

### 具体的にどれくらいバラつくか

基本の待ち時間に対して、前後20%の範囲でばらつきます。

| リトライ回数 | 基本待ち時間 | ばらつき範囲 |
| ------------ | ------------ | ------------ |
| 1回目        | 1秒          | 0.8秒〜1.2秒 |
| 2回目        | 2秒          | 1.6秒〜2.4秒 |
| 3回目        | 4秒          | 3.2秒〜4.8秒 |

---

## やめどきを決める（最大回数）

### なぜ無限にリトライしないのか

友達に電話して3回かけても出なかったら、「今日は忙しいんだな」ってあきらめるよね。何十回もかけ続けたら迷惑だし、自分の時間も無駄になります。

コンピュータでも同じです。サーバーが本当に壊れている場合、いくらリトライしても成功しません。無限にリトライを続けると、ユーザーをずっと待たせることになり、コンピュータのリソースも無駄に使います。

だから、最大3回（デフォルト設定）までリトライして、それでもダメならあきらめてエラーを返します。

---

## リトライしてはいけないエラー

全部のエラーに対してリトライするわけではありません。

### リトライする場合（一時的なトラブル）

- ネットワークが一瞬切れた
- サーバーが混み合っている（「429 レート制限」エラー）
- サーバー側の一時的な問題（「500番台」エラー）
- 時間がかかりすぎた（タイムアウト）

### リトライしない場合（根本的な問題）

- パスワードが間違っている（何度やっても同じ）
- リクエストの内容が間違っている（内容を直さない限りダメ）
- 探しているものが存在しない

リトライしても意味がないエラーには、すぐにあきらめてユーザーに知らせます。

---

## リトライ中にユーザーに知らせる

リトライが発生すると、画面に通知が送られます。「今リトライしています。1回目の試行中です」といった情報が送られるので、ユーザーは何が起きているか分かります。

また、ユーザーがリトライを待ちたくない場合は、いつでも「中断」できます。リトライの待ち時間中でも、中断ボタンを押せばすぐに止まります。

---

## まとめ

| 仕組み                 | 日常の例え                                                           |
| ---------------------- | -------------------------------------------------------------------- |
| リトライ               | 電話が話し中だったら、かけ直す                                       |
| 指数バックオフ         | レストランが混んでいたら、だんだん長く待つ                           |
| ジッター               | 授業が終わったら、バラバラのタイミングで出ていく                     |
| 最大回数               | 3回かけてダメならあきらめる                                          |
| リトライ対象の判別     | 一時的なトラブルだけリトライする（パスワード間違いはリトライしない） |
| ユーザーへの通知と中断 | 「今やり直し中です」と知らせて、いつでも止められるようにする         |
