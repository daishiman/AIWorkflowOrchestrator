## 目的

Phase 2 で策定したテスト有効化設計（モック戦略・エラーシミュレーション設計・実装パターン）が、Phase 1 の要件（FR-001 ~ FR-017, NFR-001 ~ NFR-007）を満たしているかを検証する。テスト設計の妥当性、モック戦略の適切さ、既存テストとの整合性、および既知の落とし穴（P9/P13/P20）への対策を多角的にレビューし、ゲート判定（PASS / MINOR / MAJOR）を行う。

## 実行タスク

- 観点レビュー: テスト設計・モック戦略・スコープ遵守を検証する
- リスクレビュー: 既知Pitfall対策の妥当性を確認する
- ゲート判定: PASS/MINOR/MAJORの判定基準に基づき進行可否を決定する

### Task 1: レビュー観点の逐次検証

### レビュー観点 1: テスト設計の妥当性

| チェック項目                                                 | 判定基準                                                       |
| ------------------------------------------------------------ | -------------------------------------------------------------- |
| 17箇所全ての TODO に対する有効化設計が策定されているか       | Phase 2 設計書に全17箇所の設計が個別に記載されている           |
| 各テストのアサーションが実装の振る舞いを正しく検証しているか | `expect()` の引数が実装コードの出力仕様と一致している          |
| テストの粒度が適切か（1テスト1検証事項）                     | 各テストが単一の振る舞いのみを検証している                     |
| テスト名が検証内容を正確に表現しているか                     | テスト名（`it("...")`）が期待動作を明確に記述している          |
| コメントアウト解除とテスト書き換えの判断が正しいか           | SE-TODO-1/2はコメントアウト解除、SE-TODO-3/4/5は書き換えが適切 |

### レビュー観点 2: モック戦略の適切さ

| チェック項目                                                       | 判定基準                                                                |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| 既存の `vi.mock` / `vi.hoisted` パターンを逸脱していないか         | 新規の `vi.mock` 呼び出しが追加されていない                             |
| `mockCreate` の引数検証パターンが実装のSDK呼び出しと一致しているか | `agent-client.ts` の `Anthropic().messages.create()` 呼び出し引数と整合 |
| `mockAgentAPI.query` の引数検証パターンが実装と一致しているか      | `skill-executor.ts` の `agentAPI.query()` 呼び出し引数と整合            |
| `mockRejectedValueOnce` の使用がテスト間分離を保証しているか       | 1テスト限りのモック変更で後続テストに影響しない                         |
| エラーオブジェクトの構造（`status` プロパティ追加）が型安全か      | `as Record<string, unknown>` を使用し `any` 型を回避している            |

### レビュー観点 3: 既存テストとの整合性

| チェック項目                                                 | 判定基準                                                   |
| ------------------------------------------------------------ | ---------------------------------------------------------- |
| 有効化により既存テスト（TODO以外）が破壊されないか           | `beforeEach` のモックリセットで影響を遮断している          |
| `beforeEach` / `afterEach` のリセット処理が十分か            | `vi.clearAllMocks()` / `mockCreate.mockReset()` が設定済み |
| 既存の類似テスト（EDGE-AC-08等）とパターンが統一されているか | 同一のアサーション構文・モック設定パターンを使用している   |
| テスト実行順序への依存がないか                               | 各テストが独立して実行可能（P9準拠）                       |

### レビュー観点 4: 既知の落とし穴への対策

| チェック項目                                                                               | 判定基準                                                             |
| ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| P9（テスト間リーク）: モジュールスコープ変数のリセットが漏れなく行われているか             | `beforeEach` で `vi.clearAllMocks()` / `mockCreate.mockReset()` 実施 |
| P13（タイマー無限ループ）: `runAllTimers` ではなく `advanceTimersByTime` を使用しているか  | 全タイマーテストで `vi.advanceTimersByTimeAsync()` を使用            |
| P13（タイマー無限ループ）: setTimeout + Promise + 再スケジュールパターンが回避されているか | 30秒タイムアウトテストで無限ループリスクが評価されている             |
| P20（ログ出力汚染）: テスト中の console 出力が抑制されているか                             | エラーテストで `console.error` が意図せず出力されない設計            |
| P21（DI追加時の大規模修正）: モック追加が最小限に抑えられているか                          | 既存モック構成の拡張のみで新規テストに対応                           |

### レビュー観点 5: スコープ遵守

| チェック項目                                     | 判定基準                                                               |
| ------------------------------------------------ | ---------------------------------------------------------------------- |
| プロダクションコードの変更が含まれていないか     | `skill-executor.ts` / `agent-client.ts` への変更が設計に含まれていない |
| 新規テストケースの追加が含まれていないか         | 既存17箇所の TODO 有効化に限定されている                               |
| テストフレームワーク設定の変更が含まれていないか | `vitest.config.ts` 等の変更が設計に含まれていない                      |
| 対象外のテストファイルへの変更が含まれていないか | 対象は3ファイルのみに限定されている                                    |

### レビュー観点 6: 要件カバレッジ

| チェック項目                                           | 判定基準                                           |
| ------------------------------------------------------ | -------------------------------------------------- |
| FR-001 ~ FR-017 の全要件に対応する設計が存在するか     | 17箇所全ての FR に対応する有効化設計がある         |
| AC-001 ~ AC-017 の全受入基準を満たす設計になっているか | 各 AC の Then 条件がテストのアサーションで検証可能 |
| NFR-001（全テスト PASS）を達成する見込みがあるか       | モック設計が実装の振る舞いと整合している           |
| NFR-003（TODO除去）の対応方針が設計に含まれているか    | コメント削除の対象行が明確になっている             |
| NFR-006（`any` 型禁止）が設計で遵守されているか        | 全コードサンプルで `any` 型が使用されていない      |

## ゲート判定基準

### PASS（Phase 4 へ進行）

以下の **全条件** を満たす場合:

- [ ] 17箇所全ての TODO に対する有効化設計が策定されている
- [ ] モック戦略が既存パターン（`vi.mock` / `vi.hoisted`）と整合している
- [ ] `mockCreate` / `mockAgentAPI.query` の引数検証パターンが実装と一致している
- [ ] エラーシミュレーション設計（401/500/タイムアウト/API key not found）が妥当である
- [ ] 既存テストとの整合性が設計段階で確認されている
- [ ] P9/P13/P20 への対策が設計に組み込まれている
- [ ] スコープ外の変更が含まれていない
- [ ] NFR-006（`any` 型禁止）が全コードサンプルで遵守されている
- [ ] 全 6 レビュー観点で問題なし

### MINOR（指摘対応後 Phase 4 へ進行）

以下のいずれかに該当する場合:

| MINOR 条件                                                    | 対応内容                                       |
| ------------------------------------------------------------- | ---------------------------------------------- |
| モック引数検証パターンの一部が実装の引数構造と不一致          | 実装コードを再確認し、引数パターンを修正する   |
| エラーメッセージの期待値が実装のエラーメッセージと不一致      | 実装のエラーメッセージを確認し期待値を修正する |
| テスト名の記述に改善余地がある                                | テスト名を修正してから Phase 4 へ進行          |
| P13 リスク評価の記載が不十分                                  | タイムアウトテストのリスク評価を追記する       |
| 一部の設計コードサンプルに軽微な構文誤りがある                | コードサンプルを修正する                       |
| MINOR 指摘は全て未タスク仕様書に変換後 Phase 4 へ（省略不可） | 未タスク仕様書を作成してから進行する           |

### MAJOR（Phase 1 または Phase 2 へ差し戻し）

以下のいずれかに該当する場合:

| MAJOR 条件                                               | 差し戻し先 | 理由                               |
| -------------------------------------------------------- | ---------- | ---------------------------------- |
| 実装コードの振る舞いが設計の前提と異なっている           | Phase 2    | 実装の再分析に基づく設計のやり直し |
| プロダクションコードの変更が不可避と判明                 | Phase 1    | スコープの見直しが必要             |
| 既存テストが破壊される設計になっている                   | Phase 2    | テスト間分離設計のやり直し         |
| モック戦略が根本的に不適切（既存パターンでは対応不可能） | Phase 2    | モック戦略の根本見直し             |
| TODO 箇所数が17箇所以外（追加/削除）であることが判明     | Phase 1    | 要件の見直しが必要                 |

## 実行手順

### Step 1: Phase 2 成果物の読み込み

1. `phase-2-design.md` を読み込む
2. Phase 1 の `phase-1-requirements.md`（FR/NFR/AC）を読み込む
3. 対象3テストファイルの現状コードを読み込む

### Step 2: レビュー観点 1-6 の検証

1. 各観点のチェック項目を逐次確認する
2. 不合格項目がある場合は具体的な指摘内容を記録する
3. 指摘の重大度（MINOR / MAJOR）を判定する

### Step 3: 実装コードとの照合検証

1. `skill-executor.ts` の `execute()` メソッドの引数・戻り値を確認し、SE-TODO-1/2 の設計と照合する
2. `agent-client.ts` の `query()` メソッド内の `Anthropic().messages.create()` 呼び出しを確認し、AC-TODO-5/6/7 の設計と照合する
3. `agent-client.ts` のエラーハンドリング実装を確認し、AC-TODO-1/8/9 の設計と照合する
4. `agent-client.ts` の API キー取得ロジックを確認し、AC-TODO-2/3/4 の設計と照合する

### Step 4: 既存テストパターンとの一貫性確認

1. EDGE-AC-08（API key not configured テスト、L833）のパターンと AC-TODO-4 設計の一貫性を確認する
2. AC-04/05（タイムアウト・中断テスト）のモックパターンと SE-TODO-3 設計の一貫性を確認する
3. AC-14（エラー後ステータステスト）のパターンと AC-TODO-8/9 設計の一貫性を確認する

### Step 5: ゲート判定

1. 全レビュー観点の結果を集約する
2. PASS / MINOR / MAJOR のいずれかを判定する
3. 判定結果と理由を `outputs/phase-3/design-review-result.md` に記録する

### Step 6: MINOR/MAJOR の場合の対応指示

1. MINOR: 具体的な修正項目を列挙し、未タスク仕様書に変換後 Phase 4 へ進行可能とする
2. MAJOR: 差し戻し先の Phase と再実行スコープを明記する
