## 目的

Phase 2 で作成した設計書を多角的にレビューし、Phase 4（テスト作成）および Phase 5（実装）への進行可否を判定する。
設計の整合性・リスク・4条件（価値性・実現性・整合性・運用性）を評価し、MAJOR 課題がある場合は差し戻す。

## 背景

本タスクは `SkillCreatorService` への LLM 呼び出し統合であり、既存の create ワークフロー・テスト・型定義に影響する。
設計レビューを通じて、実装開始前に手戻りのリスクを最小化する。

## 実行タスク

### タスク1: 設計の整合性チェックリスト

**目的**: Phase 2 設計書の各観点が技術的に整合しているかを評価する。

**実行手順**:

1. Phase 2 設計書（`phase-2-design.md`）を精読する
2. 以下のチェックリストを全項目評価する
3. 各項目を PASS / FAIL / CONCERN で評価し、FAIL/CONCERN の場合は理由を記録する

**整合性チェックリスト**:

| No  | チェック項目                                                                         | 評価   | 備考 |
| --- | ------------------------------------------------------------------------------------ | ------ | ---- |
| 1   | `LlmClient` インターフェースが TypeScript で正しく定義可能か                         | 未評価 |      |
| 2   | コンストラクタへの `llmClient` オプショナル追加が後方互換か                          | 未評価 |      |
| 3   | `loadAgent("extract-purpose")` の戻り値（string）を `system` に渡す設計が妥当か      | 未評価 |      |
| 4   | `skillInput` の構築フォーマットが extract-purpose エージェントの入力仕様に合致するか | 未評価 |      |
| 5   | LLM 生成結果を `string` 直接受け取り（JSON パースなし）する設計が妥当か              | 未評価 |      |
| 6   | `trim()` による前後空白除去が `structurePlan.purpose` の要件を満たすか               | 未評価 |      |
| 7   | `isAbortError` による AbortError の rethrow が既存パターンと整合するか               | 未評価 |      |
| 8   | `llmClient` 未設定時の `options.description` フォールバックが AC-3 と矛盾しないか    | 未評価 |      |
| 9   | `extractPurposeWithLlm` メソッドの切り出しが SRP（単一責務原則）を満たすか           | 未評価 |      |
| 10  | Phase 2 で設計された 3 つの統合ポイントがテスト可能な粒度に分解されているか          | 未評価 |      |

**評価基準**:

- **PASS**: 問題なし
- **CONCERN**: 軽微な懸念（実装で対処可能、Phase 4 以降で確認）
- **FAIL**: 設計の根本的問題（差し戻し必要）

**期待される成果物**:

- 整合性チェックリスト評価結果（各項目の PASS / FAIL / CONCERN）

### タスク2: リスク評価

**目的**: LLM 呼び出し失敗・purpose 生成品質・既存機能への影響リスクを定量的に評価する。

**実行手順**:

1. 各リスク項目について「影響度（High/Medium/Low）× 発生確率（High/Medium/Low）」でリスクレベルを評価する
2. 各リスクに対する軽減策が Phase 5 実装設計に含まれているか確認する
3. 受容不可能なリスク（High × High）がある場合は差し戻し条件とする

**リスク評価表**:

| リスクID | リスク内容                                                        | 影響度 | 発生確率 | リスクレベル | 軽減策                                                       |
| -------- | ----------------------------------------------------------------- | ------ | -------- | ------------ | ------------------------------------------------------------ |
| R-01     | LLM 呼び出し失敗により `createSkill` 全体が失敗する               | High   | Medium   | High         | `runCreateWorkflow` の `catch` で `null` 返却し継続          |
| R-02     | LLM が不適切な purpose 文字列を返す（品質問題）                   | Medium | Medium   | Medium       | Phase 6 境界テストで空文字・長文の挙動を確認                 |
| R-03     | `llmClient` 追加による既存テストの破壊                            | High   | Low      | Medium       | コンストラクタオプショナル化で後方互換を確保                 |
| R-04     | `loadAgent` 失敗（ファイル不在）で purpose 抽出不能               | Medium | Low      | Low          | `catch` ブロックで `null` 返却・`description` フォールバック |
| R-05     | `extract-purpose` エージェントの system prompt 変更による挙動変化 | Medium | Low      | Low          | エージェント定義ファイルへの変更はレビュー対象とする         |
| R-06     | AbortSignal 未伝播による中断処理の不整合                          | Medium | Low      | Low          | `extractPurposeWithLlm` に `signal` を伝播する設計で対処     |

**期待される成果物**:

- リスク評価表（影響度・確率・軽減策記入済み）

### タスク3: 4条件の評価

**目的**: 設計が「価値性・実現性・整合性・運用性」の 4 条件を満たすかを評価する。

**実行手順**:

1. 各条件について評価基準と現状を照合する
2. 4条件全てが PASS であれば Phase 4 への進行を承認する
3. FAIL 条件がある場合は差し戻し理由として記録する

**4条件評価**:

#### 価値性（Value）

| 評価項目                                                    | 評価   | 根拠                                                             |
| ----------------------------------------------------------- | ------ | ---------------------------------------------------------------- |
| LLM による purpose 抽出がユーザー体験を改善するか           | 未評価 | エージェント定義文字列でなく実際の目的文が SKILL.md に反映される |
| AC-1〜AC-7 の受入条件が充足されることでビジネス価値があるか | 未評価 | スキル作成の自動化精度が向上する                                 |

#### 実現性（Feasibility）

| 評価項目                                                                  | 評価   | 根拠                                                                      |
| ------------------------------------------------------------------------- | ------ | ------------------------------------------------------------------------- |
| 既存の TypeScript コードベースで `LlmClient` インターフェースが実装可能か | 未評価 | 標準的な TypeScript パターンで実装可能                                    |
| `vi.mock` による `LlmClient` モックが技術的に実現可能か                   | 未評価 | コンストラクタ注入で差し替え可能                                          |
| Phase 5 の実装が 1 ファイルの変更で完結するか                             | 未評価 | `SkillCreatorService.ts` のみ変更（`LlmClient` 型は同ファイルに定義可能） |

#### 整合性（Consistency）

| 評価項目                                                                          | 評価   | 根拠                                                 |
| --------------------------------------------------------------------------------- | ------ | ---------------------------------------------------- |
| 既存の `runCreateWorkflow` フォールバックパターン（`catch` → `null`）と整合するか | 未評価 | 同一パターンを踏襲                                   |
| `AbortSignal` 伝播が既存の `throwIfAborted` パターンと整合するか                  | 未評価 | `extractPurposeWithLlm` へ `signal` を渡す設計で整合 |
| 命名規則（camelCase・TypeScript 慣習）が統一されているか                          | 未評価 | Phase 1 命名決定表に準拠                             |

#### 運用性（Operability）

| 評価項目                                       | 評価   | 根拠                                               |
| ---------------------------------------------- | ------ | -------------------------------------------------- |
| LLM 呼び出し失敗時にユーザー体験が劣化しないか | 未評価 | `null` フォールバックで `description` を使用し継続 |
| テスト実行時に実際の LLM 接続が不要か          | 未評価 | `vi.mock` でモック化可能                           |
| 将来の LLM プロバイダー変更に対応可能か        | 未評価 | `LlmClient` インターフェースで抽象化済み           |

**期待される成果物**:

- 4条件評価結果（全項目の PASS / FAIL / 根拠）

### タスク4: Phase 4 への進行判定基準

**目的**: レビュー結果に基づき、Phase 4 への進行を PASS / FAIL で判定する。

**実行手順**:

1. タスク1〜3の評価結果を集約する
2. 進行判定基準に照合し、判定を下す
3. FAIL の場合は差し戻し先 Phase と理由を明記する

**進行判定基準**:

| 判定条件                                         | 判定   |
| ------------------------------------------------ | ------ |
| 整合性チェックリストに FAIL 項目がない           | 未評価 |
| R-01〜R-06 の全リスクに軽減策が定義されている    | 未評価 |
| 4条件（価値性・実現性・整合性・運用性）が全 PASS | 未評価 |
| MAJOR 課題がない（CONCERN は許容）               | 未評価 |

**判定結果**:

| 判定     | 内容                                |
| -------- | ----------------------------------- |
| **PASS** | Phase 4（テスト作成）へ進行         |
| **FAIL** | 差し戻し先 Phase を明記して差し戻し |

**差し戻し条件（FAIL 時）**:

| MAJOR 課題の種類                             | 差し戻し先 |
| -------------------------------------------- | ---------- |
| `LlmClient` インターフェース設計の根本的問題 | Phase 2    |
| フォールバック動作が AC-3 と矛盾する         | Phase 2    |
| 後方互換が確保できない設計上の問題           | Phase 2    |
| AC-1〜AC-7 の受入条件が充足できない要件問題  | Phase 1    |

**期待される成果物**:

- Phase 4 進行判定結果（PASS / FAIL）
- FAIL の場合の差し戻し先と理由

### タスク5: 統合テスト観点のレビューゲート実施

**目的**: Phase 2 で定義した統合ポイントがテスト可能な設計になっているかを検証する。

**実行手順**:

1. Phase 2 の統合ポイント定義表を確認する
2. 各統合ポイントがユニットテストレベルで検証可能かを評価する
3. 統合テストシナリオの正常系・異常系がカバーされる設計になっているかを確認する
4. Phase 4 テスト作成の前提として不足している統合設計がないか確認する

**統合テスト観点チェックリスト**:

| No  | 統合観点                                                                        | 評価   | 備考 |
| --- | ------------------------------------------------------------------------------- | ------ | ---- |
| 1   | `loadAgent` → `generate` の呼び出し連鎖がモックでテスト可能か                   | 未評価 |      |
| 2   | `generate` の引数（`system`, `user`）が正しく渡されることを検証できるか         | 未評価 |      |
| 3   | `structurePlan.purpose` に LLM 結果が格納されることを検証できるか               | 未評価 |      |
| 4   | `llmClient.generate` が throw した場合に `runCreateWorkflow` が `null` を返すか | 未評価 |      |
| 5   | AbortError が rethrow されることをテストで検証できるか                          | 未評価 |      |

**期待される成果物**:

- 統合テスト観点チェックリスト評価結果
