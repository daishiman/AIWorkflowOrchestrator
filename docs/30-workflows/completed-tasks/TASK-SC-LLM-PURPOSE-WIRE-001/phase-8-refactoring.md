## 目的

Phase 5 で実装した purpose 抽出ロジックと `SkillCreatorService.ts` 全体を対象に、
可読性・保守性・パターン整合性の観点でリファクタリングを行う。
実装の動作を変えることなく、コードの品質を向上させることが目的である。

## 背景

TDD サイクル（Phase 4〜6）では「動く実装」を優先するため、コードの最適化は意図的に後回しにされる。
Phase 8 はこの技術的負債を解消し、後続の品質保証フェーズ（Phase 9）へ
クリーンな状態で移行するためのフェーズである。
特に `SkillCreatorService` 内に複数の LLM 呼び出しが存在する場合、
それらのパターンを統一することで将来の変更コストを下げる。

## 実行タスク

### タスク1: リファクタリング対象の洗い出し

**目的**: 変更すべき箇所を客観的な基準で特定する。

**洗い出し基準**:

| 基準           | 説明                                                            |
| -------------- | --------------------------------------------------------------- |
| 重複           | 同一または類似のコードブロックが複数箇所に存在する              |
| 複雑性         | 単一関数・メソッドの責務が複数になっている（循環複雑度が高い）  |
| 命名ドリフト   | 変数名・関数名が既存コードの命名規則と乖離している              |
| パターン不統一 | 他の LLM 呼び出し箇所と引数構造・エラーハンドリング構造が異なる |
| 過度なネスト   | `if/try/catch` が3階層以上ネストしている                        |

**実行手順**:

1. `SkillCreatorService.ts` を通読し、上記5基準に該当する箇所を特定する。
2. purpose 抽出ロジック（`loadAgent` → `llmClient.generate` → `structurePlan.purpose`）を重点的に確認する。
3. 洗い出した対象を変更内容テーブルに記録する。

**期待される成果物**:

- リファクタリング対象リスト

---

### タスク2: 変更内容の計画と実施

**目的**: 洗い出した対象を安全に変更する。

**変更内容テーブル（テンプレート）**:

| 対象                             | Before                            | After                                                 | 理由                   |
| -------------------------------- | --------------------------------- | ----------------------------------------------------- | ---------------------- |
| purpose 抽出ブロックの変数名     | 単一文字変数・略称変数の使用      | `purposeAgentDef`, `purposeResult` 等の意味のある命名 | 命名規則への統一       |
| LLM 呼び出しのエラーハンドリング | 個別の try/catch が散在           | 共通エラーハンドリングパターンに統一                  | パターン統一・重複削除 |
| `structurePlan.purpose` への代入 | インライン代入                    | 処理ステップごとに明示的に分離                        | 可読性向上             |
| コメント                         | 実装時の一時コメント・TODO が残存 | 不要コメントを削除し必要なものを整理                  | コードの明確化         |

**実行手順**:

1. 変更内容テーブルを作成し、各変更の Before/After と理由を記録する。
2. 変更内容を1件ずつ適用する（一括変更は避ける）。
3. 各変更後に `pnpm --filter @repo/desktop test` を実行し、テストが全件 PASS していることを確認する。

**期待される成果物**:

- 変更内容テーブル（実施済みバージョン）
- 各変更適用後のテスト PASS 確認記録

---

### タスク3: purpose 抽出ロジックの可読性向上

**目的**: purpose 抽出フローを一読して理解できる状態にする。

**可読性向上の観点**:

- ステップ1（エージェント定義の取得）・ステップ2（LLM 呼び出し）・ステップ3（結果格納）が
  コード上でも明確に3段階に分かれていること。
- 各ステップの意図がコードを読むだけで伝わること（コメントに依存しない）。
- エラー発生時にどのステップで失敗したかがログ・例外メッセージから判断できること。

**実行手順**:

1. purpose 抽出ブロックを抜き出し、可読性の問題点を列挙する。
2. 可読性改善の根拠がある箇所に限定して、ヘルパーメソッド抽出・ステップ分割・変数名変更を行う。
3. 変更後のコードを読み、「3ステップが明確か」「エラー特定が容易か」を確認する。

**期待される成果物**:

- リファクタリング後の purpose 抽出ブロックのコードスニペット（outputs/phase-8/ に記録）

---

### タスク4: SkillCreatorService 内の LLM 呼び出しパターンの統一化

**目的**: `llmClient.generate` を使用する全箇所が同一パターンで実装されていることを確認・修正する。

**統一化の確認観点**:

| 観点               | 確認内容                                                              |
| ------------------ | --------------------------------------------------------------------- |
| 引数構造           | `{ system: string, user: string }` の形式が全箇所で一致しているか     |
| エラーハンドリング | 全 LLM 呼び出し箇所で同じエラー処理パターンが使われているか           |
| 戻り値の処理       | `generate` の戻り値をトリム・バリデーションする処理が統一されているか |
| ログ出力           | 呼び出し前後のログレベル・メッセージ形式が統一されているか            |

**実行手順**:

1. `SkillCreatorService.ts` 内の全 `llmClient.generate` 呼び出し箇所を列挙する。
2. 上記4観点でパターンが不統一な箇所を特定する。
3. purpose 抽出の呼び出しを基準として、他の呼び出し箇所を統一する（または purpose 側を既存パターンに合わせる）。
4. 変更後にテストを実行して全件 PASS を確認する。

**期待される成果物**:

- LLM 呼び出しパターン統一化の変更内容記録

---

### タスク5: リファクタリング後の動作確認

**目的**: リファクタリングによって機能が変化していないことを既存テストで確認する。

**実行手順**:

1. 以下のコマンドで全テストを実行する:
   ```bash
   pnpm --filter @repo/desktop test
   ```
2. 全テストが PASS していることを確認する。
3. 型チェックを実行して新たな型エラーが発生していないことを確認する:
   ```bash
   pnpm --filter @repo/desktop typecheck
   ```
4. FAIL があった場合は、リファクタリングによる意図しない動作変更がないか確認し、修正する。

**期待される成果物**:

- リファクタリング後のテスト全件 PASS 確認記録
