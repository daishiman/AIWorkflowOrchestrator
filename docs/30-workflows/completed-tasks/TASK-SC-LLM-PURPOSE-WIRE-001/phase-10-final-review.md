## 目的

受入条件 AC-1〜AC-7 の最終評価と、依存タスクの完了確認、
4条件（価値性・実現性・整合性・運用性）の観点から実装全体を総合レビューする。
MAJOR 課題がある場合は適切なフェーズへ差し戻し、全条件をクリアした場合のみ Phase 11 へ進む。

受入条件への対応状況と実装品質を最終確認することで、
後続フェーズでの手戻りを防ぐ。

## 実行タスク

### タスク1: 受入条件 AC-1〜AC-7 の最終評価

**目的**: タスク仕様書に定義された全受入条件が実装によって満たされていることを確認する。

**最終評価チェックリスト**:

| ID   | 受入条件                                                                                       | 確認方法                                          | 判定            |
| ---- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------- | --------------- |
| AC-1 | `loadAgent("extract-purpose")` の結果が LLM の system prompt として渡される                    | `SkillCreatorService.ts` の実装コードを目視確認   | □ PASS / □ FAIL |
| AC-2 | `llmClient.generate({ system: purposeAgentDef, user: skillInput })` 相当の呼び出しが実装される | `SkillCreatorService.ts` の実装コードを目視確認   | □ PASS / □ FAIL |
| AC-3 | `structurePlan.purpose` に LLM の生成結果が格納される（エージェント定義文字列でなく推論結果）  | purpose 抽出テストの PASS 確認                    | □ PASS / □ FAIL |
| AC-4 | `SkillCreatorService` の既存 LLM 呼び出しパターンと整合する実装形式を採用する                  | Phase 8 のパターン統一化記録を確認                | □ PASS / □ FAIL |
| AC-5 | `extract-purpose` エージェント定義ファイルの期待する出力フォーマットが明確化・文書化される     | Phase 12 ドキュメントまたは agents ファイルを確認 | □ PASS / □ FAIL |

**実行手順**:

1. 上記チェックリストを上から順に評価する。
2. FAIL が1件以上ある場合は MAJOR 課題として記録し、差し戻し先を決定する。
3. 全件 PASS の場合のみ次のタスクへ進む。

### タスク3: 4条件の最終評価

**目的**: 実装が中長期的な価値と実現可能性の観点で妥当であることを評価する。

**4条件評価テーブル**:

#### 価値性の評価

| 評価観点             | 内容                                                                                                                                         |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 何のコストが下がるか | `structurePlan.purpose` に LLM 推論結果が入ることで、下流処理（スキル生成・ドキュメント生成）で purpose 文字列を手動修正するコストがなくなる |
| 品質向上             | エージェント定義に沿って生成された purpose により、スキルの意図が自動的に正確に記述される                                                    |
| 判定基準             | 上記コスト削減効果が実装コストに見合うか                                                                                                     |

**判定**: □ 価値あり / □ 要再検討

---

#### 実現性の評価

| 評価観点     | 内容                                                                                                     |
| ------------ | -------------------------------------------------------------------------------------------------------- |
| 実装量       | Phase 5 での実装が中規模スコープ（`SkillCreatorService.ts` への数行〜数十行の追加）に収まっているか      |
| 依存増加     | 新たなライブラリや外部サービスへの依存が追加されていないか（既存の `llmClient` を使用している場合は OK） |
| テスト容易性 | LLM モックで全テストケースが実行可能か（実際の LLM API を呼び出さないか）                                |

**判定**: □ 実現性あり / □ 要再検討

---

#### 整合性の評価

| 評価観点     | 内容                                                                                          |
| ------------ | --------------------------------------------------------------------------------------------- |
| 責務境界     | `SkillCreatorService` が purpose 抽出の責務を持つことが、サービスの責務定義と矛盾していないか |
| 状態所有権   | `structurePlan.purpose` の所有権が `SkillCreatorService` にあることが設計上明確か             |
| 既存パターン | 追加した LLM 呼び出しが既存の `llmClient.generate` 呼び出しパターンと整合しているか           |

**判定**: □ 整合性あり / □ 要再検討

---

#### 運用性の評価

| 評価観点                     | 内容                                                                                            |
| ---------------------------- | ----------------------------------------------------------------------------------------------- |
| エージェント定義変更への追随 | `extract-purpose` エージェント定義ファイルを変更した場合、実装コードの変更なしに動作が変わるか  |
| エラー対応                   | LLM が purpose 生成に失敗した場合のフォールバック動作が運用者に理解しやすい形で実装されているか |
| 監視可能性                   | purpose 抽出の成功・失敗がログで確認できるか                                                    |

**判定**: □ 運用性あり / □ 要再検討

### タスク4: MAJOR 課題がある場合の差し戻し

**差し戻し判断テーブル**:

| 課題の種類                               | 差し戻し先   | 理由                                       |
| ---------------------------------------- | ------------ | ------------------------------------------ |
| AC-1〜AC-3 が FAIL（LLM 接続の核心部分） | Phase 5      | 実装の根本的な修正が必要                   |
| AC-4 が FAIL（パターン不整合）           | Phase 8      | リファクタリングで対応可能                 |
| AC-5 が FAIL（ドキュメント未整備）       | Phase 12     | ドキュメント更新で対応可能                 |
| AC-6 が FAIL（既存テスト FAIL）          | Phase 4 or 5 | テストまたは実装の修正が必要               |
| AC-7 が FAIL（ユニットテスト未作成）     | Phase 4      | テスト作成フェーズへ差し戻し               |
| 価値性・実現性・整合性・運用性 CRITICAL  | Phase 1 or 2 | 要件定義または設計の根本的な見直しが必要   |
| 依存タスク未完了                         | 待機         | 依存タスクの完了後に Phase 10 を再実行する |
