## 目的

実装（Phase 5）からリファクタリング（Phase 8）・品質保証（Phase 9）までの全成果物を対象に、多角的な最終レビューを実施する。要件充足・設計整合・コード品質・テスト品質・ドキュメント品質・セキュリティ・既知Pitfall対策の7つの観点から総合的に検証し、Phase 11（手動テスト）への進行可否を判定する。

## 実行タスク

- レビュー観点検証: 観点1〜7を順に評価し、証跡をチェックテーブルへ記録する
- 品質ゲート再実行: Lint/TypeCheck/新規テスト/既存回帰/カバレッジの統合確認を再実行する
- 判定と未タスク化: PASS/MINOR/MAJOR/CRITICALを確定し、MINOR以上は未タスク登録方針を明記する

## 判定基準

| 判定     | 条件                                                       | 対応                                                   |
| -------- | ---------------------------------------------------------- | ------------------------------------------------------ |
| PASS     | 全レビュー観点で問題なし                                   | Phase 11 へ進む                                        |
| MINOR    | 軽微な指摘あり（機能影響なし、コードスタイル等）           | 全指摘を未タスク仕様書に変換後 Phase 11 へ（省略不可） |
| MAJOR    | 重大な問題あり（機能不足、設計の根本的問題）               | 影響範囲に応じて Phase 1-5 へ戻る                      |
| CRITICAL | 致命的な問題あり（セキュリティ脆弱性、データ破壊の可能性） | Phase 1 へ戻り要件再確認                               |

### MINOR判定時の必須対応

MINOR指摘は「機能影響なし」であっても**全て**未タスク仕様書に変換する。省略は不可。

1. `docs/30-workflows/unassigned-task/` に指示書を作成
2. `task-workflow.md` 残課題テーブルに登録
3. 関連仕様書に参照リンクを追加

## レビュー観点

### 観点1: 要件充足

Phase 1 で定義した全要件（FR-001〜FR-007、NFR-001〜NFR-007）が実装によってカバーされているかを検証する。

| チェック項目                                                              | 検証方法                                                   |
| ------------------------------------------------------------------------- | ---------------------------------------------------------- |
| FR-001: ハンドラ境界検出が正しく動作するか                                | テストケースTC-001の結果確認                               |
| FR-002: v8カバレッジJSON解析が正しく動作するか                            | テストケースTC-002の結果確認                               |
| FR-003: ハンドラ単位カバレッジ算出が正しく動作するか                      | テストケースTC-003の結果確認                               |
| FR-004: JSON・Markdown形式でレポート出力されるか                          | テストケースTC-004の結果確認                               |
| FR-005: 修正対象ハンドラの指定オプションが機能するか                      | テストケースTC-005の結果確認                               |
| FR-006: Phase 7判定結果（PASS/FAIL）が正しく出力されるか                  | テストケースTC-006の結果確認                               |
| FR-007: `skillHandlers.ts` 以外のファイルにも適用可能なインターフェースか | コードレビューで `CoverageByHandlerOptions` の汎用性を確認 |
| NFR-001: 実行速度が5秒以内か                                              | テストケースTC-007の結果確認（パフォーマンステスト）       |
| NFR-002: 不正入力に対するエラーハンドリングが適切か                       | テストケースTC-008の結果確認                               |
| NFR-003: 集計スクリプト自体のカバレッジ基準達成                           | Phase 9品質レポートの数値確認                              |
| NFR-004: P41対策（v8インライン関数カウント問題）が実装されているか        | コードレビューでカバレッジ算出ロジック内のP41対策を確認    |
| NFR-005: P40対策（モノレポパス解決）が実装されているか                    | コードレビューでパス解決ロジックの相対パスベース処理を確認 |
| NFR-006: TypeScript strictモードでコンパイル通過                          | Phase 9品質レポートのTypeCheck結果確認                     |
| NFR-007: ts-morph以外の追加依存が最小限か                                 | `package.json` の dependencies 確認                        |

### 観点2: 設計整合

Phase 2 の設計からの逸脱がないかを検証する。逸脱がある場合は、Phase 5 の実装ログに逸脱理由が記録されていることを確認する。

| チェック項目                                                         | 検証方法                                                                                                      |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 5モジュール構成が維持されているか                                    | コードレビューで HandlerDetector, CoverageParser, CoverageCalculator, Phase7Judge, ReportFormatter の存在確認 |
| データフローが一方向（入力→検出→解析→算出→判定→出力）か              | コードレビューで関数呼び出しの方向を確認                                                                      |
| CLI インターフェースが `CoverageByHandlerOptions` 型に準拠しているか | 型定義とコマンドライン引数パーサーの整合性確認                                                                |
| 設計逸脱がある場合、逸脱理由が文書化されているか                     | `outputs/phase-5/implementation-log.md` に逸脱記録があることを確認                                            |

### 観点3: コード品質

| チェック項目                                                       | 検証方法                                                                                 |
| ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| SOLID原則（特に単一責務・依存性逆転）に準拠しているか              | コードレビューで各関数の責務を確認                                                       |
| `any` 型が使用されていないか                                       | `grep -rn "any" apps/desktop/scripts/coverage-by-handler.ts` の結果が空であること        |
| `@ts-ignore` / `@ts-expect-error` が使用されていないか             | `grep -rn "ts-ignore\|ts-expect-error" apps/desktop/scripts/coverage-by-handler.ts` が空 |
| 型アサーション（`as`）がバリデーション目的以外で使用されていないか | コードレビューで `as` の使用箇所と理由を確認                                             |
| エラーハンドリングが一貫しているか                                 | 全エラーパスで明確なメッセージが返されることを確認                                       |
| boolean変数名が `is`/`has`/`can`/`should` プレフィックスか         | コードレビューで命名規約を確認                                                           |
| 未使用importがないか                                               | `pnpm lint` の結果で確認                                                                 |

### 観点4: テスト品質

| チェック項目                                                       | 検証方法                                                              |
| ------------------------------------------------------------------ | --------------------------------------------------------------------- |
| TC-001〜TC-008の全テストケースが実装されているか                   | テストファイル内の `describe` / `it` ブロックとテストケース一覧の突合 |
| テスト間で状態を共有していないか（P9対策）                         | `beforeEach` で必ずリセット処理が実行されることを確認                 |
| エッジケース（0ハンドラ、1ハンドラ、不正入力）がカバーされているか | テストファイル内のエッジケーステストの存在確認                        |
| テストデータが再利用可能な構造で定義されているか                   | テストヘルパー・ファクトリの使用状況確認                              |
| テストが決定論的に動作するか（実行順序に依存しないか）             | テストを複数回実行して全て同じ結果になることを確認                    |

### 観点5: ドキュメント品質

| チェック項目                                                  | 検証方法                                                          |
| ------------------------------------------------------------- | ----------------------------------------------------------------- |
| Phase 7判定ルール（Rule-1〜Rule-4）が明確に文書化されているか | 判定ルール文書が曖昧語チェックリストに抵触しないことを確認        |
| Phase 7テンプレートにレポートセクションが追加されているか     | テンプレートファイルの更新確認                                    |
| 各Phaseの成果物が全て作成されているか                         | `outputs/` ディレクトリの成果物一覧と仕様書の成果物テーブルの突合 |
| テストケース一覧と実装テストの対応が取れているか              | Phase 4のテストケース定義とテストコードの突合                     |

### 観点6: セキュリティ

| チェック項目                                                   | 検証方法                                                                   |
| -------------------------------------------------------------- | -------------------------------------------------------------------------- |
| ファイルパス入力にパストラバーサル対策があるか                 | `../` や絶対パス指定に対するバリデーションの存在確認                       |
| ユーザー入力（コマンドライン引数）のサニタイズが行われているか | コマンドライン引数パーサーでの入力検証確認                                 |
| エラーメッセージに内部パス情報が過剰に漏洩していないか         | エラーハンドリングでスタックトレースやフルパスが外部出力されないことを確認 |
| 依存パッケージに既知の脆弱性がないか                           | `pnpm audit` の結果確認（ts-morph の依存ツリー）                           |

### 観点7: 既知Pitfall対策

| チェック項目                                           | 関連Pitfall | 検証方法                                                                               |
| ------------------------------------------------------ | ----------- | -------------------------------------------------------------------------------------- |
| v8インライン関数カウント問題への対策が実装されているか | P41         | カバレッジ算出ロジックでインライン arrow function を独立関数としてカウントする処理確認 |
| モノレポ環境でのパス解決がディレクトリ依存しないか     | P40         | テスト実行コマンドが `cd apps/desktop` で実行されていることを確認                      |
| テスト間の状態リークが防止されているか                 | P9          | `beforeEach` / `afterEach` でのリセット処理確認                                        |
| テスト環境でのログ出力汚染がないか                     | P20         | テスト実行時にconsole出力が汚染されていないことを確認                                  |

## 統合テスト連携

### レビュー前の統合確認

レビュー開始前に以下のコマンドを実行し、全てPASSであることを前提条件とする。

```bash
# 1. Lint
cd apps/desktop && pnpm lint

# 2. TypeCheck
pnpm typecheck

# 3. 新規テスト
cd apps/desktop && pnpm vitest run scripts/coverage-by-handler.test.ts

# 4. 既存テスト回帰確認
cd apps/desktop && pnpm vitest run src/main/ipc/__tests__/skillHandlers.test.ts

# 5. カバレッジ確認
cd apps/desktop && pnpm vitest run scripts/coverage-by-handler.test.ts --coverage --coverage.include='scripts/coverage-by-handler.ts'
```
