## 目的

Phase 4（テスト作成）に進む前に、Phase 1（要件定義）と Phase 2（設計）の妥当性を多角的に検証する。検証の結果に基づき、PASS / MINOR / MAJOR の判定を行い、次のアクションを決定する。

## 実行タスク

- 観点レビュー実施: 観点1〜4（要件網羅性/設計妥当性/既知Pitfall対策/実装可能性）を順に検証する
- エッジケース判定検証: Phase 7判定ルールの7シナリオに対する判定結果を確認する
- 判定確定と引き継ぎ作成: PASS/MINOR/MAJORを確定し、Phase 4への進行条件を明文化する

## 判定基準

| 判定              | 条件                                                   | 対応                  |
| ----------------- | ------------------------------------------------------ | --------------------- |
| PASS              | 全レビュー観点で問題なし                               | Phase 4 へ進む        |
| MINOR             | 軽微な指摘あり（機能影響なし）                         | 指摘対応後 Phase 4 へ |
| MAJOR（要件問題） | 要件の抜け漏れ、受け入れ基準の曖昧さ                   | Phase 1 へ戻る        |
| MAJOR（設計問題） | アーキテクチャの根本的な問題、インターフェースの不整合 | Phase 2 へ戻る        |

## レビュー観点

### 観点1: 要件網羅性

| チェック項目                                                  | 判定基準                                                                                   |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| FR-001〜FR-007 が全てのユースケースをカバーしているか         | skillHandlers.ts の3登録関数・23ハンドラに対する集計が全て実行可能であること               |
| NFR-001〜NFR-007 がプロジェクトの品質基準と整合しているか     | `quality-requirements.md` のカバレッジ閾値（Lines 80%, Functions 80%, Branches 60%）と一致 |
| Phase 7 判定ルール（Rule-1〜4）がエッジケースを網羅しているか | 以下のシナリオを全て正しく判定できること                                                   |
| 受け入れ基準が全て検証可能（テスト実行で確認可能）であるか    | 各基準に対応するテストケースが設計可能であること                                           |

#### Phase 7 判定ルールのエッジケース検証

| シナリオ                                                   | 期待される判定  | 適用ルール |
| ---------------------------------------------------------- | --------------- | ---------- |
| 修正対象ハンドラ 100%、ファイル全体 45%                    | PASS            | Rule-1, 2  |
| 修正対象ハンドラ 100%、ファイル全体 Branch 50%（基準未達） | FAIL            | Rule-4     |
| 修正対象ハンドラ Line 75%（基準未達）                      | FAIL            | Rule-1     |
| 修正対象ハンドラ指定なし                                   | N/A（判定なし） | -          |
| ファイルにハンドラが1個のみ                                | 従来基準適用    | -          |
| 全ハンドラが基準を満たす                                   | PASS            | Rule-1     |
| 修正対象ハンドラ 100%、他に未カバーハンドラあり            | PASS + 未タスク | Rule-2, 3  |

### 観点2: 設計妥当性

| チェック項目                                         | 判定基準                                                                                                                                     |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| モジュール構成が単一責務を満たしているか             | 5つのモジュール（HandlerDetector, CoverageParser, CoverageCalculator, Phase7Judge, ReportFormatter）がそれぞれ独立したテスト可能な責務を持つ |
| データフローに循環依存がないか                       | 入力→検出→解析→算出→判定→出力の一方向フローであること                                                                                        |
| 公開関数のシグネチャがテスタビリティを確保しているか | 各関数が純粋関数または明示的な副作用を持ち、モックなしでテスト可能であること                                                                 |
| CLI インターフェースが将来の拡張に対応可能か         | `CoverageByHandlerOptions` にオプショナルフィールドを追加するだけで拡張可能であること                                                        |
| 型定義が `strict: true` でコンパイル可能か           | `any` 型、`@ts-ignore`、型アサーション（`as`）が含まれていないこと                                                                           |
| エラーハンドリングが全ケースをカバーしているか       | Step 5 のエラーケース表が実運用で発生しうる全パターンを網羅していること                                                                      |

### 観点3: 既知の落とし穴への対策

| チェック項目                                                | 関連Pitfall | 判定基準                                                                         |
| ----------------------------------------------------------- | ----------- | -------------------------------------------------------------------------------- |
| v8 インライン関数カウント問題への対策が設計に含まれているか | P41         | Step 4（P41対策設計）が Function カバレッジ算出に反映されていること              |
| モノレポパス解決が設計に含まれているか                      | P40         | カバレッジ JSON のファイルパスとソースファイルパスの突合方法が明記されていること |
| テスト間の状態リークが設計で防止されているか                | P9          | 各テストケースが独立して実行可能な設計であること                                 |

### 観点4: 実装可能性

| チェック項目                                              | 判定基準                                                                                    |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| ts-morph で `ipcMain.handle()` の検出が技術的に可能か     | `CallExpression` ノードの走査で第1引数（チャンネル名）と第2引数（コールバック）が取得可能   |
| `IPC_CHANNELS.*` 定数参照の解決が可能か                   | ts-morph の `getDefinitions()` または `getType()` で定数値を解決可能                        |
| v8 カバレッジ JSON のフォーマットが安定しているか         | Vitest v2.x の v8 カバレッジ出力フォーマットが文書化されているか確認                        |
| `scripts/` ディレクトリ配置がモノレポ構成と整合しているか | `apps/desktop/scripts/` に配置することで `apps/desktop/vitest.config.ts` の管轄内になること |
| 実行速度要件（5秒以内）が達成可能か                       | ts-morph の AST 解析 + JSON 読み込みが1,075行ファイルに対して5秒以内であること              |

## 統合テスト連携

### レビュー時の統合確認事項

| 確認事項                   | 検証方法                                                                                                                          |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| IPC チャンネル名の解決精度 | `skillHandlers.ts` の `IPC_CHANNELS.SKILL_LIST` 等の定数参照が正しいチャンネル名文字列に解決されるか、ts-morph の実機テストで確認 |
| v8 JSON との突合精度       | 実際の `coverage-final.json` を使用して、行番号の突合がオフバイワンエラーなく動作するか確認                                       |
| Phase 7 判定の一貫性       | 同じ入力に対して常に同じ判定結果が出力されるか（決定論的動作）                                                                    |
