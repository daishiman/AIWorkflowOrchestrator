## 目的

Phase 2 で策定した L1/L2/L3 の 3 層バリデーター設計を以下の観点でレビューし、**Phase 4（テスト作成）に進んでよいかを判定する**。

- 設計の論理的整合性（責務境界・データフロー）
- 既知の苦戦箇所（4 件）に対する対策の十分性
- 後続タスクおよび先行タスクとの干渉リスク
- 実装コスト・リスクの見積もり妥当性

## 判定基準（PASS / FAIL）

### PASS 条件

以下を全て満たす場合、Phase 4（テスト作成）への進行を許可する。

- チェックリスト A〜E の全項目が PASS
- ブロッカー確認セクションで「ブロッカーなし」と確認済み
- 実装コスト見積もりが妥当と判断されている

### FAIL 条件（Phase 4 進行不可）

以下のいずれかに該当する場合、Phase 2 に差し戻す。

| FAIL パターン                          | 対処                                                         |
| -------------------------------------- | ------------------------------------------------------------ |
| A-1〜A-5 のいずれかが FAIL             | L1/L2/L3 のデータフローを Phase 2 で再設計                   |
| B-1 が FAIL（strict 移行不可な設計）   | 方言ハンドリングを Phase 2 で再設計                          |
| C-3 が FAIL（TC-004 が壊れる）         | 除外ポリシーを Phase 2 で修正し、TC-004 テストとの干渉を解消 |
| D-1 が FAIL（consumer に依存した設計） | allowlist ベース生成に変更し Phase 2 を更新                  |
| ブロッカーが存在する                   | ブロッカー解消後に Phase 3 を再実施                          |

## 30種の思考法監査

30 種の思考法は `outputs/phase-3/elegance-thinking-audit.md` に集約し、本 Phase では次の結論だけを保持する。

- 論理分析系: CLI 契約ドリフトと Phase 責務誤記を矛盾として検出する
- 構造分解系: 成果物契約、mirror 契約、close-out 契約を分離して漏れを確認する
- メタ・抽象系: validator 追加タスクと task spec close-out を混線させない
- 発想・拡張系: strict mode や CI 組込は follow-up へ退避し、初回価値へ集中する
- システム系: `.claude` / `.agents` / task spec / aiworkflow 正本の参照方向を一方向に寄せる
- 戦略・価値系: 最小複雑性で drift 検出を成立させる
- 問題解決系: 4 条件を PASS にする最短経路を優先する
