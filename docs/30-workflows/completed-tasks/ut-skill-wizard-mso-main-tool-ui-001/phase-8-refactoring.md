## 検討観点

### 1. バッジロジックの抽出（ヘルパー関数化の要否）

以下の基準でヘルパー関数化の要否を判断する。

**ヘルパー関数化を検討する場合**

- 「主ツールかどうか」を判定するロジックが `renderQuestion` 関数内で複数箇所に記述されている
- バッジ表示に関連する JSX が 10 行を超え、`renderQuestion` 全体の可読性を損なっている

**ヘルパー関数化を見送る場合（推奨）**

- バッジ表示ロジックが Q5 分岐内の 1 箇所のみに存在する
- `renderQuestion` 全体の行数が許容範囲内（目安: 80 行以内）である
- 関数を抽出しても再利用の見込みがない

本タスクは `renderQuestion` 内の Q5 キー分岐のみへの変更であるため、原則としてヘルパー関数化は見送り、インライン記述を維持する。

### 2. 削除容易性の確認（コメント・コード構造）

将来「主ツール」バッジ表示を削除・変更する際のコストを最小化するため、以下を確認する。

- バッジ表示に関するコードが Q5 分岐の1ブロックに集約されており、他の設問レンダリングと混在していないこと
- バッジ表示を削除する際に影響を受けるコードが最小限であること
- バッジに関連するコメントが存在する場合、内容が正確かつ過剰でないこと（削除時に残骸が残らない構造）

削除容易性の確認観点チェックリスト:

- [ ] バッジ表示コードが Q5 分岐内の連続したブロックに収まっている
- [ ] バッジ表示コードが他の設問の `renderQuestion` 分岐に影響を与えていない
- [ ] 不要なコメント（TODO・FIXME 等の未解決コメント）が残っていない

### 3. 命名の一貫性確認（camelCase 等）

以下の命名規則に沿っていることを確認する。

| 対象                   | 規則                   | 確認ポイント                                                              |
| ---------------------- | ---------------------- | ------------------------------------------------------------------------- |
| 変数名                 | camelCase              | `mainTool`、`isMainTool`、`selectedTools` 等が camelCase である           |
| コンポーネント内関数名 | camelCase              | `renderBadge` 等の補助関数を作成した場合は camelCase                      |
| Tailwind クラス        | ケバブケース           | Tailwind のユーティリティクラスがプロジェクトの既存スタイルと一貫している |
| aria 属性値            | 日本語または英語で統一 | 既存の `aria-label` の言語に合わせる                                      |

命名の一貫性チェックリスト:

- [ ] 新規追加した変数・定数が camelCase である
- [ ] 既存コードの命名スタイルと揃っている
- [ ] aria 属性値の言語が既存コードと統一されている

## 注意事項

**小規模タスクのため過剰な抽象化を避ける。**

以下は本タスクでは実施しない。

- バッジコンポーネントの独立ファイル化（`MainToolBadge.tsx` 等の新規ファイル作成）
- バッジ判定ロジックのカスタムフック化
- Q5 以外の設問への汎用バッジシステムの設計

これらの抽象化が必要になった場合は、別タスクとして起票・計画する。
