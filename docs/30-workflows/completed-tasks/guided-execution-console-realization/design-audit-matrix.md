# Guided Execution Console 設計監査マトリクス

## 思考リセット

この監査では、過去の `依存管理を厚くするほど良い` という前提をいったん外し、`指定順どおり進めれば最終成果物へ到達できるか` を主論点として再評価した。  
成果物の削除は行わず、見方だけをリセットして root 文書を再点検している。

## 監査結論

30 種の思考法を束ねると、最もエレガントな結論は `Terminal-first` ではなく `Guided Execution-first` である。  
さらに今回の再監査では、`dependency-first` ではなく `sequence-first` が一般ユーザー向けに最も素直であると結論づけた。

## 30思考法適用ログ

| 思考法               | 監査観点                         | 結論                                                                                              |
| -------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------- |
| 批判的思考           | 何を本当に分かりにくくしているか | 問題は task の存在ではなく、`依存` 語彙が前に出すぎていたこと                                     |
| 演繹思考             | 目的から必要条件を逆算する       | 目的が `順番どおり進めれば達成できること` なら、root 文書に canonical order が必要                |
| 帰納的思考           | 直近のユーザー指摘を一般化する   | 繰り返し問題になったのは dependency の厳密さではなく、`最初に何を読むか` の曖昧さだった           |
| アブダクション       | 最も説明力の高い仮説を取る       | 混乱の主因はファイル不足ではなく、順番説明の重心がずれていたこと                                  |
| 垂直思考             | 根本原因を掘る                   | `依存管理` を説明しようとして `実行ガイド` が弱くなっていた                                       |
| 要素分解             | pack を最小単位へ分ける          | 入口、主ルート、周辺task、監査根拠、phase gate の5要素で足りる                                    |
| MECE                 | 漏れと重複を確認する             | root 文書は `読む順番` `進める順番` `設計意図` `周辺参照` に分けると整理しやすい                  |
| 2軸思考              | 必読と条件付きを分ける           | `must-read / optional` と `internal / surrounding` の2軸が最も分かりやすい                        |
| プロセス思考         | 実行の流れを確認する             | `root Phase 1-3 → Task01 → Task02 → Task03 → 必要なら周辺task → governance` が最短主ルート        |
| メタ思考             | 監査の枠組み自体を疑う           | 依存関係監査の枠が強すぎると、ユーザー目的から外れやすい                                          |
| 抽象化思考           | 上位概念を定義する               | この pack は `dependency ledger` ではなく `execution playbook` である                             |
| ダブル・ループ思考   | 前提そのものを見直す             | `依存を厳密化するほど良い` を外し、`順番を明快にするほど良い` に置き換えた                        |
| ブレインストーミング | 改善案を広く出す                 | references 化、番号付け、要約カード化、1枚ガイド化の候補を比較した                                |
| 水平思考             | 別の見方を試す                   | task spec を設計書ではなく、実行者向け onboarding card と見なすと整理できた                       |
| 逆説思考             | 逆を考える                       | dependency をさらに増やすほど、一般ユーザーには読みにくくなる                                     |
| 類推思考             | 類似構造から学ぶ                 | Apple 的には dependency map より setup flow に近い見せ方が自然                                    |
| if思考               | 条件分岐を検証する               | 子task だけを AI に渡すなら、親 pack へ戻る導線が必須                                             |
| 素人思考             | 初心者の目線で見る               | 初心者は `何に依存するか` より `次に何をすればいいか` を知りたい                                  |
| システム思考         | 文書全体のつながりを見る         | `00-ai-read-order`、`index`、`execution-topology`、`system-alignment` は一連の surface として働く |
| 因果関係分析         | 表現と理解負荷の因果を追う       | dependency という語が増えるほど、実装着手の心理負荷が上がる                                       |
| 因果ループ           | ループを見つける                 | 分かりにくさが補助資料追加を呼び、補助資料追加がさらに分かりにくさを生む循環がある                |

| プラスサム思考       | 両立可能性を探る                 | 初心者には実行順、上級者には周辺task 参照を同じ pack で両立できる                                 |
| 価値提案思考         | 誰に何を届けるか                 | 価値は `迷わず進めること` であり、dependency の完全把握ではない                                   |

| 論点思考             | 真の論点を定義する               | 論点は `依存関係の精密さ` ではなく `指定順で目的達成できるか` である                              |
| KJ法                 | 発見を束ねる                     | 指摘は `入口` `主ルート` `周辺task` `監査根拠` `phase gate` の5群にまとまる                       |

## 4条件判定

| 条件         | 判定 | 根拠                                                                                              |
| ------------ | ---- | ------------------------------------------------------------------------------------------------- |
| 矛盾なし     | PASS | root 文書群が `依存管理` より `推奨実行順` を主語にする方針へ揃った                               |
| 漏れなし     | PASS | 入口、主ルート、周辺task、監査根拠、phase gate の5要素が root 文書で説明できる                    |
| 整合性あり   | PASS | `実行コンソール` / `推奨実行順` / `実行前の前提` / `周辺task` の語彙へ寄せた                      |
| 依存関係整合 | PASS | この pack で必要な前後順は `root Phase 1-3 → Task01 → Task02 → Task03` として十分に定義されている |

## 採用しない案

| 案                                             | 不採用理由                                                           |
| ---------------------------------------------- | -------------------------------------------------------------------- |
| raw terminal を初期画面にする                  | 一般ユーザーの理解コストが高い                                       |
| terminal / API を別ブランドで分断する          | 学習コストが増え、結果画面が分裂する                                 |
| transcript を自動で chat 化する                | manual boundary と provenance を壊す                                 |
| open-terminal CTA を各 surface 独自実装にする  | drift と no-op を再発させる                                          |
| 周辺task をすべて strict dependency として扱う | 実装順が重く見えすぎ、ユーザーが求める `順番どおり進める` 感覚を壊す |
