## 目的

Phase 2 で作成した設計を多角的にレビューし、実装フェーズ（Phase 4以降）への進行可否を判定する。
`weekly` ガードとの対称性が保たれているかを重点的に確認する。

## 多角的思考の適用方針

- 論理分析系: ガード条件の漏れ・矛盾がないかを確認する
- 構造分解系: 要件、設計、テストの責務を分けて確認する
- メタ・抽象系: 「1-31 の整数 בלבד」という抽象条件をコードへ落とせているかを確認する
- 発想・拡張系: `NaN` / 小数を 1 つのガードでまとめて拒否できるかを見る
- システム系: UI 側の入力制御に依存しすぎていないかを確認する
- 戦略・価値系: 追加差分が小さく、保守しやすいかを確認する
- 問題解決系: 根本原因を 1 箇所で止める設計になっているかを見る

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: 設計整合性チェック

**目的**: Phase 1 の要件と Phase 2 の設計が整合しているか確認する

**実行手順**:

1. Phase 1 の受け入れ基準（AC-1〜AC-7）を読み込む
2. Phase 2 の実装設計書を読み込む
3. 以下の観点でチェックする:

   | チェック観点        | 確認内容                                                   |
   | ------------------- | ---------------------------------------------------------- |
   | AC-1 対応           | `dayOfMonth=0` でガードされるか                            |
   | AC-2 対応           | `dayOfMonth=32` でガードされるか                           |
   | AC-3 対応           | `dayOfMonth=-1` でガードされるか                           |
   | AC-4 対応           | `dayOfMonth=1` で正常動作するか                            |
   | AC-5 対応           | `dayOfMonth=31` で正常動作するか                           |
   | AC-6 対応           | 既存テストへの影響がないか                                 |
   | AC-7 対応           | JSDoc更新設計が含まれているか                              |
   | 非整数値チェック    | `Number.isInteger(dayOfMonth)` で NaN / 小数も拒否できるか |
   | `weekly` との対称性 | ブロック構文・早期リターンパターンが一致しているか         |

4. 判定を記録する

**期待される成果物**:

- `outputs/phase-3/design-checklist.md`（設計チェックリスト）

---

### タスク2: シンプル代替案検討

**目的**: より簡潔な実装方法がないか検討し、選択した方針の根拠を記録する

**実行手順**:

1. 代替案を検討する:
   - 案A: `!Number.isInteger(dayOfMonth) || dayOfMonth < 1 || dayOfMonth > 31` （選択案）
   - 案B: `dayOfMonth == null || dayOfMonth < 1 || dayOfMonth > 31` （null/undefined に強いが非整数を取りこぼす）
   - 案C: `!(dayOfMonth >= 1 && dayOfMonth <= 31)` （範囲比較のみで整数性が曖昧になる）
2. 各案のメリット・デメリットを比較する
3. 選択した案の理由を記録する

**期待される成果物**:

- `outputs/phase-3/alternatives.md`（代替案検討書）

---

### タスク3: ゲート判定

**目的**: PASS / MINOR / MAJOR / CRITICAL を判定し、次のアクションを決定する

**実行手順**:

1. 以下の判定基準に従ってゲート判定を行う:

   | 判定     | 条件                     | 次のアクション             |
   | -------- | ------------------------ | -------------------------- |
   | PASS     | 全レビュー観点で問題なし | Phase 4 へ進行             |
   | MINOR    | 軽微な指摘あり           | 指摘対応後、Phase 4 へ     |
   | MAJOR    | 重大な問題あり           | Phase 2 へ戻る             |
   | CRITICAL | 致命的な問題あり         | Phase 1 へ戻りユーザー確認 |

2. 戻り先決定基準:

   | 問題の種類       | 戻り先              |
   | ---------------- | ------------------- |
   | 要件の問題       | Phase 1（要件定義） |
   | 設計の問題       | Phase 2（設計）     |
   | テスト設計の問題 | Phase 4（テスト）   |

3. 判定結果を `outputs/phase-3/gate-decision.md` に記録する

**期待される成果物**:

- `outputs/phase-3/gate-decision.md`（ゲート判定書）

---

### タスク4: Phase 4 開始条件確認

**目的**: Phase 4（テスト作成）を開始するための前提条件が整っているか確認する

**実行手順**:

1. 以下の前提条件をチェックする:
   - [ ] Phase 1 の全成果物が揃っている
   - [ ] Phase 2 の全成果物が揃っている
   - [ ] ゲート判定が PASS または MINOR（対応済み）である
   - [ ] TC-11〜TC-15 のテスト仕様が確定している
   - [ ] 実装方針が確定している

2. 全て満たされていれば Phase 4 へ進む

**期待される成果物**:

- `outputs/phase-3/gate-decision.md` への追記（Phase 4 開始条件）
