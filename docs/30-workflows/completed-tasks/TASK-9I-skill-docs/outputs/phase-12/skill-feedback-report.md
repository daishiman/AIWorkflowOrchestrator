## ワークフロー改善点

### 改善点 1: Phase 間の仕様整合性チェックの自動化

Phase 5 仕様書で `outputFormat` の選択肢が Phase 1/2 と異なっていた。Phase 1/2 では `pdf` を含む3形式（markdown, html, pdf）が検討されていたが、Phase 5 では markdown/html の2形式に絞り込まれた。この絞り込みの判断は正しいが、Phase 間の仕様変更がドキュメント上で明示的に追跡されていなかった。

**提案**: Phase 3（設計レビュー）の仕様書テンプレートに「Phase 1/2 からの仕様変更一覧」セクションを追加し、変更理由を必ず記録するようにすべき。

### 改善点 2: Phase 4（テスト作成）と Phase 5（実装）の並列実行推奨

本タスクでは TDD の Red -> Green サイクルに従い、Phase 4 でテストを全て作成してから Phase 5 で実装した。しかし、セクション生成やフォーマット変換のような独立性の高い機能は、テスト作成と実装を同時並行で進めることが可能だった。

**提案**: Phase 仕様書テンプレートの「並列実行の推奨」セクションで、Phase 4-5 の並列実行パターンを明示的に推奨すべき。独立性の高い機能群（例: generate と export は別メソッド）では、機能単位での Red -> Green サイクルが効率的。

## 技術的教訓

### 教訓 1: LLM 連携パターンの DI 設計

`LLMQueryFn` を `(prompt: string) => Promise<{ content: string }>` というシンプルな関数型で定義し、Constructor Injection で注入する設計は、テスタビリティと柔軟性の両立に効果的だった。テスト時は `vi.fn().mockResolvedValue()` で簡単にモック化でき、本番では任意の LLM プロバイダを差し替えられる。

この「関数型 DI」パターンは、外部 API 連携のある他のサービスにも応用可能。

### 教訓 2: IPC バリデーション共通関数の抽出

`validateStringArg` 関数を skillHandlers.ts のモジュールスコープに定義し、全 docs ハンドラーで共有する設計にした。P42 準拠の3段バリデーション（型チェック -> 空文字列 -> trim 空文字列）を1箇所に集約できたため、各ハンドラーの実装がシンプルになった。

今後新規 IPC ハンドラーを追加する際も、この共通関数を再利用すべき。

### 教訓 3: テンプレートセクションの prompt 設計

`DEFAULT_DOC_TEMPLATE` の各セクションに定義した `prompt` フィールドは、LLM への指示文そのものとして機能する。「200文字以内で」「テーブル形式で」といった出力形式の指定を prompt に含めることで、LLM の出力品質が安定する。

将来のカスタムテンプレート実装（UT-9I-002）では、ユーザーが prompt をカスタマイズできる UI が必要になる。
