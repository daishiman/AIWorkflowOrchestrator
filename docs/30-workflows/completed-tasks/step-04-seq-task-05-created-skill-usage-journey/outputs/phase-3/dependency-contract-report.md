## 2. Task04 契約チェック

Task04（評価・採点ゲート機能）のスコアリングゲート連携マトリクスとの契約を検証する。

参照: `completed-tasks/step-03-seq-task-04-evaluation-and-scoring-gate/outputs/phase-2/scoring-gate-matrix.md`

---

### 2.1 EP-3 入力契約

| 項目     | 内容                                                                                                                                                                                                                                                                                                                              |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 契約内容 | EP-3 入力: `skillName: string`（利用前評価対象）                                                                                                                                                                                                                                                                                  |
| 設計対応 | ipc-integration-design.md セクション3: `skill:optimize:evaluate` を再利用。引数は `{ prompt: selectedSkill.promptContent }`                                                                                                                                                                                                       |
| 判定     | **適合**                                                                                                                                                                                                                                                                                                                          |
| 根拠     | Task04 の契約では `skillName` を入力としているが、実際の IPC 呼び出しでは `prompt`（スキルのプロンプト本文）を渡す。これは `skillName` からスキルデータを取得し、そのプロンプト本文を IPC に渡すフローで整合する。Renderer 側で skillName → promptContent の変換を行う設計が ipc-integration-design.md セクション8 に示されている |

---

### 2.2 EP-3 出力契約

| 項目     | 内容                                                                                                                                                                                                                                            |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 契約内容 | EP-3 出力: `gate: ScoringGateResult`（利用可否参考情報、利用ブロック機能なし）                                                                                                                                                                  |
| 設計対応 | ipc-integration-design.md セクション3: `PromptEvaluation` → `getScoreGateResult(evaluation.score)` で変換                                                                                                                                       |
| 判定     | **適合**                                                                                                                                                                                                                                        |
| 根拠     | IPC の戻り値 `PromptEvaluation` を `getScoreGateResult()` で `ScoringGateResult` に変換する設計が明示。Task04 で定義された `getScoreGateResult()` 関数をそのまま再利用。利用ブロック機能なしの制約も「EP-3 はブロックしない」設計判断として明記 |

---

### 2.3 EP-4 入力契約

| 項目     | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 契約内容 | EP-4 入力: `executionResult: string`（Agent の実行結果）                                                                                                                                                                                                                                                                                                                                                                                         |
| 設計対応 | ipc-integration-design.md セクション4: `skill:optimize:evaluate` を再利用。引数は `{ prompt: skill.promptContent }`                                                                                                                                                                                                                                                                                                                              |
| 判定     | **適合**                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| 根拠     | Task04 契約では `executionResult` を入力としているが、Phase 2 設計では EP-4 も EP-3 と同一の `skill:optimize:evaluate` チャネルを再利用し、スキルのプロンプト本文を再評価する方式を採用。実行結果は `agentSlice.lastExecutionResult` に別途保持され、UI 表示に使用される。再評価の入力はスキルのプロンプト本文であり、実行結果そのものではない点が Task04 契約と異なるが、評価の目的（スキル品質の再確認）は同一であり、実装上の最適化として妥当 |

---

### 2.4 EP-4 出力契約

| 項目     | 内容                                                                                                                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 契約内容 | EP-4 出力: `evaluation: PromptEvaluation`（更新後評価）+ `gate: ScoringGateResult`（再評価後判定）                                                                                                     |
| 設計対応 | ipc-integration-design.md セクション4: `PromptEvaluation` → `getScoreGateResult()` → `setPostExecutionScore()` → `ScoreDelta` 算出フロー                                                               |
| 判定     | **適合**                                                                                                                                                                                               |
| 根拠     | IPC 戻り値 `PromptEvaluation` を `getScoreGateResult()` で `ScoringGateResult` に変換し、`calculateScoreDelta()` で delta を算出。state-management-design.md で `postExecutionScore: ScoringGateResult | null` として agentSlice に保持。quality-display-placement.md 地点6で ScoreDelta 表示仕様を定義。全ての出力型が Task04 契約と一致 |

### 2.5 ScoringGate CTA 制御

| 項目     | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 契約内容 | ScoringGate 4段階に基づく CTA ボタンの有効/無効/非表示制御。NEEDS_IMPROVEMENT は保存/利用ブロック、SAVE_ALLOWED は保存可/利用ブロック、USE_ALLOWED は利用可、RECOMMENDED は推奨バッジ表示                                                                                                                                                                                                                                                                            |
| 設計対応 | screen-transition-design.md セクション7: 16パターン CTA マトリクス（ScoringGate 4段階 x CTA 4種）。セクション7.2: `getCTAVisibility()` 関数の TypeScript 実装                                                                                                                                                                                                                                                                                                        |
| 判定     | **適合**                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 根拠     | Task04 の scoring-gate-matrix.md セクション2-1 で定義された canSave/canUse フラグと、Phase 2 の CTA マトリクスが完全に一致。NEEDS_IMPROVEMENT: canSave=false, canUse=false → 「今すぐ使う」disabled, 「保存して後で使う」disabled。SAVE_ALLOWED: canSave=true, canUse=false → 「保存して後で使う」primary, 「今すぐ使う」disabled。USE_ALLOWED: canUse=true → 「今すぐ使う」primary。RECOMMENDED: canUse=true + isRecommended=true → 「今すぐ使う」primary-highlight |

### 2.6 非ブロッキング要件（5項目）

Task04 契約および Phase 1 要件で定義された「ブロックしない」要件の適合確認。

#### 2.6.1 EP-3 は利用をブロックしない

| 項目     | 内容                                                                                                                                                                                          |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 契約内容 | EP-3（利用前評価）は情報提供のみであり、スキルの実行をブロックしない                                                                                                                          |
| 設計対応 | ipc-integration-design.md セクション3: 「EP-3 はブロックしない」設計判断を3つの理由付きで明示。quality-display-placement.md セクション2.3: CTA 無効化「しない」、ドロップダウン制限「しない」 |
| 判定     | **適合**                                                                                                                                                                                      |

#### 2.6.2 EP-3 評価失敗時にバナー非表示（エラー透過）

| 項目     | 内容                                                                                                                |
| -------- | ------------------------------------------------------------------------------------------------------------------- |
| 契約内容 | EP-3 の評価が失敗した場合、バナーを非表示にして通常フローを継続する                                                 |
| 設計対応 | ipc-integration-design.md セクション8 Renderer 側コード: `catch { setPreEvaluationResult(null); }` でバナー非表示化 |
| 判定     | **適合**                                                                                                            |

#### 2.6.3 EP-4 はユーザー任意実行

| 項目     | 内容                                                                                                                                |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 契約内容 | EP-4（利用後再評価）はユーザーの任意操作であり、Agent 実行完了後に自動実行しない                                                    |
| 設計対応 | ipc-integration-design.md セクション4: 「EP-4 の任意性」を3つの理由付きで明示。「ユーザーが『再評価する』ボタンを押下（任意操作）」 |
| 判定     | **適合**                                                                                                                            |

#### 2.6.4 Workspace スキル選択でスキルのフィルタリングをしない

| 項目     | 内容                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------- |
| 契約内容 | Workspace のスキル選択ドロップダウンで、ScoringGate に基づくスキルの除外やフィルタリングを行わない |
| 設計対応 | quality-display-placement.md セクション2.3: 「ドロップダウン制限: しない。全スキルが選択可能」     |
| 判定     | **適合**                                                                                           |

#### 2.6.5 改善フィードバックの強制をしない（NEEDS_IMPROVEMENT 以外）

| 項目     | 内容                                                                                                                                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 契約内容 | NEEDS_IMPROVEMENT 以外のゲートでは改善フローへの遷移を強制しない（情報提供と選択肢の提示に留める）                                                                                                                                         |
| 設計対応 | screen-transition-design.md セクション5.1: SAVE_ALLOWED は「改善推奨バナー + 改善ボタン」、USE_ALLOWED は「任意改善ボタン」、RECOMMENDED は「改善不要メッセージ」                                                                          |
| 判定     | **適合**                                                                                                                                                                                                                                   |
| 根拠     | NEEDS_IMPROVEMENT のみ「強い誘導: 改善完了まで利用不可」とし、それ以外は改善を推奨/任意として選択肢を提示するに留めている。SAVE_ALLOWED は「改善推奨」だが利用ボタンの無効化は canUse=false による仕様であり、改善フロー自体は強制されない |
