## 4. 方針C 採用理由の確定

### 4.1 採用理由

1. **後方互換性の最大化**: Renderer 側の戻り値解釈パターンに変更を加えないため、既存の AgentView、SkillSelectorPanel、useSkillExecution 等のコンポーネントに影響がない
2. **既修正タスクの成果維持**: P44（skill:import インターフェース修正）、P45（skill:remove インターフェース修正）の成果を無効化しない
3. **P25 リスク回避**: OperationResult<T> の廃止が不要であり、TASK-9C 系への波及影響がない
4. **段階的移行の容易性**: 7ステップの段階的移行計画により、各ステップで独立してテスト回帰を実行可能
5. **セキュリティ改善の即時性**: sanitizeErrorMessage の導入は方針に関係なく必要であり、方針C では最小の追加変更で達成可能

### 4.2 方針A/B を不採用とした理由

**方針A（全チャネル直接返却+throw統一）**:

- `skill:list`, `skill:getImported`, `skill:execute` 等の既存ラッパー返却を全て変更する必要があり、テスト影響が大きい
- OperationResult の廃止が必要（P25 波及影響リスク）
- 長期的には最もクリーンだが、本タスクの目的（契約一貫性の確保）に対してオーバーエンジニアリング

**方針B（全チャネルラッパー返却+unwrap統一）**:

- `skill:import`（P44 修正済み）と `skill:remove`（P45 修正済み）を再びラッパーで包む必要があり、既修正成果を無効化する
- `skill:abort`（boolean）と `skill:get-status`（null許容）のプリミティブ型をラッパー化すると、直感的でない API 設計になる
