## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

UT-FIX-SKILL-REMOVE-INTERFACE-001 タスクの Phase 7（カバレッジ確認）で、`skillHandlers.ts` のカバレッジ数値に大きな乖離が判明した:

| 指標       | ファイル全体 | skill:remove単体 | 最低基準 |
| ---------- | ------------ | ---------------- | -------- |
| Lines      | 45.14%       | 事実上100%       | 80%      |
| Branches   | 75.75%       | 100%（全5分岐）  | 60%      |
| Functions  | 37.50%       | 事実上100%       | 80%      |
| Statements | 45.14%       | 事実上100%       | 80%      |

`skillHandlers.ts` は15個のIPCハンドラを含む約435行のファイルであり、修正対象の `skill:remove` ハンドラ（約20行）は全分岐がテストでカバーされている。しかし、ファイル全体のカバレッジは残り14個のスコープ外ハンドラの未カバーにより低値を示す。

Phase 7 では「ファイル全体の基準未達は本タスクスコープ外に起因する」と判定して PASS としたが、この判定プロセスは属人的であり、標準化されたルールが存在しない。

### 1.2 問題点・課題

1. **カバレッジ閾値のスコープ判定基準が未定義**: 15ハンドラを含むファイルで1ハンドラのみ修正する場合、ファイル全体のカバレッジ閾値を適用すべきかハンドラ単位で適用すべきかの判定基準が定義されていない
2. **ハンドラ単位のカバレッジが計測できない**: Vitest の v8 カバレッジプロバイダはファイル単位でカバレッジを報告するため、ファイル内の特定コードブロック（ハンドラ）のカバレッジを個別に確認する手段がない
3. **P41（v8インライン関数カウント）の影響が不透明**: インラインアロー関数（`getAllowedWindows: () => [mainWindow]` 等）が各ハンドラに存在し、未実行のハンドラ分が Function Coverage を押し下げるが、どのハンドラの影響かが特定できない
4. **Phase 7 判定の再現性**: 修正対象ハンドラのカバレッジが十分であることの立証が、カバレッジレポートの行番号の手動確認に依存しており、判定の再現性が低い

### 1.3 放置した場合の影響

- 今後の `skillHandlers.ts` 修正タスクの Phase 7 で毎回同じ判定議論が発生する
- 判定が属人化し、担当者によって PASS/FAIL の判断が異なるリスクがある
- ファイル全体のカバレッジ改善が進まない（どのハンドラが未テストかの可視化ができない）
- ファイル分割（UT-FIX-7-1-002）を実施しない場合、問題が恒常的に残り続ける

## 2. 何を達成するか（What）

### 2.1 目的

`skillHandlers.ts` のような複数ハンドラを含むファイルに対して、ハンドラ単位でカバレッジを計測・レポートする基盤を構築し、Phase 7 の判定基準を明確化する。

### 2.2 最終ゴール

1. **ハンドラ単位カバレッジ集計スクリプト**: v8 カバレッジ JSON を解析し、各 `ipcMain.handle` ブロックの Line/Branch/Function カバレッジを個別に算出するスクリプトが存在する
2. **Phase 7 カバレッジ判定ルール**: 修正対象ハンドラ vs ファイル全体のカバレッジ閾値適用ルールが文書化されている
3. **レポートテンプレート**: Phase 7 仕様書テンプレートに「ハンドラ単位カバレッジレポート」セクションが追加されている

### 2.3 スコープ

#### 含むもの

- ハンドラ単位カバレッジ集計スクリプトの設計・実装・テスト
- `skillHandlers.ts` を対象とした集計スクリプトの動作検証
- Phase 7 カバレッジ判定ルールの策定・文書化
- Phase 7 テンプレートへの「ハンドラ単位カバレッジレポート」セクション追加

#### 含まないもの

- `skillHandlers.ts` のファイル分割（UT-FIX-7-1-002 のスコープ）
- `skillHandlers.ts` 内の skill:remove 以外のハンドラへのテスト追加
- Vitest 本体のカスタムレポータープラグイン作成（v8 JSON の後処理スクリプトに留める）
- 他の IPC ハンドラファイル（`authHandlers.ts` 等）へのスクリプト適用（本タスクでは `skillHandlers.ts` のみで検証）

## 3. どのように実行するか（How）

### 3.1 前提条件

- Vitest v8 カバレッジプロバイダが設定済みであること（`apps/desktop/vitest.config.ts` で `coverage.provider: 'v8'`）
- `skillHandlers.ts` の既存テスト（`skillHandlers.test.ts`）が存在し、PASS すること
- `pnpm vitest run --coverage` で v8 カバレッジ JSON が生成できること

### 3.2 依存タスク

| タスクID                          | 関係   | 状況   | 説明                                                 |
| --------------------------------- | ------ | ------ | ---------------------------------------------------- |
| UT-FIX-SKILL-REMOVE-INTERFACE-001 | 先行   | 完了   | 本タスクの発見元。Phase 7 でカバレッジ乖離を確認     |
| UT-FIX-7-1-002                    | 並行可 | 未着手 | ファイル分割アプローチ。本タスクとは独立して実施可能 |

### 3.3 必要な知識

| 知識領域                        | 参照先                                                                            |
| ------------------------------- | --------------------------------------------------------------------------------- |
| Vitest v8 カバレッジプロバイダ  | Vitest 公式ドキュメント `coverage.provider: 'v8'`                                 |
| v8 カバレッジ JSON フォーマット | V8 Coverage Report 形式（`scriptCoverage`, `ranges`, `startOffset`, `endOffset`） |
| IPC ハンドラ構造                | `apps/desktop/src/main/ipc/skillHandlers.ts`                                      |
| カバレッジ基準                  | `.claude/skills/aiworkflow-requirements/references/quality-requirements.md`       |
| P41 インライン関数カウント      | `.claude/rules/06-known-pitfalls.md#P41`                                          |
| P40 テスト実行ディレクトリ依存  | `.claude/rules/06-known-pitfalls.md#P40`                                          |

### 3.4 推奨アプローチ

#### アプローチ概要

v8 カバレッジプロバイダが出力する JSON カバレッジデータ（`coverage/coverage-final.json` または `coverage/tmp/` 配下のファイル）を解析し、`skillHandlers.ts` 内の各 `ipcMain.handle(...)` ブロックの行範囲を特定して、ハンドラごとのカバレッジを算出する。

#### 実装方針

```
入力:
  1. skillHandlers.ts のソースコード（ipcMain.handle ブロックの行範囲を特定）
  2. v8 カバレッジ JSON（各行のヒット回数データ）

処理:
  1. TypeScript AST を解析し、ipcMain.handle() の呼び出しブロック（チャンネル名、開始行、終了行）を抽出
  2. v8 カバレッジ JSON から skillHandlers.ts の行ごとのカバレッジデータを取得
  3. 各ハンドラブロックの行範囲でカバレッジデータをフィルタリング
  4. ハンドラごとの Line/Branch/Function カバレッジを算出

出力:
  ハンドラ別カバレッジレポート（テーブル形式）
```

#### Phase 7 判定ルール案

```
ルール1: 修正対象ハンドラのカバレッジが全指標で最低基準を満たす場合 → PASS
ルール2: ファイル全体のカバレッジが最低基準を満たさない場合でも、
         修正対象外ハンドラに起因する場合は PASS とする
ルール3: ルール2 を適用する場合、未タスク検出（Phase 12）で
         未カバーハンドラのテスト追加タスクを作成する
ルール4: Branch Coverage はファイル全体で最低基準（60%）を満たす必要がある
         （分岐はハンドラ間で独立しているため）
```

## 3.5 実装課題と解決策（親タスクからの教訓）

UT-FIX-SKILL-REMOVE-INTERFACE-001 の Phase 7 で得られた教訓を以下に記録する。

### 課題1: カバレッジ閾値スコープの曖昧性

| 項目         | 内容                                                                                                                                                                                                                    |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **課題**     | Phase 7 で `skillHandlers.ts` 全体のカバレッジ（Lines 45.14%, Functions 37.50%）が最低基準（80%）を大幅に下回ったが、修正対象の `skill:remove` ハンドラは全5分岐カバー・11テスト PASS で事実上100%だった                |
| **発見経緯** | `pnpm vitest run --coverage` のレポートでファイル全体のカバレッジが赤表示（基準未達）となり、PASS/FAIL の判定に迷った。ハンドラ一覧表を作成し、修正対象外の14ハンドラが未カバーであることを手動確認して PASS と判定した |
| **解決策**   | ハンドラ単位のカバレッジ集計スクリプトを作成し、修正対象ハンドラのカバレッジを自動的に抽出・判定できるようにする。Phase 7 判定ルールを文書化して属人的判断を排除する                                                    |
| **教訓**     | 複数ハンドラを含む大規模ファイルでは、ファイル全体のカバレッジは修正対象の品質を正確に反映しない。カバレッジ基準の適用スコープを明確にしないと、Phase 7 の判定が毎回議論になる                                          |

### 課題2: v8 インライン関数カウントの影響（P41）

| 項目         | 内容                                                                                                                                                                                                  |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **課題**     | v8 カバレッジプロバイダがインラインアロー関数（`getAllowedWindows: () => [mainWindow]`）を独立した関数としてカウントし、Functions 37.50% という実態より低い値を報告した                               |
| **発見経緯** | Phase 7 レポート作成時に Functions カバレッジが Lines カバレッジより低い原因を調査し、各ハンドラの `getAllowedWindows` コールバック（計15個）が未実行の独立関数としてカウントされていることを確認した |
| **解決策**   | ハンドラ単位カバレッジスクリプトでインラインアロー関数を検出し、P41 の影響を注記としてレポートに含める。修正対象ハンドラの `getAllowedWindows` は SH-RM-07 で実行・検証済みであることを記録した       |
| **教訓**     | P41 の影響はファイル全体のカバレッジを見る場合に特に顕著になる。ハンドラ単位で計測すれば、P41 対策済みのハンドラと未対策のハンドラを区別できる                                                        |

### 課題3: ハンドラ単位カバレッジの手動確認コスト

| 項目         | 内容                                                                                                                                                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **課題**     | 修正対象ハンドラのカバレッジが十分であることの立証が、カバレッジレポートの行番号とソースコードの手動突合に依存していた                                                                                                                            |
| **発見経緯** | Phase 7 レポートで「skill:remove ハンドラの分岐カバレッジ確認」セクションを作成する際、行範囲（行140-159）を手動で特定し、各分岐のテスト対応を人力で確認した。15ハンドラのうち1つだけだったため可能だったが、複数ハンドラ修正時にはスケールしない |
| **解決策**   | TypeScript AST 解析で `ipcMain.handle` ブロックの行範囲を自動特定し、v8 カバレッジ JSON との突合を自動化する                                                                                                                                      |
| **教訓**     | 手動確認は1ハンドラでは可能だが、複数ハンドラ修正や定期的なカバレッジ監視にはスケールしない。自動化の投資対効果は大きい                                                                                                                           |

### 発見元の原文

```
UT-FIX-SKILL-REMOVE-INTERFACE-001 Phase 7 カバレッジ確認レポートより:

skillHandlers.ts 全体のカバレッジ:
- Lines: 45.14% (基準80% 未達)
- Functions: 37.50% (基準80% 未達)
- Branches: 75.75% (基準60% 達成)

判定: PASS（skill:remove ハンドラ範囲で基準充足）
判定根拠: ファイル全体の Lines/Functions の低値は、テストスコープ外の14個のハンドラーが
未カバーであることに起因する。修正対象の skill:remove ハンドラは全5分岐カバー・
11テスト PASS で事実上100%。
```

### 既存タスクとの差分

| 観点         | UT-FIX-7-1-002（ファイル分割）                           | 本タスク（測定基盤）                           |
| ------------ | -------------------------------------------------------- | ---------------------------------------------- |
| アプローチ   | skillHandlers.ts を3-4ファイルに分割                     | ファイル構造は変えず、カバレッジ集計方法を改善 |
| 解決する問題 | ファイルの責務分離、テストファイルの肥大化               | カバレッジ閾値のスコープ判定、ハンドラ単位計測 |
| 副次効果     | ファイル単位カバレッジが各ハンドラグループに対応         | 他の大規模ハンドラファイルにも適用可能         |
| 実施順序     | 本タスク後でもよい                                       | ファイル分割前でも有用                         |
| 補完関係     | ファイル分割後も測定基盤があるとハンドラ単位の監視が可能 | ファイル分割がなくてもハンドラ単位の判定が可能 |

### 補足事項

- 本タスクと UT-FIX-7-1-002（ファイル分割）は補完的な関係にあり、どちらか一方のみ実施してもよい
- 集計スクリプトは `skillHandlers.ts` 以外の大規模ハンドラファイル（`authHandlers.ts` 等）にも将来適用可能だが、本タスクでは `skillHandlers.ts` のみで検証する
- Phase 7 判定ルールの策定は、今後の全タスクの Phase 7 に影響するため、レビュー時に慎重に検討すること
