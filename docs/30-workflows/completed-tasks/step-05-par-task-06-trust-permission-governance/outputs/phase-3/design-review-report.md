| 利点           | 判定ロジックが単純化される（1つの条件式で分岐可能）。ユーザーの認知負荷が減少する。テストケース数が大幅に減少する。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| 採用しない理由 | Bash コマンドの中にも sudo（critical）と chmod（high）で異なる対応が必要。2段階では chmod に対して過剰制限（critical扱い）または不十分制限（safe扱い）のどちらかになる。`rm -rf /`（システム破壊）と `curl example.com`（外部通信）を同一の「危険」レベルに分類すると、警告疲れ（alert fatigue）を引き起こす。Phase 1 OUT-1 の BASH_COMMANDS 24パターンの分析では、不可逆的操作（Critical: 11件）と可逆的だがリスクのある操作（High: 10件）の間に明確なリスク差がある。Task-08 の公開ゲートで「公開不可（UNSAFE）」と「警告付き公開可（SAFE_WITH_WARNINGS）」の区別が必要であり、2段階では表現力が不足する。 |
| 結論           | **不採用**。4段階は複雑性の増加に見合うリスク粒度の向上を提供している。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

### SA-02: 承認履歴の永続化なし（セッションのみ）の検討

| 項目           | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 代替案         | 承認履歴を electron-store に永続化せず、セッション中のメモリのみで管理する                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| 利点           | electron-store のスキーマ管理が不要になる。マイグレーションロジック（V1→V2）が不要。パフォーマンスが向上する（ディスク I/O がゼロ）。                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 採用しない理由 | `approved`（恒久許可）をセッション単位にすると、アプリ再起動のたびにユーザーが全ツールの権限を再承認する必要があり、UX が著しく悪化する。Permission History Panel（既存 UI）はアプリ再起動後も履歴を表示する前提で設計されており、セッションのみの管理では既存 UI との整合性が破壊される。Task-08（スキル公開）の安全性チェックで `deniedRatio` を算出するために過去の承認履歴データが必要であり、セッション終了で履歴が消失すると公開判定の精度が低下する。ユーザーが「以前許可したツール」を確認できなくなり、意図しない恒久許可の発見が遅れるセキュリティリスクがある。 |
| 結論           | **不採用**。恒久許可と履歴の永続化は UX・既存 UI 整合・公開判定精度の観点で必須。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

### SA-03: Task-08 への安全性ゲートなしで直接公開の検討

| 項目           | 内容                                                                                                                                                                                                                                                                                                                                                                                   |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 代替案         | `SafetyGatePort.evaluate()` による安全性チェックを省略し、スキルを直接公開可能にする                                                                                                                                                                                                                                                                                                   |
| 利点           | 公開フローが簡略化される。SafetyGatePort/SafetyGateResult/SafetyCheckDetail 等の型定義が不要。公開までのステップ数が減少し、スキル作成者の体験が向上する。                                                                                                                                                                                                                             |
| 採用しない理由 | Critical リスクツール（`rm -rf /`、`sudo`、`mkfs`）を含むスキルが未検証で公開されると、第三者の環境でシステム破壊が発生する。復旧手段が存在しない不可逆的損害のリスクがある。公開プラットフォームの信頼性が損なわれ、1件の悪意ある/誤ったスキルの公開が全ユーザーの信頼を毀損する。Phase 1 OUT-5 の受入基準 AC-4（共有前安全性ゲート）で安全性チェックが必須要件として定義されている。 |
| 結論           | **不採用**。安全性ゲートは公開プラットフォームの信頼性維持に不可欠であり、省略のリスクが利点を大幅に上回る。                                                                                                                                                                                                                                                                           |
