## セキュリティ観点（4件）

### チェック 1: Critical 恒久許可禁止の不変条件

| 項目     | 内容                                                                                                                                                                                                                                                                                |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 確認内容 | Critical リスクツールへの恒久許可経路が設計上完全に遮断されているか                                                                                                                                                                                                                 |
| 確認結果 | **OK**                                                                                                                                                                                                                                                                              |
| 根拠     | `outputs/phase-5/security.ts` L52-54 に `allowApproveOnce: false` / `allowPermanent: false` / `autoDenyDefault: true` が変更禁止コメント付きで定義されている。同ファイル L43-47 のコメントに「変更が必要な場合は Phase 3 設計レビューを再実施すること」と保護ルールも明記されている |

不変条件の実現方法: PermissionDialog のボタン表示ロジックが `TOOL_RISK_CONFIG[riskLevel].allowPermanent` を参照するため、`false` の間は UI 上から恒久許可ボタン自体が非表示になる。型定義レベルでの制約ではなく、設定値による動的制御であるが、定数定義のコメントで「変更禁止」が明示されている。

### チェック 2: approved_once のセッション跨ぎ非永続化

| 項目     | 内容                                                                                                                                                                                                                                                           |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 確認内容 | approved_once エントリが electron-store に書き込まれず、セッション終了で確実に消滅する設計か                                                                                                                                                                   |
| 確認結果 | **OK**                                                                                                                                                                                                                                                         |
| 根拠     | `outputs/phase-5/permission-store-interface.ts` L99 のコメント「session: undefined（electron-store に書かない）」と `outputs/phase-5/permission-state-machine.md` パス3「事後条件: expiryPolicy === "session" の全エントリが削除される」で二重に保証されている |

設計の堅牢性: `calcExpiresAt` 関数の `session` ケースが `undefined` を返す（L114-116）ことで、electron-store への書き込みが発生しない設計になっている。アプリ再起動時に `revokeSessionEntries` が呼ばれなくても、そもそも electron-store に session エントリが存在しないため永続化リスクがない。

### チェック 3: abort 後の approved_once エントリ削除

| 項目     | 内容                                                                                                                                                                                                                                                              |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| 確認結果 | **OK**                                                                                                                                                                                                                                                            |
| 根拠     | `outputs/phase-5/abort-fallback-contract.md` フロー1 Step2 に `permissionStore.revokeSessionEntries(sessionId)` が定義されており、契約条件（事後条件）に「permissionStore に expiryPolicy:"session" のエントリが0件になること」と検証可能な条件式で明記されている |

冪等性の保証: 「同一 sessionId で2回呼び出しても Step 2-4 は副作用なし（エントリなし）」と冪等性が保証されており、二重 abort の場合も安全である。

### チェック 7: 拒否後の fallback 3択表示

| 項目     | 内容                                                                                                                                                                                                                                                                                     |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 確認内容 | PermissionDialog で拒否した後に abort/skip/retry の3択が提示される設計か                                                                                                                                                                                                                 |
| 確認結果 | **OK**                                                                                                                                                                                                                                                                                   |
| 根拠     | `outputs/phase-5/abort-fallback-contract.md` フロー間の優先順位セクションに「abort > skip > retry」の3フローが定義されている。フロー2（skip）で「後続処理を続行」、フロー3（retry）で「PermissionDialog を再表示（最大3回）」、フロー1（abort）で「セッション停止」の3択が設計されている |

fallback の選択肢: (1) skip: 当該ツールをスキップして後続継続、(2) retry: ダイアログを再表示（最大3回）、(3) abort: セッション全体を停止。ユーザーの意図に応じた3択が設計されている。
