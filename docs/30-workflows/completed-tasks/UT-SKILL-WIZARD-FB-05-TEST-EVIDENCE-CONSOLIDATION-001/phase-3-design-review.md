## Phase 2設計の矛盾・漏れチェック

### RV-001: テーブル項目の過不足

| 対象テーブル    | チェック内容                                    | 判定   | 備考                               |
| --------------- | ----------------------------------------------- | ------ | ---------------------------------- |
| edge case一覧表 | ID・観点・入力値・期待動作・根拠ID・結果の6項目 | 要確認 | 「前提条件」列の追加要否を確認する |
| テスト件数集約  | 区分・件数・PASS/FAIL/SKIPの5列                 | 要確認 | 「備考」列の追加要否を確認する     |
| 仕様判断根拠    | ID・判断内容・根拠・影響範囲の4項目             | 要確認 | 「決定日」列の追加要否を確認する   |
| 実施情報        | 実施日・実施者・バージョン・環境・Issue の5項目 | 要確認 | 「レビュア」欄の追加要否を確認する |

### RV-002: ID体系の一貫性

| チェック内容                                          | 判定   | 備考                                             |
| ----------------------------------------------------- | ------ | ------------------------------------------------ |
| EC-NNN が edge case一覧表内で重複しないこと           | 要確認 | 採番ルール（3桁ゼロ埋め）の明示が必要            |
| SD-NNN が仕様判断根拠テーブル内で重複しないこと       | 要確認 | 採番ルールの明示が必要                           |
| edge case一覧表の `仕様判断根拠ID` が全て有効なSD-NNN | 要確認 | 存在しないSD-NNNを参照しないことの保証方法を設計 |
| 1つのSD-NNNが複数のEC-NNNから参照される多対1関係      | 要確認 | Phase 2設計では言及なし。許容するか明示が必要    |

### RV-003: AC-1〜5との対応漏れ

| AC   | 基準内容                                        | Phase 2での対応                                | 漏れ判定                |
| ---- | ----------------------------------------------- | ---------------------------------------------- | ----------------------- |
| AC-1 | edge case一覧表がテンプレートに含まれている     | `## edge case 一覧表` セクション設計済み       | 要確認                  |
| AC-2 | テスト件数と内訳が1箇所に集約されるテンプレート | `## テスト件数サマリー` セクション設計済み     | 要確認                  |
| AC-3 | 仕様判断の根拠が証跡ファイルに明示される構造    | `## 仕様判断根拠` セクション設計済み           | 要確認                  |
| AC-4 | task-specification-creatorスキルへの反映        | Before/After比較で変更方針を記載               | 要確認                  |
| AC-5 | 既存Phase 11実例との互換性確認                  | Phase 2では設計のみ（実例確認はPhase 6で実施） | 未対応（Phase 6で対応） |

### RV-004: docs-onlyタスクとしての実装範囲

| チェック内容                                                    | 判定   | 備考                                     |
| --------------------------------------------------------------- | ------ | ---------------------------------------- |
| 変更対象がMarkdownファイルのみであること                        | 要確認 | コード実装ゼロを確認する                 |
| 影響範囲4ファイルが全てdocsまたはskillsの参照ファイルであること | 要確認 | アプリケーションコードへの変更がないこと |

### RV-005: 既存Phase 11実例との互換性

| チェック内容                                         | 判定          | 備考                                           |
| ---------------------------------------------------- | ------------- | ---------------------------------------------- |
| 新セクション追加が既存実例の必須項目と競合しないこと | Phase 6で確認 | 新セクションは全て「追加」であり削除なし       |
| 既存実例が新テンプレートに移行できる構造であること   | Phase 6で確認 | オプション扱いにするか必須にするかの判断が必要 |

### RV-006: 双方向参照の設計

| チェック内容                                   | 判定     | 備考                                          |
| ---------------------------------------------- | -------- | --------------------------------------------- |
| EC-NNN → SD-NNN（edge caseから根拠への参照）   | 設計済み | Phase 2でカラムとして定義                     |
| SD-NNN → EC-NNN（根拠からedge caseへの逆引き） | 要確認   | Phase 2では逆引き設計なし。追加要否を判断する |

## Phase 4進行判定

### 判定基準

| 基準                             | 充足状態     | 備考                                        |
| -------------------------------- | ------------ | ------------------------------------------- |
| AC-1〜3の設計が存在する          | 充足         | Phase 2で設計済み                           |
| AC-4のスキル更新方針が明確である | 充足         | Before/Afterで方針記述済み                  |
| AC-5の互換性確認計画がある       | 充足         | Phase 6で実施予定                           |
| docs-onlyの実装範囲が適切である  | 充足         | Markdownファイルのみ対象                    |
| ID体系に重大な矛盾がない         | 条件付き充足 | 採番ルールの明示が必要（Phase 4までに対応） |

### 判定結果

**PASS（条件付き）**: 以下の条件を満たすことを前提にPhase 4に進行する。

**条件:**

1. 各テーブルの「追加要否を確認する」列（前提条件・備考・決定日・レビュア）について、Phase 4のテスト作成前に追加/非追加を明示的に決定する
2. ID採番ルール（EC-NNN・SD-NNNの採番方法）をPhase 5実装前に明示する
3. SD-NNN → EC-NNN の逆引き設計の要否をPhase 5実装前に決定する
