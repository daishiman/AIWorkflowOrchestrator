## 目的

Phase 1で確定した要件・影響範囲をもとに、edge case一覧表・テスト件数集約テンプレート・仕様判断根拠セクションの具体的な構造を設計し、Before/After比較で変更内容を明確化する。

## edge case一覧表のフォーマット設計

### 設計方針

- テスト証跡ファイル内でedge caseを網羅的に管理できるよう、1行1ケースのテーブル形式とする
- 各ケースに対して「仕様判断根拠」を紐付け、判断理由を証跡として残す
- IDは `EC-NNN` 形式で採番し、正常系・異常系テストとの区別を明確にする

### edge case一覧表テンプレート（設計案）

```markdown
## edge case 一覧表

| ID     | 観点             | 入力値（代表例）           | 期待動作             | 仕様判断根拠ID | 結果 |
| ------ | ---------------- | -------------------------- | -------------------- | -------------- | ---- |
| EC-001 | 空白文字列入力   | `" "` (スペースのみ)       | 空文字扱いでエラー   | SD-001         | -    |
| EC-002 | 最大長境界値     | 255文字の文字列            | 正常に受け付ける     | SD-002         | -    |
| EC-003 | 最大長+1境界値   | 256文字の文字列            | バリデーションエラー | SD-002         | -    |
| EC-004 | 特殊文字含む入力 | `<script>alert()</script>` | エスケープ処理される | SD-003         | -    |
| EC-005 | null/undefined   | `null`                     | デフォルト値で処理   | SD-004         | -    |
```

### 項目定義

| 項目名           | 型     | 説明                                                  |
| ---------------- | ------ | ----------------------------------------------------- |
| ID               | string | `EC-NNN` 形式の一意識別子                             |
| 観点             | string | テストするedge caseの観点名                           |
| 入力値（代表例） | string | 代表的な入力値（バッククォートで囲む）                |
| 期待動作         | string | そのedge caseで期待される動作・結果                   |
| 仕様判断根拠ID   | string | 対応する仕様判断根拠テーブルのID（`SD-NNN`形式）      |
| 結果             | string | テスト実行後に記入（PASS / FAIL / SKIP / `-`=未実行） |

## テスト件数集約テンプレートの構造設計

### 設計方針

- テストの全体像を1箇所で把握できるよう、種別ごとの件数を集約する
- サマリーと内訳の2階層構造とし、詳細は後続のテーブルに委ねる
- 実施日・実施者・環境情報も同一セクションに記載して証跡を一本化する

### テスト件数集約テンプレート（設計案）

```markdown
## テスト件数サマリー

| 区分            | 件数 | PASS | FAIL | SKIP |
| --------------- | ---- | ---- | ---- | ---- |
| 正常系テスト    | -    | -    | -    | -    |
| 異常系テスト    | -    | -    | -    | -    |
| edge caseテスト | -    | -    | -    | -    |
| **合計**        | -    | -    | -    | -    |

### 実施情報

| 項目           | 内容       |
| -------------- | ---------- |
| 実施日         | YYYY-MM-DD |
| 実施者         | -          |
| 対象バージョン | -          |
| 実施環境       | -          |
| 関連Issue      | #NNNN      |
```

### 設計根拠

- サマリーを先頭に置くことでレビュアーが全体像を即座に把握できる
- PASS/FAIL/SKIPの列を設けることで合否判定を一覧化できる
- 実施情報を同セクションに統合することで証跡として完結させる

## 仕様判断根拠セクションの設計

### 設計方針

- 「なぜそのように動作するか」の根拠を証跡ファイルに明示する
- edge case一覧表の `仕様判断根拠ID` と1:Nで紐付けられる構造にする
- 判断内容・根拠・影響範囲を3項目でシンプルに記述する

### 仕様判断根拠テンプレート（設計案）

```markdown
## 仕様判断根拠

| ID     | 判断内容                     | 根拠                                         | 影響範囲                 |
| ------ | ---------------------------- | -------------------------------------------- | ------------------------ |
| SD-001 | 空白文字列は空文字として扱う | UX仕様書 §3.2「入力値の正規化」より          | 全テキスト入力フィールド |
| SD-002 | 最大文字数は255文字とする    | DB設計書 §5.1「フィールド定義」より          | スキル名・説明フィールド |
| SD-003 | 特殊文字はHTMLエスケープ処理 | セキュリティ要件 §2.1「XSS対策」より         | 全テキスト出力箇所       |
| SD-004 | null入力はデフォルト値で補完 | API仕様書 §4.3「オプショナルパラメータ」より | オプション項目全般       |
```

### 項目定義

| 項目名   | 型     | 説明                                                 |
| -------- | ------ | ---------------------------------------------------- |
| ID       | string | `SD-NNN` 形式の一意識別子（edge case一覧と紐付け用） |
| 判断内容 | string | どのような仕様判断をしたかの記述                     |
| 根拠     | string | その判断の根拠（仕様書参照・設計方針等）             |
| 影響範囲 | string | この判断が影響するコンポーネント・フィールド範囲     |

## Before/After比較（現行テンプレート vs 改善案）

### AC-1: edge case一覧表

| 観点 | Before（現行）                  | After（改善案）                            |
| ---- | ------------------------------- | ------------------------------------------ |
| 構造 | edge caseの記載箇所が存在しない | `## edge case 一覧表` セクションを新規追加 |
| 管理 | 各テスト実施者が独自形式で記載  | `EC-NNN` IDによる標準化された管理          |
| 根拠 | 仕様判断との紐付けなし          | `仕様判断根拠ID` 列で `SD-NNN` と紐付け    |

### AC-2: テスト件数集約

| 観点 | Before（現行）                       | After（改善案）                                     |
| ---- | ------------------------------------ | --------------------------------------------------- |
| 構造 | 件数情報が複数ファイルに分散         | `## テスト件数サマリー` セクションを先頭近くに配置  |
| 内訳 | 正常系・異常系・edge caseの区別なし  | 種別ごとの件数・PASS/FAIL/SKIP を1テーブルに集約    |
| 証跡 | 実施日・実施者・環境が別ファイル記載 | `### 実施情報` サブセクションで同一ファイルに一本化 |

### AC-3: 仕様判断根拠

| 観点 | Before（現行）                       | After（改善案）                            |
| ---- | ------------------------------------ | ------------------------------------------ |
| 構造 | 仕様判断の記載箇所が存在しない       | `## 仕様判断根拠` セクションを新規追加     |
| 追跡 | 後から判断理由を追跡できない         | `SD-NNN` IDで edge case と双方向に参照可能 |
| 証跡 | 暗黙的な判断が証跡ファイルに残らない | 判断内容・根拠・影響範囲を明示的に記録     |

### AC-4: task-specification-creator スキルへの反映

| 観点 | Before（現行）                                        | After（改善案）                                          |
| ---- | ----------------------------------------------------- | -------------------------------------------------------- |
| 構造 | Phase 11テンプレートに上記3セクションが含まれていない | スキルのPhase 11テンプレートファイルに3セクションを追加  |
| 波及 | 新規タスクでも同じ問題が繰り返される                  | スキルテンプレートを更新することで全新規タスクに自動適用 |
