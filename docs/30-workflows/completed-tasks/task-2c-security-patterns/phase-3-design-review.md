### Task 3-2: 設計整合性確認

**目的**: 設計内部の整合性を確認する

**チェックリスト**:

- [ ] DANGEROUS_PATTERNS が `as const` で定義されている
- [ ] ALLOWED_TOOLS_WHITELIST が `as const` で定義されている
- [ ] AllowedTool 型が WHITELIST から推論されている
- [ ] 全関数にJSDocが付与されている
- [ ] エクスポートが正しく設計されている
- [ ] ファイル構成が packages/shared の規約に従っている

### Task 3-3: 仕様書との整合性確認

**目的**: 設計が仕様書（specification.md §7.1-7.4）と一致しているか確認する

**チェックリスト**:

- [ ] §7.1.1 の全コマンドパターンが BASH_COMMANDS に含まれている
- [ ] §7.1.1 の全保護パスが PROTECTED_PATHS に含まれている
- [ ] §7.3.1 の全ツールが WHITELIST に含まれている
- [ ] 関数シグネチャがタスク定義（task-2c-security-patterns.md）と一致している

### Task 3-4: システム仕様との整合性確認

**目的**: aiworkflow-requirements の仕様と整合しているか確認する

**チェックリスト**:

- [ ] セキュリティ設計原則（最小権限、多層防御）に準拠
- [ ] 入力バリデーションパターンに準拠
- [ ] 既存のセキュリティパターンと重複・矛盾がない

### Task 3-5: 実装可能性確認

**目的**: 設計が実装可能であることを確認する

**チェックリスト**:

- [ ] Node.js標準ライブラリのみで実装可能
- [ ] 正規表現が安全にエスケープされている
- [ ] process.env.HOME のフォールバックが考慮されている
- [ ] 計算量が O(n) 以下である
- [ ] TypeScript strict モードで問題ない

---

## 3. レビュー判定基準

### 3.1 PASS条件

- 全てのチェック項目が確認済み
- 仕様書との不整合がない
- 設計上の懸念点がない、または対策が明確

### 3.2 FAIL条件

- 要件を満たさない設計がある
- 仕様書との不整合がある
- 実装不可能な設計がある

### 3.3 FAIL時のアクション

1. Phase 2 に戻り設計を修正
2. 必要に応じて Phase 1 の要件も見直す
3. 修正後に再度 Phase 3 を実行
