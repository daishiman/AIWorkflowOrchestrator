## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

UT-SKILL-IMPORT-CHANNEL-CONFLICT-001 において、`skill:import` チャネル名がローカルインポート（既存機能）と外部ソースインポート（TASK-9F新機能）で競合する問題が発覚した。この解決過程で、IPCチャネル命名規則の3パターンが確立された:

| パターン                 | 用途             | 例                       |
| ------------------------ | ---------------- | ------------------------ |
| `skill:{動詞}`           | 既存ローカル操作 | `skill:import`           |
| `skill:{動詞}FromSource` | 外部ソース操作   | `skill:importFromSource` |
| `skill:{動詞}Source`     | ソース関連操作   | `skill:validateSource`   |

しかし、この命名規則は **UT-SKILL-IMPORT-CHANNEL-CONFLICT-001 以降に策定されたもの** であり、既存の全IPCチャネルがこの規則に準拠しているかは未検証である。

### 1.2 問題点

- 既存IPCチャネル（`channels.ts` に定義）の命名が新命名規則と整合しているか未確認
- 同一ドメイン内（例: `auth:*`, `agent:*`）で動詞の使い方が不統一の可能性がある
- 将来の機能追加時に、命名不統一がチャネル名競合（P5パターン）の温床となるリスクがある
- `grep` による文字列検索だけでは、チャネル名の「文脈」（ローカル vs 外部ソース）を判別できない

### 1.3 放置した場合の影響

- TASK-9F 以外の機能追加時にも同様のチャネル名競合が発生するリスク
- 新規開発者がチャネル名を決定する際の一貫した判断基準が欠如
- `ipcMain.handle()` の二重登録例外（P5）が予防的に検出できない
- チャネル数が増加するほど命名不統一の修正コストが増大

## 2. 何を達成するか（What）

### 2.1 目的

全既存IPCチャネルの命名を監査し、UT-SKILL-IMPORT-CHANNEL-CONFLICT-001 で確立した命名規則への準拠状況を評価する。不準拠チャネルに対するリネーム計画を策定する。

### 2.2 最終ゴール

- [ ] `channels.ts` の全チャネル名が命名規則テーブルに対応付けられている
- [ ] 命名不統一のチャネルが0件、またはリネーム計画が策定されている
- [ ] 今後の機能追加時に参照できるチャネル命名ガイドラインが完成している
- [ ] 命名規則違反を検出するスクリプトまたはチェックリストが用意されている

### 2.3 スコープ

#### 含むもの

- `apps/desktop/src/main/ipc/channels.ts` の全チャネル名の監査
- ドメイン別（skill, auth, agent, app 等）の命名パターン分析
- 不準拠チャネルのリストアップと優先度付きリネーム計画
- チャネル命名ガイドラインの作成（architecture-implementation-patterns.md への追記）
- 命名規則違反検出の自動化（grep パターンまたはスクリプト）

#### 含まないもの

- チャネル名の実際のリネーム実装（リネーム計画の策定まで）
- TASK-9F の新チャネル実装（別タスク: task-022/task-030）
- IPC ハンドラのロジック変更
- Preload/Renderer 側のコード変更

## 3. どのように実行するか（How）

### 3.1 前提条件

- UT-SKILL-IMPORT-CHANNEL-CONFLICT-001 が完了していること（`spec_created`）
- `architecture-implementation-patterns.md` の IPCチャネル名競合予防パターンセクションが存在すること

### 3.2 依存タスク

| タスクID                             | 状態         | 依存内容         |
| ------------------------------------ | ------------ | ---------------- |
| UT-SKILL-IMPORT-CHANNEL-CONFLICT-001 | spec_created | 命名規則の策定元 |

### 3.3 必要な知識

- IPCチャネル命名規則の3パターン（`architecture-implementation-patterns.md` 参照）
- P5（リスナー二重登録）パターン
- P44/P45（IPCインターフェース不整合 / 引数命名ドリフト）パターン
- Electron IPC通信の基礎（`ipcMain.handle()` / `ipcMain.on()`）

### 3.4 推奨アプローチ

1. `channels.ts` から全チャネル名を抽出（`grep -E "^\s+\w+:" apps/desktop/src/main/ipc/channels.ts`）
2. ドメイン別（コロン前のプレフィックス）にグルーピング
3. 各ドメインの動詞パターンを分析し、命名規則テーブルに照合
4. 不準拠チャネルをリストアップし、リネーム後の名前を提案
5. リネームの影響範囲を `grep -rn "チャネル名" apps/desktop/` で調査
6. 優先度（高: 競合リスクあり、中: 命名不統一、低: 慣例的に問題なし）を付与

### 3.5 実装課題と解決策（UT-SKILL-IMPORT-CHANNEL-CONFLICT-001 からの教訓）

| 課題                                            | 発見経緯                                                                               | 解決策                                                                         | 教訓                                                      |
| ----------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------- |
| grep 検索だけでは文脈判別が困難                 | Phase 4 でチャネル名の「ローカル vs 外部ソース」文脈を grep で判別しようとしたが不十分 | ファイル単位で文脈を確認し、チャネル名 + 引数型 + 用途の3点セットで判断する    | 文字列一致だけでなくセマンティクスの確認が必須            |
| Phase 4 修正箇所数の見積もり誤差（P37パターン） | Phase 4 で「3箇所」と見積もったが実際は「1箇所」だった                                 | `grep -c` の実測値ベースで期待値を設定する                                     | 概算ではなく実測値で検証テストを設計する                  |
| チャネル名の重複検出方法                        | 同名チャネルが異なるファイルに定義される可能性を見落としそうだった                     | `channels.ts` 一元管理 + `grep -rn "ipcMain.handle\|ipcMain.on" apps/desktop/` | ホワイトリスト（channels.ts）と実使用箇所の両方を検証する |

## 6. 検証方法

### テストケース

1. `channels.ts` の全チャネル名が監査レポートに含まれていることを確認
2. 不準拠チャネルのリネーム案が命名規則3パターンのいずれかに準拠していることを確認
3. リネーム案が既存チャネル名と重複しないことを `grep` で確認
4. ガイドラインに基づいて新規チャネル名を命名できることを検証

### 検証手順

```bash
# 全チャネル名の抽出
grep -E "^\s+\w+:" apps/desktop/src/main/ipc/channels.ts

# チャネル名の重複チェック
grep -oP "'[^']+'" apps/desktop/src/main/ipc/channels.ts | sort | uniq -d

# ハンドラ登録箇所の確認
grep -rn "ipcMain.handle\|ipcMain.on" apps/desktop/src/main/
```

## 7. リスクと対策

| リスク                                       | 影響度 | 発生確率 | 対策                                                               |
| -------------------------------------------- | ------ | -------- | ------------------------------------------------------------------ |
| リネーム対象チャネルが多すぎて影響範囲が膨大 | 高     | 中       | 優先度付けを行い、高リスクチャネルのみ先行リネーム                 |
| リネームにより既存テストが大量に壊れる       | 中     | 高       | リネーム計画策定のみ（本タスク）、実装は別タスクで段階的に実施     |
| 命名規則が全ドメインに適用できない特殊ケース | 低     | 中       | 例外パターンをガイドラインに明記し、判断基準を提供                 |
| チャネル名の「文脈」判別が主観的になる       | 中     | 中       | 引数型 + 用途 + ドメイン の3点セットで客観的に判定する基準を設ける |

## 9. 備考

### 設計判断の根拠

1. **監査のみ（リネーム実装は別タスク）とした理由**: 全チャネルのリネームは影響範囲が大きく、段階的な実施が安全。まず監査で全体像を把握し、リネーム計画を策定することで、後続タスクの見積もり精度を向上させる
2. **ドメイン別分析を推奨する理由**: `skill:*`, `auth:*`, `agent:*` 等のドメインごとに命名パターンが異なる可能性がある。ドメイン単位で分析することで、各ドメインの特殊事情（外部ソース操作の有無等）を考慮した判断ができる

### UT-SKILL-IMPORT-CHANNEL-CONFLICT-001 の先例

本タスクの命名規則は以下の実績に基づく:

- `skill:import`（ローカル用）と `skill:importFromSource`（外部ソース用）の分離
- 仕様書段階での予防的検出により、P5（二重登録例外）を事前に回避
- `grep -rn` による横断検索で修正箇所を漏れなく特定

### 補足

監査の結果、全チャネルが既に命名規則に準拠している場合は、「準拠確認完了」として監査レポートのみ作成し、リネーム計画は不要とする。
