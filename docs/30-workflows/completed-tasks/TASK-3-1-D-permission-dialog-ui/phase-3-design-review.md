## 目的

Phase 2で作成した設計が要件を満たしているか、実装可能か、既存実装との整合性があるかをレビューし、品質ゲートを通過させる。

## 背景

TDD（テスト駆動開発）に入る前に、設計の妥当性を確認することで、手戻りを最小化する。

---

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: 要件充足確認

**目的**: Phase 1の要件がPhase 2の設計で充足されているかを確認する

**実行手順**:

1. 機能要件の充足確認
   - [ ] skillAPIに`onPermission`メソッドが設計されている
   - [ ] skillAPIに`respondPermission`メソッドが設計されている
   - [ ] IPC通信フローが設計されている
   - [ ] PermissionDialogとの連携が設計されている

2. 非機能要件の充足確認
   - [ ] アクセシビリティ要件が設計に反映されている
   - [ ] セキュリティ要件（許可チャネルのみ使用）が設計されている
   - [ ] 既存実装の再利用が考慮されている

3. 受け入れ基準との整合確認
   - [ ] 設計が受け入れ基準を満たす実装を可能にする

**期待される成果物**:

- `outputs/phase-3/requirements-fulfillment-check.md`: 要件充足確認結果

---

### タスク2: 既存実装との整合性確認

**目的**: 設計が既存コードベースと整合しているかを確認する

**実行手順**:

1. 既存agentAPI permissionパターンとの整合確認
   - 類似のインターフェース設計になっているか
   - 同じ型を再利用可能か

2. 既存IPCチャネル設計との整合確認
   - channels.tsの既存パターンに従っているか
   - 許可リストの更新方法が適切か

3. 既存PermissionDialogとの整合確認
   - Propsインターフェースが互換性を持つか
   - 状態管理パターンが既存と統一されているか

4. TASK-3-1-C（Main Process）との接続確認
   - Main Processが送信するIPCチャネルと一致しているか
   - 型定義が整合しているか

**期待される成果物**:

- `outputs/phase-3/existing-implementation-alignment.md`: 既存実装整合確認結果

---

### タスク3: 統合テスト観点レビュー

**目的**: 統合テストの観点が設計に十分に含まれているかを確認する

**実行手順**:

1. IPC統合テスト観点
   - Main → Renderer の権限リクエスト送信テスト
   - Renderer → Main の権限応答送信テスト
   - タイムアウト時の動作テスト

2. UI統合テスト観点
   - PermissionDialog表示テスト
   - ユーザー操作（許可/拒否）テスト
   - フォーカス管理テスト

3. エラーハンドリングテスト観点
   - IPC通信エラー時のテスト
   - 不正なリクエストの処理テスト

**期待される成果物**:

- `outputs/phase-3/integration-test-review.md`: 統合テスト観点レビュー結果

---

### タスク4: レビュー結果判定

**目的**: レビュー結果を総合的に判定し、次のPhaseへの進行可否を決定する

**実行手順**:

1. レビュー結果の集計
   - PASS: 全レビュー観点で問題なし
   - MINOR: 軽微な指摘あり → 指摘対応後、次のPhaseへ
   - MAJOR: 重大な問題あり → 影響範囲に応じて戻る
   - CRITICAL: 致命的な問題あり → Phase 1へ戻りユーザー確認

2. 指摘事項の記録
   - 発見した問題点をリスト化
   - 対応方針を記載

3. 判定結果の明記

**期待される成果物**:

- `outputs/phase-3/review-result.md`: レビュー結果判定書
