## 目的

Phase 2 で確定した設計の妥当性を、ドキュメント作成開始前に多角的な視点でレビューする。フィールド定義・writer設計・validator設計案・追記計画の各観点で問題がないかを確認し、Phase 4（ドキュメント作成）への進行可否を判定する。設計上の問題を早期発見してフィードバックループを最小化することが目的である。

## 実行タスク

1. Phase 1 の current facts と Phase 2 の設計案を突合し、verify_existing 判定を確定する
2. フィールド定義、writer設計、validator設計、追記計画の4観点をレビューする
3. 30種の思考法をレビュー観点へマッピングし、抜け漏れ・過剰設計・責務混在を洗い出す
4. 重複・矛盾・未記載が見つかった場合は Phase 2 へ差し戻し条件を明文化する
5. `outputs/phase-3/` に gate 判定・compliance audit・solution elegance review を出力する

## verify_existing モード判定

docs-only タスクにおいてPhase 3 の最初に実施する必須確認。

### 確認内容

Phase 1 の P50チェックで既存ファイルが発見された場合、以下を評価する。

| 確認項目                                                              | 判定基準                                                           |
| --------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 追記先として選定したファイルに既存の qualityInsights 定義が存在するか | 存在する場合は内容の差分を確認し、追記ではなく更新が必要か判定する |
| Phase 2 の設計内容と既存定義が矛盾していないか                        | 矛盾がある場合は Phase 2 へ差し戻す                                |
| 設計した追記内容が既存記述と重複しないか                              | 重複がある場合は追記範囲を縮小するか Phase 2 へ戻る                |

### verify_existing 判定フロー

```
既存定義が存在する？
  ├─ NO  → 通常の追記設計をそのまま採用（verify_existing 不要）
  └─ YES → 既存定義との差分確認
              ├─ 差分なし（内容が同一）→ 本タスクの追記スコープを縮小
              ├─ 差分あり（追記で吸収可能）→ 追記内容を調整して続行
              └─ 差分あり（矛盾が存在する）→ Phase 2 へ差し戻し
```

## レビュー観点

### 観点 1: フィールド定義の完全性・正確性

確認する内容:

- `outputs/phase-2/field-spec.md` のフィールド数が Phase 1 の `field-inventory.md` のフィールド数と一致しているか
- 11フィールド全てに型・必須/省略可・値域・説明が記載されているか
- `taskMetrics` がオブジェクト1フィールドとして定義されており、配下5サブフィールドを含めた数え方が明確か
- rate系フィールド（`patternAdoptionRate` / `coverageTargetHitRate` / `unassignedTaskDetectionRate`）の値域が 0.0〜1.0 として正しく定義されているか
- `notes` フィールドが string 型・自由記述・省略可として定義されているか
- docs-only タスクにおける `totalTests`/`avgCoverage` の「0を記録する」という設計が明記されているか

判定基準:

- フィールド数が Phase 1 の棚卸し結果と一致している
- 各フィールドに4項目（型・必須/省略可・値域・説明）が全て記載されている

### 観点 2: writer設計・運用責任の妥当性

確認する内容:

- 全フィールドに対してwriterが定義されており、「writer不在」のフィールドが残っていないか
- 更新タイミングが「Phase 12 closeout 時」に統一されており、タスクの運用フローと整合しているか
- 手動管理を正式化する設計方針の根拠が明確か（「自動化スクリプトが存在しない」という現状認識が正確か）
- 自動化の将来方針が「スコープ外」と明記された上で記録されているか
- dual root（`.claude/` と `.agents/`）のどちらへ追記するか、同期方法が設計書に明記されているか

判定基準:

- 全フィールドにwriter・更新タイミング・運用責任者が定義されている
- 手動管理の根拠が客観的な事実（スクリプト不在）に基づいている

### 観点 3: validator設計案の適切性

確認する内容:

- validator設計案に「実装はスコープ外」が明記されているか
- 設計案の検証項目が Phase 1 で識別した silent break リスクを網羅しているか
  - rate系フィールドの値域逸脱（0.0〜1.0 を超える値）
  - `taskMetrics` 配下の必須サブフィールド欠落
  - フィールド型の不整合（例: `notes` が string でない）
- 実装アプローチ候補（JSON Schema / custom script / 既存validator拡張）が列挙されているか
- validator実装タスクへの引き継ぎ情報（候補ファイル・アプローチ）が記載されているか

判定基準:

- 「実装はスコープ外」の明記がある
- silent break の主要リスク3点（値域・必須フィールド・型）が設計案にカバーされている

### 観点 4: 追記計画の実行可能性

確認する内容:

- 追記先ファイルが存在することが確認されているか（Phase 1 の P50チェック結果と整合しているか）
- 追記内容のテンプレートが自己完結しており、読者（Claude / 人間）が単独で理解できるか
- 追記後に既存記述と矛盾・重複が発生しないか（verify_existing 判定と整合しているか）
- 追記の分量が追記先ファイルの適切な規模内に収まっているか（500行超過リスクの評価）
- dual root への追記（`.claude/` 追記後に `.agents/` へ同期する手順）が計画に含まれているか

判定基準:

- 追記先ファイルが特定されており、存在が確認されている
- 追記後の重複・矛盾リスクが評価されている

### 観点 5: 他スキルへの展開方針の妥当性

確認する内容:

- opt-in 方針の根拠（スキルごとに成熟度が異なる）が明確か
- opt-in の判断基準（usage count 10以上を推奨）が他スキルの現状と整合しているか
- `skill-creator`・`aiworkflow-requirements`・`github-issue-manager`・`int-test-skill`・`skill-fixture-runner` の5スキルが全て評価されているか
- 展開方針が「強制しない」ことが明記されており、実装強制になっていないか

判定基準:

- 5スキル全てについて展開方針が記載されている
- opt-in 方針の根拠が1つ以上明示されている

### 観点 6: 統合テスト連携観点のレビュー（docs-only版）

確認する内容:

- 設計書が「追記後の内容は読者が単独で理解できる」という自己完結要件を満たしているか
- consumer audit結果（TASK-EVALS-CONSUMER-AUDIT-001）との整合確認が設計に含まれているか
- validator設計案が「未実装である旨と実装タスクへの引き継ぎ情報」を含んでいるか
- docs-only タスクの統合ポイント4点（正本整合性・consumer audit整合性・dual root整合性・波及設計）が設計書に反映されているか

判定基準:

- 統合ポイント4点が `spec-addition-plan.md` または `writer-design.md` に記載されている

## Gate: Phase 4 への進行判定

以下の全条件を満たした場合に Phase 4（ドキュメント作成）へ進行する。条件を満たさない場合は Phase 2 へ差し戻す。

| Gate条件                                                            | 判定 | 差し戻し先        |
| ------------------------------------------------------------------- | ---- | ----------------- |
| verify_existing 判定が完了し、重複・矛盾がないか解消されている      | -    | Phase 2 Step 4    |
| フィールド定義の完全性・正確性レビューで問題がない                  | -    | Phase 2 Step 1    |
| writer設計・運用責任が全フィールドに定義されている                  | -    | Phase 2 Step 2    |
| validator設計案が「実装スコープ外」の明記を含み適切に記載されている | -    | Phase 2 Step 3    |
| 追記計画が実行可能であり、重複・矛盾リスクが評価されている          | -    | Phase 2 Step 4    |
| 他スキルへの展開方針が5スキル全てについて記載されている             | -    | Phase 2 Step 5    |
| 統合テスト連携の観点が設計に反映されている                          | -    | Phase 2 Step 2〜4 |

### go / no-go 判定

- **go**: 上記 Gate 条件が全て「PASS」であれば Phase 4 へ進行する
- **no-go**: 1件でも「FAIL」があれば指定の差し戻し先へ戻り、修正後に本 Phase を再実施する

## 統合テスト連携

Phase 3 は設計レビューフェーズであるためコード変更・ドキュメント変更は行わない（review のみ）。以下を統合観点のレビューゲートとして確認する。

- **統合ポイントのレビュー**: 観点 6 で統合テスト連携の4点が設計に反映されているかを評価する
- **consumer audit整合**: Phase 2 の writer設計が TASK-EVALS-CONSUMER-AUDIT-001 のconsumer一覧と矛盾していないかを確認する
- **dual root整合**: 追記計画に `.claude/` 追記後の `.agents/` 同期手順が含まれているかを確認する

docs-only タスクとして、以下の統合観点のレビューゲートを設ける。

- 追記内容が「読者が単独で理解できる自己完結した記述」になっているか
- validator設計案が「未実装であること」と「実装タスクへの引き継ぎ情報」を両方含んでいるか

## 多角的チェック観点

- **バイアス回避**: レビューを実施したAI/人間が設計者と同一である場合でも、設計の前提に疑問を呈する観点でチェックする
- **実行可能性**: 追記計画が「Phase 4 で実際に実行できる具体的な手順」になっているかを評価する
- **スコープ遵守**: 設計書にコード実装の混入（スクリプト作成・EVALS.json変更・validator実装）がないかを最終確認する
- **一貫性**: フィールド定義表・writer設計表・validator設計案・追記計画の4文書間で用語・フィールド名・数値が一致しているかを確認する
