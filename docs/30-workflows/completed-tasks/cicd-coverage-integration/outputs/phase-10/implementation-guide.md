# Part 1: 概念的な説明（中学生でもわかる版）

## 1. CI/CDカバレッジ統合って何？

### 1.1 身近な例で考えてみよう

**健康診断の例え話**:

学校で年に1回、健康診断がありますよね。身長・体重・視力・聴力など、いろいろな項目を検査します。

```
健康診断のチェック項目:
✅ 身長   - 成長しているか？
✅ 視力   - 目は見えているか？
✅ 聴力   - 耳は聞こえているか？
❌ 血圧   - 測ってない！

→ 検査項目が75%しかカバーされていない
```

プログラムも同じです。プログラムが正しく動くかを確認するのが「テスト」。でも、**プログラムの全部をテストしているとは限りません**。

```
プログラムのテスト状況:
✅ ログイン機能   - テスト済み
✅ データ保存     - テスト済み
✅ 検索機能       - テスト済み
❌ 削除機能       - テストなし！

→ カバレッジ（網羅率）が75%
```

**カバレッジ**とは「テストがプログラムのどれだけをカバー（網羅）しているか」を示す数字です。

### 1.2 なぜ必要なの？

**問題**: テストが足りないと、バグが本番環境で発生してしまいます。

**例**:

- ❌ 削除機能にテストがない → 本番で削除を実行 → データが消えない！
- ❌ エラー処理にテストがない → 本番でエラー発生 → アプリがクラッシュ！

**解決策**: カバレッジをチェックして、テストが十分かを確認します。

```
健康診断で「80点以上でないと部活に参加できない」というルールがあるように、
プログラムでも「カバレッジ80%以上でないとマージできない」というルールを作ります。
```

### 1.3 今回作ったもの

| 日本語               | 英語                            | 役割                                         |
| -------------------- | ------------------------------- | -------------------------------------------- |
| カバレッジ           | Coverage                        | テストがコードをどれだけ網羅しているかの指標 |
| 閾値（いきち）       | Threshold                       | 合格ラインの値（今回は80%）                  |
| CI/CD                | Continuous Integration/Delivery | 自動テスト・自動デプロイの仕組み             |
| プルリクエスト（PR） | Pull Request                    | コードの変更を提案して、レビューしてもらう   |
| ジョブ               | Job                             | CI/CDで実行する処理の単位                    |
| Codecov              | Codecov                         | カバレッジを見やすく表示してくれるサービス   |

## 2. どうやって動くの？

### 2.1 全体の流れ

```
開発者がコードを書く
    ↓
GitHubにコードをアップロード（Push）
    ↓
自動的にテストが実行される（GitHub Actions）
    ↓
カバレッジを計算（何%カバーしているか）
    ↓
Codecovにレポートを送信
    ↓
80%以上？
    ↓ Yes → ✅ 合格！マージできる
    ↓ No  → ❌ 不合格！マージできない
```

### 2.2 何がチェックされるの？

**2つの基準**:

1. **Project Coverage（プロジェクト全体）**
   - プロジェクト全体のカバレッジが80%以上か？

2. **Patch Coverage（変更部分）**
   - 今回追加したコードのカバレッジが80%以上か？

**例**:

```
既存コード: 1000行（カバレッジ 85%）
今回追加: 100行（カバレッジ 60%） ❌

→ Patch Coverageが80%未満なので不合格！
→ 「新しく追加した部分にもっとテストを書いてください」
```

### 2.3 データの保存方法

**カバレッジレポート（lcov.info）**:

| 項目       | 説明                              |
| ---------- | --------------------------------- |
| ファイル名 | どのファイルのカバレッジか        |
| 行番号     | どの行がテストされたか            |
| 割合       | そのファイルの何%がテストされたか |

**Codecovのデータ**:

| 項目             | 説明                               |
| ---------------- | ---------------------------------- |
| プロジェクト全体 | 全体のカバレッジ推移をグラフで表示 |
| ファイル別       | どのファイルのカバレッジが低いか   |
| PR差分           | 今回の変更でカバレッジが上がったか |

## 2. 設計詳細（**なぜ**付き）

### 2.1 設計判断の根拠

| 設計判断               | 選択肢                     | 採用した選択    | なぜこの選択か                                                                |
| ---------------------- | -------------------------- | --------------- | ----------------------------------------------------------------------------- |
| CI実行条件             | 全push / PR+main / PRのみ  | PR+main         | featureブランチへのpushはPRで検証するため不要。無駄なCI実行を削減             |
| カバレッジ閾値         | 60% / 70% / 80% / 90%      | 80%             | 業界標準、現実的な達成目標、既存のdesktop設定（80%）との整合性                |
| fail_ci_if_error設定   | true / false               | true            | 品質ゲートとして機能させるため。閾値未達時は確実にPRをブロック                |
| Action バージョン固定  | SHA / Tag / Major          | Major（@v5）    | セキュリティ修正を自動受信しつつ、破壊的変更を防ぐ。運用コストとのバランス    |
| カバレッジプロバイダー | v8 / istanbul              | v8              | 高速（istanbulより軽量）、Vitestとネイティブ統合、設定がシンプル              |
| Codecov統合サービス    | Codecov / Coveralls / 自前 | Codecov         | デファクトスタンダード、PR統合が優秀、無料枠充実、フラグ機能でモノレポ対応    |
| フラグ設定             | なし / パッケージ別        | shared, desktop | パッケージ別にカバレッジを追跡、問題箇所の特定が容易                          |
| PRコメント設定         | 常に表示 / 変更時のみ      | 変更時のみ      | ノイズ削減。カバレッジに変化がない場合はコメント不要                          |
| タイムアウト設定       | 5分 / 10分 / 15分          | 10分            | 通常5分以内で完了、余裕を持って設定。タイムアウトエラーを防止                 |
| threshold（許容誤差）  | 0% / 1% / 2%               | 1%              | カバレッジ計算の誤差を考慮。79%は失敗、79.5%は許容。厳格すぎない柔軟性を確保  |
| buildジョブのneeds配列 | coverage追加 / 追加しない  | 追加しない      | coverageとbuildは並列実行可能。パイプラインの並列性を維持してCI実行時間を短縮 |

### 2.2 coverageジョブの依存関係設計

**なぜtestジョブに依存させるのか**:

```yaml
coverage:
  needs: [test] # testジョブ完了後に実行
```

- testジョブで既にテストを実行済み
- coverageジョブでは同じテストをカバレッジ付きで再実行
- テストが失敗していたらcoverageを実行しても意味がない
- 依存関係を明確にしてパイプラインの信頼性を向上

**なぜbuildジョブはcoverageを待たないのか**:

```yaml
build:
  needs: [lint, typecheck, test] # coverageは含まない
```

- buildの成功にカバレッジは不要（型チェックとテスト通過で十分）
- coverageとbuildを並列実行することでCI時間を短縮
- coverageが失敗してもbuildは成功する可能性がある（別の品質指標）

## 3. 設定ファイル詳細

### 3.1 codecov.yml の設計理由

#### project.target: 80%

**なぜ80%か**:

- 業界標準: 多くのOSSプロジェクトで採用される一般的な閾値
- 現実的: 100%は非現実的（UIコードやエラーハンドリングで難しい）、70%は低すぎる
- 既存設定: desktop vitest.configで既に80%設定済み、整合性を保つ

#### patch.target: 80%

**なぜPRの変更部分も80%必要か**:

- 新規コードの品質を維持
- 技術的負債の蓄積を防止
- レガシーコードがカバレッジ低くても、新規追加コードは高品質を維持

#### threshold: 1%

**なぜ1%の許容誤差か**:

- カバレッジ計算には浮動小数点の誤差がある
- 79.0% → FAIL、79.5% → PASS（許容）
- 厳格すぎると開発者の負担が増加

#### flags: shared, desktop

**なぜパッケージ別フラグか**:

- モノレポ構成で複数パッケージが存在
- どのパッケージのカバレッジが低いか特定が容易
- パッケージ別に目標値を設定可能（将来的な拡張）

#### comment.require_changes: true

**なぜ変更時のみコメントか**:

- カバレッジに変化がない場合はコメント不要
- PRのコメント欄がノイズで埋まるのを防止
- 重要な変化だけを通知

## 6. 使用上の注意

### 6.1 CODECOV_TOKENの管理

```yaml
# ❌ 絶対にやってはいけない
- run: echo ${{ secrets.CODECOV_TOKEN }} # トークンがログに露出！

# ✅ 正しい使い方
- uses: codecov/codecov-action@v5
  with:
    token: ${{ secrets.CODECOV_TOKEN }} # GitHub Actionsが自動マスキング
```

**理由**:

- トークンが漏洩すると、悪意ある第三者がカバレッジレポートを改ざん可能
- GitHub Secretsは自動的にログをマスキング（`***`として表示）
- 明示的なechoは避け、Action内で使用する

### 6.2 fail_ci_if_error: true の影響

```yaml
# ❌ Codecovサービス障害時もCI失敗
fail_ci_if_error: true

# 状況:
# - Codecovが503エラー → CIが失敗 → PRマージできない
```

**対策**:

- Codecovサービス障害時は一時的に`false`に変更可能
- https://status.codecov.io でサービス状態を確認
- 復旧後は必ず`true`に戻す

### 6.3 カバレッジ80%を達成できない場合

```bash
# カバレッジが低いファイルを特定
# Codecovダッシュボードで確認
https://codecov.io/gh/[owner]/[repo]

# または、ローカルでHTML レポート確認
pnpm test:coverage
open packages/shared/coverage/index.html

# テストを追加
# カバレッジが低いファイルに対応するテストを作成

# 再度カバレッジ確認
pnpm test:coverage
```

## 7. Codecovダッシュボードの見方

### 7.1 PRコメントの読み方

Codecov botが投稿するコメント例:

```markdown
## Codecov Report

Coverage: 85.2% (+1.2%)

| Flag    | Coverage | Δ     |
| ------- | -------- | ----- |
| shared  | 82.0%    | +2.0% |
| desktop | 88.0%    | +0.5% |

| File | Coverage | Δ |
| ----------------------- | -------- | ----- |
| src/utils/helper.ts | 100% | +10% |
```

**読み方**:

- `Coverage: 85.2%`: プロジェクト全体のカバレッジ
- `(+1.2%)`: 前回から1.2%向上

- `Flag`: パッケージ別カバレッジ
- `Files changed`: 今回変更したファイルのカバレッジ

| 項目           | 確認内容                         |
| -------------- | -------------------------------- |

| Flags          | shared/desktop別のカバレッジ     |
| Trends         | カバレッジの推移グラフ（時系列） |

## 9. トラブルシューティング

### 9.1 coverageジョブが失敗する

**症状**: coverageジョブが赤色（FAIL）

**原因と対策**:

| 原因                            | 確認方法                             | 対策                                    |
| ------------------------------- | ------------------------------------ | --------------------------------------- |
| カバレッジが80%未満             | Codecovダッシュボードで確認          | テストを追加してカバレッジ向上          |
| CODECOV_TOKENが未設定           | GitHub Secrets設定を確認             | Secretsに`CODECOV_TOKEN`を追加          |
| Codecovサービス障害             | https://status.codecov.io で確認     | 一時的に`fail_ci_if_error: false`に変更 |
| lcov.infoファイルが生成されない | ローカルで`pnpm test:coverage`を実行 | vitest.config.tsのcoverage設定を確認    |

### 9.2 Codecovコメントが表示されない

**症状**: PRにCodecov botのコメントがない

**原因と対策**:

| 原因                                 | 確認方法                              | 対策                                 |
| ------------------------------------ | ------------------------------------- | ------------------------------------ |
| Codecov GitHub Appが未インストール   | リポジトリSettings → Integrations確認 | Codecov Appをインストール            |
| codecov.ymlのcomment設定が誤っている | codecov.ymlのcomment.require_head確認 | `require_head: true`を設定           |
| カバレッジに変化がない               | require_changes: true設定             | これは正常動作（変更時のみコメント） |
