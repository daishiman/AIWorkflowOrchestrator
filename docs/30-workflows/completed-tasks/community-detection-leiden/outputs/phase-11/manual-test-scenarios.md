## MT-1: 基本的なコミュニティ検出

### 目的

正常系の動作確認。グラフからコミュニティを正しく検出できることを確認する。

### 前提条件

- テスト用グラフデータ（10ノード、20エッジ程度）が準備されている
- LeidenAlgorithm, CommunityDetectorが正常に初期化されている

### テスト手順

```gherkin
Given 10個のエンティティが存在する
  And 20個のリレーション（エッジ）が存在する
When CommunityDetector.detect()を実行する
Then CommunityDetectionResultが返される
  And result.structure.communities.length >= 1
  And result.structure.totalModularity > 0
  And result.processingTimeMs > 0
```

### 期待結果

- [ ] コミュニティが1つ以上検出される
- [ ] 全ノードがいずれかのコミュニティに属する
- [ ] モジュラリティ > 0
- [ ] 処理時間が記録される

### 検証方法

自動テスト: `基本的なコミュニティ検出ができる`

## MT-2: 階層的コミュニティ構造

### 目的

階層検出の動作確認。複数レベルのコミュニティ構造を正しく生成できることを確認する。

### 前提条件

- 階層構造を持つテストグラフが準備されている
- maxLevels: 3 が設定可能である

### テスト手順

```gherkin
Given 50個以上のエンティティが存在する
  And 複数のクラスター構造を持つグラフである
When detect()をmaxLevels=3で実行する
Then result.structure.levels <= 3
  And レベル0のコミュニティが存在する
  And レベル1以上のコミュニティにはparentCommunityIdが設定される
```

### 期待結果

- [ ] 複数レベルのコミュニティが検出される
- [ ] レベル0（最細粒度）のコミュニティ数 >= レベル1
- [ ] 親子関係が正しく設定されている
- [ ] childCommunityIdsに子コミュニティが含まれる

### 検証方法

自動テスト: `階層的なコミュニティ構造を生成する`, `レベル1以上のコミュニティには親IDが設定される`

## MT-3: Resolutionパラメータの効果

### 目的

パラメータ調整の動作確認。resolutionパラメータが検出結果に正しく影響することを確認する。

### 前提条件

- 同一のテストグラフを使用できる
- resolution値を変更可能である

### テスト手順

```gherkin
Given 同一のKnowledge Graphが存在する
When resolution=0.5で検出を実行する
  And resolution=2.0で検出を実行する
Then resolution=2.0の結果はresolution=0.5より多くのコミュニティを持つ
```

### 期待結果

- [ ] 高resolution（2.0）でより多くのコミュニティ
- [ ] 低resolution（0.5）でより少ないコミュニティ
- [ ] 両方の結果が有効（エラーなし）

### 検証方法

自動テスト: `resolutionパラメータでコミュニティサイズが変わる`

## MT-5: 境界値テスト

### 目的

エッジケースの動作確認。極端な入力に対して適切に動作することを確認する。

### 前提条件

- 空グラフ、1ノードグラフ、孤立ノード含むグラフを準備できる

### テスト手順

```gherkin
Scenario: 空グラフ
  Given ノード数が0のグラフ
  When detect()を実行する
  Then エラーにならず空の結果を返す

Scenario: 1ノードグラフ
  Given ノード数が1のグラフ
  When detect()を実行する
  Then そのノードのみのコミュニティを返す

Scenario: 孤立ノード
  Given 接続のないノードを含むグラフ
  When detect()を実行する
  Then 孤立ノードは個別コミュニティに属する
```

### 期待結果

- [ ] 空グラフ: エラーにならず空の結果を返す
- [ ] 1ノード: そのノードのみのコミュニティを返す
- [ ] 孤立ノード: 孤立ノードのみのコミュニティが作成される

### 検証方法

自動テスト: `空のグラフでも成功する`, `単一ノードのグラフでもエラーにならない`, `孤立ノードを正しく処理する`

## MT-6: エラーハンドリング

### 目的

異常系の動作確認。エラー状況で適切にResult.errを返すことを確認する。

### 前提条件

- 不正なパラメータを指定可能である
- GraphStoreの障害をシミュレート可能である

### テスト手順

```gherkin
Scenario: GraphStore障害
  Given IKnowledgeGraphStoreがエラーを返す
  When detect()を実行する
  Then Result.err(Error)が返される

Scenario: 存在しないエンティティ
  Given 指定IDのエンティティが存在しない
  When getCommunitiesForEntity(invalidId)を実行する
  Then Result.ok([])が返される（空配列）

Scenario: 存在しないコミュニティ
  Given 指定IDのコミュニティが存在しない
  When getCommunityMembers(invalidId)を実行する
  Then Result.err(Error)が返される
```

### 期待結果

- [ ] GraphStore障害時にResult.errが返される
- [ ] 存在しないエンティティでは空配列が返される
- [ ] 存在しないコミュニティではエラーが返される
- [ ] エラーメッセージが適切である

### 検証方法

自動テスト: `GraphStore障害時にResult.errを返す`, `存在しないエンティティは空配列を返す`, `存在しないコミュニティIDでエラーを返す`
