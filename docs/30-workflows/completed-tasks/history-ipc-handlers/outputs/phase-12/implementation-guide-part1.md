# IPCハンドラー実装ガイド - Part 1: 概念的説明

## IPCハンドラーとは？

### 比喩を使った説明

IPCハンドラーは、アプリの「フロント係（画面）」と「バックオフィス（システム）」を繋ぐ「受付窓口」のようなものです。

```
想像してみてください：

銀行の窓口で、あなた（お客様）が「過去の取引履歴を見せてください」とお願いします。
窓口担当（IPCハンドラー）がそのリクエストを受け取り、
バックオフィス（データベース）に問い合わせて、
結果をあなたに返します。

この「窓口担当」の役割を果たすのがIPCハンドラーです。
```

---

## なぜIPCが必要か？

### セキュリティのための分離

Electronでは、画面（レンダラープロセス）とシステム（メインプロセス）は別々に動いています。
これはセキュリティのためです。

```
┌─────────────────────────┐     ┌─────────────────────────┐
│    レンダラープロセス    │     │     メインプロセス       │
│   （ブラウザのような）   │     │   （Node.jsのような）    │
│                         │     │                         │
│  ・画面の表示           │     │  ・ファイル操作         │
│  ・ユーザー入力の受付   │     │  ・データベースアクセス │
│  ・Webページと同じ制限  │     │  ・システムリソースへの │
│                         │     │    フルアクセス         │
└─────────────────────────┘     └─────────────────────────┘
         ↑                               ↑
         │      直接通信は危険！          │
         └───────────────────────────────┘
```

もしレンダラーがメインプロセスの機能に直接アクセスできたら、
悪意のあるWebページがファイルを削除したり、個人情報を盗んだりできてしまいます。

## 全体の流れ

### シンプルな図解

```
UI（画面）
    │
    │ 「履歴を見せて」とお願い
    ▼
┌───────────────────────────────┐
│   受付窓口（IPCハンドラー）    │
│                               │
│  ・リクエストの確認           │
│  ・データの受け渡し           │
│  ・エラー時の対応             │
└───────────────────────────────┘
    │
    │ 「履歴ください」とお願い
    ▼
┌───────────────────────────────┐
│   履歴サービス                 │
│   （HistoryService）          │
│                               │
│  ・データベースから取得       │
│  ・データの加工               │
└───────────────────────────────┘
    │
    │ データを返す
    ▼
受付窓口（IPCハンドラー）
    │
    │ 結果を返す
    ▼
UI（画面に表示）
```

---

## 4つの機能

このIPCハンドラーは、4つの「窓口」を提供します：

### 1. history:getFileHistory（履歴一覧の取得）

```
「このファイルの過去のバージョンを教えて」
→ 過去のバージョン一覧を返す
```

### 2. history:getVersionDetail（バージョン詳細の取得）

```
「このバージョンの詳しい情報を教えて」
→ 変換日時、ファイルサイズなどの詳細を返す
```

### 3. history:getConversionLogs（変換ログの取得）

```
「変換中に何が起きたか教えて」
→ 変換処理のログメッセージを返す
```

### 4. history:restoreVersion（バージョンの復元）

```
「このバージョンに戻して」
→ 指定バージョンを復元して、新しいバージョンとして保存
```

## なぜこの設計にしたか

### 1. Result型パターン

```typescript
// 成功時
{ success: true, data: 履歴データ }

// 失敗時
{ success: false, error: エラー情報 }
```

**理由**:

- UIが「成功したか失敗したか」をすぐに判断できる
- エラーメッセージをユーザーに表示しやすい

### 2. バリデーション（入力チェック）

```
「ファイルIDは？」→「空です」→「エラー！IDが必要です」
```

**理由**:

- 不正なデータがシステム深くまで入らないようにする
- 早めにエラーを返すことで、無駄な処理を防ぐ

### 3. DI（依存性注入）パターン

```typescript
registerHistoryHandlers(mainWindow, historyService);
//                                  ↑
//                     サービスを外から渡す
```

**理由**:

- テストしやすい（偽のサービスを渡せる）
- 将来的にサービスを差し替えやすい

---

## まとめ

IPCハンドラーは：

1. **画面とシステムの橋渡し役**
   - セキュリティを保ちながら通信を可能にする

2. **4つの窓口を提供**
   - 履歴一覧、詳細、ログ、復元

3. **安全で分かりやすい設計**
   - Result型で成功/失敗を明確に
   - バリデーションで不正データを排除
   - DIパターンでテストしやすく
