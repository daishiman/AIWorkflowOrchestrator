## 目的

Phase 2 の設計を 4 条件（矛盾なし・漏れなし・整合性あり・依存関係整合）で検証し、Phase 4 への進行可否を判定する。

## 実行タスク

- 4条件チェックリストの実行
- 設計上のリスク・懸念点の洗い出し
- Phase 4 進行可否の判定（PASS / FAIL）

## 実行手順

### ステップ1: 4条件チェック

| 条件         | チェック項目                                                                   | 判定基準                                                            |
| ------------ | ------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| 矛盾なし     | SKILL.md の「必須ブロック」と既存の「クイックスタート表」が矛盾しないか        | 両者の内容が一貫して対話を要求している                              |
| 矛盾なし     | discover-problem.md の「実行ゲート」と既存の Phase 0-0 フローが矛盾しないか    | ゲートが既存ステップの前に置かれている                              |
| 矛盾なし     | interview-user.md の変更が既存の 4.3（思考プロセス）と矛盾しないか             | 変更は 5.1 入力定義のみに限定されている                             |
| 漏れなし     | 3ファイルへの変更がすべて設計に含まれているか                                  | SKILL.md / discover-problem.md / interview-user.md が網羅されている |
| 漏れなし     | AC-001〜AC-006 のすべてが設計でカバーされているか                              | 各受入基準に対応する設計変更が存在する                              |
| 整合性あり   | 追加するブロックの文体・スタイルが既存ファイルと統一されているか               | Markdown フォーマット・日本語/英語の混在ルールが一致                |
| 整合性あり   | 「命令形」の強度が統一されているか（「してはならない」「必ず〜する」）         | 全文で同じ強度の命令形が使われている                                |
| 依存関係整合 | 変更によって他の agents/ ファイルが影響を受けないか                            | 他ファイルへの影響がゼロであることを確認                            |
| 依存関係整合 | SKILL.md 変更が既存の orchestrate / update / improve-prompt フローを壊さないか | 各モードの開始フローが intact であることを確認                      |

### ステップ2: リスク評価

| リスク                                                   | 発生確率 | 影響度 | 対策                                                                       |
| -------------------------------------------------------- | -------- | ------ | -------------------------------------------------------------------------- |
| 必須ブロックが「詳細すぎて」読み飛ばされる               | 低       | 高     | 7行以内を遵守し、箇条書き3項目以内に収める                                 |
| 「例外なし」が不便を生む（自動化スクリプトで呼ぶ場合等） | 中       | 中     | 現時点では対話前提の使用に絞る。自動化対応は別タスク（未タスクとして記録） |
| discover-problem.md の変更が Phase 0.5 との連携を壊す    | 低       | 低     | 実行ゲートは Phase 0-0-1 のみを強制する。Phase 0.5 以降は変更なし          |

### ステップ3: Phase 4 進行可否判定

**判定基準**:

- 4条件のすべてが PASS → Phase 4 へ進む（PASS）
- 1つでも FAIL → Phase 2 に戻り修正後にレビューを再実施（FAIL）

**判定欄**: `[ PASS / FAIL ]` ← Phase 3 実行時に記入

## 統合テスト連携

コード変更なし。設計レビューのみ。

| 観点         | 判断     | 確認内容                                                                                         |

| 最小変更原則 | **必須** | Phase 2 の設計変更が必要最小限に収まっているか                                                   |
