## 設計決定

### 1. シャード数: 8 → 16

**根拠**:

- テストファイル数: 399
- 399 ÷ 8 = 約50ファイル/シャード → 13分
- 399 ÷ 16 = 約25ファイル/シャード → 期待7-8分

**リスク**: 同時ジョブ数増加
**対策**: GitHub Actionsのconcurrency制限で管理

### 2. shared packageビルドキャッシュ

**キャッシュ戦略**:

| 要素         | 値                                                                                           |
| ------------ | -------------------------------------------------------------------------------------------- |
| path         | `packages/shared/dist`                                                                       |
| key          | `shared-build-${{ runner.os }}-${{ hashFiles('packages/shared/src/**', 'pnpm-lock.yaml') }}` |
| restore-keys | `shared-build-${{ runner.os }}-`                                                             |

**期待効果**: 20秒のビルドステップをスキップ

### 3. Vitest並列化設定

| 設定            | 変更前 | 変更後                    | 理由            |
| --------------- | ------ | ------------------------- | --------------- |
| maxForks        | 2      | 4 (CI) / 2 (local)        | I/O待ち時間活用 |
| fileParallelism | false  | true (CI) / false (local) | 8GB RAMで安定   |

### 4. カバレッジ条件分岐

| トリガー  | カバレッジ | coverageジョブ |
| --------- | ---------- | -------------- |
| PR        | なし       | スキップ       |
| main push | あり       | 実行           |

## 統合ポイント設計

### シャード分割

- Vitest `--shard=N/16` オプション使用
- テストファイルの均等分散はVitestが自動管理

### キャッシュ連携

1. **pnpm store**: `actions/setup-node`の`cache: pnpm`を活用
2. **shared build**: `actions/cache`で明示的にキャッシュ

### カバレッジ集約

1. 各シャードが`apps/desktop/coverage/`にカバレッジ出力
2. `actions/upload-artifact`でアーティファクトとしてアップロード
3. `coverage`ジョブで`actions/download-artifact`でマージ
4. `codecov/codecov-action`でCodecovにアップロード
