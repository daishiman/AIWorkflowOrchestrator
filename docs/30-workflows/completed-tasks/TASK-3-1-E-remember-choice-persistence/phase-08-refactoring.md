## 目的

TDDの「Refactor」フェーズとして、テストを維持しながらコードの品質を改善する。

## 背景

Phase 5で最小限の実装を行ったが、コードの可読性、保守性、パフォーマンスの観点で改善の余地がある可能性がある。テストが全てパスする状態を維持しながらリファクタリングを行う。

---

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: コード品質分析

**目的**: 現在のコードの品質問題を特定する

**実行手順**:

1. ESLintを実行して警告・エラーを確認:
   ```bash
   pnpm --filter @repo/desktop lint
   ```
2. 以下の観点でコードを分析:
   - 重複コードの有無
   - 長すぎる関数・クラス
   - 命名の適切性
   - コメントの必要性
3. 改善すべき箇所をリストアップ

**期待される成果物**:

- リファクタリング対象リスト

---

### タスク2: 命名・可読性改善

**目的**: 変数名・関数名・クラス名の可読性を改善する

**実行手順**:

1. 不明確な命名を特定
2. より意図が伝わる名前に変更
3. テストを実行して影響がないことを確認:
   ```bash
   pnpm --filter @repo/desktop test -- --grep "PermissionStore"
   ```

**期待される成果物**:

- 命名改善後のコード

---

### タスク3: 重複コード削除

**目的**: DRY原則に従い重複コードを削除する

**実行手順**:

1. 重複しているコードパターンを特定
2. 共通関数・メソッドに抽出
3. テストを実行して影響がないことを確認

**期待される成果物**:

- 重複削除後のコード

---

### タスク4: エラーハンドリング強化

**目的**: エラーハンドリングを適切に強化する

**実行手順**:

1. try-catchの配置を確認
2. エラーメッセージの適切性を確認
3. ログ出力の追加（必要に応じて）
4. テストを実行して影響がないことを確認

**期待される成果物**:

- エラーハンドリング強化後のコード

---

### タスク5: リファクタリング後のテスト確認

**目的**: リファクタリング後も全テストがパスすることを確認する

**実行手順**:

1. 全テストを実行:
   ```bash
   pnpm --filter @repo/desktop test -- --grep "PermissionStore"
   ```
2. 全テストがパスすることを確認
3. カバレッジが維持されていることを確認

**期待される成果物**:

- テスト実行結果（全パス確認）

## リファクタリング注意事項

**すべきこと**:

- テストを頻繁に実行して回帰を防ぐ
- 小さな変更を段階的に行う
- 変更の意図をコミットメッセージに記録

**避けるべきこと**:

- 機能追加（これはリファクタリングではない）
- テストなしでの大規模変更
- 過度な抽象化
