## 目的

実装完了後の全体的な品質・整合性を検証し、手動テストに進む前の最終確認を行う。受入基準（AC-1 ~ AC-5）の達成状況、セキュリティ維持、コード品質、テスト品質、既存機能への影響を多角的にレビューする。

## 背景

IPC ハンドラの二重登録バグ修正は Electron セキュリティモデルの中核部分に影響する変更である。修正が意図した動作を実現しつつ、既存機能やセキュリティに悪影響を与えていないことを最終確認する。

## 実行タスク

- タスク実行: 本Phaseで定義したタスクを上から順に実行し、結果を成果物に記録する。

### Task 1: 受入基準の達成確認

Phase 1 で定義した受入基準（AC-1 ~ AC-5）の達成状況を全て確認する。

#### AC-1: 二重登録例外の解消

- [ ] `app.on("activate")` イベントで `registerAllIpcHandlers()` を再実行した際に `"Attempted to register a second handler"` 例外が発生しないこと
- [ ] ハンドラの解除 → 再登録のシーケンスが正しく動作することがテストで検証されていること

#### AC-2: 新ウィンドウへの参照更新

- [ ] activate で作成された新ウィンドウで IPC 通信が動作すること
- [ ] ハンドラ内の `mainWindow` 参照が新しいウィンドウを指していること
- [ ] `mainWindow.webContents.send()` が新しいウィンドウに送信されること

#### AC-3: 初回起動フローの維持

- [ ] 初回起動時に `registerAllIpcHandlers()` が1回だけ呼ばれること
- [ ] 全チャンネルのハンドラが正常に登録されること

#### AC-4: 全プラットフォーム互換性

- [ ] Windows / Linux で既存の動作に影響がないこと（`window-all-closed` で `app.quit()` が呼ばれる動作が維持）
- [ ] macOS での activate イベントハンドリングが正常に動作すること

#### AC-5: セキュリティ維持

- [ ] ホワイトリストに含まれないチャンネルでのリクエストが拒否されること
- [ ] 4層防御の各レイヤーが機能していること

### Task 2: セキュリティ検証

#### 4層防御の維持確認

| 層  | 防御名             | 検証内容                                                                       | 結果 |
| --- | ------------------ | ------------------------------------------------------------------------------ | ---- |
| L1  | ホワイトリスト     | `apps/desktop/src/preload/channels.ts` のチャンネル定義が改変されていないこと  | -    |
| L2  | Sender検証         | 全ハンドラで `event.senderFrame.url` の送信元検証が維持されていること          | -    |
| L3  | 引数バリデーション | パストラバーサル攻撃を含む引数検証が全ハンドラで維持されていること             | -    |
| L4  | エラーサニタイズ   | エラーレスポンスにスタックトレース・ファイルパス・API キーが含まれていないこと | -    |

#### IPC_CHANNELS 定数の一元管理確認

- [ ] 全チャンネル名が `IPC_CHANNELS` 定数経由で参照されていること
- [ ] ハードコード文字列でのチャンネル名指定が存在しないこと

### Task 3: コード品質検証

- [ ] `any` 型が使用されていないこと
- [ ] `@ts-ignore` / `@ts-expect-error` が使用されていないこと（使用する場合は理由コメント必須）
- [ ] 型アサーション（`as`）が不必要に使用されていないこと
- [ ] DRY 原則が遵守されていること（コードの重複が排除されている）
- [ ] 単一責務原則（SRP）が遵守されていること（各関数が1つの責務のみ持つ）
- [ ] 命名規則が統一されていること（boolean は `is`/`has`/`can`/`should` プレフィックス）
- [ ] 未使用の import が存在しないこと

### Task 4: テスト品質検証

#### カバレッジ基準

| 指標              | 最低基準 | 推奨基準 | 達成値 |
| ----------------- | -------- | -------- | ------ |
| Line Coverage     | 80%      | 90%      | -      |
| Branch Coverage   | 60%      | 70%      | -      |
| Function Coverage | 80%      | 90%      | -      |

#### エッジケースの網羅

- [ ] 同一チャンネルへの二重登録が防止されることのテスト
- [ ] `unregisterAllIpcHandlers()` 後に `registerAllIpcHandlers()` が成功することのテスト
- [ ] `BrowserWindow.getAllWindows().length === 0` 条件のテスト
- [ ] `BrowserWindow.getAllWindows().length > 0`（ウィンドウが存在する場合に再登録しない）のテスト
- [ ] `ipcMain.handle()` と `ipcMain.on()` の両方のハンドラ種別に対する解除テスト
- [ ] テスト間で状態がリークしていないこと（`beforeEach` でリセット）

### Task 5: 既存機能への影響確認

- [ ] 既存 IPC テストが全て PASS していること
- [ ] 他の IPC 機能（ファイル操作、認証、LLM 通信、スキル管理等）に副作用がないこと
- [ ] `registerAllIpcHandlers()` の呼び出しシグネチャが変更されていないこと（変更された場合は呼び出し元が全て更新されていること）
- [ ] 初回起動時のハンドラ登録フローが変更されていないこと

| 判定     | 条件                                                     | 対応                                                            |
| -------- | -------------------------------------------------------- | --------------------------------------------------------------- |
| PASS     | 全レビュー観点で問題なし                                 | Phase 11 へ進む                                                 |
