# Phase 3: 設計レビューゲート - IPC ハンドラ二重登録バグ修正

## メタ情報

| 項目         | 値                                |
| ------------ | --------------------------------- |
| Phase        | 3                                 |
| タスクID     | UT-FIX-IPC-HANDLER-DOUBLE-REG-001 |
| タスク名     | IPC ハンドラ二重登録例外の修正    |
| 機能名       | UT-FIX-IPC-HANDLER-DOUBLE-REG-001 |
| 種別         | バグ修正 (fix)                    |
| GitHub Issue | #815                              |
| 関連Pitfall  | P5（リスナー二重登録）            |
| 作成日       | 2026-02-14                        |

## 目的

Phase 2 で設計した A案（既存ハンドラ削除後に再登録）の妥当性を検証し、Phase 4（テスト作成）以降への進行可否を判定する。

## 実行タスク

- レビュー実施: Phase 2設計の妥当性を観点別に査読する。
- 判定実施: PASS/MINOR/MAJORを根拠付きで確定する。
- フィードバック化: MINOR以上の指摘を未タスク化可否まで整理する。

## 判定基準

| 判定  | 条件                                           | 対応                                          |
| ----- | ---------------------------------------------- | --------------------------------------------- |
| PASS  | 全レビュー観点で問題なし                       | Phase 4 へ進行                                |
| MINOR | 軽微な指摘あり（機能・セキュリティに影響なし） | 指摘対応後 Phase 4 へ進行（未タスク化が必要） |
| MAJOR | 要件未充足またはセキュリティ問題あり           | Phase 1 または Phase 2 へ戻り再設計           |

## レビュー観点

### 1. セキュリティ: 4層防御の維持

| チェック項目                                                                                        | 確認結果 |
| --------------------------------------------------------------------------------------------------- | -------- |
| L1（ホワイトリスト）: `IPC_CHANNELS` 定数が変更されていないこと                                     | [ ]      |
| L2（Sender検証）: 各ハンドラ内の送信元検証ロジックが影響を受けないこと                              | [ ]      |
| L3（引数バリデーション）: 各ハンドラ内の引数バリデーションロジックが影響を受けないこと              | [ ]      |
| L4（エラーサニタイズ）: エラーレスポンスのサニタイズが維持されること                                | [ ]      |
| unregister → register の間にリクエストが処理された場合、フェイルセキュア（エラー返却）であること    | [ ]      |
| `unregisterAllIpcHandlers()` が `IPC_CHANNELS` に定義されていないチャンネルを除去しようとしないこと | [ ]      |

### 2. P5パターン: リスナー二重登録の既知パターンとの整合性

| チェック項目                                                                                      | 確認結果 |
| ------------------------------------------------------------------------------------------------- | -------- |
| P5（リスナー二重登録）の教訓が本設計に反映されていること                                          | [ ]      |
| `ipcMain.handle()` の二重登録が構造的に防止されていること（removeHandler 後に handle）            | [ ]      |
| `ipcMain.on()` の二重登録が構造的に防止されていること（removeAllListeners 後に on）               | [ ]      |
| `setupThemeWatcher()` の二重呼び出しリスクが分析されていること                                    | [ ]      |
| React StrictMode の二重実行は Renderer 側の問題であり、本修正の Main Process 側には影響しないこと | [ ]      |

### 3. mainWindow 参照: 新ウィンドウ作成後の参照更新保証

| チェック項目                                                                                             | 確認結果 |
| -------------------------------------------------------------------------------------------------------- | -------- |
| activate 後に新しい mainWindow が `registerAllIpcHandlers()` に渡されること                              | [ ]      |
| 新しい mainWindow がクロージャで各ハンドラにキャプチャされること                                         | [ ]      |
| 古い mainWindow への参照がハンドラ内に残らないこと（removeHandler で古いクロージャが破棄される）         | [ ]      |
| `mainWindowRef`（モジュールスコープ）が新しいウィンドウを指していること                                  | [ ]      |
| サービスオブジェクト（SkillService, AuthModeService 等）が再生成されるため、状態の初期化が適切であること | [ ]      |

### 4. 既存テストへの影響

| チェック項目                                                                | 確認結果 |
| --------------------------------------------------------------------------- | -------- |
| 既存の IPC ハンドラテストが変更不要であること                               | [ ]      |
| `registerAllIpcHandlers()` の既存テスト（存在する場合）が修正で壊れないこと | [ ]      |
| 新規追加の `unregisterAllIpcHandlers()` が独立してテスト可能であること      | [ ]      |
| テストモック構成（P21/P35: DI追加時のモック修正パターン）に影響がないこと   | [ ]      |

### 5. 要件との整合性

| チェック項目                                              | 確認結果 |
| --------------------------------------------------------- | -------- |
| FR-1.1: macOS で二重登録例外が解消されること              | [ ]      |
| FR-1.2: activate 後に IPC 通信が正常動作すること          | [ ]      |
| FR-1.3: 全ハンドラが新しい mainWindow 参照を使用すること  | [ ]      |
| FR-2.1: `ipcMain.handle()` の二重登録が防止されること     | [ ]      |
| FR-2.2: `ipcMain.on()` の二重登録が防止されること         | [ ]      |
| FR-2.3: 全チャンネルのハンドラが確実に解除されること      | [ ]      |
| NFR-1.1: 4層防御が維持されること                          | [ ]      |
| NFR-1.2: unregister中に未認証リクエストが処理されないこと | [ ]      |
| NFR-2.1: TypeScript コンパイルエラーがないこと            | [ ]      |
| NFR-3.1: Windows / Linux で既存動作に影響がないこと       | [ ]      |

### 6. IPC_CHANNELS 網羅性

| チェック項目                                                                              | 確認結果 |
| ----------------------------------------------------------------------------------------- | -------- |
| `IPC_CHANNELS` が `registerAllIpcHandlers()` 内で使用される全チャンネルを網羅していること | [ ]      |
| ハードコード文字列でチャンネル名を直接指定しているハンドラがないこと（P27確認）           | [ ]      |
| `registerAuthFallbackHandlers()` のチャンネルも `IPC_CHANNELS` に含まれていること         | [ ]      |

### 7. エッジケース

| チェック項目                                                                                | 確認結果 |
| ------------------------------------------------------------------------------------------- | -------- |
| activate が短時間に連続で発火した場合に安全であること                                       | [ ]      |
| 条件分岐ハンドラ（Auth/AuthFallback）が正しく解除・再登録されること                         | [ ]      |
| `setupThemeWatcher()` の二重呼び出しでリスナーが重複しないこと                              | [ ]      |
| `registerAllIpcHandlers()` 内でサービスオブジェクトが再生成される際のメモリリークがないこと | [ ]      |
