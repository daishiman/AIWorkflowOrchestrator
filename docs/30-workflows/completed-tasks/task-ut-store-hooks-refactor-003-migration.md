## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

UT-STORE-HOOKS-REFACTOR-001でP31（無限ループ問題）を解決するため、合成Hook（`useAuthModeStore()`, `useLLMStore()`, `useSkillStore()`）を非推奨とし、個別セレクタ（`useAuthMode()`, `useSetAuthMode()`等）を新設した。

Phase 8でSettingsViewとLLMSelectorPanelを個別セレクタに移行したが、他にも合成Hookを使用しているコンポーネントが存在する可能性がある。

### 1.2 問題点・課題

- 合成Hookは毎回新しいオブジェクトを返すため、`useEffect`の依存配列に含めると無限ループが発生する（P31）
- 合成Hookを使用しているコンポーネントはP31のリスクを抱えている
- コードベース内に2つのパターン（合成Hook vs 個別セレクタ）が混在すると保守性が低下

### 1.3 放置した場合の影響

- 合成Hook使用箇所でP31（無限ループ）が顕在化するリスク
- 新規開発者が誤って合成Hookパターンを模倣するリスク
- コードベースの一貫性低下
- 将来的なリファクタリングコストの増大

---

## 2. 何を達成するか（What）

### 2.1 目的

非推奨の合成Hook（`useAuthModeStore()`, `useLLMStore()`, `useSkillStore()`）を使用している全コンポーネントを、個別セレクタパターンに移行する。

### 2.2 最終ゴール

- 合成Hook使用箇所が0件になる
- 全コンポーネントが個別セレクタを使用している
- P31パターン（無限ループリスク）がコードベースから排除されている

### 2.3 スコープ

#### 含むもの

- `apps/desktop/src/renderer/` 配下の全コンポーネント調査
- 合成Hook使用箇所の個別セレクタへの移行
- 移行後の動作検証

#### 含まないもの

- 合成Hook自体の削除（将来的な削除は別タスク）
- Store Slice内部の変更
- テストファイル内の合成Hook使用（モック用途）

### 2.4 成果物

| 成果物                 | 説明                                   |
| ---------------------- | -------------------------------------- |
| 調査レポート           | 合成Hook使用箇所一覧                   |
| 移行済みコンポーネント | 個別セレクタに移行されたコンポーネント |
| テスト結果             | 移行後の全テストPASS証跡               |

## 3. どのように実行するか（How）

### 3.1 前提条件

- UT-STORE-HOOKS-REFACTOR-001が完了していること
- 個別セレクタが `store/index.ts` にエクスポートされていること

### 3.2 依存タスク

なし（単独で実行可能）

### 3.3 必要な知識

- Zustand セレクタパターン
- React useEffect依存配列の挙動
- P31（無限ループ問題）の理解
- プロジェクトのコンポーネント構成

### 3.4 推奨アプローチ

1. **調査フェーズ**: grepで合成Hook使用箇所を全て特定
2. **分析フェーズ**: 各使用箇所のP31リスクを評価
3. **移行フェーズ**: 優先度順に個別セレクタへ移行
4. **検証フェーズ**: 動作確認とテスト実行

## 3.5 実装課題と解決策（UT-STORE-HOOKS-REFACTOR-001からの学び）

UT-STORE-HOOKS-REFACTOR-001で苦戦した箇所のうち、UT-003（合成Hook移行）に関連するものを以下にまとめる。

| #   | 課題                                           | 問題                                                                                                                                          | 解決策                                                                                                                                                  | 参照                                                                        |
| --- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 1   | Zustand合成Hookの参照不安定性（P31の根本原因） | `useAuthModeStore()`等の合成Hookが毎回新しいオブジェクトを返す。そのオブジェクト内の関数を`useEffect`の依存配列に含めると無限ループが発生する | 個別セレクタ（`useAuthMode()`, `useSetAuthMode()`等）を使用する。Zustandのアクション関数は`set`/`get`がStore初期化時に1度だけ作られるため参照が安定する | `06-known-pitfalls.md` P31、`arch-state-management.md` 課題2                |
| 2   | useEffect依存配列の設計判断                    | 関数を依存配列に含めるべきか、空配列にすべきかの判断が難しい。ESLint `react-hooks/exhaustive-deps` ルールと競合する場合がある                 | **初期化処理（1回のみ実行）**: `useRef`でガードし空配列を使用。**反応的更新（依存変更時実行）**: 個別セレクタを使用し依存配列に含める                   | `documentation-changelog.md` 5.4、`arch-state-management.md` 課題4          |
| 3   | 移行時の段階的アプローチの重要性               | UT-STORE-HOOKS-REFACTOR-001では一度に全移行を試みず、Phase 8でSettingsViewとLLMSelectorPanelのみ移行した。残りをUT-003として切り出した        | 高リスク箇所（`useEffect`で依存配列に関数を含む箇所）を優先的に移行し、低リスク箇所は後回しにする                                                       | `patterns.md`「Zustand個別セレクタベース再設計パターン」の3フェーズ移行戦略 |
| 4   | ESLintキャッシュの誤検出                       | 移行後もESLintが古い警告を表示し続ける場合がある                                                                                              | `pnpm lint --cache false` でキャッシュを無効化して実行する                                                                                              | `documentation-changelog.md` 5.2                                            |

## 4. 実行手順

### Phase構成

| Phase | 名称 | 目的                     |
| ----- | ---- | ------------------------ |
| 1     | 調査 | 合成Hook使用箇所の特定   |
| 2     | 分析 | リスク評価と優先度決定   |
| 3     | 移行 | 個別セレクタへの移行実施 |
| 4     | 検証 | 動作確認とテスト実行     |

### Phase 1: 調査

#### 目的

合成Hook使用箇所を全て特定する

#### 手順

1. 以下のコマンドを実行して使用箇所を抽出:
   ```bash
   grep -rn "useAuthModeStore\|useLLMStore\|useSkillStore" apps/desktop/src/renderer/
   ```
2. 検出結果をファイル別・行番号別にリスト化
3. テストファイル（`.test.ts`, `.spec.ts`）を除外
4. 既に移行済みのファイル（SettingsView, LLMSelectorPanel）を除外

#### 成果物

合成Hook使用箇所一覧（ファイルパス、行番号、使用パターン）

#### 完了条件

- [ ] 全使用箇所がリスト化されている
- [ ] テストファイルが除外されている
- [ ] 移行済みファイルが除外されている

### Phase 2: 分析

#### 目的

各使用箇所のP31リスクを評価し、移行優先度を決定する

#### 手順

1. 各使用箇所で `useEffect` の依存配列を確認
2. P31リスク（無限ループ発生可能性）を評価:
   - **高リスク**: 合成Hookの関数を依存配列に含む
   - **中リスク**: 合成Hookの状態を依存配列に含む
   - **低リスク**: 依存配列なし or 空配列
3. 移行優先度を決定:
   - 高リスク → 即時対応
   - 中リスク → 計画的対応
   - 低リスク → 改善サイクルで対応

#### 成果物

リスク評価レポート（リスクレベル、優先度、推奨対応時期）

#### 完了条件

- [ ] 全使用箇所にリスクレベルが付与されている
- [ ] 移行優先度が決定されている

### Phase 3: 移行

#### 目的

優先度順に個別セレクタへ移行する

#### 手順

1. 高リスク箇所から順に移行
2. 移行パターン:

   ```typescript
   // Before（非推奨）
   const { mode, setMode } = useAuthModeStore();

   // After（推奨）
   const mode = useAuthMode();
   const setMode = useSetAuthMode();
   ```

3. `useEffect` 依存配列を確認・修正
4. 各ファイル移行後にTypeScriptエラーがないことを確認

#### 成果物

移行済みコンポーネント（コミット単位で管理）

#### 完了条件

- [ ] 全使用箇所が個別セレクタに移行されている
- [ ] TypeScriptエラーがない

### Phase 4: 検証

#### 目的

移行後の動作確認とテスト実行

#### 手順

1. `pnpm typecheck` 実行
2. `pnpm lint` 実行
3. `pnpm --filter @repo/desktop test` 実行
4. 手動で該当コンポーネントの動作確認

#### 成果物

検証完了レポート

#### 完了条件

- [ ] 全品質チェックがPASS
- [ ] 手動テストで問題なし

## 6. 検証方法

### テストケース

| ケース | 検証内容                                       |
| ------ | ---------------------------------------------- |
| TC-01  | grep検索で合成Hook使用が0件                    |
| TC-02  | 移行したコンポーネントで無限ループが発生しない |
| TC-03  | 全自動テストがPASS                             |
| TC-04  | 手動操作で該当画面が正常動作                   |

### 検証手順

1. grepで合成Hook使用箇所を再検索し0件であることを確認:
   ```bash
   grep -rn "useAuthModeStore\|useLLMStore\|useSkillStore" apps/desktop/src/renderer/ --include="*.tsx" --include="*.ts" | grep -v ".test." | grep -v ".spec."
   ```
2. アプリを起動し、移行したコンポーネントを含む画面を操作
3. DevToolsのConsoleで無限ループ（大量のログ出力）がないことを確認

## 9. 備考

### レビュー指摘の原文（該当する場合）

```
Phase 10最終レビュー改善提案:
「合成Hookを使用している他コンポーネントの移行 - 優先度: 中」
Phase 8でリファクタリングしたコンポーネント（SettingsView, LLMSelectorPanel）以外にも、
合成Hookを使用している箇所が存在する可能性があります。
これらを段階的に個別セレクタへ移行することで、コードベース全体の一貫性が向上します。
```

### 補足事項

- 調査結果によっては、移行対象が0件の可能性もある
- テストファイル内の合成Hook使用はモック用途のため移行対象外
- 合成Hook自体の削除は本タスクの対象外（@deprecatedコメント追加で十分）
