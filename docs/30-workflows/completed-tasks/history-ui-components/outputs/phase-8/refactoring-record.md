## リファクタリング方針

### TDD Refactorフェーズの原則

1. **テストは緑のまま** - 既存テストを壊さない
2. **小さな変更** - 一度に一つの変更
3. **振る舞いの保持** - 外部から見た動作は変えない
4. **過度な抽象化の回避** - YAGNI原則を遵守

## コードスメル分析結果

### 検出されたスメル

| スメル種別   | 場所                     | 深刻度 | 対応判断 |
| ------------ | ------------------------ | ------ | -------- |
| 重複コード   | formatDate (3箇所)       | 低     | 保留     |
| 重複コード   | formatSize (2箇所)       | 低     | 保留     |
| 重複コード   | getLogLevelStyle (2箇所) | 低     | 保留     |
| 類似構造     | LoadingSkeleton          | 低     | 保留     |
| 類似構造     | ErrorDisplay             | 低     | 保留     |
| 類似パターン | ページネーションロジック | 低     | 保留     |

### 保留理由

1. **影響範囲が限定的**
   - 重複は履歴関連コンポーネント内のみ
   - 他モジュールへの影響なし

2. **変更頻度が低い**
   - 日付/サイズフォーマットは安定した機能
   - 変更による追加テストが必要になる

3. **抽象化のコスト > メリット**
   - 新規ファイル作成とimport変更が必要
   - テスト修正が必要
   - 2-3箇所の重複であれば許容範囲

4. **YAGNI原則**
   - 現時点で問題が発生していない
   - 将来的に共通化が必要になった時点で対応
