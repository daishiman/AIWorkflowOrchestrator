## 1. 実装スコープ

### 1.1 スコープ内（In Scope）

#### データベーススキーマ

| 項目                 | 説明                                          |
| -------------------- | --------------------------------------------- |
| embeddingsテーブル   | 埋め込みベクトルを保存するDrizzle ORMスキーマ |

| 項目                 | 説明                                             |

## 2. 技術的制約

### 2.1 libSQL/Turso制約

| 制約               | 詳細                                        |
| ------------------ | ------------------------------------------- |
| ベクトル次元数上限 | 最大2048次元（実用的には1536次元推奨）      |
| インデックス構築   | データ追加後にrebuildが必要な場合がある     |
| API安定性          | ベクトル機能は比較的新しく、API変更の可能性 |
| 専用関数           | vector_distance_cos等はlibSQL固有           |

### 2.2 パフォーマンス制約

| 制約                            | 詳細                                     |
| ------------------------------- | ---------------------------------------- |
| 小規模データ (< 10,000件)       | < 50ms目標、インデックス不要でも動作可能 |
| 中規模データ (10,000-100,000件) | < 100ms目標、インデックス推奨            |
| 大規模データ (> 100,000件)      | < 200ms目標、インデックス必須            |
| バッチサイズ                    | 100件/バッチで処理（メモリ効率考慮）     |

### 2.3 データ型制約

| 制約           | 詳細                                                |
| -------------- | --------------------------------------------------- |
| ベクトル形式   | Float32Arrayのみ対応                                |
| ストレージ形式 | BLOB (Buffer)                                       |
| 次元数         | デフォルト1536次元（OpenAI text-embedding-3-small） |
| 正規化         | コサイン類似度使用時は正規化推奨                    |

## 6. 実装方針

### 6.1 アーキテクチャ方針

1. **Drizzle ORM準拠**: 既存のスキーマパターンに従う
2. **interfaces-rag整合**: EmbeddingEntity型との整合を維持
3. **libSQL依存の局所化**: ベクトル検索ロジックを分離してテスト可能に
4. **バッチ処理優先**: 大量データ対応のためバッチ処理を標準

### 6.2 テスト方針

1. **単体テスト**: 各関数の独立したテスト
2. **統合テスト**: chunks連携のテスト
3. **パフォーマンステスト**: データ規模別の検索速度テスト
4. **エッジケーステスト**: 境界値、エラーケースのテスト

### 6.3 ドキュメント方針

1. **JSDoc**: 全パブリックAPIにコメント
2. **使用例**: 主要機能の使用例を提供
3. **マイグレーションガイド**: 実行手順と注意点
