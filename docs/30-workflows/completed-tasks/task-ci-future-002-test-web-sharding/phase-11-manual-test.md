## 実行手順

### ステップ1: ローカルシャード実行テスト

Web アプリケーションのテストをシャード分割して実行し、各シャードが独立して動作することを確認する。

```bash
# ベースライン計測（シャード化前の全テスト実行時間）
time pnpm --filter @repo/web test

# シャード1の実行確認
pnpm --filter @repo/web test -- --shard=1/2

# シャード2の実行確認
pnpm --filter @repo/web test -- --shard=2/2

# シャード数を変えた場合の確認（設計書のシャード数に合わせる）
pnpm --filter @repo/web test -- --shard=1/3
pnpm --filter @repo/web test -- --shard=2/3
pnpm --filter @repo/web test -- --shard=3/3
```

**確認ポイント**:

- [ ] 各シャードがエラーなく実行完了すること
- [ ] 全シャードのテスト合計数が、シャード化前のテスト総数と一致すること
- [ ] 各シャードの実行時間が、設計書の目標値（ベースライン ÷ シャード数 × 1.2 以内）に収まること

### ステップ2: 実行時間ベースライン比較

| 計測項目                 | 計測方法                            | 期待値                               |
| ------------------------ | ----------------------------------- | ------------------------------------ |
| ベースライン（全テスト） | `time pnpm --filter @repo/web test` | 記録のみ                             |
| シャード1 実行時間       | 各シャードを個別計測                | ベースライン ÷ シャード数 × 1.2 以内 |
| シャード2 実行時間       | 各シャードを個別計測                | ベースライン ÷ シャード数 × 1.2 以内 |

実行時間をメモしておき `outputs/phase-11/manual-test-result.md` に記録する。

### ステップ3: CI 実行確認

PR を作成して GitHub Actions が正しくシャード化されて実行されることを確認する。

```bash
# ブランチを作成してプッシュ
git checkout -b ci/TASK-CI-FUTURE-002-test-web-sharding
git push -u origin ci/TASK-CI-FUTURE-002-test-web-sharding
```

**GitHub Actions 確認手順**:

1. GitHub の Actions タブを開く
2. `test-web` ジョブが matrix として複数のシャードに分割されていることを確認する
3. 各シャードが並列実行されていることを確認する
4. 全シャードが PASS していることを確認する
5. 実行時間のサマリーを記録する

**確認シナリオ**:

| シナリオ                  | 確認手順                            | 期待結果                                 |
| ------------------------- | ----------------------------------- | ---------------------------------------- |
| test-web シャード分割確認 | Actions タブ → test-web ジョブ確認  | matrix として N 個のシャードが表示される |
| 全シャード PASS           | 各シャードのステータス確認          | 全てのシャードが green（PASS）           |
| 並列数上限確認            | 同時実行ジョブ数のカウント          | 合計 20 以内に収まる                     |
| 実行時間短縮確認          | シャード化後の wall clock time 確認 | ベースラインを上回らない                 |

### ステップ4: GitHub Free Tier 並列上限の遵守確認

現状の CI 並列数内訳を確認し、`test-web` シャード追加後も 20 以内であることを検証する。

```bash
# CI yml の並列数を確認
grep -n "shard:\|strategy:\|matrix:" .github/workflows/ci.yml
```

**並列数チェックリスト**:

| ジョブ       | 並列数（実装後）       | 備考                   |
| ------------ | ---------------------- | ---------------------- |
| test-desktop | （設計書の値）         | TASK-CI-OPT-001 の成果 |
| test-web     | （新規追加シャード数） | 本タスクの成果         |
| typecheck    | 1                      | 変更なし               |
| test-shared  | 1                      | 変更なし               |
| e2e-desktop  | 1                      | 変更なし               |
| **合計**     | **≤ 20**               | **必須条件**           |

- [ ] 合計並列数が 20 以内であることを確認済み

## 問題発見時の unassigned-task 生成フロー

CI 実行中やシャード確認中に予期しない問題が発見された場合、以下のフローで unassigned-task を生成する。

1. 問題を `discovered-issues.md` に記録する
2. 問題の重大度を判定する（CRITICAL / MAJOR / MINOR）
3. MAJOR 以上の場合は `docs/30-workflows/unassigned-task/` に正式な指示書を作成する
4. MINOR の場合は `discovered-issues.md` に記録して Phase 12 へ引き継ぐ

```bash
# unassigned-task ディレクトリへの記録例
ls docs/30-workflows/unassigned-task/
```

## 多角的チェック観点

| 観点             | 確認内容                                 | 判定基準                                  |
| ---------------- | ---------------------------------------- | ----------------------------------------- |
| 機能的正確性     | 各シャードが独立して全テストを実行できる | エラーなし・テスト数一致                  |
| パフォーマンス   | シャード化による実行時間短縮             | ベースラインを上回らない                  |
| スケーラビリティ | 並列数上限の遵守                         | 合計 ≤ 20                                 |
| 変更範囲         | CI 設定ファイルのみの変更                | `ci.yml` + 必要時 `vitest.config.ts` のみ |
| 後方互換性       | 既存ジョブへの影響なし                   | test-desktop 等の動作変化なし             |
