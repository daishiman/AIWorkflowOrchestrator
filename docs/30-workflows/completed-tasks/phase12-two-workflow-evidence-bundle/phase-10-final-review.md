## 目的

Phase 1〜9 の全成果物に対して、要件充足・設計準拠・テスト品質・ドキュメント品質・運用性・保守性の多角的レビューを実施し、Phase 11（手動テスト）に進行可能な品質水準であることを確定する。

## 実行手順

### Step 1: 要件充足確認

1. Phase 1 要件定義書（`outputs/phase-1/requirements-definition.md`）の全要件を一覧化する
2. 各要件に対応する実装箇所（テンプレート・手順・チェックリスト）を特定する
3. 以下の要件トレーサビリティマトリクスを作成する:

   | 要件ID | 要件内容 | 対応する実装ファイル | 対応するテスト | 充足判定 |
   | ------ | -------- | -------------------- | -------------- | -------- |

4. 未充足の要件がある場合、MAJOR 判定として Phase 1 または Phase 5 への差し戻しを記録する

### Step 2: 設計準拠確認

1. Phase 2 設計書（`outputs/phase-2/architecture-design.md`）の設計制約を一覧化する
2. 各設計制約に対して、実装が準拠しているか確認する:
   - テンプレート構造が設計書のフォーマット仕様に従っているか
   - チェックリスト項目が設計書の検証項目定義と一致しているか
   - 監査手順のフローが設計書のワークフロー定義と一致しているか
3. 逸脱がある場合、逸脱内容と影響範囲を記録する

### Step 3: テスト品質確認

1. Phase 9 品質レポート（`outputs/phase-9/quality-report.md`）を読み、以下を確認する:
   - 全テストが PASS しているか
   - カバレッジが基準を充足しているか（Line 80%, Branch 60%, Function 80%）
2. テストが要件を網羅しているか、要件トレーサビリティマトリクス（Step 1 で作成）と照合する
3. テストされていない要件がある場合、MINOR 指摘として記録する

### Step 4: ドキュメント品質確認

1. 証跡集約テンプレートの品質を以下の観点で確認する:
   - 曖昧語チェック対象（禁止語リスト3件）が含まれていないか
   - 完了条件がチェックリスト形式で検証可能か
   - 100人中100人が同じ理解で実行できる粒度で記述されているか
   - 参照パスが具体的なファイルパスで記載されているか
2. 不備がある場合、指摘内容と修正箇所を記録する

### Step 5: 多角的レビュー

以下の非機能要件観点でレビューを実施する:

#### 5-1: セキュリティ観点

- テンプレートに機密情報（APIキー・トークン・PII）が含まれていないか
- 監査手順で生成される成果物に機密情報が記録される可能性がないか

#### 5-2: 運用性観点

- テンプレートの実行手順が自動化可能か（手動入力が最小限か）
- 監査手順のエラーハンドリング（ファイル不在時・検証失敗時）が定義されているか

#### 5-3: 保守性観点

- テンプレートの拡張ポイント（新規チェック項目の追加箇所）が明確か
- ワークフロー変更時の影響範囲が局所化されているか

### Step 6: レビュー判定

1. Step 1〜5 の全指摘を集約する
2. 以下の判定基準に従い、レビュー判定を行う:

   | 判定     | 基準                                                     | 対応                                                            |
   | -------- | -------------------------------------------------------- | --------------------------------------------------------------- |
   | PASS     | 指摘なし、または改善提案のみ                             | Phase 11 へ進行する                                             |
   | MINOR    | 機能に影響しない品質改善指摘がある                       | 全指摘を未タスク仕様書に変換後、Phase 11 へ進行する（省略不可） |
   | MAJOR    | 要件未充足または設計逸脱がある                           | 影響範囲に応じて Phase 1 / Phase 2 / Phase 5 へ戻る             |
   | CRITICAL | 要件の根本的な誤りまたはセキュリティ上の重大な問題がある | Phase 1 へ戻り要件を再確認する                                  |

3. MINOR 指摘がある場合:
   - 各 MINOR 指摘に対して未タスク仕様書（`tasks/unassigned-task/` 配下）を作成する
   - `task-workflow.md` の残課題テーブルに登録する
   - 関連仕様書に参照リンクを追加する
   - 上記3ステップを全指摘に対して完了してから Phase 11 へ進行する

4. レビュー結果を `outputs/phase-10/final-review-result.md` に記録する

| 観点             | 確認内容                                               | 判定基準                         |
| ---------------- | ------------------------------------------------------ | -------------------------------- |
| 要件充足         | Phase 1 の全要件が実装に反映されているか               | 未充足要件 = 0                   |
| 設計準拠         | Phase 2 の設計制約に逸脱がないか                       | 逸脱 = 0                         |
