### タスク 2: 重複コードの確認

**目的**: `signal?.aborted` チェックが複数箇所で重複していないかを確認する

**確認手順**:

1. `agentSlice.ts` 内で `signal?.aborted` または類似するパターンを検索する

```bash
grep -n "signal.*aborted\|aborted.*signal" \
  apps/desktop/src/renderer/store/slices/agentSlice.ts
```

2. 重複が3箇所以上あり、同一パターンであればヘルパー化を検討する

**判断基準**:

| 観点       | ヘルパー化する条件                       |
| ---------- | ---------------------------------------- |
| 重複箇所数 | 3箇所以上で同一パターンが繰り返される    |
| 保守性     | 変更時に複数箇所を同時修正する必要がある |
| 可読性     | 抽出後のコードが明らかに読みやすくなる   |

**本タスクでの予想**:
`createSkill` への `signal` 追加は1〜2箇所の変更であり、重複は発生しないと予想される。
ヘルパー化不要の場合は、その判断理由を `refactoring-log.md` に記録する。

---

### タスク 3: 変数名・コメントの整合性確認

**目的**: 追加した変数名やコメントがプロジェクト全体の命名規約と一致しているか確認する

**確認観点**:

| 観点             | 確認内容                                                               |
| ---------------- | ---------------------------------------------------------------------- |
| 変数名           | `signal` はプロジェクト内の他の AbortSignal 変数と命名が一致しているか |
| JSDoc コメント   | `@param signal` の説明がプロジェクトの既存パターンと一致しているか     |
| 引数順序の一貫性 | 他の関数で `signal` が最後のオプショナル引数として配置されているか     |

**参照すべき既存パターン**:

```bash
# プロジェクト内の AbortSignal 引数パターンを確認
grep -rn "signal.*AbortSignal\|AbortSignal.*signal" \
  apps/desktop/src/ --include="*.ts" | head -20
```

### タスク 4: リファクタリング後のテスト継続確認

**目的**: リファクタリング（コメント修正・変数名修正等）後も全テストが PASS することを確認する

**実行手順**:

1. 全テストを実行する

```bash
pnpm --filter @repo/desktop test
```

2. 全テストが PASS することを確認する
3. リファクタリング前後で振る舞いが変わっていないことを確認する
