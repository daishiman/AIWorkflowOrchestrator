## 実行手順

### Task 1: セキュリティ観点レビュー

以下の観点でPhase 2の設計を検証する:

| 観点                                 | 確認事項                                                                                                                                                                                                   | 判定基準                                              |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| PKCE実装のRFC 7636準拠               | code_verifierが43-128文字のBase64URL文字列、code_challengeがSHA-256ハッシュ                                                                                                                                | RFC 7636 Section 4.1/4.2に完全準拠していること        |
| State parameterのエントロピー        | crypto.randomBytes(32)以上で生成されているか                                                                                                                                                               | 32バイト以上のランダム文字列であること                |
| HTTPサーバーのバインドアドレス制限   | 127.0.0.1のみでリッスンする設計か                                                                                                                                                                          | 外部ネットワークからのアクセスが不可能であること      |
| トークンのRenderer非露出             | Access Token/Refresh TokenがMain Processに留まる設計か                                                                                                                                                     | Renderer ProcessにトークンがIPC経由で送信されないこと |
| safeStorage暗号化                    | Refresh Tokenの保存にsafeStorage.encryptString()が使用されるか                                                                                                                                             | 平文でのトークン保存がないこと                        |
| 使用済みstate/codeVerifierの削除     | 認証完了・エラー時に速やかに削除されるか                                                                                                                                                                   | メモリリークしないこと                                |
| security-principles.md 5原則への準拠 | 最小権限（127.0.0.1バインド）、多層防御（PKCE+State+safeStorage）、フェイルセキュア（暗号化不可時フォールバック）、完全な仲介（IPC検証）、経済的設計（不要なエンドポイント非公開）が設計に反映されているか | 5原則すべてが設計内で識別可能であること               |

### Task 2: プラットフォーム互換性レビュー

| 観点                       | 確認事項                                                  | 判定基準                                             |
| -------------------------- | --------------------------------------------------------- | ---------------------------------------------------- |
| macOSでの動作              | open-urlイベントによるカスタムURLスキーム受信設計         | macOS固有のイベントハンドリングが設計されていること  |
| Windowsでの動作            | second-instanceイベントによるDeep Link受信設計            | Windows固有のsingle instanceパターンが設計されている |
| Linuxでの動作              | HTTPサーバーフォールバックが確実に動作する設計            | カスタムURLスキーム非対応環境でもHTTPサーバーで動作  |
| 開発ビルドでの動作         | `pnpm --filter @repo/desktop dev`でPKCE認証が動作する設計 | パッケージ化不要で認証フローが完結する設計であること |
| shell.openExternalの互換性 | 各プラットフォームでブラウザが開く設計                    | OS標準ブラウザが正しく起動されること                 |

### Task 3: エラーハンドリングレビュー

| 観点                     | 確認事項                                                | 判定基準                                             |
| ------------------------ | ------------------------------------------------------- | ---------------------------------------------------- |
| HTTPサーバータイムアウト | 5分のタイムアウト後にサーバーが自動停止・クリーンアップ | リソースリークなく正常終了する設計であること         |
| ネットワークエラー       | OAuth URLアクセス不可時の処理フロー                     | ユーザーにエラー情報が通知される設計であること       |
| ポート競合               | 動的ポート割り当て失敗時のフォールバック                | リトライまたは代替手段が設計されていること           |
| OAuthエラー              | プロバイダーからのエラーレスポンス処理                  | error/error_descriptionのパース・ユーザー通知        |
| State不一致              | コールバックのstateが保存値と不一致時の拒否処理         | 認証が明確に拒否されエラーが通知される設計であること |
| 同時認証リクエスト       | 複数のOAuth認証が同時に開始された場合の処理             | 既存フローのキャンセルまたは排他制御が設計されている |
| 暗号化不可環境           | safeStorageが利用不可の場合のフォールバック             | NFR-008に基づき警告表示しつつ認証を継続する設計      |

### Task 4: アーキテクチャレビュー

| 観点                   | 確認事項                                                                   | 判定基準                                                             |
| ---------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Main Processの責務     | PKCE生成・HTTPサーバー・トークン交換・暗号化がMain Processに閉じるか       | セキュリティ上重要な処理がMain Processに集約                         |
| Preloadの責務          | safeInvoke/safeOnラッパーによるIPC API公開のみか                           | Preloadが必要最小限のAPI公開に留まっていること                       |
| Renderer Processの責務 | 認証状態表示・ログインボタン・エラー表示のみか                             | トークン操作等がRenderer側に漏れていないこと                         |
| IPC設計の妥当性        | 新規チャネルがホワイトリストに追加され、型安全なinvoke/onパターンか        | 既存IPC規約（safeInvoke/safeOn）に準拠していること                   |
| Shared Packageの責務   | IPCチャネル定数・型定義がShared Packageに配置されるか                      | packages/sharedでの一元管理が設計されていること                      |
| IPCチャネル命名規約    | 新規チャネル名がapi-ipc-auth.mdの既存パターン（auth:動詞形）に従っているか | 命名が既存規約と一貫していること、または逸脱理由が記録されていること |

### Task 5: 既存実装との互換性レビュー

| 観点                       | 確認事項                                                                                        | 判定基準                                           |
| -------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| OAuthエラー検出の維持      | TASK-FIX-GOOGLE-LOGIN-001で追加されたoauth-error-handler.tsが引き続き動作                       | エラー検出・マッピング機能が破壊されないこと       |
| 認証状態管理の互換性       | authSlice.tsの既存インターフェースが維持されるか                                                | AUTH_STATE_CHANGED通知パターンが変更されないこと   |
| カスタムプロトコルの互換性 | customProtocol.tsの既存`aiworkflow://auth/callback#...`処理が残るか                             | フォールバックとして既存処理が維持されること       |
| devMockAuth.tsの復元       | `return true;`削除後に開発環境で実際の認証フローが使用される設計か                              | 開発ビルドでHTTPサーバー経由の認証が動作すること   |
| リスナー二重登録防止の維持 | authSlice.ts内のauthListenerRegisteredフラグとresetAuthListenerFlag()テスト用関数が維持されるか | PKCEフロー移行後もリスナー二重登録が防止されること |
