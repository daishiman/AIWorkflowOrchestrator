# Phase 3: 設計レビューゲート

## メタ情報

| 項目      | 内容                                                             |
| --------- | ---------------------------------------------------------------- |
| タスクID  | UT-IMP-SKILL-VALIDATION-GATE-ALIGNMENT-001                       |
| Phase     | 3                                                                |
| 名称      | 設計レビューゲート                                               |
| 目的      | Phase 1-2 の要件・設計の妥当性を多角的に検証し、ゲート判定を行う |
| 前提Phase | Phase 1（要件定義）および Phase 2（設計）完了                    |
| 次Phase   | Phase 4（テスト作成）                                            |

## 目的

Phase 1 の要件定義と Phase 2 の設計が整合しているか、実行可能か、品質基準を満たすかを検証する。ゲート判定（PASS / MINOR / MAJOR）に基づいて次のアクションを決定する。

## 実行タスク

- 要件-設計トレーサビリティの検証: FR/NFR と設計項目の対応を確認する
- 設計の実行可能性レビュー: 手順・コマンド・差分定義の実行可能性を確認する
- Warning 分類ルールの妥当性レビュー: 3段階分類と判定フローの再現性を確認する
- 仕様書変更設計の整合性レビュー: `spec-update-workflow.md` と `phase-11-12-guide.md` の変更計画を検証する
- ゲート判定の実施: PASS / MINOR / MAJOR を根拠付きで判定する
- レビュー結果レポートの作成: 判定結果と是正アクションを成果物に記録する

## レビューゲート判定基準

| 判定              | 条件                                                             | 対応                             |
| ----------------- | ---------------------------------------------------------------- | -------------------------------- |
| PASS              | 全レビュー項目がOK、または軽微な文言修正のみ                     | Phase 4 に進む                   |
| MINOR             | 機能影響のない設計改善指摘が1件以上                              | 指摘対応後に Phase 4 に進む      |
| MAJOR（要件問題） | FR / NFR の定義不足、AC の検証方法が不明確                       | Phase 1 に戻って要件を再定義する |
| MAJOR（設計問題） | 設計が FR を充足していない、Warning 分類ルールが曖昧で再現不可能 | Phase 2 に戻って設計を修正する   |

## 実行手順

### Task 1: 要件-設計トレーサビリティの検証

1. Phase 2 設計書のトレーサビリティマトリクスを開く
2. 以下の各 FR について、設計でカバーされているか確認する:

   | FR-ID  | 要件概要                                   | 設計カバー確認                                                   | 判定 |
   | ------ | ------------------------------------------ | ---------------------------------------------------------------- | ---- |
   | FR-001 | `quick_validate.js` を正規経路に指定       | Task 1 の primary 経路定義に含まれているか                       | -    |
   | FR-002 | `.py` を fallback に限定                   | Task 1 の fallback 使用条件に含まれているか                      | -    |
   | FR-003 | `spec-update-workflow.md` を正規経路に統一 | Task 3 の変更設計（Before/After）に含まれているか                | -    |
   | FR-004 | `phase-11-12-guide.md` を正規経路に統一    | Task 4 の変更設計に含まれているか                                | -    |
   | FR-005 | Warning 3段階分類ルールを定義              | Task 2 の分類テーブル・判定フローに含まれているか                | -    |
   | FR-006 | 判定基準を明文化                           | Task 3 の Warning 運用ルール挿入設計に含まれているか             | -    |
   | FR-007 | `aiworkflow-requirements` の許容条件を定義 | Task 2 の `aiworkflow-requirements` 固有許容条件に含まれているか | -    |

3. 各 NFR について、設計で考慮されているか確認する:

   | NFR-ID  | 要件概要 | 設計での考慮                                  | 判定 |
   | ------- | -------- | --------------------------------------------- | ---- |
   | NFR-001 | 再現性   | 同一コマンドで同一結果が出る設計か            | -    |
   | NFR-002 | 可読性   | Error / Warning / Pass が識別可能な出力設計か | -    |
   | NFR-003 | 保守性   | ルール追加が1ファイルで完結する設計か         | -    |
   | NFR-004 | 実行速度 | 30秒以内の制約に影響する変更がないか          | -    |
   | NFR-005 | 後方互換 | 既存 Error 判定を変更しない設計か             | -    |

4. カバー漏れが1件でもある場合、「MAJOR（設計問題）」とし、漏れの内容を記録する

### Task 2: 設計の実行可能性レビュー

1. Phase 2 設計書の各 Task 実行手順が、以下の基準を満たすか確認する:

   | 確認項目                  | 判定基準                                                                       | 判定 |
   | ------------------------- | ------------------------------------------------------------------------------ | ---- |
   | コマンドの実行可能性      | 記載されたコマンドがそのまま実行できるか（パス・引数が正確か）                 | -    |
   | 変更対象ファイルの特定    | 変更するファイルパスが明示されているか                                         | -    |
   | Before/After 差分の明確さ | 変更前後が具体的に記載され、差分が1行単位で特定できるか                        | -    |
   | 判定フローの再現性        | 判定フロー図のどの分岐にも曖昧表現（「基準どおりに」「条件該当時に」）がないか | -    |
   | 改善案の比較基準          | 推奨案の選定根拠が定量的か（コスト / 効果 / リスク）                           | -    |

2. 実行不可能な手順がある場合、具体的な修正指示を記録する

### Task 3: Warning 分類ルールの妥当性レビュー

1. Phase 2 Task 2 の Warning 3段階分類ルールを検証する:

   | 検証項目                                                | 判定基準                                                                                      | 判定 |
   | ------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ---- |
   | 3段階（許容 / 要監視 / 要対応）の定義が重複なく網羅的か | どの Warning も必ず1つの分類に該当し、2つ以上には該当しないか                                 | -    |
   | 具体例が各分類に1つ以上含まれているか                   | 具体例が抽象的でなく、`quick_validate.js` の実際の Warning 出力と対応するか                   | -    |
   | 判定フローの分岐条件が二値（YES/NO）で判断可能か        | 分岐条件に主観的な判断（「重要な」「大きい」）が含まれていないか                              | -    |
   | `aiworkflow-requirements` 固有の許容条件が検証可能か    | 許容条件を機械的に判定できるか（`resource-map.md` / `topic-map.md` のリンク有無で判定可能か） | -    |

2. 分類ルールの再現性テスト:
   - Phase 1 Task 1 で記録した `.js` の Warning 出力から任意の3件を選び、判定フローに従って分類する
   - 分類結果が一意に決定できない Warning がある場合、判定フローの改善指摘とする

### Task 4: 仕様書変更設計の整合性レビュー

1. `spec-update-workflow.md` の変更設計を検証する:

   | 検証項目                                                         | 判定基準                                                                         | 判定 |
   | ---------------------------------------------------------------- | -------------------------------------------------------------------------------- | ---- |
   | Before/After 差分が `spec-update-workflow.md` の現状と一致するか | Before が実ファイルの記載と一致するか確認する                                    | -    |
   | `.py` 参照の全置換箇所が網羅されているか                         | `grep -c "quick_validate.py" spec-update-workflow.md` の件数分の置換設計があるか | -    |
   | Warning 運用ルールの挿入位置が適切か                             | Step 1-G の検証コマンド直後に位置し、検証→判定の流れが自然か                     | -    |

2. `phase-11-12-guide.md` の変更設計を検証する:

   | 検証項目                                             | 判定基準                                                              | 判定 |
   | ---------------------------------------------------- | --------------------------------------------------------------------- | ---- |
   | `spec-update-workflow.md` との重複が排除されているか | コマンド全文は `spec-update-workflow.md` に集約され、参照リンクのみか | -    |
   | 参照リンクが正しいパスを指しているか                 | `spec-update-workflow.md` のセクション名が正確に指定されているか      | -    |
   | 検証結果の読み方ガイドが追加されているか             | Error / Warning の識別方法が Phase 12 実行者向けに記載されているか    | -    |

### Task 5: ゲート判定の実施

1. Task 1-4 の全判定結果を集計する
2. 以下の判定ルールに従い、ゲート判定を決定する:

   | 集計結果                                      | ゲート判定        |
   | --------------------------------------------- | ----------------- |
   | 全項目 OK                                     | PASS              |
   | NG 項目が文言修正・フォーマット改善のみ       | MINOR             |
   | FR/NFR カバー漏れ、または判定フローに曖昧表現 | MAJOR（設計問題） |
   | FR/NFR 自体の定義不足、AC の検証方法不明確    | MAJOR（要件問題） |

3. MINOR 判定の場合:
   - 指摘内容を一覧化する
   - 対応方針（即時修正 / 次Phase持ち越し不可）を記載する
   - 指摘対応後、Phase 4 に進む

4. MAJOR 判定の場合:
   - 差し戻し先（Phase 1 / Phase 2）を明記する
   - 差し戻し理由と修正に必要な情報を記載する
   - 差し戻し先の Phase を再実行する

### Task 6: レビュー結果レポートの作成

1. `outputs/phase-3/design-review-report.md` を作成する
2. 以下の構成で記載する:
   - レビュー日時
   - Task 1: トレーサビリティ検証結果（FR / NFR 各項目の判定）
   - Task 2: 実行可能性レビュー結果（各確認項目の判定）
   - Task 3: Warning 分類ルール妥当性結果（再現性テスト含む）
   - Task 4: 仕様書変更設計整合性結果
   - ゲート判定: PASS / MINOR / MAJOR
   - 指摘事項一覧（該当する場合）
   - 次のアクション

## 統合テスト連携

- Phase 4 のテストケース設計が、本 Phase で確認した全 AC をカバーしているか確認する
- Warning 分類ルールの再現性テスト結果を Phase 4 のテスト設計にフィードバックする

## 多角的チェック観点

| 観点           | 適用判断 | 理由                                                                              |
| -------------- | -------- | --------------------------------------------------------------------------------- |
| セキュリティ   | 非該当   | 検証スクリプトは読み取り専用であり、セキュリティ影響がない                        |
| UI/UX          | 非該当   | ユーザー向けUIの変更を含まない                                                    |
| アーキテクチャ | 該当     | primary / fallback の2経路設計が本タスクのスコープ内で完結するか確認する          |
| API設計        | 非該当   | IPC / REST API の変更を含まない                                                   |
| IPC通信        | 非該当   | Main-Renderer間通信の変更を含まない                                               |
| 仕様書品質     | 該当     | 変更設計の Before/After が正確であること、重複排除が適切であることを確認する      |
| テスト戦略     | 該当     | Warning 分類ルールの再現性テストが Phase 4 設計への入力となる                     |
| 運用保守性     | 該当     | 判定フローが運用者にとって再現可能か、主観的判断が含まれていないか確認する        |
| スコープ遵守   | 該当     | 設計内容がタスクスコープ（index.md の「含まないもの」）を逸脱していないか確認する |
