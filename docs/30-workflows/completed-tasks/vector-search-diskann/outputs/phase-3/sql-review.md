## 2. クエリパフォーマンスレビュー

### 2.1 インデックス利用

**設計クエリ**:

```sql
SELECT ...
FROM embeddings e
INNER JOIN chunks c ON e.chunk_id = c.id
WHERE ...
ORDER BY distance ASC
LIMIT {limit}
```

| 確認項目               | 状態  | 備考                             |
| ---------------------- | ----- | -------------------------------- |
| DiskANNインデックス    | ✅ OK | vector_distance_cos()で自動使用  |
| chunks.id インデックス | ✅ OK | PRIMARY KEY                      |
| embeddings.chunk_id FK | ✅ OK | 外部キー制約で暗黙的インデックス |
| ORDER BY最適化         | ✅ OK | distance ASCはインデックスソート |

**判定**: ✅ PASS

---

### 2.2 JOINの必要性

| JOIN               | 必要性      | 理由                                  |
| ------------------ | ----------- | ------------------------------------- |
| chunks ON chunk_id | ✅ 必要     | content, contextual_content取得のため |
| files ON file_id   | ⚠️ 条件付き | fileIdsフィルター時のみ必要だが省略可 |

**最適化確認**:

- filesテーブルへのJOINは不要（chunks.file_idで直接フィルタ可能）
- 既存設計で最適化済み

**判定**: ✅ PASS

---

### 2.3 不要な処理の排除

| 確認項目           | 状態  | 備考                       |
| ------------------ | ----- | -------------------------- |
| SELECT句のカラム数 | ✅ OK | 必要なカラムのみ選択       |
| WHERE句の条件      | ✅ OK | フィルタがある場合のみ追加 |
| サブクエリなし     | ✅ OK | 単純なJOINのみ             |

**判定**: ✅ PASS

### 3.2 limit境界値

| ケース      | 期待動作      | 設計での対応                    |
| ----------- | ------------- | ------------------------------- |
| limit = 0   | エラーを返す  | ⚠️ バリデーションで弾く必要あり |
| limit = 1   | 1件返す       | ✅ 正常動作                     |
| limit = 100 | 最大100件返す | ✅ 正常動作                     |
| limit > 100 | エラーを返す  | ✅ バリデーションで弾く         |

**確認**: `validateInput()` で `limit < 1 || limit > 100` をチェック

**判定**: ✅ PASS
