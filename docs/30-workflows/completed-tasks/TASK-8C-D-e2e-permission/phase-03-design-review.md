## 目的

Phase 2 で作成した設計が実装可能であり、既存アーキテクチャ・テストパターンと整合しているかをレビューする。問題があれば Phase 2 へ差し戻す。

## 背景

E2Eテストは実行コストが高く、フレーキーテストのリスクもある。設計段階で問題を検出し、実装後の手戻りを防ぐ。

---

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: アーキテクチャ整合性レビュー

**目的**: 設計が既存アーキテクチャと整合しているか確認する

**実行手順**:

1. E2Eテスト設定との整合性確認
   - `vite.e2e.config.ts` の設定と設計が一致しているか
   - `VITE_E2E_MODE` 環境変数の利用方針が適切か

2. フィクスチャ利用方針の確認
   - `test-skill` フィクスチャが権限テストに適しているか
   - allowedTools 設定で権限確認がトリガーされる条件が明確か

3. 既存E2Eテストとの一貫性確認
   - TASK-8C-B, TASK-8C-C のE2Eテストと同様のパターンを使用しているか

**レビュー基準**:

| 基準               | PASS条件                                |
| ------------------ | --------------------------------------- |
| 設定整合性         | vite.e2e.config.ts と設計が一致         |
| フィクスチャ適合性 | test-skill が権限テストに使用可能       |
| パターン一貫性     | 他のE2Eテストと同様のライフサイクル管理 |

**期待される成果物**:

- `outputs/phase-3/architecture-review.md`: アーキテクチャレビュー結果

---

### タスク2: テストケースレビュー

**目的**: テストケース設計が要件を網羅しているか確認する

**実行手順**:

1. 要件トレーサビリティ確認

   | 要件（Phase 1）    | テストケース（Phase 2） | カバー状況 |
   | ------------------ | ----------------------- | ---------- |
   | 権限ダイアログ表示 | TC-1                    | 確認       |
   | ツール情報表示     | TC-2                    | 確認       |
   | 許可して続行       | TC-3                    | 確認       |
   | 拒否して停止       | TC-4                    | 確認       |
   | 選択記憶           | TC-5                    | 確認       |

2. エッジケース・異常系の検討
   - タイムアウト処理のテスト（元タスク仕様に記載あり）
   - 複数回連続の権限リクエスト

3. テストの独立性確認
   - 各テストが他のテストに依存せず実行可能か
   - 状態リセットが適切に設計されているか

**レビュー基準**:

| 基準           | PASS条件                                |
| -------------- | --------------------------------------- |
| 要件カバレッジ | 5件の要件が全てテストケースで検証される |
| エッジケース   | 主要なエッジケースが検討されている      |
| テスト独立性   | 各テストが独立して実行可能              |

**期待される成果物**:

- `outputs/phase-3/test-case-review.md`: テストケースレビュー結果

---

### タスク3: モック戦略レビュー

**目的**: モック戦略が実現可能で保守性が高いか確認する

**実行手順**:

1. モック実装の実現可能性確認
   - addInitScript でのモック注入が技術的に可能か
   - Permission イベントシミュレーションが可能か

2. モック保守性確認
   - モックが実装の変更に対して脆弱でないか
   - インターフェース変更時の影響範囲が限定的か

3. テスト信頼性確認
   - モックが実際の動作を適切に再現しているか
   - フォールスポジティブ/ネガティブのリスク

**レビュー基準**:

| 基準       | PASS条件                             |
| ---------- | ------------------------------------ |
| 実現可能性 | 技術的に実装可能なモック戦略         |
| 保守性     | インターフェース変更時の影響が限定的 |
| 信頼性     | 実動作と乖離しないモック設計         |

**期待される成果物**:

- `outputs/phase-3/mock-strategy-review.md`: モック戦略レビュー結果

---

### タスク4: ゲート判定

**目的**: Phase 3 の総合判定を行い、次フェーズへの進行可否を決定する

**実行手順**:

1. 全レビュー結果を集約

   | レビュー項目         | 判定      | 備考 |
   | -------------------- | --------- | ---- |
   | アーキテクチャ整合性 | PASS/FAIL | -    |
   | テストケース設計     | PASS/FAIL | -    |
   | モック戦略           | PASS/FAIL | -    |

2. 総合判定
   - 全項目 PASS: Phase 4 へ進行
   - 1項目以上 FAIL: Phase 2 へ差し戻し（MINOR は記録して進行可）

3. MINOR 指摘事項の記録
   - Phase 12 で未タスク化の対象となる指摘を記録

**期待される成果物**:

- `outputs/phase-3/gate-decision.md`: ゲート判定結果
