## 5. 設計妥当性の事前検証

### 5.1 useRefパターンの妥当性

**検証観点**: このパターンは無限ループ問題の適切な解決策か

**結論**: 適切

**理由**:

1. React公式ドキュメントでも推奨される初期化パターン
2. 06-known-pitfalls.md#P5に記載されたリスナー二重登録防止パターンと同等
3. Store Hooks自体を変更せず、呼び出し側で対処するため影響範囲が限定的
4. 将来のStore Hooks再設計の妨げにならない

#### 代替案との比較

| 手法                     | 利点                                       | 欠点                                   | 採用判定       |
| ------------------------ | ------------------------------------------ | -------------------------------------- | -------------- |
| **useRefガード**         | Store不変、StrictMode対応、緊急対応可能    | 各コンポーネントで実装が必要           | **✅ 採用**    |
| Zustand shallow比較      | Store Hooksの参照安定性を根本解決          | 全体的な再実装が必要（タスク規模増大） | 将来タスク     |
| useCallbackメモ化        | 依存配列を保持できる                       | 各Hook呼び出し側でメモ化が必要         | 長期的に不十分 |
| 個別セレクタベース再設計 | 参照安定性を根本解決、再レンダリング最適化 | アーキテクチャ変更が必要               | 将来タスク     |

**判定根拠**: useRefガードが「最もシンプルで緊急対応に適した解決策」。根本解決は将来タスク（UT-STORE-HOOKS-REFACTOR-001）で対応。

### 5.2 ESLint警告抑制の妥当性

**検証観点**: exhaustive-deps警告を抑制することは適切か

**結論**: 適切

**理由**:

1. 意図的に依存配列を空にしている（初期化1回のみ実行）
2. コメントで意図を明示している
3. 警告を無視するのではなく、理由を説明している
4. 将来のメンテナーが意図を理解できる

### 5.3 パフォーマンス影響

**検証観点**: 修正によりパフォーマンスが劣化しないか

**結論**: 影響なし（むしろ改善）

**理由**:

1. 無限ループが解消されるため、CPU使用率が大幅に改善
2. 不要なAPI呼び出しが削減される
3. レンダリング回数が適正化される

## 9. 備考

本タスクはバグ修正タスクであり、以下の特徴がある:

1. **テストファースト不要**: 既存テストで動作確認可能
2. **設計シンプル**: 確立されたパターン（useRef）の適用
3. **影響範囲限定**: 呼び出し側のみの修正

したがって、設計レビューがPASSした場合は、Phase 4（テスト作成）をスキップしてPhase 5（実装）に直接進むことを推奨する。
