## 目的

Phase 1（要件定義）とPhase 2（設計）の成果物をレビューし、実装に進む前に問題がないことを確認する。

## 背景

設計レビューゲートは、実装前に要件と設計の整合性を確認し、手戻りを防止するための重要なチェックポイントである。

---

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: 要件定義レビュー

**目的**: Phase 1の成果物が完全かつ妥当であることを確認する

**実行手順**:

1. 要件定義書の確認:
   - 機能要件が網羅されているか
   - 非機能要件が明確か
   - 曖昧な表現がないか
2. 受け入れ基準の確認:
   - 各要件に対応する受け入れ基準があるか
   - 測定可能な基準になっているか
3. スコープ定義の確認:
   - 含むもの/含まないものが明確か

**期待される成果物**:

- 要件レビュー結果

---

### タスク2: 設計レビュー

**目的**: Phase 2の設計が要件を満たし、実装可能であることを確認する

**実行手順**:

1. アーキテクチャ設計のレビュー:
   - 統合パターンが適切か
   - 依存関係が明確か
   - 拡張性・保守性が考慮されているか
2. DI設計のレビュー:
   - リポジトリの初期化方法が実現可能か
   - シングルトン管理が適切か
3. 型変換設計のレビュー:
   - 全てのフィールドがマッピングされているか
   - 変換ロジックが明確か
4. エラーハンドリング設計のレビュー:
   - エラー種別が網羅されているか
   - エラー伝搬方法が適切か

**期待される成果物**:

- 設計レビュー結果

---

### タスク3: 統合テスト観点レビュー

**目的**: 統合テストの観点が設計に反映されていることを確認する

**実行手順**:

1. 以下の統合テスト観点が設計に含まれているか確認:
   - HistoryService ↔ ConversionRepository 接続
   - IPC境界でのデータ変換
   - エラーハンドリングのE2E動作
   - ページネーションの正確性
2. テスト可能な設計になっているか確認:
   - モック/スタブが注入可能か
   - 境界条件がテスト可能か

**期待される成果物**:

- 統合テスト観点レビュー結果

---

### タスク4: レビュー結果判定

**目的**: レビュー結果を総合的に判定する

**実行手順**:

1. 各レビュー結果を集約
2. 指摘事項を分類:
   - CRITICAL: 致命的な問題（Phase 1へ戻り）
   - MAJOR: 重大な問題（影響範囲に応じて戻り）
   - MINOR: 軽微な指摘（次Phase前に対応）
   - INFO: 情報共有（対応不要）
3. 最終判定を下す

**期待される成果物**:

- レビュー判定結果（`outputs/phase-3/design-review-result.md`）

## レビューゲート

### レビュー結果判定

| 判定     | 条件                     | 次のアクション            |
| -------- | ------------------------ | ------------------------- |
| PASS     | 全レビュー観点で問題なし | 次のPhaseへ進行           |
| MINOR    | 軽微な指摘あり           | 指摘対応後、次のPhaseへ   |
| MAJOR    | 重大な問題あり           | 影響範囲に応じて戻る      |
| CRITICAL | 致命的な問題あり         | Phase 1へ戻りユーザー確認 |

### 戻り先決定基準

| 問題の種類 | 戻り先              |
| ---------- | ------------------- |
| 要件の問題 | Phase 1（要件定義） |
| 設計の問題 | Phase 2（設計）     |
