## 目的

実装開始前に、Phase 1（要件定義）とPhase 2（設計）の妥当性を検証する。重大な問題があれば該当Phaseに戻る。

## 背景

設計レビューは品質保証の重要なゲートであり、以下を確認する:

- 要件と設計の整合性
- 既存システム仕様との整合性
- 技術的な実現可能性
- 統合テスト観点

---

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: 要件-設計整合性レビュー

**目的**: 要件が設計に正しく反映されているか検証する

**実行手順**:

1. 機能要件が設計で実現可能か確認
2. 非機能要件の達成方法を確認
3. 受け入れ基準の検証方法を確認

**チェックリスト**:

- [ ] 全FR（機能要件）が設計に反映されている
- [ ] 全NFR（非機能要件）の達成方法が明確
- [ ] 各ACが検証可能な設計になっている

---

### タスク2: 既存システム整合性レビュー

**目的**: 既存のシステム仕様・実装との整合性を検証する

**実行手順**:

1. interfaces-llm.mdとの整合性確認
2. 既存LLMアダプター実装との整合性確認
3. IPC通信仕様との整合性確認

**チェックリスト**:

- [ ] AIChatRequest/Response型と整合している
- [ ] 既存LLMアダプターパターンに従っている
- [ ] IPC通信が既存設計に準拠している

---

### タスク3: 技術的実現可能性レビュー

**目的**: 設計の技術的な実現可能性を検証する

**実行手順**:

1. Vercel AI SDKの機能確認
2. 各プロバイダーAPIの互換性確認
3. エラーハンドリングの網羅性確認

**チェックリスト**:

- [ ] Vercel AI SDKで実現可能
- [ ] 4プロバイダー全てで実装可能
- [ ] エラーケースが網羅されている

---

### タスク4: 統合テスト観点レビュー

**目的**: 統合テストの観点が設計に含まれているか検証する

**実行手順**:

1. API接続テストの設計確認
2. データフローテストの設計確認
3. エラーハンドリングテストの設計確認

**チェックリスト**:

- [ ] API接続テストが設計に含まれている
- [ ] データフローテストが設計に含まれている
- [ ] エラーハンドリングテストが設計に含まれている

## 判定基準

| 判定     | 条件             | 次のアクション                      |
| -------- | ---------------- | ----------------------------------- |
| PASS     | 全観点で問題なし | Phase 4へ進行                       |
| MINOR    | 軽微な指摘あり   | 指摘対応後Phase 4へ進行             |
| MAJOR    | 重大な問題あり   | 影響範囲に応じて戻り先を決定        |
| CRITICAL | 致命的な問題あり | Phase 1へ戻りユーザーと要件を再確認 |

## 戻り先決定基準

| 問題の種類 | 戻り先              |
| ---------- | ------------------- |
| 要件の問題 | Phase 1（要件定義） |
| 設計の問題 | Phase 2（設計）     |
