## 目的

動作を変えずにコード品質を改善する（TDD: Refactor）。テストが継続成功することを確認しながらリファクタリングを行う。

## 背景

Phase 5で「テストを通すための最小限の実装」を行ったため、コードの可読性・保守性・拡張性に改善の余地がある可能性がある。テストをセーフティネットとして活用し、安全にリファクタリングを行う。

---

## 実行タスク

### タスク1: コードスメル検出

**目的**: 改善が必要なコードパターンを特定する

**実行手順**:

1. ESLintの警告を確認
2. 重複コードを特定
3. 長すぎるメソッドを特定
4. 命名の改善点を特定
5. 改善計画を策定

**チェックリスト**:

| チェック項目        | 確認結果 | 改善要否 |
| ------------------- | -------- | -------- |
| ESLint警告          | -        | -        |
| 重複コード          | -        | -        |
| メソッド長（>30行） | -        | -        |
| 複雑な条件分岐      | -        | -        |
| 不明確な命名        | -        | -        |

---

### タスク2: 重複排除

**目的**: DRY原則に従い重複コードを排除する

**実行手順**:

1. 重複コードを特定
2. 共通化可能なロジックを抽出
3. ヘルパー関数/メソッドに分離
4. テストを実行して動作確認

---

### タスク3: SOLID原則適用

**目的**: 設計原則に基づきコード構造を改善する

**実行手順**:

1. 単一責任原則（SRP）の遵守確認
2. 開放閉鎖原則（OCP）の適用検討
3. 依存性逆転原則（DIP）の適用確認
4. 必要に応じてクラス分割

**SOLID適用チェック**:

| 原則 | 項目                     | 状態 |
| ---- | ------------------------ | ---- |
| SRP  | クラスの責務が単一か     | -    |
| OCP  | 拡張に開いているか       | -    |
| LSP  | 置換可能か               | -    |
| ISP  | インターフェースが適切か | -    |
| DIP  | 抽象に依存しているか     | -    |

---

### タスク4: テスト継続成功確認

**目的**: リファクタリング後もテストが成功することを確認する

**実行手順**:

1. ユニットテストを実行
2. 統合テストを実行
3. 全テスト成功を確認

**実行コマンド**:

```bash
# リファクタリング後のテスト実行
pnpm --filter @repo/shared test
pnpm --filter @repo/shared test:integration
```
