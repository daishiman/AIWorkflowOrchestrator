## 判定基準

### PASS

全 5 観点の PASS 条件を満たしている場合。

→ Phase 4（テスト作成）へ進む。ただし本タスクは仕様書修正のみのため、Phase 5（実装 = 仕様書修正の実行）へ直接進むことも可。

### MINOR

以下のいずれかに該当する場合:

- 注記の文言・表現に軽微な不統一がある（ISO 8601 の表記ゆれ等）
- 相互参照マトリクスに記載漏れがあるが、実質的な影響はない
- コード例のフォーマットや命名規約の微小な改善が望ましい
- Date 型の注記位置（JSDoc vs 型定義横のコメント）が仕様書間で統一されていない

→ 未タスク仕様書に変換後、Phase 4 へ進む（**省略不可**）

**MINOR 指摘の未タスク変換フロー**:

1. `tasks/unassigned-task/` に指示書を作成
2. `task-workflow.md` 残課題テーブルに登録
3. 関連仕様書に参照リンクを追加

### MAJOR

以下のいずれかに該当する場合:

**要件問題（Phase 1 へ戻る）**:

- Gap の定義自体に誤りがある（存在しないフィールドを参照している等）
- スコープが不適切（実コード変更が必要な修正が含まれている）
- 影響範囲の特定が不完全（他の task-9 仕様書にも同様の Gap がある）

**設計問題（Phase 2 へ戻る）**:

- Before/After の修正内容に矛盾がある
- P5 対策のコード例が不正確（cleanup パターンの誤り）
- データフロー図の入出力型が不整合
- 実行順序の依存関係が正しくない（先行する修正に依存する修正が先に実行される等）
- DebugSession.status の idle 追加が task-9h の他のセクション（startDebugSession 等）と矛盾する

## レビュー実施手順

### Step 1: 型定義の一貫性チェック

1. Phase 2 設計書の Gap 1 修正内容（設計 3）を確認
2. 4 つの仕様書（9f, 9g, 9h, 9j）の Date 型フィールドを洗い出し、全てに注記が設計されているか検証
3. nullable と non-nullable の区別が正しいか確認

### Step 2: IPC データフローチェック

1. Phase 2 設計書の Gap 3, 4, 5, 6 修正内容（設計 1, 2, 5, 6）を確認
2. 各データフローの入出力型を追跡し、レイヤー間の型変換ポイントが明確か検証
3. safeInvoke のオブジェクト形式が全コード例に適用されているか確認

### Step 3: Pitfall 再発防止チェック

1. P44/P45: task-9a のコード例を全て確認し、positional 形式が残っていないか検証
2. P5: DebugPanel の safeOn パターンが正しく設計されているか、cleanup の呼び出しが確実か検証
3. P42: IPC バリデーションの参照が含まれているか確認

### Step 4: 相互参照整合性チェック

1. Phase 2 の相互参照マトリクスを確認
2. 各参照元→参照先の関係が正しいか、実ファイル名で検証
3. task-011 のファイル名差異が Phase 1 に記録されているか確認

### Step 5: 総合判定

1. 全観点の判定結果を集計
2. PASS / MINOR / MAJOR を判定
3. MINOR の場合は指摘事項を列挙し、未タスク変換対象を特定
