# Phase 1 成果物: FR/NFR一覧表

## タスクID: UT-IMP-PHASE12-SUBAGENT-NA-LOG-GUARD-001

## 作成日: 2026-03-01

---

## 概要

本ドキュメントは、Phase 12 仕様書別SubAgent N/A判定ログガードの機能要件（FR）4項目と非機能要件（NFR）3項目を一覧化したものである。各要件には優先度（高/中/低）を付与し、Phase 2 以降の設計・実装の判断基準とする。

---

## 機能要件（FR）一覧

### FR-1: N/A判定ログテンプレートの定義

| 項目     | 内容                                                                                                                           |
| -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 要件ID   | FR-1                                                                                                                           |
| 優先度   | **高**                                                                                                                         |
| 目的     | 仕様書が更新対象外（N/A）の場合に、判定理由と代替証跡を構造化して記録し、「更新漏れ」と「意図的なN/A」を機械的に区別可能にする |
| 対象課題 | N/A判定ログの不在により、監査時に更新漏れとN/Aの区別ができない                                                                 |

**フィールド定義:**

| フィールド名     | 型       | 必須 | 説明                                                                                                                                      |
| ---------------- | -------- | ---- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| specName         | string   | Yes  | 仕様書ファイル名（拡張子込み、例: `interfaces-agent-sdk.md`）                                                                             |
| judgment         | enum     | Yes  | `updated`（更新済み）または `na`（更新対象外）の2値                                                                                       |
| reason           | string   | Yes  | 判定理由（例: 「今回のタスクはIPC変更を含まないため」）。空文字列は禁止                                                                   |
| alternativeProof | string   | Yes  | 代替証跡（`na`の場合: 「該当チャネル未使用を `grep -rn` で確認」のように検証手段を記述。`updated`の場合: 更新内容の要約）。空文字列は禁止 |
| updatedBy        | string   | Yes  | 更新担当SubAgent名（`A`〜`E`）または `lead`                                                                                               |
| timestamp        | ISO 8601 | Yes  | 判定日時（例: `2026-03-01T10:00:00Z`）                                                                                                    |

---

### FR-2: 三点突合の判定基準定義

| 項目     | 内容                                                                                                                                |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 要件ID   | FR-2                                                                                                                                |
| 優先度   | **高**                                                                                                                              |
| 目的     | 成果物実体・artifacts.json status・phase-12-documentation.md チェックリストの3データソースの突合ルールを8パターンで網羅的に定義する |
| 対象課題 | 三点突合ルールが未定義のため、監査結果の判定が実行者依存になっている                                                                |

**データソース定義:**

| #   | データソース                             | 検証内容                                             |
| --- | ---------------------------------------- | ---------------------------------------------------- |
| 1   | 成果物実体                               | `outputs/phase-12/` 配下にファイルが物理的に存在する |
| 2   | artifacts.json の status                 | 該当 Phase 12 エントリの status が `completed`       |
| 3   | phase-12-documentation.md チェックリスト | 該当チェック項目が `[x]` でマークされている          |

**8パターンルール表:**

| #   | 成果物実体 | artifacts.json | チェックリスト | 判定     | 対処                                                    |
| --- | ---------- | -------------- | -------------- | -------- | ------------------------------------------------------- |
| 1   | 存在       | completed      | [x]            | PASS     | 対処不要                                                |
| 2   | 存在       | completed      | [ ]            | FAIL     | チェックリストを `[x]` に更新する                       |
| 3   | 存在       | 未completed    | [x]            | FAIL     | artifacts.json の status を `completed` に更新する      |
| 4   | 存在       | 未completed    | [ ]            | FAIL     | artifacts.json とチェックリストの両方を更新する         |
| 5   | 不在       | completed      | [x]            | CRITICAL | 虚偽記録の疑い — 成果物を作成するかステータスを取り消す |
| 6   | 不在       | completed      | [ ]            | FAIL     | artifacts.json の status を取り消す                     |
| 7   | 不在       | 未completed    | [x]            | FAIL     | チェックリストの `[x]` を `[ ]` に取り消す              |
| 8   | 不在       | 未completed    | [ ]            | N/A対象  | FR-1 の N/A判定ログに記録する                           |

**CRITICAL判定時エスカレーション手順:**

1. Phase 12 の実行を即座に停止する
2. 該当成果物の作成経緯を `git log` で追跡する
3. 成果物を新規作成するか、artifacts.json とチェックリストの両方のステータスを取り消す
4. 対処結果を documentation-changelog.md に記録する

### FR-3: current/baseline分離記録フォーマットの定義

| 項目     | 内容                                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 要件ID   | FR-3                                                                                                                                       |
| 優先度   | **高**                                                                                                                                     |
| 目的     | 今回のタスクで新規発生した違反（current）とタスク着手前から存在する既知の違反（baseline）を分離し、合否判定を currentViolations のみで行う |
| 対象課題 | current/baseline の分離基準が未定義で、監査結果の合否判定が実行者によって異なる                                                            |

**フィールド定義:**

| フィールド名       | 型     | 必須 | 説明                                                                    |
| ------------------ | ------ | ---- | ----------------------------------------------------------------------- |
| currentViolations  | object | Yes  | 今回のタスクで新規発生した違反。`{ total: number, details: array }`     |
| baselineViolations | object | Yes  | タスク着手前から存在する既知の違反。`{ total: number, details: array }` |
| judgmentBasis      | enum   | Yes  | 合否判定基準: `currentOnly`（currentViolations.total のみで判定）       |

**分離手順:**

| ステップ | コマンド                                | 取得データ         |
| -------- | --------------------------------------- | ------------------ |
| 1        | `git stash && node verify-all-specs.js` | baseline違反一覧   |
| 2        | `git stash pop`                         | 作業ブランチに復帰 |
| 3        | `node verify-all-specs.js`              | 全違反一覧         |
| 4        | 全違反一覧から baseline違反を差し引く   | current違反一覧    |

**合否判定ルール:**

| currentViolations.total | baselineViolations.total | 判定 |
| ----------------------- | ------------------------ | ---- |
| 0                       | 任意                     | PASS |
| 1以上                   | 任意                     | FAIL |

### FR-4: 仕様書別SubAgent分担表のテンプレート定義

| 項目     | 内容                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------ |
| 要件ID   | FR-4                                                                                                         |
| 優先度   | **中**                                                                                                       |
| 目的     | Phase 12 の仕様書更新を5つのSubAgent（A〜E）に分担し、P43対策として各SubAgentの担当を3ファイル以下に制限する |
| 対象課題 | SubAgent分担が未定義のため、1つのSubAgentに過剰な更新が集中し rate limit 中断が発生する（P43）               |

**SubAgent分担表:**

| SubAgent | 担当仕様書                  | 更新観点                                        | ファイル数上限 |
| -------- | --------------------------- | ----------------------------------------------- | -------------- |
| A        | interfaces-\*.md（最大3件） | 型定義・API契約の同期                           | 3              |
| B        | api-ipc-\*.md（最大3件）    | IPCチャネル契約の同期                           | 3              |
| C        | security-\*.md（最大3件）   | sender検証・P42バリデーション・エラーサニタイズ | 3              |
| D        | task-workflow.md            | 完了台帳・検証証跡の同期                        | 1              |
| E        | lessons-learned.md          | 教訓の構造化記録                                | 1              |

**SubAgent完了条件:**

| SubAgent | 完了条件                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------ |
| A        | 担当全仕様書に対して FR-1 の N/A判定ログが記録されている                                         |
| B        | 担当全仕様書に対して FR-1 の N/A判定ログが記録されている                                         |
| C        | 担当全仕様書に対して FR-1 の N/A判定ログが記録されている                                         |
| D        | task-workflow.md の完了台帳・残課題テーブルが更新されている                                      |
| E        | lessons-learned.md に今回のタスクで得られた教訓が追加されている（0件の場合は「教訓なし」を記録） |

**SubAgent間の依存関係（実行順序制約）:**

| 順序 | SubAgent | 理由                                                             |
| ---- | -------- | ---------------------------------------------------------------- |
| 1    | A, B, C  | 並列実行可能。型定義・IPC・セキュリティは相互に独立              |
| 2    | D        | A〜Cの完了後に実行。完了台帳にA〜Cの更新結果を反映する必要がある |
| 3    | E        | D完了後に実行。教訓記録にD（完了台帳）の情報を参照する場合がある |

## 非機能要件（NFR）一覧

### NFR-1: 再実行可能性

| 項目   | 内容                                                                               |
| ------ | ---------------------------------------------------------------------------------- |
| 要件ID | NFR-1                                                                              |
| 優先度 | **高**                                                                             |
| 目的   | 同一の入力（タスクID、ブランチ名）に対して、異なる実行者が同一の判定結果を得られる |

**検証基準:**

| #   | 基準                                                        | 数値条件         |
| --- | ----------------------------------------------------------- | ---------------- |
| 1   | 検証コマンドは全てコピー&ペーストで実行可能な形式で提供する | コマンド省略 0件 |
| 2   | 手動判断を要するステップは0件とする                         | 手動判断 0件     |
| 3   | 同一入力に対する判定結果のばらつきは0件とする               | 判定差異 0件     |

---

### NFR-2: 明確性

| 項目   | 内容                                                                          |
| ------ | ----------------------------------------------------------------------------- |
| 要件ID | NFR-2                                                                         |
| 優先度 | **中**                                                                        |
| 目的   | 各手順が「何を」「どこで」「どのコマンドで」の3要素を含み、曖昧表現を排除する |

**検証基準:**

| #   | 基準                                                                      | 数値条件       |
| --- | ------------------------------------------------------------------------- | -------------- |
| 1   | 各手順に「何を」「どこで」「どのコマンドで」の3要素が含まれている         | 3要素欠落 0件  |
| 2   | 判定基準は数値（`=== 0`, `> 0`）または列挙値（`updated`, `na`）で表現する | 曖昧基準 0件   |
| 3   | 禁則語（「適切に」「必要に応じて」「など」）が使用されていない            | 禁則語使用 0件 |

---

### NFR-3: 既存監査スクリプト互換性

| 項目   | 内容                                                                                       |
| ------ | ------------------------------------------------------------------------------------------ |
| 要件ID | NFR-3                                                                                      |
| 優先度 | **中**                                                                                     |
| 目的   | 既存の監査スクリプト（verify-all-specs.js, audit-unassigned-tasks.js）との互換性を維持する |

**検証基準:**

| #   | 基準                                                                     | 数値条件             |
| --- | ------------------------------------------------------------------------ | -------------------- |
| 1   | `verify-all-specs.js` の出力フォーマット（violations配列）と互換性を持つ | 非互換フィールド 0件 |
| 2   | `audit-unassigned-tasks.js` の未タスク検出ロジックと干渉しない           | 干渉箇所 0件         |
| 3   | 既存の `artifacts.json` スキーマに破壊的変更を加えない                   | 破壊的変更 0件       |
