## 目的

`scripts/verify-ipc-4layer.js` の重複コード削除、命名改善、責務境界の整理を行い、コードの可読性・保守性を向上させる。リファクタリング後も既存テストが全てパスすることを確認し、品質を維持する。

## 背景

Phase 5-6 での実装・テスト作成を通じて、コードの重複や命名の不統一、責務の曖昧な箇所が発見される可能性がある。リファクタリングにより、以下の品質特性を改善する:

- **可読性**: 変数名・関数名が処理内容を正確に表現している
- **保守性**: モジュール間の責務境界が明確で、変更影響範囲が限定的
- **一貫性**: 命名規則・コーディングスタイルがプロジェクト全体と統一されている

変更内容は全て「対象/Before/After/理由」テーブル形式で記録する（Feedback RT-03対応）。

## TDD検証セクション（Refactor後テスト確認）

リファクタリングは TDD の Red-Green-Refactor サイクルの「Refactor」フェーズに相当する。以下の原則を遵守する:

### Refactor の原則

1. **振る舞いを変えない**: 外部から観測可能な振る舞い（入力→出力のマッピング）を変更しない
2. **テストを先に実行**: リファクタリング前後でテスト結果が同一であることを確認する
3. **小さなステップ**: 一度に大きな変更を行わず、小さなリファクタリングを積み重ねる
4. **カバレッジ維持**: リファクタリングによりカバレッジが低下しないことを確認する

### テスト実行コマンド（参考）

```bash
# リファクタ前ベースライン
pnpm vitest run --reporter=verbose <テストファイルパス>

# リファクタ後再実行
pnpm vitest run --reporter=verbose <テストファイルパス>

# 型チェック
pnpm typecheck

# lint
pnpm lint
```

### 判定基準

| 状態                                     | 判定 | 次のアクション                         |
| ---------------------------------------- | ---- | -------------------------------------- |
| 全テスト PASS + カバレッジ維持           | PASS | Phase 9 へ進む                         |
| テスト失敗（リファクタ起因）             | FAIL | リファクタリングを修正し再テスト       |
| テスト失敗（テスト側の問題）             | FAIL | テストを修正し理由を記録、再テスト     |
| カバレッジ低下（リファクタでコード削減） | 許容 | 削減理由を記録し、基準値以上を維持確認 |
