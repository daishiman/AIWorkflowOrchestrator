## 目的

Phase 1-2 の設計成果物に矛盾・漏れ・整合性問題がないことを検証し、Phase 4（テスト作成）へ進めるかを判定する。

### タスク1: 矛盾レビュー

**目的**: Phase 1-2 の設計成果物間の矛盾を検出する

**実行手順**:

1. Phase 1 の要件（FR-1〜FR-6、NFR-1〜NFR-4）と Phase 2 の設計が1:1で対応していることを検証する
2. 受け入れ基準（AC-1〜AC-8）が設計で実現可能であることを検証する
3. 検証フロー（Rule-1〜Rule-3）が要件の全てをカバーしていることを検証する
4. 既存 `check-ipc-contracts.ts` との機能境界が矛盾なく定義されていることを検証する

**レビュー観点**:

| 観点           | 確認内容                                                  |
| -------------- | --------------------------------------------------------- |
| 要件-設計整合  | FR/NFR が設計に全て反映されているか                       |
| AC実現可能性   | 各ACが設計で達成可能か                                    |
| モジュール責務 | 各モジュールの責務が重複・欠損なく定義されているか        |
| 正規表現精度   | パーサーの正規表現が4層の実際のコードパターンに一致するか |
| CI統合整合     | GitHub Actions設計がNFR-1（30秒以内）を満たすか           |

**期待される成果物**:

- 矛盾チェック表（`outputs/phase-3/contradiction-checklist.md`）

---

### タスク2: 漏れレビュー

**目的**: Phase 1 の要件から Phase 2 への未反映項目を検出する

**実行手順**:

1. Phase 1 の要件一覧と Phase 2 の設計項目を突合する
2. トレーサビリティ行列で未対応項目がないか確認する
3. エッジケース（空ファイル、不正フォーマット、動的チャネル生成）が設計で考慮されているか確認する

**チェックリスト**:

- [ ] FR-1〜FR-6 の全てが設計に反映されている
- [ ] NFR-1〜NFR-4 の全てが設計制約として反映されている
- [ ] AC-1〜AC-8 の全てが実現手段を持つ
- [ ] エラー分類（CRITICAL/WARNING/INFO）が定義されている
- [ ] 正常系・異常系の両方のフローが設計されている

**期待される成果物**:

- 漏れレビュー結果（矛盾チェック表に統合）

---

### タスク3: ゲート判定

**目的**: Phase 4 へ進行可能かを判定する

**実行手順**:

1. タスク1・タスク2 の結果を集約する
2. 以下の判定基準でGo/No-Goを決定する
3. No-Goの場合は是正タスクと戻り先Phaseを特定する

**期待される成果物**:

- ゲート判定書（`outputs/phase-3/gate-decision.md`）
- 設計レビュー結果（`outputs/phase-3/design-review-result.md`）

## レビュー結果判定

| 判定     | 条件                     | 次のアクション             |
| -------- | ------------------------ | -------------------------- |
| PASS     | 全レビュー観点で問題なし | Phase 4 へ進行             |
| MINOR    | 軽微な指摘あり           | 指摘対応後、Phase 4 へ     |
| MAJOR    | 重大な問題あり           | 影響範囲に応じて戻る       |
| CRITICAL | 致命的な問題あり         | Phase 1 へ戻りユーザー確認 |

### 戻り先決定基準

| 問題の種類 | 戻り先              |
| ---------- | ------------------- |
| 要件の問題 | Phase 1（要件定義） |
| 設計の問題 | Phase 2（設計）     |

## 統合テスト連携（Phase 1〜11は必須）

- 統合テスト観点のレビューゲート: 検証スクリプトが4層ファイルを正しく読み取り、CI環境で正常に動作する設計になっているかを確認する
- テストデータ設計: フィクスチャファイルが4層の実際のコードパターンを正確に模倣する設計になっているかを確認する

## 多角的チェック観点（AIが判断）

- 批判的思考: 要件と設計に見落としや自己矛盾がないか
- ダブルループ思考: ルールそのものの前提が妥当か、設計の仮定が適切か
- 因果ループ思考: missing / warning / exit code の関係が循環しないか
- 逆説思考: warning を許容しつつ品質を落とさない設計になっているか

## サブタスク管理

- タスク1とタスク2は同一レビュー観点を共有するため並行確認可能
- タスク3はタスク1・2の結果が揃った後に判定する
- No-Go になった場合は戻り先を Phase 1 か Phase 2 に分けて記録する
