## 目的

## 判定基準

| 判定  | 条件             | 対応                         |
| ----- | ---------------- | ---------------------------- |
| PASS  | 全観点で問題なし | Phase 4へ進行                |
| MINOR | 軽微な指摘あり   | 指摘対応後Phase 4へ進行      |
| MAJOR | 重大な問題あり   | 影響範囲に応じて戻り先を決定 |

## レビュー観点

### 1. 要件との整合性

| チェック項目 | 確認内容                                                   | 判定 |
| ------------ | ---------------------------------------------------------- | ---- |
| FR-001対応   | EntityStore CRUD機能が設計に含まれているか                 | □    |
| FR-002対応   | RelationStore CRUD機能が設計に含まれているか               | □    |
| FR-003対応   | CommunityStore CRUD機能が設計に含まれているか              | □    |
| FR-004対応   | グラフ探索（traverse, findShortestPath）が設計されているか | □    |
| FR-005対応   | バッチ操作（bulkUpsertEntities等）が設計されているか       | □    |
| NFR対応      | Result型パターン、Branded Types等が設計に反映されているか  | □    |

### 2. アーキテクチャの妥当性

| チェック項目   | 確認内容                                  | 判定 |
| -------------- | ----------------------------------------- | ---- |
| 責務分離       | 各Storeの責務が明確に分離されているか     | □    |
| 依存関係       | Store間の依存関係が適切か（循環依存なし） | □    |
| 拡張性         | 将来の機能追加に対応できる構造か          | □    |
| テスタビリティ | モック化・テストが容易な設計か            | □    |

### 3. インターフェースの妥当性

| チェック項目   | 確認内容                                                | 判定 |
| -------------- | ------------------------------------------------------- | ---- |
| 型安全性       | EntityId, RelationId等のBranded Typesが定義されているか | □    |
| 一貫性         | API命名規則が一貫しているか                             | □    |
| エラー処理     | Result型パターンで統一されているか                      | □    |
| ドキュメント性 | 型定義からAPIの使い方が理解できるか                     | □    |

### 4. データベース設計との整合性

| チェック項目 | 確認内容                                          | 判定 |
| ------------ | ------------------------------------------------- | ---- |
| スキーマ対応 | StoredEntityがentitiesテーブルと整合しているか    | □    |
| スキーマ対応 | StoredRelationがrelationsテーブルと整合しているか | □    |
| CASCADE      | 削除時のCASCADE動作が設計されているか             | □    |
| インデックス | 頻出クエリに対するインデックスが考慮されているか  | □    |
