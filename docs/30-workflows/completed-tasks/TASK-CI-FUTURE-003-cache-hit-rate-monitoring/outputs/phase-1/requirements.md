## 機能要件

| 要件ID | 要件                                                                          | 優先度 |
| ------ | ----------------------------------------------------------------------------- | ------ |
| FR-001 | 各 CI ジョブでキャッシュの3状態（完全ヒット・フォールバック・ミス）を判定する | 必須   |
| FR-002 | 判定結果を `$GITHUB_STEP_SUMMARY` に Markdown テーブル形式で出力する          | 必須   |
| FR-003 | キャッシュミス時に `::warning::` アノテーションを出力する                     | 必須   |
| FR-004 | フォールバックヒット時に `::notice::` アノテーションを出力する                | 推奨   |
| FR-005 | 判定ステップに `if: always()` を設定し前ステップ失敗時も動作させる            | 必須   |
| FR-006 | 判定ステップに `continue-on-error: true` を設定し CI 全体への影響を防ぐ       | 必須   |

---

## 非機能要件

| 要件ID  | 要件                                                             | 優先度 |
| ------- | ---------------------------------------------------------------- | ------ |
| NFR-001 | 追加ステップの実行時間が数秒以内（既存 CI への影響を最小化）     | 必須   |
| NFR-002 | キャッシュ判定ロジックが誤判定しない（ヒット時ミス判定しない等） | 必須   |
| NFR-003 | 複数ジョブに同一ロジックを適用できる構造とする                   | 推奨   |

---

## スコープ

### 含むもの

- `.github/actions/pnpm-install-retry/action.yml` へのキャッシュヒット率確認ステップの追加
- `$GITHUB_STEP_SUMMARY` へのキャッシュ状態出力
- キャッシュミス時の `::warning::` アノテーション出力
- フォールバックヒット時の `::notice::` アノテーション出力
- `cache-hit` と cache restore 直後の `node_modules` 存在確認を利用した正確な3状態判定ロジック

### 含まないもの

- 外部モニタリングサービス（Datadog、Grafana 等）の導入
- Slack / メールアラートの設定
- キャッシュヒット率の長期トレンド蓄積・可視化ダッシュボード

---

## 背景

TASK-CI-OPT-001 にて node_modules キャッシュを `.github/actions/pnpm-install-retry/action.yml` に導入し、CI 実行時間を 15 分超から約 5〜7 分に短縮した。しかし、キャッシュのヒット率が低下しても現状では気づく手段がない。

### アーキテクチャ上の注意点

Phase 1 の現状確認で判明した通り、`id: cache-node-modules` のキャッシュステップはカスタム複合アクション（`pnpm-install-retry`）内に存在する。Phase 2 の設計では、判定ステップをアクション内に配置する方針を採用する（DRY原則・全ジョブへの自動適用）。
