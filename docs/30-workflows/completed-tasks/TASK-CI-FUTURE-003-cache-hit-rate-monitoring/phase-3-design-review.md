# Phase 3: 設計レビューゲート

## メタ情報

| 項目       | 内容                                 |
| ---------- | ------------------------------------ |
| Phase      | 3                                    |
| 機能名     | TASK-CI-FUTURE-003                   |
| タスク名   | キャッシュヒット率のモニタリング設定 |
| 前提Phase  | Phase 2                              |
| 後続Phase  | Phase 4                              |
| 作成日     | 2026-04-15                           |
| ステータス | pending                              |

## 目的

Phase 2 の設計が Phase 4 へ進む品質を満たしているかをゲート判定する。
MAJOR 問題があれば Phase 2 へ差し戻す。MINOR 問題は Phase 4 以降で対処する。

## 実行タスク

### Task 3-A: 設計の整合性確認

以下のチェックリストを全て確認する。

#### 3状態判定ロジック

| チェック項目                                                                               | 期待結果    | 判定 |
| ------------------------------------------------------------------------------------------ | ----------- | ---- |
| `cache-hit=true` のとき「完全ヒット」と判定されるか                                        | ✅ 正しい   | -    |
| `cache-hit=false` かつ `node_modules` が存在する場合「フォールバックヒット」と判定されるか | ✅ 正しい   | -    |
| `cache-hit=false` かつ `node_modules` が存在しない場合「ミス」と判定されるか               | ✅ 正しい   | -    |
| `restore-keys` フォールバック時に `cache-hit=false` になることが設計に反映されているか     | ✅ 反映済み | -    |

#### YAML 構造

| チェック項目                                                           | 期待結果    | 判定 |
| ---------------------------------------------------------------------- | ----------- | ---- |
| 判定ステップに `if: always()` が設定されているか                       | ✅ 設定済み | -    |
| 判定ステップに `continue-on-error: true` が設定されているか            | ✅ 設定済み | -    |
| `steps.<id>.outputs.cache-hit` の参照パスが正確か                      | ✅ 正確     | -    |
| `steps.<id>.outputs.cache-reason` の参照パスが正確か                   | ✅ 正確     | -    |
| `$GITHUB_STEP_SUMMARY` への書き込みが `>> $GITHUB_STEP_SUMMARY` 形式か | ✅ 正確     | -    |

#### スコープ境界

| チェック項目                                       | 期待結果    | 判定 |
| -------------------------------------------------- | ----------- | ---- |
| 外部モニタリングサービスの導入が含まれていないか   | ✅ 含まない | -    |
| 長期トレンド蓄積が含まれていないか                 | ✅ 含まない | -    |
| 既存の CI 実行フローを変更しない（追加のみ）設計か | ✅ 追加のみ | -    |

### Task 3-B: リスク評価

Phase 2 設計に基づくリスクを評価する。

| リスク                                                           | 影響度 | 発生確率 | 対策                                  |
| ---------------------------------------------------------------- | ------ | -------- | ------------------------------------- |
| `id` 未設定のキャッシュステップからの `outputs` 参照が失敗する   | 高     | 中       | Phase 5 で `id` 追加を最初に実施する  |
| 判定ステップが失敗し CI 全体がブロックされる                     | 高     | 低       | `continue-on-error: true` で対応済み  |
| `cache-hit=false` をミスと誤判定する（フォールバックを見落とす） | 中     | 中       | `node_modules` 存在チェックで対応済み |
| `$GITHUB_STEP_SUMMARY` への書き込みが既存 Summary と競合する     | 低     | 低       | `>>` による追記形式のため競合しない   |

### Task 3-C: ゲート判定

以下の基準でゲート判定を実施する。

| 判定基準                  | 合格条件                                |
| ------------------------- | --------------------------------------- |
| MAJOR 問題                | 0 件（1 件以上あれば Phase 2 差し戻し） |
| MINOR 問題                | 記録のみ（Phase 4 以降で対処可）        |
| 3状態判定ロジックの正確性 | 全チェック項目が ✅                     |
| YAML 構造の完全性         | 全チェック項目が ✅                     |
| スコープ境界の遵守        | 全チェック項目が ✅                     |

## 実行手順

1. `outputs/phase-2/design.md` を読み込む
2. Task 3-A の全チェックリストを実行し、結果（✅/❌）を記録する
3. Task 3-B のリスク評価を実施し、追加リスクがあれば記録する
4. Task 3-C のゲート判定を実施する
5. MAJOR 問題がある場合は差し戻し内容を明記して Phase 2 へ戻る
6. 合格の場合は設計レビュー結果を `outputs/phase-3/` に保存する
