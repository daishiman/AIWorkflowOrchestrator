## 目的

Phase 2 で策定した設計（型定義更新方針・動的 import 型付けパターン・ローカル型整合性設計）が、Phase 1 の要件（FR/NFR）を満たしているかを検証する。設計の妥当性・後方互換性・実現可能性を多角的にレビューし、ゲート判定（PASS / MINOR / MAJOR）を行う。

## レビュー観点

### 観点 1: 型定義の正確性

| チェック項目                                                          | 判定基準                                |
| --------------------------------------------------------------------- | --------------------------------------- |
| `d.ts` の `QueryOptions` が SDK 実シグネチャと一致しているか          | SDK の `query()` 引数と型定義が完全一致 |
| `QueryResult` 等の戻り値型が正しいか                                  | SDK の実戻り値型と一致                  |
| `createClient()` 等のファクトリ関数の型が正しいか                     | SDK のエクスポートと一致                |
| 型マッピング表（`type-mapping.md`）の差分が全て設計で解消されているか | 全差分に対する設計対応が記載済み        |

### 観点 2: 後方互換性

| チェック項目                                                      | 判定基準                                            |
| ----------------------------------------------------------------- | --------------------------------------------------- |
| `AgentExecutor.ts` が現行 `d.ts` から参照する型に影響がないか     | `AgentExecutor.ts` のコンパイルが変更なしで成功する |
| `agent-client.ts` が現行 `d.ts` から参照する型に影響がないか      | `agent-client.ts` のコンパイルが変更なしで成功する  |
| 共有パッケージ `@repo/shared` の他ファイルへの影響がないか        | `d.ts` を参照する全ファイルで型エラーが発生しない   |
| `pnpm typecheck` が全パッケージで PASS するか（設計段階での保証） | 設計書に影響範囲の網羅的分析が含まれている          |

### 観点 3: 動的 import 型付けの妥当性

| チェック項目                                                     | 判定基準                                                 |
| ---------------------------------------------------------------- | -------------------------------------------------------- |
| 選択した import パターンが TypeScript の型推論で正しく動作するか | `d.ts` + 動的 `import()` で `any` 型にならないことの保証 |
| `AgentExecutor.ts` の既存 import パターンとの一貫性があるか      | 同一プロジェクト内で統一されたパターンであること         |
| `d.ts` が不正な場合のフォールバック戦略が設計されているか        | SDK 型定義変更時の対応方針が記載されている               |

### 観点 4: 既存テストとの互換性

| チェック項目                                       | 判定基準                                       |
| -------------------------------------------------- | ---------------------------------------------- |
| 型定義変更がテストコードのコンパイルに影響しないか | テストファイルの import に型エラーが発生しない |
| モック定義が型変更で壊れないか                     | `vi.mock()` のモック定義が新型定義と整合する   |
| テスト実行フローに影響がないか                     | SkillExecutor の動作ロジックに変更なし         |

### 観点 5: スコープ遵守

| チェック項目                                                                    | 判定基準                                              |
| ------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 設計がスコープ外の変更を含んでいないか                                          | SDK 機能追加・ロジック変更が含まれていない            |
| `AgentExecutor.ts` / `agent-client.ts` の修正が不要であることが確認されているか | 設計書に「変更不要」が明記されている                  |
| 動的 import から top-level import への変更を含んでいないか                      | import 方式の変更がスコープ外であることが設計書に記載 |

## ゲート判定基準

### PASS（Phase 4 へ進行）

以下の **全条件** を満たす場合:

- [ ] 型定義が SDK 実シグネチャと完全一致している
- [ ] `AgentExecutor.ts` / `agent-client.ts` への影響がゼロであることが設計段階で確認されている
- [ ] 動的 import 型付けパターンが妥当であり、`any` 型回避が保証されている
- [ ] 既存テストとの互換性が設計段階で確認されている
- [ ] スコープ外の変更が含まれていない
- [ ] 全 5 レビュー観点で問題なし

### MINOR（指摘対応後 Phase 4 へ進行）

以下のいずれかに該当する場合:

| MINOR 条件                                                | 対応内容                        |
| --------------------------------------------------------- | ------------------------------- |
| 型定義の一部プロパティ名・型名に軽微な誤りがある          | `d.ts` の修正設計を調整         |
| ローカル型（`SDKQueryOptions`）の処理方針に改善余地がある | 整合性設計の追記・修正          |
| 設計書の記載に不足がある（影響範囲分析の漏れ等）          | 設計書を補完してから Phase 4 へ |

### MAJOR（Phase 1 または Phase 2 へ差し戻し）

以下のいずれかに該当する場合:

| MAJOR 条件                                                 | 差し戻し先 | 理由                                 |
| ---------------------------------------------------------- | ---------- | ------------------------------------ |
| SDK が型定義を公開しておらず、`d.ts` の手動維持が不可避    | Phase 2    | 設計方針の根本見直しが必要           |
| `AgentExecutor.ts` の型が壊れる設計になっている            | Phase 2    | 後方互換性の設計やり直し             |
| 動的 import から top-level import への変更が不可避と判明   | Phase 1    | スコープの見直しが必要               |
| SDK のバージョンアップが前提条件として必要と判明           | Phase 1    | 要件の見直しが必要                   |
| `as any` 除去が現行 SDK バージョンでは技術的に不可能と判明 | Phase 1    | タスク自体の実現可能性の再評価が必要 |

## 実行手順

### Step 1: Phase 2 成果物の読み込み

1. `outputs/phase-2/architecture-design.md` を読み込む
2. `outputs/phase-2/type-mapping.md` を読み込む
3. Phase 1 の要件定義書・受入基準書を読み込む

### Step 2: レビュー観点 1-5 の検証

1. 各観点のチェック項目を逐次確認する
2. 不合格項目がある場合は具体的な指摘内容を記録する
3. 指摘の重大度（MINOR / MAJOR）を判定する

### Step 3: 追加検証

1. `SkillExecutor.ts` の実コードと設計書の変更案を照合する
2. `AgentExecutor.ts` の import パターンと設計案の一貫性を確認する
3. `d.ts` の変更案が `pnpm typecheck` で成功する見込みを評価する

### Step 4: ゲート判定

1. 全レビュー観点の結果を集約する
2. PASS / MINOR / MAJOR のいずれかを判定する
3. 判定結果と理由を `design-review-result.md` に記録する

### Step 5: MINOR/MAJOR の場合の対応指示

1. MINOR: 具体的な修正項目を列挙し、修正後 Phase 4 へ進行可能とする
2. MAJOR: 差し戻し先の Phase と再実行スコープを明記する
