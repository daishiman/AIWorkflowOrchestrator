## 目的

本タスクは **コード変更を含まない docs-sync wave** であるため、
従来のコードリファクタリング（重複排除・命名改善・SOLID 適用）は対象外。
代わりに **追記内容の重複・冗長削減** と **既存エントリ形式との整合性** を
ファイル単位で整理し、追記された記述を最小複雑性へ寄せる。

Phase 5（実装）/ Phase 6（テスト拡充）で追記された内容を対象に、
冗長表現・重複説明・形式逸脱を削減し、既存エントリ群と統一感を持つ
spec へ寄せることが本 Phase のゴール。

## リファクタリング判断基準【必須】

| 判定           | 条件                                                                                | 対応                         |
| -------------- | ----------------------------------------------------------------------------------- | ---------------------------- |
| 必須リファクタ | 既存エントリ形式から逸脱（列数違い / 節構成違い / 日付形式違い）がある              | 即修正（Phase 5 へ局所差戻） |
| 推奨リファクタ | 冗長表現・重複説明があり、既存エントリと粒度が合わない                              | 整理（Phase 8 内で実施）     |
| 不要リファクタ | 多少の冗長があるが、既存エントリ間にも同程度の揺れがあり、統一感を損なわない        | スキップ（理由を記録）       |
| 禁止リファクタ | 追記内容そのものを大幅に変更する / 追記対象ファイル以外の既存エントリを併せて整える | やらない（scope 外）         |

> **scope 限定原則**: 本タスクの追記分のみを対象とし、既存エントリへの遡及修正は禁止。
> 既存エントリの不整合を発見した場合は、別タスク（unassigned-task-detection）として記録のみ。

## 追記内容の整理手順【必須】

### Step 1: 重複検出

各ファイルにおいて、追記分に **重複表現** がないかチェックする。

| ファイル                             | 重複検出観点                                                            |
| ------------------------------------ | ----------------------------------------------------------------------- |
| `task-specification-creator/LOGS.md` | 3節（コンテキスト・成果・結果）内で同じ内容を繰り返していないか         |
| `aiworkflow-requirements/LOGS.md`    | 備考列が「対象ファイル」列と同じ情報を含んでいないか                    |
| canonical spec（task-workflow 系）   | active 側と completed 側に **同タスクID** が重複登録されていないか      |
| lessons-learned                      | 3 知見の説明文が相互に冗長（同じ事例を繰り返す）になっていないか        |
| 親 `index.md`                        | フロントマターと Phase 一覧テーブルで同じ完了宣言を重複記述していないか |

### Step 2: 冗長削減

| 削減対象                                                         | 判定基準                             |
| ---------------------------------------------------------------- | ------------------------------------ |
| 「branch 内」「repo-wide」両方を毎回繰り返している説明           | 初出のみで以降は省略                 |
| 親タスク `TASK-SC-CANCEL-CLEANUP-PARTIAL-DIR-001` を毎行フル記載 | 同一エントリ内では「親タスク」と短縮 |
| 3知見の背景説明が長文                                            | 1〜2 文に収め、詳細は親タスクへ参照  |

### Step 3: 既存エントリ形式整合性チェック

Phase 4 で作成された `format-fixture-snapshots.md` と、Phase 5 で追記された実エントリを **diff レベルで比較**し、形式逸脱を検出する。

| チェック項目                                      | 基準                                                                 |
| ------------------------------------------------- | -------------------------------------------------------------------- |
| 表形式の列数                                      | 既存エントリと完全一致                                               |
| 3節構成（コンテキスト・成果・結果）の見出しレベル | 既存エントリと同じ階層（h3 / h4 等）                                 |
| 日付フォーマット                                  | `2026-04-20` 形式で統一（`2026/04/20` や `April 20, 2026` 等を排除） |
| h3 タイトル命名規則（lessons-learned）            | 既存命名パターンと整合（例: `## 知見: ...` / `### Lesson: ...` 等）  |
| Markdown リンク（`[text](path)`）                 | 既存と同じ書式 / リンク切れなし                                      |

### Step 4: 整理結果の記録

`outputs/phase-8/refactor-decision-log.md` に以下を記録：

| 記録項目                       | 内容                                                              |
| ------------------------------ | ----------------------------------------------------------------- |
| Before / After / 理由（表）    | 各ファイルの追記分について 1 行ずつ記録                           |
| スキップ理由                   | 「不要リファクタ」と判定した項目とその理由                        |
| 既存エントリ形式整合性チェック | 5 ファイル分の整合性 PASS / FAIL                                  |
| 形式逸脱検出時の差戻先         | Phase 5（追記内容）/ Phase 6（形式回帰）/ Phase 4（fixture 不備） |
