## ワークフロー改善点

### 1. ワークツリー環境での仕様書更新フロー

**発見フェーズ**: Phase 12 Task 2（システム仕様書更新）

**課題**: ワークツリー環境（`.worktrees/`）で作業する場合、正本仕様書（`api-ipc-agent.md`、`arch-electron-services.md` 等）がメインリポジトリの `.claude/skills/` 配下にあるため、ワークツリーからの直接更新はマージ後の競合リスクがある。現在は `spec-update-summary.md` に更新内容を記録し、マージ後に実施する運用としているが、P26（システム仕様書更新遅延）との整合性に注意が必要。

**提案**: ワークツリー環境でもスキルディレクトリが共有されている場合は直接更新を許可し、共有されていない場合のみ `spec-update-summary.md` に記録するフローを Phase 12 仕様書テンプレートに明文化する。

### 2. IPC タスクのテスト数レポート整合性

**発見フェーズ**: Phase 6-7（テスト拡充・カバレッジ確認）

**課題**: Phase 4-5 時点のテスト数（80テスト）と Phase 6 拡充後のテスト数（97テスト）が Phase 10 レポート（95テスト）と微妙に異なるケースが発生した。Phase ごとにスナップショットのタイミングが異なるため、最終的なテスト数が各レポート間で不一致になりやすい。

**提案**: Phase 10（最終レビュー）レポート作成時に、実際のテストファイルから `grep -c "it\|test(" *.test.ts` で最新テスト数を取得し、その値を Phase 10 レポートの正値とする。Phase 12 のドキュメントでも同じ値を使用する。

### 3. electron-store 永続化パターンのドキュメント化

**発見フェーズ**: Phase 5（実装）

**課題**: AnalyticsStore は electron-store ベースの永続化ストアとして実装されたが、P19（型キャストによる実行時検証バイパス）準拠のバリデーション、ストアデータ破損時のフォールバック（空配列返却）、100件上限のイベントサイズ管理など、複数のパターンを組み合わせている。これらのパターンは今後の electron-store 利用タスクでも再利用可能。

**提案**: `architecture-implementation-patterns.md` に「electron-store 永続化パターン」セクションを追加し、AnalyticsStore の実装を参照パターンとして記録する。記録対象:

- P19 準拠バリデーション（`unknown` 型受け取り + `Array.isArray()` + `.filter()`）
- サイズ上限管理（古いイベントの自動削除）
- ストアデータ破損時のフォールバック戦略
