## 実行タスク

### タスク1: 設計レビュー実施

#### 1.1 AC 充足確認

| AC ID | 条件                                          | 設計での対応                                                | 判定 |
| ----- | --------------------------------------------- | ----------------------------------------------------------- | ---- |
| AC-1  | `ImproveFeedbackHistory` 型が shared に定義   | Phase 2 タスク1 で型定義・配置先を設計済み                  | ✅   |
| AC-2  | `verifyAndImproveLoop()` が全履歴を蓄積・渡す | Phase 2 タスク2 で Before/After を設計済み                  | ✅   |
| AC-3  | `buildImproveFeedback()` が全試行の情報を含む | Phase 2 タスク3 でプロンプト設計済み（出力例あり）          | ✅   |
| AC-4  | 3 回ループで試行 3 が試行 1・2 を参照できる   | Phase 2 タスク3 の出力例で 3 回目の feedback 内容を例示済み | ✅   |

#### 1.2 simpler alternative の検討

| 代替案                                      | 評価                                                                     | 採否     |
| ------------------------------------------- | ------------------------------------------------------------------------ | -------- |
| 文字列を `\n---\n` で区切って連結する       | 試行境界が曖昧、LLM のパース精度が下がる、構造化されていないので拡張困難 | 不採用   |
| `Map<number, string>` で試行番号→要約を管理 | 失敗チェック情報が欠落する、型安全性が低い                               | 不採用   |
| `ImproveFeedbackHistory[]` 構造化配列       | 試行番号・失敗チェック・改善要約を明確に分離、型安全、拡張容易           | **採用** |

**結論**: 構造化配列アプローチが最もシンプルかつ拡張性が高い。代替案はいずれも情報の欠落または型安全性の低下を招く。

#### 1.3 型互換性検証テーブル（Phase 2 下書きの確認）

| Factory/関数                  | 返す型/引数型              | 注入先/消費先                           | 互換性 |
| ----------------------------- | -------------------------- | --------------------------------------- | ------ |
| `buildImproveFeedback`        | `ImproveFeedbackHistory[]` | `verifyAndImproveLoop` ループ内         | ✅     |
| `summarizeImproveSuggestions` | `string`                   | `ImproveFeedbackHistory.improveSummary` | ✅     |

**同名インターフェース型ドリフト検出**:

```bash
grep -rn "interface ImproveFeedbackHistory" packages/ apps/
```

結果: 0 件 — 新規定義のため型ドリフトリスクなし。

#### 1.4 責務境界の確認

| 確認観点                                               | 結果                                                                               |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| Facade の責務を変えないか                              | ✅ Facade は引き続き public bridge。ループ内ローカル変数の変更のみ                 |
| state owner が混在しないか                             | ✅ `feedbackHistory` はループ内ローカル変数。SkillCreatorWorkflowEngine に影響なし |
| IPC 契約に影響しないか                                 | ✅ IPC チャンネル追加・変更なし。Renderer への影響なし                             |
| improve の権限（edit 可、new file 不可）に影響しないか | ✅ GovernanceHooks の phase policy は変更対象外                                    |

#### 1.5 多角的チェック観点

**システム系:**

| 観点       | 判定                                                                                 |
| ---------- | ------------------------------------------------------------------------------------ |
| 因果関係   | feedback が構造化される → LLM が全履歴を参照 → 重複提案が減少 → verify 通過率向上    |
| 依存関係   | `ImproveFeedbackHistory` → `buildImproveFeedback` → `verifyAndImproveLoop`（一方向） |
| 状態所有権 | ループ内ローカル変数のみ。外部 state owner への影響なし                              |

**戦略・価値系:**

| 観点       | 判定                                                          |
| ---------- | ------------------------------------------------------------- |
| 価値提案   | maxImproveRetry の投資対効果を最大化する                      |
| コスト均衡 | 型 1 個 + 関数シグネチャ 1 箇所 + ループ内 〜20 行 = 低コスト |

**問題解決系:**

| 観点         | 判定                                                            |
| ------------ | --------------------------------------------------------------- |
| 仮説         | 「全履歴を LLM に渡すことで重複提案が減る」— テストで検証可能   |
| 改善優先順位 | feedback memory の構造化が最優先。UI 表示は将来タスクに分離済み |
