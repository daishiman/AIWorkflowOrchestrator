## 目的

実装前に認可ロジック設計の妥当性を検証し、セキュリティ上の問題を早期発見する。Shift Left原則に基づき、設計段階でOWASP A01準拠を確認する。

## 背景

認可の実装ミスはセキュリティインシデントに直結するため、実装前の設計レビューが重要。以下の観点でレビューを実施する：

1. セキュリティ観点（OWASP準拠）
2. 認可ロジック妥当性
3. アーキテクチャ整合性

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: セキュリティ観点レビュー

**目的**: OWASP A01準拠と認可バイパス可能性を検証する

**レビュー観点**: セキュリティ監査

**レビューチェックリスト**:

- [ ] **OWASP A01準拠**: 設計がOWASP A01: Broken Access Controlを解消しているか
  - 全対象メソッドにuserID検証が含まれているか
  - 認可チェックがビジネスロジック実行前に行われるか

- [ ] **認可バイパス可能性**: 認可チェックを回避できるパスがないか
  - 直接DBアクセスによるバイパスがないか
  - 内部APIからのアクセスでも認可チェックが適用されるか

- [ ] **情報漏洩リスク**: エラーメッセージからセッション存在有無が推測できないか
  - 存在しないセッションと認可失敗で同じエラーメッセージを返すか
  - スタックトレースやデバッグ情報が露出しないか

- [ ] **Fail-Secure設計**: エラー発生時にアクセス拒否されるか
  - DB接続エラー時にアクセス許可されないか
  - 例外発生時にデフォルトで拒否されるか

**期待される成果物**:

- セキュリティレビューチェックリスト結果

---

### タスク2: 認可ロジック妥当性レビュー

**目的**: 認可チェックのタイミングと実装方法の妥当性を検証する

**レビュー観点**: 認可ロジック

**レビューチェックリスト**:

- [ ] **認可チェックタイミング**: データ取得・操作前に認可チェックが行われるか
  - DBクエリ実行前に認可チェックが完了しているか（設計上、まずfindById後に検証）

- [ ] **認可ルール明確性**: 認可ルールが明確に定義されているか
  - `session.userId === requestUserId` のシンプルなルール
  - 追加のロール・権限チェックが将来必要になる可能性の考慮

- [ ] **エッジケース考慮**: 以下のエッジケースが考慮されているか
  - requestUserIdがnull/undefinedの場合
  - sessionIdが存在しない場合
  - session.userIdがnull/undefinedの場合

- [ ] **トランザクション整合性**: 複数操作時の整合性が保たれるか
  - 削除操作時のメッセージ削除との整合性

**期待される成果物**:

- 認可ロジックレビューチェックリスト結果

---

### タスク3: アーキテクチャ整合性レビュー

**目的**: 認可ロジックが適切なレイヤーに配置されているか検証する

**レビュー観点**: アーキテクチャ

**レビューチェックリスト**:

- [ ] **レイヤー配置**: 認可ロジックがサービス層に配置されているか
  - Repository層ではなくService層で認可チェック
  - Controller/IPC層は認可結果を利用するのみ

- [ ] **依存関係逆転の原則(DIP)**: 依存関係が適切か
  - 認可ロジックが具体的な実装に依存していないか
  - インターフェースを通じた依存になっているか

- [ ] **既存設計との整合性**: 既存のチャット履歴サービス設計と整合しているか
  - IChatHistoryServiceインターフェースの変更が適切か
  - Repository層への影響がないか

- [ ] **後方互換性**: 既存の呼び出し元への影響が適切に管理されているか
  - シグネチャ変更による影響箇所が全て特定されているか

**期待される成果物**:

- アーキテクチャレビューチェックリスト結果

---

### タスク4: レビュー結果の判定

**目的**: レビュー結果を総合判定し、次のアクションを決定する

**実行手順**:

1. 各レビュー観点の結果を集計する
2. 以下の基準で判定を行う：

   | 判定     | 条件                     | 次のアクション            |
   | -------- | ------------------------ | ------------------------- |
   | PASS     | 全レビュー観点で問題なし | Phase 4へ進行             |
   | MINOR    | 軽微な指摘あり           | 指摘対応後、Phase 4へ進行 |
   | MAJOR    | 重大な問題あり           | 影響範囲に応じて戻る      |
   | CRITICAL | 致命的な問題あり         | Phase 1へ戻りユーザー確認 |

3. 指摘事項がある場合は対応方針を決定する

**期待される成果物**:

- レビュー判定結果
- 指摘事項一覧（該当する場合）
- 対応方針（該当する場合）

---

### タスク5: レビュー結果報告書の作成

**目的**: レビュー結果を文書化し、記録として残す

**実行手順**:

1. `outputs/phase-3/` ディレクトリを作成する
2. 以下の内容を含むレビュー報告書を作成する：
   - レビュー実施日
   - 各レビュー観点の結果
   - 総合判定
   - 指摘事項と対応方針（該当する場合）
3. 報告書を保存する

**期待される成果物**:

- `outputs/phase-3/design-review-report.md`
