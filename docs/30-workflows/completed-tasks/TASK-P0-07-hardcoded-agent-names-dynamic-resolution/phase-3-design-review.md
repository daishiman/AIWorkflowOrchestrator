## 実行手順

### タスク1: 真の論点の確認

#### 主問題（1文）

manifest を主正本としてエージェントリソースを動的に解決し、静的定数はフォールバックに限定する。

#### 複数案件の切り分け

| #   | 案件                                             | 本タスクのスコープ |
| --- | ------------------------------------------------ | ------------------ |
| 1   | plan()/improve() の動的リソース解決              | スコープ内         |
| 2   | SkillCreatorWorkflowEngine の phase 状態機械変更 | スコープ外         |
| 3   | workflow-manifest.json の内容変更                | スコープ外         |
| 4   | ManifestLoader 自体の変更                        | スコープ外         |

#### why now / why this way

- **why now**: TASK-P0-03（manifest 配置）と TASK-P0-04（ManifestLoader 有効化）が完了し、動的解決の前提条件が整った
- **why this way**: manifest を正本とし静的定数をフォールバックとする二重構造は、後方互換性を維持しつつ段階的移行を実現する最もリスクの低いアプローチ

### タスク2: 因果と境界の確認

#### 因果ループ

**強化ループ（manifest 正本化）**:

```
manifest 更新 → 動的解決で即座に反映 → コード変更不要
  → 保守コスト低下 → manifest 管理への信頼向上 → manifest 更新の活発化
```

**バランスループ（フォールバック安全弁）**:

```
manifest 不在/破損 → フォールバック発動 → 静的定数で動作継続
  → 動作後退なし → 段階移行の安全性確保
  → manifest 依存度が過度に上がらない
```

#### 状態所有権

| コンポーネント                | 所有する状態                                 | 変更有無 |
| ----------------------------- | -------------------------------------------- | -------- |
| `ManifestLoader`              | manifest のロード状態・キャッシュ            | 変更なし |
| `SkillCreatorSourceResolver`  | manifest へのアクセス経路                    | 変更なし |
| `RuntimeSkillCreatorFacade`   | 動的/静的パスの選択判定                      | 変更あり |
| `manifestResourceResolver.ts` | manifest → PhaseResourceRequest 変換ロジック | 新規追加 |
| `planPromptConstants.ts`      | 静的エージェントリスト（フォールバック）     | 変更なし |
| `improvePromptConstants.ts`   | 静的エージェントリスト（フォールバック）     | 変更なし |

#### 責務境界の確認

- **Facade**: 動的/静的パスの選択と、結果の組み立て → 変更は選択ロジックのみ
- **manifestResourceResolver**: manifest → PhaseResourceRequest 変換の純粋関数 → 新規だが Facade の責務を侵さない
- **Engine**: phase 遷移ロジック → 本タスクでは触れない（スコープ外）

### タスク3: 価値とコストの見方

#### 初回スコープで得る価値

| 価値                                          | 受益者         |
| --------------------------------------------- | -------------- |
| manifest 変更だけでエージェントリスト更新可能 | 開発者・運用者 |
| コード内のハードコード依存の解消              | 保守担当者     |
| 設計原則「manifest を主正本とする」の実現     | アーキテクト   |

#### 導入コストが最も大きい部品

| 部品                                     | コスト要因                                            |
| ---------------------------------------- | ----------------------------------------------------- |
| `buildPhaseResourceRequestsFromManifest` | 新規実装 + テスト追加（ただし純粋関数で複雑度は低い） |
| Facade の plan()/improve() 変更          | 既存動的パスの引数差し替え（影響範囲は限定的）        |

#### 将来拡張との分離

| 項目                                  | 初回スコープ | 将来層         |
| ------------------------------------- | ------------ | -------------- |
| plan/improve の動的解決               | 対象         | -              |
| execute/verify/requirements-gathering | -            | 別タスクで対応 |
| phase 状態機械の manifest 同期        | -            | 別タスクで対応 |

### タスク4: 4条件の評価

| 条件   | 評価 | 根拠                                                                                               |
| ------ | ---- | -------------------------------------------------------------------------------------------------- |
| 価値性 | OK   | manifest 変更時のコード同時変更が不要になり、開発者の保守コストを直接的に下げる                    |
| 実現性 | OK   | 純粋関数1つの新規追加 + Facade の引数差し替え2箇所のみ。初回スコープで実装可能な厚みに収まっている |
| 整合性 | OK   | 責務境界を侵さず、状態所有権も既存構造を維持。manifestResourceResolver は純粋関数で副作用なし      |
| 運用性 | OK   | フォールバック発動時に warn ログが出るため検知可能。manifest 不在環境でも動作後退なし              |
