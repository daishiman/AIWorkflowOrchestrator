| 項目 | 内容                                                                                                              |

| 候補 | `buildPhaseResourceRequestsFromManifest()` → `resolvePhaseResources()` 等                                         |

| 理由 | 40 文字だが意図が明確。使用箇所は Facade 内 2 箇所 + テストのみ。短縮すると「何から」ビルドするかの情報が失われる |

### パターン3: kind→tier マッピングの定数化

| 項目 | 内容                                                                                                                                                                  |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 候補 | `KIND_TO_TIER_MAP` 定数オブジェクトとして分離                                                                                                                         |
| 判断 | **見送り**（現状維持）                                                                                                                                                |
| 理由 | 現状は agent vs それ以外の二分岐のみ。`const isAgent = resource.kind === "agent"` は十分に可読で、4 種の kind 全てが同じ「non-agent」ルールなので lookup table は過剰 |

### パターン4: パス変換ヘルパーの分離

| 項目 | 内容                                                                                      |
| ---- | ----------------------------------------------------------------------------------------- |
| 候補 | `normalizeRelativePath(path: string): string` ヘルパーとして分離                          |
| 判断 | **見送り**（現状維持）                                                                    |
| 理由 | `path.replace(/^\.\//, "")` は 1 行・1 箇所のみの使用。抽出は関数数を増やすだけで効果なし |
