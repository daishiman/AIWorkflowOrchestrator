## 目的

Phase 2 で設計した削除手順が安全であることをレビューし、実装に進むかどうかのゲート判定を行う。

## 実行タスク

- タスク1: 削除対象と残す現行フローの境界をレビューする
- タスク2: 4条件でリスクを再評価する
- タスク3: PASS / MINOR / MAJOR の戻り先を確定する

## チェック観点

- [ ] dead code の削除が他の現行コードに影響しないことを確認（使われているコードを誤って削除しない）
- [ ] 削除後に `useState` のインポートが不要になる場合は合わせて削除または整理する
- [ ] 削除する state が JSX 内のどこかで参照されていないか全行確認する
- [ ] `_handleSubmitWorkflowInput` が将来の実装に向けたスタブとして意図的に残されていないか確認する
- [ ] 後続タスク（RALLY-005〜RALLY-008）の設計前提に影響がないことを確認する

## リスク評価

| リスク                                                | レベル | 対処                                           |
| ----------------------------------------------------- | ------ | ---------------------------------------------- |
| `_handleSubmitWorkflowInput` が外部から参照されている | 低     | 削除前に grep で全件確認（Phase 1 で実施済み） |
| state が JSX で参照されていてビルドエラーが発生       | 低〜中 | 削除後に typecheck で確認                      |
| 削除対象が実は将来実装のスタブだった                  | 低     | コミット履歴で追加意図を確認                   |
| `useState` インポートが他の state でも使われている    | 低     | インポートを削除しないか、削除前に全state確認  |

## ゲート判定基準

| 判定                   | 条件                                                       |
| ---------------------- | ---------------------------------------------------------- |
| PASS（Phase 4に進む）  | 全チェック観点でリスクなし、または低リスクで対処方針が明確 |
| MINOR（Phase 2に戻る） | 設計の一部修正が必要だが実装は可能                         |
| MAJOR（Phase 2に戻る） | 削除対象に問題があり、再調査・再設計が必要                 |

## 統合テスト連携

- Phase 4 は PASS 判定を前提に開始する
- MINOR / MAJOR の場合は test plan を更新してから再レビューする
