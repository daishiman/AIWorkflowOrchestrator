## 目的

Phase 2 で設計した修正方針の妥当性を検証する。プロダクションコードへの影響がないこと、非同期エラーハンドリングの一貫性、テスト間の副作用の有無を確認する。

## 実行タスク

- レビュー観点確認: 観点 1〜5 を順番に確認し、判定根拠を記録する。
- 統合観点確認: 統合テスト連携の項目を確認し、Phase 4 へ引き継ぐ観点を明確化する。
- 判定確定: PASS/MINOR/MAJOR を判定し、MAJOR の場合は Phase 1 または Phase 2 への差し戻し先を明記する。

## 判定基準

| 判定              | 条件                                                                     | 対応                      |
| ----------------- | ------------------------------------------------------------------------ | ------------------------- |
| PASS              | 全観点で問題なし                                                         | Phase 4 へ進行            |
| MINOR             | 軽微な指摘あり（コードスタイル、命名改善等）                             | 指摘対応後 Phase 4 へ進行 |
| MAJOR（要件問題） | 要件の漏れ・矛盾がある（失敗テストの特定漏れ、スコープ逸脱等）           | Phase 1 へ戻る            |
| MAJOR（設計問題） | 設計方針に重大な問題がある（プロダクション動作変更、副作用の見落とし等） | Phase 2 へ戻る            |

## レビュー観点

### 観点 1: プロダクションコードへの影響

| チェック項目                                                                 | 判定 |
| ---------------------------------------------------------------------------- | ---- |
| テストコードのみの修正で完結するケースが正しく識別されているか               | -    |
| プロダクションコード修正が必要なケースで、修正が実行時動作を変えないか       | -    |
| fire-and-forget パターンの修正が副作用を引き起こさないか                     | -    |
| 修正対象のプロダクションコードに対するリグレッションテストが設計されているか | -    |

### 観点 2: 非同期エラーハンドリングの一貫性

| チェック項目                                                              | 判定 |
| ------------------------------------------------------------------------- | ---- |
| 修正パターン（P-AWAIT/P-CATCH/P-MOCK/P-CLEANUP/P-FIRE/P-TIMER）が網羅的か | -    |
| 各パターンの修正アプローチが `error-handling.md` の方針と整合しているか   | -    |
| `try/catch` と `.catch()` の使い分けが明確か                              | -    |
| 非同期クリーンアップ（`afterEach` / `afterAll`）の設計が一貫しているか    | -    |

### 観点 3: テスト間の副作用

| チェック項目                                                                                 | 判定 |
| -------------------------------------------------------------------------------------------- | ---- |
| 修正がテスト間の状態リークを引き起こさないか（P9 参照）                                      | -    |
| グローバルモック（`src/test/setup.ts`、`src/test/__mocks__/`）の変更が他テストに影響しないか | -    |
| `vi.useFakeTimers()` の修正が他テストのタイマー処理と競合しないか（P13 参照）                | -    |
| テスト実行順序に依存する設計になっていないか                                                 | -    |

### 観点 4: 修正の完全性

| チェック項目                                                                      | 判定 |
| --------------------------------------------------------------------------------- | ---- |
| Phase 1 の失敗テストリスト全件に修正パターンが割り当てられているか                | -    |
| 修正優先度の順序が依存関係を正しく反映しているか                                  | -    |
| `dangerouslyIgnoreUnhandledErrors` 削除後に全テストが PASS する設計になっているか | -    |

### 観点 5: Vitest/Electron 固有の考慮

| チェック項目                                                                                     | 判定 |
| ------------------------------------------------------------------------------------------------ | ---- |
| happy-dom 環境での非同期処理の制約が考慮されているか                                             | -    |
| Vitest の `pool: "forks"` 設定との相互作用が考慮されているか                                     | -    |
| Vitest Worker の予期しない終了（P22）のリスクが評価されているか                                  | -    |
| `@anthropic-ai/claude-agent-sdk` モック（vitest.config.ts の alias）との整合性が確認されているか | -    |

## 統合テスト連携【必須】

統合テスト観点のレビューゲートを実施:

| レビュー観点       | 確認項目                                                                      |
| ------------------ | ----------------------------------------------------------------------------- |
| テストセットアップ | `src/test/setup.ts` の修正がグローバルモック全体に与える影響を評価            |
| エラーハンドリング | 非同期エラーのハンドリング方針がテストスイート全体で統一されているか          |
| テスト安定性       | 修正後のテストが並列実行（`fileParallelism: true`）で安定するか               |
| モック整合性       | `src/test/__mocks__/` 配下のモック修正が IPC/SDK/Store の全テストと整合するか |

## 多角的チェック観点

| 観点               | 適用 | 確認項目                                                                        |
| ------------------ | ---- | ------------------------------------------------------------------------------- |
| エラーハンドリング | 該当 | 修正パターンが error-handling.md の方針（Result<T,E> パターン等）と矛盾しないか |
| アーキテクチャ     | 該当 | 修正がレイヤー構造（Renderer→Preload→Main）を壊さないか                         |
| パフォーマンス     | 該当 | `await` 追加による直列化でテスト実行時間が大幅に増加しないか                    |
