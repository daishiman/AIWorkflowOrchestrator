## 1. MECE検証結果

### 1-1. 4タスクの責務分離（相互排他性: Mutually Exclusive）

| タスク | 責務レイヤー             | 主要変更対象                                              | 重複判定         |
| ------ | ------------------------ | --------------------------------------------------------- | ---------------- |
| Task 1 | Store/エラーハンドリング | `chatSlice.ts`, `ChatView/index.tsx`                      | Task 4と部分重複 |
| Task 2 | UI/導線                  | `ChatView/index.tsx`, `WorkspaceView`                     | Task 1と軽微重複 |
| Task 3 | 永続化/インフラ          | `llmSlice.ts`, `store/index.ts`                           | 独立             |
| Task 4 | ストリーミング/エラーUX  | `useWorkspaceChatController.ts`, `WorkspaceChatPanel.tsx` | Task 1と部分重複 |

**重複箇所の詳細:**

| 重複ペア   | 重複内容                                                                                                                                                        | リスク                                                                   |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Task 1 ↔ 4 | エラーコード定義が両タスクに存在（`ERROR_MESSAGES` / `mapLLMErrorToStreamingError`）。同一エラーコード（`API_KEY_MISSING`, `RATE_LIMIT`等）を別々に定義する設計 | エラーコード定義の二重管理。将来のコード追加時に片方のみ更新されるリスク |
| Task 1 ↔ 2 | `ChatView/index.tsx` を両タスクが変更対象としている                                                                                                             | コンフリクトリスク（並列実行時）                                         |
| Task 2 ↔ 4 | Settings画面遷移ロジック（`setCurrentView("settings")`）を両タスクで独立実装                                                                                    | 共通ヘルパーの欠如。DRY違反                                              |

**判定: 部分的に排他性不足**

### 1-2. 網羅性検証（Collectively Exhaustive）

「AIと対話できない問題」の全原因カテゴリを列挙し、4タスクのカバレッジを確認する:

| 原因カテゴリ                                   | カバータスク | カバー状況   |
| ---------------------------------------------- | ------------ | ------------ |
| A. APIキー未設定                               | Task 1, 4    | カバー済み   |
| B. Provider/Model未選択（導線不足）            | Task 2       | カバー済み   |
| C. Provider/Model選択が再起動で消える          | Task 3       | カバー済み   |
| D. LLM API呼び出し失敗（エラー握りつぶし）     | Task 1       | カバー済み   |
| E. ストリーミングエラーのUX不足                | Task 4       | カバー済み   |
| **F. Preload Bridge/IPC通信自体の失敗**        | なし         | **未カバー** |
| **G. Main ProcessのLLMアダプター初期化失敗**   | なし         | **未カバー** |
| **H. ネットワーク接続不可（オフライン状態）**  | Task 4(部分) | **部分的**   |
| **I. APIキー入力UIの問題（Settings画面自体）** | スコープ外   | 意図的除外   |
| **J. 認証トークン期限切れ（OAuth Provider）**  | なし         | **未カバー** |

**漏れている原因カテゴリ:**

1. **F: Preload Bridge/IPC通信自体の失敗** — `window.electronAPI` が `undefined`（Task 1の`AI_UNAVAILABLE`で部分対応）だが、IPC応答が返らないケース（タイムアウト）は未定義
2. **G: Main ProcessのLLMアダプター初期化失敗** — Provider設定は正しいがアダプターのインスタンス化に失敗するケース（SDK互換性問題等）
3. **H: オフライン状態** — Task 4で`NETWORK_ERROR`をカバーしているが、ChatView（Task 1）側のオフラインハンドリングが不明確。アプリ起動時のオフライン検知と通知がない
4. **J: OAuth Provider認証期限切れ** — トークンリフレッシュ失敗時のエラーUI/リカバリフローが未定義

**判定: 主要パスはカバー済みだが、エッジケースに漏れあり**

## 2. 要素分解マトリクス

ユーザーフロー全ステップに対する4タスクのカバレッジ:

```
ユーザーフロー:
[Settings画面] → [APIキー入力] → [Provider選択] → [Model選択] → [ChatView開く]
→ [メッセージ入力] → [送信ボタン] → [IPC送信] → [Main Process受信]
→ [LLMアダプター] → [外部API呼び出し] → [レスポンス受信] → [IPC応答]
→ [ストリーミング受信] → [UI表示]
```

| ステップ                      | Task 1     | Task 2 | Task 3 | Task 4     | カバー状況                           |
| ----------------------------- | ---------- | ------ | ------ | ---------- | ------------------------------------ |
| Settings画面（APIキー入力）   | -          | -      | -      | -          | **スコープ外（意図的）**             |
| Provider選択                  | -          | 導線   | 永続化 | -          | カバー済み                           |
| Model選択                     | -          | 導線   | 永続化 | -          | カバー済み                           |
| ChatView表示                  | -          | バナー | -      | -          | カバー済み                           |
| メッセージ入力                | -          | -      | -      | -          | 変更不要                             |
| 送信ボタン押下                | -          | -      | -      | -          | 変更不要                             |
| **IPC送信（Preload Bridge）** | 部分       | -      | -      | -          | **部分的**（`AI_UNAVAILABLE`のみ）   |
| **Main Process受信**          | -          | -      | -      | -          | **未カバー**                         |
| **LLMアダプター呼び出し**     | -          | -      | -      | -          | **未カバー**                         |
| **外部API呼び出し**           | -          | -      | -      | -          | **未カバー**（エラー時のみTask 1/4） |
| レスポンス受信（成功）        | -          | -      | -      | -          | 変更不要                             |
| レスポンス受信（エラー）      | エラー表示 | -      | -      | エラー表示 | カバー済み                           |
| ストリーミング受信            | -          | -      | -      | UX改善     | カバー済み                           |
| UI表示                        | バナー     | バナー | -      | エラーUI   | カバー済み                           |

**要素分解の結論:**

- Renderer層（UI/Store）のカバレッジは高い
- **Main Process層（アダプター/IPC Handler）のエラーハンドリングは4タスクのスコープ外**
- 外部API呼び出し自体の成功パスは変更不要だが、Main Process内部でのエラー変換・エラーコード標準化がどこで行われるかが不明確

## 3. 共通パターン抽出（帰納的分析）

### 3-1. 横断課題: エラーコード定義の分散

| 抽出パターン                         | 発生箇所                                                                      | 影響                                                       |
| ------------------------------------ | ----------------------------------------------------------------------------- | ---------------------------------------------------------- |
| エラーコードのハードコード定数化     | Task 1: `ERROR_MESSAGES` Record, Task 4: `mapLLMErrorToStreamingError` switch | 同一エラーコード（`API_KEY_MISSING`等）が2箇所で定義される |
| Settings遷移パターンの独立実装       | Task 2: `setCurrentView("settings")`, Task 4: `handleOpenSettings`            | 遷移ロジックの重複                                         |
| エラーメッセージの日本語ハードコード | Task 1, Task 4 両方                                                           | i18n移行時に2箇所の修正が必要                              |

**横断的解決策の提案:**

1. **エラーコード定数を `packages/shared` に一元化する**: `LLMErrorCode` enum と `ERROR_MESSAGES` Record を shared パッケージに配置し、Task 1/4 の両方から参照する
2. **Settings遷移ヘルパーの共通化**: `useNavigateToSettings()` カスタムフックを作成し、Task 2/4 で共用する
3. **エラーメッセージ定数の集約**: 将来のi18n対応に備え、エラーメッセージ定義を1ファイルに集約する

### 3-2. 横断課題: Apple HIG準拠の重複定義

Task 1, 2, 4 全てで同一の Apple HIG カラー値（`systemRed`, `systemBlue`）を個別に定義している。デザイントークンとして CSS変数またはTailwind設定に一元化すべき。

### 3-3. 横断課題: P50チェックの4タスク並行実施

全4タスクが Phase 1 で独立にP50チェック（既実装調査）を実施する設計だが、調査対象ファイルが部分的に重複している（`ChatView/index.tsx` 等）。P50チェック結果を共有する仕組みがない。

## 4. メタ分析（分解方法自体の妥当性）

### 4-1. 現在の分解軸: 「問題種別」

4タスクは以下の軸で分解されている:

- Task 1: エラー握りつぶし（バグ修正）
- Task 2: 導線不足（UX改善）
- Task 3: 永続化欠如（機能追加）
- Task 4: エラーUX不足（UX改善）

### 4-2. 代替分解軸の検討

| 分解軸                  | メリット                                     | デメリット                                 | 推奨度   |
| ----------------------- | -------------------------------------------- | ------------------------------------------ | -------- |
| **問題種別（現行）**    | SRP準拠、各タスクの責務が明確                | エラーコード定義の重複、Settings遷移の重複 | **採用** |
| レイヤー別              | Main/Preload/Renderer の変更が集約される     | 1タスクの責務が広くなりすぎる              | 不採用   |
| ユーザーフロー別        | E2Eシナリオとの対応が明確                    | 技術的に無関係な変更が1タスクに混在する    | 不採用   |
| 画面別                  | ChatView修正とWorkspace修正を分離            | エラーハンドリングが画面ごとに断片化する   | 不採用   |
| **問題種別 + 共通基盤** | 現行 + エラーコード/遷移の共通化タスクを追加 | タスク数が増える                           | **最適** |

### 4-3. メタ分析の結論

現行の「問題種別」分解は概ね適切だが、**共通基盤タスク（Task 0）** を追加すべき:

> **Task 0（提案）: LLMエラーコード定数・Settings遷移ヘルパーの共通化**
>
> - `packages/shared` に `LLMErrorCode` enum を定義
> - `ERROR_MESSAGES` Record を共通定数として配置
> - `useNavigateToSettings()` フックを作成
> - Task 1, 2, 4 はこの共通基盤を参照する

## 5. 仮説検証

### 仮説: 「4タスク完了後にユーザーがスムーズにAIと対話できる」

#### 仮説が真になるシナリオ

1. APIキー設定済み + Provider/Model選択済み + ネットワーク正常 → メッセージ送信成功
2. APIキー未設定 → Task 2のバナーで認知 → Settings遷移 → 設定完了 → 対話開始
3. Model未選択 → Task 2のバナーで認知 → Settings遷移 → 選択完了 → 対話開始
4. アプリ再起動 → Task 3で設定復元 → そのまま対話継続
5. API呼び出し失敗 → Task 1のエラーバナーで認知 → 原因に応じた対処

#### 仮説が偽になるシナリオ（リスク）

| #   | シナリオ                                                                               | 発生確率 | 影響度 | カバー状況                                       |
| --- | -------------------------------------------------------------------------------------- | -------- | ------ | ------------------------------------------------ |
| 1   | Settings画面でAPIキーを入力したが、入力フォーマットが不正でバリデーションエラー        | 中       | 高     | **未カバー**（Settings画面はスコープ外）         |
| 2   | Provider/Model選択後、Task 3で永続化されたが、Provider側でモデルが廃止された           | 低       | 中     | Task 3で対応（nullクリア）                       |
| 3   | ChatViewでメッセージ送信したが、Main ProcessのLLMアダプターが未初期化                  | 低       | 高     | **未カバー**                                     |
| 4   | ストリーミング中にネットワークが切断され、エラーコールバックが発火しない（静かな失敗） | 中       | 高     | **部分的**（Task 4はonStreamErrorに依存）        |
| 5   | 複数のエラーが高速連続で発生し、UIが不安定になる                                       | 低       | 中     | Task 4のPhase 10でエッジケースとして定義済み     |
| 6   | APIキーは正しいが、レート制限により全リクエスト失敗 → リトライでさらに制限             | 中       | 中     | Task 4で対応（RATE_LIMIT + ヒント）              |
| 7   | Task 3の永続化値がelectron-storeの破損で読めない                                       | 低       | 中     | **未カバー**（Task 3のmigrate関数がcatchしない） |

**重要リスク（対策不足）:**

- **#1**: Settings画面のAPIキーバリデーション。4タスク全てで「Settings画面自体はスコープ外」としているが、Settings画面の品質がこの改善の成否を左右する
- **#4**: ストリーミング中のサイレント失敗。`onStreamError`が発火しないケース（ネットワーク切断でWebSocketが無応答になるケース）への対策がない。タイムアウト検知が必要
