## レビュー観点

### 観点 0: 要件との整合性

| チェック項目                                         | 期待結果                     | 結果 |
| ---------------------------------------------------- | ---------------------------- | ---- |
| Phase 1で定義した全要件が設計に反映されているか      | 全要件カバー                 |      |
| 統一APIのスコープが元タスク仕様と一致するか          | スコープ一致                 |      |
| 前提タスク（FIX-1-1, FIX-4-1）の成果を活用しているか | 型定義・チャンネル定義を活用 |      |

### 観点 1: API設計の整合性

| チェック項目                                | 期待結果                         | 結果 |
| ------------------------------------------- | -------------------------------- | ---- |
| 全メソッドが仕様書§4の定義と一致するか      | 完全一致                         |      |
| 戻り値型が統一されているか                  | `OperationResult<T>` 廃止        |      |
| execute()のシグネチャが一意か               | `SkillExecutionRequest` 単一引数 |      |
| import()の引数が仕様書と一致するか          | `skillIds: string[]`             |      |
| 全イベントリスナーがunsubscribe関数を返すか | `() => void` 返却                |      |

### 観点 2: 型安全性

| チェック項目                                      | 期待結果                       | 結果 |
| ------------------------------------------------- | ------------------------------ | ---- |
| `SkillAPI` インターフェースがエクスポートされるか | `packages/shared` or `preload` |      |
| `window.electronAPI.skill` の型が正確か           | `SkillAPI` 型と一致            |      |
| TypeScript strictモードでコンパイル可能か         | エラーなし                     |      |

### 観点 3: 移行の実現可能性

| チェック項目                             | 期待結果                       | 結果 |
| ---------------------------------------- | ------------------------------ | ---- |
| 全呼び出し元の移行手順が明確か           | 7ステップ全て手順記載あり      |      |
| 破壊的変更の影響範囲が特定されているか   | skillSlice.ts が最大影響       |      |
| 段階的移行が可能か（一時的な互換性維持） | `window.skillAPI` 並行公開可能 |      |
| テスト修正の影響範囲が把握されているか   | モック対象の変更箇所リスト     |      |

### 観点 4: アーキテクチャの妥当性

| チェック項目                                                 | 期待結果       | 結果 |
| ------------------------------------------------------------ | -------------- | ---- |
| Preload層の責務が適切か（IPC呼び出しのラッパーのみ）         | 単一責務       |      |
| Renderer→Preload→MainのデータフローがMECEか                  | 重複・漏れなし |      |
| `architecture-implementation-patterns.md` のパターンに準拠か | 準拠           |      |

### 観点 5: セキュリティ（Electron Preload）

| チェック項目                                         | 期待結果                   | 結果 |
| ---------------------------------------------------- | -------------------------- | ---- |
| contextBridge経由の公開のみか                        | 直接expose禁止             |      |
| 公開API面の最小化（不要メソッド除外）                | 使用されるメソッドのみ公開 |      |
| IPC送信者バリデーション（validateIpcSender）が維持か | 既存バリデーション保持     |      |

## 統合テスト連携【必須】

| カテゴリ           | レビュー確認項目                                | 期待結果                           |
| ------------------ | ----------------------------------------------- | ---------------------------------- |
| API設計            | 統一API全メソッドのIPC通信設計が妥当か          | 全メソッドが正しいチャンネルを使用 |
| データフロー       | Renderer→Main往復のデータフローが明確か         | フロー図が設計書に含まれている     |
| エラーハンドリング | IPC通信エラー時の設計が明確か                   | throw/catchパターンが定義          |
| 認証連携           | 権限チェック（validateIpcSender）の維持が確認か | セキュリティ要件が設計に反映       |

## 判定基準

| 判定     | 条件                                   | 対応                                                     |
| -------- | -------------------------------------- | -------------------------------------------------------- |
| PASS     | 全観点で問題なし                       | Phase 4へ進行                                            |
| MINOR    | 軽微な改善提案あり                     | `unassigned-task/` に未タスク指示書を作成後Phase 4へ進行 |
| MAJOR    | API設計の不整合や型安全性の問題あり    | Phase 2へ戻り設計修正                                    |
| CRITICAL | 仕様書との重大な乖離や移行不可能な問題 | Phase 1へ戻り要件再確認                                  |
