## 目的

## 実行タスク

### タスク1: ドキュメント構成の改善

**目的**: 仕様書の構成を見直し、読みやすさを向上させる

**手順**:

1. テーブルの読みやすさを改善する:
   - カラム幅を見直し、横幅が過大な場合はテーブルを分割する
   - カラムの記載順序が論理的か確認する（check ID -> 検証内容 -> severity -> 判定基準 -> エラーメッセージ）
   - 長い説明は本文へ逃がし、表には要点だけを残す
2. セクション間の論理的なフローを確認する:
   - Layer 1 -> Layer 2 -> Layer 3 -> Layer 4 の順序が自然か
   - 各 Layer の導入文が十分か
   - 拡張ガイドラインの配置が適切か
3. 冗長な記述を簡潔化する:
   - 同じ情報の繰り返しがないか確認する
   - 不要な修飾語を削除する

**成果物**: 構成改善の Before/After 記録

### タスク2: 表現の統一

**目的**: 仕様書全体の表現を統一し、一貫性を確保する

**手順**:

1. check ID の説明文の語尾を統一する:
   - 「〜する」「〜であること」「〜を検証」等、統一された語尾に揃える
   - 検証内容カラムと判定基準カラムで異なる語尾ルールを適用してよい
2. severity 記載の表記を統一する:
   - `error` / `warning` のフォーマット（バッククォート囲み等）を統一する
   - severity の説明が一貫しているか確認する
3. Layer 名称の日英表記を統一する:
   - 「Layer 1（構造検証）」のように日英併記するか、英語のみとするか統一する
   - 本文中の Layer 参照も同じ表記に揃える

> **Feedback RT-03 対応**: リファクタリング記録を Before/After/理由テーブル形式で記録すること。

**リファクタリング記録テンプレート**:

| #   | 対象箇所 | Before | After | 理由 |
| --- | -------- | ------ | ----- | ---- |
| 1   |          |        |       |      |
| 2   |          |        |       |      |

**成果物**: 表現統一の Before/After/理由テーブル
