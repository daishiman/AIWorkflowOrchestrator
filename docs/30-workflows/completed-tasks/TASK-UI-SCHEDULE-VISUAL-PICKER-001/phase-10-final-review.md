## ゲート判定基準テーブル

| 判定         | 基準                                                     | 次のアクション                                         |
| ------------ | -------------------------------------------------------- | ------------------------------------------------------ |
| **PASS**     | A〜E の全チェック項目で問題なし                          | Phase 11（手動テスト・目視確認）へ進む                 |
| **MINOR**    | 軽微な指摘あり（Phase 11 の進行を妨げない）              | 指摘事項を記録し Phase 11 へ進む（次フェーズ中に対処） |
| **MAJOR**    | いずれかのチェックで重大な未達がある                     | 該当する Phase（7〜9）へ差し戻し、修正後に再レビュー   |
| **CRITICAL** | 受入基準・セキュリティの致命的な問題または設計前提の崩壊 | Phase 1 または Phase 2 へ戻り、ユーザー確認を実施      |

### 差し戻し先決定基準

| 問題カテゴリ                     | 差し戻し先 |
| -------------------------------- | ---------- |
| 受入基準の未達（機能が動かない） | Phase 5〜6 |
| カバレッジ目標未達               | Phase 7    |
| コード品質・リファクタリング未了 | Phase 8    |
| セキュリティ・パフォーマンス問題 | Phase 9    |
| 設計の根本的な問題               | Phase 2〜3 |
| 要件の抜け・矛盾                 | Phase 1    |

## 多角的チェック観点

| 思考法           | 確認内容                                                                            |
| ---------------- | ----------------------------------------------------------------------------------- |
| ユーザー中心思考 | AC-01〜AC-14 の全受入基準が「ユーザーが実際に使える状態」になっているか             |
| 逆説思考         | 全チェックがPASSしているが、手動テストで初めて発覚する問題が残っていないか          |
| システム思考     | Phase 1〜9 の成果物が一貫して整合しており、矛盾や抜けがないか横断的に確認しているか |
| 制約思考         | MAJOR 以上の判定が出た場合の差し戻し先と修正コストが見積もれているか                |
| 水平思考         | 同種の機能（GitHub Actions cron UI 等）と比較して品質水準が妥当か                   |
| 垂直思考         | セキュリティ確認が表層的でなく、コードレベルで実証されているか                      |
