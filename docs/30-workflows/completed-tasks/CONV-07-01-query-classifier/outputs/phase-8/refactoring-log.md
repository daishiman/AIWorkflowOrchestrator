## リファクタリング判断

### 仕様書提案の評価

| 提案                         | 判断       | 理由                                                                                     |
| ---------------------------- | ---------- | ---------------------------------------------------------------------------------------- |
| constants.ts作成             | **見送り** | SEARCH_WEIGHTSは既にtypes.tsに定義済み。分離による複雑性増加がメリットを上回る           |
| utils.ts作成                 | **見送り** | キーワード抽出は分類器固有ロジック。共通化による再利用メリットが現時点で低い             |
| patterns.ts作成              | **見送り** | パターンはルールベース分類器の実装詳細。外部化による保守性向上より、局所性の利点が大きい |
| base-query-classifier.ts作成 | **見送り** | getSearchWeightsは2行の単純実装。継承よりもインターフェース準拠で十分                    |

### YAGNI原則に基づく判断

1. **現在の実装で十分な理由**
   - テスト186件が全てパス
   - カバレッジ94%+達成
   - 型安全性が確保されている
   - 単一責務原則を満たしている

2. **将来の拡張時に再検討すべき項目**
   - 3つ目以降の分類器実装時 → 共通基底クラス検討
   - 他モジュールでキーワード抽出が必要時 → utils.ts抽出検討
   - パターン定義が10+になった場合 → patterns.ts分離検討
