# Skill Feedback Report - Session Dock Artifact Bridge

## 概要

TASK-IMP-SESSION-DOCK-ARTIFACT-BRIDGE-001（設計タスク）の Phase 1-12 実行を通じて得られたスキル改善フィードバック。

## テンプレート改善

| ID   | 改善提案                                                                        | 優先度 |
| ---- | ------------------------------------------------------------------------------- | ------ |
| TF-1 | 設計タスクの Phase 11 テンプレートに「設計検証シナリオ」モードを追加            | 中     |
| TF-2 | Phase 12 の system-spec-update に「設計タスク vs 実装タスク」の分岐フローを追加 | 低     |

### TF-1 詳細

設計タスク（type: design）では実画面が存在しないため、Phase 11（手動テスト）が「手動テスト計画の作成」に読み替えられる。テンプレートレベルでこの分岐を明示すると、Phase 11 実行時の判断コストが減る。

### TF-2 詳細

Phase 12 Step 1-A〜Step 3 は実装タスクを前提とした手順になっている。設計タスクでは「計画のみ」が妥当だが、P57（先送りパターン）との判断が毎回必要。テンプレートに「設計タスクの場合は計画記録のみで可」と明記するとよい。

## ワークフロー改善

| ID   | 改善提案                                              | 優先度 |
| ---- | ----------------------------------------------------- | ------ |
| WF-1 | 設計タスクの Phase 4-9 を「設計検証」バッチとして統合 | 低     |

### WF-1 詳細

設計タスクでは Phase 4（テスト作成）〜Phase 9（品質検証）がすべて「設計文書の品質検証」として機能する。実装コードがないため、テストマトリクスやカバレッジ目標は「実装タスクでの基準定義」に留まる。これらを「Phase 4-9: 設計検証バッチ」として統合する選択肢がある。ただし、Phase 個別の成果物が後続タスクの参照資料として機能しているため、統合のメリットは限定的。

## ドキュメント改善

| ID   | 改善提案                                                         | 優先度 |
| ---- | ---------------------------------------------------------------- | ------ |
| DF-1 | artifacts.json の `type: "design"` 時の Phase 自動スキップルール | 低     |

### DF-1 詳細

`artifacts.json` に `type: "design"` が設定されている場合、特定の Phase（例: Phase 7 カバレッジ確認）は内容が限定的になる。Phase 仕様書に「設計タスク時の判定基準」を明記するか、artifacts.json に `designModeOverrides` フィールドを追加する選択肢がある。
