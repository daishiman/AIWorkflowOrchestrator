## 1. ワークフロー改善点

### 1.1 Phase 4-5 の実装・テスト並行化

Phase 4（実装）と Phase 5（テスト作成）を逐次実行しているが、設計書が確定した Phase 3 以降は TDD アプローチで並行作業が可能である。テストケース定義を先行させることで、実装中のフィードバックループが短縮できる。

**提案**: Phase 3 完了後に「テストケース骨格作成」サブフェーズを追加し、Phase 4 の実装と Phase 5 のテスト詳細化を並行実行可能にする。

### 1.2 Phase 6（テスト拡充）の判断基準明確化

テスト拡充フェーズで追加すべきテストの判断基準が属人的になりやすい。今回は severity filter のエッジケース（全件同一 severity、空配列、null）を網羅的に追加したが、事前にエッジケースパターンのチェックリストがあれば効率的だった。

**提案**: 設計書に「想定エッジケース一覧」セクションを設け、Phase 6 での漏れ検出を容易にする。

### 1.3 Phase 11 手動テストのスコープ定義

手動テストチェックリスト・スクリーンショット計画の作成において、自動テストとの重複を避けるスコープ定義が不明確だった。

**提案**: 「手動テストでのみ確認すべき項目」（視覚的レイアウト、アニメーション、実機特有の挙動）を Phase 2 設計書に明記する。

### 1.4 スクリーンショット harness の契約を本体型に合わせる

Playwright harness を使ったスクリーンショット取得では、`getVerifyDetail` のレスポンスだけでなく `getWorkflowState` が返す `workflowSnapshot` の形も本体実装と一致している必要があった。今回は `resumeTokenEnvelope` が不足していたため、画面自体は起動していても verify detail まで到達しなかった。

**提案**: screenshot 用モックのテンプレートを用意し、`workflowSnapshot` / `verifyDetail` / `handoffBundle` をそれぞれ別契約として記述する。これにより、将来の capture 失敗を早期に防げる。

## 2. 技術的教訓

### 2.1 useMemo による derived state パターン

```typescript
const filteredChecksByLayer = useMemo(() => {
  // severityFilter と checks から派生状態を計算
}, [checks, severityFilter]);
```

**学び**: フィルタリング結果をコンポーネント state ではなく `useMemo` による derived state として実装することで、以下の利点を得た。

- **単一の信頼源**: `severityFilter` state のみが変更ソースとなり、フィルタ結果の不整合が構造的に排除される
- **パフォーマンス**: 依存配列が変わらない限り再計算されないため、不要な再レンダリングを回避
- **テスタビリティ**: state 更新とフィルタ結果の同期を気にせずテストが書ける

**注意点**: `shouldShowCheck` 関数をコンポーネント外に定義し、純粋関数として切り出すことで、単体テスト可能性とメモ化の安定性を両立させた。

### 2.2 aria-pressed によるアクセシビリティ

セグメントコントロールの実装において、`role="group"` と `aria-pressed` を組み合わせた。

- `role="group"` でボタン群をグループ化（スクリーンリーダーに意味的なまとまりを伝達）
- `aria-pressed="true"` で選択中のボタンを明示（視覚に頼らない状態伝達）
- キーボードナビゲーション対応で Tab/Enter/Space による操作を保証

**学び**: WAI-ARIA のトグルボタンパターンに従うことで、追加の ARIA ライブラリなしにアクセシブルなセグメントコントロールを実現できた。テストケース TC-17/TC-18/TC-19 で自動検証も確保している。

### 2.3 件数サマリはフィルタ状態の可視化に効く

`表示中 X / 全 Y 件` の件数サマリは、フィルタ後の状態をユーザーに即時共有するのに有効だった。単に色や選択状態だけを見せるより、情報の絞り込み度合いが伝わりやすい。

**学び**: フィルタ UI では、トグル状態に加えて件数サマリを `role="status"` で出すと、視覚・支援技術の両方に対して説明力が上がる。

## 3. スキル改善提案（task-specification-creator 向け）

### 3.1 Phase 成果物テンプレートの充実

Phase 12 のドキュメント成果物（changelog, feedback-report）のテンプレートが抽象的で、毎回セクション構成を検討する必要がある。具体的な記入例やセクション説明を含むテンプレートがあると作成効率が向上する。

### 3.2 テストケースID命名規則の統一

今回のテストでは SF-TC-01〜SF-TC-09 と TC-10〜TC-19 で命名規則が混在した。Phase 2 の設計書段階でテストケースID体系を定義し、Phase 5/6 で一貫した命名を強制する仕組みがあると良い。

### 3.3 エッジケースチェックリストの標準化

UI フィルタリング系タスクで頻出するエッジケースパターン（空配列、null、全件同一値、境界値）を標準チェックリストとして提供すると、Phase 5/6 の品質が安定する。

## 4. 新規 Pitfall 候補

- `workflowSnapshot` の契約不足によるスクリーンショット capture 失敗

今回のタスクでは、`getVerifyDetail` だけをモックしても画面が成立せず、`workflowSnapshot.resumeTokenEnvelope` まで埋めないと `SkillLifecyclePanel` が例外を出すことが分かった。スクリーンショット自動化では、見た目の対象コンポーネントだけでなく、その手前のワークフロースナップショット契約も同時に満たす必要がある。
