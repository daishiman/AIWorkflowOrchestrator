## 目的

Phase 1〜2の成果物（要件定義・設計）をレビューし、実装に進むべきかを判断する。

## 背景

設計段階での問題を早期に発見し、手戻りを防ぐためのレビューゲートを実施する。

---

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: 要件レビュー

**目的**: 要件定義の妥当性を検証する。

**実行手順**:

1. 機能要件の網羅性を確認する
   - 会話一覧・詳細・入力・IPC接続の全機能が定義されているか
2. UI要件の妥当性を確認する
   - コンポーネント構成は適切か
   - レイアウト要件は明確か
3. 受け入れ基準の検証可能性を確認する
   - 各基準が明確に検証可能か
4. 発見課題をリスト化する

**期待される成果物**:

- レビュー結果メモ（設計レビュー結果ドキュメントにインライン記載）

---

### タスク2: 設計レビュー

**目的**: 設計の妥当性と整合性を検証する。

**実行手順**:

1. コンポーネント設計レビュー
   - Atomic Design原則への準拠
   - Props定義の型安全性
   - コンポーネント責務の明確さ
2. Preload API設計レビュー
   - IPCチャンネル名の一貫性
   - safeInvokeパターンの適用
   - ホワイトリスト登録の完全性
3. Hooks設計レビュー
   - 状態管理の適切さ
   - エラーハンドリングの設計
   - パフォーマンス考慮
4. データフロー設計レビュー
   - コンポーネント間の連携
   - IPC通信のフロー
5. 発見課題をリスト化する

**期待される成果物**:

- レビュー結果メモ

---

### タスク3: システム仕様との整合性確認

**目的**: 既存システム仕様との整合性を検証する。

**実行手順**:

1. ui-ux-history-panel.md との整合性確認
   - UIパターンの一貫性
   - コンポーネント構成の類似性
2. architecture-patterns.md との整合性確認
   - Zustand Sliceパターンへの準拠
   - Preload APIパターンへの準拠
3. interfaces-llm.md との整合性確認
   - 型定義の一貫性
   - IPC契約の整合性
4. 発見課題をリスト化する

**期待される成果物**:

- レビュー結果メモ

---

### タスク4: 統合テスト観点レビュー

**目的**: 統合テスト観点が設計に反映されているか確認する。

**実行手順**:

1. IPC通信のモック方針が明確か確認する
2. バックエンドAPI（conversationHandlers）との接続テスト方針が明確か確認する
3. エラーケースのテスト方針が明確か確認する
4. 発見課題をリスト化する

**期待される成果物**:

- レビュー結果メモ

---

### タスク5: レビュー結果判定

**目的**: レビュー結果を総合判定し、次のアクションを決定する。

**実行手順**:

1. 発見課題を重要度別に分類する
   - CRITICAL: 致命的な問題（要件不明確、設計矛盾）
   - MAJOR: 重大な問題（設計不備、整合性問題）
   - MINOR: 軽微な問題（記述不足、改善提案）
2. 総合判定を行う
   - PASS: 問題なし → Phase 4へ
   - MINOR: 軽微な指摘あり → 指摘対応後、Phase 4へ
   - MAJOR: 重大な問題あり → Phase 2へ戻り設計修正
   - CRITICAL: 致命的な問題あり → Phase 1へ戻りユーザー確認
3. 判定結果と理由をドキュメント化する

**期待される成果物**:

- `outputs/phase-3/design-review-result.md`
