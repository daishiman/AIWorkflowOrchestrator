## AC1: 永続化の正常動作

### 目的

インポートしたスキルがアプリ再起動後も正しく保持されることを保証する。

### 検証項目

| No  | 項目                                                   | 検証方法                                           |
| --- | ------------------------------------------------------ | -------------------------------------------------- |
| 1.1 | インポートしたスキルがアプリ再起動後も保持される       | E2E: インポート → 終了 → 再起動 → 一覧確認         |
| 1.2 | インポートリストが適切なelectron-storeパスに保存される | ストアファイルの存在確認                           |
| 1.3 | 保存されたデータの形式が正しい（`string[]`）           | ストアファイルの内容検証                           |
| 1.4 | 複数スキルのインポートが正しく保存される               | 3個以上のスキルをインポートし、再起動後に全て表示  |
| 1.5 | インポートと削除の組み合わせが正しく永続化される       | インポート → 削除 → インポート → 再起動 → 状態確認 |

### 完了条件

- [ ] 1.1: 3回連続で再起動テストがPASS
- [ ] 1.2: ストアファイルパスがログまたはテストで確認可能
- [ ] 1.3: ストアデータが `{"importedSkillIds": ["id1", "id2", ...]}` 形式
- [ ] 1.4: 5個のスキルをインポートし、再起動後に全て表示される
- [ ] 1.5: 複合操作シナリオがPASS

## AC2: 堅牢性の確保

### 目的

ストアデータの破損や不整合が発生しても、アプリがクラッシュせず適切にフォールバックすることを保証する。

### 検証項目

| No  | 項目                                                             | 検証方法                                                  |
| --- | ---------------------------------------------------------------- | --------------------------------------------------------- |
| 2.1 | ストアが空または存在しない場合でもアプリが起動する               | ストアファイルを削除して起動                              |
| 2.2 | 不正なデータ型が保存されている場合に空配列にフォールバックする   | ストアに `{"importedSkillIds": null}` を書き込み起動      |
| 2.3 | 配列以外の型（オブジェクト等）でも適切にハンドリングされる       | ストアに `{"importedSkillIds": {}}` を書き込み起動        |
| 2.4 | 配列内に不正な要素がある場合にサニタイズされる                   | ストアに `["id1", null, 123, "id2"]` を書き込み起動       |
| 2.5 | スキャンディレクトリに存在しないスキルIDが孤立IDとして処理される | 存在しないIDをストアに追加し、getImportedSkillsを呼び出し |

### 完了条件

- [ ] 2.1: ストアなしでアプリが正常起動し、空のスキル一覧が表示される
- [ ] 2.2: nullデータでクラッシュせず、空の状態で復旧
- [ ] 2.3: オブジェクト型でクラッシュせず、空の状態で復旧
- [ ] 2.4: 不正要素がフィルタリングされ、有効なIDのみ保持
- [ ] 2.5: 孤立IDがWARNログに出力され、表示はスキップされる

## AC3: 並行性の保証

### 目的

複数の同時操作が発生しても、データの整合性が保たれることを保証する。

### 検証項目

| No  | 項目                                                 | 検証方法                                             |
| --- | ---------------------------------------------------- | ---------------------------------------------------- |
| 3.1 | 複数のインポート操作が同時に発生しても全て保存される | 10並列のインポートリクエストを送信し、全て反映を確認 |
| 3.2 | インポートと削除が同時に発生しても整合性が保たれる   | インポートと削除を交互に100回並列実行                |
| 3.3 | persist操作が完了するまで次の操作が整合性を保つ      | タイミングテストで操作順序を検証                     |

### 完了条件

- [ ] 3.1: 10並列インポート後、全10件がストアに保存されている
- [ ] 3.2: 並列操作後の最終状態が期待通り（操作ログと一致）
- [ ] 3.3: 排他制御（mutex）のテストがPASS

## AC4: ログとエラーの整備

### 目的

本番環境でのログ出力を適切に制御し、エラーハンドリングを統一することを保証する。

### 検証項目

| No  | 項目                                                      | 検証方法                                           |
| --- | --------------------------------------------------------- | -------------------------------------------------- |
| 4.1 | DEBUGログが本番環境（production）で出力されない           | NODE_ENV=production で起動し、コンソール出力を確認 |
| 4.2 | DEBUGログが開発環境（development）で出力される            | NODE_ENV=development で起動し、DEBUGログを確認     |
| 4.3 | エラーレスポンス形式が `IPCResult<T>` で統一されている    | 全skillハンドラーのレスポンス形式を確認            |
| 4.4 | エラーコードが一貫性を持って設定されている                | エラーケースごとにコードが重複なく定義             |
| 4.5 | トラブルシューティング用のINFO/WARNログが適切に出力される | 孤立ID検出時のWARNログを確認                       |

### 完了条件

- [ ] 4.1: production環境で `[DEBUG]` を含むログが0件
- [ ] 4.2: development環境で `[DEBUG]` ログが適切に出力
- [ ] 4.3: 全IPCレスポンスが `{ success, data?, error? }` 形式
- [ ] 4.4: エラーコード一覧がドキュメント化されている
- [ ] 4.5: 孤立ID発生時に `[WARN]` ログが出力される
