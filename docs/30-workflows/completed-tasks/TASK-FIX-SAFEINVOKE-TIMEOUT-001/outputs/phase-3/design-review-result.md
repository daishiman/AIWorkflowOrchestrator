## 3. エッジケース検証

| エッジケース                        | 設計での対応                                                                                                                                                                               | 判定 |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---- |
| IPC_TIMEOUT_MS ちょうどで応答       | `Promise.race` の仕様で先に settle した方が勝つ。同時 settle は JS イベントループの microtask 順序で決定される。実用上、IPC 応答がちょうど5000msで返ることは極めて稀であり、問題にならない | OK   |
| Main Process がエラーで reject      | `Promise.race` で IPC エラーが先に reject される。タイムアウト Timer は5秒後に実行されるが、Promise は既に settled のため無視される                                                        | OK   |
| 複数の safeInvoke 同時呼び出し      | 各呼び出しが独立した Timer と IPC Promise を持つ。相互に干渉しない                                                                                                                         | OK   |
| IPC_TIMEOUT_MS = 0                  | 即座にタイムアウト reject される。定数として5000が定義されているため通常発生しない。仮に0に設定されても動作は定義済み（即時タイムアウト）                                                  | OK   |
| Preload 未読み込み時                | `ipcRenderer` が undefined の場合、`ipcRenderer.invoke()` の呼び出し時点で例外が発生する。helper 追加前と同じ挙動                                                                          | OK   |
| タイムアウト後に遅延 IPC 応答が到着 | Promise は既に rejected のため、遅延 resolve は無視される。Renderer の状態を再遷移させない                                                                                                 | OK   |
| channel 名に特殊文字が含まれる      | channel 名はホワイトリスト内の定数文字列のみ。エラーメッセージへの文字列埋め込みによるインジェクションリスクはない                                                                         | OK   |
