## 2. リファクタリング検討項目

### 2.1 検討対象

| 項目                   | 検討結果 | 理由                       |
| ---------------------- | -------- | -------------------------- |
| safeInvoke/safeOn 統合 | 不要     | 責務が明確に分離されている |
| チャネル定義の集約     | 不要     | channels.ts で適切に管理   |
| エラーハンドリング統一 | 不要     | 現状で一貫性がある         |
| 型定義の外部化         | 不要     | @repo/shared で管理済み    |

### 2.2 リファクタリング不要の根拠

1. **safeInvoke/safeOn**:
   - invoke (R→M) と on (M→R) は本質的に異なる操作
   - 分離することでセキュリティチェックが明確

2. **チャネル定義**:
   - IPC_CHANNELS で一元管理済み
   - ALLOWED_INVOKE_CHANNELS, ALLOWED_ON_CHANNELS で適切に分類

3. **エラーハンドリング**:
   - Promise.reject で一貫した処理
   - console.error でログ出力

4. **型定義**:
   - @repo/shared/types/skill-execution で共有
   - Preload/Main/Renderer間で型契約が維持
