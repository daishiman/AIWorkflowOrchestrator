# Phase 12: スキルフィードバックレポート

## 対象タスク: TASK-RT-03 Skill Creation Result Panel

---

## 1. task-specification-creator への改善提案

### 提案 1-1: Phase 5 実装計画テンプレートにファイルパス一覧を必須項目として追加

**現状**: 実装計画に新規作成・修正対象のファイルパスが明記されない場合があり、Phase 5 開始時にファイル構成を確認する工数が発生する。

**提案**: Phase 5 の実装計画テンプレートに以下のセクションを必須項目として追加:

```markdown
## 対象ファイル

### 新規作成

- path/to/NewComponent.tsx — 役割の説明

### 修正

- path/to/ExistingComponent.tsx — 変更概要
```

**期待効果**: 実装者が Phase 5 開始時に即座にファイル構成を把握でき、見落としを防止できる。

### 提案 1-2: Phase 8 リファクタリング記録に before/after 差分の要約フォーマットを追加

**現状**: リファクタリングの内容が自由記述のため、変更の具体的なインパクトが把握しにくい。

**提案**: 以下のフォーマットをテンプレート化:

```markdown
| 対象         | Before               | After                         | 理由     |
| ------------ | -------------------- | ----------------------------- | -------- |
| 共通部品抽出 | 各パネルに重複コード | result-panel-parts.tsx に集約 | DRY 原則 |
```

**期待効果**: リファクタリングの妥当性を第三者が素早く評価可能になる。

### 提案 1-3: terminal_handoff のような分岐パターンの明示的記述を Phase 2 設計ガイドに追加

**現状**: IPC レスポンスが複数のサブタイプを持つ場合（通常レスポンス vs terminal_handoff）、設計段階で分岐パターンが見落とされることがある。

**提案**: Phase 2 の設計ガイドに「レスポンス分岐パターン」セクションを追加し、以下を必須記述とする:

- レスポンスのサブタイプ一覧
- 各サブタイプに対する表示/非表示の方針
- 型絞り込み（type narrowing）の方法

**期待効果**: 分岐パターンの設計漏れを Phase 2 段階で防止できる。

## 2. aiworkflow-requirements への改善提案

### 提案 2-1: コンポーネント設計パターンの参照カタログ追加

**現状**: React コンポーネントの設計パターン（React.memo 使用判断、local state vs store、共有部品の抽出基準）が仕様書に明記されておらず、実装者ごとに判断が異なる可能性がある。

**提案**: 以下のパターンを参照カタログとして追加:

| パターン     | 適用基準                                                       | 例                     |
| ------------ | -------------------------------------------------------------- | ---------------------- |
| React.memo   | props が安定しており再レンダリング防止が有効な場合             | ErrorBanner            |
| local state  | コンポーネント固有の一時データで store 化が不要な場合          | rawPlanDetail          |
| 共有部品抽出 | 2 つ以上のコンポーネントで同一の UI パターンが繰り返される場合 | result-panel-parts.tsx |

**期待効果**: 設計判断の一貫性が向上し、コードレビュー時の議論が減少する。

### 提案 2-2: Tailwind CSS デザイントークンの正式一覧を仕様に追加

**現状**: CSS カスタムプロパティ（`--border-primary`, `--bg-secondary` 等）の一覧が散在しており、新規コンポーネント作成時に正しいトークンを見つけるのに時間がかかる。

**提案**: 以下の形式でデザイントークン一覧を正式仕様として追加:

| カテゴリ   | CSS 変数           | 用途             | Tailwind 使用例                  |
| ---------- | ------------------ | ---------------- | -------------------------------- |
| 背景       | `--bg-primary`     | メインコンテンツ | `bg-[var(--bg-primary)]`         |
| 背景       | `--bg-secondary`   | カード/パネル    | `bg-[var(--bg-secondary)]`       |
| ボーダー   | `--border-primary` | 区切り線         | `border-[var(--border-primary)]` |
| テキスト   | `--text-primary`   | 本文             | `text-[var(--text-primary)]`     |
| ステータス | `--status-success` | 成功表示         | `bg-[var(--status-success)]/10`  |
| ステータス | `--status-error`   | エラー表示       | `bg-[var(--status-error)]/10`    |

**期待効果**: デザインの一貫性が保証され、新規コンポーネント作成時の試行錯誤が削減される。
