## 目的

Phase 2の設計成果物をレビューし、実装に進んで問題ないかを判定する。テスト環境変更の設計が受け入れ基準を満たし、既存テストへの影響が管理可能であることを確認する。

## 背景

テスト環境の変更はモノレポ全体に影響を与える可能性があるため、実装開始前に設計の妥当性を慎重に検証する必要がある。特に、vitest.config.tsの`environment`設定変更はdesktopアプリの全テストに影響するため、互換性分析が十分であるかを確認する。

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: 設計成果物の網羅性確認

**目的**: Phase 2の全成果物が揃っていることを確認する。

**実行手順**:

1. 以下の4ファイルが`outputs/phase-2/`に存在することを確認する
   - `approach-selection.md`（アプローチ選定書）
   - `vitest-config-design.md`（Vitest設定変更設計書）
   - `clipboard-mock-design.md`（Clipboard APIモック設計書）
   - `compatibility-analysis.md`（互換性影響分析レポート）
2. 各ファイルが空でないことを確認する
3. 不足がある場合はPhase 2に戻る

**期待される成果物**:

- チェック結果の記録（レビュー結果に含める）

---

### タスク2: 設計レビュー実施

**目的**: 設計内容を以下のレビュー観点でチェックし、問題がないかを判定する。

**実行手順**:

1. **要件との整合性チェック**
   - Phase 1の受け入れ基準（AC-1〜AC-6）を全て満たす設計になっているか
   - スコープ外の変更が含まれていないか
   - 5つの`describe.skip`ブロック全てに対する解決方針が記載されているか

2. **技術的実現可能性チェック**
   - 選定したアプローチで全スキップテストが有効化可能か
   - Clipboard APIモック設計が実装可能か
   - vitest.config.ts変更が他テストに悪影響を与えないか

3. **既存テスト互換性チェック**
   - 互換性影響分析で特定された影響範囲が妥当か
   - 修正が必要なテストの修正方針が具体的か
   - パフォーマンス許容範囲（+20%）の根拠が妥当か

4. **リスク評価チェック**
   - 環境切り替えによるリスクが特定されているか
   - リスク軽減策（ロールバック計画等）が設計されているか
   - 段階的移行の検討がされているか

5. 各チェック項目について以下の判定を行う

| 判定  | 基準                               |
| ----- | ---------------------------------- |
| OK    | 問題なし                           |
| MINOR | 軽微な指摘（次Phase進行可）        |
| MAJOR | 重大な問題（修正後再レビュー必要） |

**期待される成果物**:

- `outputs/phase-3/design-review-result.md`（設計レビュー結果）

---

### タスク3: レビュー判定と次アクション決定

**目的**: レビュー結果を総合的に判定し、次のアクションを決定する。

**実行手順**:

1. タスク2の結果を集計する
2. 以下の基準で総合判定を行う

| 総合判定 | 条件                               | 次アクション                     |
| -------- | ---------------------------------- | -------------------------------- |
| PASS     | 全チェック項目がOK                 | Phase 4へ進行                    |
| MINOR    | MAJOR指摘が0件、MINOR指摘が1件以上 | MINOR指摘を記録し、Phase 4へ進行 |
| MAJOR    | MAJOR指摘が1件以上（要件問題）     | Phase 1へ戻る                    |
| MAJOR    | MAJOR指摘が1件以上（設計問題）     | Phase 2へ戻る                    |

3. MINOR判定の場合、指摘事項を未完了タスク候補として記録する

**期待される成果物**:

- `outputs/phase-3/design-review-result.md`（タスク2の成果物に判定結果を追記）
