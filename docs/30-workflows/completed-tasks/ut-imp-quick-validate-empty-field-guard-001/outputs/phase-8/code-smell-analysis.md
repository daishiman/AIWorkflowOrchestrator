## コードスメル分析結果

### 1. 重複コード

| 項目             | name（L140-142）                                                           | description（L161-163）                                                                  |
| ---------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 条件式           | `typeof frontmatter.name !== "string" \|\| frontmatter.name.trim() === ""` | `typeof frontmatter.description !== "string" \|\| frontmatter.description.trim() === ""` |
| エラーメッセージ | `"name フィールドが存在しないか無効です"`                                  | `"description フィールドが存在しないか無効です"`                                         |
| 後続処理         | 64文字制限、ハイフンケース正規表現、ディレクトリ名一致                     | 1024文字制限、角括弧検出、Anchors/Trigger確認                                            |

**共通部分**: 条件式のパターンのみ（1行）。条件式内部のフィールド参照（`frontmatter.name` vs `frontmatter.description`）も異なる。
**後続処理**: 完全に異なる検証ロジック。

**判定**: 重複は1行（条件パターン）のみで 3 行未満。YAGNI 原則に基づきインライン維持が適切。

### 2. 命名一貫性

| エラーメッセージ                                   | 言語   | フォーマット                      |
| -------------------------------------------------- | ------ | --------------------------------- |
| `"SKILL.md が存在しません"`                        | 日本語 | `{{対象}} が {{状態}}`            |
| `"SKILL.md が 500 行を超えています (N行)"`         | 日本語 | `{{対象}} が {{制約}} ({{値}})`   |
| `"YAML frontmatter が見つかりません"`              | 日本語 | `{{対象}} が {{状態}}`            |
| `"name フィールドが存在しないか無効です"`          | 日本語 | `{{field}} フィールドが {{状態}}` |
| `"name が 64 文字を超えています (N文字)"`          | 日本語 | `{{field}} が {{制約}} ({{値}})`  |
| `"name がハイフンケースではありません: X"`         | 日本語 | `{{field}} が {{期待}} : {{値}}`  |
| `"description フィールドが存在しないか無効です"`   | 日本語 | `{{field}} フィールドが {{状態}}` |
| `"description が 1024 文字を超えています (N文字)"` | 日本語 | `{{field}} が {{制約}} ({{値}})`  |

**判定**: 全メッセージが日本語で統一されている。フォーマットにはバリエーションがあるが、いずれもフィールド名を明示しており、既存パターンと一貫している。Phase 5 で追加した2つのメッセージは既存の「`{{field}} が {{状態}}`」パターンに合致。

### 3. 条件分岐の深さ

Phase 5 で変更した箇所の最大ネスト深度:

- **name バリデーション**: if → else → if/else if/else if/else（最大3段）
- **description バリデーション**: if → else → if/else + if + if/else（最大3段）

**判定**: ネストは3段が最大であり、許容範囲内。Phase 5 の変更前と同じネスト深度を維持。

### 4. 早期リターン

Phase 5 の変更では早期リターンパターンは使用していない。名前が無効な場合も `addError` を呼んだ後に description の検証を続行する設計である。これは意図的な設計であり（name が無効でも description のエラーを同時に報告する）、早期リターンの導入は不要。
