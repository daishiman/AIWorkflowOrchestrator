## Part 1: 概念的説明（中学生レベル）

### これは何をした修正？

学校で提出する書類を思い浮かべてください。「お名前」と「内容の説明」を書く欄がある書類です。

修正前のプログラムは、こういうチェックをしていました：

- 「お名前の欄に何か書いてある？」 → 書いてなければエラー

でも、これだと困ることがあります：

1. **スペースだけで埋めた場合** — 見た目は何か書いてあるように見えるけど、中身は空っぽ。先生が読んでも名前がわからない。
2. **数字だけ書いた場合（例: 123）** — 名前の欄に数字が入っていると、プログラムが「これを小文字に変えよう」としたとき、「数字は小文字にできません！」とパニックを起こす。
3. **○や×だけ書いた場合** — 同じように、プログラムが処理できない形式のデータが入ってくる。

### 3段チェックの仕組み

修正後は、3つのステップでチェックします：

**ステップ1: 「そもそも文字で書いてある？」**
数字（123）や○×（true/false）で書いてないかを確認します。文字じゃなければ、即座に「名前が正しくありません」とお知らせします。

**ステップ2: 「何か中身がある？」**
文字ではあるけど、完全に空っぽ（何も書いてない）じゃないかを確認します。

**ステップ3: 「スペースだけじゃない？」**
「　　　」のようにスペースだけで埋めてないかを確認します。スペースを取り除いて（trim）、残った中身があるかどうかをチェックします。

### なぜこの修正が必要だった？

チェックがないと、プログラムが「説明文を小文字に変換しよう」としたときに、説明文が文字列じゃなかった（配列だった）場合に「変換できません！」とクラッシュしてしまいます。これは、ユーザーに親切なエラーメッセージを出す代わりに、プログラムが突然止まってしまう状況です。

### 2. P42 準拠 3段バリデーション

P42（06-known-pitfalls.md#P42）で定義された3段バリデーション標準に準拠：

```javascript
// ✅ 修正後: P42準拠3段バリデーション
if (
  typeof frontmatter.name !== "string" || // 第1段: 型チェック
  frontmatter.name.trim() === "" // 第2段+第3段: 空文字列 + trim後空文字列
) {
  result.addError("name フィールドが存在しないか無効です");
} else {
  const name = frontmatter.name.trim(); // trim済み値を後続検証に使用
  // ... 長さ・正規表現チェック
}
```

JavaScript の短絡評価（`||`）により、`typeof` が `"string"` でない場合は `.trim()` が呼ばれないため安全。

### 3. 修正前のバグ動作

#### 根本原因: `parseFrontmatter()` の YAML 空値処理

`parseFrontmatter()` は独自の正規表現ベースパーサーであり、YAML の空値（`name:`）を `[]`（空配列）として返す。

```yaml
---
name: # → parseFrontmatter が [] を返す
description: # → parseFrontmatter が [] を返す
---
```

#### falsy チェックの問題

```javascript
// ❌ 修正前
if (!frontmatter.name) { ... }
```

| 入力値      | `!value` の結果 | 問題                                                    |
| ----------- | --------------- | ------------------------------------------------------- |
| `undefined` | `true`          | 正常に検出                                              |
| `null`      | `true`          | 正常に検出                                              |
| `""`        | `true`          | 正常に検出                                              |
| `[]`        | **`false`**     | 配列は truthy → ガードを素通り → 後続で `TypeError`     |
| `123`       | **`false`**     | 数値は truthy → ガードを素通り → 予期しない動作         |
| `true`      | **`false`**     | boolean は truthy → ガードを素通り → `TypeError`        |
| `"  "`      | **`false`**     | スペースのみは truthy → ガードを素通り → 無効な値が通過 |

#### クラッシュパターン

```
description が [] の場合:
  → desc.toLowerCase() → TypeError: desc.toLowerCase is not a function
  → desc.includes("Anchors:") → TypeError: desc.includes is not a function
```

| `null`      | 拒否（非string） |               | Error: 存在しないか無効です  |

### 6. エッジケース

| ケース                       | 対応                                                        |
| ---------------------------- | ----------------------------------------------------------- |
| frontmatter 自体が存在しない | 既存チェック（L132-136）で早期 return                       |
| name が `0`（falsy な数値）  | `typeof 0 !== "string"` → 型チェックで拒否                  |
| name が `""`（空文字列）     | `"".trim() === ""` → trim チェックで拒否                    |
| desc が `false`              | `typeof false !== "string"` → 型チェックで拒否              |
| YAML 空値 `name:` → `[]`     | `typeof [] !== "string"` → 型チェックで拒否（主要バグ修正） |

### 7. 設計変更記録

| 設計書記載内容                   | 実装での変更                                  | 理由                                                  |
| -------------------------------- | --------------------------------------------- | ----------------------------------------------------- |
| `value.trim() !== ""` のみ記載   | `typeof value !== "string"` を先行チェック    | 配列型が渡される場合を防御（parseFrontmatter の仕様） |
| `const name = frontmatter.name`  | `const name = frontmatter.name.trim()` に変更 | 前後空白を除去して後続検証の精度を向上                |
