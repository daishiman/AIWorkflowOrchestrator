## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

`UT-IPC-CHANNEL-NAMING-AUDIT-001` で `ipcMain.handle` 登録パターンを横断監査した結果、Skill系では重複式が0件だった一方、`AUTH_*` で重複式が5件検出された。機能差異はないが、同一構文の繰り返しが多く、命名監査・変更影響調査・契約更新時のノイズ源になっている。

### 1.2 問題点

- `AUTH_*` ハンドラ登録で同型コードが散在し、差分レビュー時に実質変更と構文差分が混在する
- 新規チャネル追加時に命名・入力検証・戻り値形式の適用漏れを検出しづらい
- P5/P44/P45 の再発監査で「重複式ノイズ」が増え、優先度判断の妨げになる

### 1.3 放置時の影響

- 仕様変更時の修正漏れリスクが上がる（登録点の見落とし）
- 監査コストが継続的に増える
- 認証系IPCの契約が文書と実装でドリフトしやすくなる

---

## 2. 何を達成するか（What）

### 2.1 目的

`AUTH_*` の `ipcMain.handle` 登録を一元化し、チャネル定数・ハンドラ本体・検証ルールの追跡性を高める。

### 2.2 最終ゴール

- [x] `AUTH_*` 登録が共通化され、重複式5件が0件になる
- [x] 既存挙動（戻り値/エラー形式）が不変であることをテストで保証
- [x] 仕様書（`security-electron-ipc.md` / `api-ipc-auth.md`）に登録戦略が反映される
- [x] 監査コマンドで重複式再発が検出されない

### 2.3 スコープ

#### 含むもの

- `apps/desktop/src/main/ipc/` 配下の認証系ハンドラ登録コード整理
- `AUTH_*` 定数参照の統一
- 既存テストの更新・追加
- 関連仕様書の完了記録と更新履歴

#### 含まないもの

- 認証ロジック自体の仕様変更
- Renderer UI の仕様追加
- OAuthフローの新機能追加

### 2.4 成果物

## 3. どのように実行するか（How）

### 3.1 前提条件

- `UT-IPC-CHANNEL-NAMING-AUDIT-001` の監査結果を参照できる
- 現行 AUTH IPC テストが再実行可能である

### 3.2 依存タスク

- `UT-IPC-CHANNEL-NAMING-AUDIT-001`（spec_created）

### 3.3 必要な知識

- Electron `ipcMain.handle` / `ipcRenderer.invoke` の契約
- P5（二重登録）/P44（IF不整合）/P45（命名ドリフト）
- 認証IPC仕様（`api-ipc-auth.md`, `security-electron-ipc.md`）

### 3.4 推奨アプローチ

1. `AUTH_*` ハンドラ登録箇所を列挙し、重複式を分類する
2. 共通登録ヘルパーまたは宣言的マップ化を採用し、構文重複を排除する
3. 既存戻り値・エラー挙動を固定する回帰テストを先に作成する
4. 仕様書へ「登録戦略」と「更新手順」を追記する

### 3.5 実装課題と解決策（親タスクからの教訓）

| 課題               | 発見経緯                                | 解決策                                                                            | 教訓                                               |
| ------------------ | --------------------------------------- | --------------------------------------------------------------------------------- | -------------------------------------------------- |
| 監査ノイズの混在   | Phase 10/11で skill外の重複式が継続検出 | `AUTH_*` 専用の未タスクへ分離し、主タスクの完了判定を明確化                       | 検出結果は「対象内」と「対象外」に分けて台帳化する |
| 台帳参照のドリフト | 未タスク移管時に旧パスが残存しやすい    | 指示書作成と同ターンで `task-workflow.md` を更新し `verify-unassigned-links` 実行 | 未タスクは3ステップ同時完了が必須                  |
| 仕様先送りの再発   | 「実装時にまとめて更新」で漏れが発生    | 実装前に更新対象仕様（security/api/task-workflow）を固定                          | Step 1-A/1-C を分離せず同時実施する                |

## 9. 備考

### エスカレーション基準

以下のいずれかに該当した場合は、単独修正を停止して設計レビューへ戻す。

- AUTH IPC の外部契約（引数・戻り値）変更が必要になった場合
- 既存認証フローに副作用（ログイン/リフレッシュ失敗）が確認された場合
- `ipcMain.handle` 二重登録リスクが AUTH 以外にも波及していた場合
