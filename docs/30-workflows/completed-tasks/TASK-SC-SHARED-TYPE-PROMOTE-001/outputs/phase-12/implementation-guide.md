# 実装ガイド: TASK-SC-SHARED-TYPE-PROMOTE-001

## Part 1: 中学生レベルの説明

### なぜこのタスクが必要だったの？

たとえば、クラスで「明日の遠足の集合場所」を決めたとします。
Aさんが「駅の東口」、Bさんが「駅の西口」と別々に書いてしまったら、みんなが混乱しますよね。
これが「型定義の二重管理」という問題です。

プログラムにも同じことが起きます。`StructurePlanJson`という「データの設計図」が、
もし2か所以上のファイルに別々に書かれていたら、片方を変えても片方は古いままになってしまいます。
これを防ぐために「1か所だけに書いてみんながそこを見る」ルールを決める作業です。

### 「Single Source of Truth」ってなに？

「Single Source of Truth」を日本語にすると「唯一の真実の源」です。

たとえば、学校の時間割を考えてみましょう。

- 先生の机の上の時間割（本物）
- 黒板に写した時間割（コピー）
- 生徒のノートに書いた時間割（コピー）

「3か所にバラバラに書いてあって、どれが正しいか分からない！」という状態は困ります。
「先生の机の時間割だけが正解で、他はそこを見る」と決めておけば、変更があっても1か所直すだけで済みます。

プログラムでも同じです。型定義（データの設計図）は1か所だけに書いて、他のファイルはそこを「参照」するのが正しいやり方です。

### 今回の調査結果

調べてみると、`StructurePlanJson`の設計図は**1つのファイルだけ**にしかありませんでした。
「もう既に1か所だけにある」ということは、問題がないので変更する必要がありません。

interface StructurePlanJson {

### ローカル定義維持の理由

`StructurePlanJson` は `SkillCreatorService.ts` の内部実装の詳細（generate_skill_md.js に渡すプラン JSON の形式）であり、
現時点では同一ファイル内の単一責務として機能しています。

以下の理由からローカル定義を維持します：

1. **参照箇所が 1 ファイルのみ**: 共有コストがゼロメリット
2. **内部実装型**: `SkillCreatorService.ts` 固有の実装詳細であり、外部公開の必要性が低い
3. **変更の局所性**: 変更が必要になったとき 1 ファイルだけ修正すればよい

### 将来の再判断基準

以下の条件を満たした場合、改めて `@repo/shared/types` への昇格を検討してください：

1. **2ファイル以上が参照するようになった場合**
   - `SkillCreatorService.ts` 以外の service/handler が `StructurePlanJson` を使う場合
   - renderer 側（UI コンポーネント）が型を参照する場合

2. **インタフェース定義が変更される場合**
   - フィールドの追加・削除・型変更が頻繁に発生する場合
   - 複数ファイルへの変更同期が発生した場合

3. **テストファイルが型を直接参照する場合**
   - `StructurePlanJson` をフィクスチャや型アサーションに使うテストが増えた場合
