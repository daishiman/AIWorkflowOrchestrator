## 1. 概念編：検索・置換とは何か

### 1.1 日常生活での例え

**検索**は、本の中から特定の言葉を探すことに似ています。

**置換**は、間違えた字を消して正しい字に書き直すことです。

### 1.2 プログラムでの検索・置換

コンピュータでの検索は、人間より速く正確です。

- 人間: 100ページの本から「りんご」を探す → 30分
- コンピュータ: 100ページのテキストから「りんご」を探す → 0.001秒

**なぜ速いのか？**

- コンピュータは1文字ずつ高速に比較できる
- 全てのページを同時に見るのではなく、順番に素早く確認している

### 1.3 この機能でできること

| 機能             | 説明                               | 例                                |
| ---------------- | ---------------------------------- | --------------------------------- |
| 単純検索         | 文字をそのまま探す                 | 「hello」で「hello」を探す        |
| 大文字小文字区別 | 「A」と「a」を区別するか選べる     | 「Hello」と「hello」を別扱い      |
| 単語単位検索     | 単語として独立しているものだけ探す | 「test」で「testing」は除外       |
| 正規表現検索     | パターンで探す                     | 「数字3つ」で「123」「456」を探す |
| 複数ファイル検索 | フォルダ全体から探す               | プロジェクト全体から探す          |

## 2. アーキテクチャ編：全体設計

### 2.1 コンポーネント構成

| コンポーネント        | 役割                                     | 日常の例え         |
| --------------------- | ---------------------------------------- | ------------------ |
| SearchService         | ユーザーからのリクエストを受け付ける窓口 | レストランの受付係 |
| PatternMatcher        | 検索パターンを正規表現に変換             | 翻訳者             |
| FileSearchEngine      | 1つのファイル内を検索                    | 1冊の本を読む人    |
| WorkspaceSearchEngine | フォルダ内の全ファイルを検索             | 図書館の検索係     |
| ReplaceEngine         | 見つかった文字を置換                     | 編集者             |

### 2.2 なぜこの構成にしたのか

**単一責任の原則（Single Responsibility Principle）** を採用しました。

悪い設計: 1つのクラスが全部やる

- SearchAll クラス → 検索も、置換も、ファイル読み込みも全部やる
- 問題: どこかにバグがあると全体が壊れる

良い設計: 役割を分ける

- PatternMatcher → パターン照合だけ
- FileSearchEngine → ファイル内検索だけ
- ReplaceEngine → 置換だけ
- メリット: 1つが壊れても他は動く、テストしやすい

## 3. 技術詳細編：各コンポーネント

### 3.1 PatternMatcher（パターンマッチャー）

#### 概念説明

「検索したい言葉」を「コンピュータが理解できる形」に翻訳する役割です。

#### 技術詳細

**ファイル**: packages/shared/src/search/PatternMatcher.ts

**なぜ正規表現（RegExp）を使うのか？**

単純な文字列比較だと複雑な検索ができません：

- "hello" === "Hello" は false（大文字小文字で不一致）

正規表現なら柔軟に対応できます：

- /hello/i.test("Hello") は true（iフラグで大文字小文字を無視）

**正規表現とは？**

- 文字のパターンを表現するための特殊な記法
- /パターン/フラグ の形式で書く
- 例: /hello/gi = 「helloを、大文字小文字無視（i）で、全部（g）探す」

#### 特殊文字のエスケープ処理

正規表現では . や \* が特別な意味を持ちます：

- . = 任意の1文字（「a」も「b」も「1」も全部マッチ）
- - = 直前の文字が0回以上

問題: ユーザーが「a.b」を検索したい

- 正規表現 /a.b/ → 「aXb」「a1b」「aab」全部マッチしてしまう
- 解決: エスケープして /a\.b/ にする → 「a.b」だけマッチ

#### ReDoS対策（タイムアウト機能）

**ReDoS（Regular Expression Denial of Service）とは？**

悪意のある正規表現パターンで、コンピュータを無限ループに陥れる攻撃です。

攻撃例: パターン (a+)+$ に対して "aaaaaaaaaaaaaaaaaaa!" を入力

- 計算量が指数関数的に増大
- コンピュータが固まる

対策: 5秒経過したら強制終了する

### 3.2 FileSearchEngine（ファイル検索エンジン）

#### 概念説明

1つのファイルの中身を1行ずつ読んで、検索パターンに一致する場所を見つけます。

#### 技術詳細

**ファイル**: packages/shared/src/search/FileSearchEngine.ts

**なぜ行番号に +1 するのか？**

プログラミングでは配列のインデックスは0から始まりますが、人間は1から数えます。

- プログラム内部: lines[0] = "最初の行" （0番目）
- 表示する時: "1行目" として表示

**なぜコンテキスト行が必要か？**

検索結果を見たとき、前後の文脈がないと何の話かわかりません。

コンテキストなし:

- 5行目: return value; ← これだけ見ても何の関数かわからない

コンテキストあり:

- 4行目: function calculateTotal() {
- 5行目: return value; ← 「calculateTotal関数の戻り値だ」とわかる
- 6行目: }

### 3.3 WorkspaceSearchEngine（ワークスペース検索エンジン）

#### 概念説明

フォルダ全体から検索します。図書館で全ての本を調べる係のようなものです。

#### 技術詳細

**ファイル**: packages/shared/src/search/WorkspaceSearchEngine.ts

**なぜ AsyncGenerator を使うのか？**

普通の関数だと、全ファイルの検索が終わるまで何も表示されません。

通常の関数: [読み込み中...] → 10秒後 → [100件の結果が一気に表示]
AsyncGenerator: [1件目表示] → [2件目表示] → ... → [リアルタイムで増えていく]

**なぜキャンセル機能が必要か？**

大きなプロジェクト（10,000ファイル以上）を検索する場合、全部終わるまで待てないことがあります。

- ユーザー: 「あ、検索ワード間違えた」
- キャンセルボタンを押す
- すぐに検索を止めて、新しい検索を開始できる

**デフォルト除外パターンの理由**

| ディレクトリ | 除外理由                                             |
| ------------ | ---------------------------------------------------- |
| node_modules | 外部ライブラリ（数万ファイル）。自分のコードではない |
| .git         | Gitの内部データ。検索しても意味がない                |
| dist, build  | ビルド生成物。ソースコードを見れば十分               |
| coverage     | テストカバレッジレポート。自動生成される             |

### 3.4 ReplaceEngine（置換エンジン）

#### 概念説明

見つかった文字を新しい文字に書き換えます。作文の添削をする先生のような役割です。

#### 技術詳細

**ファイル**: packages/shared/src/search/ReplaceEngine.ts

**なぜ位置を記録するのか？**

記録あり:

- 「5行目の10列目で "hello" を "hi" に置換しました」
- ユーザーは何が変わったか確認できる
- 間違いがあれば元に戻せる

記録なし:

- 「置換しました」
- 何がどう変わったかわからない

**キャプチャグループとは？**

正規表現で括弧 () で囲んだ部分を「記憶」して、置換時に使えます。

例: メールアドレスの形式を変換

- パターン: (\w+)@(\w+) （ユーザー名）@（ドメイン）
- 入力: user@domain
- 置換: $2-$1 （ドメイン-ユーザー名）
- 結果: domain-user
- $1 = 1番目の括弧の中身 (user)
- $2 = 2番目の括弧の中身 (domain)

## 4. 実装判断の理由

### 4.1 テストカバレッジ83.92%の意味

**テストカバレッジとは？**

プログラムのコードのうち、テストで確認された割合

**83.92%の内訳:**

| 項目              | 割合   | 説明                                         |
| ----------------- | ------ | -------------------------------------------- |
| 文（statements）  | 83.92% | 全ての命令文のうち、テストで実行された割合   |
| 分岐（branches）  | 81.63% | if文の全パターンのうち、テストで通過した割合 |
| 関数（functions） | 93.33% | 全ての関数のうち、テストで呼び出された割合   |
| 行（lines）       | 83.92% | 全ての行のうち、テストで実行された割合       |

**なぜ80%以上を目標にしたのか？**

- 100%は現実的ではない（エラー処理など到達困難なコードがある）
- 70%未満だと重要なバグを見逃すリスクが高い
- 80%は「十分に信頼できる」という業界標準

### 4.2 型定義の設計

**なぜinterfaceで型を定義するのか？**

理由1: 型安全性

- TypeScriptが間違いを教えてくれる

理由2: 自己文書化

- コードを読むだけで何が必要かわかる

理由3: IDE補完

- options. と打つと候補が出る

### 4.3 エラーハンドリングの方針

無効な正規表現の処理で、例外を投げる代わりに安全な値を返す方法を採用しました。

**なぜ例外を投げないのか？**

- ユーザーが正規表現を間違えるのは普通のこと
- 例外だとプログラムが止まってしまう
- 「何も置換されなかった」という結果の方が自然

## 5. 用語集

### プログラミング基礎用語

| 用語         | 英語                        | 説明                                                                                    |
| ------------ | --------------------------- | --------------------------------------------------------------------------------------- |
| 正規表現     | Regular Expression (RegExp) | 文字列のパターンを表現する特殊な記法。「数字3つ」「メールアドレス形式」などを表現できる |
| エスケープ   | Escape                      | 特殊な意味を持つ文字を「普通の文字」として扱うための処理                                |
| インデックス | Index                       | 配列や文字列の位置を表す番号。0から始まる                                               |
| 非同期       | Async/Asynchronous          | 処理の完了を待たずに次の処理に進むこと                                                  |

### アーキテクチャ用語

| 用語           | 説明                                                       |
| -------------- | ---------------------------------------------------------- |
| 単一責任の原則 | 1つのクラス/関数は1つの責務だけを持つべきという設計原則    |
| ファサード     | 複雑なシステムへの「窓口」となるシンプルなインターフェース |
| ジェネレーター | 値を一度に全部返すのではなく、1つずつ返す特殊な関数        |

### セキュリティ用語

| 用語         | 説明                                                                           |
| ------------ | ------------------------------------------------------------------------------ |
| ReDoS        | Regular Expression Denial of Service。悪意のある正規表現でシステムを止める攻撃 |
| タイムアウト | 一定時間経過したら処理を強制終了する仕組み                                     |

### テスト用語

| 用語           | 説明                                                            |
| -------------- | --------------------------------------------------------------- |
| カバレッジ     | テストでどれだけのコードを確認したかの割合                      |
| TDD            | Test-Driven Development。テストを先に書いてから実装する開発手法 |
| ユニットテスト | プログラムの最小単位（関数やクラス）を個別にテストすること      |
