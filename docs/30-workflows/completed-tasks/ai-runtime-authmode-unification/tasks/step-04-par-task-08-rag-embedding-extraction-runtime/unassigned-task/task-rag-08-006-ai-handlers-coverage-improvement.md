## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

`aiHandlers.ts` のテストカバレッジが基準未達で、未検証の分岐が複数残っている。Phase 12 の未タスク化対象として、既存テストを拡張して 80% 基準に近づける必要がある。

### 1.2 問題点・課題

- 未カバーハンドラに回帰が入っても気づきにくい
- ハンドラ登録解除や例外分岐が保証されていない
- カバレッジ不足のままだと、仕様変更の安全網が弱い

### 1.3 放置した場合の影響

- 重要な IPC 経路の回帰が見逃される
- 後続の仕様更新でテスト品質が追いつかない
- 品質ゲートが実質的に機能しない

---

## 2. 何を達成するか（What）

### 2.1 目的

`aiHandlers.ts` の未カバーロジックをテストで押さえ、カバレッジ基準に近づける。

### 2.2 最終ゴール

- 未カバー分岐が主要テストで通る
- ハンドラ登録と解除の挙動が確認できる
- カバレッジが改善する

### 2.3 スコープ

#### 含むもの

- `apps/desktop/src/main/ipc/aiHandlers.test.ts`
- 必要に応じた補助テスト

#### 含まないもの

- IPC の実装変更
- UI 変更

### 2.4 成果物

- 追加テスト
- 改善済みカバレッジ結果

---

## 3. どのように実行するか（How）

### 3.1 前提条件

- 未カバー行と分岐が特定されていること
- 現行のテストスタイルを壊さないこと

### 3.2 依存タスク

- なし

### 3.3 必要な知識

- Vitest
- Electron IPC のモック方法
- `ipcMain.handle` の登録パターン

### 3.4 推奨アプローチ

既存テストに不足分だけを足す。新しいモック基盤を大きく作り直さず、行・分岐の未達を狙い撃ちで埋める。

---

## 4. 実行手順

### Phase 1: 未カバー確認

#### 目的

狙う分岐を絞る。

#### 手順

1. 未カバー行を確認する
2. ハンドラ単位で不足ケースを洗い出す
3. 追加テストの順番を決める

#### 完了条件

- 追加対象が明確

### Phase 2: テスト追加

#### 目的

不足分岐を埋める。

#### 手順

1. 正常系を追加する
2. 失敗系を追加する
3. 解除系を追加する

#### 完了条件

- 主要分岐が通る

### Phase 3: 確認

#### 目的

改善が有効か確かめる。

#### 手順

1. テストを実行する
2. カバレッジ結果を確認する
3. 退行がないか確認する

#### 完了条件

- カバレッジが改善している
