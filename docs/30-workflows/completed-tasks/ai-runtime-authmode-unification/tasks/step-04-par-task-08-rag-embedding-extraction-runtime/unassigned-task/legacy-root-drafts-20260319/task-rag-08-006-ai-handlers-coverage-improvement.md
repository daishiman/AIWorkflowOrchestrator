## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

TASK-08-RAG-EMBEDDING の Phase 10 最終レビューで MINOR 指摘 P10-M01 として検出された。

`aiHandlers.ts` のカバレッジが基準未達の状態にある：

- **Stmts（ステートメント）**: 44.72%（基準: 80%）
- **Funcs（関数）**: 33.33%（基準: 80%）

Phase 10 では SCF（Selective Coverage Filter）適用でゲート通過したが、実測値は基準を大幅に下回っており、テスト品質が不十分な状態が継続している。

### 1.2 問題点・課題

**カバレッジ未達の主な原因**:

1. **mock 削除後のテスト不在**: L-RAG-01 の教訓通り、mock 削除後に対応するテストが作成されていないハンドラが複数存在する

2. **guidance-only レスポンスの変更後テスト不足**: guidance-only レスポンス形式が変更されたが、対応するテストケースが未更新のまま

3. **エラーパスのテスト不足**: 各ハンドラの異常系（バリデーションエラー、外部サービスエラー、タイムアウト）のテストが不足

**具体的な未テスト関数の特定方法**:

```bash
# カバレッジレポートから未テスト関数を特定
cd apps/desktop
pnpm vitest run --coverage src/main/handlers/aiHandlers.ts 2>&1 | grep "Uncovered"
```

### 1.3 放置した場合の影響

**短期的影響**:

- SCF による一時的なゲート通過が継続し、実際のバグが隠蔽される
- aiHandlers のリグレッションが検出されにくくなる

**中長期的影響**:

- 新規 RAG ハンドラ追加時に低カバレッジが継承される
- P9（テスト間状態リーク）のリスクが高まる

**影響度**: 中（機能は動作するが、テスト品質基準を下回り継続的なリグレッションリスクがある）

## 2. 何を達成するか（What）

### 2.1 目的

`aiHandlers.ts` のカバレッジを基準値（Stmts 80%, Funcs 80%）以上に引き上げ、SCF に依存しない健全なテスト品質を達成する。

### 2.2 最終ゴール

- aiHandlers.ts の Stmts カバレッジ: 80% 以上
- aiHandlers.ts の Funcs カバレッジ: 80% 以上
- guidance-only レスポンス形式の変更に対応したテストを完備する
- 全ての異常系パスに対応するテストを追加する

### 2.3 スコープ

#### 含むもの

- `aiHandlers.test.ts` の既存テスト調査・分析
- 未テスト関数・ブランチの特定
- 不足テストケースの追加（正常系・異常系・境界値）
- guidance-only レスポンス形式テストの更新・追加

#### 含まないもの

- aiHandlers.ts 本体の実装変更（テスト追加のみ）
- 他のハンドラファイルへのカバレッジ改善（別タスク化を推奨）
- E2E テストの追加

### 2.4 成果物

1. 更新された `apps/desktop/src/main/handlers/__tests__/aiHandlers.test.ts`
2. カバレッジレポート（実測値を記録）

## 3. どのように実行するか（How）

### 3.1 前提条件

- [ ] `aiHandlers.ts` の現行実装を全件読み込んでから作業を開始する
- [ ] `aiHandlers.test.ts` の現行テストを全件読み込んでから作業を開始する
- [ ] カバレッジレポートを実行して現在の未カバー箇所を特定する
- [ ] TASK-08-RAG-EMBEDDING が完了していること

### 3.2 依存タスク

- TASK-08-RAG-EMBEDDING（aiHandlers の実装基盤）
- UT-RAG-08-001（communityHandlers 統一）とは独立して実行可能

### 3.3 必要な知識・スキル

- Vitest のカバレッジ機能（v8 プロバイダー）
- IPC ハンドラのモックパターン（P21 参照）
- guidance-only レスポンス形式の理解
- P41（v8 カバレッジのインライン関数カウント）の理解

### 3.4 推奨アプローチ

1. **カバレッジ分析**: 現在の未カバー関数・ブランチを一覧化する
2. **優先順位付け**: 重要度の高いハンドラから順にテストを追加する
3. **TDD アプローチ**: 各ハンドラの正常系 → 異常系 → 境界値の順でテストを追加
4. **インライン関数対策**: P41 を参考に、コールバックの呼び出し確認テストを追加する

### 3.5 苦戦ポイント（過去の教訓）

**L-RAG-01: mock 削除は型制約の影響範囲を事前調査すべき**

mock を削除・変更する際は、`grep -rn "mockAiHandlers\|vi.mock.*aiHandlers"` で全依存箇所を事前把握する。mock 削除後にテストが連鎖失敗するリスクがある。

**L-RAG-05: mock 削除後のテスト不在**

現状、guidance-only レスポンス形式の変更後に対応するテストが作成されていない。このタスクの主目的の一つが、この空白を埋めることにある。

**P23 + P9 複合リスク**:

モジュールスコープのモック変数がテスト間で共有される場合、`beforeEach` でのリセットが必須。特に `ipcMain.handle` のモックは二重登録になりやすい（P5 参照）。

**P41: v8 カバレッジのインライン関数カウント**:

aiHandlers 内にコールバック形式のインライン関数がある場合、それらが独立した関数としてカウントされる。セキュリティテストで `getAllowedWindows()` 等のコールバックを明示的に呼び出す検証を追加すること。

**P21: 既存テストへの DI 追加時の大規模修正**:

新しいサービスが aiHandlers に DI で追加されている場合、既存の全テストファイルにモックを追加する必要がある。影響範囲を `grep -rn "aiHandlers" **/*.test.ts` で事前確認する。

## 4. Phase 構成

### Phase 1: カバレッジ分析

**目的**: 未カバー箇所を定量化し、テスト追加計画を立てる

**実行手順**:

1. カバレッジ計測を実行する

```bash
cd apps/desktop
pnpm vitest run --coverage --reporter=verbose src/main/handlers/aiHandlers.ts
```

2. 未カバー関数・ブランチを一覧化する
3. guidance-only レスポンス形式の現行実装を確認する

**成果物**:

- 未カバー箇所の一覧（実装コメントとして記録）

**完了条件**:

- [ ] 現行カバレッジ値が確認されている（Stmts, Branches, Funcs, Lines）
- [ ] 未カバー関数の一覧が作成されている
- [ ] guidance-only レスポンスの現行形式が確認されている

### Phase 2: テスト追加

**目的**: 未カバー箇所に対するテストを追加する

**実行手順**:

1. `aiHandlers.test.ts` の現行テストを読み込む
2. 未カバー関数の正常系テストを追加する
3. 異常系テストを追加する（バリデーションエラー、外部サービスエラー）
4. guidance-only レスポンス形式のテストを更新・追加する
5. P41 対策として、インライン関数コールバックの呼び出し確認を追加する

**重要**: テスト追加時は既存テストの `beforeEach` リセットパターンを継承すること（P9 対策）

**成果物**:

- 更新された `aiHandlers.test.ts`

**完了条件**:

- [ ] 未カバー関数のテストが追加されている
- [ ] 異常系テストが含まれている
- [ ] guidance-only レスポンス形式のテストが更新されている
- [ ] 各テスト後に状態がリセットされている（beforeEach）

### Phase 3: カバレッジ検証

**目的**: 基準値達成を確認する

**実行手順**:

1. カバレッジ計測を再実行する
2. 基準値（Stmts 80%, Funcs 80%）達成を確認する
3. 未達の場合は Phase 2 に戻る

**完了条件**:

- [ ] aiHandlers.ts の Stmts カバレッジ >= 80%
- [ ] aiHandlers.ts の Funcs カバレッジ >= 80%
- [ ] 全テストが PASS している

## 7. リスクと対策

| リスク                                        | 影響度 | 発生確率 | 対策                                                   |
| --------------------------------------------- | ------ | -------- | ------------------------------------------------------ |
| mock 変更による既存テスト連鎖失敗（L-RAG-01） | 中     | 中       | mock 変更前に全依存箇所を grep で確認する              |
| テスト間状態リーク（P9）                      | 中     | 中       | beforeEach でモックをリセット、共有変数を使わない      |
| P41: インライン関数が未カウント               | 低     | 中       | コールバック呼び出し確認テストを明示的に追加する       |
| SCF 削除後の他テストへの影響                  | 低     | 低       | SCF 削除は段階的に実施し、各段階でカバレッジを確認する |

## 9. 備考

### 発見経緯

TASK-08-RAG-EMBEDDING Phase 10 最終レビューで MINOR P10-M01 として検出。SCF 適用でゲート通過したが、実測値が基準を大幅に下回っていることから未タスクとして切り出した。

### 補足事項

- SCF（Selective Coverage Filter）はあくまで一時的な対処であり、本タスクで実測値を基準値以上に引き上げることが目的
- guidance-only レスポンス形式の変更履歴は TASK-08-RAG-EMBEDDING の Phase 5 実装ドキュメントを参照すること
- カバレッジ改善後は SCF の適用箇所を削除することが望ましい
