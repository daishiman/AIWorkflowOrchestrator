## 1. なぜこのタスクが必要か（Why）

### 1.1 背景

`openai-provider.ts` はモック越しの確認に偏っており、実際のユニットテストが不足している。Embedding 系の安定性を上げるには、外部 API を呼ばずにロジックを直接確認するテストが必要になる。

### 1.2 問題点・課題

- 外部 API 依存をモックしても、内部分岐の保証にはならない
- エラー処理やレスポンス整形の回帰を検出しづらい
- カバレッジが 0% 近いままだと品質ゲートが弱い

### 1.3 放置した場合の影響

- Provider 周辺の不具合が後から見つかる
- テストの守備範囲が実質的に空白になる
- 近接する embedding 系タスクの検証が不十分になる

---

## 2. 何を達成するか（What）

### 2.1 目的

OpenAI provider の主要分岐をユニットテストで押さえ、外部 API を使わずに回帰検出できるようにする。

### 2.2 最終ゴール

- 正常系・異常系の基本ケースがテストされる
- API モックで安定して実行できる
- カバレッジが改善する

### 2.3 スコープ

#### 含むもの

- `packages/shared/src/services/embedding/openai-provider.ts`
- 対応テストファイル

#### 含まないもの

- OpenAI API の本番接続確認
- Embedding 全体設計の変更

### 2.4 成果物

- 新規ユニットテスト
- 改善済みカバレッジ結果

---

## 3. どのように実行するか（How）

### 3.1 前提条件

- 外部通信をしないモック方針を取ること
- provider の分岐を整理できること

### 3.2 依存タスク

- なし

### 3.3 必要な知識

- Vitest
- fetch / client mock
- エラーパスのテスト設計

### 3.4 推奨アプローチ

API 呼び出しはモックで固定し、返却値の整形と例外分岐を確認する。ネットワークに依存するテストは作らない。

---

## 4. 実行手順

### Phase 1: 対象整理

#### 目的

テスト対象の分岐を明確にする。

#### 手順

1. Provider の公開関数を確認する
2. 分岐ごとの期待値を決める
3. モック範囲を決める

#### 完了条件

- 対象ケースが固まっている

### Phase 2: テスト実装

#### 目的

主要ケースを追加する。

#### 手順

1. 正常系を追加する
2. エラー系を追加する
3. パース失敗系を追加する

#### 完了条件

- 主要分岐が通る

### Phase 3: 確認

#### 目的

安定して実行できるか確認する。

#### 手順

1. テストを実行する
2. カバレッジを確認する
3. flaky がないか確認する

#### 完了条件

- テストが安定して PASS する

## 6. 検証方法

### テストケース

- TC-001: 正常応答が正しく整形される
- TC-002: API エラーが扱える
- TC-003: 予期しない応答形が失敗する

### 検証手順

1. テストを実行する
2. カバレッジを確認する
3. モック漏れがないか確認する
