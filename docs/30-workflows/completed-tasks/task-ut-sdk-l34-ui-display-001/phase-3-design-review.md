## 実行手順

### Step 1: 要件レビュー思考法の適用

#### 1-1: 真の論点

**主問題（1文）**: Layer3/4のバックエンド検証結果がUI表示に反映されていないため、
ユーザーがスキル品質問題を把握できず、品質改善サイクルが回らない。

**why now**: UT-IMP-SDK-06でバックエンドのLayer3/4実装が完了し、IPC経由でchecksが届く
状態になったが、フロントエンドが未対応のままであり、機能追加の効果が半減している。

**why this way**: `check.layer`フィールドが既存型定義に含まれており、バックエンド変更なしで
Layer別グルーピングが実装可能。最小コストでユーザー価値を最大化できる設計。

#### 1-2: 因果と境界の確認

**強化ループ**:

```
Layer3/4 UIグルーピング → ユーザーがL4-001 errorを認識
→ スキルのAnchorsセクション修正 → スキル品質向上
→ VerificationEngine PASS率向上 → さらなるLayer拡張投資
```

**バランスループ**:

```
checks数増加 → UX劣化リスク → 折りたたみ機能で対応
→ 情報密度のバランス維持
```

**状態所有権の明確化**:
| 状態 | 所有者 | 更新タイミング |
| ---------------- | ----------------------- | --------------------------------- |
| `verifyDetail` | IPC → Redux store | reverify完了時 |
| `checksByLayer` | `useMemo`（派生状態） | `verifyDetail.checks`変更時に再計算 |
| `expandedLayers` | `SkillLifecyclePanel` local state | ユーザー操作時のみ |

**責務境界**:

- `SkillCreatorVerificationEngine`（Main）: Layer3/4チェックロジック（変更不要）
- IPC/preload: verifyDetailの型定義（変更不要）
- `SkillLifecyclePanel`（Renderer）: UI表示責務（本タスクの変更対象）
- `VerifyLayerGroup`（ローカル）: Layer単位のアコーディオン表示責務

#### 1-3: 価値とコストの見方

| 観点         | 評価                                                          |
| ------------ | ------------------------------------------------------------- |
| 初回価値     | Layer3/4のエラー・警告がユーザーに視覚的に伝わる              |
| 導入コスト   | 2000行超コンポーネントへの変更リスク、既存テストの整合維持    |
| 高コスト項目 | 既存テストのfixture更新（`layer3-verify-status` vs `L3-001`） |
| 将来層       | check IDの日本語ラベル、severityフィルタ（本タスク外）        |

#### 1-5: 30思考法（7群）具体所見と改善案

| 群           | 具体的所見（例）                                                                                                                                                            | 改善案（例）                                                                                                                                 |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 論理分析系   | 「Layer3/4が届いている」という前提は `check.layer` の存在に依存する。未知の layer 値が混入すると UI が破綻しうる。                                                          | UI側は `layer1..4` 以外を捨てずに「その他」扱いにするか、未知値を `discovered-issues.md` へ記録する（少なくとも落ちないこと）。              |
| 構造分解系   | やることは「派生データ化（グルーピング）」「表示（アコーディオン）」「集計（badge）」「見た目（severity色）」の4要素。混ぜると `SkillLifecyclePanel` の変更リスクが上がる。 | 100行を超える・責務が増える場合のみ `VerifyLayerGroup` を分離して境界を固定する（Phase 5 の分離条件を維持）。                                |
| メタ・抽象系 | UI表現（アコーディオン）を先に決めすぎると、検証結果の「読む順序」や「見落とし防止」が曖昧になる。                                                                          | 表現より先に「最小の情報設計」を固定する（順序: Layer順、空Layer非表示、error→warning→info集計、ID/summary表示）。                           |
| 発想・拡張系 | 代替案として Tabs、フィルタ（warning以上）、検索、ツリー表示も成立するが、初回は過剰機能になりやすい。                                                                      | 初期リリースはアコーディオン+集計バッジに限定し、フィルタ等は Phase 12 の未タスク候補として明確に切り出す。                                  |
| システム系   | reverify により `verifyDetail` が更新されても、展開状態を維持する要件がある。ここを誤ると「見ていた箇所が勝手に閉じる」体験になる。                                         | `expandedLayers` は `verifyDetail` 変更でリセットしない（Phase 5 の設計を維持）。全展開/全折りたたみの明示操作だけを追加する。               |
| 戦略・価値系 | 価値は「問題箇所特定の時間短縮」。コストは「巨大コンポーネントへの差分リスク」と「テスト更新」。                                                                            | 既存 `verifyCheckSeverityStyles` を再利用し、外部アイコン依存を増やさない。UI変更は Renderer 内に閉じ、IPC境界を増やさない。                 |
| 問題解決系   | 根本原因は「checks が増えたのに、構造のない一覧表示のまま」。論点は「どう並べるか」「何を折りたたむか」「何を集計するか」。                                                 | 仮説: Layer別表示+集計で認知負荷が下がる。Phase 4/6 テストで「グルーピング」「badge集計」「空Layer非表示」「折りたたみ」を明示的に検証する。 |
