## 実行手順

### Task 1: 要件との整合性検証

Phase 1 で定義した全機能要件（FR-3A: 12件, FR-3B: 11件, FR-3C: 12件, FR-3D: 10件 = 45件）が Phase 2 の設計に反映されていることを検証する。

#### 検証マトリクス

| 検証観点                    | 検証方法                                                                  | 判定基準             |
| --------------------------- | ------------------------------------------------------------------------- | -------------------- |
| 機能要件カバレッジ          | Phase 1 の全 FR-ID が Phase 2 のコンポーネント/Props に対応付けられている | 100% カバレッジ必須  |
| 非機能要件カバレッジ        | NFR-P/A/R の全項目が設計に反映されている                                  | 100% カバレッジ必須  |
| IPC チャネル対応            | Phase 1 の 22 チャネルが Phase 2 の Preload API に全て定義されている      | 1:1 対応必須         |
| 型定義対応                  | Phase 1 の 22 バックエンド型が Phase 2 の Props/Hook で参照されている     | 全型が参照されている |
| 受け入れ基準 → テスト設計性 | Phase 1 の受け入れ基準が Phase 4 のテストケースに変換可能                 | 全基準がテスト可能   |

### Task 2: アーキテクチャの妥当性検証

#### Atomic Design 準拠チェック

| 検証観点         | 検証方法                                             | 判定基準                   |
| ---------------- | ---------------------------------------------------- | -------------------------- |
| atoms の責務     | atoms が単一の UI 要素のみを担当している             | ビジネスロジックを含まない |
| molecules の責務 | molecules が atoms の組み合わせで構成されている      | 単一の機能単位を表現       |
| organisms の責務 | organisms がビュー全体のレイアウトを担当している     | 複数 molecules を統合      |
| Props の型安全性 | 全 Props に TypeScript 型定義がある                  | `any` 型なし               |
| ファイル配置     | 各コンポーネントが適切なディレクトリに配置されている | `views/ビュー名/` 配下     |

#### レイヤー依存方向チェック

| 検証観点              | 検証方法                                                                | 判定基準                           |
| --------------------- | ----------------------------------------------------------------------- | ---------------------------------- |
| Renderer → Preload    | コンポーネントが `window.electronAPI.skill.*` 経由でのみ IPC を呼び出す | 直接 `ipcRenderer` 使用なし        |
| IPC_CHANNELS 定数使用 | 全チャネル名が `IPC_CHANNELS.*` 定数で参照されている                    | ハードコード文字列なし（P27 対策） |
| 状態管理方向          | カスタム Hook → useState / agentSlice のみ                              | Context や直接 Store アクセスなし  |

### Task 3: IPC 契約整合性検証

バックエンド仕様書（TASK-9D/9G/9H/9J）と Phase 2 の Preload API 設計の契約を突合する。

| 検証項目               | 検証方法                                                         | 判定基準                                   |
| ---------------------- | ---------------------------------------------------------------- | ------------------------------------------ |
| チャネル名一致         | バックエンド仕様のチャネル名と Preload API のチャネル名が一致    | 22 チャネル全一致                          |
| 引数型一致             | ハンドラの引数型と safeInvoke の引数型が一致                     | P44 パターン（型不整合）の防止             |
| 戻り値型一致           | ハンドラの戻り値型と safeInvoke の戻り値型が一致                 | 型アサーション不要                         |
| イベント購読契約       | `skill:debug:event` の DebugEvent 型がバックエンドと一致         | P5 対策の cleanup 関数が設計に含まれている |
| 引数命名セマンティクス | 引数名が実際に渡される値のセマンティクスと一致                   | P45 パターン（命名ドリフト）の防止         |
| 3段バリデーション      | 全文字列引数に型/空文字列/トリム空文字列チェックが設計されている | P42 準拠                                   |

### Task 4: Apple HIG 準拠検証

| 検証項目         | 検証方法                                               | 判定基準                            |
| ---------------- | ------------------------------------------------------ | ----------------------------------- |
| カラーパレット   | 全色指定が `01-architecture.md` のシステムカラーを参照 | カスタムカラー使用なし              |
| スペーシング     | 8px グリッド準拠                                       | 全スペーシングが 8 の倍数           |
| 角丸             | 8px〜12px の範囲                                       | コンポーネント間で統一              |
| 影               | 繊細な影（`0 1px 3px rgba(0,0,0,0.04)` 基準）          | 過剰な影なし                        |
| フォント         | システムフォント（`-apple-system`）使用                | カスタムフォントなし                |
| インタラクション | 全操作にホバー/アクティブ/フォーカス状態               | 状態なしの操作要素なし              |
| アニメーション   | 200-300ms 基準、目的を持ったアニメーションのみ         | 装飾的アニメーションなし            |
| 破壊的操作       | 削除操作に確認ダイアログ                               | チェーン削除/スケジュール削除が対象 |

### Task 5: セキュリティ検証

| 検証項目               | 検証方法                                               | 判定基準                             |
| ---------------------- | ------------------------------------------------------ | ------------------------------------ |
| IPC バリデーション     | 全ハンドラに P42 準拠3段バリデーションが設計されている | 22 ハンドラ全対応                    |
| エラーサニタイズ       | IPC エラーが Renderer に内部情報を漏洩しない設計       | サニタイズ処理が全ハンドラに含まれる |
| contextBridge 経由     | 全 IPC 呼び出しが contextBridge 経由                   | 直接 `ipcRenderer` 使用なし          |
| チャネルホワイトリスト | 全チャネルが `IPC_CHANNELS` 定数でホワイトリスト管理   | ハードコード文字列なし               |
| 送信元ウィンドウ検証   | ハンドラで送信元ウィンドウの検証が設計に含まれている   | 全ハンドラで検証                     |

### Task 6: 既知の落とし穴チェック

| Pitfall | 検証項目                         | 判定基準                                                        |
| ------- | -------------------------------- | --------------------------------------------------------------- |
| P5      | イベント購読の useEffect cleanup | `skill:debug:event` の購読に cleanup 関数がある                 |
| P13     | タイマーテストの設計             | ScheduleManager のタイマーテストで `advanceTimersByTime` を使用 |
| P27     | ハードコード文字列の不使用       | 全チャネル名が `IPC_CHANNELS` 定数                              |
| P31     | agentSlice の個別セレクタ使用    | 合成 Hook（`useAgentStore()`）を使用していない                  |
| P39     | テスト環境の指定                 | happy-dom 環境で `fireEvent` を使用する設計                     |
| P40     | テスト実行ディレクトリの指定     | `cd apps/desktop` から実行する旨が記載されている                |
| P47     | CSS 変数テストのアサーション戦略 | Record 定数の export が設計に含まれている                       |

### Task 7: 判定

#### 判定基準

| 判定  | 条件                                                               | 対応                                    |
| ----- | ------------------------------------------------------------------ | --------------------------------------- |
| PASS  | Task 1-6 の全検証項目が合格                                        | Phase 4（テスト作成）へ進行             |
| MINOR | 軽微な修正で対応可能な指摘がある（機能影響なし）                   | 指摘対応後 Phase 4 へ進行               |
| MAJOR | 要件の欠落、アーキテクチャの根本的問題、セキュリティ上の懸念がある | 要件問題 → Phase 1 / 設計問題 → Phase 2 |

#### レビュー観点の重要度

| レビュー観点       | 重要度 | MAJOR になる条件                                      |
| ------------------ | ------ | ----------------------------------------------------- |
| 要件カバレッジ     | 高     | 機能要件が1つでも設計に反映されていない               |
| IPC 契約整合性     | 高     | チャネル名/引数型/戻り値型に不一致がある              |
| セキュリティ       | 高     | バリデーション/サニタイズ/ホワイトリストに欠陥がある  |
| Atomic Design 準拠 | 中     | レイヤー違反（atoms にビジネスロジック等）がある      |
| Apple HIG 準拠     | 中     | カラー/スペーシング/インタラクションに逸脱がある      |
| パフォーマンス     | 中     | 大量データ時のレンダリング戦略が欠落している          |
| アクセシビリティ   | 中     | WCAG 2.1 AA の基準を満たさない設計がある              |
| 落とし穴対策       | 中     | P5/P31/P42 等の既知問題への対策が設計に含まれていない |

#### 技術的実現可能性の追加検証

| 技術的懸念               | 検証方法                                                         | リスクレベル |
| ------------------------ | ---------------------------------------------------------------- | ------------ |
| recharts 統合            | recharts のバンドルサイズと tree-shaking 可能性を確認            | 低           |
| ドラッグ＆ドロップ       | HTML5 DnD API の happy-dom テスト互換性を確認                    | 中           |
| リアルタイムイベント購読 | `safeOn` パターンの StrictMode 互換性が設計に含まれているか確認  | 中           |
| 仮想スクロール           | 大量データ（100チェーン、200スケジュール等）時のレンダリング戦略 | 低           |
| キーボードショートカット | グローバルショートカット（F5等）とブラウザデフォルトの競合       | 低           |

## 次 Phase

### PASS の場合

Phase 4（テスト作成: TDD Red）へ進む。Phase 1 の受け入れ基準と Phase 2 の設計を入力として、テストケース設計とテストコード作成を行う。

### MINOR の場合

指摘事項への対応方針を記録し、Phase 4 へ進む。MINOR 指摘は Phase 12 で未タスク仕様書に変換する（省略不可）。

### MAJOR の場合

- 設計問題（アーキテクチャの根本的問題、IPC 契約不整合）→ Phase 2 へ戻る
