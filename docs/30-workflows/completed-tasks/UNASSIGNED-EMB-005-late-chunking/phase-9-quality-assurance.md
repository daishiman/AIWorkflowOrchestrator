## 目的

品質とリスクを定量化して運用判断を可能にする。Late Chunking実装の品質ゲートを通過し、本番投入可否を判定する。

## 背景

Late Chunkingは文書全体のコンテキストを考慮した後処理型チャンキング手法であり、従来の事前チャンキングに比べて検索品質を10〜30%向上させることが期待される。`packages/shared/` に実装した当該機能の品質・リスク・因果ループを包括的に評価する。

## SubAgentチーム編成

| SubAgent   | 関心ごと           | 主担当                                     |
| ---------- | ------------------ | ------------------------------------------ |
| SubAgent-A | アルゴリズム責務   | Late Chunking ロジック正確性・境界条件     |
| SubAgent-B | パフォーマンス契約 | 処理速度・メモリ消費・スループット         |
| SubAgent-C | API/型契約         | 公開インターフェース・型安全性・後方互換性 |
| SubAgent-D | 統合監査           | 矛盾・漏れ・整合・依存判定                 |

## 実行タスク

- 品質監査: 機能・セキュリティ・保守性を評価する
- リスク評価: 残存リスクを影響度×発生頻度で分類する
- 因果ループ監査: 修正が新規障害を生む循環を評価する

## 実行手順

1. 入力成果物を確認する。
2. SubAgent-A/B/C を並列実行し、SubAgent-D で統合判定する。
3. 以下のコマンドで品質ゲートを通過することを確認する。
   ```bash
   pnpm --filter @repo/shared typecheck
   pnpm lint
   pnpm --filter @repo/shared test
   ```
4. リスク台帳で残存リスクを影響度×発生頻度で分類する。
5. 因果ループ監査で修正による副作用がないことを確認する。
6. 成果物を `outputs/phase-9/` に保存する。
7. 完了条件で矛盾・漏れ・整合・依存を判定する。

## リスク台帳（想定リスク）

| リスクID | リスク種別   | 内容                                                     | 影響度 | 発生頻度 | 対策                                         |
| -------- | ------------ | -------------------------------------------------------- | ------ | -------- | -------------------------------------------- |
| RSK-9-01 | メモリOOM    | 大規模文書全体をコンテキストとして保持した際のメモリ枯渇 | 高     | 中       | バッファサイズ上限の設定・ストリーミング処理 |
| RSK-9-02 | 速度低下     | 全文コンテキスト参照による処理時間の増加                 | 中     | 高       | キャッシュ戦略・並列処理の導入               |
| RSK-9-03 | 境界品質低下 | チャンク境界の不適切な切断による意味破損                 | 高     | 低       | 境界検出アルゴリズムの強化・単体テスト追加   |
| RSK-9-04 | API非互換    | 既存embeddingパイプラインとのインターフェース不整合      | 高     | 低       | 後方互換性テスト・段階的ロールアウト         |

## 統合テスト連携

- SubAgent-A/B/C の検証ケースを並列で設計する。
- SubAgent-D が統合順序を直列で確定する。
- Late Chunking有効/無効の切り替えが正常に動作することを統合対象に固定する。
- 処理速度とメモリ消費量のベンチマーク値をログで突合する。
- 既存のembeddingパイプラインとの後方互換性を再発させない。
- 統合ログは `outputs/phase-9/` に保存する。
