## 目的

Phase 1（要件定義）と Phase 2（設計）の成果物をレビューし、実装に進む前に設計の妥当性を検証する。問題がある場合は適切なフェーズに戻り修正を行う。

## 背景

設計レビューは、実装開始後の手戻りを防ぐための重要なゲートである。要件と設計の整合性、技術的実現可能性、品質基準への適合を確認する。

---

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: 要件-設計整合性レビュー

**目的**: Phase 1 の要件が Phase 2 の設計で網羅されていることを確認する

**実行手順**:

1. Phase 1 の機能要件（FR-001〜FR-007）と設計の対応を確認する：

| 機能ID | 機能名                   | 設計での対応                           | 充足 |
| ------ | ------------------------ | -------------------------------------- | ---- |
| FR-001 | 全スキルスキャン         | scanAll() メソッド                     | □    |
| FR-002 | 単一スキルパース         | parseSkill() + parseFrontmatter()      | □    |
| FR-003 | サブディレクトリスキャン | scanSubDirectory() × 6種類             | □    |
| FR-004 | その他ファイル検出       | scanOtherFiles()                       | □    |
| FR-005 | 説明抽出                 | extractDescription()                   | □    |
| FR-006 | ディレクトリ自動作成     | ensureAiworkflowDir()                  | □    |
| FR-007 | 読み取り専用フラグ       | scanDirectory() の readonly パラメータ | □    |

2. 不足がある場合は Phase 2 へ戻り設計を追加する
3. `outputs/phase-03/requirements-design-mapping.md` にレビュー結果を記録する

**期待される成果物**:

- `outputs/phase-03/requirements-design-mapping.md`

---

### タスク2: 技術的実現可能性レビュー

**目的**: 設計が技術的に実現可能であることを確認する

**実行手順**:

1. 以下の技術的観点をレビューする：

| 観点               | 確認項目                                                | 結果 |
| ------------------ | ------------------------------------------------------- | ---- |
| Node.js API 互換性 | fs/promises, path が Electron Main Process で使用可能か | □    |
| yaml パッケージ    | YAML Frontmatter パースに適切なパッケージか             | □    |
| 非同期処理         | async/await パターンが適切に設計されているか            | □    |
| エラーハンドリング | try-catch が適切に設計されているか                      | □    |
| 型安全性           | TASK-1-1 の型定義と整合しているか                       | □    |

2. `outputs/phase-03/technical-feasibility.md` にレビュー結果を記録する

**期待される成果物**:

- `outputs/phase-03/technical-feasibility.md`

---

### タスク3: 品質基準適合レビュー

**目的**: 設計が品質基準に適合していることを確認する

**実行手順**:

1. 以下の品質基準をレビューする：

| 基準           | 確認項目                                     | 結果 |
| -------------- | -------------------------------------------- | ---- |
| 単一責任の原則 | 各メソッドが単一の責務を持っているか         | □    |
| テスト容易性   | モック可能な設計になっているか               | □    |
| 保守性         | 新しいサブディレクトリタイプを追加しやすいか | □    |
| セキュリティ   | パストラバーサル対策が設計に含まれているか   | □    |
| ログ出力       | 適切な箇所でログ出力が設計されているか       | □    |

2. `outputs/phase-03/quality-review.md` にレビュー結果を記録する

**期待される成果物**:

- `outputs/phase-03/quality-review.md`

---

### タスク4: レビュー結果判定

**目的**: レビュー結果を総合判定し、次のアクションを決定する

**実行手順**:

1. タスク1〜3 のレビュー結果を集計する
2. 以下の判定基準に基づき判定を行う：

| 判定     | 条件                     | 次のアクション            |
| -------- | ------------------------ | ------------------------- |
| PASS     | 全レビュー観点で問題なし | Phase 4（テスト作成）へ   |
| MINOR    | 軽微な指摘あり           | 指摘対応後、Phase 4へ     |
| MAJOR    | 重大な問題あり           | Phase 2（設計）へ戻る     |
| CRITICAL | 致命的な問題あり         | Phase 1（要件定義）へ戻る |

3. `outputs/phase-03/review-decision.md` に判定結果を記録する

**期待される成果物**:

- `outputs/phase-03/review-decision.md`
