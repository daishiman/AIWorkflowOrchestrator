## 目的

Phase 2で作成した設計の妥当性を検証し、実装フェーズに進む前に問題を発見・修正する。

## 背景

設計レビューは実装前の重要なゲートであり、
設計の問題を早期に発見することで手戻りコストを最小化する。

---

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: 要件充足性レビュー

**目的**: 設計がPhase 1の要件を全て満たしていることを確認する

**実行手順**:

1. Phase 1の機能要件と設計を突合
2. Phase 1の非機能要件と設計を突合
3. 不足している設計要素を特定
4. レビュー結果を記録

**レビュー観点**:

- [ ] 6種類のコンポーネント全てがProps設計されているか
- [ ] WCAG 2.1 AA要件がアクセシビリティ設計に反映されているか
- [ ] useFileContext/useDiffApply連携が設計されているか
- [ ] エラーハンドリングが設計されているか

**期待される成果物**:

- `outputs/phase-3/requirements-review.md`

---

### タスク2: 技術的妥当性レビュー

**目的**: 設計が技術的に実現可能であることを確認する

**実行手順**:

1. Monaco Editor統合の技術的実現可能性を確認
2. ドラッグ&ドロップ実装方針（HTML5 DnD）の確認
3. パフォーマンス懸念事項（大きなファイルの差分表示等）の確認
4. レビュー結果を記録

**レビュー観点**:

- [ ] Monaco Diff Editorの設定は妥当か
- [ ] D&D実装でHTML5 Drag and Drop APIが使用可能か
- [ ] 大きなファイル（10MB）の差分表示でパフォーマンス問題はないか
- [ ] Tailwind CSSでスタイリング可能か

**期待される成果物**:

- `outputs/phase-3/technical-review.md`

---

### タスク3: 統合テスト観点レビュー

**目的**: 統合テストの観点から設計を検証する

**実行手順**:

1. コンポーネント間連携のテスト可能性を確認
2. Hooks統合テストのシナリオを検討
3. モック戦略の妥当性を確認
4. レビュー結果を記録

**レビュー観点**:

- [ ] 各コンポーネントがHooksと独立してテスト可能か
- [ ] コンポーネント統合テストのシナリオが設計から導出可能か
- [ ] 外部依存（Monaco Editor等）のモック戦略は妥当か

**期待される成果物**:

- `outputs/phase-3/integration-test-review.md`

---

### タスク4: レビュー結果判定

**目的**: 全レビュー結果を総合し、次フェーズへの進行可否を判定する

**実行手順**:

1. 全レビュー結果を集約
2. 判定基準に基づき判定
3. 指摘事項がある場合は対応計画を作成
4. 判定結果を記録

**判定基準**:
| 判定 | 条件 | 次のアクション |
| -------- | ------------------------ | ------------------------- |
| PASS | 全レビュー観点で問題なし | Phase 4へ進行 |
| MINOR | 軽微な指摘あり | 指摘対応後、Phase 4へ |
| MAJOR | 重大な問題あり | Phase 2へ戻り設計修正 |
| CRITICAL | 致命的な問題あり | Phase 1へ戻りユーザー確認 |

**期待される成果物**:

- `outputs/phase-3/review-result.md`
