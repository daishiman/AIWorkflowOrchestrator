## 目的

Phase 2 のE2Eテスト設計を多角的にレビューし、全AC（AC-1〜AC-8）/ NFR（NFR-1〜NFR-4）のカバレッジ網羅性と技術的実現可能性を検証する。PASS / MINOR / MAJOR / CRITICAL の判定を行う。

## 背景

設計レビューは Phase 4（テスト作成）に進む前のゲートである。ここで設計の問題を検出しないと、テスト作成・実装フェーズで大きな手戻りが発生する。特に以下の観点が重要:

1. **P60対策**: IPC レスポンス形式が実装と一致しているか
2. **網羅性**: 全AC・NFR がテストシナリオでカバーされているか
3. **実現可能性**: 設計したテストインフラが実際に動作可能か

---

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: テストシナリオの網羅性確認

**目的**: 全AC・NFR がテストでカバーされていることを確認する

**実行手順**:

1. Phase 1 の AC-FR-シナリオ対応表を読み込む
2. シナリオA〜E が AC-1〜AC-8 を全て網羅しているか確認する
3. 各ACとシナリオのマッピングに抜けがないか確認する
4. NFR-1〜NFR-4 の検証方法が全て設計されているか確認する
5. 抜けがある場合、具体的な追加テストケースを提案する

**期待される成果物**:

- 網羅性確認結果（PASS / 抜け一覧）

### タスク2: IPC レスポンス形式の整合性確認（P60対策）

**目的**: 設計した IPC レスポンス形式が実装と一致するか確認する

**実行手順**:

1. `apps/desktop/src/preload/skill-creator-api.ts` の実際のIPC定義を読む
2. Phase 2 で定義した IPC レスポンス形式と比較する
3. テストのアサーション形式（`result.error.code` vs `result.code`）が一貫しているか確認する
4. 不整合がある場合、Phase 2 設計書の修正を指示する

**期待される成果物**:

- IPC 整合性確認結果

### タスク3: テストインフラの実現可能性確認

**目的**: 設計したテストインフラが技術的に実現可能か確認する

**実行手順**:

1. LLMモックが E2Eレベルで使用可能か確認する
2. IPC統合テストが `apps/desktop` の vitest 環境で動作可能か確認する（P40対策）
3. タイムアウト設定（150,000ms）が Vitest で機能するか確認する
4. 既存テストパターンとの整合性を確認する（P63対策: インポートパス）

**期待される成果物**:

- 実現可能性確認結果

### タスク4: TerminalHandoff 検証の完全性確認

**目的**: TerminalHandoff（AC-4）のテスト設計が完全か確認する

**実行手順**:

1. `suggestedCommand` の形式検証基準が明確か確認する
2. TerminalHandoff が返却されない場合（通常フロー / API Key 設定済み）も正しくテストされているか確認する
3. セキュリティ観点（シェルインジェクション防止）のテストが含まれているか確認する

**期待される成果物**:

- TerminalHandoff 検証完全性確認結果

### タスク5: 後方互換テストの妥当性確認

**目的**: AC-8（既存 `skill:create` の後方互換）テスト設計の妥当性を確認する

**実行手順**:

1. 既存 `skill:create` チャンネルの動作確認テストが設計されているか確認する
2. 新旧チャンネル共存テストが設計されているか確認する

**期待される成果物**:

- 後方互換テスト妥当性確認結果

### タスク6: 総合判定

**目的**: Phase 4 に進めるかを判定する

**実行手順**:

1. タスク1〜5 の結果を統合する
2. 以下の判定基準で判定する:
   - **PASS**: 全レビュー観点で問題なし → Phase 4 へ
   - **MINOR**: 軽微な指摘あり → 指摘対応後 Phase 4 へ
   - **MAJOR**: 重大な設計問題あり → Phase 2 へ戻る
   - **CRITICAL**: 致命的な問題あり → Phase 1 へ戻りユーザー確認

**期待される成果物**:

- 総合判定結果レポート
