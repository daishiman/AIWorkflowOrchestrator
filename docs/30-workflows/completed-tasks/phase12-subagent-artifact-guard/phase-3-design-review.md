## 目的

Phase 1（要件定義）と Phase 2（設計）の妥当性を多角的に検証し、Phase 4 以降への進行可否を判定する。

## 背景

本タスクはドキュメント改善タスクのため、コード実装は含まれない。設計レビューでは、テンプレート構造の整合性、三点突合ルールの検証可能性、監査基準の明確性を重点的に確認する。

## 判定基準

| 判定              | 条件                                             | 対応                  |
| ----------------- | ------------------------------------------------ | --------------------- |
| PASS              | 全レビュー観点でクリア                           | Phase 4 へ進行        |
| MINOR             | 軽微な修正で対応可能（表現改善、参照リンク追加） | 指摘対応後 Phase 4 へ |
| MAJOR（要件問題） | 要件の不足・矛盾が発見された                     | Phase 1 へ戻る        |
| MAJOR（設計問題） | 設計の整合性・実現可能性に重大な問題が発見された | Phase 2 へ戻る        |

## 実行タスク

- Task 3-1 SubAgent責務マトリクス網羅性レビュー: プロファイルと責務分離の漏れを検証する
- Task 3-2 三点突合ルール検証可能性レビュー: 機械実行可能な突合手順かを検証する
- Task 3-3 テンプレート構造整合性レビュー: summary/report/changelog の整合を検証する
- Task 3-4 監査基準明確性レビュー: current/baseline 判定の一意性を検証する
- Task 3-5 親タスク教訓反映度レビュー: 親タスクで得た教訓の設計反映を検証する

### Task 3-1: SubAgent責務マトリクスの網羅性レビュー

#### レビュー観点

| #   | 確認項目                                                            | 判定基準                                                 |
| --- | ------------------------------------------------------------------- | -------------------------------------------------------- |
| 1   | 3プロファイル（標準5仕様書/UI6仕様書/再確認）が全て定義されているか | 全プロファイルの責務表が存在する                         |
| 2   | 各SubAgentの責務が一意で重複がないか                                | 同一仕様書を複数SubAgentが担当していない                 |
| 3   | SubAgent間の依存チェーンが循環していないか                          | A→B→C→D→Eの一方向チェーンが成立する                      |
| 4   | 各SubAgentの完了条件が自律的に判定可能か                            | 他SubAgentの結果に依存せず判定できる条件が設定されている |
| 5   | プロファイル選択基準がタスク種別から一意に決定可能か                | 判断フローチャートで分岐が明確                           |

#### 手順

1. Phase 2 成果物 `architecture-design.md` の SubAgent責務マトリクスを確認する
2. 上記5項目を逐次チェックする
3. 不備があれば指摘事項として記録する

### Task 3-2: 三点突合ルールの検証可能性レビュー

#### レビュー観点

| #   | 確認項目                                                       | 判定基準                                                              |
| --- | -------------------------------------------------------------- | --------------------------------------------------------------------- |
| 1   | 三点（phase-12-documentation/changelog/summary）の定義が明確か | 各「点」の参照箇所が特定されている                                    |
| 2   | 突合アルゴリズムが機械的に実行可能か                           | grep/rg コマンドで検証可能                                            |
| 3   | 突合結果の判定パターン（PASS/DRIFT/N/A）が網羅的か             | 全てのケースが分類されている                                          |
| 4   | Step 2 該当なしの場合の判定フローが定義されているか            | ドキュメントのみタスクでの N/A 判定が明文化されている                 |
| 5   | 既存テンプレートのStep 2判定同期プロファイルと整合しているか   | `phase12-system-spec-retrospective-template.md` セクション3.3との一致 |

#### 手順

1. Phase 2 成果物 `template-structure-design.md` の三点突合設計を確認する
2. 機械検証コマンドが実際に実行可能か確認する
3. 既存テンプレートとの整合を突合する

### Task 3-3: テンプレート構造の整合性レビュー

#### レビュー観点

| #   | 確認項目                                                              | 判定基準                     |
| --- | --------------------------------------------------------------------- | ---------------------------- |
| 1   | 3成果物間のデータフローに矛盾がないか                                 | 整合テーブルの全行が一致     |
| 2   | summary↔reportのSubAgent名が一致ルールに従っているか                  | 名称一致の検証手順が明確     |
| 3   | summary↔changelogのStep 2判定が一致ルールに従っているか               | 判定一致の検証手順が明確     |
| 4   | report完了条件がPhase仕様書の完了条件と対応しているか                 | 対応関係表が存在する         |
| 5   | 既存テンプレート2点（summary/report）との後方互換性が確保されているか | 既存構造を破壊する変更がない |

#### 手順

1. Phase 2 成果物の整合テーブルを確認する
2. 既存テンプレート2点と設計の差分を確認する
3. 後方互換性に問題がないか判定する

### Task 3-4: 監査基準の明確性レビュー

#### レビュー観点

| #   | 確認項目                                               | 判定基準                                        |
| --- | ------------------------------------------------------ | ----------------------------------------------- |
| 1   | current/baselineの分離定義が明確か                     | 定義文が一意で解釈の揺れがない                  |
| 2   | 合否基準（currentViolations=0）が定式化されているか    | 数値基準が明記されている                        |
| 3   | 記録フォーマットが統一されているか                     | フォーマット例が示されている                    |
| 4   | 全体監査FAILでもcurrent PASSとなるケースの説明が明確か | baseline起因のFAILがcurrent判定に影響しない説明 |
| 5   | `spec-update-workflow.md` Step 1-G.1 との整合があるか  | 既存ルールとの矛盾がない                        |

#### 手順

1. Phase 2 成果物の監査基準設計を確認する
2. `spec-update-workflow.md` の Step 1-G.1 と突合する
3. 判定ルールの曖昧箇所がないか確認する

### Task 3-5: 親タスク教訓の反映度レビュー

#### レビュー観点

| #   | 教訓                           | 設計への反映確認                                               |
| --- | ------------------------------ | -------------------------------------------------------------- |
| 1   | Main契約/Preload契約の表現差   | 層別契約の分離記載がテンプレートに含まれているか               |
| 2   | Phase 12 成果物名のドリフト    | 成果物名1対1突合ルールが設計されているか                       |
| 3   | 未タスク `## メタ情報` 重複    | 1セクション原則 + rg機械確認が設計に含まれているか             |
| 4   | SubAgent責務が成果物に残らない | spec-sync-subagent-report.mdが標準成果物として定義されているか |

#### 手順

1. 未タスク指示書セクション3.5の4教訓を確認する
2. Phase 2 設計における対応箇所を特定する
3. 反映漏れがないか確認する
