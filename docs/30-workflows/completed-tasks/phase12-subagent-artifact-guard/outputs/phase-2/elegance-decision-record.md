## 2. エレガンス判定（Task 2-5）

### 2.1 比較対象

- **案A（全面破棄）**: 既存の Phase 12 運用構造（テンプレート・SubAgent分担・三点突合手順）を廃止し、新規ガードフレームワークを一から設計・構築する
- **案B（増分改善）**: 既存のテンプレート・SubAgent分担・突合手順を活かし、ガード機能（SubAgent責務固定・三点突合ルール化・currentViolations=0合否基準）を追加する

### 2.2 5軸評価（定量比較）

各軸を★1〜5の5段階で評価する（★5が最高評価）。

| 評価軸     | 案A（全面破棄）の評価 | 案A の根拠                                         | 案B（増分改善）の評価 | 案B の根拠                                           | 差分（B-A） |
| ---------- | --------------------- | -------------------------------------------------- | --------------------- | ---------------------------------------------------- | ----------- |
| 再利用性   | ★★                    | 新構造の学習コストが発生。完成まで再利用不可       | ★★★★★                 | 既存テンプレートを活用。すぐに別タスクへ適用可能     | +3 案B優位  |
| 移行コスト | ★                     | 既存成果物（summary/report/changelog）が全て無効化 | ★★★★                  | 既存成果物を継続利用。ガード追加のみ                 | +3 案B優位  |
| 検証可能性 | ★★★                   | 白紙から設計できるが、新基準整備が必要             | ★★★★                  | 既存検証コマンド（verify/audit）をそのまま継承・拡張 | +1 案B優位  |
| 後方互換性 | ★                     | 破壊的変更。依存タスク3件も再設計が必要            | ★★★★★                 | 既存ワークフロー・依存タスクと完全互換               | +4 案B優位  |
| 運用リスク | ★★                    | 未知の設計リスク。移行期の混乱が予測される         | ★★★★                  | 既知の問題点のみを対処。変更差分が限定的             | +2 案B優位  |
| **合計**   | **★9**                | -                                                  | **★22**               | -                                                    | +13 案B優位 |

### 2.3 採用案の決定

**採用案: 案B（増分改善）**

### 2.4 採用理由（5点）

1. **実績ある基盤の活用**: `phase12-system-spec-retrospective-template.md` と `phase12-spec-sync-subagent-template.md` は複数タスクで使用実績があり、破棄コストが高い。既存構造を活かすことで即座に運用可能。

2. **依存タスク3件との後方互換**: `UT-IMP-PHASE12-SPEC-SYNC-SUBAGENT-GUARD-001` / `UT-IMP-PHASE12-STEP2-TARGET-TRACE-GUARD-001` / `UT-IMP-PHASE12-EVIDENCE-VALUE-SYNC-GUARD-001` の3件は本タスクの成果物を継承する。全面破棄すると3件の再設計が必要になり、スコープが爆発する。

3. **ガード追加の無矛盾性**: 三点突合ルール・currentViolations=0合否基準・SubAgent責務固定は、既存テンプレート構造に矛盾しない追加機能として実装できる。既存セクション（§3.3 Step 2判定・§5 苦戦箇所等）を拡張するだけで対応可能。

4. **検証コマンドの継続利用**: `verify-unassigned-links.js` / `audit-unassigned-tasks.js` / `verify-all-specs.js` の既存スクリプトをそのまま使用できる。案Aでは新スクリプトの開発が必要。

5. **段階的改善の性質との整合**: 本タスクは「Phase 12 運用品質固定化」を目的とする段階的改善タスク（docs/chore分類）であり、一度に全面刷新するアーキテクチャ的変更（全面破棄）は性質に反する。

### 2.5 却下案（案A）の却下理由

| 却下理由                         | 詳細                                                                              |
| -------------------------------- | --------------------------------------------------------------------------------- |
| 既存成果物の全面無効化           | 実績ある `spec-update-summary.md` / `spec-sync-subagent-report.md` が無効化される |
| 依存タスク3件への波及            | 3件の依存タスクが本タスクの成果物を参照するため、全面破棄は3件の再設計を強制する  |
| スコープ逸脱                     | 新規フレームワーク設計はOut of Scope（scope-definition.md §3.3参照）              |
| 検証基準の再整備コスト           | 現行スクリプトとの接続が切れ、新基準の整備に追加工数が発生する                    |
| 「段階的改善」という性質に反する | 本タスクはdocs/chore分類（改善タスク）であり、アーキテクチャ変更は対象外          |

### 2.6 トレードオン整理

| 区分           | 内容                                                                   |
| -------------- | ---------------------------------------------------------------------- |
| **捨てるもの** | 一度に全面刷新する短期的な見た目の単純さ（案Aの一時的なシンプルさ）    |
| **得るもの**   | 既存運用との整合・検証安定性・依存タスクとの後方互換・再確認コスト削減 |
