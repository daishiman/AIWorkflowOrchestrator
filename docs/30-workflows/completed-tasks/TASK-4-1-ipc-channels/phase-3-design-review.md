## 目的

Phase 1（要件定義）とPhase 2（設計）の成果物をレビューし、実装に進む前に設計の妥当性を検証する。

## 背景

IPCチャネル定義は後続タスク（TASK-4-2, TASK-5-1）の基盤となるため、
設計段階で問題を検出し、手戻りを防止することが重要。

---

## 実行タスク

> 以下のタスクを順番に実行してください。

### タスク1: 要件充足性の確認

**目的**: 設計が要件を満たしているか確認する

**実行手順**:

1. Phase 1の要件定義書を読み込む
2. Phase 2の設計書を読み込む
3. 各要件に対して設計がカバーしているか確認する
4. 不足があれば記録する

**レビュー観点**:

- [ ] 13チャネル全てが設計に含まれているか
- [ ] 通信方向（R→M / M→R）が正しく設計されているか
- [ ] ホワイトリスト登録が漏れなく設計されているか

**期待される成果物**:

- 要件充足性チェックリスト

---

### タスク2: 既存パターンとの整合性確認

**目的**: 既存コードパターンとの整合性を確認する

**実行手順**:

1. `apps/desktop/src/preload/channels.ts`を読み込む
2. 設計が既存パターンに従っているか確認する
3. 命名規則の一貫性を確認する
4. 不整合があれば記録する

**レビュー観点**:

- [ ] チャネル定数名が既存パターンに従っているか（SCREAMING_SNAKE_CASE）
- [ ] チャネル値が既存パターンに従っているか（`namespace:action`形式）
- [ ] コメントスタイルが一貫しているか
- [ ] グループ化が論理的か

**期待される成果物**:

- 整合性チェックリスト

---

### タスク3: セキュリティ要件の確認

**目的**: セキュリティ要件が満たされているか確認する

**実行手順**:

1. セキュリティガイドラインを確認する
2. ホワイトリスト設計が適切か確認する
3. 既存のセキュリティパターンとの整合性を確認する

**レビュー観点**:

- [ ] 全チャネルがホワイトリストに登録される設計か
- [ ] invoke/onの分類が正しいか
- [ ] 機密性の高い操作に対する考慮があるか

**期待される成果物**:

- セキュリティチェックリスト

---

### タスク4: レビュー結果の判定

**目的**: レビュー結果を判定し、次のアクションを決定する

**実行手順**:

1. 全チェックリストの結果を集計する
2. 問題の重大度を判定する
3. 次のアクションを決定する

**期待される成果物**:

- レビュー結果レポート（outputs/phase-3/review-result.md）

## レビュー結果判定

| 判定     | 条件                     | 次のアクション            |
| -------- | ------------------------ | ------------------------- |
| PASS     | 全レビュー観点で問題なし | Phase 4へ進行             |
| MINOR    | 軽微な指摘あり           | 指摘対応後、Phase 4へ     |
| MAJOR    | 重大な問題あり           | Phase 2へ戻り設計修正     |
| CRITICAL | 致命的な問題あり         | Phase 1へ戻りユーザー確認 |
