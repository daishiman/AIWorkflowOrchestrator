## 目的

Phase 2 で作成した4件の改善設計を独立レビューし、Phase 4（テスト作成）へ進むか、Phase 2 に差し戻すかを判定する。

---

## 実行タスク

- 4件の改善設計を独立レビュー
- CSS 変数未定義テーマでのフォールバック動作確認
- カテゴリ上限値の UX 妥当性確認
- transition アニメーションのパフォーマンス影響評価
- PASS / MINOR / MAJOR / CRITICAL の判定（MAJOR 以上は Phase 2 に差し戻し）

---

## レビュー観点

### 1. CSS 変数置換設計レビュー

| 観点                         | 確認内容                                                                | 判定 |
| ---------------------------- | ----------------------------------------------------------------------- | ---- |
| 全ハードコードカラーの網羅性 | `bg-blue-*`、`hover:bg-blue-*`、`text-blue-*`、`border-blue-*` 漏れなし | -    |
| CSS 変数フォールバック有無   | `var(--status-primary, #2563eb)` 形式で定義されているか                 | -    |
| ホバー状態の整合性           | `hover:opacity-90` への統一が Tailwind との競合なし                     | -    |
| テーマ切替後の表示確認       | ライトテーマ・ダークテーマ両方で色が正しく変わるか                      | -    |

### 2. カテゴリ上限設計レビュー

| 観点                  | 確認内容                                                    | 判定 |
| --------------------- | ----------------------------------------------------------- | ---- |
| 上限値の妥当性        | `MAX_CATEGORY_COUNT = 3`（全7件の半数）の UX 観点での妥当性 | -    |
| 解除動作の保証        | 上限到達時でも選択済みカテゴリを解除できること              | -    |
| disabled 状態の視認性 | `opacity-40 cursor-not-allowed` で上限到達が伝わるか        | -    |
| 型安全性              | `handleCategoryClick` の引数型が `SkillCategory` で正しいか | -    |
| 既存テストへの影響    | `SkillInfoStep.test.tsx` の既存テストが壊れないか           | -    |

### 3. カテゴリアニメーション設計レビュー

| 観点                      | 確認内容                                                                        | 判定 |
| ------------------------- | ------------------------------------------------------------------------------- | ---- |
| パフォーマンス影響        | `transition-all` で不要プロパティが含まれないか（ボタン小サイズのため許容範囲） | -    |
| `duration-200` の視認性   | 200ms でアニメーションが体感できるか                                            | -    |
| `scale-[1.02]` の視覚効果 | 選択済み状態の scale 変化が過度でないか                                         | -    |
| アクセシビリティ          | `disabled` ボタンのフォーカス動作に問題ないか                                   | -    |

### 4. ProgressBar アニメーション設計レビュー

| 観点                    | 確認内容                                                          | 判定 |
| ----------------------- | ----------------------------------------------------------------- | ---- |
| `duration-300` の視認性 | 300ms でスムーズな進捗変化が体感できるか                          | -    |
| `width` 変化の滑らかさ  | `style={{ width: ...% }}` + `transition-all` で滑らかに変化するか | -    |
| 0% → 16.7% の初回遷移   | 初回回答時の遷移がスムーズに見えるか                              | -    |
| 既存 CSS との競合       | 既存の CSS 定義に transition 関連がすでにある場合の重複確認       | -    |

## 判定基準

| 判定     | 条件                                         | アクション               |
| -------- | -------------------------------------------- | ------------------------ |
| PASS     | 全観点で問題なし                             | Phase 4 へ進む           |
| MINOR    | 軽微な改善点あり（機能に影響しない）         | Phase 4 へ進み、後で修正 |
| MAJOR    | 設計に問題あり（実装に影響する）             | Phase 2 に差し戻し       |
| CRITICAL | 既存機能への破壊的影響、または前提条件の欠如 | Phase 1 に差し戻し       |

---

## チェックリスト

### CSS 変数監査

- [ ] 置換対象のハードコードカラーが網羅されている
- [ ] CSS 変数フォールバック（`var(--xxx, fallback)`）が定義されている
- [ ] ホバー状態の Tailwind クラスとの競合がない

### カテゴリ上限

- [ ] `MAX_CATEGORY_COUNT = 3` の値が UX 的に妥当
- [ ] 解除動作（`formData.category.includes(value)` 分岐）が正しい
- [ ] `isAtLimit` フラグの disabled ボタン表示が明確
- [ ] 型安全性に問題なし

### アニメーション

- [ ] `transition-all duration-200` のパフォーマンス影響が許容範囲内
- [ ] ProgressBar `duration-300` で視覚的に滑らかな進捗変化が実現可能
- [ ] アクセシビリティ（ARIA 属性等）に問題なし
