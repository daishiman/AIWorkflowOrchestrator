# Part 1: 概念的な説明（中学生でもわかる版）

## 1. フロントエンドテストって何？

### 1.1 身近な例で考えてみよう

スマートフォンのアプリを想像してください。ボタンを押したら正しく動く、文字を入力したら正しく表示される、エラーが起きたら適切なメッセージが出る。これらが全部ちゃんと動くかを確認するのが「テスト」です。

```
ユーザー ─→ [ボタンをタップ] ─→ アプリ ─→ [正しい画面が表示される]
                                  ↑
                              テストで確認
```

### 1.2 なぜ必要なの？

テストがないと、こんな問題が起きます:

- 新しい機能を追加したら、別の機能が壊れた
- 本番環境でエラーが発生して、ユーザーが困った
- バグの原因を探すのに何時間もかかった

テストがあると、問題を**自動的に**、**すぐに**発見できます。

### 1.3 今回作ったもの

| 日本語         | 英語                      | 役割                                   |
| -------------- | ------------------------- | -------------------------------------- |
| APIモック      | MSW (Mock Service Worker) | 外部サービスの代わりになる「ニセモノ」 |
| テストランナー | Vitest UI                 | テストを実行して結果を見やすく表示     |
| ヘルパー関数   | Test Utilities            | テストを書くときに使う便利な道具セット |
| データ工場     | Factories                 | テスト用のサンプルデータを自動生成     |

---

## 2. どうやって動くの？

### 2.1 全体の流れ

```
テストを書く
    ↓
テストを実行する（pnpm test）
    ↓
結果を確認する
    ↓
問題があれば修正する
    ↓
カバレッジを確認する（80%以上を目指す）
```

### 2.2 APIモック（MSW）の仕組み

通常、アプリは外部のサーバー（Supabase、Anthropic API）と通信します。でもテスト中は:

```
アプリ ──→ [リクエスト] ──→ MSW（モック） ──→ [ニセの返答]
                              ↑
                    本物のサーバーには行かない
```

**なぜ必要か**: 本物のサーバーを使うと:

- テストが遅くなる
- ネットワークの状態に左右される
- APIの利用料金がかかる

### 2.3 データの保存方法

テストで使うデータは「ファクトリー」で生成します:

**チャットセッション**:
| 項目 | 説明 |
| ---------- | ------------------------ |
| ID | 一意の識別番号 |
| タイトル | セッションの名前 |
| 作成日時 | いつ作られたか |
| 更新日時 | いつ変更されたか |

# Part 2: 技術的な詳細（開発者向け）

## 1. アーキテクチャ概要

### 1.1 ファイル構成

```
apps/desktop/src/test/
├── mocks/
│   ├── handlers.ts   # APIモックハンドラー定義
│   └── server.ts     # MSWサーバー設定
├── utils.tsx         # カスタムレンダー関数
├── test-helpers.ts   # ストアモック・waitFor
├── factories.ts      # テストデータファクトリー
└── setup.ts          # Vitest グローバルセットアップ
```

### 1.2 依存関係

```
vitest.config.ts
    ↓ 読み込み
setup.ts
    ↓ 初期化
mocks/server.ts ─→ mocks/handlers.ts
    ↓ 利用
utils.tsx + test-helpers.ts + factories.ts
    ↓ 利用
*.test.tsx（各テストファイル）
```

## 2. MSW ハンドラー設計（設計理由付き）

### 2.1 Supabase Auth ハンドラー

**設計判断**: ワイルドカードでサブドメインに対応

| エンドポイント                  | メソッド | レスポンス         | なぜこの設計か                      |
| ------------------------------- | -------- | ------------------ | ----------------------------------- |
| `*.supabase.co/auth/v1/token`   | POST     | access_token, user | 認証フローの基本。JWTトークンを返す |
| `*.supabase.co/auth/v1/signup`  | POST     | user, session      | 新規登録のモック                    |
| `*.supabase.co/auth/v1/signout` | POST     | 空                 | ログアウト成功を示す                |

**なぜワイルドカード**: Supabaseのサブドメインはプロジェクトごとに異なるため、`*.supabase.co` でマッチさせる。

### 2.2 Anthropic API ハンドラー

**設計判断**: ストリーミングと非ストリーミングの両対応

| リクエスト条件  | レスポンス形式          | なぜこの設計か               |
| --------------- | ----------------------- | ---------------------------- |
| `stream: true`  | SSE (text/event-stream) | 実際のAPI動作を模倣          |
| `stream: false` | JSON                    | 単純なテスト用               |
| APIキー無効     | 401エラー               | エラーハンドリングのテスト用 |

## 3. テストユーティリティ設計

### 3.1 カスタムレンダー関数

| 関数名                 | 用途                   | なぜ必要か                             |
| ---------------------- | ---------------------- | -------------------------------------- |
| renderWithRouter       | Router込みレンダリング | ルーティング依存コンポーネントのテスト |
| renderWithMemoryRouter | メモリルーター使用     | SSR環境やテスト分離のため              |
| renderWithProviders    | 全Provider込み         | 完全な統合テスト用                     |

**なぜ3種類**: テストの粒度に応じて最小限のラッパーを使うことで、テストの実行速度と明確性を保つ。

### 3.2 ストアモック

| 関数名     | 用途           | なぜ必要か                               |
| ---------- | -------------- | ---------------------------------------- |
| mockStore  | 状態を設定     | 特定の状態でのコンポーネント動作をテスト |
| resetStore | 初期状態に戻す | テスト間の独立性を保証                   |

**なぜZustand対応**: プロジェクトの状態管理にZustandを使用しているため。

### 3.3 ファクトリー関数

| 関数名                | 生成データ         | なぜ必要か                       |
| --------------------- | ------------------ | -------------------------------- |
| createMockChatSession | チャットセッション | セッション関連テストのデータ生成 |
| createMockChatMessage | チャットメッセージ | メッセージ関連テストのデータ生成 |
| resetFactories        | カウンターリセット | テスト間でユニークIDを保証       |

**なぜファクトリー**:

- 毎回手書きすると冗長でエラーが起きやすい
- デフォルト値を持ちつつ、一部だけ上書きできる柔軟性
- IDの自動インクリメントでテスト間の干渉を防止

## 4. カバレッジ閾値設計

### 4.1 vitest.config.ts 設定

| パラメータ | 値  | なぜこの値か                             |
| ---------- | --- | ---------------------------------------- |
| lines      | 80% | 業界標準の目標値。高すぎず低すぎない     |
| functions  | 80% | 関数単位でのカバレッジ確保               |
| branches   | 60% | 条件分岐は複雑になりがちなため緩めに設定 |
| statements | 80% | 行カバレッジと同等                       |

**なぜ閾値を設定**: CI/CDで自動的に品質低下を検出するため。閾値未達でテストが失敗する。

### 4.2 除外パターン

| パターン              | なぜ除外か                               |
| --------------------- | ---------------------------------------- |
| `node_modules/`       | 外部ライブラリは対象外                   |
| `**/*.test.{ts,tsx}`  | テストファイル自体はカバレッジ対象外     |
| `**/*.config.{ts,js}` | 設定ファイルはテスト対象外               |
| `e2e/**`              | E2Eテストは別のカバレッジ測定対象        |
| `src/test/**`         | テストユーティリティはヘルパーなので除外 |

## 6. 使用上の注意

### 6.1 MSW ハンドラーの追加方法

新しいAPIをモックする場合:

```
1. handlers.ts に http.get/post を追加
2. エラーケースも追加（401, 404, 500など）
3. setup.ts で自動的に読み込まれる
```

### 6.2 テスト間の独立性

| すべきこと                | 避けるべきこと       |
| ------------------------- | -------------------- |
| beforeEachでセットアップ  | グローバル変数の共有 |
| afterEachでクリーンアップ | テスト順序への依存   |
| ファクトリーでデータ生成  | ハードコードされたID |

## 8. 用語集

| 用語                  | 読み方                         | 説明                                                                                                                                                     |
| --------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| MSW                   | エムエスダブリュー             | Mock Service Worker。ネットワークレベルでAPIをモックするライブラリ。なぜ選んだか: 実際のHTTPリクエストをインターセプトするため、より現実的なテストが可能 |
| Vitest                | ヴィテスト                     | Viteベースの高速テストフレームワーク。なぜ選んだか: Vite環境との親和性が高く、ESM対応                                                                    |
| React Testing Library | リアクトテスティングライブラリ | ユーザー視点でReactコンポーネントをテストするライブラリ。なぜ選んだか: 実装詳細に依存しないテストが書ける                                                |
| Zustand               | ズスタンド                     | 軽量な状態管理ライブラリ。なぜ選んだか: Reduxより簡潔でボイラープレートが少ない                                                                          |
| Factory               | ファクトリー                   | テストデータを生成するヘルパー関数。デザインパターンの一つ                                                                                               |
| カバレッジ            | カバレッジ                     | テストがコードのどれくらいを網羅しているかの指標                                                                                                         |
| SSE                   | エスエスイー                   | Server-Sent Events。サーバーからクライアントへの一方向ストリーミング                                                                                     |
| IPC                   | アイピーシー                   | Inter-Process Communication。Electronのプロセス間通信                                                                                                    |
