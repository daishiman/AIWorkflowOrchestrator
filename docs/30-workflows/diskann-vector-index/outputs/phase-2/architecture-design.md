## 3. データモデル

### 3.1 エンティティ関係図 (ER図)

```
┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
│      files      │       │     chunks      │       │   embeddings    │
├─────────────────┤       ├─────────────────┤       ├─────────────────┤
│ id (PK)         │◀──────│ file_id (FK)    │       │ id (PK)         │
│ name            │  1:N  │ id (PK)         │◀──────│ chunk_id (FK)   │
│ path            │       │ content         │  1:1  │ vector          │
│ ...             │       │ ...             │       │ model_id        │
└─────────────────┘       └─────────────────┘       │ dimensions      │
                                                     │ ...             │
                                                     └─────────────────┘
```

### 3.2 カーディナリティ

| 関係                      | カーディナリティ | 説明                        |
| ------------------------- | ---------------- | --------------------------- |
| files → chunks            | 1:N              | 1ファイルに複数チャンク     |
| chunks → embeddings       | 1:1              | 1チャンクに1埋め込み        |
| embeddings → vector_index | N:1              | 複数埋め込みが1インデックス |

### 3.3 削除カスケード

```
files削除
    ↓ CASCADE
chunks削除
    ↓ CASCADE
embeddings削除
```

## 4. インデックス戦略

### 4.1 通常インデックス

| インデックス名          | カラム   | 種類   | 目的                   |
| ----------------------- | -------- | ------ | ---------------------- |
| embeddings_chunk_id_idx | chunk_id | UNIQUE | 一意性保証・高速検索   |
| embeddings_model_id_idx | model_id | 通常   | モデル別フィルタリング |

### 4.2 ベクトルインデックス

| 項目           | 値                      |
| -------------- | ----------------------- |
| インデックス名 | embeddings_vector_idx   |
| アルゴリズム   | DiskANN                 |
| 次元数         | 1536                    |
| メトリクス     | cosine (コサイン類似度) |
| 最大要素数     | 1,000,000               |

### 4.3 インデックス選択基準

| データ規模       | インデックス使用 | 理由                     |
| ---------------- | ---------------- | ------------------------ |
| < 10,000件       | 不要             | 線形スキャンで十分高速   |
| 10,000-100,000件 | 推奨             | パフォーマンス向上       |
| > 100,000件      | 必須             | 線形スキャンでは遅すぎる |

## 5. libSQL ベクトル検索API

### 5.1 サポート関数

| 関数                  | 説明             | 戻り値    |
| --------------------- | ---------------- | --------- |
| `vector_distance_cos` | コサイン距離     | 0.0 - 2.0 |
| `vector_distance_l2`  | ユークリッド距離 | 0.0 - ∞   |
| `vector_dot`          | 内積             | -∞ - ∞    |

### 5.2 類似度計算

```
コサイン類似度 = 1 - (コサイン距離 / 2)
```

| コサイン距離 | コサイン類似度 | 解釈     |
| ------------ | -------------- | -------- |
| 0.0          | 1.0            | 完全一致 |
| 1.0          | 0.5            | 直交     |
| 2.0          | 0.0            | 正反対   |

### 5.3 インデックス構文

```sql
-- インデックス作成
CREATE INDEX embeddings_vector_idx
ON embeddings(vector)
USING vector(1536)
WITH (metric = 'cosine');

-- インデックス削除
DROP INDEX IF EXISTS embeddings_vector_idx;
```

## 6. データ変換

### 6.1 Float32Array ⇔ Blob

```typescript
// Float32Array → Buffer (Blob)
function vectorToBlob(vector: Float32Array): Buffer {
  return Buffer.from(vector.buffer);
}

// Buffer (Blob) → Float32Array
function blobToVector(blob: Buffer): Float32Array {
  return new Float32Array(blob.buffer, blob.byteOffset, blob.length / 4);
}
```

### 6.2 データサイズ

| 次元数 | Float32サイズ | Blobサイズ  |
| ------ | ------------- | ----------- |
| 1536   | 4 bytes/要素  | 6,144 bytes |
| 768    | 4 bytes/要素  | 3,072 bytes |
| 384    | 4 bytes/要素  | 1,536 bytes |

## 8. エラーハンドリング

### 8.1 エラー種別

| エラー種別             | 対処                           |
| ---------------------- | ------------------------------ |
| UNIQUE制約違反         | 重複チェック後に再試行         |
| 外部キー制約違反       | 親レコード存在確認             |
| 次元数不一致           | バリデーションエラーを返す     |
| インデックス構築失敗   | ログ出力、再構築オプション提供 |
| トランザクションエラー | 自動ロールバック               |

### 8.2 リトライ戦略

| エラー種別   | リトライ | 最大回数 | バックオフ      |
| ------------ | -------- | -------- | --------------- |
| 接続エラー   | Yes      | 3        | 指数 (1s,2s,4s) |
| タイムアウト | Yes      | 2        | 固定 (5s)       |
| 制約違反     | No       | -        | -               |
| クエリエラー | No       | -        | -               |

## 9. 既存システムとの統合

### 9.1 chunks テーブル連携

- **外部キー**: embeddings.chunk_id → chunks.id
- **カスケード削除**: chunks削除時にembeddingsも自動削除
- **一意性**: 1つのchunkに対して1つのembeddingのみ

### 9.2 relations.ts 更新

```typescript
// 追加するリレーション
export const embeddingsRelations = relations(embeddings, ({ one }) => ({
  chunk: one(chunks, {
    fields: [embeddings.chunkId],
    references: [chunks.id],
  }),
}));

// chunksRelationsに追加
export const chunksRelations = relations(chunks, ({ one }) => ({
  // 既存のリレーション...
  embedding: one(embeddings, {
    fields: [chunks.id],
    references: [embeddings.chunkId],
  }),
}));
```

### 9.3 FTS5 との連携

- FTS5 (chunks_fts) はテキスト検索用
- ベクトルインデックスはセマンティック検索用
- 将来的にハイブリッド検索で両方を組み合わせ可能

## 10. パフォーマンス設計

### 10.1 目標値

| データ規模       | 検索時間目標 | 達成手段                     |
| ---------------- | ------------ | ---------------------------- |
| < 10,000件       | < 50ms       | 線形スキャン or インデックス |
| 10,000-100,000件 | < 100ms      | DiskANNインデックス          |
| > 100,000件      | < 200ms      | DiskANNインデックス + 最適化 |

### 10.2 最適化ポイント

1. **インデックスパラメータ調整**
   - efConstruction: 構築時の精度 (推奨: 200)
   - efSearch: 検索時の精度 (推奨: 100)

2. **クエリ最適化**
   - 必要なカラムのみSELECT
   - JOINの最小化
   - LIMITの早期適用

3. **バッチ処理最適化**
   - 適切なバッチサイズ (100件)
   - トランザクション範囲の最適化

## 11. セキュリティ考慮事項

### 11.1 入力バリデーション

| 項目           | バリデーション                        |
| -------------- | ------------------------------------- |
| ベクトル次元数 | 設定値と一致することを確認            |
| ベクトル値     | 有限値であることを確認 (NaN, Inf除外) |
| chunk_id       | 存在するchunkへの参照であること       |
| limit          | 正の整数であること                    |
| minSimilarity  | 0.0 - 1.0 の範囲                      |

### 11.2 SQLインジェクション対策

- Drizzle ORMのパラメータバインディングを使用
- 動的SQLは使用しない
- ユーザー入力は常にバリデーション後に使用
