## 1. 概要

### 1.1 Skillとは（定義の再整理）

Skillは、Claude（メインのオーケストレーター）が **「必要だ」と判断したときだけ** 参照・起動する、自己完結型のパッケージ。
単なる「保存プロンプト（スラッシュコマンド）」ではなく、以下を束ねた **実行設計の単位** である。

- **段階的ロード（Progressive Disclosure）** により、最初はメタ情報だけ、必要時に SKILL.md、実行直前に必要リソースのみを読み込む
- **Task（使い捨ての作業窓）** に処理を分離し、重い思考・探索・試行錯誤をメインコンテキストへ持ち込まずに完了させる
- **scripts/references/assets** を同梱し、「判断はLLM、決定論的処理はスクリプト、知識は外部化」という分業を可能にする

> 重要: Skillは「メインに指示を追加する機構」ではなく、**コンテキストと作業領域をフェーズ単位で分離して汚さないための仕組み**。

### 1.2 Skillが提供するもの

| 提供内容         | 説明                                                          |
| ---------------- | ------------------------------------------------------------- |
| 専門ワークフロー | 特定ドメイン向けの複数ステップ手順（実行設計）                |
| ツール統合       | 特定ファイル形式・コマンド・スクリプトを安全に扱う手順        |
| ドメイン専門知識 | 企業固有の用語、スキーマ、業務ルール（外部化前提）            |
| バンドルリソース | scripts（決定論処理）/ references（知識）/ assets（出力素材） |

### 1.3 責務境界（誤解防止版）

| 行うこと                                                  | 行わないこと                                                   |
| --------------------------------------------------------- | -------------------------------------------------------------- |
| **Skill内のワークフロー設計（段階・判断ポイント）を提示** | メイン会話の長期的な指揮統制そのもの（オーケストレーター責務） |
| Task単位で必要な入力/出力/制約を明示                      | 他スキルの“自動実行”を強制する（呼ぶ/呼ばないはメイン判断）    |
| scripts による確実な実行（低自由度領域の外出し）          | README等の補助ドキュメント作成（不要）                         |
| テンプレで出力形式を標準化                                | すべての知識を SKILL.md にベタ書き（referencesへ外部化）       |

## 2. コア原則

### 2.1 簡潔さが鍵（Concise is Key）

コンテキストウィンドウは公共財。Skillはシステムプロンプト、会話履歴、他スキルのメタデータ、ユーザーリクエストとコンテキストを共有する。

**デフォルトの前提: Claude は既に非常に賢い。** Claude が持っていないコンテキストのみを追加する。

各情報に対して問いかける：

- 「Claude は本当にこの説明を必要としているか？」
- 「この段落はトークンコストに見合う価値があるか？」

**冗長な説明よりも簡潔な例を優先する。**

### 2.2 知識圧縮アンカー（Squeeze / Anchors）

> ※「書籍参照」そのものを frontmatter フィールドで構造化しない。
> ただし **“知識圧縮アンカー”** という設計思想は、**SKILL.md の description に 埋め込む**。

**知識圧縮アンカーとは**
詳細を長文で書かずに、Claudeが学習済み/既知の枠組みや、プロジェクト内の一次資料（runbook、設計、スキーマ）を **短い参照行** として置くことで、方針をブレさせず・トークンを節約する方法。

- 例：書籍名、設計思想名、社内ルール名、API/Schema名、Runbook名、決定事項ID など
- 重要：**アンカーは「何を参照し、何を適用するか」まで一行で明示**する（単なる名称羅列は不可）

**規則（description に埋め込む）**

- 1 Skill あたり 1〜5 個まで（過多禁止）
- 「アンカー名」＋「適用範囲」＋「今回の目的」を同一行に入れる
- Markdownの箇条書き（`-` や `*`）は禁止（description 内）

### 2.3 適切な自由度の設定（Set Appropriate Degrees of Freedom）

タスクの脆弱性と変動性に応じて具体性のレベルを調整：

| 自由度 | 使用場面                                     | 記述形式                         |
| ------ | -------------------------------------------- | -------------------------------- |
| 高     | 複数アプローチが有効、判断がコンテキスト依存 | テキストベース指示               |
| 中     | 推奨パターンあり、一定変動は許容             | 擬似コード or パラメータ付き手順 |
| 低     | 脆弱でエラー誘発、一貫性重要                 | scripts 実行 + 少数パラメータ    |

### 2.4 Progressive Disclosure（段階的開示）

必要な情報を必要な時にのみ読み込む3層システム：

| レベル | 読み込み対象                                         | 目安       |
| ------ | ---------------------------------------------------- | ---------- |
| 1      | メタデータ（name + description）                     | 最小       |
| 2      | SKILL.md 本文                                        | 中         |
| 3      | バンドルリソース（agents/references/scripts/assets） | 必要時のみ |

**読み込み判断基準**:

| 条件                 | 読み込むレベル         |
| -------------------- | ---------------------- |
| スキルの存在確認のみ | Level 1                |
| 基本的な使用         | Level 2                |
| Task仕様が必要       | Level 3（agents/）     |
| 詳細な知識が必要     | Level 3（references/） |
| 決定論的処理が必要   | Level 3（scripts/）    |
| 出力素材が必要       | Level 3（assets/）     |

## 3. Skill構造仕様

### 3.1 標準フォルダ構造（改訂：agents/ を追加）

```
skill-name/
├── SKILL.md              # 必須: 中枢（500行以内推奨）
├── agents/               # 推奨: Task仕様書（実行直前にロードされる前提で軽量に）
│   ├── task-1.md
│   └── task-n.md
├── scripts/              # 任意: 実行可能コード（Python/Bash/Node等）
│   └── log_usage.mjs     # 推奨: フィードバックループ用標準スクリプト
├── references/           # 任意: 必要時に読む参照資料（知識の外部化）
└── assets/               # 任意: 出力で使用する素材（テンプレ/雛形等）
```

**重要**: 以下のファイルは作成しない（SkillはAI実行のための情報のみ）

- README.md
- INSTALLATION_GUIDE.md
- QUICK_REFERENCE.md
- その他の補助ドキュメント

### 3.1.1 agents/ の位置づけ（誤解防止）

- `skills/.../agents/*.md` は **「サブエージェント（永続人格）の定義」ではない**
- ここに書くのは **Taskの仕様書**（役割・入力・出力・制約・参照先）
- **実行直前に、そのTask分だけまとめて読まれる前提**
  → だから _軽量に_、知識は `references/` に逃がす

## 3.2 SKILL.md 仕様

### 3.2.1 YAML Frontmatter

**公式フィールド（Anthropic準拠）**:

| フィールド      | 型       | 必須 | 説明                                       |
| --------------- | -------- | ---- | ------------------------------------------ |
| `name`          | string   | 必須 | スキル識別子（ハイフンケース、最大64文字） |
| `description`   | string   | 必須 | スキル説明と発動条件（最大1024文字）       |
| `license`       | string   | 任意 | ライセンス情報                             |
| `allowed-tools` | string[] | 任意 | 許可ツール                                 |
| `metadata`      | object   | 任意 | 追加メタ                                   |

**プロジェクト拡張フィールド（改訂）**:

| フィールド     | 型       | 必須 | 説明                                                |
| -------------- | -------- | ---- | --------------------------------------------------- |
| `tags`         | string[] | 任意 | 検索用タグ                                          |
| `dependencies` | string[] | 任意 | 依存スキルのパス（※参照のみ。自動実行を意味しない） |

> **削除**: `references:` フィールド（書籍等の構造化リスト）は本プロジェクトでは採用しない。
> 理由：description 内にアンカーとして統合し、トリガー性能（発見性）を優先するため。

### 3.2.2 name フィールドの規則

| 規則                     | 説明                         |
| ------------------------ | ---------------------------- |
| ハイフンケース           | 小文字、数字、ハイフンのみ   |
| 最大64文字               | 長すぎる名前は不可           |
| 先頭・末尾にハイフン不可 | `my-skill` ○、`-my-skill-` × |
| 連続ハイフン不可         | `my-skill` ○、`my--skill` ×  |
| ディレクトリ名と一致     | フォルダ名と完全一致         |

### 3.2.2.1 自動生成時の正規化

UIウィザードや補助ツールで自然言語からスキル名を生成する場合は、`kebab-case` 規則に合わせて正規化する。

1. 入力を小文字化する
2. 非許容文字をハイフンに置換する
3. 連続ハイフンを1つに圧縮する
4. 先頭・末尾のハイフンを除去する
5. 空文字になる場合は `new-skill` を使う

同名のディレクトリがすでに存在する場合は、呼び出し側が `-2` 以降の連番で一意化する。
`SkillService.toWizardSkillName()` はこの規則に従う。

### 3.2.2.2 定数定義と一元化管理

`name` フィールドの検証ルールは実装リポジトリ側で以下の定数として一元管理される：

| 定数名                  | 値                         | 場所                                         |
| ----------------------- | -------------------------- | -------------------------------------------- |
| `SKILL_NAME_PATTERN`    | `^[a-z0-9]+(-[a-z0-9]+)*$` | `packages/shared/src/constants/skillName.ts` |
| `MAX_SKILL_NAME_LENGTH` | `64`                       | `packages/shared/src/constants/skillName.ts` |
| `MIN_SKILL_NAME_LENGTH` | `1`                        | `packages/shared/src/constants/skillName.ts` |

export 経路は `packages/shared/src/constants/index.ts` を経由する。
`skill-creator` / `skill-wizard` / Renderer の IPC 境界でも同一定数を参照することで、検証ルールの divergence を防ぐ。

関連タスク: `UT-SKILL-NAME-PATTERN-001`

### 3.2.3 description フィールド（最重要：トリガー設計）

**descriptionはスキルの主要なトリガーメカニズム。**
Skillは段階的ロードされるため、発見フェーズでは本文より description が効く。

| 規則                          | 説明                                                                 |
| ----------------------------- | -------------------------------------------------------------------- |
| 最大1024文字                  | 簡潔かつ包括的に                                                     |
| 角括弧禁止                    | `<` `>` は使用不可                                                   |
| 「何を」と「いつ」を含める    | 機能＋発動条件を必ず書く                                             |
| 本文に When to Use 不要       | 発動条件は description に集約                                        |
| アンカーは description に統合 | ドキュメント/リファレンス/スイーズ情報は **Markdown禁止で** 埋め込む |

**description 記述形式（Markdown禁止版）**
※ `-` や `*` による箇条書きは使わない。行区切りで表現する。

```yaml
description: |
  {{スキルの概要（2〜3行）}}

  Anchors:
  • {{アンカー名}} / 適用: {{適用範囲}} / 目的: {{目的}}
  • {{アンカー名}} / 適用: {{適用範囲}} / 目的: {{目的}}

  Trigger:
  Use when {{英語での発動条件（短く、具体例語彙を含める）}}.
```

> Anchors には「書籍」「社内ルール」「スキーマ」「Runbook」「API仕様」「設計方針」などを混在させてよい。
> ただし **“適用範囲” と “目的” を必ず添える**。

### 3.2.4 本文（Markdown Body）

Frontmatter の後に続く指示とガイダンス。スキル発動後にのみ読まれる。

**推奨セクション構造**:

| セクション              | 必須 | 説明                                         |
| ----------------------- | ---- | -------------------------------------------- |
| 概要                    | 必須 | 1-2文で目的                                  |
| ワークフロー            | 推奨 | Phase ベースの流れ（Task分割の案内を含める） |
| Task仕様（ナビ）        | 必須 | agents/ の各Taskをいつ呼ぶか、入出力は何か   |
| ベストプラクティス      | 必須 | すべきこと/避けるべきこと                    |
| リソース/スクリプト参照 | 推奨 | references/ scripts/ assets/ への導線        |

**行数制約**: 500行以内。超過時は references/ に分離。

## 3.3 agents/ ディレクトリ仕様（Task仕様書）

### 3.3.1 目的

- Taskを「一時的ワーカー」として起動するときの **仕様書**
- Task内の試行錯誤ログをメインへ持ち込まない前提で、**入出力と制約**に集中させる

### 3.3.2 agents/\*.md 標準フォーマット（必須テンプレ）

`skills/<skill-name>/agents/*.md` は **Task仕様書**であり、各Taskを「一時的ワーカー」として起動する際の **役割・判断基準・入出力契約**を定義する。

- **実在する専門家名**は「思考様式・判断軸の参照ラベル」として扱う
  - 本人を名乗る／本人の発言を捏造する／個人情報を扱う、はしない
  - 参照するのは **フレームワーク・方法論・思考の型**のみ

- agents/\*.md は **実行直前に一括ロード**される前提のため、過度に長文化しない
  - 長い知識本文・サンプル・詳細手順は `references/` に外部化し、ここは「参照先」と「適用方法（短文）」に留める

---

## 3.4 scripts/ ディレクトリ仕様（維持）

（※あなたの原文を基本維持。冪等性・終了コード・ヘルプ等は量産に必須なので残しています）

### 3.4.1 使用場面

| 場面                         | 説明                   |
| ---------------------------- | ---------------------- |
| 同じコードを繰り返し書き直す | スクリプト化して再利用 |
| 決定論的な信頼性が必要       | AIの不確実性を排除     |
| 複雑な処理の確実な実行       | 冪等性を保証           |

### 3.4.2 スクリプト実装要件

| 要件       | 説明                   |
| ---------- | ---------------------- |
| 冪等性     | 何度実行しても同じ結果 |
| エラー出力 | stderr に詳細を出す    |
| 引数検証   | 必須引数を確認         |
| ヘルプ     | `-h`/`--help`          |
| 終了コード | 成功0、一般1、引数2…   |

### 3.4.3 終了コード規則

| 終了コード | 意味           |
| ---------- | -------------- |
| 0          | 成功           |
| 1          | 一般的エラー   |
| 2          | 引数エラー     |
| 3          | ファイル不在   |
| 4          | 検証失敗       |
| 5          | 依存関係エラー |

### 3.4.4 標準スクリプト: log_usage.mjs

フィードバックループの核。詳細は 7章参照。

## 3.5 references/ ディレクトリ仕様（維持＋補強）

### 3.5.1 役割（定義の明確化）

- references/ は **知識の外部ストレージ**
- SKILL.md や agents/\*.md を軽量に保つための逃がし先
- 「毎回読む前提」ではなく **必要時にだけ読む** ことを前提に設計

### 3.5.2 使用場面（原文維持）

| 場面                 | パス形式                                 |
| -------------------- | ---------------------------------------- |
| データベーススキーマ | `references/{{schema-name}}.md`          |
| APIドキュメント      | `references/{{api-name}}.md`             |
| ドメイン知識         | `references/{{domain-name}}.md`          |
| ポリシー・ルール     | `references/{{policy-name}}.md`          |
| ワークフローガイド   | `references/{{workflow-name}}.md`        |
| 出力パターン         | `references/{{output-type}}-patterns.md` |

### 3.5.3 ベストプラクティス（原文維持）

| プラクティス             | 説明                                      |
| ------------------------ | ----------------------------------------- |
| SKILL.md を軽量に保つ    | 詳細は references/                        |
| 重複を避ける             | 情報は SKILL.md か references/ のどちらか |
| 大きなファイル（>10k語） | SKILL.md に検索パターンを含める           |
| 100行超のファイル        | 先頭に目次                                |

#### 3.5.4 Progressive Disclosure パターン

**パターン1: 高レベルガイドと参照**

```markdown
# {{スキル名}}

## Quick start

{{基本的な使用方法}}

## Advanced features

- **{{機能1}}**: See [references/{{feature-1}}.md](references/{{feature-1}}.md)
- **{{機能2}}**: See [references/{{feature-2}}.md](references/{{feature-2}}.md)
- **{{機能N}}**: See [references/{{feature-n}}.md](references/{{feature-n}}.md)
```

**パターン2: ドメイン別構成**

```
{{skill-name}}/
├── SKILL.md (概要とナビゲーション)
└── references/
    ├── {{domain-1}}.md ({{ドメイン1の説明}})
    ├── {{domain-2}}.md ({{ドメイン2の説明}})
    └── {{domain-n}}.md ({{ドメインNの説明}})
```

**パターン3: バリアント別構成**

```
{{skill-name}}/
├── SKILL.md (ワークフロー + バリアント選択)
└── references/
    ├── {{variant-1}}.md ({{バリアント1パターン}})
    ├── {{variant-2}}.md ({{バリアント2パターン}})
    └── {{variant-n}}.md ({{バリアントNパターン}})
```

**重要なガイドライン**:

- 深くネストした参照を避ける（SKILL.md から1レベルに保つ）
- すべての参照ファイルは SKILL.md から直接リンク（相対パス使用）

### 3.5 assets/ ディレクトリ仕様

コンテキストに読み込むためではなく、Claude が生成する出力で使用するファイル。

#### 3.5.1 使用場面

| 場面             | パス形式                           |
| ---------------- | ---------------------------------- |
| テンプレート     | `assets/{{template-name}}.{{ext}}` |
| 画像・アイコン   | `assets/{{image-name}}.{{ext}}`    |
| ボイラープレート | `assets/{{boilerplate-name}}/`     |
| フォント         | `assets/{{font-name}}.{{ext}}`     |
| サンプルデータ   | `assets/{{data-name}}.{{ext}}`     |

#### 3.5.2 利点

- 出力リソースをドキュメントから分離
- コンテキストに読み込まずにファイルを使用可能

## 4. ワークフローパターン

### 4.1 シーケンシャルワークフロー

複雑なタスクでは、操作を明確な順序のステップに分解。SKILL.md の冒頭でプロセスの概要を示す：

```markdown
{{タスク名}}は以下のステップで行う：

1. {{ステップ1の説明}}（run scripts/{{script-1}}.mjs）
2. {{ステップ2の説明}}（edit {{config-file}}.json）
3. {{ステップ3の説明}}（run scripts/{{script-2}}.mjs）
4. {{ステップNの説明}}（run scripts/{{script-n}}.mjs）
```

### 4.2 条件分岐ワークフロー

分岐ロジックを持つタスクでは、Claude を判断ポイントに導く：

```markdown
1. {{判断ポイント}}を判断する：
   **{{条件A}}？** → 「{{ワークフローA}}」に従う
   **{{条件B}}？** → 「{{ワークフローB}}」に従う

2. {{ワークフローA}}: See [references/{{workflow-a}}.md](references/{{workflow-a}}.md)
3. {{ワークフローB}}: See [references/{{workflow-b}}.md](references/{{workflow-b}}.md)
```

2. {{アクション項目N}}

## {{出力タイプ}}構造

# {{タイトル変数}}

## 6. スキル作成・更新プロセス

### 6.1 プロセス概要

**新規作成フロー**:

```
1. 具体例でスキルを理解する
       ↓
2. 再利用可能なスキルコンテンツを計画する
       ↓
3. スキルを初期化する（init_skill.mjs）
       ↓
4. スキルを編集する（リソース実装 + SKILL.md 作成）
       ↓
5. スキルを検証する（quick_validate.mjs）
       ↓
6. 実際の使用に基づいてイテレーション
```

**更新フロー**:

```
1. 更新トリガーを特定する
       ↓
2. 影響範囲を分析する
       ↓
3. 更新を実装する
       ↓
4. 検証する（quick_validate.mjs）
       ↓
5. フィードバックを記録する（log_usage.mjs）
```

### 6.2 Step 1: 具体例でスキルを理解する

スキルの使用パターンが既に明確に理解されている場合のみスキップ。既存スキルでも価値がある。

効果的なスキルを作成するには、スキルがどのように使用されるかの具体例を明確に理解する。

**確認すべき質問**:

- 「このスキルはどのような機能をサポートすべきか？」
- 「このスキルがどのように使用されるか、いくつか例を挙げられるか？」
- 「このスキルをトリガーするためにユーザーは何と言うか？」
- 「参照すべき書籍や知識体系は何か？」

**このステップの完了条件**: スキルがサポートすべき機能の明確な理解が得られた時点。

### 6.3 Step 2: 再利用可能なスキルコンテンツを計画する（追記）

具体例を効果的なスキルに変換するため、各例を分析：

1. 例をゼロから実行する方法を検討
2. これらのワークフローを繰り返し実行する際に役立つスクリプト、参照資料、素材を特定
3. 参照すべき書籍を特定（コンテキスト圧縮）
4. Task分割（agents/）を必須分析対象にする

**分析パターン**:

| パターン             | 問題                         | 解決策                                       |
| -------------------- | ---------------------------- | -------------------------------------------- |
| コード重複           | 同じコードを毎回書き直す     | `scripts/{{script-name}}.mjs` にスクリプト化 |
| ボイラープレート重複 | 同じテンプレートを毎回作成   | `assets/{{template-name}}/` に素材化         |
| 知識再発見           | 同じ情報を毎回調査           | `references/{{reference-name}}.md` に参照化  |
| 原則適用             | 同じ判断基準を毎回思い出す   | `references` に書籍参照として知識体系を圧縮  |
| 思考ログ肥大         | 探索・試行錯誤がメインに残る | agents/ に Task化して隔離                    |
| フェーズ混線         | リサーチと生成が同窓で混ざる | Taskをフェーズ単位で分ける                   |
| 知識ベタ書き         | SKILL/agents が肥大          | references へ外部化                          |

### 6.4 Step 3: スキルを初期化する

開発中のスキルが既に存在し、イテレーションが必要な場合のみスキップ。

新規スキルを作成する場合、常に `init_skill.mjs` を実行：

```bash
Node scripts/init_skill.mjs <skill-name> --path .claude/skills
```

スクリプトの実行内容：

- 指定パスにスキルディレクトリを作成
- 適切な frontmatter と TODO プレースホルダを含む SKILL.md テンプレートを生成
- 例示リソースディレクトリを作成：`scripts/`, `references/`, `assets/`

初期化後、生成された SKILL.md と例示ファイルを必要に応じてカスタマイズまたは削除。

### 6.5 Step 4: スキルを編集する

スキルは別の Claude インスタンスが使用するために作成される。Claude に有益で非自明な情報を含める。

#### 6.5.1 再利用可能コンテンツから開始

実装は Step 2 で特定した再利用可能リソースから開始：`scripts/`, `references/`, `assets/`

**スクリプトのテスト**: 追加したスクリプトは実際に実行してバグがないことと期待通りの出力を確認。類似スクリプトが多い場合は代表的なサンプルのみテスト。

**不要なディレクトリの削除**: 初期化スクリプトが作成した例示ファイルで不要なものは削除。

#### 6.5.2 SKILL.md を更新（改訂：references フィールド削除・description統合）

**Frontmatter テンプレ（改訂版）**

```yaml
---
name: {{skill-name}}
description: |
  {{スキルの機能説明（2〜3行）}}

  • {{ドキュメント/ルール/スキーマ/書籍名など}} / 適用: {{適用範囲}} / 目的: {{目的}}
  • {{同上}} / 適用: {{適用範囲}} / 目的: {{目的}}

  Trigger:
    Use when {{発動条件}}.
    {{word1}}, ..., {{wordN}}
allowed-tools:
  - {{tool1}}
  ...
  - {{toolN}}
---
```

**本文の作成（追記：Taskナビ必須）**

- agents/ の各Taskを「いつ」「何の入力で」「何を返すか」導線として書く
- references/ は「読む条件」を明記（常時読み込み禁止）
- scripts/ は「引数」「期待出力」「失敗時の扱い」を明記

### 6.6 Step 5: スキルを検証する

開発完了後、検証スクリプトを実行：

```bash
Node scripts/quick_validate.mjs .claude/skills/<skill-name>
```

**検証項目**:

- SKILL.md の存在
- YAML frontmatter の形式
- 必須フィールド（name, description）の存在
- name のハイフンケース規則
- description の文字数制限と禁止文字

### 6.7 Step 6: イテレーション

スキルをテストした後、ユーザーが改善を要求することがある。

**イテレーションワークフロー**:

1. 実際のタスクでスキルを使用
2. 苦戦や非効率に気づく
3. SKILL.md またはバンドルリソースをどう更新すべきか特定
4. 変更を実装して再テスト
5. `scripts/log_usage.mjs` でフィードバックを記録

### 6.8 スキル更新プロセス

既存スキルの更新・改善を行うプロセス。新規作成とは異なり、既存の構造を維持しながら改善を加える。

#### 6.8.1 更新トリガー

| トリガー           | 説明                                        | 対応                           |
| ------------------ | ------------------------------------------- | ------------------------------ |
| フィードバック蓄積 | LOGS.md に改善点が蓄積                      | パターンを分析し優先度を決定   |
| 仕様変更           | 参照書籍の新版、API変更、ドメイン知識の更新 | 影響範囲を特定し段階的に更新   |
| パフォーマンス問題 | スキルの実行効率が低下                      | ボトルネックを特定し最適化     |
| 使用パターン変化   | 想定外の使用方法が主流に                    | description と発動条件を見直し |
| 依存スキル更新     | 依存先スキルの変更による影響                | 互換性を確認し必要に応じて更新 |

#### 6.8.2 影響範囲分析

更新前に以下を確認：

| 確認項目             | 確認方法                                     |
| -------------------- | -------------------------------------------- |
| 依存エージェント     | skill_list.md でスキルを使用するエージェント |
| 依存スキル           | dependencies フィールドの参照先              |
| スクリプト利用状況   | scripts/ 内のファイルを呼び出すワークフロー  |
| references/ 参照状況 | SKILL.md からのリンク                        |

#### 6.8.3 更新タイプ別ワークフロー

**Type A: コンテンツ更新（低リスク）**

対象: 誤字修正、説明文の改善、参照書籍の追加

```
1. SKILL.md を直接編集
2. quick_validate.mjs で検証
3. log_usage.mjs で記録
```

**Type B: 構造更新（中リスク）**

対象: セクション追加、ワークフロー変更、スクリプト追加

```
1. 変更計画を立案（影響範囲を明記）
2. バックアップを作成（git stash または別ブランチ）
3. 段階的に変更を実装
4. 各段階で quick_validate.mjs を実行
5. 依存エージェントでの動作確認
6. log_usage.mjs で記録
```

**Type C: 破壊的更新（高リスク）**

対象: name 変更、description の大幅変更、ディレクトリ構造変更

```
1. 影響を受けるすべてのエージェント・コマンドをリストアップ
2. マイグレーション計画を作成
3. 新旧両方のパスで一時的に動作するよう移行期間を設ける
4. 依存先を順次更新
5. 旧パスを削除
6. skill_list.md を更新
7. log_usage.mjs で記録
```

#### 6.8.4 更新時の注意事項

| 注意事項                       | 理由                                     |
| ------------------------------ | ---------------------------------------- |
| description は慎重に変更       | 発動条件が変わりエージェントの挙動に影響 |
| name 変更は最終手段            | すべての参照先の更新が必要               |
| scripts/ の互換性を維持        | 引数・出力形式の変更は依存先に影響       |
| references/ の削除前に確認     | SKILL.md からのリンク切れを防ぐ          |
| 更新後は必ずフィードバック記録 | 継続的改善のためのデータ蓄積             |

## 7. フィードバックループ

### 7.1 目的

スキルが使用されるたびにフィードバックを収集し、継続的に改善する仕組みを提供する。

### 7.2 実装方式

**採用方式**: エージェント責務方式（明示的な記録フェーズ）

**理由**:

- 確実性が最も高い（ワークフローに組み込むため記録漏れがない）
- AIの不確実性を排除（スクリプトで確実に実行）
- メンテナンス性が高い（エージェントテンプレートで標準化）

### 7.3 標準ログスクリプト: log_usage.mjs

**ファイル**: `scripts/log_usage.mjs`

**責務**:

| 処理           | 説明                                                 |
| -------------- | ---------------------------------------------------- |
| 実行記録の追記 | 使用履歴をログファイルに記録                         |
| メトリクス更新 | 使用回数・成功率を更新                               |
| レベル評価     | 現在のメトリクスがレベルアップ条件を満たすかチェック |

**引数**:

| 引数       | 必須 | 説明                       |
| ---------- | ---- | -------------------------- |
| `--result` | 必須 | `success` または `failure` |
| `--phase`  | 任意 | 実行したフェーズ名         |
| `--agent`  | 任意 | 実行したエージェント名     |
| `--notes`  | 任意 | 追加のフィードバックメモ   |

**使用形式**:

```bash
node .claude/skills/{{skill-name}}/scripts/log_usage.mjs \
  --result {{success|failure}} \
  --phase "{{phase-name}}" \
  --agent "{{agent-name}}"
```

## 8. 品質基準

### 8.1 スキル作成時のチェックリスト

| チェック項目                                 | 検証方法                               |
| -------------------------------------------- | -------------------------------------- |
| SKILL.md が 500 行以内                       | `wc -l SKILL.md`                       |
| YAML frontmatter が有効                      | quick_validate.py                      |
| name がハイフンケース（最大64文字）          | 正規表現で検証                         |
| description が 1024 文字以内                 | 文字数カウント                         |
| 書籍参照が含まれている                       | references フィールド確認              |
| 不要な補助ドキュメントがない                 | README.md 等の不在確認                 |
| references/ のファイルが SKILL.md からリンク | grep で検証                            |
| agents/\*.md が「仕様書」になっている        | 役割/入力/出力/制約/参照が揃っているか |
| agents に知識本文が埋め込まれていない        | 大段落がある場合 references へ移動     |
| description に Anchors と Trigger がある     | 1024文字以内、Markdown不使用           |
| references/ は SKILL.md から直リンク         | grep で検証                            |

### 8.2 ベストプラクティス要約

| カテゴリ               | ベストプラクティス                                      |
| ---------------------- | ------------------------------------------------------- |
| 簡潔さ                 | 説明より例を優先、Claude が既に知っていることは書かない |
| 書籍参照               | 1-3冊の著名書籍で知識体系を圧縮参照                     |
| 自由度                 | タスクの脆弱性に応じて具体性を調整                      |
| Progressive Disclosure | SKILL.md を軽量に、詳細は references/ に                |
| 重複回避               | 情報は SKILL.md か references/ のどちらか一方のみ       |
| スクリプト             | 繰り返し書くコードはスクリプト化、必ずテスト            |
| 発動条件               | description に明確に記述（本文ではなく）                |
| 相対パス               | references/ へのリンクは相対パスで記述                  |

## 9. 命名規則

### 9.1 スキル名

| 規則                       | パターン                                  |
| -------------------------- | ----------------------------------------- |
| ハイフンケース             | `{{domain}}-{{topic}}`                    |
| 具体的で明確               | 曖昧な単語（optimization, utils）を避ける |
| 動詞+名詞 または 名詞+名詞 | `{{verb}}-{{noun}}` / `{{noun}}-{{noun}}` |
| 最大64文字                 | 簡潔に                                    |

### 9.2 ファイル名

| ファイル種別 | 命名規則                                                  |
| ------------ | --------------------------------------------------------- |
| スクリプト   | `{{verb}}_{{target}}.py` または `{{verb}}_{{target}}.mjs` |
| 参照資料     | `{{topic}}.md` または `{{domain}}.md`                     |
| アセット     | `{{purpose}}.{{ext}}` または `{{asset-name}}/`            |

## 10. ファイル参照形式

### 10.1 相対パスの記述規則

**SKILL.md からの相対パス形式を使用**:

| 参照対象   | パス形式                 |
| ---------- | ------------------------ |
| スクリプト | `scripts/{{file}}.py`    |
| 参照資料   | `references/{{file}}.md` |
| アセット   | `assets/{{file}}`        |

**SKILL.md での参照記述形式**:

```markdown
## Resources

- **{{リソース1名}}**: See [references/{{resource-1}}.md](references/{{resource-1}}.md)
- **{{リソース2名}}**: See [references/{{resource-2}}.md](references/{{resource-2}}.md)
- **{{リソースN名}}**: See [references/{{resource-n}}.md](references/{{resource-n}}.md)

## Scripts

- `scripts/{{script-1}}.py`: {{スクリプト1の説明}}
- `scripts/{{script-n}}.mjs`: {{スクリプトNの説明}}
```

### 10.2 禁止される参照形式

| 形式                 | 問題点                                 |
| -------------------- | -------------------------------------- |
| スキル名のみ         | パスが不明確で読み込みできない         |
| 絶対パス             | 環境依存（ユーザーごとにパスが異なる） |
| `../` を含む相対パス | 曖昧さが生じ、正確なパス解決ができない |

## 11. skill_list.md 仕様

### 11.1 目的

利用可能な全スキルのインデックスを提供し、スキルの発見性とエージェントへの割り当てを効率化する。

### 11.2 ファイル配置

`.claude/skills/skill_list.md`

### 11.3 記述形式

```markdown
## {{番号}}. {{エージェント役割名}}

- **エージェント名:** `@{{agent-name}}`
- **エージェントの配置:** `.claude/agents/{{agent-name}}.md`

| スキル名           | パス                                     | 概要                |
| ------------------ | ---------------------------------------- | ------------------- |
| **{{skill-name}}** | `.claude/skills/{{skill-name}}/SKILL.md` | {{20-40文字の概要}} |
```

### 11.4 更新ルール

| ルール             | 説明                                                 |
| ------------------ | ---------------------------------------------------- |
| スキル作成時       | 対応するエージェントセクションにエントリを追加       |
