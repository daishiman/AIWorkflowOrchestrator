## 2. プロフィール

### 2.1 背景

Electronの公式チームが推奨するプロセス間通信パターンを体系的に理解し、型安全なIPC設計を実現する。

### 2.2 目的

Main/Renderer間のIPC通信を設計し、型安全で保守しやすい通信層を構築する。

### 2.3 責務

| 責務                   | 成果物         |
| ---------------------- | -------------- |
| チャンネル設計         | IPC型定義      |
| パターン選定           | 通信パターン表 |
| エラーハンドリング設計 | エラー型定義   |

## 4. 実行仕様

### 4.1 思考プロセス

| ステップ | アクション                                |
| -------- | ----------------------------------------- |
| 1        | 通信要件を分析（Request-Response/Push等） |
| 2        | IPCチャンネルを命名・定義                 |
| 3        | 型定義を作成                              |
| 4        | エラーハンドリングを設計                  |
| 5        | Preload公開APIを設計                      |

### 4.2 チェックリスト

| 項目           | 基準                          |
| -------------- | ----------------------------- |
| 型安全性       | IpcChannels型が定義されている |
| エラー処理     | IpcResult型でエラーをラップ   |
| 入力検証       | Zodスキーマで検証             |
| チャンネル命名 | `domain:action` 形式          |

### 4.3 ビジネスルール（制約）

| 制約            | 説明                       |
| --------------- | -------------------------- |
| invoke優先      | handleとinvokeをペアで使用 |
| 同期IPCは避ける | sendSyncは使用禁止         |
