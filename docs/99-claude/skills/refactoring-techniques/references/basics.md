# リファクタリング基本概念

## リファクタリングとは

外部から見た振る舞いを変えずに、内部構造を改善するプロセス。
バグ修正や機能追加ではなく、コードの**設計を改善する**作業。

---

## 2つの帽子

Kent Beckが提唱した原則:

| モード           | 目的         | テスト       |
| ---------------- | ------------ | ------------ |
| リファクタリング | 構造改善のみ | 常にグリーン |
| 機能追加         | 新機能の実装 | 新テスト追加 |

**重要**: 2つを同時に行わない。帽子を切り替えて作業する。

---

## リファクタリングの価値

### 経済的価値

- **変更コスト削減**: 複雑なコードは変更に時間がかかる
- **バグ減少**: 理解しやすいコードはバグが少ない
- **開発速度向上**: 長期的な開発速度が向上

### 技術的価値

- **可読性向上**: コードの意図が明確になる
- **重複排除**: DRY原則の適用
- **設計改善**: より良い抽象化

---

## 実施タイミング

### リファクタリングすべき時

1. **機能追加前**: 追加しやすい構造にする
2. **バグ修正前**: 問題を理解しやすくする
3. **コードレビュー時**: 問題を発見したら即座に
4. **技術的負債返済**: 計画的なリファクタリング

### リファクタリングを避けるべき時

1. **締め切り直前**: リスクが高すぎる
2. **テストがない**: まずテストを書く
3. **全面書き換えが必要**: リファクタリングでは対応不可

---

## 安全なリファクタリングの原則

### 1. テストの保護

```
リファクタリング前: テストがグリーン
    ↓
変更を適用
    ↓
リファクタリング後: テストがグリーン
```

### 2. 小さなステップ

- 1回の変更は5分以内で完了できる粒度
- 各ステップでテストを実行
- 失敗したら即座にロールバック

### 3. バージョン管理

- 変更前にコミット
- 各ステップでコミット（推奨）
- ロールバック可能な状態を維持

## 基本的なリファクタリング

### Extract Method（メソッド抽出）

最も頻繁に使用するリファクタリング。

**適用条件**:

- コードブロックにコメントが必要
- 同じコードが複数箇所に存在
- メソッドが長すぎる

**手順**:

1. 抽出対象を特定
2. 新メソッドを作成
3. 抽出対象を新メソッドの呼び出しに置換
4. テスト実行

### Rename（名前変更）

意図を明確にする最も簡単なリファクタリング。

**適用条件**:

- 名前から意図が読み取れない
- 略語が使われている
- 処理内容と名前が一致しない

### Inline（インライン化）

不要な間接化を解消。

**適用条件**:

- メソッドの中身が名前と同じくらい明確
- 間接化が過剰
- 抽出が不適切だった

## メトリクス基準

| メトリクス   | 警告閾値 | 危険閾値 |
| ------------ | -------- | -------- |
| メソッド行数 | 20行     | 30行     |
| パラメータ数 | 3個      | 4個      |
| 循環的複雑度 | 7        | 10       |
| ネスト深度   | 2段階    | 3段階    |
| クラス行数   | 300行    | 500行    |
