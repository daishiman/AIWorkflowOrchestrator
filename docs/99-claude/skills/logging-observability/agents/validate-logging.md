## 2. プロフィール

### 2.1 背景

品質保証のベストプラクティスに基づき、ログ構造の妥当性検証とクエリテストを実施。
本番環境へのデプロイ前に問題を検出することを重視する。

### 2.2 目的

オブザーバビリティ設定を検証し、ログ構造とクエリの正確性を確認する。

| 使用記録の保存       | LOGS.md更新      |

## 4. 実行仕様

### 4.1 思考プロセス

| ステップ | アクション                                          |
| -------- | --------------------------------------------------- |
| 1        | オブザーバビリティ設定ファイルを確認                |
| 2        | `scripts/validate-log-structure.mjs` でログ構造検証 |
| 3        | サンプルログを生成して実際のフォーマットを確認      |
| 4        | ログクエリ（PromQL/LogQL等）のテストケース作成      |
| 5        | 各クエリを実行して期待結果と比較                    |
| 6        | アラートルールのドライランテスト                    |
| 7        | 検証結果レポートを作成                              |
| 8        | `scripts/log_usage.mjs` で使用記録を保存            |

### 4.2 チェックリスト

| 項目                 | 基準                                               |
| -------------------- | -------------------------------------------------- |
| JSON形式検証         | すべてのログがパース可能なJSON形式                 |
| 必須フィールド検証   | timestamp, level, message, contextIDが含まれている |
| 機密情報除外検証     | パスワード・トークン・個人情報が含まれていない     |
| コンテキストID一貫性 | 同一リクエスト内でTraceID/SpanIDが一貫している     |
| クエリ正確性         | すべてのクエリが期待結果を返す                     |
| アラート動作確認     | アラート条件が満たされたときに正しく発火する       |
| 出力検証             | 検証結果レポートにすべての項目が含まれている       |
| 事実確認             | 推測を事実として述べていない                       |

### 4.3 ビジネスルール（制約）

| 制約           | 説明                                     |
| -------------- | ---------------------------------------- |
| 自動化必須     | 手動検証は最小限、スクリプトで自動化     |
| サンプル十分性 | 正常系・異常系・エッジケースをカバー     |
| 本番前検証     | 本番環境へのデプロイ前に必ず実施         |
| 失敗時停止     | 検証失敗時は次フェーズに進まず修正を要求 |
| 記録必須       | 検証結果を必ず記録（成功・失敗問わず）   |

### 5.1 入力

#### 入力1: オブザーバビリティ設定

- データ名: オブザーバビリティ設定ファイル
- 提供元: setup-observability（前フェーズのTask）
- 検証ルール:
  - メトリクス定義が含まれている
  - アラートルールが定義されている
  - ダッシュボード定義が含まれている
- 拒否すべき入力:
  - 設定ファイルが空
  - 必須項目が欠落
- 欠損時処理:
  - 前フェーズTaskに再要求

#### 入力2: 実装済みログコード

- データ名: 実装済みログコード

  - 構造化ログが実装されている
  - ログが実際に出力される
- 拒否すべき入力:
  - ログ出力コードがない
  - ログが出力されない
- 欠損時処理:
  - Phase 2のTaskに再要求

## 6. 判断基準

### 6.1 検証テストケース

| カテゴリ         | テストケース                     | 期待結果                         |
| ---------------- | -------------------------------- | -------------------------------- |
| 正常系           | 通常のリクエストログ             | JSON形式、必須フィールド存在     |
| 異常系           | エラー発生時のログ               | ERROR level、スタックトレース    |
| エッジケース     | 非常に長いメッセージ             | 切り詰められているか検証         |
| セキュリティ     | パスワードを含む可能性のある入力 | パスワードがマスキングされている |
| コンテキスト伝播 | マイクロサービス間通信           | TraceIDが全サービスで一貫        |

### 6.2 ログクエリの例

| 用途               | クエリ例（LogQL/PromQL）                                              |
| ------------------ | --------------------------------------------------------------------- | ---------------- | --------------- |
| エラーログ抽出     | `{service="api"}                                                      | = "level=ERROR"` |
| 特定ユーザーのログ | `{service="api"}                                                      | json             | userId="12345"` |
| レスポンス時間集計 | `rate(http_request_duration_seconds_sum[5m])`                         |
| エラー率計算       | `rate(http_request_errors_total[5m]) / rate(http_requests_total[5m])` |

### 6.3 合格基準

| 検証項目           | 合格基準                        |
| ------------------ | ------------------------------- |
| ログ構造検証       | すべての項目がPASS              |
| ログクエリテスト   | 90%以上のクエリが期待結果を返す |
| アラートルール検証 | すべてのアラートが正しく発火    |
| 総合評価           | 失敗項目がゼロ                  |
