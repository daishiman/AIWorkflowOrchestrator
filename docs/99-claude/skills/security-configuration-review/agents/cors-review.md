## 4. 実行仕様

### 4.1 思考プロセス

1. ステップ1: 現在のCORS設定を特定（ミドルウェア設定、サーバー設定ファイル確認）
2. ステップ2: Access-Control-Allow-Origin の値を評価（ワイルドカード、具体的ドメイン、動的設定）
3. ステップ3: Access-Control-Allow-Credentials の設定と影響を確認
4. ステップ4: 許可メソッド（Access-Control-Allow-Methods）の必要最小限チェック
5. ステップ5: 許可ヘッダー（Access-Control-Allow-Headers）の妥当性評価
6. ステップ6: プリフライトリクエストのキャッシュ設定確認
7. ステップ7: セキュリティリスクと推奨設定の文書化

### 4.2 チェックリスト

- 項目: Access-Control-Allow-Origin の設定
  - 基準: ワイルドカード（\*）が認証情報を含むリクエストで使用されていない。信頼できるオリジンのみ許可。
- 項目: Access-Control-Allow-Credentials の設定
  - 基準: 必要な場合のみtrue、かつオリジンが明示的に指定されている
- 項目: Access-Control-Allow-Methods の制限
  - 基準: 必要なHTTPメソッドのみ許可（GET、POST等）。不要なメソッド（DELETE、PUT等）が無制限に許可されていない
- 項目: Access-Control-Allow-Headers の制限
  - 基準: 必要なカスタムヘッダーのみ許可。ワイルドカードや過度に広範なヘッダー許可がない
- 項目: オリジン検証ロジック
  - 基準: 動的なオリジン許可の場合、ホワイトリストベースの検証が実装されている
- 項目: 出力検証: すべての必須項目が含まれているか
  - 基準: 現状分析、セキュリティリスク評価、推奨設定、実装例が含まれている
- 項目: 事実確認: 推測を事実として述べていないか
  - 基準: 設定変更の影響については「可能性がある」等の限定詞を使用

### 4.3 ビジネスルール（制約）

- 内容: ワイルドカード（\*）は認証情報を含まないパブリックAPIのみで使用可能
- 内容: 本番環境でのCORS設定変更は、開発環境での十分なテスト後に実施
- 内容: オリジンリストは環境変数で管理し、コードに直接埋め込まない

## 5. インターフェース

### 5.1 入力

#### 入力1

- データ名: CORS設定ファイル または ミドルウェア設定
- 提供元: 外部（ユーザー指定）
- 検証ルール:
  有効な設定ファイルパスまたは設定オブジェクト
- 拒否すべき入力:
  不完全な設定情報
- 欠損時処理:
  ユーザーに設定ファイルの場所を再要求

#### 入力2

- データ名: 想定されるクライアントオリジンリスト
- 提供元: 外部（ユーザー指定）
- 検証ルール:
  有効なURL形式のオリジンリスト
- 拒否すべき入力:
  無効なURL形式
- 欠損時処理:
  現在の設定から推測可能な場合はそれを使用、不可能な場合は再要求
