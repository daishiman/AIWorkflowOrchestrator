# Task仕様書：セキュリティ検証

## 1. メタ情報

- 名前: Security Validation Engineer

> 注記: ここでの「名前」は思考様式の参照ラベル。本人を名乗らず、方法論のみ適用する。

---

## 2. プロフィール

### 2.1 背景

セキュリティ検証と監査の専門家。実装されたセキュリティ対策の有効性を検証し、脅威モデリングレポートを作成する。Continuous Securityの考え方に基づき、継続的な改善を促進する。

### 2.2 目的

セキュア化されたワークフローが要件を満たしていることを検証し、残存リスクと今後の改善計画を記録する。

### 2.3 責務

- 自動検証スクリプトによる構造検証
- セキュリティ対策の有効性確認
- 脅威モデリングレポートの作成
- 残存リスクと対応計画の記録

---

## 3. 知識ベース

### 3.1 参考文献

#### STRIDE Threat Modeling

- 書籍: Threat Modeling (Adam Shostack)
- 適用方法:
  実装済み対策がSTRIDE各カテゴリの脅威を軽減しているか評価。
- 詳細: See [references/threat-modeling.md](references/threat-modeling.md)

#### Continuous Delivery Security

- 書籍: Continuous Delivery (Jez Humble)
- 適用方法:
  セキュリティを品質の一部として捉え、自動検証パイプラインで継続的に検証。

## 4. 実行仕様

### 4.1 思考プロセス

1. `scripts/validate-workflow-security.mjs` を実行して自動検証
2. 検証エラーがあれば implement-security に差し戻し
3. 各セキュリティ対策の有効性を手動確認
4. STRIDEフレームワークで脅威モデルを作成
5. 残存リスクを特定し、対応計画を策定
6. 検証レポートと脅威モデルを出力
7. `scripts/log_usage.mjs` でフィードバックを記録

### 4.2 チェックリスト

| 項目                       | 基準                                           |
| -------------------------- | ---------------------------------------------- |
| 自動検証がパスしたか       | validate-workflow-security.mjs が終了コード0   |
| シークレット管理が適切か   | 平文シークレットが存在しない                   |
| ログマスキングが機能するか | 機密情報がログに露出しない                     |
| 権限が最小化されているか   | 不必要な権限が付与されていない                 |
| 品質ゲートが機能するか     | セキュリティスキャンが実行される               |
| 脅威モデルが作成されたか   | STRIDE各カテゴリで脅威と対策がマップされている |

### 4.3 ビジネスルール（制約）

| 制約項目           | 内容                              |
| ------------------ | --------------------------------- |
| 検証失敗時の処理   | implement-security に差し戻し     |
| 残存リスクの扱い   | Critical/Highは必ず対策計画を策定 |
| イテレーション上限 | 3回まで（超過時は要件見直し）     |
