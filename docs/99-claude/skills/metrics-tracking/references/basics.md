## メトリクス追跡とは

開発チームのパフォーマンスを可視化し、データ駆動の意思決定と継続的改善を実現する手法。

### 主要な価値

| 価値             | 説明                               |
| ---------------- | ---------------------------------- |
| 予測可能性向上   | 過去データから見積もり精度を高める |
| ボトルネック発見 | プロセスの問題点を数値で特定       |
| 透明性確保       | チーム内外への進捗状況の可視化     |
| 改善測定         | 施策効果を定量的に評価             |

## 基本メトリクス

### ベロシティ（Velocity）

**定義**: スプリント期間中に完了したストーリーポイントの合計

```
ベロシティ = 完了ストーリーの合計ポイント
```

**使用法**:

- スプリント終了時に計測
- 3-5スプリントの平均値で計画

**注意**:

- チーム構成変更時は変動する
- 絶対値でチーム間比較しない
- 個人ベロシティは計測しない

### バーンダウンチャート（Burndown Chart）

**定義**: スプリント期間中の残作業量推移グラフ

**要素**:

- X軸: スプリント日数
- Y軸: 残りストーリーポイント
- 理想線: 一定ペースで完了した場合
- 実績線: 実際の完了状況

**良い兆候**: 実績線が理想線に沿っている
**悪い兆候**: 終了間際まで残作業が多い

### リードタイム（Lead Time）

**定義**: 課題がバックログに追加されてから完了するまでの時間

```
リードタイム = 完了日時 - 作成日時
```

**分析観点**:

- 長い課題の特徴分析
- ボトルネック（レビュー待ち、テスト待ち）特定

## メトリクス選択原則

### 1. ビジネスゴール紐付け

**良い例**:
| 目標 | メトリクス |
| -------------- | -------------- |
| 市場投入速度 | リードタイム |
| 品質向上 | バグ修正時間 |

**悪い例**:
| 目標 | メトリクス | 問題 |
| ------ | ------------ | -------------- |
| 不明確 | コード行数 | 意味のない指標 |

### 2. 計測可能性確認

**良い例**:

- Jiraに課題データ → リードタイム自動計算可能
- GitHubにPRデータ → レビュー時間計測可能

**悪い例**:

- 手動入力のみ → 入力負荷が高く継続困難

### 3. チーム文化配慮

**原則**:

- チーム全体のメトリクスのみ公開
- 個人のベロシティ・コミット数は計測しない
- 「改善のツール」であり「評価のツール」ではない

## 実践手順

### ステップ1: 最初のメトリクスを選ぶ

**推奨**: ベロシティとバーンダウンから開始

理由:

- アジャイル開発の標準メトリクス
- Jira/GitHub Projectsで簡単に可視化
- 計画精度向上に直結

### ステップ2: データを収集する

1. スプリントボードを作成
2. 各ストーリーにポイント付与
3. 完了ストーリーを「Done」に移動
4. スプリント終了時に集計

### ステップ3: 結果を振り返る

- 計画vs実績の差
- バーンダウンで見えたボトルネック
- 次スプリントで改善できること
