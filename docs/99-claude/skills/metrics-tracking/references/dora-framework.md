## DORA 4メトリクス概要

DevOps Research and Assessment (DORA) が科学的研究に基づいて定義した、ソフトウェアデリバリーパフォーマンスを測定する4つの主要メトリクス。

| メトリクス         | 英語名                       | 測定対象     |
| ------------------ | ---------------------------- | ------------ |
| デプロイ頻度       | Deployment Frequency         | スループット |
| 変更のリードタイム | Lead Time for Changes        | スループット |
| 変更失敗率         | Change Failure Rate          | 安定性       |
| サービス復旧時間   | Mean Time to Recovery (MTTR) | 安定性       |

---

## 各メトリクスの詳細

### デプロイ頻度（Deployment Frequency）

**定義**: 本番環境へのデプロイ回数

**計算式**:

```
デプロイ頻度 = デプロイ回数 / 計測期間
```

**パフォーマンス区分**:
| レベル | 頻度 |
| ------ | ---- |
| Elite | オンデマンド（1日複数回） |
| High | 週1回〜月1回 |
| Medium | 月1回〜6ヶ月に1回 |
| Low | 6ヶ月に1回未満 |

**データソース**: CI/CDパイプライン、デプロイメントログ

### 変更のリードタイム（Lead Time for Changes）

**定義**: コミットから本番稼働までの時間

**計算式**:

```
リードタイム = 本番デプロイ日時 - コミット日時
```

**パフォーマンス区分**:
| レベル | 時間 |
| ------ | ---- |
| Elite | 1時間未満 |
| High | 1日〜1週間 |
| Medium | 1週間〜1ヶ月 |
| Low | 1ヶ月以上 |

**データソース**: Git履歴、CI/CDパイプライン

### 変更失敗率（Change Failure Rate）

**定義**: デプロイ後に障害やロールバックが発生した割合

**計算式**:

```
変更失敗率 = 失敗デプロイ数 / 総デプロイ数 × 100
```

**パフォーマンス区分**:
| レベル | 割合 |
| ------ | ---- |
| Elite | 0-15% |
| High | 16-30% |
| Medium | 31-45% |
| Low | 46%以上 |

**データソース**: インシデント管理、デプロイメントログ

### サービス復旧時間（MTTR）

**定義**: 障害検知から復旧までの平均時間

**計算式**:

```
MTTR = Σ(復旧時刻 - 検知時刻) / 障害件数
```

**パフォーマンス区分**:
| レベル | 時間 |
| ------ | ---- |
| Elite | 1時間未満 |
| High | 1日未満 |
| Medium | 1日〜1週間 |
| Low | 1週間以上 |

**データソース**: インシデント管理システム、モニタリングツール

## 相関関係

### スループットと安定性

| 認識                       | 実態                       |
| -------------------------- | -------------------------- |
| トレードオフがある         | Elite組織は両方が高い      |
| 速度を上げると品質が下がる | 高頻度デプロイで品質も向上 |

**理由**:

- 小さな変更は検証しやすい
- 問題発生時の原因特定が容易
- フィードバックループが短い

### 組織文化との関連

| 文化要素     | メトリクスへの影響                |
| ------------ | --------------------------------- |
| 心理的安全性 | 問題の早期報告 → MTTR短縮         |
| 学習志向     | 失敗からの学び → 変更失敗率低下   |
| 権限委譲     | 迅速な意思決定 → リードタイム短縮 |

## 計測実装ガイド

### Phase 1: 基盤構築

1. データソースの特定
2. 自動収集の仕組み構築
3. 基本ダッシュボード作成

### Phase 2: 分析開始

1. 現状のベースライン測定
2. パフォーマンス区分の確認
3. ボトルネック特定

### Phase 3: 改善サイクル

1. 改善施策の立案
2. 施策実施
3. 効果測定
4. 次サイクルへ

## トレンド分析

### 移動平均

```javascript
// 4週移動平均
const movingAverage = (data, window = 4) => {
  return data.map((_, i) => {
    if (i < window - 1) return null;
    const slice = data.slice(i - window + 1, i + 1);
    return slice.reduce((a, b) => a + b) / window;
  });
};
```

### 傾向判定

| パターン | 判定基準      | アクション     |
| -------- | ------------- | -------------- |
| 改善傾向 | 3期連続で改善 | 施策継続       |
| 横ばい   | 変動が5%以内  | 新施策検討     |
| 悪化傾向 | 2期連続で悪化 | 原因調査・対策 |

## ベストプラクティス

### すべきこと

| 推奨                      | 理由                     |
| ------------------------- | ------------------------ |
| 4メトリクスをセットで見る | 単一指標のゲーミング防止 |
| チーム単位で計測          | 心理的安全性の確保       |
| 長期トレンドで判断        | 短期変動に惑わされない   |
| 改善にフォーカス          | 評価ではなく学習         |

### 避けるべきこと

| 禁止             | 問題点             |
| ---------------- | ------------------ |
| 個人への紐付け   | 心理的安全性の破壊 |
| チーム間の比較   | 不健全な競争       |
| 絶対値のみで判断 | コンテキスト無視   |
| 短期的な目標設定 | 本質的改善の阻害   |
