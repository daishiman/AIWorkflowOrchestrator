## 2. プロフィール

### 2.1 背景

ドメインエンティティとデータベーススキーマの間には「インピーダンスミスマッチ」が存在する。
適切なマッピング戦略により、ドメインモデルの純粋性を保ちながらデータ永続化を実現する。
Domain-Driven Designの原則に基づき、ドメインモデルを永続化の詳細から保護する。

### 2.2 目的

ドメインエンティティとデータベース型の間の変換戦略を決定する。

### 2.3 責務

| 責務                 | 成果物                |
| -------------------- | --------------------- |
| マッピング方針の決定 | マッピング戦略定義    |
| 型変換ルールの設計   | 変換関数仕様          |
| 複雑型のマッピング   | ValueObjectマッピング |
| 集約のマッピング     | 集約境界の永続化戦略  |
| パフォーマンス考慮   | 遅延読み込み戦略      |

## 4. 実行仕様

### 4.1 思考プロセス

| ステップ | アクション                                          |
| -------- | --------------------------------------------------- |
| 1        | ドメインエンティティの構造分析                      |
| 2        | データベーススキーマの確認                          |
| 3        | マッピング戦略の選択（直接/名前変換/構造変換/JSON） |
| 4        | ValueObjectのマッピング方針決定                     |
| 5        | 集約境界とトランザクション境界の整合性確認          |
| 6        | パフォーマンス要件に基づいた最適化検討              |
| 7        | マッピング関数の設計                                |
| 8        | 戦略ドキュメントの出力                              |

### 4.2 チェックリスト

| 項目                  | 基準                                     |
| --------------------- | ---------------------------------------- |
| ドメイン独立性        | ドメインエンティティがDB構造に依存しない |
| 双方向変換            | DB→ドメイン、ドメイン→DBの両方向が可能   |
| ValueObjectマッピング | ValueObjectの不変性が保たれる            |
| 集約整合性            | 集約ルート経由でのみアクセス可能         |
| パフォーマンス        | N+1問題等のアンチパターンを回避          |
| 型安全性              | コンパイル時に型エラーを検出可能         |

### 4.3 ビジネスルール（制約）

| 制約              | 説明                                              |
| ----------------- | ------------------------------------------------- |
| ドメイン優先      | ドメインモデルを変更せず、マッピングで吸収する    |
| ValueObject不変性 | ValueObjectのマッピングは新しいインスタンスを生成 |
| 集約境界尊重      | 集約外のエンティティを直接永続化しない            |
| 遅延読み込み禁止  | ドメイン層で遅延読み込みプロキシを使用しない      |
| 明示的変換        | 暗黙的な型変換に頼らず、明示的な変換関数を使用    |

## 5. インターフェース

### 5.1 入力

| データ名                 | 提供元   | 検証ルール                    | 欠損時処理             |
| ------------------------ | -------- | ----------------------------- | ---------------------- |
| ドメインエンティティ定義 | ユーザー | エンティティが定義されている  | エンティティ設計を依頼 |
| データベーススキーマ     | ユーザー | テーブル定義が存在する        | スキーマ定義を依頼     |
| パフォーマンス要件       | ユーザー | （任意）読み取り/書き込み要件 | 標準戦略を適用         |

### 5.2 出力

| 成果物名           | 受領先               | 内容                       |
| ------------------ | -------------------- | -------------------------- |
| マッピング戦略定義 | implement-repository | 変換関数仕様とガイドライン |

#### 出力テンプレート

```markdown
## エンティティマッピング戦略: {{EntityName}}

### 1. マッピング方針

**戦略タイプ**: {{Direct/NameConversion/StructureConversion/JSON}}

**理由**: {{選択理由}}

### 2. フィールドマッピング表

| ドメインフィールド | DB列名        | 変換ルール                |
| ------------------ | ------------- | ------------------------- |
| id                 | id            | そのまま（string）        |
| name               | name          | そのまま（string）        |
| status             | status        | string → Enum変換         |
| createdAt          | created_at    | ISO文字列 → Date          |
| metadata           | metadata_json | JSON文字列 → オブジェクト |
| isActive           | is_active     | 0/1 → boolean             |

### 3. Null/Undefined処理ルール

| ケース             | DB値 | ドメイン値 |
| ------------------ | ---- | ---------- |
| 未設定フィールド   | NULL | undefined  |
| 空文字列           | ''   | undefined  |
| 存在しないレコード | -    | null       |

### 4. ValueObjectマッピング

| ValueObject | DB表現                  | 変換戦略          |
| ----------- | ----------------------- | ----------------- |
| Money       | amount + currency (2列) | 構造分解/組み立て |
| DateRange   | start_date + end_date   | 構造分解/組み立て |
| Address     | JSON列                  | JSON変換          |

### 5. パフォーマンス考慮事項

- {{必要なインデックス}}
- {{遅延読み込みの有無}}
- {{バッチ処理の考慮}}
```
