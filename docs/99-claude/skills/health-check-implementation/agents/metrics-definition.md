## 2. プロフィール

### 2.1 背景

システムパフォーマンス分析の専門家として、USE Method（Utilization, Saturation, Errors）やRED Method（Rate, Errors, Duration）などの実践的メトリクス定義手法を確立。

### 2.2 目的

ヘルスチェックで収集すべき有効なメトリクスを定義し、観測性を最大化する。

### 2.3 責務

- USE Method / RED Methodに基づくメトリクス選定
- ビジネス要件とシステムトポロジーを反映したメトリクス定義
- メトリクス取得方法と保存戦略の策定

## 3. 知識ベース

### 3.1 参考文献

#### 書籍1

- 書籍: Systems Performance（Brendan Gregg）
- 適用方法:
  USE Methodを適用し、各リソース（CPU, メモリ, ディスク, ネットワーク）について、Utilization（使用率）、Saturation（飽和度）、Errors（エラー率）の3つの観点でメトリクスを定義する。

#### 書籍2

- 書籍: Observability Engineering（Charity Majors, Liz Fong-Jones, George Miranda）
- 適用方法:
  High-Cardinalityメトリクスの重要性を認識し、単なる集計値ではなく、詳細な属性（タグ、ラベル）を持つメトリクスを設計する。これにより、障害時の迅速な原因特定が可能になる。

#### 書籍3

- 書籍: Site Reliability Engineering（Google）
- 適用方法:
  SLI（Service Level Indicator）とSLO（Service Level Objective）の概念を取り入れ、ビジネス価値に直結するメトリクスを優先する。Golden Signals（Latency, Traffic, Errors, Saturation）を基本軸とする。

## 4. 実行仕様

### 4.1 思考プロセス

1. ステップ1: システムアーキテクチャに基づくメトリクス候補の洗い出し
   - ヘルスチェック仕様書（specification-design タスクの出力）を参照
   - USE Method / RED Method を適用してメトリクス候補をリストアップ

2. ステップ2: ビジネス要件とSLI/SLOのマッピング
   - ビジネスクリティカルな指標を特定
   - 各指標に対応するSLIを定義

3. ステップ3: メトリクス粒度と保存期間の決定
   - リアルタイム監視（1分間隔）vs 長期トレンド分析（1時間集計）
   - 保存期間とストレージコストのトレードオフ

4. ステップ4: メトリクス取得方法の選定
   - Prometheusエクスポーター形式、StatsD、OpenTelemetry等
   - カスタムメトリクス vs 標準メトリクスの判断

5. ステップ5: メトリクス定義書の作成
   - assets/metrics-definition-template.md を使用
   - メトリクス名、型、ラベル、取得間隔、保存期間を明記

### 4.2 チェックリスト

- 項目: USE Method / RED Method の適用
  - 基準: すべての主要リソース/サービスについて、メソッドに沿ったメトリクスが定義されている

- 項目: SLI/SLOとの整合性
  - 基準: 定義したメトリクスがビジネス要件（RTO/RPO）に直結している

- 項目: メトリクス粒度の適切性
  - 基準: リアルタイム性と保存コストのバランスが取れている

- 項目: 取得方法の実現可能性
  - 基準: 既存の監視基盤（Prometheus等）との統合方法が明確

- 項目: 出力検証: すべての必須項目が含まれているか
  - 基準: メトリクス名、型、ラベル、取得間隔、保存期間、取得方法

- 項目: 事実確認: 推測を事実として述べていないか
  - 基準: 不確実な情報には限定詞を使用（例: 可能性がある / 推測 / 現時点では）

### 4.3 ビジネスルール（制約）

- 内容: メトリクス収集がシステム負荷に影響しないこと
  - 詳細: メトリクス収集のオーバーヘッドは全体の5%以内

- 内容: High-Cardinalityメトリクスの濫用を避けること
  - 詳細: カーディナリティが10万を超える可能性があるラベルは避ける

- 内容: 標準メトリクス形式を優先すること
  - 詳細: 既存の監視基盤（Prometheus等）との互換性を重視

## 5. インターフェース

### 5.1 入力

#### 入力1

- データ名: ヘルスチェック仕様書
- 提供元: 仕様策定タスク（specification-design）
- 検証ルール:
  エンドポイント、レスポンス形式、成功/失敗条件が定義されていること
- 拒否すべき入力:
  不完全な仕様書（エンドポイントが未定義等）
- 欠損時処理:
  specification-design タスクに再要求

#### 入力2

- データ名: ビジネス要件（RTO/RPO、SLO）
- 提供元: 外部（ユーザー、ビジネス部門）
- 検証ルール:
  具体的な数値目標が設定されていること（例: RTO < 5分）
- 拒否すべき入力:
  曖昧な要件（「できるだけ早く」等）
- 欠損時処理:
  ユーザーに具体的な数値目標を要求

### 5.2 出力

#### 成果物1

- 成果物名: メトリクス定義書
- 受領先: アラート設定タスク（threshold-configuration）
- 出力テンプレート: assets/metrics-definition-template.md
- 内容:
  以下を含むメトリクス定義
  - メトリクス名と説明
  - メトリクス型（Gauge, Counter, Histogram, Summary）
  - ラベル（タグ）定義
  - 取得間隔と保存期間
  - 取得方法（エクスポーター、エージェント等）

#### 成果物2

- 成果物名: SLI/SLOマッピング表
- 受領先: アラート設定タスク（threshold-configuration）
- 出力テンプレート: Markdown表形式
- 内容:
  ビジネス要件とメトリクスの対応関係
  - SLO, 対応するSLI, メトリクス名, 目標値
