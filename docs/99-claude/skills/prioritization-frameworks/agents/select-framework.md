# Task仕様書：フレームワーク選択

## 1. Trigger

```
You are selecting the optimal prioritization framework for a project.
Consider: project scope, stakeholders constraints, evaluation criteria, and decision timeline.
```

## 2. Context

### 目的

プロジェクトの目的、制約条件、ステークホルダーのニーズを分析し、
最適な優先順位付けフレームワーク（MoSCoW、RICE、Kano Modelなど）を選択する。

### 背景

優先順位付けフレームワークは、プロジェクトの性質や目的によって適切なものが異なる。
MoSCoW法は要件分類に、RICE Scoringは定量的評価に、Kano Modelは顧客満足度分析に適している。

### 対象ユーザー

- プロダクトマネージャー
- プロジェクトリーダー
- ステークホルダー

### 前提条件

- プロジェクトの目的と成果物が定義されている
- ステークホルダーが明確である
- 制約条件（リソース、予算、期限）が把握されている

### 参照リソース

- `../references/basics.md`: 各フレームワークの基本概念
- `../references/patterns.md`: フレームワーク選択パターン
- 『Inspired』（Marty Cagan）: プロダクト価値の最大化

### 制約・注意事項

- 複数フレームワークの併用も検討する
- ステークホルダーの合意を優先する
- 過度に複雑なフレームワークを避ける

## 3. Instructions

### Step 1: プロジェクト状況の把握

**目的**: プロジェクトの目的、制約、ステークホルダーを明確化

**実行内容**:

1. プロジェクトの目的と期待成果を確認
2. 優先順位付けの対象（フィーチャー、バグ修正、技術債など）を特定
3. ステークホルダーのリストと関心事を整理
4. 制約条件（リソース、予算、期限）を把握

**入力**:

- プロジェクト要件書
- ステークホルダーリスト
- リソース・予算情報

**出力**:

- プロジェクト状況サマリー（Markdown形式）

**判断基準**:

- 目的が明確に定義されているか
- 制約条件が定量的に把握されているか

### Step 2: フレームワーク候補の選定

**目的**: プロジェクト特性に応じたフレームワーク候補を選定

**実行内容**:

1. `../references/basics.md` で各フレームワークの特性を確認
2. プロジェクト特性に応じて候補を絞り込む
   - 定性的分類が必要 → MoSCoW法
   - 定量的評価が必要 → RICE Scoring
   - 顧客満足度分析が必要 → Kano Model
   - 迅速な判断が必要 → Value vs Effort
3. 複数フレームワークの併用可能性を検討

**入力**:

- Step 1のプロジェクト状況サマリー
- `../references/basics.md`

**出力**:

- フレームワーク候補リスト（各候補の適用理由を含む）

**判断基準**:

- 候補が2〜3個に絞られているか
- 各候補の選定理由が明確か

### Step 3: 評価基準の定義

**目的**: フレームワーク選択の評価基準を定義

**実行内容**:

1. 以下の観点で評価基準を定義
   - 実装容易性（導入に必要な工数とスキル）
   - ステークホルダー理解度（関係者が理解しやすいか）
   - 評価精度（意思決定の質）
   - 柔軟性（変更への対応力）
2. 各基準の重み付けを設定
3. ステークホルダーと評価基準を合意

**入力**:

- Step 2のフレームワーク候補リスト
- ステークホルダーの要望

**出力**:

- 評価基準表（基準名、重み、説明を含む）

**判断基準**:

- 評価基準が3〜5個に絞られているか
- 重み付けの合計が100%になっているか

### Step 4: フレームワークの選択

**目的**: 評価基準に基づいて最適なフレームワークを選択

**実行内容**:

1. 各候補を評価基準でスコアリング
2. 総合スコアを算出し、最適なフレームワークを特定
3. 選択理由を明文化
4. ステークホルダーに選択結果を共有し、合意を得る

**入力**:

- Step 2のフレームワーク候補リスト
- Step 3の評価基準表

**出力**:

- フレームワーク選択結果（選択理由、評価スコア、合意記録を含む）

**判断基準**:

- 選択理由が明確に記述されているか
- ステークホルダーの合意が得られているか

### Step 5: 適用計画の策定

**目的**: 選択したフレームワークの適用計画を策定

**実行内容**:

1. フレームワーク適用の具体的手順を定義
2. 必要なリソースとツールを特定
3. タイムラインとマイルストーンを設定
4. リスクと軽減策を識別

**入力**:

- Step 4のフレームワーク選択結果
- `../references/patterns.md`（実装パターン）

**出力**:

- 適用計画書（手順、リソース、タイムライン、リスクを含む）

**判断基準**:

- 具体的な実行手順が定義されているか
- リスク軽減策が検討されているか

## 4. Artifacts

### 成果物1: フレームワーク選択レポート

**形式**: Markdown

**保存先**: プロジェクトドキュメントフォルダ

**テンプレート**: なし（自由形式）

**必須要素**:

- プロジェクト状況サマリー
- フレームワーク候補と評価
- 選択結果と理由
- ステークホルダー合意記録

**品質基準**:

- 選択理由が客観的データに基づいているか
- ステークホルダーの合意が文書化されているか

### 成果物2: 適用計画書

**形式**: Markdown

**保存先**: プロジェクトドキュメントフォルダ

**テンプレート**: なし（自由形式）

**必須要素**:

- 適用手順
- 必要なリソースとツール
- タイムラインとマイルストーン
- リスクと軽減策

**品質基準**:

- 実行可能な具体的手順が定義されているか
- リスクが識別され、軽減策が提示されているか

## 5. Validation

### 検証項目

#### 完全性の検証

- [ ] すべてのStepが完了しているか
- [ ] 必須の成果物がすべて作成されているか
- [ ] プロジェクト状況が漏れなく把握されているか

#### 正確性の検証

- [ ] フレームワーク選択理由が論理的か
- [ ] 評価基準が適切に設定されているか
- [ ] ステークホルダーの要望が反映されているか

#### 合意形成の検証

- [ ] ステークホルダーの合意が得られているか
- [ ] 選択結果が関係者全員に共有されているか
- [ ] 異論や懸念事項が記録されているか

#### 実行可能性の検証

- [ ] 適用計画が現実的か
- [ ] 必要なリソースが確保できるか
- [ ] タイムラインが妥当か

### エラーハンドリング

#### エラー1: プロジェクト目的が不明確

**検出条件**: プロジェクトの目的や成果物が定義されていない

**対処方法**: ステークホルダーに再確認を求め、目的を明確化

#### エラー2: 制約条件が不足

**検出条件**: リソース、予算、期限のいずれかが未定義

**対処方法**: デフォルト値を仮定し、ステークホルダーに確認を求める

#### エラー3: ステークホルダー合意が得られない

**検出条件**: フレームワーク選択に異論がある

**対処方法**: 評価基準を再検討し、代替案を提示

- [ ] フレームワーク選択レポートが作成されているか
- [ ] 適用計画書が作成されているか
- [ ] 選択理由が明確に記述されているか
- [ ] ステークホルダーの合意が文書化されているか
- [ ] 適用手順が具体的に定義されているか
- [ ] リスクと軽減策が識別されているか
