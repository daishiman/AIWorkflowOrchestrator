## フェーズテンプレート（各フェーズ共通）

```markdown
## ワークフロー

### Phase {{phase_number}}: {{phase_name}}

#### 目的

{{このフェーズで何を達成するか}}

#### 背景

{{なぜこのフェーズが必要か}}

#### ゴール

{{このフェーズの具体的な完了状態}}

#### 読み込むスキル

- `.claude/skills/{{skill-name}}/SKILL.md`
  ...
- `.claude/skills/{{skill-name}}/SKILL.md`

**スキル参照の原則**:

1. まず SKILL.md のみを読み込む
2. SKILL.md 内の description で必要なリソース（resources/, scripts/, templates/ など）を確認
3. 必要に応じて該当するリソースのみを追加で読み込む

#### 完了条件

- [ ] {{条件1}}
      ...
- [ ] {{条件N}}
```

## ワークフロー設計規則

| 規則                   | 説明                                                               |
| ---------------------- | ------------------------------------------------------------------ |
| 目的・背景・ゴール必須 | 各フェーズで何を達成するか明確に記述                               |
| スキル参照は段階的     | SKILL.md → 必要なリソースの順で Progressive Disclosure             |
| 成果物を明示           | 各フェーズで生成されるファイルパスを具体的に記述                   |
| 完了条件はチェック可能 | 自動または手動で検証可能な条件を設定                               |
| 最終フェーズは記録     | 最終Phaseに「記録と評価」を含め、使用スキルの`log_usage.mjs`を実行 |

## 必須要素

| 要素           | 必須 | 説明                                   |
| -------------- | ---- | -------------------------------------- |
| 目的           | 必須 | このフェーズで何を達成するか           |
| 背景           | 必須 | なぜこのフェーズが必要か               |
| ゴール         | 必須 | このフェーズの具体的な完了状態         |
| 読み込むスキル | 必須 | Phase別に読み込むスキルの相対パス      |
| 完了条件       | 必須 | 検証可能なチェックリスト形式の完了条件 |

## 目的の記述ガイドライン

| ガイドライン       | 説明                                 |
| ------------------ | ------------------------------------ |
| 1文で簡潔に        | 「〜を達成する」「〜を決定する」形式 |
| 動詞で開始         | 「分析する」「設計する」「生成する」 |
| 具体的な対象を明記 | 何を対象にするかを明確に             |

### 例

- ✅ 良い例: 「ユーザー要件を分析し、エージェント設計方針を決定する」
- ✅ 良い例: 「YAML Frontmatterとワークフローを設計する」
- ❌ 悪い例: 「準備をする」（抽象的すぎる）
- ❌ 悪い例: 「色々な作業を行う」（具体性がない）

## 背景の記述ガイドライン

| ガイドライン       | 説明                                   |
| ------------------ | -------------------------------------- |
| 理由を説明         | なぜこのフェーズが必要かを明確に       |
| リスクを明記       | このフェーズを飛ばした場合の問題を記述 |
| 前フェーズとの関係 | 前フェーズの成果を受けてこのフェーズへ |

### 例

- ✅ 良い例: 「曖昧な要件のままエージェント設計を開始すると、単一責任原則が守られず手戻りが発生します。要件を明確化し、既存エージェントとの重複を避けることが重要です。」
- ✅ 良い例: 「エージェントの構造が明確でないと、実装時に一貫性が失われます。YAML Frontmatter、ワークフロー、ツール権限を体系的に設計することで、保守性の高いエージェントを実現します。」
- ❌ 悪い例: 「必要だから」（理由が不明確）

## ゴールの記述ガイドライン

| ガイドライン   | 説明                                   |
| -------------- | -------------------------------------- |
| 完了状態を明記 | 「〜された状態」「〜が定義された状態」 |
| 検証可能       | 完了を確認できる状態を記述             |
| 具体的な成果物 | 何が生成/決定されるかを明記            |

### 例

- ✅ 良い例: 「エージェントの目的・専門分野が明確化され、設計方針が決定された状態」
- ✅ 良い例: 「エージェントファイルの完全な構造が定義された状態」
- ✅ 良い例: 「依存関係が明確化され、協調プロトコルが定義された状態」
- ❌ 悪い例: 「だいたい完了」（曖昧）
- ❌ 悪い例: 「良い感じに仕上がった」（検証不可能）

## 読み込むスキルの記述ガイドライン

| ガイドライン        | 説明                                    |
| ------------------- | --------------------------------------- |
| 相対パス必須        | `.claude/skills/{{name}}/SKILL.md` 形式 |
| Phase別にマッピング | 各Phaseで必要なスキルのみを列挙         |
| 原則を明記          | Progressive Disclosureの原則を毎回記載  |

### スキル参照の原則（必須記載事項）

```markdown
**スキル参照の原則**:

1. まず SKILL.md のみを読み込む
2. SKILL.md 内の description で必要なリソース（resources/, scripts/, templates/ など）を確認
3. 必要に応じて該当するリソースのみを追加で読み込む
```

## 完了条件の記述ガイドライン

| ガイドライン       | 説明                           |
| ------------------ | ------------------------------ |
| チェックリスト形式 | `- [ ]` 形式で記述             |
| 検証可能           | 自動または手動で確認できる条件 |
| 3-7個が目安        | 少なすぎず多すぎない適切な粒度 |
| 具体的             | 抽象的な表現を避ける           |

### 例

- ✅ 良い例: `- [ ] エージェントの目的が明確`
- ✅ 良い例: `- [ ] YAML Frontmatter が完全に設計されている（name, description, tools, model）`
- ✅ 良い例: `- [ ] 行数が450-550行範囲内`
- ❌ 悪い例: `- [ ] ちゃんと完了している`（検証不可能）
- ❌ 悪い例: `- [ ] 良い`（抽象的）

## 最終Phase「記録と評価」の標準形式

すべてのエージェントの最終Phaseは以下の形式で記録フェーズを含める必要があります：

```markdown
### Phase N: 記録と評価

#### 目的

スキル使用実績を記録し、継続的改善に貢献する

#### 背景

スキルの成長には使用データの蓄積が不可欠です。各スキルの実行記録を保存し、メトリクスを更新することで、スキルの品質向上に貢献します。

#### ゴール

実行記録が保存され、メトリクスが更新された状態

#### 読み込むスキル

なし

#### 完了条件

- [ ] 使用したスキルの `log_usage.mjs` が実行されている
- [ ] LOGS.md に新規エントリが追記されている
- [ ] EVALS.json のメトリクスが更新されている
```

## Phase数の推奨

| Phase数 | 推奨度 | 用途                               |
| ------- | ------ | ---------------------------------- |
| 3-5個   | 推奨   | 標準的なエージェント               |
| 5-7個   | 許容   | 複雑なエージェント                 |
| 2個以下 | 非推奨 | 分解が不十分                       |
| 8個以上 | 非推奨 | 分解しすぎ、エージェント分割を検討 |

## 完全な例: Phase 1 (要件理解と分析)

```markdown
### Phase 1: 要件理解と分析

#### 目的

ユーザー要件を分析し、エージェント設計方針を決定する

#### 背景

曖昧な要件のままエージェント設計を開始すると、単一責任原則が守られず手戻りが発生します。要件を明確化し、既存エージェントとの重複を避けることが重要です。

#### ゴール

エージェントの目的・専門分野が明確化され、設計方針が決定された状態

#### 読み込むスキル

- `.claude/skills/agent-persona-design/SKILL.md`

**スキル参照の原則**:

1. まず SKILL.md のみを読み込む
2. SKILL.md 内の description で必要なリソース（resources/, scripts/, templates/）を確認
3. 必要に応じて該当するリソースのみを追加で読み込む

#### 完了条件

- [ ] エージェントの目的が明確
- [ ] 設計方針が決定（専門家モデル or 役割ベース）
- [ ] 実在する専門家の候補が特定されている（専門家モデルの場合）
- [ ] 既存エージェントとの重複がない
```

## 検証チェックリスト

- [ ] 全Phaseに「目的」「背景」「ゴール」「読み込むスキル」「完了条件」が含まれている
- [ ] 各Phaseの目的が1文で簡潔に記述されている
- [ ] 各Phaseの背景が「なぜ必要か」を説明している
- [ ] 各Phaseのゴールが検証可能な完了状態を示している
- [ ] 読み込むスキルが相対パス形式で記述されている
- [ ] 「スキル参照の原則」が各Phaseに記載されている
- [ ] 完了条件がチェックリスト形式で記述されている
- [ ] 完了条件が検証可能である
- [ ] 最終Phaseに「記録と評価」が含まれている
- [ ] Phase数が3-7個の範囲内である
