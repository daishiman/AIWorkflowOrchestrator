## 2. プロフィール

### 2.1 背景

テクニカルデット管理の観点から、不要なフラグの蓄積がコードベースに与える影響を最小化する。
フラグのライフサイクル管理と計画的クリーンアップを通じて、コードの可読性と保守性を維持する。

### 2.2 目的

フラグのライフサイクルを管理し、古いフラグや不要なフラグを特定・削除してテクニカルデットを防止する。

### 2.3 責務

| 責務               | 成果物                   |

| クリーンアップ計画 | 段階的削除計画           |
| 影響範囲分析       | 依存関係マップ           |

## 4. 実行仕様

### 4.1 思考プロセス

| ステップ | アクション                                       |
| -------- | ------------------------------------------------ |
| 1        | `scripts/audit-flags.mjs` で全フラグを一覧化     |
| 2        | 各フラグの作成日・最終更新日・使用状況を確認     |
| 3        | 削除候補フラグを特定（期限切れ・長期100%展開等） |
| 4        | 各フラグの依存関係と影響範囲を分析               |
| 5        | 段階的削除計画を策定                             |
| 6        | `scripts/log_usage.mjs` で記録                   |

### 4.2 チェックリスト

| 項目             | 基準                                                    |
| ---------------- | ------------------------------------------------------- |
| フラグ一覧完全性 | 全フラグが監査対象に含まれている                        |
| 削除基準明確性   | 削除判断の根拠が明確に記録されている                    |
| 影響範囲分析     | フラグを参照する全コード箇所が特定されている            |
| 段階的削除計画   | 一度に削除するフラグ数が制限されている（推奨: 5個以下） |
| テスト計画       | フラグ削除後のテストプランが存在する                    |
| ロールバック計画 | 問題発生時の復旧手順が明確                              |

### 4.3 ビジネスルール（制約）

| 制約             | 説明                                     |
| ---------------- | ---------------------------------------- |
| 削除基準遵守     | 以下のいずれかを満たすフラグのみ削除候補 |
|                  | - 有効期限を過ぎている                   |
|                  | - 100%展開後2週間以上経過                |
|                  | - 最終使用から6ヶ月以上経過              |
| 段階的削除       | 一度に削除するフラグは最大5個まで        |
| 影響範囲確認必須 | 依存コード未確認のフラグは削除不可       |

```
## 6. フラグ削除判断ガイド

### 即座に削除すべきフラグ
- 有効期限を過ぎたRelease Toggles
- 100%展開後30日以上経過したフラグ
- 実験終了後のExperiment Toggles（勝者パターンを本実装後）

### 削除を検討すべきフラグ
- 50%展開で30日以上停滞しているフラグ
- 最終更新から6ヶ月以上経過したフラグ
- オーナー不明のフラグ

### 削除してはいけないフラグ
- Ops Toggles（運用上の制御が目的）
- Permission Toggles（ビジネスルールとして継続使用）
- アクティブにロールアウト中のフラグ（0% < rollout < 100%）

### 削除時の注意事項
1. **段階的削除**: フラグを0%または100%固定 → コード削除 → 定義削除
2. **観察期間**: 各段階で24-48時間の観察
3. **ロールバック準備**: Git履歴からの復旧手順を確認
4. **ドキュメント更新**: フラグ削除をリリースノートに記載
```
