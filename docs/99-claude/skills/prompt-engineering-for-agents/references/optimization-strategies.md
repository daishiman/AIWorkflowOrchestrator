# プロンプト最適化戦略

## 概要

エージェント向けプロンプトを最適化するための実践的な戦略集です。
明確性、簡潔性、構造化、効率性の4つの観点から体系的に改善します。

## 最適化の4つの観点

### 1. 明確性（Clarity）

曖昧さを排除し、指示を明確にする。

### 2. 簡潔性（Conciseness）

冗長性を削減し、本質のみを残す。

### 3. 構造化（Structure）

論理的な構成で情報を整理する。

### 4. 効率性（Efficiency）

Token消費を最適化し、パフォーマンスを向上させる。

## 戦略1: 曖昧表現の排除

### 目的

指示の明確性を向上させ、一貫した動作を実現する。

### 曖昧な表現リスト

| 曖昧な表現   | 問題点             | 改善例                                 |
| ------------ | ------------------ | -------------------------------------- |
| 適宜         | 判断基準が不明確   | 「条件Xの場合はYを、条件Zの場合はWを」 |
| 必要に応じて | いつ必要かが不明   | 「テストカバレッジ<80%の場合は追加」   |
| など         | 範囲が不明確       | 具体的な項目をすべて列挙               |
| いくつかの   | 数が不明確         | 「3-5個の」のように具体的な数値        |
| できるだけ   | 基準が不明確       | 「80%以上」のように具体的な基準値      |
| 可能な限り   | 優先度が不明確     | 「必須」「推奨」「オプション」を明示   |
| 適切に       | 何が適切かが不明確 | 具体的な基準を記述                     |
| よしなに     | 完全に曖昧         | 具体的な手順を記述                     |

### Before/After例

❌ **Before**:

```markdown
必要に応じてテストを追加し、適宜リファクタリングしてください。
```

✅ **After**:

```markdown
以下の条件でテストを追加してください:

- 新規関数: 単体テスト必須
- 既存関数変更: 既存テスト更新必須
- カバレッジ<80%: 追加テスト必須

リファクタリング基準:

- メソッド>20行: Extract Method適用
- 重複コード>3箇所: Extract Function適用
- 循環的複雑度>10: 分割検討
```

## 戦略2: 具体的な基準値の設定

### 目的

測定可能な基準により、一貫した判断を実現する。

### 数値基準の例

**コード品質**:

- テストカバレッジ: 80%以上
- 循環的複雑度: 10以下
- メソッド行数: 20行以下
- クラス行数: 200行以下

**パフォーマンス**:

- 応答時間: 3秒以内
- メモリ使用量: 100MB以下
- API呼び出し: 10回/秒以下

**品質管理**:

- コードレビュー: 承認2名以上
- テスト実行: 100%合格必須
- Lint警告: 0件

### 実装例

❌ **Before**:

```markdown
できるだけ高品質なコードを書いてください。
```

✅ **After**:

```markdown
以下の品質基準を満たしてください:

- テストカバレッジ: 80%以上
- 循環的複雑度: 10以下
- ESLint警告: 0件
- TypeScript型エラー: 0件
- コードレビュー承認: 2名以上
```

## 戦略3: 構造化とセクション分割

### 目的

情報を論理的に整理し、理解しやすくする。

### 推奨7セクション構造

```markdown
## 1. 役割定義

エージェントの役割と専門分野

## 2. 専門分野

具体的な専門領域のリスト

## 3. ワークフロー

Phase 1-Nの詳細手順

## 4. スキル管理

依存スキルと参照リソース

## 5. ベストプラクティス

すべきこと・避けるべきこと

## 6. 詳細リファレンス

外部リソースへの参照

## 7. 変更履歴

バージョン管理
```

### Before/After例

❌ **Before**:

```markdown
リファクタリングエージェントはコードの匂いを検出してリファクタリングします。
Long MethodやDuplicate Codeを見つけたらExtract MethodやExtract Functionを
使います。テストは必ず実行します。テストがない場合はエラーにします。
```

✅ **After**:

```markdown
## 役割

あなたは **リファクタリング専門家** です。
コードの匂いを体系的に検出し、適切なパターンでリファクタリングします。

## ワークフロー

### Phase 1: Code Smells検出

1. Long Methodを検出（20行以上）
2. Duplicate Codeを特定（3箇所以上）

### Phase 2: リファクタリング実施

1. Extract Methodパターンを適用
2. テストを実行して検証

## ベストプラクティス

✅ **すべきこと**:

- 各ステップでテスト実行
- 小さな変更に分割

❌ **避けるべきこと**:

- テストなしリファクタリング
- 大規模一括変更
```

## 戦略4: Token最適化

### 目的

Token消費を削減し、パフォーマンスを向上させる。

### 最適化テクニック

#### 1. プログレッシブディスクロージャー

**基本原則**:

```
SKILL.md（軽量）
  ↓ 必要時
references/basics.md（基本）
  ↓ 必要時
references/advanced.md（詳細）
```

**実装**:

```markdown
<!-- SKILL.md -->

詳細は `references/patterns.md` を参照

<!-- references/patterns.md -->

さらなる詳細は `references/advanced-patterns.md` を参照
```

#### 2. 外部リソース化

**5個以上の例示は外部化**:

```markdown
<!-- SKILL.md -->

## 例

基本的な2つの例をここに記載。

詳細な例は `references/examples.md` を参照。

<!-- references/examples.md -->

10個の詳細な例を記載。
```

#### 3. 重複の削除

❌ **Before**:

```markdown
## ワークフロー

### Phase 1

エージェントの役割と専門分野を考慮して実施

### Phase 2

エージェントの役割と専門分野を考慮して実施

### Phase 3

エージェントの役割と専門分野を考慮して実施
```

✅ **After**:

```markdown
## 共通原則

すべてのPhaseで役割と専門分野を考慮。

## ワークフロー

### Phase 1: 検出

### Phase 2: 計画

### Phase 3: 実施
```

#### 4. 圧縮技術

**箇条書きの活用**:

```markdown
❌ 長い文章で説明
「エージェントはコードの匂いを検出し、それに基づいて適切な
リファクタリングパターンを選択し、テストを実行して検証します」

✅ 箇条書き

1. Code Smells検出
2. パターン選択
3. テスト検証
```

**テーブルの活用**:

```markdown
❌ 繰り返し

- Long Method: 20行以上のメソッド
- Large Class: 200行以上のクラス
- Long Parameter List: 5個以上のパラメータ

✅ テーブル
| Code Smell | 基準 |
| -------------------- | --------- |
| Long Method | 20行以上 |
| Large Class | 200行以上 |
| Long Parameter List | 5個以上 |
```

## 戦略5: 一貫性の確保

### 目的

用語、形式、構造を統一し、予測可能性を向上させる。

### 用語の統一

**プロジェクト全体で統一**:

| 概念     | 統一用語 | 避ける用語         |
| -------- | -------- | ------------------ |
| 作業単位 | タスク   | ジョブ、作業       |
| 段階     | Phase    | ステージ、フェーズ |
| 成果物   | 成果物   | アウトプット       |
| 手順     | 手順     | ステップ、工程     |

### 形式の統一

**ベストプラクティスの形式**:

```markdown
✅ **すべきこと**:

- 項目1
- 項目2

❌ **避けるべきこと**:

- 項目1
- 項目2
```

**ワークフローの形式**:

```markdown
### Phase N: {{Phase名}}

**目的**: {{Phase目的}}

**手順**:

1. {{ステップ1}}
2. {{ステップ2}}

**成果物**:

- {{成果物1}}

**判断ポイント**:

- {{判断基準1}}
```

## 戦略6: 検証とテスト

### 目的

プロンプトの効果を測定し、継続的に改善する。

### 品質指標

**4つの評価軸**:

1. **明確性** (1-5点)
   - 指示の明瞭さ
   - 曖昧表現の有無
   - 判断基準の明確さ

2. **具体性** (1-5点)
   - 実行可能性
   - 具体的な手順
   - 測定可能な基準

3. **構造化** (1-5点)
   - セクション構成
   - 論理的な流れ
   - 一貫性

4. **完全性** (1-5点)
   - 必須要素の充足
   - エラーハンドリング
   - エッジケースのカバー

### 評価プロセス

```bash
# 1. 品質チェック
node scripts/validate-prompt-quality.mjs <prompt-file>

# 2. 構造検証
node scripts/validate-skill.mjs

# 3. Token数確認
node scripts/analyze-prompt.mjs <prompt-file>
```

### 改善サイクル

```
1. 評価 → 2. 問題特定 → 3. 改善 → 4. 再評価
    ↑                                      ↓
    ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ← ←
```

## 戦略7: テンプレート活用

### 目的

一貫性を保ちながら、効率的にプロンプトを作成する。

### テンプレートの使用

```bash
# テンプレートをコピー
cp assets/prompt-template.md my-agent-prompt.md

# プレースホルダーを置換
# {{agent-name}} → 実際のエージェント名
# {{role-description}} → 役割の説明
# etc.
```

### カスタマイズポイント

**必須カスタマイズ**:

- 役割定義
- タスク範囲
- 制約条件

**推奨カスタマイズ**:

- ワークフロー
- Few-Shot Examples
- エラーハンドリング

**オプションカスタマイズ**:

- 品質基準
- プロジェクト固有知識

## 実践例: Before/After

### Before（最適化前）

```markdown
リファクタリングエージェント

コードをリファクタリングします。必要に応じてテストを追加し、
適宜Code Smellsを検出します。できるだけ品質を高めてください。

例:
Long Methodを見つけたらリファクタリング
Duplicate Codeも同様
テストがない場合はエラー
```

**問題点**:

- 曖昧表現多数（「必要に応じて」「適宜」「できるだけ」）
- 基準不明確（何行がLong Method？）
- 構造化されていない
- 例示が不十分

### After（最適化後）

````markdown
# リファクタリング専門家

## 役割

あなたは **リファクタリング専門家** です。

マーティン・ファウラー『リファクタリング』に基づき、
Code Smellsを体系的に検出し、適切なパターンでリファクタリングします。

## ワークフロー

### Phase 1: Code Smells検出

**手順**:

1. Long Methodを検出（20行以上）
2. Duplicate Codeを特定（3箇所以上、5行以上）
3. Large Classを発見（10メソッド以上）

**成果物**:

- `docs/code-smells-report.md`

### Phase 2: リファクタリング実施

**手順**:

1. 優先度順にソート（セキュリティ > 複雑度 > 重複度）
2. Extract Methodパターンを適用
3. 各変更後にテストを実行（100%合格必須）

**成果物**:

- リファクタリング済みコード
- テスト結果レポート

## ベストプラクティス

✅ **すべきこと**:

- 1コミット1変更
- 各変更後にテスト実行
- テストカバレッジ80%以上を維持

❌ **避けるべきこと**:

- テストなしリファクタリング
- 複数変更の同時実施
- 大規模一括変更

## 例

### 例1: Long Method検出

**入力**:
\```typescript
function processOrder(order) {
// 25行のコード
}
\```

**処理**:

1. 行数カウント: 25行
2. Long Method判定: Yes（>20行）
3. Extract Method適用

**出力**:
\```typescript
function processOrder(order) {
const validated = validateOrder(order);
const processed = applyRules(validated);
return saveOrder(processed);
}
\```

### 例2: テスト不足エラー

**入力**:
テストカバレッジ: 0%

**処理**:

1. カバレッジ確認: 0%
2. 基準未達（<80%）
3. エラー生成

**出力**:
エラー: テストカバレッジ不足（0% < 80%）
推奨: まずテストを追加
````

**改善点**:

- 曖昧表現を排除
- 具体的な基準値を設定（20行以上、80%以上）
- 7セクション構造で整理
- 具体的な例示を追加

## ベストプラクティス

### すべきこと

- ✅ 曖昧表現を具体的な基準に置換
- ✅ 測定可能な数値基準を設定
- ✅ 7セクション構造で整理
- ✅ プログレッシブディスクロージャー実装
- ✅ Token数を継続的に監視
- ✅ 品質指標で定期評価

### 避けるべきこと

- ❌ 「適宜」「など」「できるだけ」を使用
- ❌ 基準のない指示
- ❌ 非構造化された長文
- ❌ 過度な情報の詰め込み
- ❌ 重複する説明
- ❌ 一貫性のない用語

## 次のステップ

最適化戦略を理解したら:

1. **anti-patterns.md**: よくある失敗パターンと対処法を確認
2. **実践**: 既存プロンプトを最適化
3. **評価**: 品質指標で効果を測定
