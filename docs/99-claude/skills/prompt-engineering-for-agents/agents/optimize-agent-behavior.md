# エージェント動作最適化タスク

## タスク概要

既存エージェントのSystem Promptを最適化し、動作品質を向上させるタスクです。
明確性、簡潔性、構造化、効率性の4つの観点から体系的に改善します。

## 前提条件

- 最適化対象のエージェントが存在する
- 現在の問題点が特定されている
- `references/optimization-strategies.md` を理解している

## 実行手順

### Phase 1: 現状分析

**目的**: 現在のプロンプトの問題点を特定

**手順**:

1. 既存のSystem Promptを読み込み
2. `scripts/analyze-prompt.mjs` で構造を分析
3. 以下の4つの観点で評価（各1-5点）:
   - **明確性**: 曖昧な表現の有無
   - **簡潔性**: 冗長性の程度
   - **構造化**: セクション構成の論理性
   - **効率性**: Token消費の適切さ
4. 3点以下の項目を改善対象として特定
5. `references/anti-patterns.md` でアンチパターンを確認

**分析テンプレート**:

```markdown
## 現状分析結果

### 評価スコア

- 明確性: {{点数}}/5
- 簡潔性: {{点数}}/5
- 構造化: {{点数}}/5
- 効率性: {{点数}}/5

### 検出されたアンチパターン

1. **{{アンチパターン名}}**:
   - 箇所: {{該当箇所}}
   - 問題: {{問題点}}
   - 優先度: {{高/中/低}}

2. **{{アンチパターン名}}**:
   [同様]

### 改善優先順位

1. **最優先**: {{問題1}}（影響度大）
2. **高優先**: {{問題2}}（頻度高）
3. **中優先**: {{問題3}}（改善効果中）
```

**成果物**:

- 現状分析レポート
- 改善優先順位リスト

### Phase 2: 曖昧表現の排除

**目的**: 曖昧な表現を具体的な基準に置換

**手順**:

1. 以下の曖昧表現を検索:

   ```bash
   grep -i "適宜\|必要に応じて\|など\|いくつかの\|できるだけ" <prompt-file>
   ```

2. 各表現を具体的な基準に置換:

| 曖昧表現     | 置換例                         |
| ------------ | ------------------------------ |
| 適宜         | 「条件Xの場合はYを実施」       |
| 必要に応じて | 「テストカバレッジ<80%の場合」 |
| など         | 具体的な項目をすべて列挙       |
| いくつかの   | 「3-5個の」                    |
| できるだけ   | 「80%以上」                    |

3. Before/After を記録

**Before/After例**:

```markdown
## Before

必要に応じてテストを追加し、適宜リファクタリングしてください。
```

```markdown
## After

以下の条件でテストを追加してください:

- 新規関数: 単体テスト必須
- 既存関数変更: 既存テスト更新必須
- カバレッジ<80%: 追加テスト必須

リファクタリング基準:

- メソッド>20行: Extract Method適用
- 重複コード>3箇所: Extract Function適用
```

**成果物**:

- 曖昧表現置換リスト
- Before/After比較

### Phase 3: 構造化改善

**目的**: 情報を論理的に整理し、理解しやすくする

**手順**:

1. 現在のセクション構成を確認
2. 推奨7セクション構造に準拠しているか確認:
   - 役割定義
   - 専門分野
   - ワークフロー
   - スキル管理
   - ベストプラクティス
   - 詳細リファレンス
   - 変更履歴
3. 欠けているセクションを追加
4. 非構造化された長文を箇条書きに分割
5. 関連情報をセクションでグループ化

**改善例**:

```markdown
## Before（非構造化）

このエージェントはリファクタリングします。Long MethodやDuplicate Codeを
見つけてExtract MethodやExtract Functionを使います。テストは必ず実行します...
（延々と続く長文）

## After（構造化）

## 役割

リファクタリング専門家

## ワークフロー

### Phase 1: Code Smells検出

1. Long Method検出（20行以上）
2. Duplicate Code検出（3箇所以上）

### Phase 2: リファクタリング実施

1. Extract Method適用
2. テスト実行

## ベストプラクティス

✅ **すべきこと**:

- 各変更後にテスト実行

❌ **避けるべきこと**:

- テストなしリファクタリング
```

**成果物**:

- 構造化されたSystem Prompt
- セクション対応表

### Phase 4: Token最適化

**目的**: Token消費を削減し、効率性を向上

**手順**:

1. 現在のToken数を測定
2. 以下の最適化テクニックを適用:

#### テクニック1: 重複の削除

```markdown
## Before

### Phase 1

エージェントの役割を考慮して実施

### Phase 2

エージェントの役割を考慮して実施

## After

## 共通原則

すべてのPhaseで役割を考慮

### Phase 1: 検出

### Phase 2: 実施
```

#### テクニック2: 箇条書きの活用

```markdown
## Before

エージェントはコードの匂いを検出し、それに基づいて適切なパターンを
選択し、テストを実行して検証します。

## After

1. Code Smells検出
2. パターン選択
3. テスト検証
```

#### テクニック3: テーブルの活用

```markdown
## Before

- Long Method: 20行以上のメソッド
- Large Class: 200行以上のクラス

## After

| Code Smell  | 基準      |
| ----------- | --------- |
| Long Method | 20行以上  |
| Large Class | 200行以上 |
```

#### テクニック4: 外部化

5個以上の例示や詳細説明は `references/` に外部化:

```markdown
## Before（SKILL.mdに10個の例示）

### 例1: ...

### 例2: ...

...

### 例10: ...

## After

### 例1: 典型例

### 例2: 境界例

詳細な例は `references/examples.md` を参照。
```

**成果物**:

- Token削減レポート
- 最適化前後のToken数比較

### Phase 5: Few-Shot Examples改善

**目的**: 効果的な例示に改善

**手順**:

1. 現在の例示数を確認
2. 10個以上の場合、2-5個に削減:
   - 典型例2個
   - 境界例1個
   - 失敗例1個（オプション）
3. 抽象的な例を具体的な値に置換
4. 入力→処理→出力の流れを明示

**改善例**:

````markdown
## Before（抽象的）

### 例1

**入力**: {{long_method}}
**出力**: {{short_method}}

## After（具体的）

### 例1: Long Method検出（典型例）

**入力**:
\```typescript
function processOrder(order) {
// 25行のコード
}
\```

**処理**:

1. 行数カウント: 25行
2. Long Method判定: Yes（>20行）
3. Extract Method適用

**出力**:
\```typescript
function processOrder(order) {
const validated = validateOrder(order);
return saveOrder(validated);
}
\```
````

**成果物**:

- 改善されたFew-Shot Examples
- 例示削減リスト

### Phase 6: 制約の明確化

**目的**: すべきこと・避けるべきことを具体化

**手順**:

1. 現在の制約を確認
2. 以下の形式に整理:

```markdown
## ベストプラクティス

✅ **すべきこと**:

- {{制約1}}（{{理由}}）
- {{制約2}}（{{理由}}）
- {{制約3}}（{{理由}}）

❌ **避けるべきこと**:

- {{禁止事項1}}（{{理由}}）
- {{禁止事項2}}（{{理由}}）
- {{禁止事項3}}（{{理由}}）
```

3. 各項目に理由を追加
4. 具体的な基準値を設定

**改善例**:

```markdown
## Before

すべきこと:

- テストを実行

## After

✅ **すべきこと**:

- 各変更後にテストを実行（理由: リグレッションを防止）
- テストカバレッジ80%以上を維持（理由: 品質基準）
- 1コミット1変更（理由: レビュー容易性）

❌ **避けるべきこと**:

- テストなしリファクタリング（理由: リスクが高い）
- 複数変更の同時実施（理由: 問題の特定が困難）
```

**成果物**:

- 明確化された制約リスト

### Phase 7: 品質検証と最終調整

**目的**: 最適化の効果を検証

**手順**:

1. `scripts/validate-prompt-quality.mjs` で品質チェック
2. 以下の指標で再評価（各1-5点）:
   - 明確性
   - 簡潔性
   - 構造化
   - 効率性
3. 最適化前後のスコアを比較
4. すべての指標が4点以上か確認
5. Token削減率を確認（目標: 20%以上削減）

**評価テンプレート**:

```markdown
## 最適化効果

### スコア比較

| 指標   | 最適化前 | 最適化後 | 改善   |
| ------ | -------- | -------- | ------ |
| 明確性 | {{点数}} | {{点数}} | +{{N}} |
| 簡潔性 | {{点数}} | {{点数}} | +{{N}} |
| 構造化 | {{点数}} | {{点数}} | +{{N}} |
| 効率性 | {{点数}} | {{点数}} | +{{N}} |

### Token削減

- 最適化前: {{N}} tokens
- 最適化後: {{N}} tokens
- 削減率: {{N}}%

### 改善点

1. {{改善点1}}
2. {{改善点2}}
3. {{改善点3}}
```

**成果物**:

- 最適化効果レポート
- 最終版System Prompt

## 注意事項

### すべきこと

- ✅ 現状分析を丁寧に実施
- ✅ 優先順位をつけて段階的に改善
- ✅ Before/Afterを記録
- ✅ 効果を定量的に測定
- ✅ 継続的に改善

### 避けるべきこと

- ❌ 分析なしで改善開始
- ❌ 一度にすべてを変更
- ❌ 効果測定をスキップ
- ❌ 過度な最適化（可読性低下）
- ❌ 一度きりの改善で終了
