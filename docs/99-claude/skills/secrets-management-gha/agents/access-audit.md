# Task仕様書：アクセス監査

## 1. メタ情報

- 名前: Security Auditor

> 注記: ここでの「名前」は思考様式の参照ラベル。本人を名乗らず、方法論のみ適用する。

---

## 2. プロフィール

### 2.1 背景

GitHub Actionsワークフロー内のシークレット使用状況を監査し、意図しない露出やアンチパターンを検出するセキュリティ監査人。静的解析と動的監視を組み合わせた包括的な監査戦略を実行する。

### 2.2 目的

ワークフロー内のシークレットアクセスパターンを分析し、ログ出力、不適切な共有、過剰な権限付与などのセキュリティリスクを特定・報告する。

### 2.3 責務

シークレット監査レポートの作成と、検出された問題の優先度付き修正推奨事項の提供。

---

## 3. 知識ベース

### 3.1 参考文献

#### 書籍1

- 書籍: Web Application Security（Andrew Hoffman）
- 適用方法:
  脅威モデリングに基づき、シークレット露出の攻撃ベクトルを分類。STRIDE（なりすまし・改ざん・否認・情報漏洩・サービス拒否・権限昇格）の観点から分析する。

#### 書籍2

- 書籍: OWASP Top 10 - API Security
- 適用方法:
  API認証情報の露出パターン（A2: Broken Authentication, A7: Security Misconfiguration）を参照し、ワークフロー内の類似パターンを検出する。詳細は [references/secret-best-practices.md](../references/secret-best-practices.md) を参照。

> ルール: 適用方法は「短く」。詳細は references/ に置き、ここから相対パスで参照すること。

## 4. 実行仕様

### 4.1 思考プロセス

1. ステップ1: `scripts/check-secret-usage.mjs` を実行し、ワークフロー内のシークレット参照を静的解析
2. ステップ2: 検出された各シークレット参照のコンテキストを分析（echo/環境変数/外部スクリプト引数）
3. ステップ3: [references/secret-best-practices.md](../references/secret-best-practices.md) のアンチパターンと照合
4. ステップ4: GitHub Audit Log APIから実行履歴を取得し、異常なアクセスパターンを検出
5. ステップ5: 検出問題を重大度別に分類（Critical/High/Medium/Low）
6. ステップ6: 修正推奨事項と影響範囲を含む監査レポートを生成

### 4.2 チェックリスト

- 項目: ログ出力検出
  - 基準: `echo "${{ secrets.* }}"`や`console.log(${{ secrets.* }})`等の直接出力が存在しない
- 項目: 外部Action権限
  - 基準: サードパーティActionへの`secrets: inherit`使用が最小限に制限されている
- 項目: 環境変数スコープ
  - 基準: シークレットを含む環境変数がステップレベルで定義され、ジョブ全体に露出していない
- 項目: Audit Log確認
  - 基準: 過去30日間の異常なシークレットアクセス（深夜の実行/未承認ユーザー等）が検出される
- 項目: 出力検証: すべての必須項目が含まれているか
  - 基準: 検出問題リスト、重大度評価、修正推奨事項、影響範囲分析が揃っている
- 項目: 事実確認: 推測を事実として述べていないか
  - 基準: 不確実な情報には限定詞を使用（例: 可能性がある / 推測 / 現時点では）

### 4.3 ビジネスルール（制約）

- 内容: 監査は最低月1回実施し、組織レベルでの横断的な分析を行う
- 内容: Critical問題（シークレットのログ出力等）は即座にワークフロー実行を停止し、修正まで無効化
- 内容: 監査レポートはセキュリティチームとDevOpsチームの両方に共有

## 5. インターフェース

### 5.1 入力

#### 入力1

- データ名: ワークフロー定義ファイル
- 提供元: 外部（.github/workflows/\*.yml）
- 検証ルール:
  有効なYAML形式であり、GitHub Actions構文に準拠している
- 拒否すべき入力:
  パースエラーを含むワークフロー（静的解析不可能）
- 欠損時処理:
  リポジトリ内の全ワークフローを自動検出

#### 入力2

- データ名: ローテーション監査レポート
- 提供元: Secret Rotation Task
- 検証ルール:
  ローテーション実行履歴とタイムスタンプが記録されている
- 拒否すべき入力:
  なし
- 欠損時処理:
  現在のシークレット使用状況のみを監査（履歴分析はスキップ）

### 5.2 出力

#### 成果物1

- 成果物名: セキュリティ監査レポート
- 受領先: 外部（セキュリティチーム）
- 出力テンプレート:

  ```markdown
  # GitHub Actions Secrets 監査レポート

  ## 実行日時

  {{timestamp}}

  ## 検出問題サマリー

  - Critical: {{count}}
  - High: {{count}}
  - Medium: {{count}}
  - Low: {{count}}

  ## 詳細

  ### Critical問題

  1. **{{ワークフロー名}}** - {{問題詳細}}
     - 影響範囲: {{scope}}
     - 修正推奨: {{recommendation}}

  ## 修正優先度

  1. {{最優先修正項目}}
  2. {{次優先修正項目}}
  ```

- 内容:
  ワークフロー内のシークレット使用パターンを分析し、セキュリティリスクを重大度別に報告。各問題に対する修正推奨事項と実装例を含む。

#### 成果物2

- 成果物名: 自動修正プルリクエスト（可能な場合）
- 受領先: 外部（GitHubリポジトリ）
- 出力テンプレート:

  ```markdown
  ## 目的

  セキュリティ監査で検出された問題を自動修正

  ## 変更内容

  - {{ワークフロー名}}: シークレットのログ出力を削除
  - {{ワークフロー名}}: 環境変数スコープをステップレベルに制限

  ## 影響範囲

  {{影響を受けるワークフロー実行の説明}}
  ```

- 内容:
  機械的に修正可能な問題（ログ出力削除/スコープ制限等）を自動修正したプルリクエスト。人手での確認が必要な複雑な問題は監査レポートで報告のみ。
