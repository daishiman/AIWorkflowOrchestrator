## 4. 実行仕様

### 4.1 思考プロセス

1. **防御設計の完全性評価**
   - 脅威モデルで特定されたすべての攻撃パターンに対する防御が存在するか確認
   - 各防御層が独立して機能するか検証（多層防御の実現）
   - 単一障害点（Single Point of Failure）が存在しないか確認

2. **セキュリティチェックリストの適用**
   - `assets/defense-checklist.md` の各項目を順次評価
   - 各項目について「実装済み」「部分的」「未実装」を判定
   - 未実装項目の優先度を評価

3. **コード実装の検証**
   - 入力検証ロジックの実装確認（ホワイトリスト方式か）
   - プロンプト構造化の実装確認（デリミタ、エスケープ処理）
   - 出力検証の実装確認（機密情報漏洩検出）
   - エラーハンドリング確認（fail-secure原則）

4. **改善推奨事項の提案**
   - 優先度の高い脆弱性から改善策を提示
   - 実装コスト vs セキュリティ効果を評価
   - 具体的なコード修正例を提供

### 4.2 チェックリスト

- [ ] **完全性**: すべての攻撃パターンに対する防御が存在する
- [ ] **多層防御**: 最低3層の独立した防御メカニズムが実装されている
- [ ] **入力検証**: ホワイトリスト方式が採用されている
- [ ] **プロンプト構造化**: システム指示とユーザー入力が明確に分離されている
- [ ] **出力検証**: 機密情報漏洩の検出メカニズムが存在する
- [ ] **コンテキスト分離**: 最小権限原則が適用されている
- [ ] **Fail-Secure**: すべてのエラーハンドリングが安全側に倒れる
- [ ] **ログと監視**: 攻撃試行の記録メカニズムが存在する
- [ ] **ドキュメント**: 防御メカニズムが文書化されている
- [ ] **テストケース**: セキュリティテストケースが作成されている

### 4.3 ビジネスルール（制約）

- 検証結果は定量的に評価し、主観的な判断を避ける
- 脆弱性を発見した場合、必ず改善策を提案する
- 改善策は実装可能性を考慮する（理想論だけでなく現実的な解決策）
- 検証レポートはステークホルダーが理解できる言葉で記述する

## 5. インターフェース

### 5.1 入力

#### 入力1

- **データ名**: 防御設計書
- **提供元**: defense-design タスクの出力
- **検証ルール**:
  - 入力検証、プロンプト構造化、出力検証、コンテキスト分離の4要素が含まれていること
  - 各防御メカニズムに具体的な実装方針が記述されていること
- **拒否すべき入力**:
  - 抽象的な記述のみで具体性がない設計書
  - 脅威モデルとの対応関係が不明確な設計書

#### 入力2

- **データ名**: 実装コード（オプション）
- **提供元**: 外部（既存のコードベース）
- **検証ルール**:
  - 実行可能なコードであること
  - 防御設計書に記載された機能が実装されていること
- **拒否すべき入力**:
  - 設計書と全く異なる実装

### 5.2 出力

#### 出力1

- **データ名**: 検証レポート
- **構造**:

  ```markdown
  # プロンプトインジェクション防御 検証レポート

  ## 1. 評価サマリ

  - 総合評価: [優/良/可/不可]
  - 検証項目合格率: XX%
  - 重大な脆弱性数: X件
  - 改善推奨項目数: X件

  ## 2. 詳細評価

  ### 2.1 入力検証

  - 実装状況: [実装済み/部分的/未実装]
  - 評価: [コメント]
  - 問題点: [具体的な問題]

  ### 2.2 プロンプト構造化

  ...

  ## 3. 発見された脆弱性

  ### 脆弱性1

  - 種類: [脆弱性の分類]
  - 重大度: [高/中/低]
  - 説明: [具体的な問題]
  - 攻撃シナリオ例: [攻撃の流れ]
  - 改善策: [具体的な修正方法]

  ## 4. 改善推奨事項

  [優先度順にリスト]
  ```

- **フォーマット**: Markdown
- **必須要素**: 評価サマリ、詳細評価、脆弱性リスト、改善推奨事項

#### 出力2

- **データ名**: 改善ガイドライン
- **形式**: 実装可能なコード例を含むドキュメント
- **目的**: 開発者が即座に修正を適用できるようにする

### 5.3 依存関係

- **前提タスク**: threat-modeling, defense-design
- **後続タスク**: なし（最終フェーズ）
- **並列実行**: 不可（防御設計完了後に実行）

## 6. 実行例

### 入力例

```markdown
# 防御設計書

## 入力検証

ブラックリスト方式で既知の攻撃パターンを拒否する。

## プロンプト構造化

ユーザー入力の前後にマーカーを追加する。
```

### 処理フロー

1. チェックリスト適用
   - 入力検証: ブラックリスト方式 → ❌ ホワイトリスト方式を推奨
   - プロンプト構造化: マーカー追加のみ → ⚠️ エスケープ処理が不明確

2. 脆弱性特定
   - 脆弱性1: ブラックリスト方式は回避可能
   - 脆弱性2: エスケープ処理が未定義

3. 改善策提案
   - 入力検証をホワイトリスト方式に変更
   - エスケープ処理の実装例を提供

### 出力例

````markdown
# 検証レポート

## 評価サマリ

- 総合評価: 可
- 重大な脆弱性: 1件
- 改善推奨項目: 2件

## 発見された脆弱性

### 脆弱性1: 入力検証のブラックリスト依存

- 重大度: 高
- 説明: ブラックリスト方式は新しい攻撃パターンに対応できない
- 改善策: ホワイトリスト方式への変更
  ```typescript
  // 改善例
  function validateInput(input: string): boolean {
    // 許可されたパターンのみを受け入れる
    return /^[a-zA-Z0-9\s?.!]{1,500}$/.test(input);
  }
  ```
````

## 改善推奨事項

1. [高] 入力検証をホワイトリスト方式に変更
2. [中] プロンプト構造化にエスケープ処理を追加

```

## 7. エラーハンドリング

| エラー状況                     | 対処方法                                     |
| ------------------------------ | -------------------------------------------- |
| 防御設計書が不完全             | 不足要素を明示し、defense-designに差し戻し   |
| 実装コードが設計と不一致       | 不一致箇所を指摘し、修正を要求               |
| チェックリストの判定が困難     | 判断根拠を明示し、追加情報を要求             |

## 8. パフォーマンス要件

- 検証時間: 設計書の規模に応じて10-30分
- レポート生成: 5分以内
- コード検証（オプション）: コードベースの規模に応じて変動

## 9. 品質基準

- **完全性**: すべてのチェックリスト項目を評価している
- **具体性**: 発見された問題に具体的な改善策が含まれている
- **実装可能性**: 改善策が現実的に実装可能である
- **優先度**: 脆弱性と改善項目に優先度が付けられている
```
