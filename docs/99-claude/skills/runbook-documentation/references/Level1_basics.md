# ランブック基礎概念（Level 1）

> **読込条件**: 初回利用時、ランブック作成が初めての場合

---

## 1. ランブックとは

### 1.1 定義

ランブック（Runbook）とは、システム運用において繰り返し実行される手順を文書化したものである。

| 特徴     | 説明                                       |
| -------- | ------------------------------------------ |
| 再現性   | 誰が実行しても同じ結果を得られる           |
| 標準化   | 手順が統一されており、属人化を防ぐ         |
| 迅速性   | 調査や判断の時間を削減し、対応を高速化する |
| 知識継承 | 暗黙知を形式知化し、チーム全体で共有可能   |

### 1.2 ランブックの種類

| 種類                   | 目的                       | 例                       |
| ---------------------- | -------------------------- | ------------------------ |
| インシデント対応       | 障害発生時の対応手順       | DB接続エラー復旧         |
| トラブルシューティング | 問題の原因究明と解決       | パフォーマンス低下診断   |
| リカバリー手順         | システム復旧の手順         | バックアップからの復元   |
| オペレーションチェック | 定期的な確認作業           | デプロイ前チェックリスト |
| エスカレーション       | 問題のエスカレート判断基準 | 重大障害の通知フロー     |

## 2. ランブックの構成要素

### 2.1 必須要素

| 要素             | 説明                         | 例                                               |
| ---------------- | ---------------------------- | ------------------------------------------------ |
| タイトル         | 何のランブックか一目で分かる | 「データベースフェイルオーバー手順」             |
| 目的             | このランブックを使う理由     | 「プライマリDBが応答しない場合の復旧」           |
| 適用条件         | いつ使うべきかの判断基準     | 「DB接続タイムアウトが5分以上継続」              |
| 前提条件         | 必要なアクセス権限、ツール   | 「本番環境へのSSHアクセス権限」                  |
| 手順             | 番号付きの実行ステップ       | 「1. ステータス確認」「2. フェイルオーバー実行」 |
| 期待される結果   | 各ステップの成功判定基準     | 「スタンバイがプライマリに昇格」                 |
| エスカレーション | いつ誰にエスカレートするか   | 「30分で解決しない場合はDBA」                    |

### 2.2 推奨要素

| 要素                   | 説明                     | 例                         |
| ---------------------- | ------------------------ | -------------------------- |
| 想定所要時間           | 作業にかかる目安時間     | 「約15分」                 |
| ロールバック手順       | 失敗時の復旧方法         | 「フェイルバック手順」     |
| トラブルシューティング | よくある問題と対処法     | 「レプリケーション遅延時」 |
| 関連リンク             | アラート、ダッシュボード | 「Grafanaリンク」          |
| 変更履歴               | 更新日、担当者、変更内容 | 「2024-01-15 手順3を追加」 |

## 3. 良いランブックの特徴

### 3.1 明確性

- **曖昧な表現を避ける**: 「適切に」「必要に応じて」は禁止
- **具体的な数値を使う**: 「5分待つ」「3回リトライ」
- **判断基準を明示**: 「CPU使用率が90%を超えたら」

### 3.2 実行可能性

- **コピペで動くコマンド**: 変数や環境依存部分は明示
- **前提条件を網羅**: 必要な権限、ツール、知識を列挙
- **ステップの独立性**: 各ステップは前のステップの結果に依存する場合は明記

### 3.3 保守性

- **バージョン管理**: 変更履歴を記録
- **担当者の明記**: 問い合わせ先を記載
- **定期レビュー**: 最終更新日を記録し、定期的に見直す

## 4. スコープ定義の基礎

### 4.1 対象システムの特定

| 確認事項       | 質問                             |
| -------------- | -------------------------------- |
| システム構成   | どのコンポーネントが対象か？     |
| 依存関係       | 何に依存しているか？             |
| クリティカル度 | ダウン時のビジネス影響は？       |
| 障害頻度       | 過去にどのような障害があったか？ |

### 4.2 優先順位付け

| 優先度 | 基準                                 |
| ------ | ------------------------------------ |
| 高     | 障害頻度が高い、ビジネス影響が大きい |
| 中     | 障害頻度は低いが影響は大きい         |
| 低     | 障害頻度も影響も小さい               |
