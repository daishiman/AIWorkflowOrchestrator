## ワークフロー改善点

### 削除済み前提の早期検出

**問題**: タスク仕様書が作成された時点ですでにファイルが削除済みだったが、
Phase 1 の P0 チェックまでその事実が明確化されなかった。

**改善案**: タスク仕様書作成時（spec_created フェーズ）に
`test -e <target_file>` を自動実行し、削除済みなら仕様書に明記する仕組みを追加する。

**補足**: `generate-index.js` のような正本生成スクリプトも同時に存在確認し、`N/A` と決め打ちせず再生成を先に走らせる。

## 技術的教訓

### 削除後の grep / git status 安全化

削除済みファイルに対して直接 `grep` や `vitest run` を実行すると
「ファイルが見つからない」エラーが発生し、ワークフローが中断する。

**対策**: 全フェーズで以下のパターンを使用する。

```bash
if [ -e "$target_file" ]; then
  # 存在時のみ実行
  grep -n "describe.skip" "$target_file"
else
  echo "N/A: $target_file は削除済み"
fi
```

`artifacts.json` の同値性確認も `ls` ではなく `diff -q artifacts.json outputs/artifacts.json` を使う。

### 選択肢A/B の判断基準

| 基準                                                  | 方針            |
| ----------------------------------------------------- | --------------- |
| companion test がエッジケースをカバー済み             | 選択肢A（削除） |
| companion test にカバーされていないエッジケースが残存 | 選択肢B（移植） |

今回は F-2/F-3/E-4/W-8b 全て companion test でカバー済みであったため、
選択肢A（削除）を採用した。

## 設計判断の教訓

### テストを削除するか書き直すかの判断フロー

```
1. 対象ファイルが削除済みか確認
   ↓ 削除済みの場合
2. companion test でエッジケースがカバーされているか確認
   ↓ カバー済みの場合
3. 選択肢A（削除）を採用 → 残存参照のみ整理
   ↓ カバーされていない場合
4. 選択肢B（移植）を採用 → 新フロー API に書き直して companion test へ追加
```

### 削除済み時の残存参照整理

- `describe.skip` 件数: 対象ファイル削除により自動的に 0 件
- `TODO(W2-seq-03a)` コメント: 周辺ファイルを grep で確認し 0 件
- companion test の補完: 不要（エッジケースカバー済み）

## スキル改善提案

### CI での削除済み検出ルール追加

削除済みテストファイルへの参照（import / require）が残存していないかを
CI ステップで自動検証するルールを追加できる。

```bash
# 削除されたテストファイルへの参照がないか確認
git log --diff-filter=D --name-only -- "*.test.tsx" | \
  xargs -I{} grep -rn "{}" apps/ --include="*.ts" --include="*.tsx"
```

`grep` の集計は `describe.skip` だけでなく `it.skip` / `test.skip` を含む場合があるため、レポート側の件数ラベルも実際の集計ルールに合わせて明記する。

## 新規 Pitfall 候補

### 旧フロー依存テストの direct reference が残るパターン

旧テストファイルが `import { planSkill } from "..."` のような形で
存在しない関数を import していると、ファイルが削除されても
他ファイルから参照されていた場合に TypeScript エラーが発生する。

**対策**: タスク完了時に `typecheck` を必ず実行し 0 error を確認する（AC-4 として標準化済み）。
