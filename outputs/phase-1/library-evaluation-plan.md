# ライブラリ評価計画 - TASK-UI-SCHEDULE-CRON-SEMANTIC-001

## 評価対象アプローチ

| アプローチ                    | 概要                                               | バンドルサイズ | 正確性                                  | 保守性                   | 実装コスト |
| ----------------------------- | -------------------------------------------------- | -------------- | --------------------------------------- | ------------------------ | ---------- |
| A: `cron-parser`              | npm の `cron-parser` で next-execution-time を計算 | ~10KB gzip     | 高（月末日・うるう年・到達可能性判定）  | 高（npm更新で仕様追従）  | 低         |
| B: カスタム実装               | 日付計算を自前実装                                 | 0追加          | 低〜中（2月31日のような単純ケースのみ） | 低（自前カバレッジ維持） | 高         |
| C: `@datasert/cron-validator` | 軽量バリデーター特化                               | 小             | 中（機能限定）                          | 中                       | 低〜中     |

## 推奨案

**アプローチA: `cron-parser` を採用**

### 採用理由

1. `CronExpressionParser.parse()` と `interval.next()` の組み合わせで `"0 0 31 2 *"` のような意味論的不正ケースを検出できる
2. next-execution-time 計算を使って、うるう年や月末日の到達可能性を安全側に判定できる
3. カスタム実装では `"0 0 30 2 *"` や月末・うるう年の正確な対処が困難
4. Renderer バンドルでtree-shakingが効くため実影響は限定的

### 却下理由

- B: 保守コストが高く、エッジケースのカバレッジが不十分
- C: 機能が限定的でnext-run計算に対応していない可能性あり

## インストール方針

```bash
pnpm --filter @repo/desktop add cron-parser
```

- `dependencies` セクションに追加（Renderer実行時に必要なため `devDependencies` ではない）
- バージョン指定: `^5.x`（最新安定版）
