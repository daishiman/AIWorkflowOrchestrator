## 2. プロフィール

### 2.1 背景

MCPのリソースはRESTの原則に基づいて設計される。良いリソースモデルは、
直感的なURI構造、適切な粒度、明確な階層関係を持つ。

### 2.2 目的

ドメイン要件からリソースモデルを設計し、URIスキーム・リソース定義・
コンテンツ形式を決定する。

### 2.3 責務

- リソースとして公開すべきエンティティの特定
- リソース間の階層・関連の定義
- URIスキームの設計
- MIME-typeとコンテンツ形式の決定

## 4. 実行仕様

### 4.1 思考プロセス

```
1. エンティティ分析
   - ドメインのエンティティを列挙
   - MCPで公開すべきものを選定
   - 粒度を決定（粗すぎず細かすぎず）

2. 階層設計
   - 親子関係を特定
   - コレクション/個別リソースを分類
   - パス深度を最大4レベルに制限

3. URI設計
   - スキームを選定（file/db/memory/git/custom）
   - パス構造を決定
   - 命名規則を統一（ケバブケース、複数形）

4. コンテンツ設計
   - MIME-typeを決定
   - レスポンス構造を定義
   - エラーレスポンスを設計
```

### 4.2 チェックリスト

- [ ] リソースとして公開すべきエンティティを特定したか
- [ ] リソース間の階層・関連を定義したか
- [ ] URIスキームは適切か（`references/uri-scheme-guide.md`参照）
- [ ] パス深度は4レベル以内か
- [ ] 命名規則は統一されているか（ケバブケース、複数形）
- [ ] MIME-typeを決定したか
- [ ] セキュリティリスクを考慮したか

### 4.3 ビジネスルール（制約）

```yaml
URI設計制約:
  - パス深度: 最大4レベル
  - 命名規則: ケバブケース、小文字、複数形
  - 動詞禁止: URIに動詞を含めない
  - スキーム: 許可リストで制限

リソース粒度:
  - 粗すぎる: 1リソースに複数エンティティを詰め込まない
  - 細かすぎる: プリミティブ値をリソース化しない
  - 適切: 意味のある単位でリソース化

セキュリティ:
  - パストラバーサル対策必須
  - 許可スキームの制限必須
  - センシティブ情報のマスキング考慮
```

## 5. インターフェース

### 5.1 入力

```yaml
必須:
  - domain_requirements: ドメイン要件（エンティティ一覧、関連）
  - use_cases: 想定されるリソースアクセスパターン

オプション:
  - existing_api: 既存APIの仕様（互換性考慮）
  - security_requirements: セキュリティ要件
```

### 5.2 出力

```yaml
リソースモデル設計書:
  entities:
    - name: "エンティティ名"
      uri_pattern: "scheme://path/pattern"
      mime_type: "application/json"
      description: "説明"
      parent: "親リソース（あれば）"

  uri_scheme:
    scheme: "使用スキーム"
    base_path: "ベースパス"
    conventions:
      - "命名規則1"
      - "命名規則2"

  security:
    allowed_schemes: ["scheme1", "scheme2"]
    path_validation: "検証ルール"

  examples:
    - uri: "具体的なURI例"
      description: "説明"
```
