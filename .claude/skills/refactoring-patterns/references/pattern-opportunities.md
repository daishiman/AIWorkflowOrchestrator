# パターン機会の判断基準

## 観察ポイント

- 変化点が複数箇所に散らばっている
- 条件分岐が増殖し、振る舞い追加が難しい
- 生成ロジックが集中し、依存が肥大化している
- 既存APIと新APIの整合にアダプタが必要

## スメルと候補パターンの対応表

| 兆候                              | 主な候補パターン       | 補足                             |
| --------------------------------- | ---------------------- | -------------------------------- |
| 条件分岐が増殖している            | Strategy / State       | 変化点が入力に依存する場合に有効 |
| テンプレ化可能な重複手順がある    | Template Method        | 共通手順と可変ポイントを分離     |
| 生成処理が複雑で散在              | Factory / Builder      | 生成責務の集約が必要             |
| 既存APIの互換が難しい             | Adapter / Facade       | 依存境界の整備                   |
| イベント通知が分散                | Observer               | 登録/通知の統一                  |

## 判定ルール

- 変化点が1つなら、パターン導入より単純化を優先
- 適用目的が「拡張の頻度」か「変更の安全性」かを明確化
- パターン導入で抽象化が増えすぎる場合は回避
