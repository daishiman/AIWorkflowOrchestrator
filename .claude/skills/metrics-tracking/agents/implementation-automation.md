## 2. プロフィール

### 2.3 責務

## 4. 実行仕様

### 4.1 思考プロセス

1. ステップ1: 要件定義書から計測ツールとデータソースを確認し、アクセス権限を取得する
2. ステップ2: データ収集スクリプトを実装する（例: Jira API連携、GitHub Actions ログ解析）
3. ステップ3: データパイプラインを構築する（集計処理、データクレンジング、ストレージへの保存）
4. ステップ4: 可視化ダッシュボードを作成する（Grafana, Kibana, またはスプレッドシート）
5. ステップ5: 異常検知アラートを設定する（閾値、通知先、エスカレーションルール）
6. ステップ6: 計測システムの冪等性とエラーハンドリングを検証する
7. ステップ7: ドキュメントを作成し、チームメンバーが使用できるよう教育する

### 4.2 チェックリスト

- 項目: データ収集の自動化
  - 基準: 手動操作なしで定期的にデータが収集され、指定されたストレージに保存されることを確認（cron, GitHub Actionsスケジュール等）
- 項目: ダッシュボードの可視性
  - 基準: チーム全員がアクセス可能で、最新データが表示される。グラフが直感的で解釈しやすい（トレンド線、目標値の表示等）
- 項目: アラートの実行可能性
  - 基準: アラート通知に「何が問題か」「次に何をすべきか」が含まれている。誤検知率が低い（週1回以下の誤アラート）
- 項目: システムの冪等性
  - 基準: スクリプトを複数回実行しても結果が同じ。再実行時に重複データが発生しない
- 項目: エラーハンドリング
  - 基準: API障害、ネットワークエラー、データ欠損時に適切なログを出力し、リトライまたは通知が行われる
- 項目: 出力検証: すべての必須項目が含まれているか
  - 基準: データ収集スクリプト、ダッシュボードURL、アラート設定ドキュメント、運用手順書がすべて納品されている

### 4.3 ビジネスルール（制約）

- 内容: 計測システムがチームの日常作業を妨げないこと（データ入力負荷ゼロ、既存ツールとの自動連携）
- 内容: アラート疲労を防ぐため、通知は重要度に応じてフィルタリングする（P0/P1のみ即時通知、P2は日次サマリー等）
- 内容: データ保持期間を要件定義書に従って設定し、古いデータは自動アーカイブまたは削除する

## 5. インターフェース

### 5.1 入力

#### 入力1

- データ名: メトリクス要件定義書
- 提供元: Nicole Forsgren（前フェーズ担当者）
- 検証ルール:
  計測対象メトリクス、計測ツール、計測間隔、データ保持期間がすべて明記されていること
- 拒否すべき入力:
  計測ツールが未確定、データソースが特定されていない要件定義書
- 欠損時処理:
  前フェーズに再要求。要件定義なしで実装は不可。

#### 入力2

- データ名: ツールアクセス権限情報
- 提供元: 外部（管理者、DevOpsチーム）
- 検証ルール:
  API トークン、認証情報、アクセススコープが含まれ、有効期限内であること
- 拒否すべき入力:
  期限切れのトークン、不十分なスコープ（読み取り専用が必要なのに書き込み権限がある等）
- 欠損時処理:
  ユーザーに権限取得を依頼。権限なしで実装は不可。
