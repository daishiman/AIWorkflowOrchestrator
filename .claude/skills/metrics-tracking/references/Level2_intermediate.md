# Level 2: Intermediate

## 概要

リードタイム分析、複数チームでのメトリクス計測、ダッシュボード実装、Jira/GitHub Projects 連携を扱います。

scripts/ と assets/ の活用を前提とした運用を整理します。

## 前提条件

- Level 1 の内容を理解している
- ベロシティとバーンダウンを実際に計測した経験がある
- SKILL.md の適用範囲を説明できる

## リードタイム分析

### サイクルタイムとの違い

**リードタイム**:

- 定義: 課題作成から完了までの全期間
- 含まれる時間: バックログ待ち + 開発 + レビュー + テスト + デプロイ

**サイクルタイム**:

- 定義: 作業開始から完了までの期間
- 含まれる時間: 開発 + レビュー + テスト + デプロイ

**使い分け**:

- リードタイム: 顧客から見た待ち時間（ビジネス視点）
- サイクルタイム: チームの実作業時間（開発視点）

### リードタイムの内訳分析

リードタイムをフェーズごとに分解し、ボトルネックを特定する。

**典型的なフェーズ**:

1. バックログ待ち: 課題作成 → 作業開始
2. 開発: 作業開始 → PR作成
3. レビュー: PR作成 → レビュー承認
4. テスト: レビュー承認 → テスト完了
5. デプロイ: テスト完了 → 本番リリース

**分析方法**:

```
各フェーズの平均時間を算出:
バックログ待ち: 3日
開発: 2日
レビュー: 1日
テスト: 0.5日
デプロイ: 0.5日
---
合計リードタイム: 7日
```

**ボトルネック特定**:

- 最も時間がかかるフェーズを改善対象とする
- 例: バックログ待ちが3日 → スプリント計画の改善、WIP制限の導入

### 統計的な分析

平均値だけでなく、中央値、95パーセンタイルを計測する。

**なぜ必要か**:

- 平均値は外れ値に引っ張られやすい
- 中央値は典型的なケースを示す
- 95パーセンタイルは「ほぼ確実にこの時間内に完了する」保証値

**例**:

```
リードタイムデータ: 1, 2, 2, 3, 3, 3, 4, 5, 20日

平均値: 4.8日（20日の外れ値に引っ張られている）
中央値: 3日（典型的なケース）
95パーセンタイル: 20日（5%は20日かかる）
```

## ダッシュボード実装

### ダッシュボードの目的

- チーム全員が常に最新のメトリクスを確認できる
- 手動集計の負荷をゼロにする
- トレンドを一目で把握できる

### 推奨ツール

**軽量な開始**:

- Google Sheets + Apps Script: 無料、学習コスト低
- Jira ダッシュボード: Jira 利用チームなら追加コストなし

**本格的な実装**:

- Grafana: オープンソース、カスタマイズ性高
- Kibana: Elasticsearch と統合、ログとメトリクスを一元管理
- Tableau: BI ツール、複雑な分析に対応

### ダッシュボードの構成要素

**必須項目**:

1. ベロシティトレンド（過去6スプリント）
2. 現在スプリントのバーンダウンチャート
3. リードタイムの推移（週次）
4. 最終更新日時

**推奨項目**: 5. サイクルタイムの分布（ヒストグラム）6. フェーズ別時間の内訳（積み上げ棒グラフ）7. 異常値の一覧（リードタイム > 14日等）

### 自動更新の実装

**Jira + Google Sheets の例**:

1. Jira REST API でスプリントデータを取得
2. Google Apps Script で定期実行（毎朝9時等）
3. Sheets にデータを追記
4. グラフを自動更新

## Jira/GitHub Projects 連携

### Jira 連携パターン

**自動ラベル付け**:

- PR マージ時に Jira 課題を自動で「Done」に移動
- GitHub Actions で Jira API を呼び出す

**リードタイム自動計測**:

- Jira Automation で課題作成日と完了日を記録
- カスタムフィールドにリードタイム（日数）を自動計算

### GitHub Projects 連携パターン

**PR とイシューの紐付け**:

- PR 説明に `Closes #123` を記載
- PR マージ時にイシューを自動クローズ

**ラベルベースのメトリクス**:

- ラベル（`in-progress`, `in-review`, `done`）でフェーズを管理
- GitHub API でラベル変更履歴を取得し、フェーズ別時間を計算

## 複数チームでのメトリクス計測

### 課題

- チームごとにストーリーポイントの基準が異なる
- ベロシティの絶対値を比較すると誤解を招く

### 解決策

**正規化指標を使う**:

- スループット: 完了したストーリー数（ポイント不要）
- リードタイム: 時間なので比較可能
- デプロイ頻度: 回数なので比較可能

**チーム内比較に限定**:

- ベロシティは同一チームの時系列比較のみに使用
- 他チームとの比較には使わない

**組織全体のメトリクス**:

- 全チームのスループット合計
- 全チームのリードタイム中央値
- 組織のデプロイ頻度

## 実践手順

1. リードタイムの内訳を分析し、ボトルネックを特定する
2. ダッシュボードツールを選定し、基本的なグラフを作成する
3. Jira または GitHub と連携し、データ収集を自動化する
4. 週次でダッシュボードをレビューし、トレンドを確認する
5. `scripts/log_usage.mjs` で実行記録を残す
