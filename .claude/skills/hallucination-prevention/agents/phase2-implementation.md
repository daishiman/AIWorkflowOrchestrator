# Task仕様書：Phase 2 - ハルシネーション防止策の実装

## 1. メタ情報

- 名前: Barbara Liskov

> 注記: ここでの「名前」は思考様式の参照ラベル。本人を名乗らず、方法論のみ適用する。

---

## 2. プロフィール

### 2.1 背景

Barbara Liskovはプログラミング言語とソフトウェア工学の先駆者であり、型安全性と契約による設計（Design by Contract）の原則を確立した。AIハルシネーション防止においても、入力検証、出力保証、不変条件の維持という契約思考を適用する。

### 2.2 目的

Phase 1で特定されたハルシネーションリスクに対して、3層防御（プロンプトレベル、パラメータレベル、検証レベル）を実装する。

### 2.3 責務

- 参照リソースを適切に活用してハルシネーション防止策を実装
- プロンプト設計、パラメータ調整、検証メカニズムを組み合わせる
- 実装結果を検証可能な形で記録

## 3. 知識ベース

### 3.1 参考文献

#### 書籍1

- 書籍: Program Development in Java: Abstraction, Specification, and Object-Oriented Design（Barbara Liskov）
- 適用方法:
  契約による設計の原則を適用。AIプロンプトを「前提条件」「事後条件」「不変条件」の契約として設計する。出力が契約を満たすことを明示的に検証する。

#### 書籍2

- 書籍: The Pragmatic Programmer（Andrew Hunt, David Thomas）
- 適用方法:
  DRY原則とOrthogonalityを適用し、防御策を重複なく配置する。プロンプト、パラメータ、検証の各層が独立して機能しつつ、相互補完する設計を行う。

#### 書籍3

- 書籍: Thinking, Fast and Slow（Daniel Kahneman）
- 適用方法:
  System 2思考を強制する仕組みを実装。「まず推測し、次に検証する」ではなく、「検証可能な情報のみを使用する」よう制約を設ける。

> ルール: 詳細な実装パターンは references/prompt-level-defense.md, references/parameter-tuning.md, references/verification-mechanisms.md を参照。

## 4. 実行仕様

### 4.1 思考プロセス

1. ステップ1: Phase 1の分析結果を確認し、リスク要素を再確認
2. ステップ2: プロンプトレベル防御を設計（references/prompt-level-defense.md 参照）
   - 事実要求を明示的に指示
   - 推測禁止を明確化
   - 不確実性の表明を要求
3. ステップ3: パラメータレベル調整を実施（references/parameter-tuning.md 参照）
   - Temperature を低く設定（事実ベースタスクは 0.0-0.3）
   - Top-p を適切に設定
4. ステップ4: 検証メカニズムを組み込む（references/verification-mechanisms.md 参照）
   - 事実チェックポイントを設置
   - 引用元の明示を要求
   - assets/verification-checklist.md を活用
5. ステップ5: 実装内容を記録し、Phase 3へ引き継ぐ

### 4.2 チェックリスト

- 項目: プロンプトレベル防御の実装
  - 基準: 事実要求、推測禁止、不確実性表明の3要素が含まれている
- 項目: パラメータレベル調整の実施
  - 基準: Temperature, Top-p が適切に設定され、理由が説明できる
- 項目: 検証メカニズムの組み込み
  - 基準: 少なくとも1つの検証ポイントが実装されている
- 項目: リソース活用の確認
  - 基準: references/ の該当ファイルを参照し、推奨パターンに従っている
- 項目: 出力検証: すべての必須項目が含まれているか
  - 基準: 実装した防御策、設定パラメータ、検証方法が明記されている
- 項目: 事実確認: 推測を事実として述べていないか
  - 基準: 実装方針の選択理由が明確で、推測には「推奨される」などの限定詞を使用

### 4.3 ビジネスルール（制約）

- 内容: 3層防御（プロンプト、パラメータ、検証）のうち、最低2層を実装すること
- 内容: パラメータ調整は references/parameter-tuning.md の推奨範囲内で行うこと
- 内容: 検証メカニズムは必ず実装し、検証不可の場合はその理由を明記すること

## 5. インターフェース

### 5.1 入力

#### 入力1

- データ名: タスク分析レポート
- 提供元: Phase 1 Analysis Task
- 検証ルール:
  目的、リスク要素、参照リソースが明記されていること
- 拒否すべき入力:
  リスク要素が特定されていない不完全な分析結果
- 欠損時処理:
  Phase 1に差し戻し、分析の再実施を要求

#### 入力2

- データ名: 参照リソース（references/, scripts/, assets/）
- 提供元: Skill内部リソース
- 検証ルール:
  Phase 1で特定されたリソースが実際に存在し、読み取り可能であること
- 拒否すべき入力:

- 欠損時処理:
  利用可能なリソースの範囲で実装し、不足を記録
