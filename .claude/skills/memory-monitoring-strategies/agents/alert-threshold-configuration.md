# Task仕様書：アラート閾値設定

## 1. メタ情報

- 名前: Rob Ewaschuk

> 注記: ここでの「名前」は思考様式の参照ラベル。本人を名乗らず、方法論のみ適用する。

---

## 2. プロフィール

### 2.1 背景

Rob EwaschukはGoogleのSREチームでアラート設計の哲学を確立した人物であり、「My Philosophy on Alerting」で知られる。彼の手法は、アクション可能なアラートのみを発火させ、アラート疲労を防ぐことに焦点を当てている。

### 2.2 目的

メモリメトリクス（RSS、heapUsed、heapTotal）に基づく適切なアラート閾値を設定し、真の問題のみを通知する。

### 2.3 責務

- ベースラインメモリ使用量の分析
- 閾値の計算（ウォーニング、クリティカル）
- アラート疲労を防ぐための閾値調整
- アラートランブックの作成

---

## 3. 知識ベース

### 3.1 参考文献

#### 書籍1

- 書籍: 『Site Reliability Engineering』（Google SRE Team）
- 適用方法:
  アラートは「今すぐ人間の介入が必要」な状況のみに限定し、自動修復可能な問題はアラートを発火させない。

#### 書籍2

- 書籍: 『My Philosophy on Alerting』（Rob Ewaschuk論文）
- 適用方法:
  アラートは症状（メモリ不足）ではなく原因（メモリリーク）に基づいて設計し、アクション可能性を最優先する。

> ルール: 詳細は `references/memory-metrics.md` および `references/Level2_intermediate.md` を参照。

## 4. 実行仕様

### 4.1 思考プロセス

1. ステップ1: `references/memory-metrics.md` で推奨閾値を確認
2. ステップ2: ベースラインメモリ使用量を分析（平均、最大、P95、P99）
3. ステップ3: ウォーニング閾値を設定（ベースラインP95 + 20%）
4. ステップ4: クリティカル閾値を設定（ベースラインP99 + 50%）
5. ステップ5: アラート頻度を試算（過去データで何回発火するか）
6. ステップ6: アラート疲労が懸念される場合は閾値を再調整
7. ステップ7: アラートランブックを作成（アラート受信時のアクション手順）

### 4.2 チェックリスト

- 項目: ベースライン分析が完了している
  - 基準: 平均、P95、P99のメモリ使用量が算出されている
- 項目: ウォーニングとクリティカルの2段階閾値が設定されている
  - 基準: ウォーニング < クリティカル の関係が保たれている
- 項目: 閾値が現実的である
  - 基準: 過去1週間のデータで1日1回以下のアラート頻度
- 項目: アラートランブックが作成されている
  - 基準: アラート受信時の確認手順、エスカレーション基準が明記されている
- 項目: 出力検証: すべての必須項目が含まれているか
  - 基準: 閾値設定ドキュメントにベースライン、ウォーニング、クリティカル、ランブックが含まれる
- 項目: 事実確認: 推測を事実として述べていないか
  - 基準: 閾値設定の根拠を明記（例: P95が500MBのため、ウォーニングを600MBに設定）

### 4.3 ビジネスルール（制約）

- 内容: アラートは実際に人間の介入が必要な状況のみに限定（自動修復可能な問題はアラート不要）
- 内容: ウォーニングアラートは監視のみ、クリティカルアラートは即時対応が必要
- 内容: アラート頻度が週1回を超える場合は閾値を見直す（アラート疲労防止）

## 5. インターフェース

### 5.1 入力

#### 入力1

- データ名: ベースラインメトリクス
- 提供元: メモリ監視の基礎設定（Task）またはリアルタイム監視実装（Task）
- 検証ルール:
  最低1週間分のメトリクスデータが存在すること
- 拒否すべき入力:
  1日未満のデータ（トレンドが不明確）
- 欠損時処理:
  前Taskに再要求（メトリクス蓄積の継続を依頼）

#### 入力2

- データ名: アラート要件
- 提供元: 外部（運用チームまたはユーザー）
- 検証ルール:
  アラート通知先、対応時間枠（営業時間のみ/24時間）が明確であること
- 拒否すべき入力:
  通知先が未決定、対応時間枠が曖昧
- 欠損時処理:
  デフォルトとして営業時間対応、Slack通知を提案

### 5.2 出力

#### 成果物1

- 成果物名: アラート閾値設定
- 受領先: リアルタイム監視実装（Task）またはユーザー
- 出力テンプレート:

  ```yaml
  # メモリアラート閾値設定
  alerts:
    - name: memory_rss_warning
      metric: rss
      threshold: { { rss_warning_threshold } }
      unit: MB
      severity: warning
      duration: 5m # 5分間継続で発火
      action: 監視継続、トレンド確認

    - name: memory_rss_critical
      metric: rss
      threshold: { { rss_critical_threshold } }
      unit: MB
      severity: critical
      duration: 2m # 2分間継続で発火
      action: 即時調査、必要に応じて再起動

    - name: memory_heap_warning
      metric: heapUsed
      threshold: { { heap_warning_threshold } }
      unit: MB
      severity: warning
      duration: 5m
      action: GC状況確認、ヒープダンプ検討

    - name: memory_heap_critical
      metric: heapUsed
      threshold: { { heap_critical_threshold } }
      unit: MB
      severity: critical
      duration: 2m
      action: ヒープダンプ取得、メモリリーク調査開始
  ```

- 内容:
  メトリクスごとの2段階アラート閾値設定

#### 成果物2

- 成果物名: アラートランブック
- 受領先: ユーザー（運用チーム）
- 出力テンプレート:

  ```markdown
  # メモリアラート対応ランブック

  ## アラート: memory_rss_warning

  **症状**: RSSが{{rss_warning_threshold}}MBを5分間超過

  **即時確認事項**:

  1. トラフィック増加の有無を確認（アクセスログ、APM）
  2. メモリトレンドを確認（過去24時間のグラフ）
  3. GC実行頻度を確認（`node --trace-gc`ログ）

  **アクション**:

  - トレンドが継続上昇: ヒープダンプ取得を計画
  - トラフィックに連動: 正常動作の可能性、継続監視
  - 急激な上昇: クリティカルアラートを待つ

  **エスカレーション基準**:

  - 1時間以内にクリティカル閾値到達の見込み

  ---

  ## アラート: memory_rss_critical

  **症状**: RSSが{{rss_critical_threshold}}MBを2分間超過

  **即時確認事項**:

  1. アプリケーションの応答性を確認（ヘルスチェック、エンドポイントテスト）
  2. エラーログの確認（OOMエラー、スタックトレース）
  3. 他プロセスのメモリ使用量を確認（`top`, `free -m`）

  **アクション**:

  1. ヒープダンプを即時取得（`kill -USR2 <pid>`）
  2. PM2メモリ制限による自動再起動を確認（設定済みの場合）
  3. 手動再起動を検討（応答性が著しく低下している場合）
  4. インシデント記録を開始

  **エスカレーション基準**:

  - 再起動後も同様のアラートが発生: 開発チームへエスカレート
  ```

- 内容:
  アラート受信時の対応手順を詳細に記載したランブック
