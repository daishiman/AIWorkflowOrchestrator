# ロードマップ策定ガイド

## 概要

プロダクトロードマップは、製品の進化を時系列で示す戦略的計画。優先順位付けされたイニシアチブと大まかなタイムラインを可視化し、チームとステークホルダーの方向性を統一します。

## ロードマップの進化

### 従来型ロードマップ（避けるべき）

❌ **機能リスト型**:

```
Q1: 機能A、機能B、機能C
Q2: 機能D、機能E、機能F
Q3: 機能G、機能H、機能I
```

**問題点**:

- 機能に焦点が当たり、成果が見えない
- 柔軟性がない（変更が困難）
- ステークホルダーが機能リリースに固執

### 現代型ロードマップ（推奨）

✅ **アウトカム指向型**:

```
Q1: ユーザーオンボーディングの最適化
  目標: 完了率を60%→85%に向上
  主要施策: インタラクティブチュートリアル、プログレッシブディスクロージャー

Q2: エンゲージメントの深化
  目標: 週次リテンション30%→60%に向上
  主要施策: パーソナライゼーション、通知最適化
```

**利点**:

- 成果（Why）に焦点
- 柔軟性が高い（手段は変更可能）
- ステークホルダーが価値を理解しやすい

## ロードマップの種類

### 1. ビジョンロードマップ（1-3年）

**目的**: 長期的な方向性を示す

**構成**:

- 主要なテーマ/領域
- マイルストーン
- 戦略的目標

**例**:

```
Year 1: 個人ユーザー向けプロダクト確立
Year 2: チーム機能の追加
Year 3: エンタープライズ展開
```

### 2. 戦略ロードマップ（6-12ヶ月）

**目的**: OKR達成のための主要イニシアチブを計画

**構成**:

- 四半期ごとのテーマ
- 期待される成果
- 主要施策

**例**:

```
Q1: ユーザー獲得の加速
  成果: MAU 10K→25K
  施策: リファラルプログラム、SEO最適化

Q2: マネタイゼーション基盤
  成果: MRR $50K→$150K
  施策: 価格戦略見直し、エンタープライズプラン
```

### 3. リリースロードマップ（3-6ヶ月）

**目的**: 具体的な機能リリース計画

**構成**:

- スプリント/月単位
- リリース予定の機能
- 依存関係

**例**:

```
Sprint 1-2: ダッシュボード刷新（デザイン完了が前提）
Sprint 3-4: API統合機能
Sprint 5-6: モバイルアプリベータ版
```

## ロードマップ作成プロセス

### Step 1: インプットの収集

**必要な情報**:

1. **ビジョンとOKR**
   - プロダクトビジョン
   - 今四半期と次四半期のOKR

2. **データと洞察**
   - ユーザーフィードバック
   - プロダクトメトリクス
   - 市場調査
   - 競合分析

3. **制約条件**
   - 利用可能なリソース（人員、予算）
   - 技術的制約
   - 依存関係

4. **ステークホルダー要望**
   - 営業/マーケティングの要望
   - エグゼクティブの優先事項
   - カスタマーサクセスの洞察

### Step 2: イニシアチブの特定

**ブレインストーミング**:

- OKR達成のための施策を列挙
- ユーザー価値の高い改善を抽出
- 技術的負債の解消項目を特定

**イニシアチブフォーマット**:

```
イニシアチブ名: ユーザーオンボーディング最適化

目的: 新規ユーザーの価値実現を加速
成果指標: オンボーディング完了率 60%→85%
主要施策:
  - インタラクティブチュートリアル
  - プログレッシブディスクロージャー
  - コンテキストヘルプ
期間: 6-8週間
依存関係: デザインシステムv2完成
```

### Step 3: 優先順位付け

**フレームワーク: RICE**

```
RICE Score = (Reach × Impact × Confidence) / Effort
```

- **Reach（到達範囲）**: 何人のユーザーに影響するか（月間）
- **Impact（影響度）**: 各ユーザーへの影響（3=大、2=中、1=小、0.5=小さい）
- **Confidence（確信度）**: 成功の確信（100%=高、80%=中、50%=低）
- **Effort（工数）**: 人月単位の工数

**例**:

```
イニシアチブA: リファラルプログラム
  Reach: 10,000ユーザー
  Impact: 2（中程度の影響）
  Confidence: 80%
  Effort: 2人月
  RICE: (10,000 × 2 × 0.8) / 2 = 8,000

イニシアチブB: エンタープライズSSO
  Reach: 500ユーザー（エンタープライズ）
  Impact: 3（大きな影響）
  Confidence: 100%
  Effort: 4人月
  RICE: (500 × 3 × 1.0) / 4 = 375
```

リファラルプログラムの方が高スコア → 優先度が高い

**他の優先順位付け手法**:

- **WSJF（Weighted Shortest Job First）**: SAFe Agileで使用
- **Kano Model**: 顧客満足度に基づく分類
- **Value vs. Effort Matrix**: シンプルな2×2マトリックス

### Step 4: タイムライン設定

**原則**:

- 日付ではなく「順序」を重視
- バッファを含める（予期せぬ問題用）
- 依存関係を考慮

**タイムライン例**:

```
Now - Next - Later

Now（現在-6週間）:
  - ユーザーオンボーディング最適化
  - モバイルアプリUI改善

Next（6週間-3ヶ月）:
  - リファラルプログラム
  - API v2リリース

Later（3ヶ月以降）:
  - エンタープライズSSO
  - 高度な分析機能
```

### Step 5: 可視化

**推奨フォーマット**:

1. **テーマ型ロードマップ**

   ```
   Q1: Growth（成長）
     - リファラルプログラム
     - SEO最適化

   Q2: Monetization（収益化）
     - 価格戦略見直し
     - エンタープライズプラン
   ```

2. **Now-Next-Later**
   - 時間軸を曖昧にして柔軟性を確保

3. **OKR連動型**
   - 各イニシアチブをOKRに紐付け

**ツール**:

- ProductPlan
- Aha!
- Roadmunk
- Notion / Confluence（シンプルな場合）

## ステークホルダー別ロードマップ

### 経営陣向け

**焦点**:

- ビジネスゴールとの整合性
- 収益への影響
- 市場ポジショニング

**粒度**: 高レベル（テーマとマイルストーン）

**例**:

```
Q1-Q2: ユーザー基盤拡大
  目標: MAU 10K→50K
  収益影響: MRR +$100K見込み

Q3-Q4: エンタープライズ展開
  目標: 大企業顧客10社獲得
  収益影響: ARR +$500K見込み
```

### エンジニアリングチーム向け

**焦点**:

- 技術的依存関係
- 必要なスキルセット
- 技術的負債への対処

**粒度**: 詳細（機能レベル）

**例**:

```
Sprint 1-2:
  - ダッシュボード刷新（React移行）
  - API v2基盤整備

Sprint 3-4:
  - エンタープライズSSO実装
  - テストカバレッジ向上（60%→80%）
```

### 営業/マーケティング向け

**焦点**:

- 顧客に訴求できる機能
- 競合との差別化
- リリースタイミング

**粒度**: 中レベル（主要機能）

**例**:

```
Q1:
  - モバイルアプリベータ版（2月）
  - リファラルプログラム（3月）
  訴求ポイント: 場所を選ばないアクセス

Q2:
  - エンタープライズSSO（5月）
  - 高度な権限管理（6月）
  訴求ポイント: エンタープライズグレードのセキュリティ
```

## ロードマップの更新と維持

### 定期的なレビュー

**月次レビュー**:

- 進捗確認
- 優先順位の再評価
- 新たなインプットの反映

**四半期レビュー**:

- OKR結果に基づく大幅な見直し
- 次四半期の詳細計画
- リソース再配分

### 変更管理

**ロードマップ変更のトリガー**:

- 市場の大きな変化
- 重要な顧客フィードバック
- 技術的な発見（予想より困難/容易）
- リソースの変更（人員増減）

**変更プロセス**:

1. 変更提案と理由を文書化
2. ステークホルダーレビュー
3. 影響評価（他のイニシアチブへの影響）
4. 承認と公開
5. チームへの周知

## よくある落とし穴

### 1. 機能リストになる

❌ **悪い例**:

```
Q1: ダークモード、絵文字サポート、エクスポート機能
```

✅ **良い例**:

```
Q1: ユーザーエクスペリエンスの向上
  目標: ユーザー満足度70%→90%
  施策: カスタマイゼーション強化、アクセシビリティ改善
```

### 2. 詳細すぎる

ロードマップは「戦略的計画」であり、「実装計画」ではありません。

❌ 各機能のUIモックアップまで含める
✅ イニシアチブの目的と期待される成果を示す

### 3. 日付へのコミットメント

❌ "機能Xは5月15日リリース"
✅ "機能Xは Q2にリリース予定"

### 4. ステークホルダー不在

ロードマップは一方的な発表ではなく、対話を通じて作成すべきです。
