## ステークホルダー分析

### ステークホルダー分類

| カテゴリ   | 定義                           | 例                           |
| ---------- | ------------------------------ | ---------------------------- |
| プライマリ | 直接システムを使用する         | エンドユーザー、オペレーター |
| セカンダリ | システムの恩恵を間接的に受ける | マネージャー、レポート受領者 |
| サポート   | システムの運用・保守を担当     | 開発チーム、運用チーム       |
| スポンサー | 投資・意思決定の権限を持つ     | プロジェクトオーナー、経営層 |
| 規制者     | 法的・組織的制約を設定する     | 法務部門、コンプライアンス   |

### ステークホルダーマトリクス

| ステークホルダー | 関心事項   | 影響度   | 関与レベル               | コミュニケーション頻度 |
| ---------------- | ---------- | -------- | ------------------------ | ---------------------- |
| [名前/役職]      | [関心事項] | 高/中/低 | 承認者/協力者/情報受領者 | 毎日/週次/月次         |

### 影響度×関心度マトリクス

```
高
影  | 重要管理対象 | 密接に連携    |
響  | （満足維持） | （最大の注意）|
度  |-------------|--------------|
低  | 最小限の労力 | 常に情報提供  |
    | （監視のみ） | （関心維持）  |
    |-------------|--------------|
         低           高
           関心度
```

## 要件抽出技法

### インタビュー

| 種類     | 用途                     | 特徴                     |
| -------- | ------------------------ | ------------------------ |
| 構造化   | 定量的情報収集           | 事前質問リスト、比較容易 |
| 半構造化 | 深掘りと柔軟性のバランス | ガイド付き、脱線許容     |
| 非構造化 | 探索的情報収集           | 自由形式、新発見に有効   |

### ワークショップ

| 技法                         | 目的               | 参加者規模 |
| ---------------------------- | ------------------ | ---------- |
| ブレインストーミング         | アイデア創出       | 5-12人     |
| JAD（共同設計）              | 合意形成と詳細設計 | 5-20人     |
| ユーザーストーリーマッピング | 機能の優先度付け   | 5-15人     |

### ドキュメント分析

| 対象                   | 抽出可能な情報         |
| ---------------------- | ---------------------- |
| 既存システムマニュアル | 現行機能、操作フロー   |
| 業務フロー図           | 処理手順、判断ポイント |
| 法規制文書             | 遵守すべき制約         |
| 競合製品資料           | 市場期待、差別化要件   |

## レビュープロセス

### レビュー種別

| 種別                     | 目的             | 参加者             | 時間    |
| ------------------------ | ---------------- | ------------------ | ------- |
| ウォークスルー           | 知識共有、教育   | 作成者主導、少人数 | 30-60分 |
| テクニカルレビュー       | 技術的妥当性確認 | 技術専門家         | 1-2時間 |
| インスペクション         | 欠陥発見の最大化 | 訓練されたチーム   | 2-4時間 |
| ステークホルダーレビュー | 合意形成と承認   | 意思決定者、代表者 | 1-2時間 |

### レビュー実施フロー

```
1. 準備
   ├─ レビュー対象の配布（2-3日前）
   ├─ チェックリストの準備
   └─ 参加者の役割確認

2. 個人レビュー
   ├─ 各参加者が事前に確認
   └─ コメント・質問の準備

3. レビュー会議
   ├─ 作成者による概要説明（10分）
   ├─ 順次レビュー（ページ/セクション単位）
   ├─ 指摘事項の記録
   └─ アクションアイテムの確認

4. フォローアップ
   ├─ 指摘事項の対応
   ├─ 改訂版の作成
   └─ 再レビュー（必要に応じて）
```

### レビューコメント分類

| 分類 | 定義               | 対応優先度       |
| ---- | ------------------ | ---------------- |
| 重大 | 要件の欠落、矛盾   | 必須対応         |
| 主要 | 曖昧さ、検証不能   | 高優先度で対応   |
| 軽微 | 表記ゆれ、形式不備 | 可能な限り対応   |
| 質問 | 理解確認、確認事項 | 回答または明確化 |
| 提案 | 改善案、代替案     | 検討後判断       |

## 合意形成と承認

### 承認プロセス

```
1. ドラフト作成
   ↓
2. 内部レビュー（作成チーム）
   ↓
3. ステークホルダーレビュー
   ↓
4. フィードバック反映
   ↓
5. 最終確認レビュー
   ↓
6. 正式承認（署名/記録）
   ↓
7. ベースライン確定
```

### 承認記録テンプレート

```markdown
## 承認記録

| 承認者 | 役職   | 承認日 | 署名   | コメント       |
| ------ | ------ | ------ | ------ | -------------- |
| [名前] | [役職] | [日付] | [署名] | [任意コメント] |

### 承認条件

- [ ] 全必須レビュー完了
- [ ] 重大・主要コメント全対応
- [ ] 品質スコア80以上

### 次のアクション

- ベースライン登録
- 設計フェーズへのハンドオフ
```

## コンフリクト解決

### 対立パターンと解決策

| パターン         | 原因                   | 解決策                     |
| ---------------- | ---------------------- | -------------------------- |
| 機能の優先度対立 | 異なるビジネス目標     | MoSCoW法で客観的に評価     |
| リソース制約     | スコープと予算の不一致 | スコープ調整、フェーズ分割 |
| 技術的実現可能性 | 要件と技術の乖離       | プロトタイプ、技術検証     |
| 組織間の利害対立 | 部門間の優先度の違い   | エスカレーション、上位判断 |

### エスカレーションルール

1. **レベル1**: プロジェクトマネージャーによる調整
2. **レベル2**: ステアリングコミッティへの報告
3. **レベル3**: スポンサーによる最終判断

## 変更管理

### 変更要求プロセス

```
1. 変更要求の提出
   ├─ 変更内容の記述
   ├─ 変更理由の説明
   └─ 影響範囲の予備分析

2. 影響分析
   ├─ スコープへの影響
   ├─ スケジュールへの影響
   └─ コストへの影響

3. 変更審査
   ├─ 変更管理委員会（CCB）によるレビュー
   └─ 承認/却下/保留の決定

4. 実施（承認された場合）
   ├─ 要件ドキュメントの更新
   ├─ 追跡マトリクスの更新
   └─ ステークホルダーへの通知
```
