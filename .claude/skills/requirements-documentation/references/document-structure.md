## IEEE 830 SRS 標準構造

IEEE 830は、ソフトウェア要件仕様書（SRS）の標準構造を定義する。

### 必須セクション

| セクション    | 内容                                       | 重要度 |
| ------------- | ------------------------------------------ | ------ |
| 1. 序論       | 目的、スコープ、定義、参照文書             | 必須   |
| 2. 全体説明   | 製品パースペクティブ、機能、制約           | 必須   |
| 3. 具体的要求 | 機能要件、非機能要件、外部インターフェース | 必須   |
| 4. 付録       | 補足情報、モデル、インデックス             | 推奨   |

### セクション詳細

#### 序論セクション

```markdown
## 1. 序論

### 1.1 目的

[このドキュメントの目的と対象読者]

### 1.2 スコープ

[システムの範囲と限界]

### 1.3 定義・略語・頭字語

[用語集]

### 1.4 参照文書

[関連ドキュメント]

### 1.5 概要

[ドキュメント構成の説明]
```

#### 全体説明セクション

```markdown
## 2. 全体説明

### 2.1 製品パースペクティブ

[システムの位置づけ、他システムとの関係]

### 2.2 製品機能

[主要機能の概要]

### 2.3 ユーザー特性

[想定ユーザーの属性]

### 2.4 制約

[設計・実装の制約条件]

### 2.5 仮定と依存関係

[前提条件]
```

## 要件ID体系

### 命名規則

| 種別           | プレフィックス | 例      |
| -------------- | -------------- | ------- |
| 機能要件       | FR-            | FR-001  |
| 非機能要件     | NFR-           | NFR-001 |
| ユースケース   | UC-            | UC-001  |
| ビジネスルール | BR-            | BR-001  |
| 制約           | CON-           | CON-001 |

### ID付与ルール

1. **連番**: 3桁のゼロパディング（001, 002, ...）
2. **サブID**: ドット区切りで階層化（FR-001.1, FR-001.2）
3. **バージョン管理**: IDは変更しない（削除時も欠番維持）

## 機能要件の記述パターン

### 基本構造

```markdown
### FR-001: [機能名]

**優先度**: Must have | Should have | Could have | Won't have

**概要**:
[機能の簡潔な説明（1-2文）]

**詳細**:
[機能の詳細な説明]

**前提条件**:

- [実行前に満たすべき条件]

**入力**:
| 項目 | 型 | 必須 | 制約 | 例 |
|------|-----|------|------|-----|
| [項目名] | [型] | Yes/No | [制約] | [例] |

**出力**:
| 項目 | 型 | 制約 | 例 |
|------|-----|------|-----|
| [項目名] | [型] | [制約] | [例] |

**受入基準**:
[Given-When-Then形式]

**関連要件**: [他の要件へのリンク]
```

## 非機能要件カテゴリ

### NFR分類（ISO/IEC 25010準拠）

| カテゴリ       | サブカテゴリ                         | 例                       |
| -------------- | ------------------------------------ | ------------------------ |
| パフォーマンス | 応答時間、スループット、キャパシティ | API応答 < 200ms (95%ile) |
| セキュリティ   | 認証、認可、機密性、完全性           | OAuth 2.0認証必須        |
| 信頼性         | 可用性、障害耐性、回復性             | 可用性 99.9%             |
| 保守性         | モジュール性、再利用性、テスト可能性 | コードカバレッジ 80%以上 |
| 移植性         | 適応性、インストール性               | Docker対応必須           |
| ユーザビリティ | 学習性、操作性、アクセシビリティ     | WCAG 2.1 AA準拠          |

### NFR記述パターン

```markdown
### NFR-001: [カテゴリ名]

**カテゴリ**: [ISO/IEC 25010カテゴリ]

**要件**:
[非機能要件の記述]

**測定指標**:
| 指標 | 目標値 | 測定方法 | 測定タイミング |
|------|--------|---------|--------------|
| [指標名] | [具体的数値] | [測定手法] | [いつ測定] |

**優先度**: High | Medium | Low

**関連機能要件**: [FR-XXX]
```

## ユースケース記述形式

### Cockburn形式

```markdown
## UC-001: [ユースケース名]

**ID**: UC-001
**アクター**: [プライマリアクター]、[セカンダリアクター]
**ゴール**: [ユーザーが達成したいこと]

**事前条件**:

- [実行前に満たすべき状態]

**基本フロー**（正常系）:

1. [アクター]が[アクション]
2. システムが[応答]
3. ...

**代替フロー**（異常系・分岐）:

- 2a. [条件]の場合: [代替処理]

**例外フロー**（エラー）:

- E1. [エラー条件]: [エラー処理]

**事後条件**:

- [実行後の期待状態]

**関連要件**: [FR-XXX], [NFR-XXX]
```

## 受入基準（Given-When-Then）

### 形式

```gherkin
シナリオ: [シナリオ名]
  Given [前提条件]
  And [追加の前提条件]
  When [実行するアクション]
  And [追加のアクション]
  Then [期待される結果]
  And [追加の期待結果]
```

### 良い受入基準の特徴

| 特徴       | 説明                     | 例                                     |
| ---------- | ------------------------ | -------------------------------------- |
| 具体的     | 曖昧さがなく、明確       | ○ 「3秒以内」 ✕ 「速く」               |
| 測定可能   | 客観的に検証可能         | ○ 「エラーコード400」 ✕ 「適切に処理」 |
| 独立       | 他のシナリオに依存しない | 1シナリオで完結                        |
| テスト可能 | 自動テストに変換可能     | E2Eテストとして実装可能                |
