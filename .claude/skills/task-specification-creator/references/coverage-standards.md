## テスト数記載基準

Phase 7/9/10/12 でテスト数を記載する際は、以下の基準を遵守すること:

| ルール | 説明 |
| ------ | ---- |
| **実測値のみ使用** | `pnpm test` の実行結果から取得した実際の数値のみ記載する。推定値・概算値は使用しない |
| **実行コマンドを明記** | テスト数を取得したコマンド（例: `pnpm vitest run --reporter=verbose`）を成果物に記録する |
| **タイムスタンプを付与** | テスト実行日時を記録し、数値の鮮度を保証する |

> **注意**: テスト数は実装の進行に伴い変動する。Phase間で数値が異なる場合は、各Phase実行時点の実測値を記載し、差分の理由を明記すること。

## P41 Exemption: v8 Function Coverage の特例ルール

> **根拠**: Vitest の v8 カバレッジプロバイダは、インライン arrow function（例: `getAllowedWindows: () => [mainWindow]`）を独立した関数としてカウントする。セキュリティ検証用オプションオブジェクト内のコールバック等が実行されない場合、Function Coverage が大幅に低下する（P41: 44.44%まで低下した事例あり）。

### Exemption 適用条件

| 条件 | 説明 |
| --- | --- |
| v8 プロバイダ使用 | `coverage.provider: 'v8'` が設定されている |
| インラインコールバック | オプションオブジェクト内の arrow function がカウント対象 |
| セキュリティ検証用コールバック | `validateIpcSender` 等のセキュリティ関数のオプション |

### Exemption 適用時の運用

| 項目 | ルール |
| --- | --- |
| 自動 FAIL としない | Function Coverage 0% でも P41 該当箇所は exemption として記録 |
| ハンドラ単位カバレッジ | ファイル全体ではなくハンドラ単位で判定する（handler-scope coverage） |
| 記録必須 | Phase 7 成果物に「P41 exemption 適用: [対象関数名]」を明記 |
| コールバック検証推奨 | 可能な場合は `mock.calls[i][2].getAllowedWindows()` 等で明示的に検証 |

### handler-scope vs file-scope カバレッジの使い分け

| スコープ | 適用場面 | 判定基準 |
| --- | --- | --- |
| file-scope | 単一責務のファイル（1ハンドラ/1サービス） | ファイル全体のカバレッジ基準を適用 |
| handler-scope | 複数ハンドラを含むファイル（IPCハンドラ集約ファイル等） | ハンドラ単位でカバレッジを計測・判定 |

> **根拠**: TASK-10A-G / TASK-9A-B で、IPCハンドラ集約ファイルのファイル全体カバレッジが P41 により低下した。ハンドラ単位で計測することで、実装品質を正確に評価できる。

## 2段階テスト設計パターン

テスト拡充の効率化のため、Phase 4 と Phase 6 で役割を分離する:

| Phase | テスト内容 | 設計方針 |
| --- | --- | --- |
| Phase 4 | 正常系テスト（Happy Path） | 受け入れ基準から導出。基本動作の検証に集中 |
| Phase 6 | エッジケース・異常系テスト | Phase 7 カバレッジ計測結果をフィードバックとして追加 |

**フィードバックループ**:
```
Phase 4（正常系テスト作成）
  → Phase 5（実装 or モック調整）
    → Phase 6（Phase 7 結果を参照してエッジケース追加）
      → Phase 7（カバレッジ計測・判定）
        → 未達の場合: Phase 6 へ戻る
```

> **根拠**: TASK-10A-G で Phase 4 に正常系14件を集中配置し、Phase 6 でカバレッジ不足箇所を補完する設計が、テスト作成の効率とカバレッジ達成率の両方を改善した。
