# generate-unassigned-task

## 概要

レビューで発見された未対応課題や、スコープ外だが将来対応が必要なタスクを
「誰でも実行可能な粒度」でドキュメント化するエージェント。

## 起動タイミング

- Phase 7（最終レビューゲート）でMINOR/MAJOR判定された未対応項目がある場合
- Phase 8（手動テスト）で発見された改善点がスコープ外の場合
- Phase 9（ドキュメント更新）で追加タスクが発見された場合

## 入力

| 項目                   | 説明                                |
| ---------------------- | ----------------------------------- |
| 課題リスト             | レビュー/テストで発見された課題一覧 |
| 発見元Phase            | どのPhaseで発見されたか             |
| 元タスクのコンテキスト | 関連するタスク仕様書の情報          |

## 出力

| 成果物             | パス                                     |
| ------------------ | ---------------------------------------- |
| 未完了タスク指示書 | `docs/30-workflows/unassigned-task/*.md` |

---

## 処理フロー

```
課題リストを受け取る
    ↓
各課題を分析・分類
    ↓
タスクIDを生成
    ↓
テンプレートに基づいて指示書を生成
    ↓
品質チェックを実施
    ↓
ファイルを出力
```

---

## ステップ詳細

### Step 1: 課題の分析・分類

課題の内容を分析し、以下のカテゴリに分類する:

| 分類             | 判定基準                         |
| ---------------- | -------------------------------- |
| 要件             | 機能要件の追加・変更が必要       |
| 改善             | 既存機能の改善・拡張             |
| バグ修正         | 不具合の修正                     |
| リファクタリング | コード品質の改善（機能変更なし） |
| セキュリティ     | セキュリティ関連の対応           |
| パフォーマンス   | 性能改善                         |

### Step 2: タスクIDの生成

```
task-{{分類略称}}-{{機能名}}-{{連番}}
```

例:

- `task-req-auth-001` （要件: 認証機能）
- `task-imp-ui-002` （改善: UI）
- `task-sec-api-001` （セキュリティ: API）

### Step 3: テンプレートに基づく指示書生成

`assets/unassigned-task-template.md` を参照し、以下を埋める:

#### 必須項目

1. **メタ情報**: タスクID、分類、優先度、見積もり規模
2. **Why**: 背景、問題点、放置した場合の影響
3. **What**: 目的、最終ゴール、スコープ、成果物
4. **How**: 前提条件、依存タスク、推奨アプローチ
5. **実行手順**: Phase構成、Claude Codeコマンド
6. **完了条件**: 機能/品質/ドキュメント要件
7. **検証方法**: テストケース、検証手順
8. **リスク**: リスクと対策

### Step 4: コマンド選定

`.claude/commands/ai/command_list.md` を参照し、タスクに最適なコマンドを選定:

```
/ai:design-architecture  # アーキテクチャ設計が必要な場合
/ai:generate-unit-tests  # テスト作成が必要な場合
/ai:create-component     # UIコンポーネント作成の場合
/ai:security-audit       # セキュリティ対応の場合
# など
```

### Step 5: 品質チェック

以下の品質基準を満たすことを確認:

#### Why（なぜ必要か）

- [ ] 背景が明確に記述されている
- [ ] 問題点・課題が具体的に説明されている
- [ ] 放置した場合の影響が記載されている

#### What（何を達成するか）

- [ ] 目的が具体的に定義されている
- [ ] 最終ゴールが検証可能な形で記述されている
- [ ] スコープが明確に定義されている

#### How（どのように実行するか）

- [ ] Claude Codeスラッシュコマンドが選定されている
- [ ] 完了条件が検証可能な形で定義されている
- [ ] テストケース/検証方法が記載されている

### Step 6: ファイル出力

ファイル命名規則に従って出力:

| タスク種別       | ファイル名パターン                  |
| ---------------- | ----------------------------------- |
| 要件系           | `requirements-{{機能領域}}.md`      |
| 改善系           | `task-{{改善領域}}-improvements.md` |
| バグ修正         | `task-{{機能名}}-bugfix.md`         |
| リファクタリング | `task-{{対象}}-refactoring.md`      |
| セキュリティ     | `task-{{対象}}-security.md`         |
| パフォーマンス   | `task-{{対象}}-performance.md`      |

---

## 記録対象の判定基準

以下のいずれかに該当する場合に未完了タスクとして記録する:

1. Phase 7レビューでMINOR判定された未対応項目
2. Phase 8手動テストで発見されたがスコープ外の改善点
3. 将来的に必要となる拡張機能
4. 技術的負債として認識された項目
5. セキュリティ上の懸念（緊急性が低いもの）
6. パフォーマンス改善の余地

---

## 完了条件

- [ ] 全課題に対して指示書が作成されている
- [ ] 各指示書が品質チェックを通過している
- [ ] ファイルが正しい命名規則で配置されている
- [ ] 100人中100人が同じ理解で実行できる粒度で記述されている
