# 優先順位付けフレームワーク：基礎知識

## 概要

優先順位付けフレームワークは、限られたリソースで最大の価値を提供するための意思決定手法です。
本ドキュメントでは、基本的なフレームワークと選択基準を整理します。

## なぜ優先順位付けが必要か

### ビジネス上の課題

- **リソースの制約**：時間、予算、人材は常に限定的
- **機会費用**：ある施策を選ぶことは、別の施策を諦めることを意味する
- **ステークホルダーの期待**：複数の利害関係者からの要求を調整する必要がある
- **市場競争**：競合に対する差別化と迅速な意思決定が求められる

### 優先順位付けの効果

- 透明性の高い意思決定プロセスの確立
- ステークホルダー間の合意形成の促進
- ROI（投資対効果）の最大化
- チームの焦点を明確化し、生産性を向上

## 主要フレームワーク概要

### MoSCoW法

**適用シーン**：要件の分類と優先度決定、スプリント計画、リリース計画

**概要**：
4つのカテゴリで要件を分類する定性的手法。シンプルで理解しやすく、ステークホルダーとの合意形成に適している。

**4つのカテゴリ**：

1. **Must have（必須）**：プロジェクト成功に不可欠、これなしではリリース不可
   - 法的要件、ビジネス継続に必須の機能
   - 目安：全体の60%以下に抑える

2. **Should have（重要）**：重要だが必須ではない、代替手段がある
   - 価値は高いが、短期的には回避策で対応可能
   - 次のリリースで優先的に検討

3. **Could have（あれば望ましい）**：リソースに余裕があれば実装
   - Nice to have機能
   - 優先度は低いが、将来的な価値がある

4. **Won't have（今回はスコープ外）**：今回のスコープ外、将来検討の可能性
   - 明示的に除外することで、期待値を管理
   - バックログに記録し、将来の検討対象として残す

**利点**：

- シンプルで理解しやすい
- ステークホルダーとの対話を促進
- 迅速な分類が可能

**制約**：

- 定量的な比較が難しい
- Must haveが過剰に多くなりやすい
- 同じカテゴリ内の優先順位付けには別の手法が必要

**判断基準**：

```
Must have判定：
- これがなければリリースできないか？
- 法的・規制的に必須か？
- ビジネスの継続に不可欠か？

Should have判定：
- 回避策があるか？
- 次のリリースまで待てるか？
- 価値は高いが、短期的には代替可能か？

Could have判定：
- リソースに余裕がある場合のみ実装するか？
- 延期しても大きな問題はないか？

Won't have判定：
- 今回のスコープに含めるべきでないか？
- 将来の検討対象として残すべきか？
```

### Value vs Effort マトリックス

**適用シーン**：迅速な優先順位付け、初期段階のアイデア評価

**概要**：
価値（Value）と労力（Effort）の2軸でプロットし、4象限で分類する視覚的手法。

**4象限の分類**：

1. **Quick Wins（高価値・低労力）**：最優先で実装
   - すぐに成果が出る施策
   - チームのモチベーション向上にも寄与

2. **Big Bets（高価値・高労力）**：戦略的に投資
   - 長期的な価値が高い重要プロジェクト
   - リソース配分を慎重に検討

3. **Fill-ins（低価値・低労力）**：リソースに余裕があれば実施
   - 簡単に実装できるが、価値は限定的
   - アイドルタイムの活用

4. **Time Sinks（低価値・高労力）**：避けるべき
   - 投資対効果が低い
   - 本当に必要か再検討

**利点**：

- 視覚的でわかりやすい
- 迅速な判断が可能
- チーム全体での共通理解を促進

**制約**：

- 定量的な精度は低い
- 主観的な評価になりやすい
- 複数の評価軸を考慮できない

### Weighted Scoring（重み付けスコアリング）

**適用シーン**：複数基準の統合評価、カスタム評価基準を持つプロジェクト

**概要**：
複数の評価基準に重み付けをして総合スコアを算出する定量的手法。

**手順**：

1. **評価基準の定義**：
   - 顧客価値、ビジネス価値、技術的実現性、戦略的適合性など
   - 3〜7個の基準に絞る

2. **重み付けの設定**：
   - 各基準の重要度を百分率で設定（合計100%）
   - ステークホルダーと合意

3. **スコアリング**：
   - 各項目を1〜10点で評価
   - 重み付けを適用して総合スコアを算出

4. **ランキング**：
   - 総合スコアの高い順に優先順位を決定

**計算式**：

```
総合スコア = Σ(評価基準スコア × 重み)

例：
顧客価値: 8点 × 40% = 3.2
ビジネス価値: 6点 × 30% = 1.8
実現性: 7点 × 30% = 2.1
総合スコア: 7.1
```

**利点**：

- カスタマイズ可能な評価基準
- 定量的な比較が可能
- 複数の観点を統合できる

**制約**：

- 重み付けの設定が恣意的になりやすい
- スコアリングに時間がかかる
- 評価基準が多すぎると複雑化

## フレームワーク選択基準

### プロジェクト特性による選択

| 特性                         | 推奨フレームワーク | 理由                                         |
| ---------------------------- | ------------------ | -------------------------------------------- |
| 要件が多数、迅速な分類が必要 | MoSCoW法           | シンプルで理解しやすく、迅速な合意形成が可能 |
| 定量的な評価が求められる     | RICE Scoring       | データドリブンな意思決定、客観的な比較が可能 |
| 顧客満足度が重要             | Kano Model         | 顧客価値と満足度の関係を分析、戦略的投資判断 |
| 初期段階のアイデア評価       | Value vs Effort    | 視覚的でわかりやすく、迅速な判断が可能       |
| 複数の評価軸が必要           | Weighted Scoring   | カスタム基準での評価、複雑な意思決定に対応   |

### ステークホルダーによる選択

- **経営層**：ROI重視 → RICE Scoring、Value vs Effort
- **プロダクトマネージャー**：顧客価値重視 → Kano Model、MoSCoW法
- **開発チーム**：実装容易性重視 → Value vs Effort、MoSCoW法
- **営業・マーケティング**：市場競争力重視 → Kano Model、RICE Scoring

### 複数フレームワークの併用

**推奨パターン**：

1. **MoSCoW → RICE**：
   - MoSCoWでMust/Shouldを絞り込み
   - RICE ScoringでMust/Should内の優先順位を決定

2. **Kano → MoSCoW**：
   - Kano ModelでBasic/Performance/Excitementを分類
   - MoSCoWで実装タイミングを決定

3. **Value vs Effort → RICE**：
   - Value vs EffortでQuick Winsを特定
   - Big BetsについてはRICE Scoringで詳細評価

## ベストプラクティス

### すべきこと

- **ステークホルダーを巻き込む**：評価基準と結果を共有し、合意を得る
- **定期的に見直す**：市場や状況の変化に応じて優先順位を再評価
- **判断根拠を記録する**：なぜその優先順位にしたのかを文書化
- **定量と定性をバランスする**：数値だけでなく、背景や文脈も考慮
- **複数の視点で評価する**：顧客、ビジネス、技術の3つの観点

### 避けるべきこと

- **HiPPO（Highest Paid Person's Opinion）**：権限者の意見だけで決定しない
- **過度な精度への追求**：見積もりは不確実性を含むことを認識
- **一度決めたら変更しない**：新しい情報に基づいて柔軟に見直す
- **フレームワークへの盲従**：状況に応じてカスタマイズする
- **評価基準の曖昧さ**：明確な定義と判断基準を設定
