# 優先順位付けフレームワーク：実装パターン

## 概要

本ドキュメントでは、RICE ScoringとKano Modelの詳細、実装パターン、アンチパターン、複雑な意思決定シナリオでの活用方法を整理します。

## RICE Scoring

### 概要

Intercom社のSean McBrideが開発した定量的優先順位付けフレームワーク。
4つの要素（Reach、Impact、Confidence、Effort）を数値化し、スコアを算出して客観的に比較します。

### 適用シーン

- 複数の施策やフィーチャーを定量的に比較したい場合
- データドリブンな意思決定が求められる場合
- ROI（投資対効果）を明確にしたい場合
- ロードマップ策定や複数案の比較

### 4つの要素

#### 1. Reach（到達範囲）

**定義**：一定期間（通常は四半期）に影響を受けるユーザー数または取引数

**測定方法**：

- アクティブユーザー数（月間、四半期）
- トランザクション数（購入、登録など）
- ページビュー数
- APIコール数

**例**：

- 新機能が月間10,000人のアクティブユーザーに影響を与える場合、Reach = 10,000
- 四半期で30,000人に影響を与える場合、Reach = 30,000

**注意点**：

- 測定可能な現実的な数値を使用する
- 楽観的すぎる見積もりを避ける
- データソースを明記する（アナリティクス、ユーザー調査など）

#### 2. Impact（影響度）

**定義**：個別のユーザーや取引への影響度

**スケール**（0.25〜3の5段階）：

- **3 = Massive（大規模）**：ユーザー体験を劇的に改善、主要なペインポイントを解決
- **2 = High（高）**：重要な改善、明確な価値提供
- **1 = Medium（中）**：中程度の改善、目立つ変化
- **0.5 = Low（低）**：小さな改善、限定的な効果
- **0.25 = Minimal（最小）**：わずかな改善、ほとんど気づかれない

**判断基準**：

- ユーザーの主要なペインポイントを解決するか？
- コンバージョン率や満足度にどの程度影響するか？
- 競合との差別化にどれだけ寄与するか？

**例**：

- セキュリティ脆弱性の修正：Impact = 3（ユーザーの安全性に直結）
- チェックアウトプロセスの簡素化：Impact = 2（コンバージョン率向上）
- UIの色調整：Impact = 0.25（限定的な効果）

#### 3. Confidence（確信度）

**定義**：見積もりへの確信度（データの信頼性、実現可能性）

**スケール**（50%、80%、100%の3段階）：

- **100% = High**：確かなデータと経験に基づく見積もり
- **80% = Medium**：いくつかのデータがあり、合理的な見積もり
- **50% = Low**：データが不足、推測に基づく見積もり

**判断基準**：

- 過去の類似プロジェクトのデータがあるか？
- ユーザーリサーチやA/Bテストで検証済みか？
- 技術的な実現可能性は確認済みか？
- 工数見積もりに不確実性はないか？

**重要ルール**：

- Confidenceが50%を下回る場合、追加調査を実施してから評価する
- 不確実性が高い場合、プロトタイプやスパイクで検証する

#### 4. Effort（労力）

**定義**：実装に必要な工数（人月で測定）

**測定方法**：

- エンジニアリング工数（設計、開発、テスト、デプロイ）
- デザイン工数
- プロダクトマネジメント工数
- その他関連工数（インフラ、ドキュメント作成など）

**見積もりのコツ**：

- 楽観的見積もりではなく、現実的な見積もりを使用
- バッファを含める（予期せぬ問題への対応）
- 過去のプロジェクトデータを参考にする
- チーム全体で見積もりを検証する

**例**：

- 小規模な機能追加：0.5人月
- 中規模の新機能：2〜3人月
- 大規模なアーキテクチャ変更：10人月以上

### RICE Scoreの計算

**計算式**：

```
RICE Score = (Reach × Impact × Confidence) ÷ Effort
```

**例1**：チェックアウトプロセスの簡素化

```
Reach: 10,000人/四半期
Impact: 2（高）
Confidence: 80%（0.8）
Effort: 2人月

RICE Score = (10,000 × 2 × 0.8) ÷ 2 = 8,000
```

**例2**：新しいソーシャルログイン機能

```
Reach: 5,000人/四半期
Impact: 1（中）
Confidence: 100%（1.0）
Effort: 1人月

RICE Score = (5,000 × 1 × 1.0) ÷ 1 = 5,000
```

**例3**：UIの色調整

```
Reach: 20,000人/四半期
Impact: 0.25（最小）
Confidence: 100%（1.0）
Effort: 0.5人月

RICE Score = (20,000 × 0.25 × 1.0) ÷ 0.5 = 10,000
```

### 実装手順

1. **施策リストの作成**：評価対象の施策をすべてリストアップ
2. **データ収集**：Reach算出に必要なユーザーデータ、トラフィックデータを収集
3. **4要素の評価**：各施策についてReach、Impact、Confidence、Effortを評価
4. **スコア算出**：計算式に従ってRICE Scoreを算出
5. **ランキング**：スコアの高い順に並べ替え
6. **検証と調整**：結果が直感と大きく異なる場合、評価を再確認
7. **ドキュメント化**：評価根拠と前提条件を記録

### ベストプラクティス

**すべきこと**：

- 評価基準をチーム全体で統一する（特にImpactのスケール）
- 見積もりの前提条件を明記する
- 定期的に見直し、実績と比較して精度を向上させる
- ステークホルダーと評価プロセスを共有する

**避けるべきこと**：

- 過度な精度への追求（見積もりには不確実性があることを認識）
- Impactの主観的な評価（チーム内で基準を統一）
- Reachの楽観的な見積もり（現実的なデータを使用）
- 一度算出したスコアを絶対視（新しい情報に基づいて更新）

## Kano Model

### 概要

品質管理研究者Noriaki Kanoが開発した顧客満足度分析フレームワーク。
機能の実装有無と顧客満足度の関係を5つのカテゴリで分類し、戦略的な機能投資判断を支援します。

### 適用シーン

- 顧客満足度が重要な意思決定基準である場合
- 機能の戦略的価値を評価したい場合
- 競合との差別化ポイントを特定したい場合
- 要件定義や機能企画

### 5つのカテゴリ

#### 1. Basic（当たり前品質）

**定義**：ないと不満だが、あっても当然と思われる機能

**特徴**：

- テーブルステーク（競合も実装している標準機能）
- ないとユーザーは不満を感じる
- あっても満足度は上がらない
- 品質は高く保つ必要がある

**例**：

- ECサイトの検索機能
- モバイルアプリのログイン機能
- Webサイトのセキュリティ（SSL/TLS）
- 基本的なエラーハンドリング

**戦略**：

- **必ず実装する**：Basicがないと市場で競争できない
- **品質を最優先**：不具合や使いにくさは顧客満足度を大きく低下させる
- **過度な投資は避ける**：あっても満足度は上がらないため、最低限の品質を確保

#### 2. Performance（一元的品質）

**定義**：あるほど満足、ないほど不満を感じる機能

**特徴**：

- 満足度と実装度が比例する
- 競合との差別化ポイントになる
- ユーザーが意識的に評価する
- 投資対効果が明確

**例**：

- ECサイトの配送速度
- 検索エンジンの精度
- アプリの読み込み速度
- カスタマーサポートの応答時間

**戦略**：

- **戦略的に投資**：競合との差別化に活用
- **継続的改善**：ユーザーの期待値は上昇し続けるため、定期的な改善が必要
- **定量測定**：パフォーマンス指標を設定し、改善効果を測定

#### 3. Excitement（魅力的品質）

**定義**：あると感動するが、なくても仕方ないと思われる機能

**特徴**：

- ユーザーの期待を超える
- 競合にない独自機能
- 顧客満足度を大きく向上させる可能性
- リスクも高い（ユーザーに受け入れられない可能性）

**例**：

- Amazonの1-Click購入（登場時）
- Spotifyのパーソナライズドプレイリスト
- Tesla車の自動運転機能
- 予期せぬサプライズ機能

**戦略**：

- **実験的に実装**：MVPやプロトタイプで検証
- **リソースに余裕がある場合に限定**：Basic、Performanceを優先した上で投資
- **リスク管理**：失敗しても大きな損失にならない範囲で実験
- **時間経過でPerformanceに変化**：成功した場合、ユーザーの期待値が上がり、Performanceカテゴリに移行

#### 4. Indifferent（無関心品質）

**定義**：あってもなくても無関心な機能

**特徴**：

- ユーザーにとって価値がない
- 実装しても満足度は上がらない
- リソースの無駄遣い

**例**：

- ユーザーが使わない設定オプション
- 過度に複雑な機能
- ターゲット外のユーザー向け機能

**戦略**：

- **実装しない**：リソースを価値ある機能に集中
- **既存機能の場合は削除を検討**：メンテナンスコストを削減
- **ユーザー調査で検証**：本当にIndifferentかを確認

#### 5. Reverse（逆品質）

**定義**：あると不満、ないほうが良い機能

**特徴**：

- ユーザー体験を損なう
- 実装すると満足度が低下
- セグメントによって評価が異なる場合がある

**例**：

- 過剰な通知
- 強制的なチュートリアル
- 不要な登録ステップ
- 煩わしい広告

**戦略**：

- **実装を避ける**：リソースの無駄かつユーザー満足度を低下させる
- **既存機能の場合は即座に削除**：ユーザー体験を改善
- **セグメント別に検証**：一部のユーザーには価値がある可能性を確認

### 実装手順

1. **機能リストの作成**：評価対象の機能をすべてリストアップ
2. **ユーザー調査の設計**：アンケートやインタビューを設計
   - 機能的質問：「この機能があったらどう感じますか？」
   - 逆機能的質問：「この機能がなかったらどう感じますか？」
3. **データ収集**：ユーザー調査を実施（n ≥ 30推奨）
4. **カテゴリ判定**：回答をマトリックスで分析し、カテゴリを特定
5. **競合分析**：競合製品との比較でBasic機能を確認
6. **投資優先度の決定**：Basic → Performance → Excitementの順に優先度を設定
7. **ドキュメント化**：分類結果と投資戦略を記録

### ベストプラクティス

**すべきこと**：

- Basic機能の品質を最優先する
- Performanceで競合と差別化する
- Excitementは実験的に実装し、リスクを管理する
- 定期的に再評価する（時間経過でカテゴリは変化する）
- ユーザーセグメント別に評価する

**避けるべきこと**：

- Basic機能の軽視（テーブルステークを欠くと市場で競争できない）
- Excitementへの過度な投資（Basic、Performanceを犠牲にする）
- Indifferent、Reverseの実装（リソースの無駄）
- 一度の調査結果を絶対視（継続的な検証が必要）

## 複数フレームワークの組み合わせパターン

### パターン1：MoSCoW → RICE

**目的**：大量の要件を効率的に優先順位付け

**手順**：

1. MoSCoW法でMust、Shouldを絞り込む（Won'tを除外）
2. Must、Should内の項目をRICE Scoringで定量評価
3. スコアの高い順に実装順序を決定

**利点**：

- 迅速にスコープを絞り込める
- 定量的な根拠で優先順位を決定できる

**適用シーン**：

- スプリント計画
- リリース計画

### パターン2：Kano → MoSCoW

**目的**：顧客満足度を考慮した戦略的優先順位付け

**手順**：

1. Kano ModelでBasic、Performance、Excitementを分類
2. Basic機能をMustに、Performance機能をShould、Excitementを Couldに対応付け
3. MoSCoWで実装タイミングを決定

**利点**：

- 顧客満足度と実装タイミングを統合できる
- 戦略的な投資判断が可能

**適用シーン**：

- プロダクトロードマップ策定
- 機能企画

### パターン3：Value vs Effort → RICE → 実装

**目的**：段階的な優先順位付け

**手順**：

1. Value vs EffortでQuick Winsを特定し、即座に実装
2. Big BetsについてRICE Scoringで詳細評価
3. スコアに基づいて実装順序を決定

**利点**：

- Quick Winsで早期に成果を出せる
- 複雑な意思決定にリソースを集中できる

**適用シーン**：

- プロジェクト開始時
- 複数の大規模施策の比較

### パターン4：Kano + RICE の統合評価

**目的**：顧客満足度とROIを両立

**手順**：

1. Kano ModelでカテゴリとImpactを評価
2. RICE ScoringでReach、Confidence、Effortを評価
3. 両方のスコアを組み合わせて総合評価

**利点**：

- 顧客価値とビジネス価値を統合できる
- 多角的な評価が可能

**適用シーン**：

- 戦略的な機能投資判断
- 複雑なプロダクト意思決定

## アンチパターン

### HiPPO（Highest Paid Person's Opinion）

**問題**：権限者の意見だけで優先順位を決定する

**影響**：

- データや顧客価値が無視される
- チームのモチベーション低下
- 誤った意思決定のリスク

**対策**：

- 客観的なフレームワークを導入し、評価基準を明確にする
- データに基づく議論を促進
- ステークホルダー全員が意見を表明できる環境を作る

### Feature Creep（機能の肥大化）

**問題**：優先順位を明確にせず、すべての要望を受け入れる

**影響**：

- リソースの分散
- リリースの遅延
- 品質の低下

**対策**：

- MoSCoW法でWon't haveを明確にする
- スコープを厳格に管理
- ステークホルダーと優先順位で合意

### Analysis Paralysis（分析麻痺）

**問題**：完璧な評価を求めすぎて、意思決定が遅延する

**影響**：

- 市場機会の損失
- チームの生産性低下
- 競合に先を越される

**対策**：

- 適切な精度で評価を完了する（完璧を求めない）
- タイムボックスを設定（例：評価に2週間以内）
- 不確実性を受け入れ、後で調整する

### Sunk Cost Fallacy（サンクコスト誤謬）

**問題**：既に投資した施策を、優先順位が低くても継続する

**影響**：

- 非効率なリソース配分
- 機会費用の損失
- プロジェクトの失敗

**対策**：

- 定期的に優先順位を見直す
- 過去の投資ではなく、将来の価値で評価
- ピボットや中止の判断を恐れない

### One-Size-Fits-All（画一的アプローチ）

**問題**：すべてのプロジェクトに同じフレームワークを適用する

**影響**：

- 不適切な評価基準
- 過度な負担（小規模プロジェクトに重厚なフレームワーク）
- 形骸化（形式的な運用）

**対策**：

- プロジェクトの特性に応じてフレームワークを選択
- 必要に応じてカスタマイズ
- シンプルさを保つ
