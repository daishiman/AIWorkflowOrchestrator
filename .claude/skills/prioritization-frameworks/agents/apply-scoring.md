# Task仕様書：スコアリング適用と評価

## 1. Trigger

```
You are applying a prioritization framework to score and rank features or requirements.
Consider: framework characteristics, evaluation criteria, stakeholder expectations, and data availability.
```

## 2. Context

### 目的

選択したフレームワーク（MoSCoW、RICE、Kano Modelなど）を適用して、要件や施策を評価し、優先順位付けを実施する。

### 背景

フレームワークの選択が完了した後、実際に評価基準を定義し、各項目をスコアリングして優先順位を決定する必要がある。
各フレームワークには固有の評価軸と手順があり、それらを正しく適用することで客観的な優先順位付けが可能になる。

### 対象ユーザー

- プロダクトマネージャー
- プロジェクトリーダー
- 開発チーム

### 前提条件

- 適用するフレームワークが選択されている（select-framework.mdの完了）
- 評価対象の要件・施策リストが定義されている
- 必要なデータ（ユーザー数、リソース情報など）が入手可能

### 参照リソース

- `references/basics.md`：MoSCoW法、Value vs Effort、Weighted Scoringの詳細
- `references/patterns.md`：RICE Scoring、Kano Modelの詳細、実装パターン
- `assets/moscow-template.md`：MoSCoW分類結果テンプレート
- `assets/rice-scoring-template.md`：RICE Scoreランキングテンプレート
- `assets/kano-model-template.md`：Kanoカテゴリ分類テンプレート

### 制約・注意事項

- フレームワークの評価基準を厳格に適用する
- 主観的な評価を避け、データに基づく判断を優先する
- ステークホルダーと評価基準で合意を得る
- 評価根拠を明確に記録する

## 3. Instructions

### Step 1: 評価基準の定義

**目的**：選択したフレームワークの評価基準を具体化し、チーム全体で統一する

**実行内容**：

1. 適用するフレームワークの評価基準を確認
   - **MoSCoW法**：Must/Should/Could/Won'tの判断基準（`references/basics.md`参照）
   - **RICE Scoring**：Reach、Impact、Confidence、Effortの定義（`references/patterns.md`参照）
   - **Kano Model**：Basic/Performance/Excitement/Indifferent/Reverseの判定基準（`references/patterns.md`参照）
   - **Value vs Effort**：価値と労力の評価軸（`references/basics.md`参照）
   - **Weighted Scoring**：カスタム評価基準と重み付け（`references/basics.md`参照）

2. チーム全体で評価基準を共有し、解釈を統一
   - 評価スケールの定義（例：Impactの0.25〜3のスケール）
   - 判断例の共有（過去の評価事例を参考）
   - 曖昧な基準の明確化

3. 評価に必要なデータソースを特定
   - ユーザーデータ（アクティブユーザー数、セグメント分布など）
   - リソース情報（開発者数、稼働率など）
   - 競合分析データ（市場調査、ユーザー評価など）

**入力**：

- フレームワーク選択結果（select-framework.mdから）
- 要件・施策リスト

**出力**：

- 評価基準定義書（Markdown形式）
- 必要データリスト

**判断基準**：

- 評価基準が明確に定義されているか
- チーム全体で評価基準の解釈が統一されているか
- 必要なデータソースが特定されているか

### Step 2: データ収集と前提条件の整理

**目的**：評価に必要なデータを収集し、前提条件を明確化する

**実行内容**：

1. 各フレームワークに応じたデータを収集
   - **MoSCoW法**：ビジネス要件、法的要件、ステークホルダーの期待値
   - **RICE Scoring**：アクティブユーザー数、トラフィックデータ、工数見積もり
   - **Kano Model**：ユーザー調査データ（n ≥ 30推奨）、競合機能分析
   - **Value vs Effort**：価値見積もり（ROI、ビジネスインパクト）、工数見積もり
   - **Weighted Scoring**：各評価基準に対応するデータ

2. データの信頼性と有効期限を確認
   - 古いデータ（3〜6ヶ月以上前）は更新を検討
   - サンプル数不足のデータは追加調査を実施
   - データソースを明記（アナリティクス、ユーザー調査など）

3. 前提条件と制約を文書化
   - 評価期間（例：四半期、半期）
   - リソース制約（予算、人員、期限）
   - 技術的制約（インフラ、スキルセット）

**入力**：

- 評価基準定義書（Step 1から）
- 必要データリスト（Step 1から）

**出力**：

- 収集データまとめ（データソース、信頼性、有効期限を含む）
- 前提条件・制約リスト

**判断基準**：

- 必要なデータがすべて収集されているか
- データの信頼性が確認されているか
- 前提条件と制約が明確に文書化されているか

### Step 3: 評価の実施

**目的**：定義した基準に従って各項目を評価する

**実行内容**：

1. フレームワーク別の評価を実施

#### MoSCoW法の場合

1. 各要件について4つの判断基準を適用（`references/basics.md`参照）
   - Must have：リリースに不可欠か？
   - Should have：回避策があるか？
   - Could have：リソースに余裕があれば実装するか？
   - Won't have：今回のスコープ外か？

2. 分類結果を`assets/moscow-template.md`に記録
3. Must haveが全体の60%を超える場合、再評価を検討

#### RICE Scoringの場合

1. 各施策について4要素を評価（`references/patterns.md`参照）
   - Reach：一定期間に影響を受けるユーザー数
   - Impact：個別ユーザーへの影響度（0.25/0.5/1/2/3）
   - Confidence：見積もりへの確信度（50%/80%/100%）
   - Effort：実装に必要な工数（人月）

2. RICE Score = (Reach × Impact × Confidence) ÷ Effort を算出
3. スコアの高い順にランク付け
4. 結果を`assets/rice-scoring-template.md`に記録

#### Kano Modelの場合

1. ユーザー調査を実施（機能的質問と逆機能的質問）
2. 回答をマトリックスで分析し、5カテゴリに分類（`references/patterns.md`参照）
   - Basic：ないと不満、あっても当然
   - Performance：あるほど満足、ないほど不満
   - Excitement：あると感動、なくても仕方ない
   - Indifferent：あってもなくても無関心
   - Reverse：あると不満、ないほうが良い

3. 競合分析でBasic機能を確認
4. 投資優先度を決定（Basic → Performance → Excitement）
5. 結果を`assets/kano-model-template.md`に記録

#### Value vs Effortの場合

1. 各項目を価値と労力の2軸で評価
2. 4象限にプロット
   - Quick Wins（高価値・低労力）：最優先
   - Big Bets（高価値・高労力）：戦略的投資
   - Fill-ins（低価値・低労力）：リソース余裕時
   - Time Sinks（低価値・高労力）：避ける

3. 視覚的なマトリックスを作成

#### Weighted Scoringの場合

1. 各項目を評価基準でスコアリング（1〜10点）
2. 重み付けを適用して総合スコアを算出
3. 総合スコアの高い順にランク付け

**入力**：

- 収集データまとめ（Step 2から）
- 前提条件・制約リスト（Step 2から）
- 評価対象の要件・施策リスト

**出力**：

- 評価結果（フレームワーク別のテンプレートを使用）
- スコア算出の詳細記録（計算過程、前提条件）

**判断基準**：

- すべての項目が評価されているか
- 評価基準が一貫して適用されているか
- 評価根拠が記録されているか

### Step 4: 結果の検証と調整

**目的**：評価結果の妥当性を検証し、必要に応じて調整する

**実行内容**：

1. 結果の一貫性を確認
   - 直感と大きく異なる結果がないか確認
   - 異なる場合、評価基準や前提条件を再確認
   - 評価の見落としや誤りをチェック

2. 複数フレームワークの結果を比較（該当する場合）
   - 異なるフレームワークで大きく異なる結果が出た場合、理由を分析
   - 各フレームワークの強みを活かして統合評価を検討

3. ステークホルダーと評価結果を共有
   - 評価プロセスと基準を説明
   - 異論や懸念事項を記録
   - 必要に応じて評価を調整

4. 見直しのタイミングを設定
   - 定期的な再評価スケジュール（例：四半期ごと）
   - 再評価のトリガー（市場変化、新情報の入手など）

**入力**：

- 評価結果（Step 3から）
- ステークホルダーのフィードバック

**出力**：

- 検証済み評価結果
- 調整記録（変更理由を含む）
- 再評価スケジュール

**判断基準**：

- 評価結果が妥当であるか
- ステークホルダーの合意が得られているか
- 見直しのタイミングが設定されているか

### Step 5: ドキュメント化と共有

**目的**：評価結果と判断根拠を文書化し、関係者全員に共有する

**実行内容**：

1. 最終的な優先順位リストを作成
   - フレームワーク別のテンプレートを使用
   - スコア、ランク、カテゴリを明記
   - 実装順序と予定タイミングを記載

2. 評価プロセスと根拠を記録
   - 使用したフレームワークと選択理由
   - 評価基準と判断基準
   - 前提条件と制約
   - データソースと信頼性
   - ステークホルダーの合意記録

3. 関係者全員に共有
   - 優先順位リストをプロジェクトドキュメントに保存
   - ステークホルダーに通知
   - 開発チームに実装順序を伝達

4. 次のステップを定義
   - 実装計画の策定
   - リソース配分の調整
   - 進捗確認の方法

**入力**：

- 検証済み評価結果（Step 4から）
- 調整記録（Step 4から）

**出力**：

- 最終優先順位リスト
- 評価プロセス記録
- 実装計画（概要）

**判断基準**：

- すべての成果物が作成されているか
- 関係者全員に共有されているか
- 次のステップが明確に定義されているか

### エラーハンドリング

#### エラー1：データ不足

**検出条件**：評価に必要なデータが入手できない

**対処方法**：

- Confidence（RICE Scoring）を50%に設定し、データ不足を明記
- 追加調査を実施してから再評価
- 前提条件を仮定し、ステークホルダーに確認を求める

#### エラー2：評価基準の解釈不一致

**検出条件**：チーム内で評価結果に大きな差がある

**対処方法**：

- 評価基準を再確認し、解釈を統一
- 評価例を共有し、キャリブレーションを実施
- 合議で評価を決定

#### エラー3：ステークホルダーの異論

**検出条件**：評価結果に対して異論がある

**対処方法**：

- 異論の理由を詳しく聞く
- 評価基準や前提条件を再確認
- 必要に応じて再評価を実施
- 合意形成のためのワークショップを開催

#### エラー4：直感と大きく異なる結果

**検出条件**：評価結果が直感や経験と大きく異なる

**対処方法**：

- 評価基準や前提条件を再確認
- データの正確性を検証
- 複数のフレームワークで評価して比較
- 必要に応じて評価を調整
