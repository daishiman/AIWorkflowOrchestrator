# Task仕様書：優先順位検証

## 1. Trigger

```
You are validating prioritization results to ensure accuracy, stakeholder alignment, and actionability.
Verify scoring consistency, gather consensus, and establish review cycles.
```

## 2. Context

### 目的

優先順位付け結果の妥当性を検証し、ステークホルダーとの合意を形成し、
継続的な見直しプロセスを確立する。

### 背景

優先順位付けは一度決めたら終わりではなく、プロジェクトの進行や状況変化に応じて
定期的に見直す必要がある。検証プロセスでは、スコアリングの一貫性、
ステークホルダーの合意、実行可能性を確認する。

### 対象ユーザー

- プロダクトマネージャー
- プロジェクトリーダー
- ステークホルダー全体

### 前提条件

- スコアリングが完了している
- 優先順位リストが作成されている
- 判断理由が文書化されている

### 参照リソース

- `../references/basics.md`: 基本的な検証観点
- `../references/patterns.md`: 高度な検証パターン
- `../scripts/validate-skill.mjs`: スキル構造検証スクリプト
- 『Inspired』（Marty Cagan）: プロダクト価値の最大化
- 『The Pragmatic Programmer』（Andrew Hunt, David Thomas）: 実践的改善

### 制約・注意事項

- 検証は客観的データに基づく
- ステークホルダーの意見を平等に扱う
- 変更理由を明確に記録する
- 政治的圧力に屈しない

## 3. Instructions

### Step 1: スコアリング一貫性の検証

**目的**: スコアリングが評価基準に従って一貫して適用されているか確認

**実行内容**:

1. すべての項目が評価されているか確認
2. 評価基準が一貫して適用されているか確認
   - **MoSCoW法**: 判断基準に従ってカテゴリ分類されているか
   - **RICE Scoring**: 4要素がすべて定義範囲内か
   - **Kano Model**: 顧客満足度データに基づいて分類されているか
3. 類似項目のスコアが一貫しているか確認
4. 外れ値や異常なスコアを特定し、再評価の必要性を判断

**入力**:

- スコアリング結果
- 評価基準定義書

**出力**:

- 一貫性検証レポート（問題点と推奨アクションを含む）

**判断基準**:

- すべての項目が評価されているか
- 評価基準が一貫しているか
- 外れ値が説明されているか

### Step 2: データ品質の検証

**目的**: スコアリングに使用したデータの品質と信頼性を確認

**実行内容**:

1. データソースを確認
   - **RICE Scoring**: ユーザー数、アナリティクスデータの新しさと正確性
   - **Kano Model**: ユーザー調査のサンプル数と代表性
2. データの欠損や古さを識別
3. 前提条件と仮定を確認
4. Confidenceレベルが適切か確認（RICEの場合）
5. 必要に応じてデータ更新や追加調査を推奨

**入力**:

- スコアリング結果
- データソース情報

**出力**:

- データ品質レポート（信頼性評価と改善推奨を含む）

**判断基準**:

- データが最新か（3ヶ月以内）
- サンプル数が十分か（n >= 30）
- 前提条件が明確か

### Step 3: ステークホルダー合意の形成

**目的**: ステークホルダー全員から優先順位への合意を得る

**実行内容**:

1. 優先順位付け結果をステークホルダーに提示
2. 各ステークホルダーの意見と懸念を収集
3. 異論がある場合、その根拠を確認
4. 必要に応じて評価基準や前提条件を調整
5. 合意形成のための議論をファシリテート
6. 最終的な合意を文書化

**入力**:

- 優先順位付けレポート
- ステークホルダーリスト

**出力**:

- ステークホルダー合意記録（意見、調整内容、合意日時を含む）

**判断基準**:

- すべてのステークホルダーから意見が得られたか
- 異論が解決されたか
- 合意が文書化されているか

### Step 4: 実行可能性の検証

**目的**: 優先順位に従った実行が現実的か確認

**実行内容**:

1. 上位優先項目の実行計画を確認
   - リソース（人員、予算、時間）が確保できるか
   - 技術的実現可能性
   - 依存関係や制約
2. ロードマップやスプリント計画との整合性を確認
3. リスクと軽減策を識別
4. 必要に応じて優先順位を微調整
5. 実行計画を策定

**入力**:

- 優先順位リスト
- リソース情報
- プロジェクト計画

**出力**:

- 実行可能性レポート（リスク、制約、実行計画を含む）

**判断基準**:

- リソースが確保できるか
- 技術的に実現可能か
- 依存関係が解決されているか

### Step 5: 継続的見直しプロセスの確立

**目的**: 優先順位を定期的に見直すプロセスを確立

**実行内容**:

1. 見直しサイクルを設定
   - スプリント開始時（2週間ごと）
   - 四半期開始時
   - 重要なマイルストーン達成時
2. 見直しトリガーを定義
   - 市場状況の変化
   - ユーザーフィードバック
   - リソース変更
   - 技術的制約の発生
3. 見直しプロセスを文書化
4. 責任者と実施方法を明確化
5. `../scripts/log_usage.mjs` で記録を保存

**入力**:

- プロジェクト計画
- ステークホルダー合意記録

**出力**:

- 見直しプロセス文書（サイクル、トリガー、責任者、手順を含む）

**判断基準**:

- 見直しサイクルが設定されているか
- トリガーが明確か
- 責任者が割り当てられているか

### エラーハンドリング

#### エラー1: スコアリング不一貫

**検出条件**: 類似項目のスコアが大きく異なる

**対処方法**: 評価基準を再確認し、不一貫な項目を再評価。

#### エラー2: データ品質不足

**検出条件**: データが古い、サンプル数不足、バイアスが大きい

**対処方法**: Confidenceを50%に設定し、追加調査を推奨。データ不足を明記。

#### エラー3: ステークホルダー不合意

**検出条件**: 重要なステークホルダーが優先順位に異論を持つ

**対処方法**: 異論の根拠を確認し、評価基準や前提条件を再検討。必要に応じて再スコアリング。

#### エラー4: 実行不可能

**検出条件**: 上位優先項目のリソースが確保できない、技術的制約がある

**対処方法**: 制約を明確化し、実行可能な範囲で優先順位を調整。

#### エラー5: 見直しプロセス未定義

**検出条件**: 継続的見直しプロセスが設定されていない

**対処方法**: デフォルトサイクル（スプリント開始時）を設定し、ステークホルダーに確認。
