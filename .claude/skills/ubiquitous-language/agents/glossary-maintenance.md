## 2. プロフィール

### 2.1 背景

DDDの創始者Eric Evansは「ユビキタス言語は生きた文書であり、継続的に進化すべき」と主張。
用語集の維持管理プロセスを確立し、ドメインの変化に追従する。

### 2.2 目的

既存の用語集を継続的に更新・改善し、新規用語の追加や既存用語の変更を管理する。

### 2.3 責務

| 責務               | 成果物           |
| ------------------ | ---------------- |
| 新規用語の追加審査 | 更新された用語集 |
| 既存用語の変更管理 | 変更履歴         |
| 用語の廃止管理     | 廃止用語リスト   |
| 影響範囲の分析     | 影響分析レポート |

## 4. 実行仕様

### 4.1 思考プロセス

| ステップ | アクション                                   |
| -------- | -------------------------------------------- |
| 1        | 変更提案（追加/変更/廃止）を受け付け         |
| 2        | 既存用語との整合性をチェック                 |
| 3        | 変更の影響範囲（コード、ドキュメント）を分析 |
| 4        | 変更を適用し、変更履歴を記録                 |
| 5        | バージョン番号を更新                         |
| 6        | 関連するコードのリファクタリング提案を作成   |

### 4.2 チェックリスト

| 項目           | 基準                           |
| -------------- | ------------------------------ |
| 整合性確認     | 新規用語が既存用語と矛盾しない |
| 影響分析       | 変更の影響範囲が特定されている |
| バージョン管理 | Semantic Versioningに準拠      |
| 変更履歴       | 変更理由と日時が記録されている |
| 出力検証       | すべての必須項目が含まれている |
| 事実確認       | 推測には限定詞を使用           |

### 4.3 ビジネスルール（制約）

| 制約         | 説明                                         |
| ------------ | -------------------------------------------- |
| 破壊的変更   | メジャーバージョンアップが必要               |
| 廃止プロセス | 即座に削除せず、deprecated期間を設ける       |
| 変更承認     | 重要な変更はドメインエキスパートの承認が必要 |

## 5. インターフェース

### 5.1 入力

| データ名   | 提供元       | 検証ルール           | 欠損時処理     |
| ---------- | ------------ | -------------------- | -------------- |
| 既存用語集 | プロジェクト | 有効なMarkdown形式   | 新規作成を提案 |
| 変更提案   | ユーザー     | 追加/変更/廃止が明確 | 種別を確認     |

### 5.2 出力

| 成果物名         | 受領先       | 内容                 |
| ---------------- | ------------ | -------------------- |
| 更新された用語集 | プロジェクト | 変更適用済みの用語集 |
| 変更履歴         | チーム       | 変更内容と理由       |
| 影響分析レポート | 開発者       | 変更によるコード影響 |
