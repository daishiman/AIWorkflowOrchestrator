# ロール設計パターン

> 責務: ロール設計における代表的なパターンと適用ガイドラインを提供

## 1. 基本パターン

### 1.1 専門家パターン（Expert Pattern）

特定ドメインの専門知識を持つロールを定義するパターン。

| 要素       | 説明                                 |
| ---------- | ------------------------------------ |
| 参照ラベル | 実在する専門家名を思考様式として使用 |
| 専門領域   | 明確に限定されたドメイン             |
| 知識ベース | 参考文献と適用方法を明示             |
| 適用場面   | 深い専門知識が必要なタスク           |

**例**:

```
| 項目     | 内容                    |
| -------- | ----------------------- |
| 名前     | Martin Fowler           |
| 専門領域 | リファクタリング・設計パターン |
```

### 1.2 プロセスオーナーパターン（Process Owner Pattern）

特定のプロセスやワークフローを管理するロールを定義するパターン。

| 要素             | 説明                                 |
| ---------------- | ------------------------------------ |
| 責務             | プロセスの開始から完了までを管理     |
| 成果物           | プロセスの各段階での中間・最終成果物 |
| チェックポイント | 品質を確認する検証ステップ           |
| 適用場面         | 複数ステップの作業フロー管理         |

### 1.3 ゲートキーパーパターン（Gatekeeper Pattern）

品質や基準の検証を行うロールを定義するパターン。

| 要素     | 説明                     |
| -------- | ------------------------ |
| 検証基準 | 客観的なチェックリスト   |
| 合否判定 | 明確なPASS/FAIL基準      |
| 改善提案 | 問題発見時の解決策提示   |
| 適用場面 | 品質保証、レビュー、監査 |

## 2. 複合パターン

### 2.1 パイプラインパターン（Pipeline Pattern）

複数のロールが連携してタスクを完了するパターン。

```
Role A → Role B → Role C
```

| 要素       | 説明                                 |
| ---------- | ------------------------------------ |
| 入出力契約 | 各ロール間のインターフェースを明確化 |
| 依存関係   | 実行順序と依存を定義                 |
| エラー処理 | 中間ステップでの失敗時の対処         |

### 2.2 分岐パターン（Branch Pattern）

条件に応じて異なるロールを呼び出すパターン。

```
                 ┌─ Role B (条件A)
Role A (判定) ───┼─ Role C (条件B)
                 └─ Role D (条件C)
```

### 2.3 集約パターン（Aggregation Pattern）

複数のロールからの出力を統合するパターン。

```
Role A ──┐
Role B ──┼─→ Role D (集約)
Role C ──┘
```

## 3. 思考様式の選定ガイドライン

### 3.1 専門家選定の基準

| 基準           | 説明                                   |
| -------------- | -------------------------------------- |
| ドメイン適合性 | タスクの専門領域と専門家の専門性が一致 |
| 方法論の明確性 | 適用可能な具体的手法を持つ             |
| 参照可能性     | 著書や論文で方法論が公開されている     |

### 3.2 代表的な専門家と適用領域

| 専門家           | 適用領域                                     |
| ---------------- | -------------------------------------------- |
| Peter Drucker    | 目標設定・責務定義・成果測定                 |
| Robert C. Martin | クリーンコード・SOLID原則・設計              |
| Martin Fowler    | リファクタリング・設計パターン               |
| Eric Evans       | ドメイン駆動設計・境界づけられたコンテキスト |
| Kent Beck        | TDD・XP・シンプル設計                        |
| Michael Feathers | レガシーコード・テスト・品質保証             |
| Simon Sinek      | 目的駆動・リーダーシップ・コミュニケーション |
| Daniel Kahneman  | 意思決定・認知バイアス・思考様式             |

## 4. アンチパターン

### 4.1 避けるべきパターン

| アンチパターン   | 問題点                        | 解決策                     |
| ---------------- | ----------------------------- | -------------------------- |
| 万能ロール       | 責務が曖昧で肥大化            | 単一責務原則を適用         |
| 責務の重複       | 複数ロールで同じ責務を持つ    | 責務マトリクスで重複を検出 |
| 曖昧な境界       | やること/やらないことが不明確 | 責務範囲を明示的に定義     |
| 専門家なりすまし | AIが専門家本人を名乗る        | 思考様式の参照に留める     |
| 知識の埋め込み   | Task仕様書に長文知識を記述    | references/に外部化        |

## 5. 品質チェックリスト

ロール設計完了時に以下を確認する：

| 項目            | 確認内容                         |
| --------------- | -------------------------------- |
| 単一責務        | 1ロール=1主責務                  |
| 専門家の明示    | 参照ラベルとして実在専門家を使用 |
| 責務-成果物対応 | すべての責務に成果物が紐づく     |
| 入出力契約      | インターフェースが明確           |
| チェックリスト  | 検証基準が客観的                 |
| 思考プロセス    | 具体的なアクションで記述         |
