# Level 1: パフォーマンステストの基礎

## 概要

パフォーマンステストの基本概念、SLO/SLI設計、ベースライン測定の基礎を学びます。

---

## 1. パフォーマンステストとは

### 1.1 定義

パフォーマンステストは、システムの応答速度、安定性、スケーラビリティを測定・評価するテスト手法です。

### 1.2 目的

| 目的               | 説明                               |
| ------------------ | ---------------------------------- |
| ボトルネックの特定 | システムの性能を阻害する要因を発見 |
| 容量計画           | 必要なリソース量を予測             |
| SLO達成状況の確認  | サービスレベル目標の達成可否を評価 |
| リグレッション防止 | 変更による性能劣化を検出           |
| ユーザー体験の保証 | 実際のユーザーが感じる速度を最適化 |

### 1.3 重要性

- **ビジネス影響**: レイテンシ100ms増加でコンバージョン率1%低下（Amazon調査）
- **ユーザー体験**: 3秒以上の読み込みで53%のユーザーが離脱（Google調査）
- **コスト削減**: 事前検出により本番障害を回避

---

## 2. SLO/SLI設計

### 2.1 SLI（Service Level Indicator）

システムの性能を測定可能な指標にしたもの。

**主要SLI**:

| SLI種別      | 測定内容               | 例                    |
| ------------ | ---------------------- | --------------------- |
| Availability | システムの可用性       | アップタイム率 99.9%  |
| Latency      | リクエストの応答時間   | P95レイテンシ < 500ms |
| Throughput   | 単位時間あたりの処理量 | 1000 req/s            |
| Error Rate   | エラー発生率           | エラー率 < 0.1%       |
| Saturation   | リソースの飽和度       | CPU使用率 < 70%       |

### 2.2 SLO（Service Level Objective）

SLIに対する目標値を定めたもの。

**SLO設計原則**:

1. **測定可能**: 明確に測定できる指標である
2. **達成可能**: 現実的に達成できる目標である
3. **ビジネス価値**: ビジネス目標に紐づいている
4. **複数指標**: 単一指標ではなく多面的に評価

**SLO例**:

```markdown
## レイテンシSLO

- P50レイテンシ: < 100ms
- P95レイテンシ: < 500ms
- P99レイテンシ: < 1000ms

## 可用性SLO

- 月間アップタイム: 99.9%
- エラー率: < 0.1%

## スループットSLO

- ピーク時RPS: > 1000 req/s
```

### 2.3 エラーバジェット

100% - SLO = エラーバジェット

例: SLO 99.9% → エラーバジェット 0.1% = 43分/月

エラーバジェット内であればリスクを取った開発が可能。

## 3. ベースライン測定

### 3.1 ベースラインとは

現状のシステム性能を測定し、改善の基準点を確立すること。

### 3.2 測定手順

**Step 1: 測定環境の準備**

- 本番相当のインフラ構成
- 本番相当のデータ量
- 外部依存の模倣またはモック化

**Step 2: ウォームアップ**

- キャッシュの事前ロード
- JITコンパイルの完了
- コネクションプールの確立

**Step 3: 測定実行**

- 最低3回測定して統計を取る
- 各測定間でシステムをクリーンアップ
- 同一条件で再現性を確保

**Step 4: 結果の記録**

- パーセンタイル値（P50/P95/P99）
- リソース使用率（CPU、メモリ、I/O）
- エラー率

### 3.3 測定時の注意点

| 注意点                       | 理由                         |
| ---------------------------- | ---------------------------- |
| 平均値だけを見ない           | 外れ値を見落とす             |
| 1回の測定で判断しない        | 偶発的な結果の可能性         |
| 開発環境だけでテストしない   | 本番との乖離により誤った結論 |
| バックグラウンド処理を止める | 測定結果のブレを抑える       |

## 4. 基本的なメトリクス

### 4.1 レイテンシ（待ち時間）

リクエストを送信してから応答を受け取るまでの時間。

**測定方法**:

```javascript
const start = Date.now();
await fetch("https://api.example.com/users");
const latency = Date.now() - start;
```

**パーセンタイル分析**:

| パーセンタイル | 意味                         | 重要度 |
| -------------- | ---------------------------- | ------ |
| P50（中央値）  | 半数のユーザーが体験する速度 | 中     |
| P95            | 95%のユーザーが体験する速度  | 高     |
| P99            | 99%のユーザーが体験する速度  | 高     |
| P99.9          | 最も遅い1%のユーザーの体験   | 中     |

### 4.2 スループット（処理量）

単位時間あたりの処理量。

**指標**:

- **RPS**: Requests Per Second（リクエスト/秒）
- **TPS**: Transactions Per Second（トランザクション/秒）
- **Throughput**: データ転送量（MB/s）

### 4.3 エラー率

全リクエストに対するエラーの割合。

```
エラー率 = (エラー数 / 総リクエスト数) × 100
```

**許容範囲**: 通常 < 0.1%

### 4.4 リソース使用率

| リソース     | 測定項目               | 目標例 |
| ------------ | ---------------------- | ------ |
| CPU          | CPU使用率              | < 70%  |
| メモリ       | メモリ使用率           | < 80%  |
| ディスク     | I/O待ち時間            | < 10%  |
| ネットワーク | ネットワーク帯域使用率 | < 70%  |

## 5. テストタイプの基礎

### 5.1 負荷テスト（Load Testing）

**目的**: 想定される通常負荷・ピーク負荷でシステムが正常動作するか確認

**シナリオ**:

- 段階的に負荷を増加（Ramp-up）
- 定常状態を維持（Steady State）
- 段階的に負荷を減少（Ramp-down）

### 5.2 ストレステスト（Stress Testing）

**目的**: システムの限界点と破綻条件を特定

**シナリオ**:

- 想定を超える負荷をかける
- システムが破綻するまで負荷を増加
- 破綻後の回復能力を確認

### 5.3 スパイクテスト（Spike Testing）

**目的**: 急激な負荷変動への対応能力を確認

**シナリオ**:

- 低負荷から急激に高負荷へ
- 高負荷から急激に低負荷へ

### 5.4 耐久テスト（Soak Testing）

**目的**: 長時間稼働時のメモリリークや性能劣化を検出

**シナリオ**:

- 中程度の負荷を長時間（数時間〜数日）維持
- リソース使用率の推移を監視

## 6. 基本的なツール

### 6.1 k6

**特徴**:

- JavaScriptで記述
- CLI/Cloud対応
- 軽量・高速

**基本スクリプト例**:

```javascript
import http from "k6/http";
import { check, sleep } from "k6";

export const options = {
  stages: [
    { duration: "1m", target: 10 }, // Ramp-up
    { duration: "3m", target: 10 }, // Steady
    { duration: "1m", target: 0 }, // Ramp-down
  ],
};

export default function () {
  const res = http.get("https://api.example.com/users");
  check(res, { "status is 200": (r) => r.status === 200 });
  sleep(1);
}
```

### 6.2 JMeter

**特徴**:

- GUIで設定可能
- プラグイン豊富
- プロトコル対応広い

**用途**: Web全般、複雑なシナリオ

### 6.3 Chrome DevTools

**特徴**:

- ブラウザ組み込み
- フロントエンド分析に最適

**用途**: フロントエンドのパフォーマンス分析

## 7. よくある間違い

### 7.1 平均値だけを見る

**問題**: 外れ値を見落とす

**対策**: P95/P99パーセンタイルを確認

### 7.2 本番と異なる環境でテスト

**問題**: 本番で問題が発生

**対策**: 本番相当のインフラ・データ量でテスト

### 7.3 単一メトリクスのみ測定

**問題**: ボトルネックの見落とし

**対策**: レイテンシ、スループット、エラー率、リソース使用率を総合的に測定

### 7.4 ウォームアップなし

**問題**: 初回起動の遅さが結果に影響

**対策**: 測定前に十分なウォームアップ期間を設ける
