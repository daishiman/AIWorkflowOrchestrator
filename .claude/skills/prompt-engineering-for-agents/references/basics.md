# プロンプトエンジニアリング基礎

## 概要

エージェント向けプロンプトエンジニアリングの基本原則と用語を整理します。
System Prompt設計の基礎知識として、まずこのドキュメントを参照してください。

## プロンプトエンジニアリングとは

### 定義

プロンプトエンジニアリングは、言語モデルから望ましい応答を引き出すために、
入力プロンプトを体系的に設計・最適化する技術です。

### エージェント向けプロンプトの特徴

一般的なプロンプトとの違い:

| 一般的プロンプト | エージェント向けプロンプト           |
| ---------------- | ------------------------------------ |
| 1回限りの質問    | 継続的な対話・タスク実行             |
| 単一の回答       | 複数ステップのワークフロー           |
| 文脈が限定的     | 広範な文脈とスキル統合               |
| 明示的な指示     | 暗黙的な判断基準とベストプラクティス |
| 短期的な品質     | 長期的な一貫性と再現性               |

## 基本概念

### 1. System Prompt

**定義**: エージェントの役割、動作、制約を定義する基盤となるプロンプト

**目的**:

- エージェントの行動指針を確立
- 一貫した判断基準を提供
- 期待される動作範囲を明確化

**例**:

```markdown
あなたは **コードレビュー専門家** です。

TypeScriptコードのセキュリティ脆弱性とパフォーマンス問題を検出し、
具体的な修正案を提示します。
```

### 2. Role Prompting

**定義**: エージェントに特定の役割・ペルソナを与える技術

**効果**:

- ✅ 専門性が向上
- ✅ 一貫した振る舞い
- ✅ 文脈理解の向上

**基本形式**:

```markdown
あなたは **{{役割名}}** です。

{{役割の詳細説明}}
```

**良い例**:

```markdown
あなたは **セキュリティ監査人** です。

OWASP Top 10に基づき、Webアプリケーションの脆弱性を
体系的に検出し、CWE分類に従って報告します。
```

**悪い例**:

```markdown
あなたはコードをチェックする人です。
```

### 3. Few-Shot Learning

**定義**: 少数の例示によって期待される動作を学習させる技術

**推奨数**: 2-5個

- 最小限: 2個（典型例）
- 最大: 5個（典型例 + 境界例）

**基本形式**:

```markdown
## 例

### 例1: {{シナリオ1}}

**入力**:
{{入力例1}}

**期待される出力**:
{{出力例1}}

### 例2: {{シナリオ2}}

**入力**:
{{入力例2}}

**期待される出力**:
{{出力例2}}
```

**選択基準**:

- 典型的なケース（最も頻繁に発生）
- 境界ケース（エッジケース）
- 失敗しやすいケース（よくあるミス）

### 4. 制約条件（Constraints）

**定義**: エージェントの動作を制限するルール

**目的**:

- 不適切な動作を防止
- 品質基準を明確化
- エラーを減らす

**基本形式**:

```markdown
## 制約

**すべきこと**:

- {{制約1}}
- {{制約2}}

**避けるべきこと**:

- {{禁止事項1}}
- {{禁止事項2}}
```

**具体例**:

```markdown
## ベストプラクティス

✅ **すべきこと**:

- 変数名は説明的に（`getUserData` ○、`getData` ×）
- 1つのコミットで1つの変更
- テスト追加を必須とする

❌ **避けるべきこと**:

- テストなしのリファクタリング
- 複数の変更を同時にコミット
- 曖昧な変数名（`temp`, `data`, `obj`）
```

### 5. ワークフロー（Workflow）

**定義**: タスクを段階的に実行するための手順

**目的**:

- タスクを体系的に実行
- 成果物を明確化
- ツール使用を適切化

**基本形式**:

```markdown
## ワークフロー

### Phase 1: {{Phase名}}

**目的**: {{Phase目的}}

**手順**:

1. {{ステップ1}}
2. {{ステップ2}}
3. {{ステップ3}}

**成果物**:

- {{成果物1}}

**判断ポイント**:

- {{判断基準1}}
```

### 6. プログレッシブディスクロージャー（Progressive Disclosure）

**定義**: 必要な情報を段階的に提示する設計原則

**目的**:

- Token消費を最適化
- 認知負荷を軽減
- 必要な情報に素早くアクセス

**実践方法**:

```markdown
# エージェントSKILL.md（軽量）

↓ 参照
references/basics.md（基本知識）
↓ 必要に応じて
references/patterns.md（詳細パターン）
↓ さらに詳細
references/advanced-techniques.md（高度技術）
```

## プロンプト設計の基本原則

### 原則1: 明確性（Clarity）

**定義**: 指示は明確で曖昧さがないこと

**実践**:

- ❌ 「適宜」「など」「必要に応じて」を避ける
- ✅ 具体的な条件と行動を記述

**悪い例**:

```markdown
必要に応じてテストを追加してください。
```

**良い例**:

```markdown
以下の条件でテストを追加してください:

- 新規関数を追加した場合: 単体テスト必須
- 既存関数を変更した場合: 既存テストの更新必須
- APIエンドポイントを変更した場合: 統合テスト必須
```

### 原則2: 具体性（Specificity）

**定義**: 抽象的な指示ではなく、具体的な行動を指定

**実践**:

- ❌ 「コードを改善」
- ✅ 「Long Methodを Extract Methodパターンでリファクタリング」

**悪い例**:

```markdown
コードの品質を向上させてください。
```

**良い例**:

```markdown
以下のリファクタリングを実施してください:

1. 20行以上のメソッド → Extract Methodで分割
2. 重複コード → Extract Functionで共通化
3. マジックナンバー → 名前付き定数に置換
```

### 原則3: 構造化（Structure）

**定義**: 論理的なセクション構成で情報を整理

**推奨7セクション構造**:

1. 役割定義
2. 専門分野
3. ワークフロー
4. スキル管理
5. ベストプラクティス
6. 詳細リファレンス
7. 変更履歴

### 原則4: 測定可能性（Measurability）

**定義**: 成果物や成功基準を定量的に定義

**実践**:

- ❌ 「できるだけ早く」
- ✅ 「3秒以内に応答」

**悪い例**:

```markdown
できるだけ高品質なコードを書く。
```

**良い例**:

```markdown
以下の品質基準を満たす:

- テストカバレッジ: 80%以上
- 循環的複雑度: 10以下
- コードレビュー: 承認2名以上
```

### 原則5: 一貫性（Consistency）

**定義**: エージェント間で用語・形式・構造を統一

**実践**:

- 同じ用語を使用（「タスク」 vs 「ジョブ」 → 「タスク」に統一）
- 同じテンプレートを使用
- 同じセクション構造を維持

## プロンプトの構成要素

### 必須要素

1. **役割定義**: エージェントの役割（1-2文）
2. **タスク範囲**: 実施するタスクのリスト
3. **制約条件**: すべきこと・避けるべきこと

### 推奨要素

4. **出力形式**: 期待される成果物の形式
5. **ワークフロー**: 段階的な手順
6. **例示**: 2-5個のFew-Shot Examples
7. **リファレンス**: 詳細知識への参照

### オプション要素

8. **エラーハンドリング**: エラー時の動作
9. **品質基準**: 成功の定量的指標
10. **変更履歴**: バージョン管理

## 用語集

### プロンプト関連

- **System Prompt**: エージェントの基盤となるプロンプト
- **User Prompt**: ユーザーからの入力プロンプト
- **Assistant Response**: エージェントの応答
- **Context Window**: プロンプトと応答の合計Token上限

### テクニック関連

- **Role Prompting**: 役割を与える技術
- **Few-Shot Learning**: 少数例示による学習
- **Chain-of-Thought**: 思考過程を明示的に記述
- **Self-Consistency**: 複数回実行して一貫性を確認

### 設計パターン関連

- **Constrained Behavior**: 制約による動作制御
- **Structured Workflow**: 構造化ワークフロー
- **Knowledge Reference**: 外部知識への参照
- **Progressive Disclosure**: 段階的情報開示

## ベストプラクティス

### すべきこと

- ✅ 明確で具体的な指示
- ✅ 2-5個のFew-Shot Examples
- ✅ 推奨7セクション構造
- ✅ 測定可能な成功基準
- ✅ 曖昧な表現を排除
- ✅ テンプレートを活用
- ✅ 段階的に情報を提示

### 避けるべきこと

- ❌ 曖昧な表現（「適宜」「など」）
- ❌ 10個以上のFew-Shot Examples
- ❌ 非構造化された長文
- ❌ 測定不可能な基準
- ❌ 矛盾する指示
- ❌ 長すぎる文（3行以上）
- ❌ 過度な知識の詰め込み
