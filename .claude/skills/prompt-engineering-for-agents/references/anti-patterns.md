# プロンプトエンジニアリング アンチパターン

## 概要

エージェント向けプロンプト設計でよく見られる失敗パターンと、その対処法をまとめています。
これらのアンチパターンを避けることで、プロンプトの品質を大幅に向上させることができます。

## アンチパターン一覧

### 1. 曖昧指示病（Ambiguous Instruction Syndrome）

#### 症状

「適宜」「必要に応じて」「など」などの曖昧な表現が多用されている。

#### 問題点

- エージェントの判断が一貫しない
- 期待と異なる動作をする
- デバッグが困難

#### 悪い例

```markdown
必要に応じてテストを追加し、適宜リファクタリングしてください。
できるだけ品質を高めてください。
```

#### 良い例

```markdown
以下の条件でテストを追加してください:

- 新規関数: 単体テスト必須
- 既存関数変更: 既存テスト更新必須
- カバレッジ<80%: 追加テスト必須

リファクタリング基準:

- メソッド>20行: Extract Method適用
- 重複コード>3箇所: Extract Function適用
```

#### 対処法

1. 曖昧な表現を排除
2. 具体的な条件を明示
3. 測定可能な基準を設定

### 2. 例示過多症候群（Example Overload Syndrome）

#### 症状

Few-Shot Examplesが10個以上ある。

#### 問題点

- Token消費が過大
- 認知負荷が高い
- 本質が見えにくい

#### 悪い例

```markdown
## 例

### 例1: ケース1

### 例2: ケース2

### 例3: ケース3

...

### 例15: ケース15
```

#### 良い例

```markdown
## 例

### 例1: 典型的なケース

### 例2: 境界ケース

### 例3: 失敗ケース

詳細な例は `references/examples.md` を参照。
```

#### 対処法

1. 例示は2-5個に制限
2. 典型例・境界例・失敗例を選択
3. 5個以上は外部ファイル化

### 3. 非構造化長文病（Unstructured Wall of Text）

#### 症状

セクション分けがなく、長い段落が続く。

#### 問題点

- 理解しづらい
- 必要な情報を見つけにくい
- 保守が困難

#### 悪い例

```markdown
このエージェントはコードをリファクタリングします。Long MethodやDuplicate Codeを
見つけたらExtract MethodやExtract Functionを使います。テストは必ず実行します。
テストがない場合はエラーにします。20行以上がLong Methodです。3箇所以上の重複が
Duplicate Codeです。Extract Methodは...（延々と続く）
```

#### 良い例

```markdown
## 役割

リファクタリング専門家

## ワークフロー

### Phase 1: 検出

- Long Method検出（20行以上）
- Duplicate Code検出（3箇所以上）

### Phase 2: 実施

- Extract Method適用
- テスト実行

## ベストプラクティス

✅ すべきこと: 各変更後にテスト実行
❌ 避けるべきこと: テストなしリファクタリング
```

#### 対処法

1. 7セクション構造を使用
2. 箇条書きを活用
3. 論理的に情報を整理

### 4. 役割定義欠如（Missing Role Definition）

#### 症状

エージェントの役割が不明確または抽象的。

#### 問題点

- 専門性が発揮されない
- 一貫性のない判断
- 動作が予測不能

#### 悪い例

```markdown
あなたはコードを書く人です。
```

#### 良い例

```markdown
あなたは **リファクタリング専門家** です。

マーティン・ファウラー『リファクタリング』に基づき、
Code Smellsを体系的に検出し、適切なパターンで
リファクタリングします。

**専門分野**:

- Long Method検出とExtract Method適用
- Duplicate Code検出とExtract Function適用
- Test-Driven Refactoring実践
```

#### 対処法

1. 明確な役割名（1-2語）
2. 専門分野を3-5個リスト
3. 参考文献・標準を明示

### 5. 制約なし放任主義（Constraint-Free Chaos）

#### 症状

「すべきこと」「避けるべきこと」が定義されていない。

#### 問題点

- 不適切な動作を防げない
- 品質基準が不明確
- エラーが多発

#### 悪い例

```markdown
リファクタリングを実施してください。
```

#### 良い例

```markdown
## ベストプラクティス

✅ **すべきこと**:

- 1コミット1変更
- 各変更後にテスト実行
- テストカバレッジ80%以上を維持

❌ **避けるべきこと**:

- テストなしリファクタリング
- 複数変更の同時実施
- 大規模一括変更
```

#### 対処法

1. 具体的な制約を明示
2. 理由を添える
3. 代替手段を提示

### 6. 知識重複の泥沼（Knowledge Duplication Swamp）

#### 症状

同じ情報が複数箇所に重複している。

#### 問題点

- Token浪費
- 保守コスト増大
- 矛盾のリスク

#### 悪い例

```markdown
<!-- エージェントA -->

## リファクタリングパターン

Extract Method: 長いメソッドを分割...（詳細500行）

<!-- エージェントB -->

## リファクタリングパターン

Extract Method: 長いメソッドを分割...（同じ内容500行）
```

#### 良い例

```markdown
<!-- エージェントA -->

## スキル管理

依存スキル:

- `skills/refactoring-patterns/SKILL.md`

<!-- エージェントB -->

## スキル管理

依存スキル:

- `skills/refactoring-patterns/SKILL.md`

<!-- skills/refactoring-patterns/SKILL.md -->

## リファクタリングパターン

Extract Method: 長いメソッドを分割...（詳細500行）
```

#### 対処法

1. 共通知識は外部スキル化
2. プログレッシブディスクロージャー
3. 参照パスを明示

### 7. 抽象例示の罠（Abstract Example Trap）

#### 症状

Few-Shot Examplesが抽象的なプレースホルダー。

#### 問題点

- 学習効果なし
- 期待される動作が不明確
- パターン認識できない

#### 悪い例

```markdown
### 例1

**入力**: {{some_input}}
**出力**: {{some_output}}
```

#### 良い例

````markdown
### 例1: Long Method検出

**入力**:
\```typescript
function processOrder(order) {
// 25行のコード
}
\```

**処理**:

1. 行数カウント: 25行
2. Long Method判定: Yes（>20行）
3. Extract Method適用

**出力**:
\```typescript
function processOrder(order) {
const validated = validateOrder(order);
return saveOrder(validated);
}
\```
````

#### 対処法

1. 実際の値を使用
2. 入力→処理→出力を明示
3. 具体的なコードを記載

### 8. 測定不能基準病（Unmeasurable Criteria Disease）

#### 症状

「高品質」「適切に」「効率的に」などの測定不能な基準。

#### 問題点

- 判断基準が不明確
- 一貫性のない動作
- 成功の定義が曖昧

#### 悪い例

```markdown
高品質なコードを書いてください。
効率的にリファクタリングしてください。
```

#### 良い例

```markdown
以下の品質基準を満たしてください:

- テストカバレッジ: 80%以上
- 循環的複雑度: 10以下
- ESLint警告: 0件

リファクタリング効率基準:

- 所要時間: 1ファイルあたり10分以内
- 変更範囲: 1回あたり50行以内
```

#### 対処法

1. 定量的な基準を設定
2. 測定方法を明示
3. 合格ラインを明確化

### 9. エラーハンドリング無視（Error Handling Neglect）

#### 症状

エラー時の動作が定義されていない。

#### 問題点

- エラー時の動作が不明確
- 復旧できない
- ユーザー体験が悪化

#### 悪い例

```markdown
## ワークフロー

1. ファイルを読み込み
2. 分析を実施
3. レポートを生成
```

#### 良い例

```markdown
## ワークフロー

1. ファイルを読み込み
   - エラー時: 3回までRetry
   - 失敗時: エラーレポート生成

2. 分析を実施
   - タイムアウト: 30秒
   - エラー時: 部分的な結果を返す

3. レポートを生成
   - 失敗時: キャッシュから前回結果を読み込み
```

#### 対処法

1. Retry戦略を定義
2. Fallback動作を設定
3. Escalation条件を明示

### 10. ワークフロー欠如（Workflow Absence）

#### 症状

タスクの手順が定義されていない。

#### 問題点

- タスクが体系的に実行されない
- ツール使用が不適切
- 成果物が不明確

#### 悪い例

```markdown
コードをリファクタリングしてテストを実行してください。
```

#### 良い例

```markdown
## ワークフロー

### Phase 1: Code Smells検出

**手順**:

1. 対象ファイルを読み込み
2. Long Methodを検出（20行以上）
3. 検出結果をレポート

**ツール使用**:

- Read: ファイル読み込み
- Write: レポート生成

**成果物**:

- `docs/code-smells-report.md`

### Phase 2: リファクタリング実施

**手順**:

1. Extract Methodパターンを適用
2. テストを実行（100%合格必須）
3. コミット

**ツール使用**:

- Edit: コード編集
- Bash: テスト実行

**成果物**:

- リファクタリング済みコード
- テスト結果レポート
```

#### 対処法

1. Phase分けして構造化
2. ツール使用を明示
3. 成果物を定義

## トラブルシューティング

### 問題: エージェントの動作が一貫しない

**原因**: 曖昧指示病
**対処**: 具体的な条件と基準を設定

### 問題: Token消費が過大

**原因**: 例示過多症候群、知識重複の泥沼
**対処**: 例示を2-5個に制限、外部スキル化

### 問題: 必要な情報が見つからない

**原因**: 非構造化長文病
**対処**: 7セクション構造で整理

### 問題: エージェントの専門性が低い

**原因**: 役割定義欠如
**対処**: 明確な役割と専門分野を定義

### 問題: 不適切な動作が多い

**原因**: 制約なし放任主義
**対処**: すべきこと・避けるべきことを明示

### 問題: 保守コストが高い

**原因**: 知識重複の泥沼
**対処**: 共通知識を外部スキル化

### 問題: 例示の効果が薄い

**原因**: 抽象例示の罠
**対処**: 実際の値を使用した具体例

### 問題: 判断基準が曖昧

**原因**: 測定不能基準病
**対処**: 定量的な基準を設定

### 問題: エラー時に動作不能

**原因**: エラーハンドリング無視
**対処**: Retry、Fallback、Escalationを定義

### 問題: タスクが体系的に実行されない

**原因**: ワークフロー欠如
**対処**: Phase分けして構造化

## ベストプラクティス

### すべきこと

- ✅ 具体的で測定可能な基準
- ✅ 7セクション構造で整理
- ✅ 2-5個の具体的な例示
- ✅ すべきこと・避けるべきことを明示
- ✅ エラーハンドリングを定義
- ✅ ワークフローを構造化
- ✅ 知識を外部化してプログレッシブディスクロージャー

### 避けるべきこと

- ❌ 曖昧な表現（「適宜」「など」）
- ❌ 非構造化された長文
- ❌ 10個以上の例示
- ❌ 抽象的なプレースホルダー
- ❌ 測定不能な基準
- ❌ 制約のない指示
- ❌ 知識の重複
- ❌ エラーハンドリングの欠如
- ❌ ワークフローの欠如

## 次のステップ

アンチパターンを理解したら:

1. **既存プロンプトの診断**: チェックリストで問題を特定
2. **段階的改善**: 1つずつアンチパターンを解消
3. **品質評価**: `scripts/validate-prompt-quality.mjs` で検証
