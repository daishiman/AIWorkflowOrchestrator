# モジュラーアーキテクチャ 基本概念

> 相対パス: `references/basics.md`
> 読込条件: 初回利用時

---

## モジュラーアーキテクチャとは

システムを独立した再利用可能なモジュールに分割する設計アプローチ。各モジュールは明確な責務を持ち、定義されたインターフェースを通じて他のモジュールと連携する。

### 主要な価値

| 価値         | 説明                                   |
| ------------ | -------------------------------------- |
| 保守性向上   | 変更の影響範囲を限定できる             |
| 再利用性     | モジュール単位での再利用が可能         |
| テスト容易性 | モジュール単位での独立したテストが可能 |
| 並行開発     | チーム間で独立して開発できる           |

## 凝集性（Cohesion）

モジュール内の要素がどれだけ関連しているかの度合い。高い凝集性が望ましい。

### 凝集性の種類（良い順）

| 種類         | 説明                                 | 評価 |
| ------------ | ------------------------------------ | ---- |
| 機能的凝集   | 単一の機能を実行するために必要な要素 | 最良 |
| 順序的凝集   | 一連の処理を順番に実行する要素       | 良   |
| 通信的凝集   | 同じデータを操作する要素             | 普通 |
| 手続き的凝集 | 実行順序で関連する要素               | 低   |
| 時間的凝集   | 同時に実行される要素                 | 低   |
| 論理的凝集   | 論理的に似た機能の要素               | 低   |
| 偶発的凝集   | 関連性のない要素の集まり             | 最悪 |

### 良い例

```typescript
// 機能的凝集：ユーザー認証に関連する要素のみ
class AuthenticationService {
  login(credentials: Credentials): Token {}
  logout(token: Token): void {}
  validateToken(token: Token): boolean {}
}
```

### 悪い例

```typescript
// 偶発的凝集：無関係な機能の混在
class UtilityService {
  formatDate(date: Date): string {}
  sendEmail(to: string, body: string): void {}
  calculateTax(amount: number): number {}
}
```

## 結合度（Coupling）

モジュール間の依存関係の強さ。低い結合度が望ましい。

### 結合度の種類（良い順）

| 種類             | 説明                           | 評価 |
| ---------------- | ------------------------------ | ---- |
| データ結合       | プリミティブデータのみを渡す   | 最良 |
| スタンプ結合     | データ構造を渡すが一部のみ使用 | 良   |
| コントロール結合 | フラグで相手の動作を制御       | 普通 |
| 外部結合         | 外部データフォーマットを共有   | 低   |
| 共通結合         | グローバルデータを共有         | 低   |
| 内容結合         | 相手の内部実装に直接アクセス   | 最悪 |

### 良い例

```typescript
// データ結合：必要なデータのみを渡す
function calculateTotal(price: number, quantity: number): number {
  return price * quantity;
}
```

### 悪い例

```typescript
// 内容結合：相手の内部実装に依存
function processOrder(order: Order) {
  // 内部のprivateメソッドに直接アクセス
  order._internalValidate();
}
```

## 依存関係ルール

### Clean Architectureの同心円モデル

```
       ┌─────────────────────────┐
       │    External Systems     │  ← Frameworks, DB, UI
       │  ┌───────────────────┐  │
       │  │   Interface       │  │  ← Controllers, Gateways
       │  │  ┌─────────────┐  │  │
       │  │  │  Use Cases  │  │  │  ← Application Business Rules
       │  │  │  ┌───────┐  │  │  │
       │  │  │  │Entity │  │  │  │  ← Enterprise Business Rules
       │  │  │  └───────┘  │  │  │
       │  │  └─────────────┘  │  │
       │  └───────────────────┘  │
       └─────────────────────────┘

        依存の方向 → 内側へのみ
```

### 依存性逆転の原則（DIP）

| 原則             | 説明                               |
| ---------------- | ---------------------------------- |
| 上位モジュール   | 下位モジュールに依存してはならない |
| 両方のモジュール | 抽象に依存すべき                   |
| 抽象             | 詳細に依存してはならない           |
| 詳細             | 抽象に依存すべき                   |

```typescript
// 悪い例：具象に依存
class OrderService {
  private mysqlRepo: MySQLOrderRepository;
}

// 良い例：抽象に依存
class OrderService {
  private repo: OrderRepository; // インターフェース
}
```

## モジュール境界の決定基準

| 基準             | 説明                               |
| ---------------- | ---------------------------------- |
| ビジネスドメイン | 業務の区切りでモジュールを分割     |
| 変更理由         | 同じ理由で変更されるものを一緒に   |
| チーム境界       | チームの責任範囲に合わせる         |
| デプロイ単位     | 独立してデプロイできる単位         |
| データ所有権     | データの管理責任でモジュールを決定 |

---

## チェックリスト

- [ ] 各モジュールが単一の責任を持っている
- [ ] モジュール間の依存関係が一方向である
- [ ] 循環依存が存在しない
- [ ] インターフェースを通じて通信している
- [ ] 凝集性が高く、結合度が低い
