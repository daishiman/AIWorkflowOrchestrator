## 4.1 シーケンシャルワークフロー

複雑なタスクでは、操作を明確な順序のステップに分解。

**記述形式**:

```markdown
{{タスク名}}は以下のステップで行う：

1. {{ステップ1の説明}}（run scripts/{{script-1}}.mjs）
2. {{ステップ2の説明}}（edit {{config-file}}.json）
3. {{ステップ3の説明}}（run scripts/{{script-2}}.mjs）
4. {{ステップNの説明}}（run scripts/{{script-n}}.mjs）
```

**特徴**:

| 特徴     | 説明                               |
| -------- | ---------------------------------- |
| 依存関係 | 各ステップは前のステップに依存     |
| 明示性   | スクリプト実行やファイル編集を明示 |
| 順序重要 | 順序が重要なタスクに適用           |

**適用例**:

- データベースマイグレーション
- ビルド＆デプロイパイプライン
- 多段階のコード生成

## 4.2 条件分岐ワークフロー

分岐ロジックを持つタスクでは、Claude を判断ポイントに導く。

**記述形式**:

```markdown
1. {{判断ポイント}}を判断する：
   **{{条件A}}？** → 「{{ワークフローA}}」に従う
   **{{条件B}}？** → 「{{ワークフローB}}」に従う

2. {{ワークフローA}}: See [references/{{workflow-a}}.md](references/{{workflow-a}}.md)
3. {{ワークフローB}}: See [references/{{workflow-b}}.md](references/{{workflow-b}}.md)
```

**特徴**:

| 特徴         | 説明                                        |
| ------------ | ------------------------------------------- |
| 判断ポイント | 明示的に定義                                |
| 外部化       | 各分岐のワークフローを references/ に外部化 |
| 対応明確     | 条件と結果の対応を明確に                    |

**適用例**:

- エラーハンドリング（エラー種別による分岐）
- 機能フラグによる処理分岐
- ユーザー入力による動的ルーティング

## 4.3 Phase ベースワークフロー

複数フェーズに分かれるタスクでは、各フェーズを明確に定義。

**記述形式**:

```markdown
### Phase 1: {{Phase名}}

**目的**: {{Phaseの目的}}

**アクション**:

1. {{アクション1}}
2. {{アクション2}}

**Task**: `agents/{{task-name}}.md` を参照
```

**特徴**:

| 特徴       | 説明                           |
| ---------- | ------------------------------ |
| 明確な目的 | 各Phaseに明確な目的            |
| 具体的手順 | アクションリストで具体的な手順 |
| 詳細分離   | Task仕様書への参照で詳細を分離 |

**適用例**:

- スキル作成ワークフロー
- コードレビュープロセス
- 機能開発サイクル

## ワークフロー選択ガイド

| タスクの特性                 | 推奨パターン     |
| ---------------------------- | ---------------- |
| 順序が重要、依存関係あり     | シーケンシャル   |
| 条件によって処理が変わる     | 条件分岐         |
| 複数の独立したフェーズがある | Phase ベース     |
| 複雑で上記が組み合わさる     | Phase + 条件分岐 |

## Task分割の判断基準

### 分割すべき場合

| 条件                         | 理由                                 |
| ---------------------------- | ------------------------------------ |
| 思考ログが肥大する場合       | 探索・試行錯誤がメインに残ると汚れる |
| フェーズ間で責務が異なる場合 | リサーチと生成を同窓で混ぜない       |
| 入出力が明確に定義できる場合 | 各Taskが独立して検証可能             |
| 専門性が異なる場合           | 分析タスクと実装タスクは別の思考様式 |

### 分割しない場合

| 条件             | 理由                             |
| ---------------- | -------------------------------- |
| 単純なタスク     | ステップが3未満                  |
| 入出力が曖昧     | 明確な境界が定義できない         |
| 密結合で分離困難 | 分離するとオーバーヘッドが増える |
