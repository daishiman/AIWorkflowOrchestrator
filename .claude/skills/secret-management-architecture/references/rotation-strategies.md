# ローテーション戦略

> **責務**: キーローテーションの戦略とパターン
> **対象Task**: design-rotation

---

## 1. ローテーション周期

| 分類     | 推奨周期 | 最大許容 | 自動化 | 備考                |
| -------- | -------- | -------- | ------ | ------------------- |
| Critical | 30日     | 30日     | 必須   | HSMバックアップ必須 |
| High     | 90日     | 90日     | 必須   | 監査証跡必須        |
| Medium   | 180日    | 180日    | 推奨   |                     |
| Low      | 365日    | 365日    | 任意   |                     |

## 2. ゼロダウンタイムローテーション

### 2.1 デュアルシークレット方式

```
Phase 1: 準備
┌─────────────────────────────────────┐
│  Current: SecretV1 (Active)         │
│  New:     SecretV2 (Preparing)      │
└─────────────────────────────────────┘
        ↓
Phase 2: 並行運用
┌─────────────────────────────────────┐
│  Current: SecretV1 (Active)         │
│  New:     SecretV2 (Active)         │
│  Both secrets are valid             │
└─────────────────────────────────────┘
        ↓
Phase 3: 移行
┌─────────────────────────────────────┐
│  Old:     SecretV1 (Deprecated)     │
│  Current: SecretV2 (Active)         │
│  Applications migrate to V2         │
└─────────────────────────────────────┘
        ↓
Phase 4: 完了
┌─────────────────────────────────────┐
│  Old:     SecretV1 (Revoked)        │
│  Current: SecretV2 (Active)         │
└─────────────────────────────────────┘
```

### 2.2 タイムライン例

| フェーズ | 期間   | アクション                         |
| -------- | ------ | ---------------------------------- |
| 準備     | 0日目  | 新シークレット生成                 |
| 並行運用 | 1-7日  | 両方のシークレットが有効           |
| 移行     | 7-14日 | アプリケーションを新シークレットへ |
| 完了     | 14日目 | 旧シークレット無効化               |

## 3. 自動ローテーションフロー

### 3.1 Vault自動ローテーション

```yaml
# Vault Database Secrets Engine 設定例
rotation:
  schedule: "0 0 * * *" # 毎日深夜
  statement: |
    ALTER USER "{{name}}"
    WITH PASSWORD '{{password}}';
```

### 3.2 AWS Secrets Manager自動ローテーション

```
┌──────────────────────────────────────┐
│     Secrets Manager Rotation         │
│                                      │
│  1. createSecret                     │
│     └→ 新シークレット生成            │
│  2. setSecret                        │
│     └→ 対象サービスに設定            │

└──────────────────────────────────────┘
```

## 4. シークレット種別別戦略

### 4.1 データベース認証情報

| 項目             | 戦略                             |
| ---------------- | -------------------------------- |
| ローテーション   | Vault Database Secrets Engine    |
| 方式             | 動的シークレット（オンデマンド） |
| TTL              | 1時間（短命トークン）            |
| フェイルオーバー | 複数DB接続プール                 |

### 4.2 APIキー

| 項目           | 戦略                    |
| -------------- | ----------------------- |
| ローテーション | 事前生成 + デュアルキー |
| 方式           | 静的シークレット        |
| 猶予期間       | 7日間                   |
| 通知           | 期限7日前にアラート     |

### 4.3 暗号化キー

| 項目           | 戦略                               |
| -------------- | ---------------------------------- |
| ローテーション | KMS自動ローテーション              |
| 方式           | キーバージョニング                 |
| 旧キー         | 復号用に保持（暗号化には使用不可） |
| 保持期間       | データ保持期間 + 1年               |

## 5. 緊急ローテーション

### 5.1 トリガー条件

| 条件                 | 対応                          |
| -------------------- | ----------------------------- |
| シークレット漏洩確認 | 即時ローテーション + 調査     |
| 不正アクセス検知     | 即時ローテーション + ブロック |
| 従業員離職（管理者） | 24時間以内にローテーション    |
| コンプライアンス要求 | 要求期限内にローテーション    |

### 5.2 緊急ローテーション手順

```
1. インシデント確認
   └→ 影響範囲の特定

2. 即時対応
   ├→ 疑わしいセッション無効化
   └→ 一時的なアクセス制限

3. 緊急ローテーション実行
   ├→ 新シークレット生成
   ├→ 依存サービスへの配布
   └→ 旧シークレット即時無効化

4. 影響確認
   ├→ サービス正常性確認
   └→ ログ調査

5. 事後対応
   ├→ インシデントレポート作成
   └→ 再発防止策の実施
```

## 6. ロールバック戦略

### 6.1 ロールバック条件

| 条件               | 判断基準               |
| ------------------ | ---------------------- |
| サービス障害       | エラー率 > 5%          |
| 認証失敗           | 認証失敗率 > 1%        |
| パフォーマンス劣化 | レイテンシ > 閾値の2倍 |

### 6.2 ロールバック手順

```
1. 障害検知
   └→ 自動/手動での検知

2. ロールバック判断
   └→ ローテーションが原因か確認

3. 旧シークレット再有効化
   ├→ 旧シークレットのステータス変更
   └→ アプリケーション再起動/キャッシュクリア

4. サービス復旧確認

5. 根本原因調査
   └→ ローテーション失敗の原因特定
```
