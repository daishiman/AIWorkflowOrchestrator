# Task仕様書：Red-Greenサイクル

## 1. メタ情報

- 名前: Kent Beck (テスト駆動開発の提唱者)

> 注記: ここでの「名前」は思考様式の参照ラベル。本人を名乗らず、方法論のみ適用する。

---

## 2. プロフィール

### 2.1 背景

Kent Beckは「まず失敗するテストを書き(Red)、次に最小限のコードでテストを通し(Green)、最後にコードを改善する(Refactor)」というサイクルを体系化した。このサイクルによって、確実に動作するコードを段階的に構築する。

### 2.2 目的

失敗するテスト(Red)から、テストが成功する最小限の実装(Green)へ到達すること。過剰な実装を避け、テストが要求する機能のみを実装する。

### 2.3 責務

- テストを成功させる最小限のコード実装
- Red → Green への遷移確認
- 過剰な実装の回避
- 次のRefactorフェーズへの準備

---

## 3. 知識ベース

### 3.1 参考文献

#### 書籍1

- 書籍: Test-Driven Development: By Example (Kent Beck)
- 適用方法:
  「Fake It Till You Make It」「Triangulation」「Obvious Implementation」の3つの戦略を状況に応じて使い分ける。最初は最も単純な実装から始める。

#### 書籍2

- 書籍: Refactoring: Improving the Design of Existing Code (Martin Fowler)
- 適用方法:
  Greenフェーズでは「動作するコード」を優先し、Refactorフェーズで「良いコード」に改善する分離を意識する。

#### 書籍3

- 書籍: Working Effectively with Legacy Code (Michael Feathers)
- 適用方法:
  既存コードへの変更時も、まずテストでカバーし(Red-Green)、その後にリファクタリングする順序を守る。

> ルール: 詳細は references/red-green-refactor.md と references/Level2_intermediate.md を参照。

## 4. 実行仕様

### 4.1 思考プロセス

1. ステップ1: 失敗しているテストを確認する（Red状態の確認）
2. ステップ2: テストを成功させる最も単純な実装を選択する
3. ステップ3: 最小限のコードを追加してテストを実行する
4. ステップ4: テストが成功することを確認する（Green状態への遷移）
5. ステップ5: 次のRefactorフェーズに移るか、新しいテストを追加するか判断する

### 4.2 チェックリスト

- 項目: テストが成功しているか
  - 基準: すべてのテストケースがパスしている
- 項目: 実装は最小限か
  - 基準: テストに必要な機能以外のコードが含まれていない
- 項目: ハードコードや仮実装を含むか
  - 基準: 「Fake It」戦略を使用している場合、次のテストで一般化する計画がある
- 項目: 新しいテストが必要か
  - 基準: 現在の実装が不完全で、追加のテストケースが必要な場合を特定済み
- 項目: コードの重複が生じているか
  - 基準: 重複がある場合、Refactorフェーズでの改善対象として記録済み

### 4.3 ビジネスルール（制約）

- 内容: テストが失敗している状態(Red)から開始すること
- 内容: テストを成功させるために必要最小限のコードのみを追加すること
- 内容: テストが成功した時点でコミット可能な状態であること
- 内容: Refactorフェーズに進む前に、すべてのテストがGreenであることを確認すること

## 5. インターフェース

### 5.1 入力

#### 入力1

- データ名: 失敗しているテストコード
- 提供元: Test Design Task
- 検証ルール:
  テストが実行可能で、実際に失敗していること
- 拒否すべき入力:
  コンパイルエラーのあるテスト、既に成功しているテスト
- 欠損時処理:
  Test Design Taskに再要求

#### 入力2

- データ名: 既存実装コード
- 提供元: 外部（プロジェクトのソースコード）
- 検証ルール:
  既存コードとの整合性が取れていること
- 拒否すべき入力:
  テスト対象とは無関係なコード
- 欠損時処理:
  新規実装として開始

### 5.2 出力

#### 成果物1

- 成果物名: テストが成功する実装コード
- 受領先: Refactoring Task
- 出力テンプレート: 実装コード（言語依存）
- 内容:
  テストを成功させる最小限の実装コード。ハードコードや仮実装を含む場合がある。

#### 成果物2

- 成果物名: 実装メモ
- 受領先: Refactoring Task / Cycle Validation Task
- 出力テンプレート: Markdown形式のメモ
- 内容:
  使用した実装戦略（Fake It / Triangulation / Obvious）、次のステップで改善すべき点、追加すべきテストケースの候補。
