# SkillDocGenerator LLM プロバイダ連携・IPC error contract 教訓

## L-LLM-IPC-001: stub→本番置換パターン

| 項目       | 内容                                                                                                                                                                                                                       |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 課題       | `SkillDocGenerator` の初期実装がスタブ（`LLMClient` 未注入）のままテストされており、本番 `AnthropicProvider` への切替えで挙動差異が検出された                                                                              |
| 解決策     | DI コンストラクタ引数 `llmClient?: ILLMClient` を追加し、テスト時はスタブを注入・本番は `AnthropicProvider` を注入する切替パターンを採用した。スタブはインターフェース準拠の型を持つ最小実装とし、型ドリフトを防ぐ         |
| 標準ルール | `SkillDocGenerator` の統合テストでは「スタブ注入→期待値確認」と「`AnthropicProvider` 注入→呼出し確認」の両ケースを用意する。スタブは必ず `ILLMClient` を `satisfies` またはキャスト不使用で実装し型安全を保つ               |
| 関連タスク | TASK-UT-9I-001                                                                                                                                                                                                             |

## L-LLM-IPC-002: AbortError vs graceful degradation

| 項目       | 内容                                                                                                                                                                                                                       |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 課題       | LLM クエリ中にキャンセルが発生した場合と、プロバイダ内部エラーが発生した場合で処理を統一しようとしたが、abort 系は即時伝播・その他は null 返却という要件が競合した                                                          |
| 解決策     | `try/catch` 内で `error instanceof AbortError` または `error.name === 'AbortError'` を判定し、abort 系は `throw` で即時 rethrow・それ以外は `null` 返却で graceful degradation するパターンを標準化した                    |
| 標準ルール | LLM プロバイダ呼び出しは必ず「AbortError → rethrow / 通常エラー → null 返却 + ログ出力」の2分岐で実装する。呼び出し元は abort エラーを catch して中断フローへ、null を受け取った場合はフォールバック（description 等）を使う |
| 関連タスク | TASK-UT-9I-001, TASK-SC-LLM-PURPOSE-WIRE-001                                                                                                                                                                              |

## L-LLM-IPC-003: LLMDocQueryAdapter DI 設計

| 項目       | 内容                                                                                                                                                                                                                       |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 課題       | `LLMDocQueryAdapter` が `AnthropicProvider` を直接インスタンス化していたため、単体テストで実際の API 呼び出しが発生しテストが不安定になっていた                                                                             |
| 解決策     | コンストラクタ引数 `provider: ILLMProvider` でインターフェースを受け取る DI パターンへ移行。テスト時は `vi.fn()` ベースのモックを注入し、本番は `AnthropicProvider` を Electron main 側でインスタンス化して渡す             |
| 標準ルール | Adapter 層の LLM 依存は必ずコンストラクタ DI で解決し、`new AnthropicProvider()` をアダプタ内部で呼ばない。インターフェース型（`ILLMProvider` 等）をパラメータとして受け取ることで、テスト容易性と本番 DI を両立させる      |
| 関連タスク | TASK-UT-9I-001                                                                                                                                                                                                             |

## L-LLM-IPC-004: IPC error contract 強化

| 項目       | 内容                                                                                                                                                                                                                       |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 課題       | IPC ハンドラが `Error` オブジェクトをそのまま renderer へ送ると、Electron の構造化クローンで `message` しか伝播せず `stack` / `code` 等の付加情報が欠落していた                                                            |
| 解決策     | IPC ハンドラの catch ブロックで `{ success: false, error: { message, code, path } }` 形式の構造化エラーオブジェクトを返すように統一した。AbortError は `code: 'ABORTED'` として構造化し、renderer 側でキャンセルとして扱う |
| 標準ルール | IPC error contract は「構造化エラー path（`{ success, error: { message, code } }`）」と「AbortError 分岐（`code: 'ABORTED'`）」を明記した型定義を `packages/shared/src/ipc/` に配置し、main / preload / renderer の3層で共有する |
| 関連タスク | TASK-UT-9I-001                                                                                                                                                                                                             |
