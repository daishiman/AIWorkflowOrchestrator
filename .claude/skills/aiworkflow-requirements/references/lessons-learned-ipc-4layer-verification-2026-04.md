## L-IPC4L-001: コメント処理はステートマシン方式で文字列リテラル内パターンを保護する

| 項目       | 内容                                                                                                                        |
| ---------- | --------------------------------------------------------------------------------------------------------------------------- |
| 課題       | 正規表現ベースのコメント除去では、文字列リテラル内の `//` や `/*` パターンを誤検出し、有効なコードまで除去してしまう          |
| 解決策     | ステートマシン方式を採用し、文字列リテラル（`'`/`"`/`` ` ``）内かどうかの状態を追跡しながらコメントを判定・除去する           |
| 標準ルール | ソースコードを静的解析するスクリプトでは、正規表現1行置換でなくステートマシン方式のコメント処理を使う                          |
| 関連タスク | UT-IMP-IPC-4LAYER-ALIGNMENT-CI-001                                                                                          |

## L-IPC4L-002: spread/定数参照の解決には `buildConstValueMap()` パターンが有効

| 項目       | 内容                                                                                                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 課題       | `...APPROVAL_CHANNELS` のようなspreadパターンで参照される定数を正しく展開しないと、チャンネル定義の漏れが発生する                                 |
| 解決策     | `buildConstValueMap()` で各ファイル内のconst定義を収集し、spreadパターンを検出した際にマップから展開する（約80行の実装）                            |
| 標準ルール | 静的解析で定数参照やspreadを扱う場合、まずファイル内const→外部importの優先度でマップを構築してから参照解決する                                      |
| 影響範囲   | parsers.test.ts の79テスト中、spread関連テストが複数存在                                                                                          |
| 関連タスク | UT-IMP-IPC-4LAYER-ALIGNMENT-CI-001                                                                                                               |

## L-IPC4L-003: mainハンドラは6パターン対応が必要

| 項目       | 内容                                                                                                                                                           |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 課題       | `ipcMain.handle()` の直接呼び出しだけでなく、DI注入・ラッパー関数・ファクトリパターン・配列スタイル・デコレータ風など、実コードベースには6種類のハンドラ登録がある |
| 解決策     | 各パターンを正規表現で個別にマッチングし、いずれかにマッチすればハンドラとして認識する                                                                           |
| 標準ルール | IPC関連の静的解析では、コードベースの実際の登録パターンを網羅的に調査してからパーサを設計する                                                                     |
| 関連タスク | UT-IMP-IPC-4LAYER-ALIGNMENT-CI-001                                                                                                                             |

## L-IPC4L-004: ローカル定数マップでファイル内const vs 外部importの優先度管理

| 項目       | 内容                                                                                                                                           |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 課題       | 同名の定数がファイル内constと外部importの両方に存在する場合、解決順序を誤るとチャンネル名が不正になる                                            |
| 解決策     | `buildConstValueMap()` でファイル内constを優先し、未解決の場合のみ外部importを参照する2段階解決を実装                                             |
| 標準ルール | 定数解決は「ローカル優先・外部フォールバック」の原則で行い、解決不能な場合はwarningとして報告する                                                  |
| 関連タスク | UT-IMP-IPC-4LAYER-ALIGNMENT-CI-001                                                                                                             |

## L-IPC4L-005: Rule-1/Rule-2のギャップは「スクリプト不具合」ではなく「コードベースの既存ギャップ」

| 項目       | 内容                                                                                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 課題       | 検証スクリプトが検出したRule-1（層間不整合）/Rule-2（未使用チャンネル）のギャップ20件について、スクリプトのバグと誤認しがちだった                           |
| 解決策     | 各ギャップを手動で確認し、実際にコードベース上で定義はあるが使われていない/登録漏れのチャンネルであることを検証。設計制限として文書化した                     |
| 標準ルール | 検証スクリプトの検出結果を「バグ」と断定する前に、コードベース側の実態を確認する。既存ギャップはsuppression listや既知問題として管理する                      |
| 関連タスク | UT-IMP-IPC-4LAYER-ALIGNMENT-CI-001                                                                                                                      |
