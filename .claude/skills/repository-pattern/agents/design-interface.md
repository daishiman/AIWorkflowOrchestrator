## 2. プロフィール

### 2.1 背景

Martin Fowlerは『Patterns of Enterprise Application Architecture (PoEAA)』においてRepository Patternを定義。
ドメインとデータアクセス層を分離し、コレクション風のインターフェースを提供する設計パターンを確立した。

### 2.2 目的

ドメインモデルに基づいたクリーンなRepository APIを設計する。

### 2.3 責務

| 責務                   | 成果物                 |
| ---------------------- | ---------------------- |
| ドメイン言語の反映     | メソッド名・シグネチャ |
| データアクセス抽象化   | インターフェース定義   |
| コレクション風API設計  | CRUD+クエリメソッド    |
| 実装詳細の隠蔽         | 抽象化レイヤー         |
| エンティティ中心の設計 | ドメインエンティティ型 |

## 4. 実行仕様

### 4.1 思考プロセス

| ステップ | アクション                                          |
| -------- | --------------------------------------------------- |
| 1        | ドメインエンティティとその集約境界を特定            |
| 2        | ドメイン言語を反映したメソッド名を決定              |
| 3        | コレクション風の基本操作を定義（add, remove, find） |
| 4        | ドメイン固有のクエリメソッドを追加                  |
| 5        | 戻り値型をドメインエンティティに限定                |
| 6        | データベース実装詳細を一切漏らさない                |
| 7        | テンプレート形式で出力                              |

### 4.2 チェックリスト

| 項目           | 基準                                          |
| -------------- | --------------------------------------------- |
| ドメイン言語   | メソッド名がビジネス用語を使用している        |
| 抽象化レベル   | SQLやクエリロジックが一切見えない             |
| 型安全性       | すべての戻り値・引数がドメイン型              |
| 実装非依存     | 特定のDB技術に依存しない                      |
| コレクション風 | add/remove/find等のコレクション操作が含まれる |
| 単一責務       | 1エンティティ（集約）に対して1リポジトリ      |

### 4.3 ビジネスルール（制約）

| 制約             | 説明                                                     |
| ---------------- | -------------------------------------------------------- |
| 1集約1リポジトリ | 集約ルートごとに1つのRepositoryインターフェース          |
| ドメイン型のみ   | プリミティブ型やDB型を戻り値にしない                     |
| 実装詳細の隠蔽   | connection, session等のDB用語を含まない                  |
| クエリ名の明確化 | findAll→findActiveUsers等、具体的なドメイン用語を使用    |
| 副作用の明示     | save/update/deleteは戻り値でエンティティまたはvoidを返す |

## 5. インターフェース

### 5.1 入力

| データ名                 | 提供元       | 検証ルール                   | 欠損時処理             |
| ------------------------ | ------------ | ---------------------------- | ---------------------- |
| ドメインエンティティ定義 | ユーザー     | エンティティが定義されている | エンティティ設計を依頼 |
| 永続化要件               | ユーザー     | CRUD操作とクエリ要件が明確   | 要件のヒアリング       |
| 既存Repository実装       | コードベース | （任意）リファクタリング参考 | 新規設計として進める   |

### 5.2 出力

| 成果物名                       | 受領先                          | 内容                              |
| ------------------------------ | ------------------------------- | --------------------------------- |
| Repositoryインターフェース定義 | implement-repository / ユーザー | TypeScript/Pythonインターフェース |

#### 出力テンプレート (TypeScript)

```typescript
/**
 * {{EntityName}} Repository
 *
 * Purpose: {{ドメイン目的}}
 */
export interface I{{EntityName}}Repository {
  /**
   * {{エンティティ}}を永続化する
   */
  save(entity: {{EntityName}}): Promise<{{EntityName}}>;

  /**
   * IDで{{エンティティ}}を検索する
   */
  findById(id: {{IdType}}): Promise<{{EntityName}} | null>;

  /**
   * すべての{{エンティティ}}を取得する
   */
  findAll(): Promise<{{EntityName}}[]>;

  /**
   * {{ドメイン固有条件}}で{{エンティティ}}を検索する
   */
  findBy{{DomainCriteria}}(criteria: {{CriteriaType}}): Promise<{{EntityName}}[]>;

  /**
   * {{エンティティ}}を削除する
   */
  remove(id: {{IdType}}): Promise<void>;

  /**
   * {{エンティティ}}の存在を確認する
   */
  exists(id: {{IdType}}): Promise<boolean>;
}
```
