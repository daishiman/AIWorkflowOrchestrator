## L-CI-MEASURE-001: `gh run view --json jobs` 返却フィールドの事前把握

| 項目       | 内容                                                                                                                                                        |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 課題       | CLI `gh run view --json jobs` が `createdAt` フィールドを返さないことを設計段階で把握できていなかった                                                      |
| 症状       | Phase 5 計測フェーズで REST API への手順変更が余儀なくなり、時間損失が発生した                                                                              |
| 解決策     | Phase 2 設計時に `gh run view <run-id> --json jobs \| jq '.[0] \| keys'` で返却フィールドを確認し、REST API 併用要否を事前判定する                          |
| 標準ルール | CI計測テンプレートの Phase 2 に「フィールド確認コマンド」を必須手順として組み込み、`createdAt` 有無によって REST API 使用条件を明記する                      |
| 関連タスク | TASK-CI-FUTURE-005                                                                                                                                          |

## L-CI-MEASURE-002: REST API vs CLI 選択指針の事前記載

| 項目       | 内容                                                                                                                                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 課題       | `gh run view --json jobs` と REST API `/repos/{owner}/{repo}/actions/runs/{run_id}/jobs` のフィールド差異がテンプレートに記載されておらず、実装時に手戻りが発生した                                            |
| 解決策     | CI計測テンプレートに「REST API vs CLI 比較表」を追加し、返却フィールド一覧と差異を明記する                                                                                                                      |
| 標準ルール | Phase 2 設計テンプレートに CLI 実行例と予想返却内容の表を含める。`created_at` / `started_at` / `completed_at` の有無を比較表で示す                                                                               |
| 比較表     | CLI `gh run view --json jobs`: `startedAt` ✅ / `completedAt` ✅ / `createdAt` ❌。REST API jobs endpoint: `created_at` ✅ / `started_at` ✅ / `completed_at` ✅                                                |
| 関連タスク | TASK-CI-FUTURE-005                                                                                                                                                                                              |

## L-CI-MEASURE-003: Python を計算スクリプトの正規手順に採用

| 項目       | 内容                                                                                                                                              |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 症状       | `jq fromdateiso8601` が環境依存（jq バージョン・glibc 対応の差異）で動作不安定な場合がある                                                       |
| 解決策     | Python の `datetime.fromisoformat()` または `dateutil.parser.parse()` で ISO 8601 計算を確実化する                                               |
| コード例   | `python3 -c "from datetime import datetime; print((datetime.fromisoformat('2026-04-15T12:01:00Z'.replace('Z','+00:00')) - datetime.fromisoformat('2026-04-15T12:00:01Z'.replace('Z','+00:00'))).seconds)"` |
| 標準ルール | CI計測タスクテンプレートの計算フェーズ（Phase 5）に Python スクリプト例を含める。jq は補助として可だが正規手順は Python を推奨                    |
| 関連タスク | TASK-CI-FUTURE-005                                                                                                                                |

## L-CI-MEASURE-004: 全シャード計測値の記録と統計サマリーの併記

| 項目       | 内容                                                                                                                                           |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 課題       | 最大キューイング時間だけ記録すると「なぜその値が出たのか」の追跡が困難になる                                                                   |
| 解決策     | 全 17 シャードの `created_at` / `started_at` / キューイング時間を一覧記録し、同時に min/max/avg を統計として付記する                           |
| 効果       | 「シャード 8 番のみ 59 秒、他は 3〜20 秒」という興味深い挙動パターンを可視化でき、将来の最適化の指針になる                                    |
| 標準ルール | `measurement-result.md` テンプレートに「全シャード個別記録表」「統計サマリー（min/max/avg）」「異常値パターン分析」の3セクションを必須化する    |
| 関連タスク | TASK-CI-FUTURE-005                                                                                                                             |

| ---------- | ------------------------------------------------------------------------------------------------------------------------- |

## L-CI-007-001: CI 設定変更タスクの Phase 11 証跡カテゴリ分離

| 項目       | 内容                                                                                                              |
| ---------- | ----------------------------------------------------------------------------------------------------------------- |
| 発見日     | 2026-04-16                                                                                                        |
| 背景       | TASK-CI-FUTURE-007 の Phase 11 で「CLI 実行確認」と「YAML 静的確認（workflow-static-check）」が混在し、信頼性が曖昧になった |
| 問題       | CI 設定変更タスクでは実際の CI ログが取れない項目があり、「実行済み」と「静的に確認済み」を同列に記録すると証跡の信頼性が不明確になる |
| 解決策     | Phase 11 証跡を 2 カテゴリに分離して記録する: `CLI 実行確認`（ローカル実行で確認済み）/ `workflow-static-check`（YAML ロジックを静的に確認） |
| 標準ルール | `workflow-static-check` 項目は「観測待ち（CI 実行後に確認が必要）」としてラベルを付け、将来の CI 実行時の再検証対象として明示する |
| 関連タスク | TASK-CI-FUTURE-007                                                                                                |

## L-CI-007-002: CI 設定追加項目での変更対象と参照対象の分離

| 項目       | 内容                                                                                                                         |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 発見日     | 2026-04-16                                                                                                                   |
| 背景       | TASK-CI-FUTURE-007 で `backend` flag を Codecov に追加する際、「どのファイルを変更するか」と「flag がどのパスを参照するか」が混在して記録された |
| 問題       | 設定追加項目（flag・path・carryforward 等）を変更ファイルと同列に書くと、「変更したもの」と「設定値として参照するもの」の区別が読者に伝わらない |
| 解決策     | system-spec-update-summary.md の実装正本テーブルを「変更対象ファイル（YAML/設定ファイル）」と「設定追加内容（flag 名・path・carryforward 値）」に分けて記載する |
| 標準ルール | flag 追加・path 設定・carryforward 設定は「参照対象」列に分離し、「変更対象」列はファイルパスのみを記載する              |
| 関連タスク | TASK-CI-FUTURE-007                                                                                                           |
